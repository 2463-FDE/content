## Claims (each MUST carry a source)

- ReAct interleaves free-form **reasoning traces** ("thoughts") with **task-specific actions** in a single loop: thoughts induce, track, and update action plans and handle exceptions, while actions interface with external sources (e.g., a Wikipedia API) to gather observations that feed the next thought. The unit is a Thought → Action → Observation cycle repeated until the model emits a finish action. — [ReAct: Synergizing Reasoning and Acting in Language Models (arXiv 2210.03629)](https://arxiv.org/abs/2210.03629)
- ReAct "overcomes issues of hallucination and error propagation prevalent in chain-of-thought reasoning by interacting with a simple Wikipedia API, and generates human-like task-solving trajectories that are more interpretable than baselines without reasoning traces" — i.e., grounding each reasoning step in a real observation is what curbs hallucination, and the visible trace is what makes the agent debuggable. — [ReAct (arXiv 2210.03629)](https://arxiv.org/abs/2210.03629)
- ReAct was validated across two distinct task families: knowledge-intensive reasoning (HotpotQA multi-hop QA, FEVER fact verification) and interactive decision-making (ALFWorld, WebShop) — establishing the reason+act pattern as general rather than task-specific. — [ReAct (arXiv 2210.03629)](https://arxiv.org/abs/2210.03629)
- Every agentic system is built on the same primitive Anthropic calls the **augmented LLM**: an LLM enhanced with retrieval, tools, and memory that the model itself drives (generating its own search queries, selecting tools, deciding what to retain). — [Building effective agents — Anthropic](https://www.anthropic.com/research/building-effective-agents)
- Anthropic draws a hard architectural line between **workflows** ("systems where LLMs and tools are orchestrated through predefined code paths") and **agents** ("systems where LLMs dynamically direct their own processes and tool usage, maintaining control over how they accomplish tasks"). Named workflow patterns are prompt chaining, routing, parallelization, orchestrator-workers, and evaluator-optimizer; agents are reserved for when you cannot hardcode the path but can still verify progress. — [Building effective agents — Anthropic](https://www.anthropic.com/research/building-effective-agents)
- Anthropic's core guidance is anti-complexity: "Start with simple prompts, optimize them with comprehensive evaluation, and add multi-step agentic systems only when simpler solutions fall short," and it is "crucial for the agents to gain 'ground truth' from the environment at each step (such as tool call results or code execution) to assess its progress" — the same observation-grounding principle as ReAct, applied to production agents. — [Building effective agents — Anthropic](https://www.anthropic.com/research/building-effective-agents)
- **Provider-native tool use is a contract, not model-side execution:** "The model never executes anything on its own. It emits a structured request, your code (or Anthropic's servers) runs the operation, and the result flows back into the conversation." You define a tool by name, description, and `input_schema` (JSON Schema); Claude replies with `stop_reason: "tool_use"` and one or more `tool_use` blocks; your app runs the operation and returns a `tool_result` block. — [How tool use works — Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)
- The **agentic loop** for client tools is a `while` loop keyed on `stop_reason`: (1) send request with `tools` + user message; (2) Claude returns `stop_reason: "tool_use"` and `tool_use` block(s); (3) execute each tool, format outputs as `tool_result` blocks; (4) send a new request with the original messages, the assistant response, and the `tool_result` blocks; (5) repeat while `stop_reason == "tool_use"`. The loop exits on any other stop reason (`end_turn`, `max_tokens`, `stop_sequence`, `refusal`). — [How tool use works — Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)
- Claude distinguishes **client tools** (user-defined, plus Anthropic-schema `bash`/`text_editor`/`memory`/`computer` — your code executes and returns `tool_result`) from **server tools** (`web_search`, `web_fetch`, `code_execution`, `tool_search` — Anthropic runs the code, the server-side loop iterates internally, and you never construct a `tool_result`). A server-side loop that hits its iteration cap returns `stop_reason: "pause_turn"`, which you continue by re-sending the conversation. — [How tool use works — Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/how-tool-use-works)
- `tool_choice` steers whether the model may/must call a tool. Claude's options are `auto` (default — model decides each turn), `any` (must call some tool), `tool` (must call a named tool), and `none` (no tools); adding `strict: true` to a custom tool definition guarantees the emitted arguments conform to your schema. — [Tool use overview — Claude docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview)
- OpenAI's Responses API implements the same pattern under the name **function calling**: tools are `{"type": "function", "name", "description", "parameters"}` (JSON Schema); "OpenAI's model does not execute your function — it only decides which function should be called and what arguments to pass," returning a function call with `name` + JSON `arguments`; your app executes and returns a `function_call_output` item carrying the `call_id` and `output`, then the loop continues. `tool_choice` accepts `auto` (default), `required`, a named function, or `none`, and `strict: true` enforces schema-conformant arguments. — [Function calling — OpenAI API](https://developers.openai.com/api/docs/guides/function-calling)

## Concepts

- `react-loop` — The Thought → Action → Observation cycle from the ReAct paper: the model writes a reasoning trace, emits an action against an external tool/environment, reads the returned observation, and repeats until a finish action. Grounding each step in a real observation is what distinguishes it from pure chain-of-thought and what reduces hallucination and error propagation.
- `augmented-llm` — Anthropic's foundational building block for all agentic systems: a base LLM enhanced with retrieval, tools, and memory that the model itself drives (writing its own queries, choosing tools, managing what to retain). Every workflow or agent is composed of augmented-LLM calls.
- `workflow-vs-agent` — The architectural distinction between **workflows** (LLMs + tools orchestrated through predefined, developer-authored code paths — predictable, e.g., prompt chaining, routing, orchestrator-workers) and **agents** (the LLM dynamically directs its own control flow and tool usage). Agents trade predictability for flexibility and are reserved for tasks whose path cannot be hardcoded but whose progress can still be verified.
- `tool-calling-loop` — The provider-native agentic loop: a host-side `while` loop keyed on the response `stop_reason`. While the model returns `tool_use` (Claude) / a function call (OpenAI), the application executes the requested tool, feeds the result back as `tool_result` / `function_call_output`, and re-invokes the model; the loop terminates on a non-tool stop reason (`end_turn`, `max_tokens`, etc.).
- `tool-use-contract` — The client/model division of labor: the model never runs code, it only emits a structured, schema-validated request (`tool_use` block / function call with `name` + JSON args); the application (or the provider's server, for server tools) executes and returns a typed result. Tools are defined by name, description, and a JSON-Schema input spec; `strict` mode guarantees arguments match that schema.
- `tool-choice` — The request parameter controlling whether and which tool the model may call: Claude's `auto`/`any`/`tool`/`none` and OpenAI's `auto`/`required`/named-function/`none`. `auto` lets the model decide per turn; the forcing modes guarantee a (specific) tool call — the primary knob for steering an agent between "answer directly" and "always act."
