## Shared lead-in — GenAI semantic conventions as the backend-neutral contract

Both providers document the OpenTelemetry GenAI semantic conventions as the span
vocabulary they ingest, and differ only in the export target:

- AWS (https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-configure.html): "When you use agent frameworks like Strands, LangChain, or CrewAI with supported third-party instrumentation libraries, the framework itself comes with built in support for OTEL and GenAI semantic conventions, and it can also be instrumented with an auto-instrumentation package such as opentelemetry-instrument-langchain." Supported libraries: "OpenInference, Openllmetry, OpenLit, Traceloop".
- GCP (https://docs.cloud.google.com/stackdriver/docs/instrumentation/ai-agent-overview, "Last updated 2026-10-09 UTC"): "Cloud Trace automatically extracts events from spans written by generative AI applications when those spans conform to the semantic conventions for spans and events." "We recommend that you instrument your application with OpenTelemetry".
- Lesson claim derived: one set of spans, exported to a provider-chosen target. Trace/span framing from the GCP tracing page below: "A trace is composed of individual spans, which represent a single unit of work, like a function call or an interaction with an LLM, with the first span representing the overall request." AWS: AgentCore Observability offers "detailed visualizations of each step in the agent workflow". "Instrument early" is the lesson's own practice advice, not a provider claim.

## AWS — ADOT → CloudWatch / X-Ray, AgentCore Observability

Source: https://docs.aws.amazon.com/xray/latest/devguide/xray-services-adot.html

- "The AWS Distro for OpenTelemetry (ADOT) is an AWS distribution based on the Cloud Native Computing Foundation (CNCF) OpenTelemetry project … a distribution of upstream OpenTelemetry components including SDKs, auto-instrumentation agents, and collectors that are tested, optimized, secured, and supported by AWS."
- "Use the AWS Distro for OpenTelemetry (ADOT) to collect and send metrics and traces to AWS X-Ray and other monitoring solutions, such as Amazon CloudWatch".

Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html

- "AgentCore Observability helps you trace, debug, and monitor agent performance in production environments."
- "dashboards powered by Amazon CloudWatch and telemetry for key metrics such as session count, latency, duration, token usage, and error rates." "AgentCore emits telemetry data in standardized OpenTelemetry (OTEL)-compatible format".
- "All of the metrics, spans, and logs output by AgentCore are stored in Amazon CloudWatch".

Source: https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-configure.html

- "To view metrics, spans, and traces generated by the AgentCore service, you first need to complete a one-time setup to turn on Amazon CloudWatch Transaction Search."
- "To view this data in the CloudWatch console generative AI observability page and in Amazon CloudWatch, you need to add the AWS Distro for Open Telemetry (ADOT) SDK to your agent code." Steps: `aws-opentelemetry-distro` in requirements; "Execute your agent code using the OpenTelemetry auto-instrumentation command: opentelemetry-instrument python my_agent.py"; container form `CMD ["opentelemetry-instrument", "python", "main.py"]`.
- Outside the runtime: "To enable observability for agents hosted outside of the AgentCore runtime, first follow the steps in the previous sections to enable CloudWatch Transaction Search and add the ADOT SDK to your code." Lambda: "use the AWS Lambda Layer for OpenTelemetry".
- "The ADOT Collector is not supported for agent observability. To send telemetry from an agent hosted outside of AgentCore runtime, you must use either the ADOT SDK or the AWS Lambda Layer for OpenTelemetry." (AWS check: correct answer; ECS is the lesson's hypothetical host.)

Background only (not cited in Sources): https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch-OTLPEndpoint.html — CloudWatch exposes OTLP HTTP endpoints for logs, metrics and traces.

## GCP — OTLP → Cloud Trace, Agent Runtime tracing

Source: https://docs.cloud.google.com/stackdriver/docs/reference/telemetry/overview ("Last updated 2026-10-09 UTC")

- "the Telemetry (OTLP) API, which implements the OpenTelemetry Protocol … designed for use with applications that are instrumented by using one of the OpenTelemetry SDKs or that use any OpenTelemetry Collector."
- "we recommend that you use an exporter that writes OTLP-formatted data to an Collector, which then sends your trace data to the Telemetry API." Collector config `endpoint: https://telemetry.googleapis.com`. "When you can't use a collector, you can use an OpenTelemetry library that contains an in-process OTLP exporter".

Source: https://docs.cloud.google.com/trace/docs/migrate-to-otlp-endpoints ("Last updated 2026-10-09 UTC")

- A Google Cloud exporter "Transforms the recorded data from OTLP format into a proprietary format defined by … the Cloud Trace API." "For trace data, we recommend that you migrate your application to use the Telemetry (OTLP) API … because this export doesn't require a data transformation. Data transformation might cause loss of some data." (GCP check: correct answer; GKE is the lesson's hypothetical host.)

Source: https://docs.cloud.google.com/stackdriver/docs/instrumentation/ai-agent-overview ("Last updated 2026-10-09 UTC")

- "when your instrumentation sends telemetry to your Google Cloud project, you can use Google Cloud Observability to view and analyze that data." Event extraction from GenAI-convention spans (quoted above).
- "We also recommend that you store your prompts and responses in a Cloud Storage bucket instead of in a log entry"; log entry maximum 256 KiB; "Cloud Logging truncates that data" when fields exceed limits. (GCP check: log-entry distractor.)

Source: https://docs.cloud.google.com/gemini-enterprise-agent-platform/scale/runtime/tracing (title "Set up tracing"; "Last updated 2026-10-13 UTC"; the former `cloud.google.com/vertex-ai/generative-ai/docs/agent-engine/manage/tracing` URL redirects into the Agent Platform docs)

- ADK: "To enable OpenTelemetry for AdkApp, set the following environment variables when you deploy the agent to Agent Runtime": `GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY=true`, `OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental` ("enables use of the latest generative AI semantic conventions"), `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT` ("enables the logging of input prompts, output responses, and user IDs").
- "GOOGLE_CLOUD_AGENT_ENGINE_ENABLE_TELEMETRY enables the agent traces, logs, and metrics … but doesn't include prompts and response data." "To use trace ingestion, you need to enable the Telemetry API."
- "To enable tracing for LangchainAgent, specify enable_tracing=True"; same for LanggraphAgent. "This exports traces to Cloud Trace".
- Naming: the lesson writes "Agent Runtime (formerly Agent Engine)" per the program's naming rule; the evidence on the page is the Agent Runtime product name alongside the retained `AGENT_ENGINE` environment-variable name.

Supporting (not cited in Sources): https://docs.cloud.google.com/gemini-enterprise-agent-platform/optimize/observability/overview — "your agents must be configured to send telemetry data in the OpenTelemetry format to storage systems in Google Cloud Observability."
