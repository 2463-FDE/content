Scope note: this day is **agent memory only** — the working/short-term vs long-term
distinction and the stores behind each. The ReAct loop (w03d1), tools & MCP (w03d2),
and framework comparison (w03d3) are covered elsewhere; LangGraph persistence /
checkpointers as a subsystem is a W4 topic. Here the checkpointer is mentioned only as
the *mechanism* that backs short-term memory.

## Concept IDs

These seed the interview question bank. Each is addressable by ID.

- `short-term-memory` — Thread-scoped "working" memory: the ongoing conversation's
  message history within a single session/thread. It is part of the agent's runtime
  state and is bounded by the LLM's context window, so it needs trimming/summarization
  as it grows. (LangGraph backs it with a checkpointer; the OpenAI Agents SDK backs it
  with a Session.)
- `long-term-memory` — Persistent memory that lives **outside** any single thread and
  **outside** the context window, recallable at any time and in any thread/session.
  Stored in an external store and retrieved on demand rather than always being present.
- `memory-store` — The persistent, cross-thread key/value store that holds long-term
  memories (LangGraph's `BaseStore`), organized by a custom `namespace` (like a folder,
  e.g. a user or org ID) and a `key` (like a filename). Distinct from the checkpointer,
  which only persists within-thread state.
- `memory-type-taxonomy` — The semantic / episodic / procedural split borrowed from
  human psychology: **semantic** = facts and concepts; **episodic** = past events and
  experiences; **procedural** = the rules/instructions for performing tasks (prompt +
  code + weights).
- `virtual-context-management` — MemGPT's OS-analogy pattern: treat the context window
  as "main context" (RAM, in-context) and external stores as "external context" (disk,
  out-of-context), with the LLM issuing function/tool calls to page data between them —
  the conceptual foundation for LLM-managed long-term memory.

## Claims (each MUST carry a source)

- Short-term memory is thread-scoped: it "tracks the ongoing conversation by maintaining
  message history within a session," is managed as part of the agent's LangGraph state,
  and is persisted by a checkpointer. — [Memory overview - Docs by LangChain](https://docs.langchain.com/oss/python/concepts/memory)
- Long-term memory "stores user-specific or application-level data across sessions and is
  shared across conversational threads"; it "can be recalled at any time and in any
  thread" and is "scoped to any custom namespace, not just within a single thread ID." —
  [Memory overview - Docs by LangChain](https://docs.langchain.com/oss/python/concepts/memory)
- Long-term memories are organized under a custom `namespace` (similar to a folder) and a
  distinct `key` (like a file name); namespaces typically include user or org IDs to
  organize information hierarchically. — [Memory overview - Docs by LangChain](https://docs.langchain.com/oss/python/concepts/memory)
- The three memory types are semantic (retention of specific facts and concepts),
  episodic (recalling past events/experiences), and procedural (remembering the rules
  used to perform tasks — for an agent, "a combination of model weights, agent code, and
  agent's prompt"); the distinction is that "facts can be written to semantic memory,
  whereas experiences can be written to episodic memory." — [Memory overview - Docs by LangChain](https://docs.langchain.com/oss/python/concepts/memory)
- A core short-term-memory challenge is that the "full history may not fit inside an LLM's
  context window," which motivates techniques to trim or summarize (forget stale
  information) to manage token usage and performance. — [Memory overview - Docs by LangChain](https://docs.langchain.com/oss/python/concepts/memory)
- MemGPT proposes "virtual context management, a technique drawing inspiration from
  hierarchical memory systems in traditional operating systems," to work around the
  fixed LLM context window — analogous to OS virtual memory paging between fast and slow
  storage. — [MemGPT: Towards LLMs as Operating Systems (arXiv:2310.08560)](https://arxiv.org/abs/2310.08560)
- MemGPT splits memory into **main context** (the LLM prompt tokens — "anything in main
  context is considered in-context," analogous to RAM) and **external context**
  ("out-of-context data must always be explicitly moved into main context," analogous to
  disk). — [MemGPT: Towards LLMs as Operating Systems (ar5iv)](https://ar5iv.labs.arxiv.org/html/2310.08560)
- MemGPT's main context has three sections — read-only system instructions, a fixed-size
  read/write **working context** block editable only via function calls, and a **FIFO
  queue** holding a rolling message history — while external context is split into
  **recall storage** (conversation-history database) and **archival storage** (a
  read/write database of arbitrary-length text). — [MemGPT: Towards LLMs as Operating Systems (ar5iv)](https://ar5iv.labs.arxiv.org/html/2310.08560)
- In MemGPT, "memory edits and retrieval are entirely self-directed": the LLM
  autonomously issues function calls to move data between main context and external
  context, i.e. the model manages its own memory. — [MemGPT: Towards LLMs as Operating Systems (ar5iv)](https://ar5iv.labs.arxiv.org/html/2310.08560)
- The OpenAI Agents SDK provides Sessions as automatic short-term/conversational memory:
  before each run "the runner automatically retrieves the conversation history for the
  session and prepends it," and after each run "all new items generated during the run
  … are automatically stored," eliminating manual `.to_input_list()` handling between
  turns. — [Sessions - OpenAI Agents SDK](https://openai.github.io/openai-agents-python/sessions/)
- OpenAI Sessions ship multiple pluggable backends — SQLite (default, file or in-memory),
  Redis, SQLAlchemy, MongoDB, Dapr, and OpenAI-hosted Conversations storage — so
  short-term memory can scale from a local file to a production datastore without
  changing agent code. — [Sessions - OpenAI Agents SDK](https://openai.github.io/openai-agents-python/sessions/)
- Anthropic's memory tool "lets Claude store and retrieve information across
  conversations in a directory of memory files," building up knowledge over time "without
  keeping everything in the context window" — an explicit long-term-memory mechanism
  distinct from the in-context conversation. — [Memory tool - Claude Platform Docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- The memory tool is client-side: Claude only *requests* file operations (view, create,
  str_replace, insert, delete, rename) under a `/memories` prefix, and the application
  executes them against storage it controls; it is generally available (tool type
  `memory_20250818`, no beta header) on all Claude 4+ models. — [Memory tool - Claude Platform Docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- The memory tool pairs with context editing and server-side compaction: for
  long-running agents "compaction keeps the active context small … and memory preserves
  the information that must survive summarization" — showing short-term (context) and
  long-term (memory files) management are complementary, not interchangeable. — [Memory tool - Claude Platform Docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
