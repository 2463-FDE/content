## Claims

### 1. MCP is an open standard that gives LLM apps a uniform interface to external tools and context — the "USB-C port for AI."
MCP is "an open-source standard for connecting AI applications to external systems," connecting them to data sources, tools, and workflows. The official framing: "Think of MCP like a USB-C port for AI applications. Just as USB-C provides a standardized way to connect electronic devices, MCP provides a standardized way to connect AI applications to external systems." It replaces per-integration custom code with one protocol.
- [What is the Model Context Protocol (MCP)? — modelcontextprotocol.io](https://modelcontextprotocol.io/docs/getting-started/intro)
- [Introducing the Model Context Protocol — Anthropic (2024-11-25)](https://www.anthropic.com/news/model-context-protocol)

### 2. MCP was introduced and open-sourced by Anthropic on 2024-11-25 to kill the fragmented-integration ("N×M") problem.
Anthropic describes AI assistants as "constrained by their isolation from data—trapped behind information silos and legacy systems," and MCP as "a universal, open standard for connecting AI systems with data sources, replacing fragmented integrations with a single protocol." Build once against the protocol instead of one bespoke connector per data source.
- [Introducing the Model Context Protocol — Anthropic (2024-11-25)](https://www.anthropic.com/news/model-context-protocol)

### 3. Architecture is host / client / server, built on JSON-RPC 2.0, with a 1:1 client-to-server relationship.
MCP "follows a client-host-server architecture where each host can run multiple client instances." The **host** is the LLM application (coordinator, enforces consent/security, coordinates sampling); each **client** "maintains an isolated server connection" with "a 1:1 relationship with a particular server"; **servers** "expose resources, tools and prompts via MCP primitives." Messaging uses "JSON-RPC 2.0 messages." It is inspired by the Language Server Protocol (LSP): standardize one integration surface across a whole ecosystem.
- [Architecture — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/architecture)
- [Specification overview — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25)

### 4. The three server primitives split by *who controls them*: Tools (model-controlled), Resources (application-controlled context/data), Prompts (user-controlled templates).
Servers offer: "**Resources**: Context and data, for the user or the AI model to use"; "**Prompts**: Templated messages and workflows for users"; "**Tools**: Functions for the AI model to execute." Tools specifically "are designed to be **model-controlled**, meaning that the language model can discover and invoke tools automatically." This control-model distinction is the load-bearing mental model for the day.
- [Specification overview — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25)
- [Server / Tools — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

### 5. Clients expose three server-initiated primitives back to servers: Sampling, Roots, Elicitation.
"Clients may offer the following features to servers: **Sampling** (server-initiated agentic behaviors and recursive LLM interactions); **Roots** (server-initiated inquiries into URI or filesystem boundaries to operate in); **Elicitation** (server-initiated requests for additional information from users)." These are negotiated via capabilities — e.g. sampling "requires the client to declare support in its capabilities."
- [Specification overview — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25)
- [Architecture / Capability Negotiation — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/architecture)

### 6. Tool discovery + invocation are `tools/list` and `tools/call`; the Tool object carries `name`, `inputSchema` (JSON Schema), optional `outputSchema`, `title`, `description`, `annotations`.
Clients "send a `tools/list` request" (paginated via cursor) to discover tools, then "send a `tools/call` request" with `name` + `arguments`. A Tool definition includes `name` (unique id), `description`, `inputSchema` ("**MUST** be a valid JSON Schema object," defaults to JSON Schema 2020-12), optional `outputSchema`, optional `title`, and optional `annotations`. When the tool list changes, a server that declared `listChanged` **SHOULD** send `notifications/tools/list_changed`.
- [Server / Tools — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

### 7. Tool results carry `content` (text/image/audio/resource_link/embedded resource) and optional `structuredContent` validated against `outputSchema`.
Unstructured results go in the `content` array (multiple typed items). Structured results go in `structuredContent` as a JSON object; "For backwards compatibility, a tool that returns structured content SHOULD also return the serialized JSON in a TextContent block." If a tool declares an `outputSchema`, "Servers **MUST** provide structured results that conform to this schema" and "Clients **SHOULD** validate structured results against this schema."
- [Server / Tools — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

### 8. Two distinct error channels: JSON-RPC protocol errors vs. tool-execution errors (`isError: true`) — and the difference is pedagogically important.
Protocol errors (unknown tool, malformed request, server error) are standard JSON-RPC `error` objects. Tool execution errors are returned in a *successful* result with `isError: true` inside the result. Rationale from the spec: "**Tool Execution Errors** contain actionable feedback that language models can use to self-correct and retry with adjusted parameters," and "Clients **SHOULD** provide tool execution errors to language models to enable self-correction." Business-logic/validation failures belong in `isError`, not JSON-RPC errors.
- [Server / Tools (Error Handling) — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

### 9. Two standard transports: **stdio** (local subprocess over stdin/stdout) and **Streamable HTTP** (single endpoint, POST + optional SSE). Streamable HTTP replaced the deprecated HTTP+SSE transport.
"The protocol currently defines two standard transport mechanisms: stdio ... and Streamable HTTP." In stdio "the client launches the MCP server as a subprocess" exchanging newline-delimited JSON-RPC over stdin/stdout; "Clients **SHOULD** support stdio whenever possible." In the 2025-11-25 baseline, Streamable HTTP uses "a single HTTP endpoint path" supporting POST and GET, optionally upgrading to Server-Sent Events, and "replaces the HTTP+SSE transport from protocol version 2024-11-05." HTTP clients must send `MCP-Protocol-Version: <revision>` on every request; sessions may be tracked via the `MCP-Session-Id` header.
- [Basic / Transports — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

### 10. Tools are arbitrary code execution — the spec mandates human-in-the-loop and treats tool annotations as untrusted.
"Tools represent arbitrary code execution and must be treated with appropriate caution." The spec requires: "there **SHOULD** always be a human in the loop with the ability to deny tool invocations," hosts "**MUST** obtain explicit user consent before invoking any tool," and — a common footgun — "clients **MUST** consider tool annotations to be untrusted unless they come from trusted servers." Streamable HTTP servers "**MUST** validate the `Origin` header ... to prevent DNS rebinding attacks" and "**SHOULD** bind only to localhost" when local.
- [Specification overview (Security & Trust) — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25)
- [Server / Tools (Security) — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)
- [Basic / Transports (Security Warning) — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

### 11. Capabilities are negotiated at init — a feature is only usable if declared. This is how MCP stays extensible and backward-compatible.
MCP "uses a capability-based negotiation system where clients and servers explicitly declare their supported features during initialization. Capabilities determine which protocol features and primitives are available." E.g. tool support requires the server to declare the `tools` capability (`{"capabilities":{"tools":{"listChanged":true}}}`); resource subscription notifications require declaring subscription support. "Features can be added to servers and clients progressively."
- [Architecture / Capability Negotiation — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/architecture)
- [Server / Tools (Capabilities) — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

### 12. The 2026-07-28 revision is published; 2025-11-25 remains the deployed compatibility baseline.
The official site labels **2026-07-28 as latest**. Its transport overview still names **stdio** and **Streamable HTTP**; Streamable HTTP carries each message as an HTTP POST to a single MCP endpoint and may return a request-scoped SSE stream. The revision also documents backward compatibility with earlier connection-scoped, `initialize`-handshake revisions. That makes the lesson's architecture useful when labeled precisely: teach the 2026-07-28 revision as latest, and teach 2025-11-25 initialization/capability mechanics as a widely deployed baseline learners will still support. Streamable HTTP still replaces the deprecated 2024-11-05 HTTP+SSE design.
- [Transport overview — MCP spec 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports) — accessed 2026-09-25.
- [Streamable HTTP — MCP spec 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) — accessed 2026-09-25; single endpoint, Origin validation, and localhost binding.
- [Versioning and backward compatibility — MCP spec 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) — accessed 2026-09-25.
- [Basic / Transports — MCP spec 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) — accessed 2026-09-25; deployed baseline and HTTP+SSE replacement.
