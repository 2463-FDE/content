## Claims (each MUST carry a source)

### StateGraph & state

- A `StateGraph` is defined by a **state schema** — a `TypedDict`, Pydantic `BaseModel`, or dataclass — and "the schema of the State will be the input schema to all Nodes and Edges in the graph." Nodes are plain functions that receive the current state and return **partial state updates**; "Nodes and Edges are nothing more than functions—they can contain an LLM or just good ol' code." — [Graph API — Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/graph-api)
- Every state key has an independent **reducer** that determines how a node's returned update is merged into state. The default reducer **overwrites** the value; custom reducers are attached via `Annotated` type hints (e.g., `operator.add` to append to lists), and the prebuilt `add_messages` reducer handles message lists with ID-based updates and deserialization. — [Graph API — Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/graph-api)
- Control flow: **normal edges** route directly between nodes; **conditional edges** call a routing function that returns target node names; `START`/`END` are virtual entry/terminal nodes; `Command` lets a node combine a state update with a routing decision, and `Send` supports dynamic fan-out with different state per target. "You MUST compile your graph before you can use it" — `.compile()` validates the structure and is where runtime configuration like a checkpointer is applied. — [Graph API — Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/graph-api)

### Checkpointers, threads & persistence

- **Checkpointers persist a thread's graph state as checkpoints** — snapshots of graph state — providing "short-term, thread-scoped memory." The `thread_id` passed in the graph config identifies which conversation/task the checkpoints belong to; persistence is what enables conversation continuity, human-in-the-loop workflows, time travel, and fault tolerance. (**Stores**, by contrast, hold application-defined key-value data for long-term, **cross-thread** memory — a separate concept from checkpointing.) — [Persistence — Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/persistence)
- Practical limits from the official docs: keep `thread_id` under 255 characters (Postgres column limit), expect checkpoints to **accumulate** over long conversations (latency + storage cost — prune), and note that **subgraphs checkpoint under their own namespace**, so a parent graph does not immediately observe child state updates. — [Persistence — Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/persistence)
- The checkpointer contract is `BaseCheckpointSaver`: `put` (store a checkpoint), `put_writes` (store pending writes), `get_tuple` (fetch a checkpoint), `list` (enumerate checkpoints), `delete_thread` (drop a thread), plus `a`-prefixed async variants. Shipped implementations: `InMemorySaver` (`langgraph-checkpoint`, dev/testing — lost on restart), `SqliteSaver`/`AsyncSqliteSaver` (`langgraph-checkpoint-sqlite`, demos/non-production), `PostgresSaver`/`AsyncPostgresSaver` (`langgraph-checkpoint-postgres`, production). Default serialization is `JsonPlusSerializer` (ormsgpack with JSON fallback); wrap with `EncryptedSerializer` for checkpoint encryption at rest. — [checkpoints — LangChain Reference](https://reference.langchain.com/python/langgraph/checkpoints)

### Durability modes

- Checkpoint write timing is tunable per invocation via `Durability = Literal['sync', 'async', 'exit']`: `'sync'` — "changes are persisted synchronously before the next step starts" (most durable, slowest); `'async'` — "changes are persisted asynchronously while the next step executes" (good balance; small crash window); `'exit'` — "changes are persisted only when the graph exits" (fastest; no mid-run crash recovery). Passed as e.g. `graph.stream(input, config, durability="sync")`. — [Durability — LangChain Reference](https://reference.langchain.com/python/langgraph/types/Durability)

### Human-in-the-loop: interrupt & resume

- `interrupt()` pauses graph execution by **raising a special exception** the runtime catches; the graph state is saved via the checkpointer and the interrupt payload is surfaced to the caller. **A checkpointer is mandatory** for interrupts — "state is saved using the checkpointer so execution can be resumed later." — [Interrupts — Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/interrupts)
- Resume by re-invoking the graph with `Command(resume=...)` on the **same `thread_id`**; the resume value "becomes the return value of the `interrupt()` call" inside the node. The thread ID is "your persistent cursor": reusing it resumes the same checkpoint, a new value starts a fresh thread with empty state. `Command(resume=...)` is the **only** `Command` pattern intended as input to `invoke()`/`stream()`. — [Interrupts — Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/interrupts)
- Critical resume semantics: on resume "the runtime restarts the **entire node from the beginning** — it does not resume from the exact line where `interrupt` was called." Consequences the docs call out: code before `interrupt()` runs multiple times and must be **idempotent**; never wrap `interrupt()` in a bare `try/except` (it swallows the control-flow exception); multiple interrupts in one node are matched to resume values **strictly by index**, so their order must stay consistent across executions. — [Interrupts — Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/interrupts)
- Canonical HITL patterns from the docs: **approval workflows** (approve/reject before a sensitive action), **state review & editing**, **tool-call review** (inspect/correct an agent's tool call before execution), and **input validation** — with validation loops built via conditional edges rather than loops inside a node. — [Interrupts — Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/interrupts)

### Time travel: replay & fork

- `get_state_history(config)` returns prior checkpoints in reverse chronological order, each carrying a `checkpoint_id` in its `config["configurable"]`. Invoking the graph with a prior checkpoint's config **replays**: nodes before that checkpoint are not re-run (results come from the checkpoint), nodes after it re-execute completely — "replay re-executes nodes—it doesn't just read from cache. LLM calls, API requests, and interrupts fire again and may return different results." — [Use time travel — Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/use-time-travel)
- `update_state` **forks** a thread: "it creates a new checkpoint that branches from the specified point. The original execution history remains intact." Then `invoke(None, config)` continues execution from the fork with the modified state. The `as_node` parameter attributes the update to a specific node's writes, so the graph resumes from that node's successors — usable to skip nodes or disambiguate parallel branches. — [Use time travel — Docs by LangChain](https://docs.langchain.com/oss/python/langgraph/use-time-travel)

## Concepts

- `stategraph-state-reducers` — Defining a StateGraph's state schema (TypedDict / Pydantic / dataclass) and per-key reducers: default overwrite vs. `Annotated` custom reducers (`operator.add`, `add_messages`); nodes return partial updates merged by each key's reducer; `START`/`END`, conditional edges, and mandatory `.compile()`.
- `checkpointer-thread-persistence` — The persistence model: a checkpointer saves a snapshot (checkpoint) of graph state per super-step, scoped to a `thread_id`; threads are the unit of conversation/task isolation, and persistence is what unlocks continuity, HITL, time travel, and fault tolerance. Distinct from cross-thread Stores.
- `checkpointer-backends` — The `BaseCheckpointSaver` contract (`put`/`put_writes`/`get_tuple`/`list`/`delete_thread` + async variants) and its implementations: `InMemorySaver` (dev), `SqliteSaver` (demos), `PostgresSaver`/`AsyncPostgresSaver` (production), plus `JsonPlusSerializer` and `EncryptedSerializer`.
- `durability-modes` — The `sync` / `async` / `exit` durability setting controlling when checkpoints are written relative to step execution, trading crash-recoverability against throughput; chosen per `invoke`/`stream` call.
- `interrupt-command-resume` — Human-in-the-loop pause/resume: `interrupt()` raises a runtime-caught exception, persists state through the checkpointer, and surfaces a payload; `Command(resume=...)` on the same thread re-enters the node **from the top** (idempotent pre-interrupt code, no bare try/except, index-based matching for multiple interrupts).
- `time-travel-fork` — Inspecting and rewriting history: `get_state_history` + `checkpoint_id` to replay from a prior checkpoint (later nodes genuinely re-execute), and `update_state` (with `as_node`) to fork a new branch while the original history stays intact.
