# w04d4 — Neo4j knowledge-graph modeling & Cypher for GraphRAG

version-stamps:

Scope note: this day is **KG schema design, Cypher fundamentals, and graph retrieval
for RAG** — the property-graph model, how to derive a schema from a domain, Cypher
pattern matching, and the retrieval patterns (vector + traversal, text-to-Cypher)
that make a knowledge graph useful as a RAG backend. Automated KG *construction
pipelines*, agentic orchestration over graphs, and vector-DB comparisons are other
days' topics; the LLM-built graph in the GraphRAG paper appears here only as the
motivating retrieval architecture.

## Concept IDs

These seed the interview question bank. Each is addressable by ID.

- `property-graph-model` — Neo4j's data model: nodes (entities) with **labels**,
  directed **relationships** with a single type connecting exactly two nodes, and
  key/value **properties** on both. Schema-flexible: Neo4j does not mandate uniform
  properties across entities of the same label.
- `kg-schema-design` — The modeling workflow: dominant nouns in the use case become
  node labels (CamelCase), verbs become relationship types (ALL_CAPS_UNDERSCORE,
  as specific as possible, always directed), attributes become properties
  (camelCase); define use-case questions first, test the model against them,
  refactor; enforce unique IDs with uniqueness constraints.
- `cypher-pattern-matching` — Cypher's declarative, ASCII-art pattern syntax:
  `(node)-[:REL_TYPE]->(other)`; a pattern is "a queryable specification of a graph
  structure," a path is the actual matched sequence; covers fixed-length,
  variable-length/quantified, and `SHORTEST` path patterns.
- `neo4j-vector-index` — Neo4j's built-in HNSW vector index:
  `CREATE VECTOR INDEX ... FOR (m:Movie) ON m.embedding OPTIONS {...}` with
  `vector.dimensions` (1–4096) and `vector.similarity_function` (cosine or
  euclidean); queried via `db.index.vector.queryNodes(indexName, k, queryVector)`
  returning nodes + similarity scores. This is what lets one database serve both
  semantic search and graph traversal.
- `graph-enhanced-retrieval` — The vector-then-traverse GraphRAG pattern: find
  entry-point nodes by embedding similarity, then run a Cypher retrieval query to
  walk relationships and pull connected context (neo4j-graphrag-python's
  `VectorCypherRetriever` / `HybridCypherRetriever`); contrast with the paper's
  global mode (community summaries over an LLM-derived entity graph).
- `text2cypher` — Retrieval by query generation: an LLM translates a natural-language
  question into a Cypher query against the known schema, executes it, and returns
  exact structured results (`Text2CypherRetriever`) — precise for aggregations and
  multi-hop questions, but only as good as the schema it is prompted with.

## Claims (each MUST carry a source)

### Property graph & schema design

- Cypher (created 2011) is a **declarative** query language — you specify *what* to
  retrieve, not *how* — using an ASCII-art syntax of rounded brackets for nodes and
  arrows for relationships (`(nodes)-[:CONNECT_TO]->(otherNodes)`), making it "highly
  intuitive to both read and write"; unlike SQL, Neo4j does not mandate uniform
  properties across entities, and `RETURN` comes at the end. —
  [Overview - Cypher Manual](https://neo4j.com/docs/cypher-manual/current/introduction/cypher-overview/)
- Neo4j's modeling workflow: define the domain, define use-case questions the app
  must answer, build data + instance models, define entities, test the model against
  every use case, then refactor. "The dominant nouns in your application use case
  are represented as nodes" (CamelCase labels); relationship types use "all capital
  letters and an underscore character as a separator"; property keys are "not
  capitalized and can be camelCase." —
  [Tutorial: Create a graph data model - Getting Started](https://neo4j.com/docs/getting-started/data-modeling/guide-data-modeling/)
- Relationship types should be **as specific as possible** rather than generic; all
  relationships have an explicit direction; relationship properties clarify *how*
  two nodes relate; unique identifiers should be enforced with uniqueness
  constraints to prevent duplicate nodes. —
  [Tutorial: Create a graph data model - Getting Started](https://neo4j.com/docs/getting-started/data-modeling/guide-data-modeling/)

### Cypher fundamentals (current version state)

- Graph pattern matching is "the mechanism used to navigate, describe and extract
  data from a graph by applying a declarative pattern"; a pattern is "a queryable
  specification of a graph structure" while a path is "an actual sequence of nodes
  and relationships in the graph that matches a pattern." Covers fixed-length,
  variable-length (quantified) paths, `SHORTEST` paths, and — Cypher 25+ —
  `REPEATABLE ELEMENTS` and `ACYCLIC` match modes. —
  [Patterns - Cypher Manual](https://neo4j.com/docs/cypher-manual/current/patterns/)
- Two Cypher language versions coexist: **Cypher 25** gets all new features;
  **Cypher 5** is frozen as of Neo4j 2025.06 ("No new features will be added to
  Cypher 5"). Version is selected per-database (`db.query.default_language` /
  `DEFAULT LANGUAGE CYPHER 25`) or per-query by prepending `CYPHER 25` / `CYPHER 5`.
  From Neo4j 2026.02, new deployments explicitly set
  `db.query.default_language=CYPHER_25`; if unset, the default is Cypher 5. —
  [Select Cypher version - Cypher Manual](https://neo4j.com/docs/cypher-manual/current/queries/select-version/)

### Vector search inside Neo4j

- Neo4j vector indexes are Lucene-backed HNSW approximate-nearest-neighbor indexes:
  "A vector index allows you to retrieve a neighborhood of nodes or relationships
  based on the similarity between the embedding properties." Created with
  `CREATE VECTOR INDEX ... FOR (m:Movie) ON m.embedding OPTIONS { indexConfig: {
  'vector.dimensions': 1536, 'vector.similarity_function': 'cosine' }}`;
  dimensions range 1–4096; similarity functions are cosine and euclidean (for
  l2-normalized vectors they "produce the same similarity ordering"). Queried with
  `db.index.vector.queryNodes(indexName, k, query)`, which returns nodes plus scores
  where "the closer to 1.0 the score is, the more similar the indexed vector is to
  the query vector." —
  [Vector indexes - Cypher Manual](https://neo4j.com/docs/cypher-manual/current/indexes/semantic-indexes/vector-indexes/)

### Graph retrieval for RAG

- `neo4j-graphrag-python` is Neo4j's **first-party** GraphRAG package (successor to
  the deprecated `neo4j-genai`), offering long-term support; requires Python
  3.10–3.14 (the spaCy `nlp` extra is currently not supported on 3.14) and Neo4j
  >= 5.18.1. —
  [GraphRAG for Python — neo4j-graphrag-python docs](https://neo4j.com/docs/neo4j-graphrag-python/current/)
- Retriever taxonomy: `VectorRetriever` (vector-index similarity search);
  `VectorCypherRetriever` — after finding similar nodes it "executes a Cypher query
  to traverse the graph based on these nodes," enriching results with connected
  context; `HybridRetriever` / `HybridCypherRetriever` (vector + full-text index,
  optionally with traversal); `Text2CypherRetriever` — "first asks an LLM to
  generate a Cypher query to fetch the exact information required to answer the
  question from the database," then executes it; plus external-vector-DB retrievers
  (Weaviate/Pinecone/Qdrant joined back to Neo4j). —
  [User Guide: RAG — neo4j-graphrag-python docs](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html)
- The GraphRAG paper (Microsoft, arXiv:2404.16130) motivates graph retrieval for
  *global* questions ("What are the main themes?") that vanilla RAG cannot answer:
  an LLM first extracts an entity knowledge graph from source documents, community
  detection groups closely related entities, and the system "pregenerate[s]
  community summaries for all groups of closely related entities"; at query time,
  partial answers from community summaries are synthesized into a final answer,
  showing "substantial improvements over a conventional RAG baseline for both the
  comprehensiveness and diversity" on ~1M-token corpora. —
  [From Local to Global: A Graph RAG Approach to Query-Focused Summarization (arXiv:2404.16130)](https://arxiv.org/abs/2404.16130)

## Teaching-angle notes (non-claims)

- The vendor-neutral throughline: **schema quality determines retrieval quality.**
  Text2Cypher fails on vague relationship types; VectorCypherRetriever's traversal
  query is only writable if the model followed specific, directed relationship
  design. Ties w04d4 back to the modeling tutorial's "be as specific as possible."
- Two distinct GraphRAG shapes worth contrasting in class: (a) Neo4j-style
  vector-entry + Cypher traversal (local, entity-anchored), and (b) the paper's
  community-summary map-reduce (global sensemaking). Same name, different retrieval
  mechanics.
- Cypher version churn is a live stale-advice trap: most tutorials online are
  Cypher 5–era; students on a 2026.02+ Neo4j default to Cypher 25.
