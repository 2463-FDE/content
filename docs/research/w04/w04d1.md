## Claims

### When one agent isn't enough (and when it still is)
- **Single agent is the default.** LangChain's own multi-agent docs open with the caveat: "Not every complex task requires this approach — a single agent with the right (sometimes dynamic) tools and prompt can often achieve similar results." The three legitimate drivers for multi-agent are **context management** (specialized knowledge without overwhelming one context window), **distributed development** (team-owned agents with clear boundaries), and **parallelization**. [Multi-agent — Docs by LangChain](https://docs.langchain.com/oss/python/langchain/multi-agent)
- **Multi-agent underperforms when agents must share tight context.** Anthropic: multi-agent systems fall short for "domains that require all agents to share the same context or involve many dependencies between agents" — most coding tasks lack enough parallelizable components. [How we built our multi-agent research system — Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Empirically, MAS gains are often minimal — and failures are systematic.** The MAST paper (Berkeley) analyzed 150+ expert-annotated traces (κ = 0.88) across 7 frameworks and built a taxonomy of **14 failure modes in 3 categories**: (1) system design issues, (2) inter-agent misalignment, (3) task verification. MAST-Data now spans 1,600+ annotated traces. [Why Do Multi-Agent LLM Systems Fail? — arXiv 2503.13657](https://arxiv.org/abs/2503.13657)

### Supervisor architecture (central coordinator)
- **Definition:** a central supervisor agent coordinates specialized worker agents; all routing/communication flows through the supervisor, which "makes decisions about which agent to invoke based on the current context and task requirements." Prebuilt as `create_supervisor()` in `langgraph-supervisor`, with `create_handoff_tool()` for delegation and `create_forward_message_tool()` / `create_handoff_back_messages()` for message plumbing. [langgraph-supervisor — LangChain Reference](https://reference.langchain.com/python/langgraph-supervisor) · [langgraph-supervisor — PyPI](https://pypi.org/project/langgraph-supervisor/)
- **LangChain 1.0's "subagents" pattern is the same shape**: "a main agent coordinates specialized agents as tools, with all routing flowing through the primary coordinator." [Multi-agent — Docs by LangChain](https://docs.langchain.com/oss/python/langchain/multi-agent)

### Swarm architecture (peer-to-peer, no supervisor)
- **Definition (verbatim):** "a type of multi-agent architecture where agents dynamically hand off control to one another based on their specializations." No central coordinator; agents transfer directly via handoff tools. [langgraph-swarm-py — GitHub](https://github.com/langchain-ai/langgraph-swarm-py)
- **Sticky active agent:** "The system remembers which agent was last active, ensuring that on subsequent interactions, the conversation resumes with that agent." API: `create_swarm(agents, default_active_agent="Alice")` + `create_handoff_tool(agent_name="Bob", description="Transfer to Bob")`. [langgraph-swarm — LangChain Reference](https://reference.langchain.com/python/langgraph-swarm) · [langgraph-swarm-py — GitHub](https://github.com/langchain-ai/langgraph-swarm-py)

### Handoff mechanics (OpenAI Agents SDK — the canonical implementation)
- **Handoffs are tools.** "Handoffs allow an agent to delegate tasks to another agent"; they are "represented as tools to the LLM" with default name `transfer_to_<agent_name>` (e.g. `transfer_to_refund_agent`). [Handoffs — OpenAI Agents SDK](https://openai.github.io/openai-agents-python/handoffs/)
- **`handoff()` customization params (verified):** `agent`, `tool_name_override`, `tool_description_override`, `on_handoff` (callback), `input_type` (schema for handoff args), `input_filter` (controls what conversation history the receiving agent sees; prebuilt filters in `agents.extensions.handoff_filters`, e.g. remove tool calls), `is_enabled`, `nest_handoff_history`. [Handoffs — OpenAI Agents SDK](https://openai.github.io/openai-agents-python/handoffs/)
- **Prompting matters:** the SDK ships `RECOMMENDED_PROMPT_PREFIX` / `prompt_with_handoff_instructions()` in `agents.extensions.handoff_prompt` so agents understand handoffs. Nested handoff history (collapsing prior transcript into a summary block) is an opt-in beta via `RunConfig.nest_handoff_history`. [Handoffs — OpenAI Agents SDK](https://openai.github.io/openai-agents-python/handoffs/)
- **LLM-orchestration vs code-orchestration:** letting the LLM route (tools + handoffs) "is great when the task is open-ended"; orchestrating via code (structured-output classification, chaining, parallel fan-out) "makes tasks more deterministic and predictable, in terms of speed, cost and performance." [Orchestrating multiple agents — OpenAI Agents SDK](https://openai.github.io/openai-agents-python/multi_agent/)

### Orchestrator-worker in production (Anthropic's research system)
- **Architecture:** "orchestrator-worker pattern, where a lead agent coordinates the process while delegating to specialized subagents that operate in parallel," each with its own context window (separation of concerns, reduced path dependency). [How we built our multi-agent research system — Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Numbers to teach:** multi-agent Claude (Opus 4 lead + Sonnet 4 subagents) beat single-agent Opus 4 by **90.2%** on Anthropic's internal research eval; token usage explains **~80% of variance** in performance; agents use ~**4×** chat tokens and multi-agent systems ~**15×** — so the economics only work for high-value tasks. Parallel tool calling cut research time "up to 90%" for complex queries. [How we built our multi-agent research system — Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)
- **Orchestration prompt lessons:** teach the orchestrator explicit delegation (objective, output format, tools, task boundaries) to prevent duplication, and embed scaling rules (simple query → 1 agent; complex → 10+ subagents). [How we built our multi-agent research system — Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)

### The counter-argument and its 2026 resolution (context engineering)
- **Cognition's two principles (June 2025, verbatim):** (1) "Share context, and share full agent traces, not just individual messages"; (2) "Actions carry implicit decisions, and conflicting decisions carry bad results." Parallel subagents that can't see each other's work make conflicting implicit choices (their Flappy Bird example: mismatched background vs bird styles). [Don't Build Multi-Agents — Cognition](https://cognition.com/blog/dont-build-multi-agents)
- **2026 refinement:** Cognition (2026-04-22) now names three patterns that work in production — **code-review loop** (fresh-context reviewer, ~2 bugs/PR caught), **smart-friend** (stronger model as consultant), **manager-child delegation** — under one throughline: "multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions." [Multi-Agents: What's Actually Working — Cognition](https://cognition.com/blog/multi-agents-working)

## Concept IDs

Scoped tightly to this day (orchestration architectures + handoff mechanics + when-to-multi-agent). Later-day topics (evals, deployment, memory systems) deliberately excluded.

- **`supervisor-orchestration`** — Central-coordinator architecture: a supervisor agent routes all work to specialized workers (LangGraph `create_supervisor`, LangChain "subagents" pattern); all communication flows through the hub.
- **`swarm-handoff-architecture`** — Decentralized peer-to-peer architecture: agents transfer control directly via handoff tools, with the system resuming at the last-active agent (`create_swarm`, `default_active_agent`).
- **`handoff-tool-mechanics`** — Handoffs as tool calls: `transfer_to_<agent>` naming, `handoff()` customization (`on_handoff`, `input_type`, `input_filter`), history-visibility control, and handoff-aware prompting.
- **`llm-vs-code-orchestration`** — The routing-decision axis: LLM-driven orchestration (open-ended, flexible) vs code-driven orchestration (deterministic, predictable speed/cost), and choosing per task shape.
- **`orchestrator-worker-parallelism`** — Anthropic's lead-agent + parallel-subagent pattern: separate context windows, explicit delegation specs, scaling rules, and the 15×-token / 90.2%-improvement economics.
- **`multi-agent-context-engineering`** — Why naive multi-agent fails: shared full traces vs fragmented context, actions carrying implicit decisions, MAST's 14 failure modes, and the single-threaded-writes rule (extra agents contribute intelligence, not actions).
