## Claims

### Why GraphRAG at all (the motivating gap)
- **Baseline vector RAG fails on global sensemaking questions.** The Microsoft paper targets queries "directed at an entire text corpus" (e.g. "what are the top themes?") — query-focused summarization tasks that chunk-retrieval RAG cannot handle. GraphRAG "scales with both the generality of user questions and the quantity of source text." [From Local to Global — arXiv 2404.16130](https://arxiv.org/abs/2404.16130)
- **The mechanism:** an LLM builds an entity knowledge graph from the docs, community summaries are **pre-generated** for groups of closely related entities, and answers are produced hierarchically — partial answers per community summary, then a final summarizing pass. On ~1M-token corpora this gives "substantial improvements over a conventional RAG baseline for both the comprehensiveness and diversity" of answers. [From Local to Global — arXiv 2404.16130](https://arxiv.org/abs/2404.16130)
- **Official framing:** GraphRAG is "a structured, hierarchical approach to RAG, as opposed to naive semantic-search approaches using plain text snippets." [Welcome — GraphRAG (Microsoft)](https://microsoft.github.io/graphrag/)

### The indexing side: docs → knowledge graph
- **Microsoft's index pipeline is four stages:** (1) segment raw text into **TextUnits**; (2) extract entities, relationships, and claims per unit; (3) hierarchical community detection with the **Leiden** algorithm; (4) bottom-up **community summary** generation. [Welcome — GraphRAG (Microsoft)](https://microsoft.github.io/graphrag/)
- **Neo4j's equivalent is `SimpleKGPipeline`** — orchestrates `FixedSizeSplitter` (chunking; `approximate=True` default for clean chunk boundaries) → `TextChunkEmbedder` (embeddings stored as chunk properties) → `LLMEntityRelationExtractor` (schema-guided extraction; structured output for OpenAI/VertexAI; per-chunk error handling via `on_error`) → `Neo4jWriter` (default batch_size 1000) → optional **entity resolver** (`SinglePropertyExactMatchResolver`, `SpaCySemanticMatchResolver`, or `FuzzyMatchResolver`). [User Guide: KG Builder — neo4j-graphrag-python](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_kg_builder.html)
- **Schema constrains extraction:** `schema={"node_types": [...], "relationship_types": [...], "patterns": [("Person","PARENT_OF","Person")]}`; set `additional_node_types: False` to reject undefined types. A `name: STRING` property is auto-added when properties are omitted. [User Guide: KG Builder — neo4j-graphrag-python](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_kg_builder.html)
- **Two graphs coexist:** the **lexical graph** (Document + Chunk nodes, `NEXT_CHUNK` / `FROM_DOCUMENT` relationships — preserves document structure for RAG context) and the **entity graph** (schema-pruned domain entities/relationships). `create_lexical_graph=True` controls the former. This is the structural hook that makes vector+graph hybrid retrieval possible. [User Guide: KG Builder — neo4j-graphrag-python](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_kg_builder.html)

### The retrieval side: vector + graph hybrid
- **Retriever ladder in `neo4j-graphrag` (all first-party):** `VectorRetriever` (pure vector-index similarity) → `VectorCypherRetriever` (vector entry point **plus a Cypher traversal** to enrich with connected-node context) → `HybridRetriever` (vector **and full-text** indexes searched simultaneously, results merged) → `HybridCypherRetriever` (hybrid entry + follow-up Cypher graph traversal) → `Text2CypherRetriever` (LLM generates Cypher from natural language, executes it, returns structured results). [User Guide: RAG — neo4j-graphrag-python](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html)
- **`ToolsRetriever`** lets an LLM select among multiple retrievers as tools per query and combine results with attribution — the "router" pattern over the ladder above. [User Guide: RAG — neo4j-graphrag-python](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html)
- **External vector stores compose with the graph:** `WeaviateNeo4jRetriever`, `PineconeNeo4jRetriever`, `QdrantNeo4jRetriever` do vector search externally, then map hits back to Neo4j nodes — vectors and graph do not have to live in the same database. [User Guide: RAG — neo4j-graphrag-python](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html)
- **Generation is one class:** `GraphRAG(retriever=..., llm=..., prompt_template=...)` then `rag.search(query_text=..., retriever_config={"top_k": 5}, return_context=True)` — retriever fetches context, LLM answers against it. [User Guide: RAG — neo4j-graphrag-python](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html)
- **First-party status:** the package replaced the deprecated `neo4j-genai`; Neo4j positions it as the long-term-maintained official library. Recent releases added query validation before execution (block destructive Cypher, 1.16.0) and schema constraint alignment (EXISTENCE/KEY, 1.15.0). [GraphRAG for Python — docs](https://neo4j.com/docs/neo4j-graphrag-python/current/) · [Releases — neo4j/neo4j-graphrag-python](https://github.com/neo4j/neo4j-graphrag-python/releases)

### Query modes (Microsoft GraphRAG — the local/global vocabulary)
- **Local search** = entity-centric: embed the query, match against **entity description embeddings** to find graph access points, then fan out to connected entities, relationships, covariates, community reports, **and** the associated raw text chunks; candidates are "prioritized and filtered to fit within a single context window" before generation. Best for questions about specific entities. [Local Search — GraphRAG](https://microsoft.github.io/graphrag/query/local_search/)
- **Global search** = map-reduce over community reports: **map** — chunk community reports and have the LLM produce intermediate points each with a numerical importance rating; **reduce** — filter/aggregate the top-rated points as context for the final answer. Community hierarchy level is the cost/quality dial (lower level = more detail, more compute). [Global Search — GraphRAG](https://microsoft.github.io/graphrag/query/global_search/)
- **Four query modes ship in the reference library:** Global, Local, **DRIFT** (entity-centric with added community context — a local/global blend), and Basic (plain vector similarity). [Welcome — GraphRAG (Microsoft)](https://microsoft.github.io/graphrag/)

### Teaching angle (E2E milestone)
- The milestone build maps cleanly to: `SimpleKGPipeline` ingest (lexical + entity graph in Neo4j from w04d4's modeling) → vector index on chunk embeddings → `VectorCypherRetriever` or `HybridCypherRetriever` for hybrid retrieval → `GraphRAG.search()` for grounded answers — with the Microsoft local/global taxonomy as the conceptual frame for *why* the graph hop adds value over w02's pure-vector RAG.

## Concept IDs

Scoped tightly to this day (GraphRAG E2E = KG construction from text + hybrid vector/graph retrieval + query modes). Multi-agent orchestration (w04d1-d2) and Neo4j modeling/Cypher fundamentals (w04d4) deliberately excluded.

- **`kg-construction-pipeline`** — Turning unstructured docs into a knowledge graph with `SimpleKGPipeline`: splitter → chunk embedder → schema-guided `LLMEntityRelationExtractor` → `Neo4jWriter` → entity resolution (exact/semantic/fuzzy resolvers).
- **`lexical-vs-entity-graph`** — The two coexisting graph layers: Document/Chunk lexical graph (`NEXT_CHUNK`, `FROM_DOCUMENT`) preserving source text for RAG context vs the schema-pruned domain entity graph — and why hybrid retrieval needs both.
- **`hybrid-vector-graph-retrieval`** — The retriever ladder: `VectorRetriever` → `VectorCypherRetriever` / `HybridRetriever` / `HybridCypherRetriever` — vector (and full-text) similarity as the graph entry point, Cypher traversal as the context expander.
- **`text2cypher-retrieval`** — `Text2CypherRetriever`: LLM-generated Cypher from natural language as a structured-retrieval path, plus guardrails (query validation before execution to block destructive operations).
- **`community-summarization`** — The Microsoft indexing insight: Leiden hierarchical community detection over the entity graph plus pre-generated bottom-up community summaries as a corpus-level semantic index.
- **`local-vs-global-search`** — The query-mode taxonomy: local (entity embeddings → graph fan-out → filtered context window) vs global (map-reduce with rated points over community reports) vs DRIFT blend; matching mode to question shape.
