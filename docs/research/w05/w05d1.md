## Claims

### Why spec-before-code (the motivating failure mode)
- **"Vibe coding" fails predictably:** describing goals conversationally to a coding agent yields code that "looks right, but doesn't quite work" — it may not compile, solves partial problems, or ignores architectural requirements. GitHub's diagnosis: the issue isn't agent capability but treating agents "like search engines" instead of "literal-minded pair programmers." [Spec-driven development with AI — The GitHub Blog](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)
- **The paradox is measured, not vibes:** controlled studies show 20–56% productivity gains from AI assistants, yet the most rigorous RCT found a **19% slowdown** for experienced developers; telemetry across 10,000+ developers showed "98% more pull requests but 91% longer review times with flat delivery metrics." The paper's thesis: "Specification discipline, not model capability, is the binding constraint on AI-assisted software dependability." [The Productivity-Reliability Paradox — arXiv 2605.01160](https://arxiv.org/abs/2605.01160)
- **SDD is the inversion:** position "specifications as the source of truth and code as a generated or verified secondary artifact." Specs become "living, executable artifacts" rather than docs written after the fact. [Spec-Driven Development: From Code to Contract — arXiv 2602.00180](https://arxiv.org/abs/2602.00180) · [GitHub Blog](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)
- **Rigor is a spectrum, not a binary:** the taxonomy paper distinguishes **spec-first** (write spec, then code), **spec-anchored** (spec maintained alongside code), and **spec-as-source** (code always regenerated from spec), each with different applicability — plus a decision framework for "when SDD provides value and when simpler approaches suffice." [arXiv 2602.00180](https://arxiv.org/abs/2602.00180)

### The canonical workflow shape (GitHub Spec Kit)
- **Four gated phases:** Specify (goals + user journeys) → Plan (architecture, stack, constraints) → Tasks (small reviewable units) → Implement. "Each phase has a specific job, and you don't move to the next one until the current task is fully validated." Each phase emits a Markdown artifact (`spec.md` → `plan.md` → `tasks.md`) that is the structured context for the next. [GitHub Blog](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/) · [Spec Kit Documentation](https://github.github.com/spec-kit/)
- **Command surface (current):** core `/speckit.constitution` (project principles), `/speckit.specify`, `/speckit.plan`, `/speckit.tasks`, `/speckit.implement`; optional `/speckit.clarify` (underspecified areas), `/speckit.analyze` (cross-artifact consistency), `/speckit.checklist`, `/speckit.taskstoissues`, `/speckit.converge` (assess codebase against specs). Philosophy: "specifications define the *what* before the *how*," multi-step refinement over one-shot generation. [github/spec-kit — GitHub](https://github.com/github/spec-kit)
- **Human role = steward, not doer:** developers steer, verify artifacts, spot gaps, and refine before advancing phases; review shifts from "thousand-line code dumps" to focused per-task changes. [GitHub Blog](https://github.blog/ai-and-ml/generative-ai/spec-driven-development-with-ai-get-started-with-a-new-open-source-toolkit/)
- **Three usage modes:** 0-to-1 greenfield generation, creative exploration (parallel implementations across stacks from one spec), and iterative enhancement of brownfield systems. Agent-agnostic: 30+ integrations, switch agents without changing artifacts. [github/spec-kit — GitHub](https://github.com/github/spec-kit) · [Spec Kit Documentation](https://github.github.com/spec-kit/)

### Requirements that an agent can't misread (Kiro / EARS)
- **Kiro's spec = three files:** `requirements.md` (user stories + acceptance criteria), `design.md` (architecture, sequence diagrams, data flow, error handling, testing strategy), `tasks.md` (discrete trackable tasks with real-time status). Three-phase workflow with **approval gates** between requirements → design → tasks; a "Quick Plan" variant auto-generates all three without gates. [Specs — Kiro Docs](https://kiro.dev/docs/specs/)
- **EARS notation** (Easy Approach to Requirements Syntax) makes acceptance criteria testable: `WHEN [condition/event] THE SYSTEM SHALL [expected behavior]` — e.g. "WHEN a user submits a form with invalid data THE SYSTEM SHALL display validation errors." Structured keywords keep requirements "unambiguous and easy to understand" and traceable through implementation. [Feature Specs — Kiro Docs](https://kiro.dev/docs/specs/feature-specs/)

### Specs as context engineering (GSD)
- **GSD's diagnosis is context rot, not just ambiguity:** "context bloat silently degrades output quality, there is no shared memory between sessions, and nothing verifies that code actually works." The fix is spec-shaped: persistent Markdown artifacts (**PROJECT.md**, **ROADMAP.md**, **PLAN.md**, **SUMMARY.md**, **STATE.md**) that survive session boundaries and feed fresh-context subagents. [open-gsd/gsd-core — GitHub](https://github.com/open-gsd/gsd-core)
- **Five-step loop per milestone:** Discuss (lock decisions upfront) → Plan (research + decompose, verify fit within context limits) → Execute (parallel waves, clean per-executor contexts) → Verify (validate built code, generate remediation plans) → Ship (PR + archive phase). Same spec-before-code spine as Spec Kit, tuned for context-window economics. [open-gsd/gsd-core — GitHub](https://github.com/open-gsd/gsd-core)
- **Project churn note for authoring:** the famous `gsd-build/get-shit-done` repo (64.6K stars, v1.42.3) was archived 2026-06-26; cite `open-gsd/gsd-core` (v1.6.1, 2026-07-01) as the live home. [gsd-build/get-shit-done — GitHub](https://github.com/gsd-build/get-shit-done)

### Evidence base (what research actually knows so far)
- **Human-in-the-loop SDD is under active empirical study:** SANER 2026 registered report (CURRANTE, a VS Code extension) studies a three-stage specification → tests → function workflow, measuring how "human intervention in specification and test refinement influences the quality and dynamics of LLM-generated code" — honest framing for students: the workflow is industry-adopted faster than it is academically validated. [Understanding Specification-Driven Code Generation with LLMs — arXiv 2601.03878](https://arxiv.org/abs/2601.03878)
- **Governance framing:** the SGM model names three moderating variables (task abstraction, codebase maturity, developer experience) and two amplifiers (code-review bottlenecks, context-window constraints); Spec Kit is cited as a practical SGM implementation. [arXiv 2605.01160](https://arxiv.org/abs/2605.01160)

### Teaching angle
- Students already live inside a spec-driven pipeline shape (this cohort's own tooling mirrors it); the day's job is to make the pattern explicit and tool-agnostic: (1) failure mode of prompt-and-pray, (2) the artifact chain spec → plan → tasks → code with human gates, (3) writing testable requirements (EARS), (4) specs as persistent context for agents, (5) when SDD is overkill (spec-first vs spec-anchored vs spec-as-source decision framework).

## Concept IDs

Scoped tightly to this day (SDD methodology + workflow shape + requirement quality). Agent architectures, evals, and CI/CD integration deliberately excluded.

- **`spec-as-source-of-truth`** — The SDD inversion: the specification is the contract and primary artifact; code is generated/verified against it — vs. code-first with docs after the fact; why non-deterministic generators make this the binding constraint.
- **`vibe-coding-failure-mode`** — Prompt-and-pray pathology: conversational goals → code that "looks right but doesn't work"; the measured productivity-reliability paradox (more PRs, longer reviews, flat delivery).
- **`sdd-phase-gates`** — The gated artifact chain: Specify → Plan → Tasks → Implement, each phase emitting a Markdown artifact validated by a human before advancing; review shifts from code dumps to per-phase artifacts.
- **`ears-requirements-notation`** — Writing acceptance criteria an agent can't misread: `WHEN [condition] THE SYSTEM SHALL [behavior]`; testability and traceability as the quality bar for requirements.
- **`specs-as-agent-context`** — Specs double as context engineering: persistent artifacts (PROJECT/ROADMAP/PLAN/STATE) carry decisions across sessions and feed fresh-context executors, countering context rot.
- **`spec-rigor-spectrum`** — Spec-first vs spec-anchored vs spec-as-source; the decision framework for when full SDD pays off and when a direct edit is the right call.
