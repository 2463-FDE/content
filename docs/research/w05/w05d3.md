## Claims (each MUST carry a source)

### GitHub spec-kit (the reference SDD toolkit)

- Spec-kit is GitHub's open-source toolkit for Spec-Driven Development, where "specifications become executable artifacts that directly generate working implementations" rather than guidance documents; current release is 0.12.3 (2026-07-01) with 30+ agent integrations (Copilot, Claude Code, Gemini CLI, Codex CLI, etc.). — [github/spec-kit — GitHub](https://github.com/github/spec-kit)
- The workflow is a fixed artifact pipeline of core slash commands: `/speckit.constitution` (governing principles) → `/speckit.specify` (what/why, no tech stack) → `/speckit.plan` (tech stack + architecture) → `/speckit.tasks` (ordered task breakdown) → `/speckit.taskstoissues` (tasks → GitHub issues) → `/speckit.implement`, plus core `/speckit.converge` (assess the codebase against spec/plan/tasks and append remaining work as new tasks). Optional commands: `/speckit.clarify` (structured de-ambiguation), `/speckit.analyze` (cross-artifact consistency check), `/speckit.checklist` (quality gates). — [github/spec-kit — GitHub](https://github.com/github/spec-kit)
- The methodology's core thesis is a "power inversion": "code serves specifications" — the spec is the generative source and implementation plans/code are "continuously regenerated output," closing the specification-implementation gap. — [spec-driven.md — github/spec-kit](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Spec-kit's constitution (`memory/constitution.md`) functions as "immutable architectural law, not guidelines": non-negotiable articles (library-first, test-first, CLI interfaces, integration-over-isolation testing) enforced as "compile-time checks" via template gates, with documented justification required for any deviation. — [spec-driven.md — github/spec-kit](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Ambiguity handling is explicit, not guessed: templates mandate that the LLM flag unclear points as `[NEEDS CLARIFICATION: specific question]` instead of making "plausible assumptions" — surfacing decisions immediately rather than deferring them silently to implementation. This is the tool-enforced "lock" side of lock-vs-defer. — [spec-driven.md — github/spec-kit](https://github.com/github/spec-kit/blob/main/spec-driven.md)

### Peers: Kiro specs & OpenSpec

- Kiro (AWS's agentic IDE) structures every spec as three files — `requirements.md` (user stories + acceptance criteria), `design.md` (architecture, sequence diagrams, implementation strategy), `tasks.md` (discrete trackable tasks) — across a three-phase requirements → design → tasks workflow, with wave-based concurrent task execution and both feature and bugfix spec types. — [Specs — Kiro Docs](https://kiro.dev/docs/specs/)
- Kiro requirements use EARS (Easy Approach to Requirements Syntax): "WHEN [condition/event] THE SYSTEM SHALL [expected behavior]" — chosen for clarity, testability, and traceability; standard workflows put approval gates between phases, while "Quick Plan" skips gates for well-understood features. — [Feature Specs — Kiro Docs](https://kiro.dev/docs/specs/feature-specs/)
- OpenSpec (v1.5.0, 2026-06-28) is the lightweight peer: each change gets its own folder (`proposal.md` — why/what, `specs/` — requirements and scenarios, `design.md`, `tasks.md`) driven by a propose → apply → archive loop (`/opsx:propose`), working with 20+ AI assistants via slash commands. It positions itself explicitly against spec-kit's "rigid phase gates": artifacts can be updated anytime "without ceremony," and it supports brownfield adoption by capturing existing system state. This is the "defer/iterate" side of lock-vs-defer. — [Fission-AI/OpenSpec — GitHub](https://github.com/Fission-AI/OpenSpec/)

### ADRs (decision capture)

- The canonical definitions: an Architectural Decision (AD) is "a justified design choice addressing functionally or non-functionally significant requirements"; an Architecturally Significant Requirement (ASR) has measurable effects on architecture and quality; an ADR documents a single decision and its rationale. The adr.github.io org maintains the template catalog (Nygard, MADR, Y-statements) and tooling list. — [Architectural Decision Records — adr.github.io](https://adr.github.io/)
- Nygard's original 2011 format is five sections — Title, Status, Context ("competing forces," stated neutrally), Decision, Consequences (positive and negative) — motivated by "large documents are never kept up to date; small, modular documents have at least a chance," stored in version control (`doc/arch/adr-NNN.md`) with sequential never-reused numbers, and superseded rather than deleted. — [Documenting Architecture Decisions — Cognitect (Nygard)](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)
- MADR 4.0.0 (Sept 2024) is the current structured Markdown template: Context and Problem Statement, Decision Drivers (optional), Considered Options, Decision Outcome with justification, Consequences, plus optional Pros/Cons of the Options and Confirmation (how compliance will be verified); ships full and minimal variants, each annotated or bare. — [About MADR — adr.github.io/madr](https://adr.github.io/madr/)
- AWS's prescriptive guidance formalizes the ADR lifecycle: Proposed → (review meeting with dedicated 10–15 min reading time) → Accepted / Rejected; accepted ADRs are immutable — new insight requires a new ADR that supersedes the old one — and the resulting decision log is consulted during code review, where reviewers can block changes that violate an accepted ADR. Scope: write an ADR for every architecturally significant decision — structure, non-functional requirements, dependencies, interfaces, construction techniques (Richards & Ford). — [ADR process — AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html)

### Knowledge modeling (machine-readable project knowledge)

- AGENTS.md is "a simple, open format for guiding coding agents" — a dedicated, predictable file (separate from the human-facing README) carrying build/test commands, code style, conventions, and security notes; 60,000+ open-source projects use it, with support across OpenAI, Google, GitHub, JetBrains, Cursor, and Devin tooling, and nested files for monorepo subprojects. Together with spec-kit's constitution and ADR decision logs, it forms the "knowledge modeling" layer: project knowledge encoded as versioned artifacts agents consume instead of tribal knowledge. — [AGENTS.md](https://agents.md/)

### Lock vs defer (the decision axis for authoring)

- Lock early, explicitly: spec-kit forces ambiguity to the surface via `[NEEDS CLARIFICATION]` markers (resolvable with the optional `/speckit.clarify` command), and locks cross-cutting principles in an immutable constitution before any planning happens; Kiro's standard workflows insert approval gates between requirements, design, and tasks. — [spec-driven.md — github/spec-kit](https://github.com/github/spec-kit/blob/main/spec-driven.md), [Feature Specs — Kiro Docs](https://kiro.dev/docs/specs/feature-specs/)
- Defer and iterate: OpenSpec rejects phase gates — artifacts are fluid, updated anytime, scoped per-change rather than per-project — trading upfront rigor for iteration speed and brownfield fit. — [Fission-AI/OpenSpec — GitHub](https://github.com/Fission-AI/OpenSpec/)
- Lock with an escape hatch: the ADR discipline is the middle path — decisions are locked (accepted ADRs are immutable, enforced at code review) but reversible through an explicit supersede process that preserves the full decision history, so future teams see why, not just what. — [ADR process — AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/adr-process.html), [Documenting Architecture Decisions — Cognitect (Nygard)](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

## Concept IDs (interview question-bank seeds)

Each id carries a one-line definition so the question-bank author seeds from a fixed meaning, not from prose.

- speckit-workflow-artifacts — spec-kit's fixed artifact pipeline: `/speckit.constitution` → `.specify` → `.plan` → `.tasks` → `.taskstoissues` → `.implement`, with core `.converge` reconciling the codebase back against spec/plan/tasks (plus optional `.clarify`/`.analyze`/`.checklist` validators); each phase emits a Markdown artifact that feeds the next and the spec — not the code — is the generative source of truth.
- speckit-constitution — the `memory/constitution.md` file of non-negotiable project principles (library-first, test-first, etc.) treated as "immutable architectural law" enforced through template gates, with any deviation requiring documented justification.
- needs-clarification-markers — spec-kit's tool-enforced ambiguity discipline: the LLM must flag unspecified details as `[NEEDS CLARIFICATION: question]` instead of guessing, optionally resolved via the `/speckit.clarify` command's structured questioning — the mechanism that locks decisions early rather than letting them leak into implementation.
- sdd-tooling-landscape — the spec-kit vs Kiro vs OpenSpec tradeoff space: spec-kit's rigid phase-gated pipeline vs Kiro's three-file (requirements/design/tasks, EARS-notation) IDE-native specs with approval gates vs OpenSpec's per-change propose→apply→archive folders with no gates — differing on where they sit on the lock-vs-defer axis and on greenfield vs brownfield fit.
- adr-lifecycle — Architecture Decision Records as immutable, version-controlled decision capture: Nygard's Title/Status/Context/Decision/Consequences (or MADR 4.0's drivers/options/outcome), moving Proposed → Accepted → Superseded, forming a decision log that is consulted (and can block changes) at code review.
- agent-knowledge-artifacts — the knowledge-modeling layer for agentic tooling: versioned machine-readable project knowledge (AGENTS.md conventions/commands, spec-kit constitutions, ADR decision logs) that replaces tribal knowledge so agents and new humans inherit the same context.
