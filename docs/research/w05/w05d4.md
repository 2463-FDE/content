## Claims

### Decomposition is a pipeline of artifacts, each a human checkpoint
- Spec Kit's core SDD process is **Spec → Plan → Tasks → Implement**. The plan phase reads "the feature requirements, user stories, and acceptance criteria" and converts business needs into concrete technical decisions with documented rationale. Decomposing this way "creates checkpoints where humans review and redirect." [spec-kit/spec-driven.md — GitHub](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- The quickstart makes phasing explicit for anything non-trivial: "For large projects like Taskify, consider implementing in phases (e.g., Phase 1: Basic project/task structure, Phase 2: Kanban functionality, Phase 3: Comments and assignments)." The sequencing "prevents context saturation and allows for validation at each stage" — generate `/speckit.checklist` once the plan exists, then `/speckit.tasks` for the actionable list, then cross-artifact `/speckit.analyze` before implementing. [Quick Start Guide — Spec Kit Documentation](https://github.github.com/spec-kit/quickstart.html)
- Kiro's spec structure is the same shape in three files: `requirements.md` "captures user stories, acceptance criteria... in structured notation," `design.md` documents "technical architecture, sequence diagrams and implementation considerations," and `tasks.md` is "a detailed implementation plan with discrete, trackable tasks." Execution is dependency-aware: "Kiro analyzes your task list, figures out which tasks depend on each other, and runs independent tasks concurrently" — waves execute sequentially, tasks within a wave concurrently. [Specs — Kiro Docs](https://kiro.dev/docs/specs/)

### Plans have phases with explicit gates, not just a task list
- Spec Kit's plan template defines **Phase 0: Research** (`research.md`) → **Phase 1: Design, data model, contracts** (`data-model.md`, `contracts/`, `quickstart.md`) → **Phase 2: Task generation** (`tasks.md`), with a Constitution Check that is a hard gate: "GATE: Must pass before Phase 0 research. Re-check after Phase 1 design." The Technical Context section forces performance goals, constraints, and scale to be stated up front. [spec-kit/templates/plan-template.md — GitHub](https://github.com/github/spec-kit/blob/main/templates/plan-template.md)
- The methodology adds **Phase -1: Pre-Implementation Gates** — Simplicity Gate (Article VII), Anti-Abstraction Gate (Article VIII), Integration-First Gate (Article IX). "These gates prevent over-engineering by making the LLM explicitly justify any complexity." Failing a gate doesn't block, but requires documented justification in a Complexity Tracking table — accountability for architectural decisions. [spec-kit/spec-driven.md — GitHub](https://github.com/github/spec-kit/blob/main/spec-driven.md)
- Same pattern in agentic coding generally: Claude Code's recommended workflow is Explore → Plan → Implement → Commit, because "letting Claude jump straight to coding can produce code that solves the wrong problem." Planning pays off "when you're uncertain about the approach, when the change modifies multiple files, or when you're unfamiliar with the code" — "If you could describe the diff in one sentence, skip the plan." [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)

### Each phase/task must be verifiable — write the check into the plan
- Claude Code docs: "Give Claude a check it can run: tests, a build, a screenshot to compare... Give Claude something that produces a pass or fail, and the loop closes on its own." And on specs: "The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works." [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- Requirements themselves should be written testable. Kiro uses **EARS notation**: "WHEN [condition/event] THE SYSTEM SHALL [expected behavior]" — yielding clarity, testability ("each requirement can be directly translated into test cases"), traceability, and completeness. [Feature Specs — Kiro Docs](https://kiro.dev/docs/specs/feature-specs/)
- Validating the intermediate artifacts (spec/plan/tasks) before code generation is measurably useful: the Spec Kit Agents paper adds "phase-level, context-grounding hooks" across Specify/Plan/Tasks/Implement — read-only repo probing validates each phase against actual repository evidence, catching hallucinated APIs and architectural mistakes. On SWE-bench Lite the grounded pipeline hit 58.2% Pass@1 (+1.7% over baseline) with 99.7–100% test compatibility. [Spec Kit Agents: Context-Grounded Agentic Workflows — arXiv 2604.05278](https://arxiv.org/abs/2604.05278)

### NFRs: use a quality model as the checklist, not vibes
- **ISO/IEC 25010:2023** (Ed. 2.0, Nov 2023) defines the product quality model of **nine characteristics** — functional suitability, performance efficiency, compatibility, usability (incl. accessibility), reliability, security, maintainability, portability/flexibility, and (new in 2023) **safety**. The model is explicitly for "eliciting and defining product and information system requirements," "validating the comprehensiveness of requirements definition," setting design/testing objectives, and "establishing measures of product quality characteristics." Performance efficiency subdivides into time behavior, resource utilization, and **capacity** — i.e., "scale" is a first-class NFR subcharacteristic, not a separate category. [ISO/IEC 25010:2023 — IEC Webstore](https://webstore.iec.ch/en/publication/90024)
- Teaching angle: a phased plan's NFR section is a pass over this model — pick which characteristics are load-bearing for this system, and state a measurable target for each, per phase.

### Performance/scale NFRs must be SLO-shaped (measurable targets on defined indicators)
- Google SRE definitions: an **SLI** is "a quantitative measure of some aspect of the level of service" (request latency, error rate, throughput, availability); an **SLO** is "a target value or range of values for a service level measured by an SLI"; an **SLA** adds consequences for missing SLOs. [Service Level Objectives — Google SRE Book](https://sre.google/sre-book/service-level-objectives/)
- Target-setting guidance to import into plan NFR sections: don't just adopt current performance as the target; keep SLIs simple ("Complicated aggregations in SLIs can obscure changes to system performance, and are also harder to reason about"); "choose just enough SLOs to provide good coverage of your system's attributes"; "Perfection can wait. You can always refine SLO definitions and targets over time"; and avoid overachieving — users depend on actual behavior, not the stated promise (the Chubby planned-outage example). [Service Level Objectives — Google SRE Book](https://sre.google/sre-book/service-level-objectives/)

### Security NFRs: pick an ASVS level, cite requirement IDs in the plan
- **OWASP ASVS 5.0.0** (May 30, 2025) is the open standard of security requirements "for designing, developing, and testing modern web applications and services" — ~350 requirements in 17 chapters, with three verification levels (L1/L2/L3) chosen by application criticality. Its stated uses map directly onto plan authoring: "use as a metric," "use as guidance" (what controls to implement), and "use during procurement" (contractual security requirements). Requirements carry stable `<chapter>.<section>.<requirement>` IDs, so a plan's security NFRs can cite specific ASVS IDs the same way it cites REQ-* IDs. [OWASP ASVS — OWASP Foundation](https://owasp.org/www-project-application-security-verification-standard/) · [OWASP/ASVS — GitHub](https://github.com/OWASP/ASVS)

## Concept IDs

Scoped tightly to this day (spec→plan decomposition + NFRs). Later-day topics (execution/orchestration, deployment, evals) deliberately excluded.

- **`spec-to-plan-pipeline`** — The Spec → Plan → Tasks artifact chain (Spec Kit `/speckit.plan`/`/speckit.tasks`, Kiro requirements/design/tasks.md): each artifact is a human review checkpoint that converts requirements into technical decisions with documented rationale.
- **`phased-plan-gates`** — Structuring a plan as phases (research → design/contracts → tasks) with explicit gates at boundaries: Spec Kit's Constitution Check ("must pass before Phase 0, re-check after Phase 1"), pre-implementation simplicity/anti-abstraction/integration gates, and complexity-tracking justification for violations.
- **`verifiable-task-decomposition`** — Every phase and task ends in a check that produces pass/fail (tests, build, contract check, end-to-end verification step); dependency-aware sequencing (Kiro waves) and cross-artifact validation (`/speckit.analyze`, context-grounding hooks) before implementation.
- **`ears-testable-requirements`** — EARS notation ("WHEN [condition] THE SYSTEM SHALL [behavior]") as the bridge from fuzzy spec language to requirements that are unambiguous, directly testable, and traceable through the plan's tasks.
- **`nfr-quality-model`** — ISO/IEC 25010:2023's nine characteristics as the NFR checklist for a plan: select the load-bearing characteristics (performance efficiency incl. capacity/scale, security, reliability...) and state a target per phase.
- **`slo-shaped-nfr-targets`** — Making perf/scale/security NFRs measurable: SLI/SLO discipline (few, simple indicators; explicit target values; don't overachieve) and ASVS level selection with citable requirement IDs instead of "must be secure."
