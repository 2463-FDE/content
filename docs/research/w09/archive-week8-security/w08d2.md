## Claims

### The root cause: there is no instructions/data boundary

- LLMs "make no architectural distinction between 'instructions' and 'data' (both are tokens on the same stream), so there is no clean equivalent to parameterized queries." — [OWASP LLM01:2026 Prompt Injection](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- Three deployment-time properties amplify it: **context-window pooling** (system prompt, user input, retrieved docs, tool outputs, history and memory are one token stream with no enforced trust boundary), **memory persistence** (an injection that writes to memory/RAG/vector store "taints every subsequent session that reads from that store"), and **agentic execution** (model output drives tool calls, so blast radius extends to whatever the tools reach, and tool outputs re-enter context enabling chained or self-replicating effects). — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- "LLMs are unable to *reliably distinguish* the importance of instructions based on where they came from. Everything eventually gets glued together into a sequence of tokens and fed to the model." — [The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- The term was coined by analogy: "I named it after SQL injection, which has the same underlying problem." — [The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- The 2026 project leads open with the thesis for the whole day: "**Stop trying to build a model that cannot be fooled. Build the system around it, so that when the model is fooled, and it will be, nothing important breaks.**" — [OWASP LLM Top 10 2026 — Preface](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM00_Preface.md)

### Direct vs indirect — and jailbreak as a subset

- **Direct:** "A user, or an attacker with the user's access path, supplies input that changes model behavior in undesired ways" — either **intentional** (crafted jailbreak) or **unintentional** (a legitimate user pastes content that carries conflicting instructions). — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- **Indirect:** "The model ingests content from an external source (a web page, a document, an email, a tool response, a retrieved RAG passage, an image, an MCP server's output, a database row, or an issue title) that contains data which acts as prompt injection. The user did not supply or see those instructions." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- **Jailbreak is a subset, not a synonym:** "Jailbreaking is the subset of prompt injection where the attacker's goal is to make the model violate its safety protocols. Application-level safeguards help contain it, but effective prevention requires ongoing updates to the model's training and safety mechanisms." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- Willison argues the conflation is *why* developers ignore the risk: those who assume prompt injection is jailbreaking "will frequently ignore this issue as irrelevant to them, because they don't see it as their problem if an LLM embarrasses its vendor by spitting out a recipe for napalm." — [The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Anthropic splits the same ground by **threat model** rather than by name: "jailbreaks and direct prompt injection, where the *user* of your application is the adversary" vs "indirect prompt injection, where the user is trusted but Claude processes *third-party content*." — [Mitigate jailbreaks and prompt injections](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks)
- **New in 2026 — the delivery-surface trust taxonomy.** Untrusted surfaces (public pages, unknown-sender mail, search results); **semi-trusted** (issue titles, package READMEs/changelogs, third-party API responses — "content the user chose to retrieve but did not author"); **trusted** (the org's own repos, DBs, internal docs and mail — where "the developer may not realize an attacker has placed content here, perhaps via an unrelated upstream vector such as a public bug-report form"). — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- The shared structure of indirect injection: "the attacker does not need to compromise the backend directly. They place text where the developer's LLM will read it, and the LLM, operating with the developer's privileges, does the work." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- **New in 2026 — the three-axis anatomy** for threat-modelling a scenario before choosing mitigations: **delivery surface** (direct input / retrieved content / tool output / tool connection channel / persistent memory), **propagation** (single-shot / multi-step kill-chain / cross-session via memory or RAG / self-replicating across agents), **encoding** (plain text / base64 or other obfuscation / invisible Unicode / multimodal or steganographic / low-resource language). — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- The foundational paper for indirect injection: adversaries can "remotely (without a direct interface) exploit LLM-integrated applications by strategically injecting prompts into data likely to be retrieved," with a taxonomy covering "data theft, worming, information ecosystem contamination"; demonstrated against Bing's GPT-4-powered Chat and code-completion engines. — [Not what you've signed up for (arXiv 2302.12173)](https://arxiv.org/abs/2302.12173)

### Retrieved documents and tool output are untrusted input

- RAG does not fix this: "research shows that they do not fully mitigate prompt injection vulnerabilities." — [OWASP LLM01:2025 (superseded, for the contrast)](https://raw.githubusercontent.com/OWASP/www-project-top-10-for-large-language-model-applications/main/2_0_vulns/LLM01_PromptInjection.md)
- **The corpus-poisoning number:** "As few as five poisoned documents have reached roughly 90% attack success against a knowledge base of millions of texts (W. Zou et al., 2025)." — [OWASP LLM01:2026, Scenario #4](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- Anthropic's implementable rule: **"Put untrusted content only in tool results."** Deliver third-party content inside `tool_result` blocks, "never in `system` prompts or plain user `text` blocks. Claude is trained to treat instructions that appear inside tool results with appropriate skepticism." — [Mitigate jailbreaks and prompt injections](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks)
- Label provenance in the tool `description` or result structure — "for example, that it is the body of an inbound email from an unknown sender, or OCR text extracted from a user-uploaded image." — [Mitigate jailbreaks and prompt injections](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks)
- **JSON-encode untrusted content:** "JSON escaping provides unambiguous delimiters between the untrusted payload and the surrounding structure, so an attacker cannot close a quote or tag to 'break out' into an instruction context." — [Mitigate jailbreaks and prompt injections](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks)
- The counter-intuitive corollary: **don't put your own instructions in tool results.** "Because Claude treats tool-result content as untrusted data, instructions you place there may be ignored or flagged as a potential injection." Send them in a following `user` turn, or use a mid-conversation system message. — [Mitigate jailbreaks and prompt injections](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks)
- Screen tool outputs *before* the model acts on them: run the tool, pass raw output to a Claude Haiku 4.5 classifier with structured outputs, "and only return the content as a `tool_result` block if the screen reports no injection attempt." — [Mitigate jailbreaks and prompt injections](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/mitigate-jailbreaks)
- **Provenance marking works, but only against non-adaptive attackers.** Spotlighting (delimiting / datamarking / encoding) "reduces the attack success rate from greater than 50% to below 2% in our experiments with minimal impact on task efficacy." — [Defending Against Indirect Prompt Injection Attacks With Spotlighting (arXiv 2403.14720)](https://arxiv.org/abs/2403.14720)
- OWASP attaches the caveat to its version of that control (#6): "This reduces attack success in non-adaptive tests only: an attacker who knows the marking scheme can mimic it, and StruQ was bypassed under adaptive attack (Nasr et al., 2025)." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- **The MCP field evidence (all 2025, all in Scenario #9):** Invariant Labs exfiltrated private repositories via a poisoned GitHub issue; General Analysis "dumped a production database through Cursor's Supabase MCP server running `service_role` and bypassing row-level security"; the malicious `postmark-mcp` package "BCC'd email to an attacker across an estimated 300 organizations." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- Tool descriptions are model-read text and therefore an injection surface: "Pin, sign, and verify every MCP server and third-party tool package, **audit tool descriptions for hidden instructions**, and monitor tool composition." Pinning "does not stop … tool-description poisoning that leaves the version unchanged." — [OWASP LLM01:2026, mitigation #10](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- The MCP spec itself carries a security-best-practices page covering the confused-deputy problem in proxy servers ("MCP proxy servers **MUST** implement per-client consent"), forbidden token passthrough, SSRF, and sandboxing/consent for locally executed servers. — [MCP Security Best Practices, spec revision 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/security_best_practices)
- The current MCP protocol revision is `2026-07-28`; revisions are `YYYY-MM-DD` strings marking "the last date backwards incompatible changes were made." — [MCP versioning](https://modelcontextprotocol.io/specification/versioning)

### The lethal trifecta

- The three legs: **access to private data**; **exposure to untrusted content** ("any mechanism by which text (or images) controlled by a malicious attacker could become available to your LLM"); **the ability to externally communicate** in a way that could be used to steal data. "If your agent combines these three features, an attacker can **easily trick it** into accessing your private data and sending it to that attacker." — [The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- The exfiltration leg is wider than people assume: "If a tool can make an HTTP request—to an API, or to load an image, or even providing a link for a user to click—that tool can be used to pass stolen information back to an attacker." — [The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- MCP is the accelerant because it "encourages users to mix and match tools from different sources." The GitHub MCP exploit had all three legs in one server: read attacker-filed public issues, access private repos, create PRs that exfiltrate. — [The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- Willison's list of production systems reported vulnerable is itself a teaching artifact: ChatGPT (Apr 2023), ChatGPT Plugins, Google Bard, Writer.com, Amazon Q, Google NotebookLM, GitHub Copilot Chat, Google AI Studio, Microsoft Copilot, Slack, Mistral Le Chat, xAI's Grok, Anthropic's Claude iOS app, ChatGPT Operator, Microsoft 365 Copilot, GitHub's official MCP server, GitLab Duo — "dozens of examples … under the exfiltration-attacks tag." — [The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- **Meta's Agents Rule of Two** states it as a hard budget: "until robustness research allows us to reliably detect and refuse prompt injection, agents **must satisfy no more than two** of the following three properties within a session" — **[A]** process untrustworthy inputs, **[B]** access sensitive systems or private data, **[C]** change state or communicate externally. — [Agents Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/)
- If all three are needed without a fresh context window, "the agent should not be permitted to operate autonomously and at a minimum requires supervision — via human-in-the-loop approval or another reliable means of validation." — [Agents Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/)
- The Email-Bot worked example gives three concrete redesigns of the *same* attack: **[BC]** process mail only from trustworthy senders; **[AC]** remove access to sensitive data; **[AB]** restrict recipients or require a human to validate the draft. — [Agents Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/)
- A session may legally **transition** configurations: "starting in [AC] to access the internet and completing a one-way switch to [B] by disabling communication when accessing internal systems." — [Agents Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/)
- Meta's own limits: satisfying the rule is not sufficient against other agent threats (hallucination, spam, excessive privileges), designs that satisfy it "can still be prone to failure (e.g., a user blindly confirming a warning interstitial)," and it "is a supplement — and not a substitute — for common security principles such as least-privilege." — [Agents Rule of Two](https://ai.meta.com/blog/practical-ai-agent-security/)
- **OWASP has now formally adopted both.** The trifecta appears as "a pre-deployment check: an agent that can simultaneously access private data, ingest untrusted content, and communicate externally has the conditions for high-impact exploitation, and removing any one leg removes them," and the Rule of Two is mitigation #8, "as a floor." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- **OpenAI restates it as source–sink analysis:** "an attacker needs both a source, or a way to influence the system, and a sink, or a capability that becomes dangerous in the wrong context." Their user-facing invariant: "potentially dangerous actions, or transmissions of potentially sensitive information, should not happen silently or without appropriate safeguards." — [Designing AI agents to resist prompt injection](https://openai.com/index/designing-agents-to-resist-prompt-injection/)

### Why input filtering alone does not work

- **The headline citation.** By tuning and scaling gradient descent, RL, random search, and human-guided exploration, the authors "bypass 12 recent defenses (based on a diverse set of techniques) with attack success rate above 90% for most; importantly, **the majority of defenses originally reported near-zero attack success rates**." Their methodological claim: evaluating against "a static set of harmful attack strings, or against computationally weak optimization methods that were not designed with the defense in mind" is "flawed." — [The Attacker Moves Second (arXiv 2510.09023)](https://arxiv.org/abs/2510.09023)
- "Plenty of vendors will sell you 'guardrail' products… If you look closely they'll almost always carry confident claims that they capture '95% of attacks' or similar... but in web application security 95% is very much a failing grade." — [The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- **Real attacks are now social engineering, which is what breaks classifiers.** "The most effective real-world versions of these attacks increasingly resemble social engineering more than simple prompt overrides… For such systems, detecting a malicious input becomes the same very difficult problem as detecting a lie or misinformation, and often without necessary context." OpenAI names the recommended-but-insufficient control by its industry nickname, "AI firewalling." — [Designing AI agents to resist prompt injection](https://openai.com/index/designing-agents-to-resist-prompt-injection/)
- OpenAI publishes a real payload as an example — a plausible corporate follow-up email whose "action items" instruct the assistant to extract an employee's name and address and submit them to an attacker-controlled "compliance validation system." Reported by external researchers (Radware, ShadowLeak); "in testing, it worked 50% of the time." — [Designing AI agents to resist prompt injection](https://openai.com/index/designing-agents-to-resist-prompt-injection/)
- **OWASP's position, stated as doctrine:** "no reliable prevention mechanism exists today, a position consistent with NIST (2025), NCSC (2025), and Debenedetti et al. (2025). **Defense is therefore architectural rather than interceptive.** Design the surrounding system on the explicit assumption that the model's instruction boundary will eventually be bypassed." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- OWASP splits its own mitigations into two classes: ones that "reduce injection success and are expected to degrade against adaptive attackers," and ones that "bound the blast radius once injection succeeds, and **these are what survive** against attackers who can probe the system." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- Even the best-published production number is not zero: Claude Opus 4.5 in Claude for Chrome reaches **~1% attack success rate** against an internal adaptive Best-of-N attacker given 100 attempts per environment — and Anthropic's own gloss is "A 1% attack success rate—while a significant improvement—still represents meaningful risk. **No browser agent is immune to prompt injection**, and we share these findings to demonstrate progress, not to claim the problem is solved." — [Mitigating the risk of prompt injections in browser use](https://www.anthropic.com/research/prompt-injection-defenses)
- OWASP's testing mitigation (#11) encodes the lesson: baseline with AgentDojo and JailbreakBench, "then red-team with the full defense specification disclosed to the testers," and "reject static-only attack-success claims." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)

### What architectural controls do

- **The governing invariant.** "The design patterns we propose share a common guiding principle: once an LLM agent has ingested untrusted input, it must be constrained so that it is **impossible** for that input to trigger any consequential actions… At a minimum, this means that restricted agents must not be able to invoke tools that can break the integrity or confidentiality of the system." — [Design Patterns for Securing LLM Agents against Prompt Injections](https://simonwillison.net/2025/Jun/13/prompt-injection-design-patterns/) · [arXiv 2506.08837](https://arxiv.org/abs/2506.08837)
- Willison's operational restatement: "any exposure to potentially malicious tokens entirely taints the output for that prompt. Any attacker who can sneak in their tokens should be considered to have complete control over what happens next — which means they control not just the textual output of the LLM but also any tool calls that the LLM might be able to invoke." — [Design Patterns review](https://simonwillison.net/2025/Jun/13/prompt-injection-design-patterns/)
- **The six patterns** (paper §3.1): **Action-Selector** ("an LLM-modulated switch statement" — the agent triggers tools but gets no feedback from them); **Plan-Then-Execute** (tool outputs return, but the plan is fixed before untrusted content is seen — `calendar.read()` "might be able to corrupt the body of the email that is sent, but it won't be able to change the recipient"); **LLM Map-Reduce** (sub-agents ingest untrusted content and return constrained values; a coordinator aggregates); **Dual LLM** (a privileged LLM never sees untrusted content and drives a quarantined one, exchanging symbolic variables `$VAR1`); **Code-Then-Execute** (the privileged LLM emits code in a sandboxed DSL "designed to enable full data flow analysis, such that any tainted data can be marked as such and tracked"); **Context-Minimization** (remove content from the context once it is no longer needed). — [Design Patterns review](https://simonwillison.net/2025/Jun/13/prompt-injection-design-patterns/) · [full text v3](https://arxiv.org/html/2506.08837v3)
- The paper is structured as **ten case studies** with per-case threat models and candidate designs — OS Assistant with fuzzy search, SQL Agent, Email and Calendar Assistant, Customer service chatbot, Booking Assistant, and more. "The **SQL Agent** case study… is a *highly* challenging environment for prompt injection, and the paper spends three pages exploring patterns for building this in a responsible way." — [full text v3](https://arxiv.org/html/2506.08837v3) · [Design Patterns review](https://simonwillison.net/2025/Jun/13/prompt-injection-design-patterns/)
- The Dual LLM pattern predates all of it (Apr 2023) and is the conceptual ancestor of CaMeL. — [The Dual LLM pattern](https://simonwillison.net/2023/Apr/25/dual-llm-pattern/)
- **CaMeL** "creates a protective system layer around the LLM, securing it even when underlying models are susceptible to attacks… explicitly extracts the control and data flows from the (trusted) query; therefore, the untrusted data retrieved by the LLM can never impact the program flow," plus "a notion of a **capability** to prevent the exfiltration of private data over unauthorized data flows by enforcing security policies when tools are called." — [Defeating Prompt Injections by Design (arXiv 2503.18813)](https://arxiv.org/abs/2503.18813)
- **The honest cost of security-by-design:** CaMeL solves "**77%** of tasks with provable security (compared to **84%** with an undefended system) in AgentDojo." — [arXiv 2503.18813](https://arxiv.org/abs/2503.18813)
- **The load-bearing OWASP mitigation (#4):** "Hold credentials and state-change capability in application code, not the model, and grant least privilege per operation. Route privileged calls through a **deterministic policy engine** that re-validates intent and arguments at execution time." NIST AI 100-2 E2025 and CISA/Five-Eyes OT joint guidance "frame this deterministic mediation as a baseline procurement expectation." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- **The forgotten control (#5):** strip tag-block (U+E0000–E007F), variation-selector (U+FE00–FE0F) and zero-width (U+200B, U+200C, U+200D, U+2060) characters "at every ingest **and render** boundary." The August 2024 M365 Copilot ASCII-smuggling PoC "exfiltrated a Slack MFA code." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- **HITL is not free (#7):** require confirmation "surfacing the exact rendered action rather than a summary to the reviewer. Invisible-character smuggling can make the displayed action differ from the executed one… and approval fatigue degrades reviewer judgment at volume." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- **Memory writes are privileged operations (#9):** "Log the causing prompt, classify writes for instruction or role-modification content, and require approval before instruction-bearing memories persist across sessions." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- **Google's five production layers** around Gemini: prompt-injection content classifiers; **security thought reinforcement**; **markdown sanitization and suspicious-URL redaction** ("our markdown sanitizer identifies external image URLs and will not render them, making the 'EchoLeak' 0-click image rendering exfiltration vulnerability not applicable to Gemini" — CVE-2025-32711); a **user confirmation (HITL) framework**; and end-user notifications when a defense fires. — [Mitigating prompt injection attacks with a layered defense strategy](https://security.googleblog.com/2025/06/mitigating-prompt-injection-attacks.html)
- **OpenAI's sink control, "Safe Url":** "designed to detect when information the assistant learned in the conversation would be transmitted to a third-party. In these rare cases we either show the user the information that would be transmitted and ask them to confirm, or we block it and tell the agent to try another way." Same mechanism covers Atlas navigations/bookmarks and Deep Research searches. — [Designing AI agents to resist prompt injection](https://openai.com/index/designing-agents-to-resist-prompt-injection/)
- OpenAI's design heuristic, which is the most quotable line for a client conversation: "**When integrating an AI model with an application system, we recommend asking what controls a human agent should have in a similar situation and implementing those.**" — [Designing AI agents to resist prompt injection](https://openai.com/index/designing-agents-to-resist-prompt-injection/)
- Anthropic's three-part production approach: RL training against injections in simulated web content; classifiers scanning "all untrusted content that enters the model's context window"; and "scaled expert human red teaming" — "Human security researchers consistently outperform automated systems at discovering creative attack vectors." — [Mitigating the risk of prompt injections in browser use](https://www.anthropic.com/research/prompt-injection-defenses)
- Note the pattern across all three vendors: **the reliable layer is a sink control**, not a source control. Willison observed the same in the incident record — reported exploits were "usually fixed by the vendors, usually by locking down the exfiltration vector such that malicious instructions no longer had a way to extract any data that they had stolen." — [The lethal trifecta for AI agents](https://simonwillison.net/2025/Jun/16/the-lethal-trifecta/)
- The standards backdrop: NIST AI 100-2 E2025 "provides a taxonomy of concepts and defines terminology in the field of adversarial machine learning (AML)… arranged in a conceptual hierarchy that includes key types of ML methods, life cycle stages of attack, and attacker goals, objectives, capabilities, and knowledge." Authors include NIST, Northeastern, Cisco, the U.K. AI Security Institute and the U.S. AI Safety Institute. — [NIST AI 100-2 E2025](https://csrc.nist.gov/pubs/ai/100/2/e2025/final)

### Responsible disclosure in the room

- The CERT/CC's seven CVD principles: **Reduce Harm**, **Presume Benevolence**, **Avoid Surprise**, **Incentivize Desired Behavior**, **Ethical Considerations**, **Process Improvement**, and "CVD is a Wicked Problem." — [Principles of Coordinated Vulnerability Disclosure](https://certcc.github.io/CERT-Guide-to-CVD/topics/principles/)
- **Reduce Harm** is defined as "balancing the ability for system defenders to take action while avoiding an increase in attacker advantage" — the argument for demoing the *minimum* that proves the claim, with a marker string and a controlled sink, not real data. — [Principles of CVD](https://certcc.github.io/CERT-Guide-to-CVD/topics/principles/)
- **Presume Benevolence:** "it is usually best to assume that any individual who has taken the time and effort to reach out to a vendor or a coordinator to report an issue is likely benevolent and sincerely wishes to reduce the risk posed by the vulnerability." — [Principles of CVD](https://certcc.github.io/CERT-Guide-to-CVD/topics/principles/)
- **Avoid Surprise:** "As with most situations in which multiple parties are engaged in a potentially stressful and contentious negotiation, surprise tends to increase the risk of a negative outcome." — the direct argument for telling the author before the room sees it. — [Principles of CVD](https://certcc.github.io/CERT-Guide-to-CVD/topics/principles/)
- **Incentivize Desired Behavior:** "it's usually better to reward good behavior than try to punish bad behavior." — [Principles of CVD](https://certcc.github.io/CERT-Guide-to-CVD/topics/principles/)
- The simultaneity norm — the reason the fix ships in the same breath as the exploit: CISA's CVD program "facilitates the timely and synchronized dissemination of vulnerability information and associated mitigations. This process ensures that all relevant stakeholders … receive critical information simultaneously, thereby minimizing the window of exploitation." — [CISA Coordinated Vulnerability Disclosure Program](https://www.cisa.gov/coordinated-vulnerability-disclosure-process)
- CISA lists **artificial intelligence** as one of the technology categories it coordinates disclosures for, alongside OT/ICS, IoT, medical devices, open source and IT; reports go through VINCE (`kb.cert.org/vince`), hosted by CMU SEI, which accepts anonymous reports "though anonymity limits engagement in case discussions." — [CISA CVD Program](https://www.cisa.gov/coordinated-vulnerability-disclosure-process)
- Vendors model the norm publicly. Google names external researchers by name in its defense post and runs an AI Vulnerability Reward Program plus "generative AI security BugSWAT events"; OpenAI runs a bug bounty that rewards "researchers who identify new prompt-injection paths or potential data-exposure risks." — [Google layered defense](https://security.googleblog.com/2025/06/mitigating-prompt-injection-attacks.html) · [Understanding prompt injections](https://openai.com/safety/prompt-injections/)
- The face-saving frame is factual, not diplomatic: **this is an unsolved industry problem.** "Prompt injection is intrinsic to current generative AI… no reliable prevention mechanism exists today." A finding here is not a competence gap; it is a design decision that has not been made yet. — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)

### Teaching angles worth stealing

- **The demo everyone should run once:** OWASP Scenario #2, verbatim — "A user asks an assistant to summarize a web page containing hidden instructions. The model inserts a markdown image whose URL exfiltrates the private conversation to an attacker-controlled domain. **The user sees only the rendered image, never the instruction.**" Three legs, one page, no exotic tooling. — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- **The "nobody is malicious" scenario** (#3) that defuses blame before the harder demos: a job description embeds an AI-detection instruction; an applicant unknowingly uses an LLM to optimize their resume against it; the recruiting system flags them — "a prompt injection with neither party acting maliciously." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md)
- **The best analogy in the literature**, for a client conversation: OpenAI's three-actor customer-support agent — the human agent "wants to act on behalf of their employer, but they are continuously exposed to external input that may attempt to mislead them," so the business puts *deterministic* limits on refund size and flags phishing rather than trying to make the agent unfoolable. — [Designing AI agents to resist prompt injection](https://openai.com/index/designing-agents-to-resist-prompt-injection/)
- **Adjacent entries to name but not teach today:** LLM03:2026 Excessive Agency ("prompt injection is the input-side compromise, and excessive functionality, permissions, or autonomy are what give that compromise consequences outside the chat window"), LLM02:2026 Sensitive Information Disclosure (what the model leaks through outputs), LLM10:2026 Improper Output Handling (sanitizing model output before downstream components act), and LLM08:2026 Hidden Context Exposure — the renamed System Prompt Leakage entry, whose design rule is "**practitioners should design under the assumption that hidden context is discoverable** and that any contents of the context should not be considered a secret." — [OWASP LLM01:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM01_PromptInjection.md) · [LLM08:2026](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM08_HiddenContextExposure.md)
- OWASP also draws the model-vs-agent boundary explicitly: "This list owns the risk when the model is a component inside your application. The moment that model becomes an actor, with tools it can call, memory it carries between sessions, and consequences it sets in motion downstream, the risk moves to the **OWASP Agentic Top 10**." — [OWASP LLM Top 10 2026 — Preface](https://raw.githubusercontent.com/GenAI-Security-Project/GenAI-LLM-Top10/main/2026/final/LLM00_Preface.md)

## Client hook

Both projects' Week 8 is **"Security / Governance / Responsible AI,"** and in both packets the client's surface ask is *"roll the AI feature out wider."* This day is the technical reason that ask cannot be answered with a marketing page — and, importantly, it is the day where a student demoes an exploit against **the code a peer wrote in Weeks 1–7**, which is exactly why the responsible-disclosure framing is load-bearing rather than decorative.

### Healthcare — Dr. Okonkwo: *"The board wants the headline AI feature: automatic visit-summaries for every patient. Turn it on for everyone."*

The Week 8 packet's hidden problem is **PHI to an LLM vendor with no BAA, plus a fake de-identification export**, and the deliverable is a Safe-Harbor scrub + a data-flow/vendor-governance memo. This day supplies the part of that memo the scrub alone does not cover: **once the encounter record is in the model's context, the untrusted content in that same context can move it.**

Specifically, this day answers:

- **"What untrusted content is already inside the ePHI boundary?"** The `ai-summary` feature sends the full encounter record — including **`notes`**. Clinical notes are free text that patients and outside parties influence (intake forms, faxed referrals, transcribed messages), and Week 6's HL7 v2 feed pipes in *external* ADT/ORU segments. That makes the summarizer an indirect-injection surface by construction: OWASP's "trusted surface" row — the org's own database — where "the developer may not realize an attacker has placed content here."
- **"Does the summarizer have the trifecta?"** Run the three-leg check on the packet's own architecture: **private data** = the encounter record; **untrusted content** = notes + HL7-sourced fields; **exfiltration** = whatever the summary renders into (the portal renders markdown; the W4 records-service has an IDOR; the W7 tracing path ships payloads to a vendor). If a markdown image URL renders in the portal, leg three exists and nobody wrote it on purpose. This is the finding.
- **"Why isn't the redactor enough?"** The Safe-Harbor scrub is a *source* control on one field set. It does nothing about instructions living in a note, and nothing about the summary being manipulated. Pair it with a sink control (strip/deny external image and link rendering in the summary output — Google's markdown-sanitization layer is the citable precedent) and OWASP mitigation #4's deterministic policy engine.
- **The disclosure framing has teeth here.** The W7 packet already contains a transcript where the summarizer "invented a medication the patient isn't on." That is a *hallucination*; this day's demo shows the same endpoint producing attacker-*chosen* clinical content. Framed as an escalation of a known W7 finding rather than a new indictment, it lands on the artifact, not on the author. Clinical-safety consequence: an injected instruction that suppresses an allergy line is the W6 dropped-AL1 failure mode, reachable on purpose.
- **Governance vocabulary the memo needs:** the vendor-risk section should state that no vendor claims a solved problem — Anthropic's own published number is ~1% ASR with "no browser agent is immune," and OWASP's position is that "no reliable prevention mechanism exists today." That converts "is the AI safe?" into "what is our residual-risk statement and who signed it," which is the actual 164.308 risk-management artifact.

### Finance — Dana: *"The board loves the AI scorer. Roll it out wider and make a nice page about how advanced it is."*

The Week 8 packet's hidden problem is **the AI scorer as an ECOA liability at scale** — generic adverse-action reasons, no model card, no disparity monitoring — and the deliverable is a reason-code mapping + model card + fair-lending monitoring spec. This day supplies the **security half of that governance package**, which the packet's fair-lending half assumes exists.

Specifically, this day answers:

- **"Can an applicant influence the decision through the application itself?"** The W2 packet already establishes that the RAG corpus is built over **past applications** and policy docs, and the W3/W8 scorer runs over applicant-supplied fields. Applicant-supplied free text and uploaded documents are the textbook direct/unintentional injection surface — OWASP's Scenario #5, **payload splitting across resume fields** so no single field trips a per-field classifier, transfers to a loan application one-for-one. A decision manipulable by the applicant is not just a security defect; it is an **unsafe and unsound underwriting practice** and it destroys the defensibility of every reason code the W3 audit trail records.
- **"Is the RAG corpus poisonable, and who can write to it?"** OWASP's number — five poisoned documents, ~90% attack success against millions — is the argument the ADR needs. The corpus contains past applications; anyone who can submit an application can write to it. That is a **cross-session, cross-borrower** taint, not a one-shot bug, and it means the W2 "corpus hygiene" ADR was a security control all along, not a data-quality one.
- **"Does the model card have a security section?"** A model card that documents drivers and disparity but not the injection surface is incomplete. Give the students the concrete headings: delivery surfaces (application free text, uploaded docs, retrieved policy passages, bureau API responses), the trifecta/Rule-of-Two configuration of the decisioning agent, the sink inventory, and the adaptive-testing statement (OWASP #11 — "reject static-only attack-success claims"). This is the artifact Priya can actually take to an examiner.
- **"What is the deterministic mediation?"** OWASP #4 maps cleanly onto lending: the model may *recommend*; only application code holds the credential to write a decision, and a policy engine re-validates the decision's arguments (amount, rate, reason code) at execution time. That is the same control shape as W6's maker-checker on money-affecting actions — say so, because it lets Sam and Priya share one control rather than fund two.
- **The disclosure framing has teeth here too.** The natural demo target is a peer's W3 decisioning agent or W2 retrieval helper. The CVD framing to use out loud: this is not "you built it wrong," it is "we now know the corpus is a write surface, here is the ingest-time redaction + provenance-marking fix, and here is the date it lands." **Avoid Surprise** means the author sees it first; **Reduce Harm** means the demo uses a marker string, not a real SSN from the W1 log dump.

## Concept IDs

Scoped tightly to this day. Deliberately excluded: PII/de-identification and vendor governance (the week's other days), model-governance/fair-lending artifacts, agentic authorization design, and general LLM output guardrails (w07d5).

- **`direct-vs-indirect-injection`** — the taxonomy and why it is the *delivery surface* that matters, not the payload: direct (intentional/unintentional) vs indirect; OWASP 2026's untrusted / semi-trusted / trusted surface split; jailbreak as a strict subset of prompt injection; the three-axis anatomy (delivery surface, propagation, encoding) as the threat-modelling step before mitigation selection.
- **`untrusted-tool-output`** — retrieved documents, tool results, MCP responses, OCR text and tool *descriptions* are attacker-controllable input. Corpus poisoning as a persistence surface (5 docs ≈ 90% ASR); `tool_result`-only delivery, provenance labelling and JSON encoding as structural separation; "don't put your own instructions in tool results"; MCP spec 2026-07-28 as the protocol-level security surface.
- **`lethal-trifecta`** — private data + untrusted content + exfiltration channel; removing any one leg removes the class; the exfiltration leg is any outbound HTTP including image loads and clickable links; the pre-deployment checklist form.
- **`capability-budget-rule-of-two`** — Meta's [A]/[B]/[C] "no more than two per session," the [AB]/[AC]/[BC] redesigns of one attack, one-way in-session transitions, mandatory supervision when all three are required, and its adoption by OWASP as mitigation #8; OpenAI's source–sink restatement of the same budget.
- **`detection-vs-architecture`** — why classifiers and "AI firewalls" are a cost control and not a security boundary: adaptive attackers took 12 defenses from near-zero to >90% ASR; social-engineering payloads make detection equivalent to lie detection; ~1% ASR is still meaningful risk; static-only attack-success claims must be rejected.
- **`injection-resistant-agent-patterns`** — the architectural answer: the "impossible to trigger consequential actions" invariant; Action-Selector, Plan-Then-Execute, Map-Reduce, Dual LLM, Code-Then-Execute, Context-Minimization; CaMeL's capabilities + data-flow tracking and its 77%-vs-84% utility cost; deterministic policy mediation, sink controls (markdown/URL sanitization, Safe Url), invisible-Unicode stripping, and HITL that renders the exact action.
