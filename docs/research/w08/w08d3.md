### Layer taxonomy — the four tools are not four options

- **NeMo Guardrails is a dialogue-management runtime, not a filter.** The paper's framing: "using a runtime inspired from dialogue management, NeMo Guardrails allows developers to add programmable rails to LLM applications — these are user-defined, independent of the underlying LLM, and interpretable," as distinct from guardrails "embedded into a specific model at training, e.g. using model alignment." — [NeMo Guardrails: A Toolkit for Controllable and Safe LLM Applications with Programmable Rails (arXiv:2310.10501, EMNLP 2023 Demo)](https://arxiv.org/abs/2310.10501)
- **NeMo ships five rail types, each at a different point in the interaction**: **input** ("can reject the input, stopping any additional processing, or alter the input (e.g., to mask potentially sensitive data, to rephrase)"), **dialog** (operates on canonical forms, decides the next step), **retrieval** ("applied to the retrieved chunks in the case of a RAG scenario; a retrieval rail can reject a chunk, preventing it from being used to prompt the LLM"), **execution** (on custom-action/tool input and output), and **output** ("can reject the output, preventing it from being returned to the user, or alter it"). — [NVIDIA-NeMo/Guardrails — GitHub](https://github.com/NVIDIA/NeMo-Guardrails)
- **Guardrails AI's unit is the Guard, and it has two placements.** "The guard object… wraps LLM calls, orchestrates validation, and keeps track of call history." `guard(model=…, messages=…)` calls the LLM then validates; **`guard.parse(llm_output=…)` applies validation as a post-process to an LLM call you made yourself**, and with `num_reasks=0` it stays "purely as a post-processor." Above zero, a validation failure costs another LLM round trip. — [The Guard — Guardrails AI docs](https://guardrailsai.com/docs/concepts/guard)
- **LLM Guard is a flat scanner pipeline**: input scanners and output scanners around the call, each returning `(sanitized_prompt, is_valid, risk_score)`. Its stated job is "sanitization, detection of harmful language, prevention of data leakage, and resistance against prompt injection attacks." No flow language, no dialogue model. — [LLM Guard docs index](https://protectai.github.io/llm-guard/) · [Anonymize Scanner](https://protectai.github.io/llm-guard/input_scanners/anonymize/)
- **Presidio is not a guardrail — it is a de-identification SDK**, described in its own README as a "Data Protection and De-identification SDK" providing "context aware, pluggable and customizable PII de-identification service for text and images." It ships as separate components: `presidio-analyzer`, `presidio-anonymizer`, `presidio-image-redactor`, `presidio-structured`, `presidio-cli`. — [data-privacy-stack/presidio — GitHub](https://github.com/microsoft/presidio) · [Presidio docs](https://data-privacy-stack.github.io/presidio/)
- **Three of the four tools wrap the fourth.** NeMo's sensitive-data rails *are* Presidio ("To use the built-in sensitive data detection rails, you must install Presidio and download the `en_core_web_lg` model for `spacy`" — or `pip install nemoguardrails[sdd]`). Guardrails Hub's `Detect PII` validator: "Detects personally identifiable information (PII) in text, **using Microsoft Presidio**." LLM Guard's `Anonymize`: "**Integration with Presidio Analyzer** — Leverages the Presidio Analyzer library, crafted with spaCy, flair and transformers libraries." **A "four-way bake-off" is a category error; the real decision is orchestration model plus what you feed the detector.** — [NeMo Presidio Integration](https://docs.nvidia.com/nemo/guardrails/configure-guardrails/guardrail-catalog/third-party/presidio) · [Guardrails Hub](https://hub.guardrailsai.com/) · [LLM Guard Anonymize Scanner](https://protectai.github.io/llm-guard/input_scanners/anonymize/)
- **NeMo's newer PII path is not Presidio.** The PII-detection catalog entry now leads with the **NVIDIA GLiNER-PII NIM** (`nvidia/gliner-pii` is the default `rails.config.gliner.model`), configurable per-position with `threshold` and an entity list (`email`, `phone_number`, `ssn`, `first_name`, `last_name`, `credit_debit_card`, …). Presidio is filed under third-party integrations. — [NeMo PII Detection catalog](https://docs.nvidia.com/nemo/guardrails/configure-guardrails/guardrail-catalog/pii-detection)
- **NeMo's catalog is the map of what a "guardrail" can even mean**: Content Safety, Jailbreak Protection, Topic Control, PII Detection, Agentic Security, Tool Calling, Hallucinations & Fact-Checking, LLM Self-Check, Third-Party APIs. Use this list as the memo's option space so nothing gets silently dropped. — [Guardrail Catalog](https://docs.nvidia.com/nemo/guardrails/configure-guardrails/guardrail-catalog)

### Where each layer sits in the request path

- **The same PII capability at the same position has two behaviours, and it is a product decision.** NeMo: "When using `detect sensitive data on input`, if sensitive data is detected, **the bot will refuse to respond** to the user's input. When using `mask sensitive data on input` the bot will **mask the sensitive parts** in the user's input and continue the processing." One produces a blocked user; the other produces a degraded answer. — [NeMo Presidio Integration](https://docs.nvidia.com/nemo/guardrails/configure-guardrails/guardrail-catalog/third-party/presidio)
- **The retrieval rail is the one teams forget and the one RAG-over-records needs.** NeMo supports sensitive-data detection as an input rail, output rail, **and retrieval rail** — the retrieval rail rejects or masks a chunk *before* it is used to prompt the LLM. If the corpus contains PHI, this is the only position that stops it entering the prompt at all. — [NVIDIA-NeMo/Guardrails — GitHub](https://github.com/NVIDIA/NeMo-Guardrails) · [NeMo Presidio Integration](https://docs.nvidia.com/nemo/guardrails/configure-guardrails/guardrail-catalog/third-party/presidio)
- **LLM Guard's Vault/Deanonymize round trip is the pattern for "the vendor never sees the identifier but the clinician still does."** `Anonymize` writes redacted values into a `Vault` (`use_faker` substitutes fabricated data; `hidden_names` maps to `[REDACTED_CUSTOM_1]`), and the paired `Deanonymize` output scanner restores them on the way back. — [Anonymize Scanner](https://protectai.github.io/llm-guard/input_scanners/anonymize/)
- **Streaming forces an explicit, documented tradeoff — and the default is the risky one.** NeMo's `rails.output.streaming` block: `stream_first: True` (**the default**) means "the client receives each chunk of tokens **before** output rails process that chunk. This provides faster time-to-first-token, but **if a rail blocks the content, the user has already received the tokens.** The stream terminates with a JSON error on violation." `stream_first: False` means "the user never sees blocked content, but **time-to-first-token increases by the rail execution time per chunk**." — [Output Rail Streaming Configuration](https://docs.nvidia.com/nemo/guardrails/configure-guardrails/yaml-schema/streaming/output-rail-streaming)
- **The streaming knobs price the tradeoff.** `chunk_size` defaults to **200 tokens** ("Larger values: fewer rail executions, but higher latency to first output. Smaller values: more rail executions, but faster time-to-first-token"); `context_size` defaults to **50 tokens** carried across chunk boundaries "so a sentence spanning two chunks can still be evaluated"; `enabled` defaults to **False**, and calling `stream_async()` with output rails configured but streaming disabled is a hard error. — [Output Rail Streaming Configuration](https://docs.nvidia.com/nemo/guardrails/configure-guardrails/yaml-schema/streaming/output-rail-streaming) · [Streaming Responses](https://docs.nvidia.com/nemo/guardrails/run-guardrailed-inference/using-python-apis/streaming)
- **NeMo has two distributions and the config is portable between them.** Library = PyPI package, self-managed Python env, application-level scaling. Microservice = "container image backed by this library," Kubernetes with Helm, scaling "managed by the orchestrator." Both take the **same YAML and Colang format**: "Configurations are portable between the library and microservice, so you can develop locally with the library and deploy to production with the microservice." — [NeMo Guardrails library overview](https://docs.nvidia.com/nemo/guardrails/latest/index.html)

### Measured latency — with the instance type named

- **LLM Guard publishes per-scanner, per-instance p90/p95/p99, which almost nobody else does.** Setup for every table: Amazon Linux 2, Python 3.11.6, 5 runs. **PromptInjection** (input length 384): AWS m5.xlarge **212.87 ms avg / 317 ms p99**; m5.xlarge **+ ONNX 104.21 / 107**; g5.xlarge GPU 81.01 / 329; **g5.xlarge GPU + ONNX 7.65 ms avg / 14.75 p99**; Azure Standard_D4as_v4 **421.46 avg / 1,237 p99**. — [Prompt Injection Scanner](https://protectai.github.io/llm-guard/input_scanners/prompt_injection/)
- **ONNX runtime is the single biggest latency lever and it is a one-line change.** Roughly 2× on CPU and ~10× on GPU across scanners, and it collapses *variance*: PromptInjection latency variance falls from 3.00 to 0.00 on m5.xlarge with ONNX. Enable with `pip install llm-guard[onnxruntime]` and `use_onnx=True`. — [Prompt Injection Scanner](https://protectai.github.io/llm-guard/input_scanners/prompt_injection/) · [Optimization Strategies](https://protectai.github.io/llm-guard/tutorials/optimization/)
- **Instance type can dominate tool choice.** The **Toxicity** scanner (input length 97) runs at **4.80 ms** on g5.xlarge GPU + ONNX, 34.13 ms on m5.xlarge + ONNX — and **620.79 ms on r6a.xlarge (AMD)**, a 129× spread on the same code and the same benchmark. Benchmark on the client's actual fleet or the number is fiction. — [Toxicity Scanner](https://protectai.github.io/llm-guard/input_scanners/toxicity/)
- **PII redaction is the expensive scanner.** **Anonymize** (input length 317, Presidio + BERT NER): m5.xlarge **177.13 ms avg / 325.71 p99**; + ONNX 128.64 / 179.93; g5.xlarge GPU + ONNX **38.11 / 99.26**; r6a.xlarge (AMD) 244.17 / 284.47. — [Anonymize Scanner](https://protectai.github.io/llm-guard/input_scanners/anonymize/)
- **Other published optimisation levers**, in the order to try them: ONNX runtime; quantized/optimized model variants ("doesn't always lead to better latency but can reduce the model size"); `low_cpu_mem_usage=True`; **smaller model variants** (distilbert, bert-small, bert-tiny — "reduced latency without significantly compromising accuracy"); `torch.set_float32_matmul_precision('high')` + inductor fx graph cache; and **streaming mode** to scan output in chunks. Note that **every lever on this list is a per-request latency lever — there is no batching or concurrency lever anywhere in the document.** — [Optimization Strategies](https://protectai.github.io/llm-guard/tutorials/optimization/) · [optimization.md raw](https://raw.githubusercontent.com/protectai/llm-guard/main/docs/tutorials/optimization.md)
- **One of those levers is already applied in the published numbers, so it is not an additional win.** `benchmarks/run.py` sets `torch.set_float32_matmul_precision("high")` at module scope before any scanner is built. Anyone quoting the tables and *then* promising a further speedup from the PyTorch hack is double-counting. — [LLM Guard benchmarks/run.py](https://raw.githubusercontent.com/protectai/llm-guard/main/benchmarks/run.py)
- **LLM Guard's shipped API runs scanners serially, and does not stop at the first failure by default.** The deployment docs: **"Scanners will be executed in the order of configuration."** `SCAN_FAIL_FAST` (bool) — "Stop scanning after the first failed check. **Default is `False`**"; `SCAN_PROMPT_TIMEOUT` default **10 seconds**, `SCAN_OUTPUT_TIMEOUT` default **30 seconds**; `CACHE_MAX_SIZE` / `CACHE_TTL` (default 1 hour) are the only built-in amortisation. **This is why a multi-scanner budget is the sum and not the max** — the parallel number requires you to fan the scanners out yourself, which the shipped API does not do. — [LLM Guard API deployment overview](https://protectai.github.io/llm-guard/api/overview/)
- **The `QPS` column in every LLM Guard benchmark table is characters per second, not queries per second — and it is the single most quotable wrong number in this whole landscape.** From `benchmarks/run.py`: `latency_ms = sum(latency_list) / float(len(latency_list)) * 1000.0` then **`throughput = input_length * (1000.0 / latency_ms)`**, where `input_length` is `len(prompt)` in characters. It checks exactly against the published tables: PromptInjection m5.xlarge `384 / 0.21287 s = 1,804` vs published **1,803.91**; Toxicity r6a.xlarge `97 / 0.62079 s = 156.25` vs published **156.25**. Worse, the harness is `timeit.repeat(lambda: scanner.scan(prompt), number=1, repeat=repeat_times)` — **strictly sequential, single-threaded, no concurrency and no batching anywhere.** The tables support *no* request-throughput claim at all. — [LLM Guard benchmarks/run.py](https://raw.githubusercontent.com/protectai/llm-guard/main/benchmarks/run.py) · [Prompt Injection Scanner](https://protectai.github.io/llm-guard/input_scanners/prompt_injection/) · [Toxicity Scanner](https://protectai.github.io/llm-guard/input_scanners/toxicity/)
- **LLM-based rails are an order of magnitude slower than purpose-trained small models, and usually less accurate.** NeMo's fact-checking rail, measured per checked fact: `align_score-base` **84.5% accuracy at 23.0 ms**; `align_score-large` **88.5% at 46.0 ms**; `gpt-3.5-turbo-instruct` 80.5% at **188.8 ms**; `text-davinci-003` 81.5% at 272.2 ms; `gpt-3.5-turbo` 82.5% at **435.1 ms**; `gemini-1.0-pro` 92.5% at **704.5 ms**. (AlignScore timings are in-memory, "without network overheads, i.e., not as a RESTful service.") — [Evaluate NeMo Guardrails Library Performance](https://docs.nvidia.com/nemo/guardrails/evaluation/evaluate-guardrails)
- **The accuracy/latency frontier for PII, measured independently.** Guardrails AI's own benchmark (24 guardrails, 6 datasets, "32 days spent on GPU"): **Presidio — latency 0.0161 s CPU / 0.0150 s GPU, F1 0.3698**. **Guardrails PII — 0.5002 s CPU / 0.0678 s GPU, F1 0.6520**. **GLiNER for PII — 0.5031 s CPU / 0.0460 s GPU, F1 0.6520**. Presidio is **~31× faster on CPU and roughly half as accurate**. — [AI Guardrails Index](https://index.guardrailsai.com/)

### False positives — the number the front desk actually feels

- **The best PII guardrail in the index scores F1 0.65.** Category bests across the whole benchmark: Topic Restriction 0.93 (Restrict to Topic, hybrid), Jailbreaking 0.81 (Detect Jailbreak), Hallucination 0.77 (Provenance LLM), Content Moderation 0.72 (Toxic Language), Competitors Check 0.67, **PII Detection 0.65 (Guardrails PII)**. Nothing here is near-perfect; a memo implying otherwise is the thing that gets the FDE fired later. — [AI Guardrails Index](https://index.guardrailsai.com/)
- **LLM self-check input rails are catastrophically imprecise, per NVIDIA's own evaluation.** On **ToxicChat** (n=10,165, 7.2% labelled harmful), `gpt-3.5-turbo-instruct` with `self check input` scores **accuracy 66.5%, precision 0.16, recall 0.85, F1 0.27** — versus `llama guard check input` at **94.4% / 0.67 / 0.44 / 0.53**. On the **OpenAI Moderation test set** (n=1,680, 31.1% harmful), self-check scores **65.9% / 0.47 / 0.88 / 0.62** versus Llama Guard's **81.9% / 0.73 / 0.66 / 0.69**. NVIDIA's own read: "The low precision and high recall numbers from the self check input with the complex prompt indicates an **overly defensive behavior** from the self check input rail." — [Evaluate NeMo Guardrails Library Performance](https://docs.nvidia.com/nemo/guardrails/evaluation/evaluate-guardrails)
- **`[derived]` Translate precision 0.16 into staffing.** *Derived from the ToxicChat row in the bullet above (accuracy 66.5%, precision 0.16, recall 0.85, base rate 7.2%). No new source — this is arithmetic on NVIDIA's published numbers.*
  - False alarms per true catch = `(1 − precision) / precision` = `0.84 / 0.16` = **5.25**. (Precision alone fixes this ratio; the base rate does not enter.)
  - Absolute daily volume, on **200 front-desk chats/day**: harmful = `200 × 0.072` = 14.4 → true catches = `14.4 × 0.85` = **12.2**; false alarms = `12.2 × 5.25` = **64.1**; total blocked = **76.3**, i.e. **~38% of all traffic flagged and ~32% of all traffic wrongly blocked.**
  - **Consistency check (do this in front of the room):** implied TN = `185.6 − 64.1` = 121.5, FN = `14.4 − 12.2` = 2.2, so accuracy = `(12.2 + 121.5) / 200` = **66.9%** — which reproduces NVIDIA's published **66.5%** to rounding. The derivation is self-consistent with the source, which is the check that makes it safe to quote.
  - The memo sentence: *"at 200 chats a day this rail wrongly blocks about 64 patients daily."* Nobody signs that; nobody was ever shown it, because the deck said "85% recall."
- **A guardrail can fail closed on its own prompt.** NeMo's moderation-rail table records `gemini-1.0-pro` producing **API errors on 36% of harmful prompts** — triggered by the self-check prompt itself — and NVIDIA notes "it is debatable whether this behavior should be treated as effective moderation or being triggered by a **false positive**." An availability incident wearing a safety costume. — [Evaluate NeMo Guardrails Library Performance](https://docs.nvidia.com/nemo/guardrails/evaluation/evaluate-guardrails)
- **Presidio ships an explicit non-guarantee, and it belongs in the memo verbatim.** "Presidio can help identify sensitive/PII data in un/structured text. However, because it is using automated detection mechanisms, **there is no guarantee that Presidio will find all sensitive information.** Consequently, additional systems and protections should be employed." — [Presidio FAQ](https://data-privacy-stack.github.io/presidio/faq/)
- **Presidio names the false-positive mechanism and the four levers.** "A driver's license number, for example, could be **any 9-digit number.** While Presidio leverages context words and other logic to improve the detection quality, it could still falsely detect non-entity values as PII entities." Levers, in order: (1) change the acceptance threshold, (2) **remove unnecessary PII recognizers** if the dataset cannot contain those entities, (3) update/replace a recognizer's logic, (4) replace it with a third-party service. Lever 2 is free and is the one teams skip. — [Presidio FAQ](https://data-privacy-stack.github.io/presidio/faq/)
- **The metric to write into acceptance criteria is F₂, not F1.** "In PII detection, recall is often more important than precision, as we'd like to avoid missing any PII. In such cases, **we recommend to use the β=2 score**, which gives more importance to recall." Presidio also ships `presidio-research` — "a set of tools that help you evaluate the performance of the Presidio Analyzer" plus "a simple PII data generator" — so this is a testable acceptance criterion, not an aspiration. — [Evaluating PII detection with Presidio](https://data-privacy-stack.github.io/presidio/evaluation/) · [Presidio FAQ](https://data-privacy-stack.github.io/presidio/faq/)
- **Presidio is explicit that managed services often beat it on coverage.** "Presidio is a library which is meant to be customized, whereas different SaaS tools for PII detection have less customization capabilities. Most of these SaaS offerings use dedicated ML models and other logic for PII detection and **often have better entity coverage or accuracy than Presidio**." Their own recommendation is to run Presidio **in parallel with** a third-party service "when the data in hand has entity types or values not supported by the 3rd party service." — [Presidio FAQ](https://data-privacy-stack.github.io/presidio/faq/)

### Coverage — what the PII layer can and cannot see

- **Presidio's recognizers are grouped by jurisdiction and each one declares its detection method**, which makes a coverage matrix mechanically derivable. **Global**: `CREDIT_CARD`, `CRYPTO`, `DATE_TIME`, `EMAIL_ADDRESS`, `IBAN_CODE`, `IP_ADDRESS`, `MAC_ADDRESS`, `NRP`, `LOCATION`, `PERSON`, `PHONE_NUMBER`, `MEDICAL_LICENSE`, `URL`. **USA**: `US_BANK_NUMBER`, `US_DRIVER_LICENSE`, `US_ITIN`, **`US_MBI`** (Medicare Beneficiary Identifier, 11 alphanumeric), **`US_NPI`** ("a 10-digit number issued to healthcare providers by CMS under HIPAA," pattern + context + checksum), `US_PASSPORT`, `US_SSN`. — [PII entities supported by Presidio](https://data-privacy-stack.github.io/presidio/supported_entities/)
- **Detection method predicts where the errors live.** Pattern **+ checksum** (`CREDIT_CARD`, `IBAN_CODE`, `US_NPI`, `UK_NHS`, `AU_MEDICARE`, `DE_HEALTH_INSURANCE`) is high-precision and cheap. Pattern **+ context** (`US_SSN`, `US_DRIVER_LICENSE`, `IP_ADDRESS`, `DATE_TIME`) is where false positives concentrate. **NER-driven** (`PERSON`, `LOCATION`, `NRP`) is where recall fails. — [PII entities supported by Presidio](https://data-privacy-stack.github.io/presidio/supported_entities/)
- **Presidio also has a clinical-NER group — and it detects content, not identifiers.** Behind the `transformers` extra, `MedicalNERRecognizer` (over `blaze999/Medical-NER`) adds `MEDICAL_DISEASE_DISORDER`, `MEDICAL_MEDICATION`, `MEDICAL_THERAPEUTIC_PROCEDURE`, `MEDICAL_CLINICAL_EVENT`, `MEDICAL_BIOLOGICAL_ATTRIBUTE`, `MEDICAL_BIOLOGICAL_STRUCTURE`, `MEDICAL_FAMILY_HISTORY`, `MEDICAL_HISTORY`. Useful for redacting clinical narrative; **not** a substitute for an identifier list. — [PII entities supported by Presidio](https://data-privacy-stack.github.io/presidio/supported_entities/)
- **Structured and unstructured are different products.** `presidio-structured` "scans datasets for PII using Presidio Analyzer, and supports the redaction of text, cells, or columns in a tabular dataset" — the easy half. The note body, the log line, and the model's own generated summary are the hard half, and only the NER path can see identifiers there. — [Presidio FAQ](https://data-privacy-stack.github.io/presidio/faq/)
- **Language and locale are hard limits.** LLM Guard's Presidio-backed Anonymize states plainly: "**Current entity detection functionality is English-specific**" (a Chinese recognizer is available as an option). Presidio's `PhoneRecognizer` must be configured with explicit `supported_regions` for non-US numbers. A multilingual patient or applicant population is a coverage gap, not a config detail. — [Anonymize Scanner](https://protectai.github.io/llm-guard/input_scanners/anonymize/) · [PII entities supported by Presidio](https://data-privacy-stack.github.io/presidio/supported_entities/)
- **Guardrails Hub's catalogue is 65 validators, tagged by risk class** — Data Leakage (`detect_pii`, `guardrails_pii`, `detect_system_prompt_leakage`), Jailbreaking (`detect_jailbreak`, `detect_prompt_injection`), Brand risk (`bert_toxic`, `competitor_check`), plus bias, gibberish, formatting and SQL-predicate validators. Useful as a checklist of *what could be validated* when scoping the memo's option space. — [Guardrails Hub](https://hub.guardrailsai.com/)

  - **Do not use LLM Guard's `QPS` column for capacity planning.** As established in the latency section, it is characters/second from a single-threaded harness. There is no published request-throughput figure for any of these tools.
  - **The only request rate the source supports is single-stream:** `1000 / avg_latency_ms`. For the fastest published configuration in the entire corpus — PromptInjection, g5.xlarge GPU + ONNX, **7.65 ms avg** — that is **~131 requests/second, single-stream**. Anything above that requires a concurrency or batching factor that **is nowhere in the source**, so it cannot be asserted; it has to be measured on the client's fleet.

Without a measured concurrency figure you cannot honestly state the crossover volume — and quoting one you derived from a chars/second column is exactly the failure mode this brief exists to teach. State it as: *"the managed meter has no idle cost and the instance does; below some volume we have not measured, managed wins."* Then make the real argument — **the data must not leave the boundary** — which is a compliance argument and does not depend on the arithmetic at all.

### The three-term cost of control (the frame for the memo)

```
cost_of_control =  latency_cost          p99 ms × turns × what a slow turn costs
                +  dollar_cost           per-1k-unit meter, or instance-hours if self-hosted
                +  false_positive_cost   FP rate × turns × cost per wrongly-blocked interaction
```

**All three term bullets below are `[derived]`** — they are arithmetic over the sourced figures in the Latency and Dollars sections above. Recompute them against the client's own scanner set before they go in a memo.

- **`[derived]` Term 2 is the one everyone models and it is the smallest** — single-digit dollars per ten thousand documents. *From AWS's worked example: $4.00 for 10,000 PII-redacted summaries.*
- **`[derived]` Term 3 is the largest and is almost never modelled** — a precision-0.16 rail raises **5.25 false alarms per true catch**, which at a 7.2% base rate and 0.85 recall means **~32% of all traffic wrongly blocked**. *From NeMo's own ToxicChat evaluation; full arithmetic and the accuracy consistency-check are in the False positives section.*
- **`[derived]` Term 1 is buyable, but the default configuration is the expensive one — and this is where a naive sum goes wrong.** *From the three LLM Guard scanner tables + the serial-execution statement in the API docs.*

  | Three-scanner stack (Anonymize + PromptInjection + Toxicity) | Serial (**the shipped default**) | Parallel (you build it) |
  |---|---|---|
  | m5.xlarge, no ONNX — **p99** `325.71 + 316.97 + 188.11` | **~831 ms** | `max(325.71, 316.97, 188.11)` = **~326 ms** |
  | m5.xlarge, no ONNX — *avg* `177.13 + 212.87 + 86.41` | ~476 ms | ~213 ms |
  | m5.xlarge **+ ONNX** — p99 `179.93 + 107.01 + 35.71` | **~323 ms** | ~180 ms |
  | g5.xlarge **GPU + ONNX** — p99 `99.26 + 14.75 + 10.65` | **~125 ms** | ~99 ms |

  Three things follow. **(a)** Serial is the correct default because LLM Guard's own API executes "scanners in the order of configuration" with `SCAN_FAIL_FAST=False` — the ~326 ms parallel number is an engineering project, not a config flag. **(b)** ONNX + GPU takes the untuned 831 ms stack to ~125 ms, a **6.6× cut for a hardware line item and a one-line `use_onnx=True`** — that is the "buyable" claim, and it survives the correction. **(c)** Summing p99s is an **upper bound**, not a p99: the p99 of a sum is not the sum of p99s unless the scanners' latencies are perfectly correlated. Quote **~831 ms as the conservative ceiling and ~476 ms (sum of averages) as the central estimate**, and say which one you are using. *Do not quote 476 ms as a p99 — that conflation is precisely the error a previous revision of this brief shipped.*
- **`[derived]` Continuity is a fourth, non-monetary term.** *Synthesis of the four "currency traps" bullets at the top of this brief — each of the three status changes is individually sourced there; the pattern is the inference.* Three of the four projects in this landscape changed ownership, governance, or lifecycle status inside twelve months (LLM Guard archived 2026-07-09; Presidio left Microsoft for `data-privacy-stack`; Guardrails AI pivoted to a sales motion with a 404ing pricing page). Record for each candidate: **licence, last release date, governing entity, container-image origin.** A control that stops receiving security updates does not fail loudly — it quietly stops being a control.
- **The strategic caveat on NeMo, stated plainly:** the library is Apache-2.0 and vendor-neutral, but the *strongest configuration of it* points at NVIDIA assets — Llama 3.1 NemoGuard 8B Content Safety, the NemoGuard Jailbreak Detection NIM, and the GLiNER-PII NIM (`nvidia/gliner-pii`, default, reachable via `https://integrate.api.nvidia.com/v1/chat/completions` with an `NVIDIA_API_KEY`). Adopting NeMo on its open path is cheap; adopting it on its recommended path is an NVIDIA infrastructure decision. — [NeMo Guardrails library overview](https://docs.nvidia.com/nemo/guardrails/latest/index.html) · [NeMo PII Detection catalog](https://docs.nvidia.com/nemo/guardrails/configure-guardrails/guardrail-catalog/pii-detection)
