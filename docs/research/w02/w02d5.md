## Claims (each MUST carry a source)

- Ragas exposes RAG-specific metrics — Faithfulness (answer grounded in retrieved context, no unsupported claims), Context Precision (relevance/signal of retrieved chunks), Context Recall (completeness of retrieval), and Response Relevancy (how directly the answer addresses the query) — and these are the canonical four for evaluating a RAG pipeline. — [List of available metrics — Ragas](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)
- Faithfulness is computed by an LLM judge that extracts claims from the response and checks whether each can be inferred from the retrieved context (score = supported claims / total claims, 0–1). — [Faithfulness — Ragas](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)
- Response Relevancy generates artificial questions (default 3) from the response and averages their embedding cosine similarity to the user input: `score = (1/N) Σ cos(E_g_i, E_o)`. — [Response Relevancy / Answer Relevancy — Ragas](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/answer_relevance/)
- An eval harness needs a labeled test set; Ragas generates one synthetically via a two-phase pipeline: build a KnowledgeGraph from documents, enrich it with transformations, then synthesize queries. The default query distribution mixes SingleHopSpecific (~50%), MultiHopAbstract (~25%), and MultiHopSpecific (~25%) synthesizers via TestsetGenerator. — [Testset Generation for RAG — Ragas](https://docs.ragas.io/en/stable/getstarted/rag_testset_generation/)
- Chunking is a load-bearing retrieval decision; LangChain's RecursiveCharacterTextSplitter splits by a priority-ordered separator list (default `["\n\n", "\n", " ", ""]`), trying the largest semantic unit first and recursing to smaller separators only when a split exceeds chunk_size; chunk_overlap (base default 200, chunk_size default 4000) carries trailing characters into the next chunk to preserve context continuity. — [Splitting recursively — LangChain docs](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter) (defaults in source: [character.py L253](https://github.com/langchain-ai/langchain/blob/master/libs/text-splitters/langchain_text_splitters/character.py), [base.py __init__](https://github.com/langchain-ai/langchain/blob/master/libs/text-splitters/langchain_text_splitters/base.py))
- A production retrieval stage is two-stage: a bi-encoder retrieves ~100 candidates cheaply (queries and docs embedded independently), then a cross-encoder reranks by jointly encoding the query-document pair for higher accuracy on the top-k — trading compute for precision only where it matters. — [Retrieve & Re-Rank — Sentence Transformers](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html)
- pgvector 0.8.3 supports HNSW indexes (`CREATE INDEX ON items USING hnsw (embedding vector_l2_ops) WITH (m = 16, ef_construction = 64)`; defaults m=16, ef_construction=64, query-time ef_search=40), iterative index scans (since 0.8.0) for filtered queries, and hybrid search combining vector + Postgres full-text search via Reciprocal Rank Fusion or a cross-encoder. — [pgvector — GitHub](https://github.com/pgvector/pgvector)
- HNSW tuning trades recall for speed/build cost: higher m and ef_construction raise recall at the cost of build time and memory; higher ef_search raises recall at the cost of query latency. — [pgvector — GitHub](https://github.com/pgvector/pgvector)
- Chroma 1.5.9 provides a minimal end-to-end RAG store: `chromadb.PersistentClient(path=...)` for local persistence, `create_collection`/`get_or_create_collection`, `collection.add(documents=..., metadatas=..., ids=...)` with automatic embedding, and `collection.query(query_texts=..., n_results=...)` for similarity search; it also supports vector, hybrid, and full-text search. — [Chroma — GitHub](https://github.com/chroma-core/chroma)

## Concepts
- `faithfulness` — RAG metric: an LLM judge decomposes the generated answer into atomic claims and scores the fraction that can be inferred from the retrieved context (0–1); measures grounding / hallucination resistance, independent of whether the answer matches a reference.
- `context-precision` — Retrieval metric: of the chunks returned for a query, what fraction are actually relevant (signal vs. noise), with rank-awareness so relevant chunks placed higher score better. Pairs with `context-recall` (did retrieval surface all needed context).
- `recursive-character-splitting` — Chunking strategy that splits text on a priority-ordered separator list (`["\n\n","\n"," ",""]`), preferring the largest semantic unit and recursing to finer separators only when a piece exceeds `chunk_size`; `chunk_overlap` repeats trailing characters into the next chunk for context continuity.
- `bi-encoder-retrieval` — First-stage retrieval where query and documents are embedded independently into vectors, enabling precomputed document embeddings and fast approximate-nearest-neighbor search over a large corpus; cheap and scalable but less precise than joint encoding.
- `cross-encoder-rerank` — Second-stage reranking where the query and each candidate document are encoded jointly by a single transformer to produce a relevance score; far more accurate than a bi-encoder but too costly to run over the full corpus, so it is applied only to the top candidates.
- `hnsw-index` — Hierarchical Navigable Small World graph index for approximate nearest-neighbor vector search (pgvector, Chroma, etc.); `m` and `ef_construction` govern build-time graph quality/recall, while query-time `ef_search` trades latency for recall.
