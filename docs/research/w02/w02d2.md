## concept-ids

- `embedding-dimensionality` — The fixed length of an embedding vector (e.g. 1536 for text-embedding-3-small, 3072 for text-embedding-3-large); higher dims can capture more nuance but cost more storage, memory, and compute, and may exceed index limits.
- `matryoshka-representation-learning` — Training that encodes information coarse-to-fine so the leading k dimensions stand alone; lets you truncate the `dimensions` API parameter for smaller/faster embeddings with minimal quality loss.
- `similarity-metrics` — The distance/similarity function (cosine, dot product / inner product, Euclidean/L2) used to rank vectors; must match how embeddings were trained and is fixed at index creation in most stores.
- `ann-index-hnsw` — Hierarchical Navigable Small World graph index: high recall and fast queries at the cost of slower builds and higher memory; tuned via `m`, `ef_construction`, and `ef_search`.
- `ann-index-ivfflat` — Inverted-file flat index that partitions vectors into lists and probes a subset at query time; faster to build and lighter than HNSW but needs training data and generally lower recall.
- `sparse-vs-dense-retrieval` — Dense (semantic) embeddings vs sparse (lexical, e.g. BM25/SPLADE) vectors; combining both (hybrid retrieval) captures meaning and exact-term matches, and sparse indexes typically require a dot-product metric.

## Claims (each MUST carry a source)

### Embeddings & dimensionality
- An embedding maps text to a fixed-length vector; OpenAI's current models are `text-embedding-3-small` (default 1536 dims) and `text-embedding-3-large` (default 3072 dims), both accepting up to 8,192 input tokens — [Vector embeddings | OpenAI API](https://developers.openai.com/api/docs/guides/embeddings)
- Both `text-embedding-3-*` models were trained so you can shorten the vector by passing the `dimensions` API parameter ("remove some numbers from the end of the sequence") without losing concept-representing properties — [Vector embeddings | OpenAI API](https://developers.openai.com/api/docs/guides/embeddings)
- Shortening is effective enough that a `text-embedding-3-large` vector cut to 256 dims still outperforms an unshortened `text-embedding-ada-002` (1536 dims) on MTEB — [Vector embeddings | OpenAI API](https://developers.openai.com/api/docs/guides/embeddings)
- If you truncate dimensions yourself after generation (rather than via the API parameter), you must re-normalize the resulting vector — [Vector embeddings | OpenAI API](https://developers.openai.com/api/docs/guides/embeddings)
- The shortening behavior comes from Matryoshka Representation Learning (MRL): a single embedding encodes information coarse-to-fine, so the first k dimensions are usable standalone — enabling up to ~14x smaller embeddings / faster retrieval with no extra inference cost — [Matryoshka Representation Learning (arXiv:2205.13147)](https://arxiv.org/abs/2205.13147)

### Similarity metrics
- Pinecone supports three metrics chosen at index creation — cosine, Euclidean (squared), and dotproduct; cosine normalizes scores to [-1, 1] and is the common choice for normalized text embeddings — [Create an index | Pinecone Docs](https://docs.pinecone.io/guides/index-data/create-an-index)
- Sparse-vector (lexical) indexes in Pinecone MUST use the `dotproduct` metric — it is the only valid option for sparse — [Create an index | Pinecone Docs](https://docs.pinecone.io/guides/index-data/create-an-index)
- Chroma supports `l2` (squared Euclidean), `cosine`, and `ip` (inner product); the default space is `l2`, and the space cannot be changed after the index is created — [Configure Collections | Chroma Docs](https://docs.trychroma.com/docs/collections/configure)
- pgvector exposes six distance operators: `<->` L2, `<#>` negative inner product, `<=>` cosine, `<+>` L1, `<~>` Hamming (binary), `<%>` Jaccard (binary) — [pgvector (GitHub)](https://github.com/pgvector/pgvector)

### Vector stores: pgvector
- pgvector's current release is 0.8.3 and provides two ANN index types: HNSW (multilayer graph, better speed/recall, slower build, more memory) and IVFFlat (divides vectors into lists, needs training data) — [pgvector (GitHub)](https://github.com/pgvector/pgvector)
- HNSW defaults are `m = 16` and `ef_construction = 64`; query-time `hnsw.ef_search` defaults to 40 — [pgvector (GitHub)](https://github.com/pgvector/pgvector)
- pgvector TYPE storage limits (how many dims a column can hold): `vector` up to 16,000 dims, `halfvec` up to 16,000 dims, `bit` up to 64,000 dims, `sparsevec` up to 16,000 non-zero elements — [pgvector (GitHub)](https://github.com/pgvector/pgvector)
- pgvector INDEX limits (max dims that HNSW/IVFFlat can index, which are far below the storage limits): `vector` up to 2,000 dims, `halfvec` up to 4,000 dims, `sparsevec` (HNSW) up to 1,000 non-zero elements — [pgvector (GitHub)](https://github.com/pgvector/pgvector)
- Consequence: a raw 3072-dim `text-embedding-3-large` vector is fully *storable* in a `vector` column (limit 16,000) but exceeds the 2,000-dim `vector` INDEX limit, so to build an ANN index you must use `halfvec` (indexable to 4,000) or shorten the vector below 2,000 dims — [pgvector (GitHub)](https://github.com/pgvector/pgvector)

### Vector stores: Chroma
- Chroma's HNSW index is configured via `space`, `ef_construction` (default 100), `ef_search` (default 100), and `max_neighbors` (default 16) — [Configure Collections | Chroma Docs](https://docs.trychroma.com/docs/collections/configure)
- Chroma also offers a newer SPANN index for distributed / Chroma Cloud deployments, but its configuration is not currently user-customizable — [Configure Collections | Chroma Docs](https://docs.trychroma.com/docs/collections/configure)

### Vector stores: Pinecone
- Pinecone is a managed/serverless vector DB supporting dense indexes (semantic search), sparse indexes (lexical search), and document records that mix dense + sparse + full-text ranking — [Create an index | Pinecone Docs](https://docs.pinecone.io/guides/index-data/create-an-index)
