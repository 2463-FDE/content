## Claims (each MUST carry a source)

- RAG combines a pre-trained parametric model (the LLM's weights) with a non-parametric memory (a dense vector index of an external corpus), and the original RAG paper showed this produces "more specific, diverse and factual language" than a parametric-only baseline — [Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks (Lewis et al., 2020)](https://arxiv.org/abs/2005.11401)
- Retrieval (RAG) is preferred for dynamic/frequently-changing knowledge and broad knowledge bases because new information can be added to the index without retraining, whereas fine-tuning bakes knowledge into weights and is better for stylistic/domain nuance — modern practice often layers both (fine-tune for voice/jargon, RAG for fresh facts) — [Glean: RAG vs fine-tuning guide](https://www.glean.com/blog/retrieval-augemented-generation-vs-fine-tuning)
- For knowledge bases under ~200,000 tokens (~500 pages), you can skip retrieval and put the whole corpus in the prompt; RAG (and chunking) becomes necessary only when the corpus exceeds the context window — [Anthropic: Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)
- RecursiveCharacterTextSplitter splits hierarchically using the default separator order `["\n\n", "\n", " ", ""]` (paragraphs → lines → words → characters), keeping semantically-related text together as long as possible — [LangChain: Splitting recursively](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter)
- chunk_overlap exists to mitigate information loss when context is split across chunk boundaries; common guidance is 10–20% of chunk size (e.g. 50–100 tokens of overlap on a 500-token chunk) — [LangChain: Splitting recursively](https://docs.langchain.com/oss/python/integrations/splitters/recursive_text_splitter)
- Three core chunking families: fixed-size (simplest, size + optional overlap), recursive (hierarchical separators, recommended default for most prose), and semantic (groups sentences by embedding similarity into context-aware chunks); the right choice depends on document structure and query patterns — [IBM: Chunking strategies for RAG](https://www.ibm.com/think/tutorials/chunking-strategies-for-rag-with-langchain-watsonx-ai)
- OpenAI's current embedding models: text-embedding-3-large defaults to 3072 dimensions and text-embedding-3-small to 1536; both support a `dimensions` parameter (Matryoshka) to shorten vectors, and a 256-dim text-embedding-3-large still beats a full 1536-dim ada-002 on MTEB — [OpenAI: Vector embeddings guide](https://developers.openai.com/api/docs/guides/embeddings)
- pgvector 0.8.3 supports two ANN index types — HNSW (better speed/recall tradeoff, no training step, can be built on an empty table) and IVFFlat — created via `CREATE INDEX ON items USING hnsw (embedding vector_l2_ops) WITH (m = 16, ef_construction = 64);`, with distance operators `<->` (L2), `<=>` (cosine), `<#>` (negative inner product); without an index it does exact search — [pgvector README](https://github.com/pgvector/pgvector)
- Chroma attaches an embedding function to a collection and applies it transparently on `add`/`update`/`upsert`/`query`; if none is specified it uses DefaultEmbeddingFunction (Sentence Transformers all-MiniLM-L6-v2, 384-dim, runs locally) — [Chroma: Embedding Functions](https://docs.trychroma.com/docs/embeddings/embedding-functions)
- Hybrid retrieval (dense embeddings + lexical BM25) outperforms either alone because embeddings catch semantic matches while BM25 catches exact term/phrase matches; Anthropic's Contextual Retrieval prepends chunk-specific context before embedding and BM25 indexing, cutting top-20 retrieval failures by 49% (35% from contextual embeddings alone) and by 67% when combined with reranking — [Anthropic: Contextual Retrieval](https://www.anthropic.com/news/contextual-retrieval)
