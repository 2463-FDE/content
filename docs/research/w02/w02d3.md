## Claims (each MUST carry a source)

- Dense (semantic) search captures meaning and matches synonyms/paraphrases, but misses exact-keyword and domain-specific terminology hits; lexical/sparse search is the inverse — they are complementary, which is the entire motivation for hybrid search. — [Hybrid search - Pinecone Docs](https://docs.pinecone.io/guides/search/hybrid-search)
- Sparse keyword retrieval (BM25-style) excels at exact term matching while dense vectors disambiguate meaning; e.g. for "How to catch an Alaskan Pollock" dense vectors read "catch" as fishing while sparse matches the literal phrase "Alaskan Pollock." — [Hybrid Search Explained - Weaviate](https://weaviate.io/blog/hybrid-search-explained)
- BM25 scores and sparse-weight outputs are NOT normalized to the dense vector range, so without explicit weighting the sparse component dominates the combined score — normalization/weighting is mandatory before production. — [Hybrid search - Pinecone Docs](https://docs.pinecone.io/guides/search/hybrid-search)
- Hybrid fusion is commonly controlled by an alpha convex combination `alpha*dense + (1-alpha)*sparse`: alpha≈0.75 is a good default for natural-language queries, 0.5 balances both signals, and ~0.25 favors high-keyword-specificity queries (SKUs, technical IDs, named entities). — [Hybrid search - Pinecone Docs](https://docs.pinecone.io/guides/search/hybrid-search)
- Reciprocal Rank Fusion (RRF) combines result lists by summing reciprocal ranks rather than raw scores, so it is robust to incompatible score scales between BM25 and dense retrieval; Weaviate ships RRF as the default `rankedFusion` with `relativeScoreFusion` as the score-based alternative. — [Hybrid Search Explained - Weaviate](https://weaviate.io/blog/hybrid-search-explained)
- The standard production pattern is two-stage: hybrid retrieval pulls a wide candidate set (e.g. dense + sparse each returning ~100), then a re-ranker collapses it to a small final set — "hybrid boosts recall; reranking restores precision." — [Hybrid Search with Reranking - Qdrant](https://qdrant.tech/articles/hybrid-search/)
- Cross-encoder re-rankers (Cohere Rerank 3.5) take the query plus candidate documents jointly and return relevance-scored ordering; v3.5 has a 4096-token context window and SOTA performance on BEIR and multilingual retrieval. — [Announcing Rerank-v3.5 - Cohere](https://docs.cohere.com/changelog/rerank-v3.5)
- Pinecone's cascading retrieval runs dense and sparse in parallel then re-ranks the merged candidates into a unified score; rerankers improved performance by up to 48% (avg 24%) over dense-only vector search. — [Introducing cascading retrieval - Pinecone](https://www.pinecone.io/blog/cascading-retrieval/)
- Late-interaction models (ColBERT) represent each document as per-token embeddings and score with MaxSim; in practice they are used as a re-ranking stage — retrieve cheaply with single-vector search, then rerank with the late-interaction model to recover linguistic nuance without scanning the whole corpus. — [Hybrid Search with Reranking - Qdrant](https://qdrant.tech/articles/hybrid-search/)
- Postgres can do hybrid natively: pgvector 0.8.0 (released 2024-10-30) added iterative index scans, which prevent over-filtering by continuing to scan an HNSW/IVFFlat index until enough rows pass `WHERE`-clause filters. — [pgvector 0.8.0 Released - PostgreSQL](https://www.postgresql.org/about/news/pgvector-080-released-2952/)
- pgvector ships a `sparsevec` type for keyword/lexical sparse vectors (alongside the `halfvec` half-precision type) — both introduced in pgvector 0.7.0 (2024-04-29) and documented in the current README, enabling dense + sparse columns in the same Postgres table. — [pgvector README - GitHub](https://github.com/pgvector/pgvector)
- The current stable pgvector release as of 2026-06 is 0.8.3 (2026-06-17); 0.8.1 (2025-09-04) added Postgres 18 support and 0.8.2 (2026-02-25) shipped a buffer-overflow fix, so any "verified current" stamp must point past 0.8.0. — [pgvector CHANGELOG - GitHub](https://github.com/pgvector/pgvector/blob/master/CHANGELOG.md)

## Concept IDs (interview question-bank seeds)

Each id carries a one-line definition so the question-bank author seeds from a fixed meaning, not from prose.

- dense-vs-sparse-retrieval — the trade-off between dense embedding similarity (captures semantic meaning/synonyms) and sparse lexical scoring like BM25 (captures exact keyword/term matches); they fail on opposite query types and are complementary.
- hybrid-retrieval — running dense and sparse retrieval together and merging their results (via weighted score combination or rank fusion) to get both semantic recall and keyword precision in one query.
- reciprocal-rank-fusion — RRF, a fusion method that combines multiple ranked result lists by summing 1/(k+rank) per document instead of raw scores, making it robust to incompatible score scales between BM25 and dense retrieval (Weaviate's default `rankedFusion`).
- cross-encoder-reranking — a second-stage re-ranker (e.g. Cohere Rerank 3.5) that feeds the query and each candidate document jointly through a transformer to produce a precise relevance score, reordering a recall-oriented candidate set.
- late-interaction-colbert — ColBERT-style retrieval that stores per-token embeddings per document and scores via MaxSim (max-similarity per query token), typically used as a reranking stage to recover fine-grained linguistic nuance after cheap single-vector retrieval.
