## Claims

### The vocabulary (run / span / trace / thread / trajectory)

- A **run** is a single unit of work an agent performs — an LLM call, a prompt format, a document retrieval — and LangSmith states the equivalence outright: "If you are familiar with OpenTelemetry, you can think of a run as a span." — [Observability concepts](https://docs.langchain.com/langsmith/observability-concepts)
- A **trace** is "a collection of runs for a single operation": one user request that triggers an agent → model call → tool → model call again puts all of those runs in one trace, bound by a unique trace ID. — [Observability concepts](https://docs.langchain.com/langsmith/observability-concepts)
- A **thread** is a sequence of traces representing one multi-turn session; a *turn* is one exchange (user message + everything the agent does in response) and each turn is its own trace. Traces are grouped into a thread by passing a `thread_id` metadata key. — [Observability concepts](https://docs.langchain.com/langsmith/observability-concepts)
- A **trajectory** is a flat, ordered, de-duplicated list of messages projected over a thread's traces with nesting removed — "the path an agent took from start to finish." — [Observability concepts](https://docs.langchain.com/langsmith/observability-concepts)
- The three shapes are explicitly differentiated by use: reach for a **trace** "when you are debugging why one operation failed or ran slow," a **thread** for behavior across turns with timing and nesting intact, a **trajectory** to read what was exchanged without execution detail. — [Observability concepts](https://docs.langchain.com/langsmith/observability-concepts)
- A **project** is the container for all traces of a single application or service. — [Observability concepts](https://docs.langchain.com/langsmith/observability-concepts)

### Why the span is the unit of an LLM call

- Run type is what makes a span legible: `@traceable(run_type="llm")` marks a function as an LLM call "so LangSmith can render token counts and latency correctly"; `run_type="tool"` marks tool spans. Default run type for the `RunTree` root in the docs' example is `chain`. — [Custom instrumentation](https://docs.langchain.com/langsmith/annotate-code)
- Wrapping is compositional: the OpenAI wrapper logs "every LLM call automatically… as a nested span," and `@traceable` on the calling function "captures the full pipeline in one trace, with the tool call and LLM call as nested spans." — [Tracing quickstart](https://docs.langchain.com/langsmith/observability-quickstart)
- There are exactly three manual-instrumentation mechanisms: the `@traceable`/`traceable` decorator (recommended for most cases), the `trace` context manager (Python only), and the low-level `RunTree` API for "explicit trace construction." — [Observability concepts](https://docs.langchain.com/langsmith/observability-concepts) · [Custom instrumentation](https://docs.langchain.com/langsmith/annotate-code)
- The `RunTree` API makes the parent/child edge literal: create a root `RunTree(name="Chat Pipeline", run_type="chain", inputs={...})`, `.post()` it, then `pipeline.create_child(name="OpenAI Call", run_type="llm", inputs={"messages": messages})`, and close with `.end(outputs=...)` + `.patch()`. — [Custom instrumentation](https://docs.langchain.com/langsmith/annotate-code)
- Turning tracing on is an environment variable, not a code change: `LANGSMITH_TRACING=true` plus `LANGSMITH_API_KEY`; `LANGSMITH_PROJECT` routes traces to a named project, and a default project is created automatically on first ingestion if unset. — [Tracing quickstart](https://docs.langchain.com/langsmith/observability-quickstart)
- Non-US accounts must also set `LANGSMITH_ENDPOINT` to their regional API URL (e.g. `https://eu.api.smith.langchain.com`) or the API key "won't be recognized and requests will fail to authenticate" — with no trailing slash. — [Tracing quickstart](https://docs.langchain.com/langsmith/observability-quickstart)

### Run trees break in two specific, teachable ways

- Nesting relies on implicit context propagation through Python `contextvars`; under **Python < 3.11** `asyncio` "lack[s] proper `contextvar` support, which can lead to disconnected traces" — child runs surface as separate top-level traces. Fix: upgrade to 3.11+, or pass the parent explicitly via `langsmith_extra={"parent": run_tree}` / `ls.tracing_context(parent=run_tree)` / the LangChain `config`. — [Troubleshoot trace nesting](https://docs.langchain.com/langsmith/nest-traces)
- **`ThreadPoolExecutor` "by default breaks tracing"** because "Python's contextvars start empty within new threads"; LangSmith ships `langsmith.utils.ContextThreadPoolExecutor` which "automatically handles context propagation." — [Troubleshoot trace nesting](https://docs.langchain.com/langsmith/nest-traces)

### Hard limits worth putting on a slide

- **A trace is capped at 25,000 runs.** "Once the trace reaches this limit, LangSmith will reject any additional runs that you send for that trace." — [Observability concepts](https://docs.langchain.com/langsmith/observability-concepts)
- **LangSmith SaaS retains trace data for 180 days from ingestion**, after which traces are permanently deleted with limited metadata kept for usage stats. To keep data beyond that, add it to a dataset — "datasets persist indefinitely, even after the source trace is deleted." — [Observability concepts](https://docs.langchain.com/langsmith/observability-concepts)

### Latency, cost, and token attribution

- Cost and token usage roll up three levels: the **trace tree** "displays the total usage for the entire trace, aggregated values for each parent run and token and cost breakdowns for each child run"; **project stats** show totals for all traces in a project; **dashboards** show trends over time. — [Cost tracking](https://docs.langchain.com/langsmith/cost-tracking)
- The UI splits usage into three buckets: **Input** (prompt tokens; subtypes cache reads, text, image), **Output** (response tokens; subtypes reasoning, text, image), and **Other** ("costs from tool calls, retrieval steps, or any custom runs") — so non-LLM spans can carry cost too. — [Cost tracking](https://docs.langchain.com/langsmith/cost-tracking)
- Automatic cost computation requires three inputs: **token counts**, the **model and provider**, and a **model price** entry. It is free when using LangChain, `@traceable` over OpenAI/Anthropic/OpenAI-compatible models, or the LangSmith OpenAI/Anthropic wrappers. — [Cost tracking](https://docs.langchain.com/langsmith/cost-tracking)
- Manual attribution is how you price non-LLM work or non-linear pricing: set `usage_metadata` on the run tree via `get_current_run_tree()` inside a `@traceable` function, or return `usage_metadata` as a top-level key of the function's output. — [Log LLM calls](https://docs.langchain.com/langsmith/log-llm-trace)
- Supported `usage_metadata` fields: `input_tokens`, `output_tokens`, `total_tokens` (optional, inferable), `input_token_details` (`cache_read`, `cache_creation`, `cache_read_over_200k`, `ephemeral_5m_input_tokens`, `ephemeral_1h_input_tokens`, `audio`, `text`, `image`), `output_token_details` (`reasoning`, `audio`, `text`, `image`); plus `input_cost` / `output_cost` / `total_cost` to submit money directly. — [Log LLM calls](https://docs.langchain.com/langsmith/log-llm-trace)
- **Time-to-first-token is auto-populated for streaming LLM runs** under `traceable` or the SDK wrappers — but if you use the `RunTree` API directly you must emit `run_tree.add_event({"name": "new_token"})` on the first token or TTFT stays empty. — [Log LLM calls](https://docs.langchain.com/langsmith/log-llm-trace)
- **The silent-wrongness trap: "Metadata and tags are not propagated from parent to child runs, or vice versa."** To group both trace charts and LLM-call charts by the same key, that metadata must be attached to the root run *and* the LLM run. Same rule for threads — without `session_id`/`thread_id` on child runs, "token counts and costs from those runs won't be included in thread-level aggregations." — [Dashboards](https://docs.langchain.com/langsmith/dashboards) · [Cost tracking](https://docs.langchain.com/langsmith/cost-tracking)

### Aggregation: prebuilt dashboards map onto golden signals

- Prebuilt dashboards are "created automatically for each project" and cover trace count, error rates, token usage and more, reachable from the **Dashboard** button on the tracing-project page. — [Dashboards](https://docs.langchain.com/langsmith/dashboards)
- The prebuilt sections are: **Traces** (count, latency, error rates), **LLM Calls** (count + latency, `run_type == "llm"`), **Cost & Tokens** (total and per-trace, broken down by token type), **Tools** (counts, error rates, latency by tool name — top 5), **Run Types** (stats for runs that are immediate children of the root run — top 5, "helps in understanding the high-level execution path of agents"), and **Feedback Scores** (top 5 feedback types). — [Dashboards](https://docs.langchain.com/langsmith/dashboards)
- Runs can be enriched with **feedback** (a tag + score, continuous or categorical, bound to a run by run ID), **tags** (strings for categorize/filter/group), and **metadata** (key-value pairs, e.g. app version or environment). — [Observability concepts](https://docs.langchain.com/langsmith/observability-concepts)

### Reading a trace in the UI

- The trace side panel offers three views with keyboard switches: **Messages** (beta, `M`) — the conversation layer for finding *where* to look; **Turns** (`T`) — per-turn cards; **Details** (`D`) — "the debugging layer. Drill into a specific run to inspect inputs, outputs, timing, token counts, errors, and metadata." — [View traces](https://docs.langchain.com/langsmith/view-traces)
- Threads and Turns "are only available for runs instrumented with a `thread_id` metadata field" — without it you see traces as individual runs. — [View traces](https://docs.langchain.com/langsmith/view-traces)
- The documented debugging loop is: scan Messages for the anomaly (bad tool result, unexpected subagent handoff, **a latency spike**) → click through to the exact run in Details → inspect inputs/outputs/timing/errors → return to the thread. — [View traces](https://docs.langchain.com/langsmith/view-traces)

### Handing the client a URL instead of an adjective

- To share: open the trace, click **Share** in the more menu at the top of the Details view, copy the public link. "Shared traces are accessible to anyone with the link, even without a LangSmith account. They can view the trace but not edit it." — [Manage a trace](https://docs.langchain.com/langsmith/manage-trace)
- The public URL shape is `https://smith.langchain.com/public/<uuid>/r` — the LangSmith OTel docs ship a live one as their "view the traces" example: `https://smith.langchain.com/public/a762af6c-b67d-4f22-90a0-728df16baeba/r`. — [Trace with OpenTelemetry](https://docs.langchain.com/langsmith/trace-with-opentelemetry)
- **The governance warning is in the docs, bolded:** "Sharing a trace publicly will make it accessible to anyone with the link. Make sure you're not sharing sensitive information." A trace contains "every run, with full inputs and outputs" — so sharing is a disclosure decision, not a UI convenience. — [Manage a trace](https://docs.langchain.com/langsmith/manage-trace) · [Observability concepts](https://docs.langchain.com/langsmith/observability-concepts)
- Unsharing is two-path and auditable: open the shared trace → **Public** in the toolbar → **Unshare**; or **Settings → Shared URLs** to see "all publicly shared traces in the selected workspace" with per-trace Unshare. — [Manage a trace](https://docs.langchain.com/langsmith/manage-trace)
- For self-hosted LangSmith inside a VPC, "the public link is accessible only to members authenticated within your VPC," and LangChain recommends configuring a private URL for enhanced security. — [Manage a trace](https://docs.langchain.com/langsmith/manage-trace)
- **The trace ID is the join key to ordinary logs:** the **See Logs** button in the Details view jumps to the deployment's server logs with "the Filters box… automatically pre-fill[ed] with the Trace ID from the trace you just viewed" (Cloud SaaS and fully self-hosted only). — [Manage a trace](https://docs.langchain.com/langsmith/manage-trace)
- Traces can be deleted before expiry via the `delete_runs` API endpoint, scoped by `session_id` (project), a list of `trace_ids`, or `metadata` key-value pairs — the compliance escape hatch when something was captured that shouldn't have been. — [Manage a trace](https://docs.langchain.com/langsmith/manage-trace)

### OpenTelemetry GenAI semantic conventions (context only — d4 goes deeper)

- **Currency:** the GenAI semantic conventions have **moved out of the main OpenTelemetry semantic-conventions repo**. `opentelemetry.io/docs/specs/semconv/gen-ai/` now reads: "GenAI semantic conventions have moved to the OpenTelemetry GenAI semantic conventions repository. This page has moved and is no longer maintained in this repository." — [OTel: GenAI semconv (moved)](https://opentelemetry.io/docs/specs/semconv/gen-ai/)
- The canonical home is `open-telemetry/semantic-conventions-genai`, covering "spans, metrics, and events for GenAI clients, MCP (Model Context Protocol), and provider-specific conventions (OpenAI, etc.)"; it extends the core semantic conventions using Weaver, is Apache-2.0, and shows 608 commits / 226 stars as of 2026-08-06. Its README still lists Schema URL as "TODO." — [semantic-conventions-genai](https://github.com/open-telemetry/semantic-conventions-genai)
- The GenAI client-span conventions are **Status: Development** — not stable, expect churn. Span kind SHOULD be `CLIENT` (MAY be `INTERNAL` for in-process models); span name SHOULD be `{gen_ai.operation.name} {gen_ai.request.model}`. — [GenAI client spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)
- A GenAI span "SHOULD cover the duration of the operation, starting when it is initiated and ending when the response is fully received"; if a transient issue caused an automatic retry, the span "SHOULD cover the duration of the logical operation with all retries" — one logical call, one span, retries inside it. — [GenAI client spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)
- Only two attributes are `Required` on an inference span: `gen_ai.operation.name` (`chat`, `generate_content`, `text_completion`) and `gen_ai.provider.name` (`openai`, `gcp.gen_ai`, `gcp.vertex_ai`). `error.type` is conditionally required when the operation ends in an error. — [GenAI client spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)
- Token attributes are `Recommended`: `gen_ai.usage.input_tokens`, `gen_ai.usage.output_tokens`, `gen_ai.usage.reasoning.output_tokens`, `gen_ai.usage.cache_creation.input_tokens`, `gen_ai.usage.cache_read.input_tokens`. **Rollup rule:** cache-creation and cache-read input tokens "SHOULD be included in `gen_ai.usage.input_tokens`" — `input_tokens` is the total including cached, not the remainder. — [GenAI client spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)
- LangSmith accepts OTLP directly: `OTEL_EXPORTER_OTLP_ENDPOINT=https://api.smith.langchain.com/otel` with `OTEL_EXPORTER_OTLP_HEADERS="x-api-key=<key>"` (append `/v1/traces` if only sending traces; add `Langsmith-Project=<name>` for a non-default project). — [Trace with OpenTelemetry](https://docs.langchain.com/langsmith/trace-with-opentelemetry)
- The documented topology is **fanout**: "The OpenTelemetry SDK instruments your application code and emits spans. Spans travel via the OTLP protocol to an OpenTelemetry Collector, which batches and routes them to one or more destinations simultaneously (*fanout*)." — i.e. instrumenting once keeps the telemetry portable across backends. — [Trace with OpenTelemetry](https://docs.langchain.com/langsmith/trace-with-opentelemetry)
- For LangChain/LangGraph apps the OTel path is one flag — `LANGSMITH_OTEL_ENABLED=true` — requiring `langsmith>=0.3.18`, with `>=0.4.25` recommended "to benefit from important OpenTelemetry fixes." — [Trace with OpenTelemetry](https://docs.langchain.com/langsmith/trace-with-opentelemetry)
- Version stamp: `langsmith` is at **0.10.16**, uploaded 2026-08-05, `requires_python >=3.10`. — [PyPI JSON API — langsmith](https://pypi.org/pypi/langsmith/json)

## Concept IDs

Tightly scoped to this day. (Guardrails, alerting/SLOs, evaluation, and OTel deep-dive belong to other days of w07.)

1. `trace-span-run-vocabulary` — run = span = one unit of work; trace = the collection of runs for one operation, bound by trace ID; project = container. The words that replace "it's slow."
2. `run-tree-nesting` — parent/child construction (`@traceable`, `trace`, `RunTree.create_child`), run types (`llm` / `tool` / `chain` / `retriever`), and the two documented ways nesting breaks (asyncio < 3.11, `ThreadPoolExecutor`).
3. `span-latency-attribution` — per-run start/end timing, the trace waterfall, TTFT for streaming runs, and locating *which* span owns the latency rather than blaming "the model."
4. `token-and-cost-rollup` — `usage_metadata` fields, input/output/other buckets, automatic vs manual cost, three-level rollup (child run → parent run → trace → project), and the no-metadata-propagation trap.
5. `shareable-trace-url` — `smith.langchain.com/public/<uuid>/r`, account-free viewing, unshare inventory under Settings → Shared URLs, and the "full inputs and outputs" disclosure warning.
6. `thread-vs-trace-vs-trajectory` — `thread_id` grouping, one trace per turn, and when to reach for each shape when reconstructing a client-reported incident.

## Client hook

### Healthcare (Week 7 — "Observability / SRE / Guardrails")

**The ask:** *"The portal is flaky and I'm always the last to know. Give me visibility — and make sure that AI summary thing can't say anything crazy."*
**In the materials:** a week of raw latency logs with **no structured tracing**, plus an incident note — *"intake froze ~20 min, no alert fired."*
**Hidden problem (this day's half):** no observability on the intake/eligibility path, so availability cliffs are invisible — no alert, no MTTR.

**What d1 answers, specifically:** the raw latency logs cannot tell you *where* the 20 minutes went, because a log line has no parent and no duration boundary. Instrumenting the intake path as a **run tree** — root `chain` span for the intake request, child `tool` span for the eligibility/payer call, child `llm` span for the summary — is what converts "intake froze" into "the eligibility span held for 19m48s and the LLM span never started." That is the *structured tracing on the critical span* the deliverable explicitly names. Three concrete carry-overs into the deliverable:

- **The critical span is the eligibility/payer call**, and it correlates with the W3 payer-outage pattern — a span boundary there is what makes the W3 finding measurable rather than anecdotal, and gives the alert (built later in the week) something with a `latency` and an `error.type` to fire on.
- **Trace ID is the join key** between the LLM telemetry and the existing app logs (LangSmith's See Logs pre-fills the Trace ID filter). The client already has logs; d1's contribution is giving those logs a correlating key instead of a timestamp guess.
- **A shared trace URL is the wrong artifact here without a scrub.** Traces carry "every run, with full inputs and outputs" — for an intake path that's PHI. Teach the share button *with* its warning: this is the hinge into the W8 Safe-Harbor de-identification deliverable and the reason redaction happens before emission, not before pressing Share. The unshare inventory (Settings → Shared URLs) is the standing audit item.

*(The "can't say anything crazy" half of the ask — the hallucinated-medication guardrail — is a different day. d1 only supplies the span the guardrail's outcome gets recorded on.)*

### Finance (Week 7 — "Observability / SRE / Guardrails")

**The ask:** *"Payments feel flaky and finance complains about 'noise' at month-end. Give me visibility so I'm not the last to know."*
**In the materials:** raw payment-path logs with no tracing, with **double-fund events from the W5 idempotency gap buried in them**; plus a ledger-vs-settlement variance nobody reconciles.
**Hidden problem (this day's half):** the unidempotent double-funds are **invisible without instrumentation**.

**What d1 answers, specifically:** "buried in the logs" is exactly the failure mode a trace fixes. A double-fund is two spans that should have been one — same logical operation, two trace IDs (or two child runs under one root). You cannot see that in a flat log stream; you can see it immediately in a run tree, and you can *query* for it once each payment span carries an idempotency-key **metadata** field. Three concrete carry-overs:

- **The critical span is the payment authorization/capture call.** Instrument it as the root of a trace with the idempotency key as run metadata — that turns "did we double-fund?" from a log-grep into a filter over traces.
- **Metadata does not propagate parent→child.** For finance this is not trivia: if the tenant/merchant/idempotency key sits only on the root run, every per-LLM-call and per-tool-call cost and error chart silently drops it. Put the correlation key on *both* the root and the child spans, or the reconciliation break-report you build later this week will aggregate against an incomplete population.
- **Cost attribution is the "noise" translation layer.** Sam is in the room now, and Sam does not buy "the AI scorer is expensive." The three-bucket rollup (input / output / **other** — tool calls and retrieval steps) plus per-trace cost gives a **dollars-per-payment-decision** number sourced from the same trace tree that shows the latency. The trace tree is the single artifact that answers "is it slow?" and "what does it cost?" in one screen — which is precisely the "visibility so I'm not the last to know" ask.
- **The shared trace URL is the deliverable's demo surface.** For finance the PHI risk is a PCI/PII risk instead — payment payloads in span inputs. Same rule, same unshare inventory, and the same reason to scrub before emission.
