# w07d2 — Modules, environments, secrets, and drift

**Verified:** 2026-10-14  
**Authority:** provisionally authoritative LTM derivative, Week 7 TUE; first-party Terraform documentation below. Static review only.

## Source-assigned scope

Critical plan-diff reading; module structure and reuse; environment separation; client-stack topology; secrets and state hygiene; drift detection; HCP Terraform/OpenTofu landscape awareness; Claude-assisted plan review with a strict never-auto-apply rule.

## Reviewed claims

- A module is a collection of Terraform resources managed together. Reuse does not justify hiding provider differences or creating an abstraction no reviewer can understand. — [Modules](https://developer.hashicorp.com/terraform/language/modules)
- Child modules receive provider configurations explicitly when aliases or multiple configurations are involved. Provider aliases and the `providers` map make those relationships reviewable. — [Providers within modules](https://developer.hashicorp.com/terraform/language/modules/develop/providers)
- CLI workspaces are separate state instances in one working directory; HashiCorp explicitly notes they are not appropriate for every decomposition or for deployments requiring separate credentials and access controls. — [Workspaces](https://developer.hashicorp.com/terraform/language/state/workspaces)
- Refresh-only planning lets reviewers reconcile state with remote changes without proposing configuration changes; ordinary plans can reveal drift while also containing intended changes. — [Refresh-only mode](https://developer.hashicorp.com/terraform/tutorials/state/refresh)
- Marking a variable sensitive redacts some CLI/UI display but does not remove the value from state. Ephemeral values and write-only arguments have specific version and provider support requirements; this lesson does not claim universal availability. — [Sensitive values](https://developer.hashicorp.com/terraform/language/manage-sensitive-data)
- Generated configuration or review comments remain proposals. Human reviewers own resource scope, state migration, deletion/replacement, security, cost, and approval.

## Review rubric

Read a plan by action, address, provider, environment, replacement reason, unknown value, data exposure, cost/security consequence, and rollback evidence. Reject blanket "looks safe" summaries and any automatic apply suggestion.
