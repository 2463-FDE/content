## Claims

### Plan first: separate exploration from execution
- **Why:** "Letting Claude jump straight to coding can produce code that solves the wrong problem." The recommended workflow is four phases — **Explore** (plan mode: "Claude reads files and answers questions without making changes"), **Plan** (ask for a detailed implementation plan; `Ctrl+G` "to open the plan in your text editor for direct editing before Claude proceeds"), **Implement** (exit plan mode, code "verifying against its plan"), **Commit** (descriptive message + PR). [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **Mechanics:** "For changes you want to review before they touch disk, switch to plan mode. Claude reads files and proposes a plan but makes no edits until you approve." Start with `claude --permission-mode plan` or toggle with `Shift+Tab` mid-session. [Common workflows — Claude Code Docs](https://code.claude.com/docs/en/common-workflows)
- **When NOT to plan (teach the judgment call):** "Plan mode is useful, but also adds overhead... Planning is most useful when you're uncertain about the approach, when the change modifies multiple files, or when you're unfamiliar with the code being modified. If you could describe the diff in one sentence, skip the plan." [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **Spec-by-interview variant:** for larger features, "have Claude interview you first" using AskUserQuestion, write the spec to `SPEC.md`, then "start a fresh session to execute it" — clean context, written spec. "Time spent making the spec precise pays off more than time spent watching the implementation." [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)

### Verification loops: give the agent a check it can run
- **Core principle (verbatim):** "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop... Give Claude something that produces a pass or fail, and the loop closes on its own." The check is "a test suite, a build exit code, a linter, a script that diffs output against a fixture, or a browser screenshot compared against a design." [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **Gating ladder (escalating enforcement):** run the check in one prompt → set it as a `/goal` condition re-checked every turn → a **Stop hook** that "runs your check as a script and blocks the turn from ending until it passes" → a fresh-context verification subagent so "the agent doing the work isn't the one grading it." [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **Evidence over assertion:** "Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned, or a screenshot." Failure pattern named in the doc: "The trust-then-verify gap... If you can't verify it, don't ship it." [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **Why this matters — the perception gap is real:** METR's RCT (16 experienced OSS maintainers, 246 tasks in mature repos, randomized AI-allowed vs not, early-2025 tools): "allowing AI actually increases completion time by 19% — AI tooling slowed developers down," while developers *believed* AI had sped them up 20% (and forecast 24%; economists predicted 39% faster). Self-reported speed-up is not a measurement — build verification into the loop. [Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity — arXiv 2507.09089](https://arxiv.org/abs/2507.09089)

### TDD with agents: tests are the spec the agent can't argue with
- **Kent Beck's framing (primary source):** augmented coding ≠ vibe coding — "In vibe coding you don't care about the code, just the behavior of the system"; in augmented coding "you care about the code, its complexity, the tests, & their coverage." His system prompt mandates strict TDD ("make it run, then improve structure. Always run all the tests... each time"), and his three abort signals for a misbehaving agent are: "Loops," "Functionality I hadn't asked for," and "Any indication that the genie was cheating, for example by disabling or deleting tests." Payoff: "I make more consequential programming decisions per hour, fewer boring vanilla decisions." [Augmented Coding: Beyond the Vibes — Kent Beck](https://newsletter.kentbeck.com/p/augmented-coding-beyond-the-vibes)
- **Reward hacking is the failure mode to teach:** test-deletion/test-disabling is the agent equivalent of gaming the metric — Beck treats it as an immediate stop-and-intervene signal (above). Guard rails: tests in a separate commit, hooks blocking edits to test files, or a separate reviewer session.
- **Writer/Reviewer and test-first splits (official pattern):** "A fresh context improves code review since Claude won't be biased toward code it just wrote" — one session implements, a second reviews; "You can do something similar with tests: have one Claude write tests, then another write code to pass them." This is TDD's red/green separation enforced by context isolation rather than willpower. [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **Prompt-level red bar:** the docs' recommended bug-fix prompt shape is TDD-native: "write a failing test that reproduces the issue, then fix it." [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)

### AI code review: fast, useful, non-blocking — and not free
- **Copilot code review (GitHub official):** request on any PR via the Reviewers sidebar, `gh pr create --reviewer @copilot`, or org rulesets for automatic review (with optional re-review on new pushes). Reviews take "less than 30 seconds" and include "suggested changes which you can apply with a couple of clicks." Critically, Copilot "always leaves a 'Comment' review, not an 'Approve' review or a 'Request changes' review" — it never counts toward required approvals and never blocks merge. AI review complements, never replaces, human review. [Using GitHub Copilot code review — GitHub Docs](https://docs.github.com/en/copilot/using-github-copilot/code-review/using-copilot-code-review)
- **Claude Code Review (Anthropic managed, research preview):** "a fleet of specialized agents examine the code changes in the context of your full codebase," then "a verification step checks candidates against actual code behavior to filter out false positives"; findings are deduplicated, severity-ranked (🔴 Important / 🟡 Nit / 🟣 Pre-existing) and posted inline. "Findings are tagged by severity and don't approve or block your PR." Tunable via `REVIEW.md` (injected as highest-priority instructions: severity redefinition, nit caps, skip rules, verification bar). Triggers: on PR open, every push, or `@claude review` / `@claude review once`. Cost: "$15-25" per review, ~20 min. [Code Review — Claude Code Docs](https://code.claude.com/docs/en/code-review)
- **Local pre-push review:** the `/code-review` command "reviews a diff in your terminal without installing the GitHub App"; `--fix` applies findings; effort levels trade confidence for coverage. [Code Review — Claude Code Docs](https://code.claude.com/docs/en/code-review)
- **Adversarial review pattern + its trap:** before treating work as done, "have a subagent review the diff in a fresh context and report gaps" — but "a reviewer prompted to find gaps will usually report some, even when the work is sound... Chasing every finding leads to over-engineering." Tell the reviewer to "flag only gaps that affect correctness or the stated requirements." [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **Field evidence — benefits AND drag:** industrial study of an LLM review tool (Qodo PR Agent-based) over 4,335 PRs: **73.8% of automated comments were resolved**, but average PR closure time rose from 5h52m to 8h20m; practitioners reported improved bug detection but also "faulty reviews, unnecessary corrections, and irrelevant comments." Teach students to expect the latency tax and tune (nit caps, skip rules) rather than accept defaults. [Automated Code Review in Practice — arXiv 2412.18531](https://arxiv.org/abs/2412.18531)

### AI in CI/CD: agents as pipeline citizens
- **Event-driven agents (GitHub Actions):** "With a simple `@claude` mention in any PR or issue, Claude can analyze your code, create pull requests, implement features, and fix bugs." GA action is `anthropics/claude-code-action@v1`; it "automatically detects whether to run in interactive mode (responds to @claude mentions) or automation mode (runs immediately with a prompt)." Prompts can invoke repo skills or plugin skills (e.g., running a `code-review` plugin skill on every `pull_request: [opened, synchronize]`). [Claude Code GitHub Actions — Claude Code Docs](https://code.claude.com/docs/en/github-actions)
- **Guardrails for CI agents (official guidance):** never commit API keys — GitHub Secrets only; "Limit action permissions to only what's necessary"; "Review Claude's suggestions before merging"; cap runaway cost with `--max-turns`, workflow timeouts, and concurrency controls. Enterprise paths exist for Bedrock/Vertex via OIDC (no static keys). [Claude Code GitHub Actions — Claude Code Docs](https://code.claude.com/docs/en/github-actions)
- **Headless/scripted agents:** `claude -p "prompt"` runs non-interactively — "how you integrate Claude into CI pipelines, pre-commit hooks, or any automated workflow," with `--output-format json|stream-json` for programmatic parsing and `--allowedTools` to scope permissions. Fan-out pattern: generate a task list, loop `claude -p "Migrate $file... Return OK or FAIL" --allowedTools "Edit,Bash(git commit *)"`, test on 2-3 files, then run at scale. [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices) · [Common workflows — Claude Code Docs](https://code.claude.com/docs/en/common-workflows)
- **Autonomous prompts must be self-contained:** scheduled/CI tasks "can't ask clarifying questions" — be explicit about success criteria and what to do with results. [Common workflows — Claude Code Docs](https://code.claude.com/docs/en/common-workflows)

## Concept IDs

Scoped tightly to this day (plan-first, TDD-with-agents, review loops, agents in CI). Adjacent-day topics (spec writing, prompt engineering, deployment/infra) deliberately excluded.

- **`plan-first-agent-workflow`** — Explore → Plan → Implement → Commit; plan mode as read-only exploration, editing the plan before approval, and the judgment call for when planning is overhead ("if you could describe the diff in one sentence, skip the plan").
- **`agentic-tdd-red-green`** — Test-first with agents: failing test as executable spec, red/green separation enforced by session isolation (one agent writes tests, another passes them), and reward-hacking detection (test deletion/disabling as an abort signal — Kent Beck's "genie cheating").
- **`verification-feedback-loops`** — Giving the agent a pass/fail check it can run (tests, build, screenshot diff), the enforcement ladder (prompt → goal → Stop hook → verification subagent), evidence-over-assertion, and the METR perception gap as the why.
- **`ai-code-review-loops`** — AI PR review as non-blocking comment-tier feedback (Copilot, Claude Code Review): severity ranking, false-positive verification passes, REVIEW.md tuning (nit caps, skip rules), fresh-context adversarial review, and the empirical trade (73.8% resolution vs longer PR closure).
- **`agents-in-ci-pipelines`** — Event-triggered agents (`@claude` on issues/PRs, `claude-code-action@v1`), headless `claude -p` with JSON output and `--allowedTools` scoping, fan-out batch patterns, and CI guardrails (secrets, max-turns, timeouts, least-privilege permissions).
