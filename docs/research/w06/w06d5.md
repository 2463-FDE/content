## Claims

### The delivery loop: spec to shipped code is one workflow, and it ends at a PR

- **Claude Code's canonical feature workflow terminates in ship, not "code done":** the four phases are Explore (plan mode, read-only) → Plan (detailed implementation plan, editable via `Ctrl+G` before proceeding) → Implement ("verifying against its plan") → **Commit** — "Ask Claude to commit with a descriptive message and create a PR." The unit of delivery is the PR, not the diff. [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **Spec-first entry point:** for larger features, have Claude interview you to a complete `SPEC.md`, then "start a fresh session to execute it." The most useful specs are "self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works." This is the w05d5 handoff feeding directly into this day's delivery run. [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **The stop-signal problem defines the whole exercise:** "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." The docs name an escalation ladder for how hard the check gates the stop: in-prompt iteration → `/goal` condition re-checked every turn → a deterministic Stop hook that "blocks the turn from ending until it passes" → a fresh-context verification subagent. "Each step trades setup for attention." And: "If you can't verify it, don't ship it" (the named "trust-then-verify gap" failure pattern). [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **Evidence over assertion at ship time:** "Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned, or a screenshot of the result. Reviewing evidence is faster than re-running the verification yourself, and it works for sessions you weren't watching." [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **End-to-end feature work is genuinely hard for agents — set expectations with data:** FeatureBench (ICLR 2026) benchmarks "end-to-end, feature-oriented software development" spanning "multiple commits and PRs scattered across the development timeline" (200 tasks, 3,825 executable environments, 24 OSS repos, execution-based evaluation). Headline: "Claude 4.5 Opus, which achieves a 74.4% resolved rate on SWE-bench, succeeds on only 11.0% of tasks." Bug-fix benchmarks wildly overstate feature-delivery capability — which is exactly why the gates below exist. [FeatureBench — arXiv 2602.10975](https://arxiv.org/abs/2602.10975)

### Quality gates that actually block: branch protection + required checks

- **GitHub's merge gate is deterministic:** "Required status checks must have a `successful`, `skipped`, or `neutral` status before collaborators can make changes to a protected branch," and with required reviews "collaborators can only push changes to a protected branch via a pull request that is approved by the required number of reviewers." Checks can be strict (branch must be up-to-date) or loose. This is the layer where agent output meets a non-negotiable pass/fail — tests, lint, build all become gates the agent must satisfy, not suggestions. [About protected branches — GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)
- **AI review findings can be wired into that gate, but deliberately aren't by default:** the Claude Code Review check run "always completes with a neutral conclusion so it never blocks merging through branch protection rules. If you want to gate merges on Code Review findings, read the severity breakdown from the check run output in your own CI" — the Details text ends with a machine-readable `bughunter-severity:` JSON comment (`{"normal": 2, "nit": 1, "pre_existing": 0}`; non-zero `normal` = at least one bug worth fixing before merge) parseable with `gh` + `jq`. Blocking on AI findings is an explicit team decision you build, not a vendor default. [Code Review — Claude Code Docs](https://code.claude.com/docs/en/code-review)
- **Agents can run inside the gate too:** `claude -p` is the non-interactive mode for "CI pipelines, pre-commit hooks, or any automated workflow" — `--output-format json` returns structured results (including `total_cost_usd`), `--json-schema` constrains output shape, and `--allowedTools "Bash,Read,Edit"` / permission rules like `Bash(git commit *)` scope what an unattended run may do. `--bare` skips auto-discovery of hooks/skills/MCP "for CI and scripts where you need the same result on every machine." Example from the docs: pipe `git diff main` into `claude -p` as a project-specific typo linter in `package.json`. [Run Claude Code programmatically — Claude Code Docs](https://code.claude.com/docs/en/headless)

### Automated review as a delivery stage

- **Managed automated PR review exists and is multi-agent:** Claude Code's Code Review (research preview) runs "a fleet of specialized agents" over the diff in the context of the full codebase — "logic errors, security vulnerabilities, broken edge cases, and subtle regressions" — with "a verification step [that] checks candidates against actual code behavior to filter out false positives," then posts deduplicated, severity-ranked inline comments. Severity taxonomy: 🔴 Important ("a bug that should be fixed before merging"), 🟡 Nit, 🟣 Pre-existing. Triggers: once on PR open, every push, or manual `@claude review` / `@claude review once`. Default scope "focuses on correctness: bugs that would break production, not formatting preferences." [Code Review — Claude Code Docs](https://code.claude.com/docs/en/code-review)
- **Review behavior is a config surface, not a prayer:** `REVIEW.md` at repo root is "injected directly into every agent in the review pipeline as highest priority" — teams redefine what Important means, cap nit volume ("report at most five nits"), skip generated code/lockfiles, add repo-specific always-checks ("new API routes must have an integration test"), set a verification bar ("behavior claims need a `file:line` citation"), and control re-review convergence ("after the first review, suppress new nits and post Important findings only"). `CLAUDE.md` violations surface as nits, bidirectionally (code that makes docs stale gets flagged too). [Code Review — Claude Code Docs](https://code.claude.com/docs/en/code-review)
- **Self-hosted equivalent via GitHub Actions:** `anthropics/claude-code-action@v1` runs the full Claude Code runtime on GitHub runners — `@claude` mention mode or automation mode (a `prompt` on `pull_request: [opened, synchronize]`), auto-detected. It "respects your `CLAUDE.md` guidelines," supports skills/plugins in the prompt (e.g. the `code-review` plugin skill per PR), and `claude_args` passes any CLI flag (`--max-turns`, `--allowedTools`, `--model`). Setup via `/install-github-app`; enterprise auth via Bedrock/Vertex with OIDC (no static keys). Security guidance is explicit: GitHub Secrets only, minimal permissions, "Review Claude's suggestions before merging." [Claude Code GitHub Actions — Claude Code Docs](https://code.claude.com/docs/en/github-actions)
- **Fresh-context adversarial review before the PR:** "have a subagent review the diff in a fresh context" — the reviewer "sees only the diff and the criteria you give it, not the reasoning that produced the change." Caveat carried into the milestone rubric: "A reviewer prompted to find gaps will usually report some, even when the work is sound" — chase only correctness-affecting findings or you over-engineer. [Best practices — Claude Code Docs](https://code.claude.com/docs/en/best-practices)

### The agent-authored PR: what actually gets merged

- **Merge/reject outcomes overstate agent failure:** across 9,799 human-reviewed agentic PRs (717 manually inspected), "only 35.7% of rejected PRs reflected clear agentic failures" — 31.2% of rejections stemmed from workflow constraints, not bad code. And among merged PRs, "15.4% required explicit reviewer involvement through feedback or direct commits." Agents differ by workflow embedding: "Copilot and Devin more often embedded in reviewer-mediated workflows, while Codex and Cursor PRs were typically merged with minimal interaction." Teaching point: the human reviewer is part of the delivery system, and merge-rate is a bad solo metric — the paper argues for "interaction-aware evaluation grounded in review behavior." [Why Are Agentic Pull Requests Merged or Rejected? — arXiv 2605.22534](https://arxiv.org/abs/2605.22534)
- **Findings-handling loop on the shipped PR:** replying to an AI review comment does nothing — "To act on a finding, fix the code and push"; push-triggered reviews auto-resolve threads when the issue is fixed. 👍/👎 reactions feed reviewer tuning. Review runs are "best-effort. A failed run never blocks your PR" — resilience of the gate is the team's CI's job, not the review service's. [Code Review — Claude Code Docs](https://code.claude.com/docs/en/code-review)

### Measuring the delivery: throughput without stability isn't delivery

- **DORA's core 2025 finding is the frame for the whole milestone:** "AI's primary role is as an amplifier, magnifying an organization's existing strengths and weaknesses," and "the greatest returns on AI investment come … from a strategic focus on the underlying organizational system" — not the tools. The report introduces the DORA AI Capabilities Model as the companion practice framework. [State of AI-assisted Software Development 2025 — DORA](https://dora.dev/dora-report-2025/)
- **The throughput–instability tension, verbatim:** "higher AI adoption is associated with an increase in both software delivery throughput and software delivery instability." 90% of tech professionals use AI at work; 30% of developers "report little to no trust in the code generated by AI." Named control systems: robust test automation ("potentially more valuable than optimizing manual code reviews"), small-batch discipline ("force large AI-generated changes into reviewable, testable units"), AI feedback moved to the **authoring** phase rather than the review phase, and context-aware review agents enforcing org standards. Measure with holistic frameworks, not lines of code. [Balancing AI tensions — DORA](https://dora.dev/insights/balancing-ai-tensions/)

### Teaching angle (★ milestone exercise)

- The milestone is the verified pipeline run once, for real: self-contained spec (w05d5 artifact) → fresh-session Explore/Plan/Implement with an executable check gating the stop → evidence-bearing commit + PR → automated review pass (managed Code Review or `claude-code-action` workflow, tuned via `REVIEW.md`-style rules) → branch protection with required status checks as the hard merge gate (optionally parsing AI-review severity into a blocking check) → human merge decision informed by the agentic-PR study (reviewer involvement is normal, merge-rate isn't the score) → debrief against DORA: did throughput come with instability, and which control system (tests, small batches, authoring-phase feedback) would have caught it? FeatureBench's 11% is the humility anchor: E2E feature delivery is the hardest thing agents do, which is exactly why the gates are the deliverable.

## Concept IDs

Scoped tightly to this day (integrated delivery + merge gates + review-as-stage + delivery measurement). Per-loop SDLC mechanics and AI-in-CI/CD fundamentals (d2), tool landscape (d1/d3), brownfield tactics (d4), and spec-handoff mechanics (w05d5) deliberately excluded — d5 assembles them.

- **`feature-delivery-loop`** — The full spec→shipped-code cycle as one workflow: self-contained SPEC.md entry, Explore→Plan→Implement→Commit ending in a PR, the stop-signal escalation ladder (in-prompt check → `/goal` → Stop hook → verification subagent), and "if you can't verify it, don't ship it."
- **`merge-quality-gate`** — Deterministic gates at the merge boundary: branch protection with required status checks and required reviews; wiring AI-review findings into a blocking check by parsing the neutral check-run's machine-readable severity JSON in your own CI; scoped headless runs (`claude -p --bare --allowedTools`) inside the gate.
- **`automated-review-stage`** — AI review as a pipeline stage, not a favor: multi-agent diff analysis with false-positive verification, Important/Nit/Pre-existing severity taxonomy, trigger modes (on-open / per-push / manual), and tuning via REVIEW.md-priority instructions (severity redefinition, nit caps, skip rules, verification bar, re-review convergence).
- **`agent-pr-lifecycle`** — The agent-authored PR through human review to merge: fix-and-push (not reply) to resolve findings, reviewer involvement as a normal part of merged agentic PRs (15.4%), rejection ≠ agent failure (only 35.7% of rejections were), and interaction-aware evaluation over raw merge-rate.
- **`delivery-throughput-stability`** — Measuring the delivery, DORA-style: AI as amplifier, throughput and instability rising together under AI adoption, and the control systems that decouple them — test automation, small-batch discipline, authoring-phase AI feedback — plus FeatureBench's SWE-bench-vs-feature-work gap (74.4% → 11.0%) as the expectation-setting datum.
