FDE Insights

Why this exists: Claude Code can read your own session history and tell you how you work. It is honest and it is generic: it scores you as a developer, not as a forward deployed engineer. This page turns that same report into an FDE self-assessment you run once a week for five weeks. Nothing to install. Run one command, paste one prompt.

How to run it

Two minutes, end of the week. The whole point is the trend across five runs, so the habit matters more than any single report.

  1. Run /insights in Claude Code and wait for the report. It reads the sessions you have actually run this program, on your own machine.
  2. In the same session, hit copy below and paste. Run 1 uses the baseline prompt. Runs 2 through 5 use the delta prompt.
  3. Nothing. It writes fde-progress.md for you. Run 1 creates the file in whatever directory you started Claude from. Runs 2 to 5 append to it. That file is the whole point, so keep it somewhere you will find it again and bring it to your week 10 defense.
This does not work: /insights based on @fde-mindset-paradigm.md. /insights is a built-in pipeline, not a prompt. It compresses each session into a fixed set of fields before any model reads them, so the report is already written by the time a file you referenced could be read. You would get an ordinary report and believe the FDE lens had been applied to it. Noticing that failure is itself the skill this page is about.

          Two rules that make this a cadence and not five disconnected reports.

          One: every run after the first must answer the previous run's "one change." Did you do
          it? Did it move anything? That is the only line the report cannot answer for you.

          Two: do not chase a good score. A run where three traits read "no evidence" is worth more
          than one where you went hunting for evidence to flatter yourself. You cannot revise the
          report after the fact, which is exactly what makes it worth reading.
        

      


      
      

        
What you are being scored against

        
All of this is copied along with the prompt, so you do not have to read it here first.
        Read it when a score surprises you.


        

          The operating model and the five stages where your work actually sits
          

            
Scope → Sequence → Build → Ship → Measure

              "Turning enterprise AI projects from long-cycle pilots into continuous value loops."

            
Most engineers live in Build and Ship, because those are the stages where the work
            feels like work. Scope and Measure are the two that get skipped, and they are the two
            that decide whether the thing you built mattered.

            
Galent's four FDSE phases say the same in verbs: Problem Decomposition &
            Scoping (note that it is first), Rapid Prototyping & Iteration, Optimization
            & Hardening, Deployment & Feedback Loop.

          

        


        

          The six traits the spine of every defense and retro
          

            
    
              
  1. Relentlessly curious about the customer's world. Surface the problem the
                customer gave up on or never articulated. Become a user before you become a builder.
    2. 
              
  2. Calibrate engineering to the situation. Both over-engineering and
                under-engineering leave scars.
    3. 
              
  3. Communicate across audiences. If you cannot explain it in one page without
                jargon, you do not understand it.
    4. 
              
  4. Stay calm when things break. Crisis composure matters as much as the fix.
    5. 
              
  5. Own outcomes without authority. Get a team that does not report to you to
                act, by explaining the why.
    6. 
              
  6. Know when to push back. Push back with an alternative, not a no.
    7. 
            

          

        


        

          The anti-patterns the wrong instinct that looks right
          

            
    
              
  • Overengineering. Two weeks on a configurable dedup engine when a one-time
                SQL query was needed. The customer cared about Friday.
    • 
              
  • Solving the wrong problem. Building Y, the literal ask, instead of X, the
                real need. The most expensive mistake.
    • 
              
  • Retreating into code. When a meeting gets tense, hiding behind the laptop.
    • 
              
  • Building without seeing the data. Empty date, epoch 1970, 2.3M keyspaces,
                14TB RAM to boot, OOM. They had never looked at the real data.
    • 
              
  • Throwing it over the wall. The old model the FDE role exists to correct.
    • 
              
  • Cannot set boundaries. FDE work expands to fill all available time.
    • 
            

          

        


        

          Loop Engineering the line that matters most
          

            
Automation runs Step 1, Step 2, Step 3. A loop runs
            Observe → Decide → Act → Verify → Repeat. Every loop needs exactly two things:
            a trigger, and a machine-verifiable stopping condition.

            
"Without a measurable stopping condition, you haven't built a
              loop. You've built a very confident token furnace."

            
"Never let the agent decide it's finished simply because it
              says so."

            
Almost everyone running long autonomous sessions builds the trigger half and skips
            the verification half. That is why buggy_code is the most common friction
            code in practice: the agent said done, and nobody checked the delivered artifact.

Friction codes

            
    
              
  • buggy_code · a loop with no verifiable stopping condition. Often
                also building without seeing the data.
    • 
              
  • wrong_approach · the XY problem. Phase 1 scoping was skipped.
    • 
              
  • misunderstood_request · scope failure, your side. The telephone game
                with you as a link in the chain.
    • 
              
  • stale_or_incorrect_prior_artifacts · trusting a document over the
                system. Trust nothing, trace everything.
    • 
              
  • resource_limit_hit · Loop Engineering cost control missing. No max
                iterations, no no-progress detection, no budget.
    • 
              
  • excessive_changes · overengineering. Trait 2 in the expensive direction.
    • 
              
  • incomplete_task · underpromise and overdeliver, inverted.
    • 
              
  • user_rejected_action · direction drift caught late. Your own
                checkpoint should have fired first.
    • 
              
  • blocked_on_external_dependency · trait 5. Who did you need, and did
                you go get them?
    • 
              
  • api_error, tooling_failure, tool_limitation ·
                machine layer, not driver layer. Do not score yourself down for these.
    •

    •

    • 
              
  • correct_code_edits · precision is the entry fee.
    • 
              
  • good_explanations · communicate across audiences.

          The three questions answer these in your own words
          

            
    
              
  1. Where did I start? At the problem, or at the ask? If every session opens
                at Build, you are being handed Y and building Y.
    2. 
              
  2. How did I know I was done? Name the machine-verifiable condition. If the
                answer is "Claude said it was finished," you have a token furnace, not a loop.
    3. 
              
  3. Who adopted it? Not "did it merge." Did anyone use it. Shelfware is the enemy.
