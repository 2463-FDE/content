Guardrails and Observability, End to End

Week 7 · Day 5 · ★ milestone Observability & Guardrails ~22 min · reading @150 wpm + diagram + check

This week you instrumented one path, built an eval harness, stood up your own tracing backend, and drew golden signals around it. Today you assemble all four into one artifact: an output guardrail on that same instrumented path, wired so a refusal is itself an observable, queryable event. Three layers — strict schema, a grounding check with a threshold, a refuse-unknown contract — one tripwire, one span, one number. And what you demo is the guardrail refusing, not succeeding; the happy path proves nothing.

The premise

A guardrail that isn't recorded didn't happen

Start with the sentence the rest of the day hangs on: a guardrail with a 0% observed refusal rate is a broken guardrail, or an unexercised one — not a clean system. It is never evidence of safety; it is an unanswered question, and the only way to answer it is to have been measuring.

The platform vendors already treat a decline as a first-class outcome rather than an error. OpenAI lists "Explicit refusals: safety-based model refusals are now programmatically detectable" as a headline benefit of Structured Outputs, and the refusal payload carries "status": "completed". Not a failure, not a timeout — a distinct terminal state you branch on.

You need the measurement because the vendor posture is not the observed behaviour. A 2026 study of commercial guardrails against manipulated medical notes found "substantial weaknesses and inconsistencies in contemporary commercial LLM guardrails, including low refusal rates for several model families." That finding exists only because someone counted refusals instead of assuming them.

So the milestone inverts the usual demo order. You feed the seeded bad case, show the user-facing decline, then the trace, the guardrail span, the score against the threshold, the counter ticking on yesterday's dashboard. Then, for contrast, one happy path. A guardrail you can only demo succeeding is one nobody has proven fires.

Layers 1 & 3

Shape is cheap; truth is not

Three layers go on one output, catching completely different failures. The cheapest is strict schema validation. Structured Outputs "ensures the model will always generate responses that adhere to your supplied JSON Schema, so you don't need to worry about the model omitting a required key, or hallucinating an invalid enum value" — with strict: true and additionalProperties: false. The subset is richer than people expect: string pattern and format, numeric minimum/multipleOf, array minItems/maxItems, enums and anyOf, defined in code with Pydantic or Zod. And it adds zero model latency.

It also catches nothing that matters clinically: a perfectly-shaped summary object that invents a medication passes strict validation. The docs are candid — "Structured Outputs can still contain mistakes." Schema enforces shape, and falsehood is well-formed.

The third layer is the refuse-unknown contract — the prompt-side half, and documented vendor guidance rather than folklore. Anthropic's hallucination page leads with "Allow Claude to say 'I don't know': explicitly give Claude permission to admit uncertainty," and adds the pattern worth stealing wholesale: make the response auditable by citing a quote per claim, and "if it can't find a quote, it must retract the claim." For long documents, extract word-for-word quotes first, and restrict the model to the provided documents. That page closes honestly — these techniques "don't eliminate them entirely." Which is why layer two is a measurement, not a prompt.

Grounding · the number

Three vendors, three shapes of "is this true?"

A grounding check turns the unanswerable question into a tunable number: how much of this output is supported by the sources you gave it? Three vendors, three shapes of that number — and the shape decides how you set the dial. Azure AI Content Safety returns ungroundedDetected (boolean), ungroundedPercentage — "the proportion of the text identified as ungrounded… this is not a confidence level" — and ungroundedDetails[].text, the offending span itself. It takes a domain of MEDICAL or GENERIC and a task of QnA or Summarization. Its two modes map onto your environments: non-reasoning is "fast detection for online applications," reasoning explains "during development and debugging."

Google's check-grounding API is claim-level: a support score from 0 to 1 plus citations to the facts supporting each claim. Two rules matter. "A sentence is considered a single claim," and partial entailment is not grounding — their example, "Google was founded by Larry Page and Sergey Brin in 1975," is entirely ungrounded on the strength of one wrong date. It is built for the critical path: latency "less than 500ms… this speed allows chat bots to call the check grounding API during each inference."

Bedrock splits the question in two: grounding ("any new information introduced in the response will be considered un-grounded") and relevance to the query, each with its own threshold. Set both at 0.7 and anything below on either is blocked. The range is 0 to 0.99, and the docs say why the top is fenced off: "a threshold of 1 is invalid as that will block all content."

Moving the dial is a precision/recall trade you state out loud, not a default you inherit: raise it and you catch subtler fabrications while declining more benign answers. Write down the number and what it cost.

The seam

The tripwire is where the telemetry hangs

Where does the event get emitted? Every framework converges on the same seam. The OpenAI Agents SDK runs an output guardrail in three steps: take the agent's output, run the guardrail function producing a GuardrailFunctionOutput inside an OutputGuardrailResult, then "check if .tripwire_triggered is true. If true, an OutputGuardrailTripwireTriggered exception is raised." That except block is your instrumentation point — the one place that knows a guardrail decided something.

Execution mode is a real cost decision. Input guardrails default to parallel execution, which "provides the best latency… however, if the guardrail fails, the agent may have already consumed tokens and executed tools before being cancelled"; blocking execution runs the check first, "preventing token consumption and tool execution." The constraint that matters for the milestone: output guardrails always run after the agent completes, so they have no parallel mode. Their latency is unavoidably additive.

Nobody hand-rolls all of it. openai-guardrails is a drop-in client doing pipeline-based validation across input, output and pre-flight stages; NeMo Guardrails organizes the same idea as rails (input, retrieval, dialog, execution, output) in YAML; Guardrails AI composes Guards from Hub validators. And Bedrock's standalone ApplyGuardrail decouples the check from the model call, so you can guard output from a model that isn't Bedrock's.

One caveat costs you the whole guarantee: on streaming, an ungrounded response "is only marked as irrelevant after the whole response is streamed." A post-hoc check on a stream has already leaked. So you buffer.

Refusal as telemetry

Publish your own attribute contract

Now make the refusal queryable. The OpenTelemetry GenAI semantic conventions have moved — the old page is a stub pointing at the semantic-conventions-genai repo, on core semconv v1.44.0. And there is no gen_ai.guardrail.* convention. None. The Tracing API spec says what to do: "for operations not covered by the semantic conventions, Instrumentation Libraries SHOULD publish their own conventions." Your attribute contract is a deliverable, not a nicety.

Ours: five attributes on the guardrail span, on the same trace as the model call — guardrail.name, guardrail.outcome ∈ {pass, block, model_refusal}, guardrail.score, guardrail.threshold, and guardrail.latency_ms. Score and threshold together, always — a score without its threshold is unreadable six weeks later, after someone retuned the dial. Two conventional surfaces come free: gen_ai.response.finish_reasons carries content_filter, and error.type is the one Stable dimension on gen_ai.client.operation.duration.

Which sets up the rule that keeps yesterday's work honest: do not set span status Error on an intentional refusal. The spec says instrumentation "SHOULD leave the status code as Unset unless there is an error." A guardrail firing is the system working. Mark it Error and you spend Thursday's error budget on your own safety control, and the burn-rate alert pages someone for correct behaviour.

And keep the event durable rather than in application logs — the Traccia work proposes a "hashed trace ledger" mapped to EU AI Act articles. A refusal you can't produce in six months is not evidence.

The wiring bug

Four terminal states, and the branch that never fires

The most likely bug of the day is a silent one, and it lives in the model_refusal branch you just added. On the Responses API a refusal is a typed content item: find the message item in response.output, take content[0], branch on type === "refusal". It is not a top-level string.

The same documentation page also carries a Chat Completions variant of that example, branching on choices[0].finish_reason and choices[0].message.refusal — and both variants sit under the page's legacy JSON mode heading, which the page itself deprecates. Copy the wrong one and your refusal branch reads None on every Responses call — invisibly: the demo shows pass on a call that was refused, and every dashboard downstream agrees.

While you are in there, branch on all four terminal states — three of which live on the response envelope, not the message: incomplete with reason max_output_tokens is truncated JSON; a refusal-typed item is a safety refusal; incomplete with reason content_filter is a halted generation; completed is success. Four states, four operator responses — and truncation is emphatically not a refusal.

Keeping these apart is not pedantry. A 2026 black-box study separated guardrail blocks from model rejections on unseen prompts at an average F1 of 98%, precisely because "the techniques used to bypass guardrails can differ substantially from those used to bypass LLM safety alignment." If an outsider can tell your two decline types apart from behaviour alone, your traces have no excuse for blurring them.

Rollout

Shadow first, enforce second

You cannot claim an improvement without a before-number, and it does not exist yet — nobody was measuring ungrounded output. So deploy twice.

Google's Model Armor names the two modes cleanly. Inspect only: "Model Armor analyzes the content against the configured… policies… it logs the details to Cloud Logging… However, it doesn't stop the request or response. This is useful for testing new policies, understanding potential violation rates, and auditing without affecting live traffic." With the footnote that decides it: "to gain value from this mode, Cloud Logging must be enabled." Shadow without a sink is a no-op. Then inspect and block, which "prevents the offending content from proceeding."

Run shadow over a slice of real or seeded traffic and you get the baseline violation rate — the number that was always true and never visible. Flip to enforce and you get the pair that makes the deliverable: refusal rate, added p95 latency, alert threshold. Same instrument, two readings, one honest claim.

One detail worth copying: Model Armor "sends a detailed description of triggered and untriggered filters." Log the untriggered ones — that resolves step one's ambiguity. A 0% refusal rate with untriggered-filter records means the check ran and found nothing; a 0% rate with silence means the check is off. (Its floor settings are worth stealing too: guardrail policy as an org-level governable artifact, not per-app config a team can quietly weaken.)

★ Milestone

The cost of the check, and the line you deliver

The guardrail is now a critical-path dependency, so it gets its own golden signals. OpenAI's published hallucination-detection benchmark — 300 statements, 50% positive prevalence — gives you numbers to argue with: ROC AUC 0.876 for gpt-4.1-mini, 0.934 for gpt-5-mini, 0.854 for gpt-5. Bigger is not better here. The latency spread is starker: a File-Search-backed check runs P50 ≈ 7.1 s / P95 ≈ 43 s on gpt-4.1-mini, and P50 ≈ 34 s / P95 ≈ 526 s on gpt-5 — against under 500 ms for a purpose-built grounding API — the difference between a check you can run inline and one you can't. Two knobs with measured effect: start confidence_threshold at 0.7, and disable reasoning in production, which "reduces median latency by 40% on average."

Say the limits out loud or the milestone teaches overconfidence. RAG does not fix hallucination — RAGTruth's ~18,000 annotated responses exist because "despite the integration of RAG, LLMs may still present unsupported or contradictory claims to the retrieved contents." Commercial guardrails under-refuse on exactly the medical-note class you are simulating. And the check's own p95 belongs beside the path it protects.

Then land the week. The client asked for visibility, and for the AI summary not to "say anything crazy." You hand over one instrumented path plus one guardrail on it, and the outcome line takes this shape: of N summaries replayed from last week's traffic, X contained a claim not supported by the source; the guardrail now blocks that class and returns a logged decline; refusal rate is R%, added p95 latency is Y ms, and an alert fires if refusal rate crosses Z% or drops to 0%. That last clause marks an engineer: you page on the guardrail going quiet, not only on it going loud.

FDE mindset

A control is a check that produces an observable, alertable event when it fires. An LLM refusal and a month-end reconciliation break are the same artifact: a deterministic assertion, a threshold, a distinct event type, a rate, an alert. Never tell a client "the feature is safe now." Tell them what you measured, what it was before, what it is now, and what will page you when that changes — then show the refusal.

Deep dive: setting the threshold, and the two alerts a guardrail needs

Optional. ~10 minutes. How to pick the number, and how to alert on it in both directions.

1 · Pick the threshold from shadow data, not from a blog post. Run inspect-only over a slice of real traffic, log every score, and plot the distribution. Your candidate threshold is wherever the seeded bad cases sit below and the bulk of legitimate summaries sit above. If those two populations overlap, no threshold saves you and you need a better check (or better retrieval) before you enforce anything. Remember the vendor semantics differ: Azure's ungroundedPercentage is a proportion of text and explicitly not a confidence; Google's support score is claim-level with sentence granularity; Bedrock gives you two independent scores and caps both at 0.99.

2 · Alert in both directions. The obvious alert is refusal rate crossing a ceiling — the guardrail suddenly blocking 15% of summaries means an upstream regression (retrieval broke, a prompt changed, the model was swapped). The alert people forget is the floor: refusal rate hitting exactly 0% for a full day on a path that previously refused. That is almost never a quality win. It is a config flag flipped, a deploy that dropped the check, or an exception being swallowed. Log untriggered filters so you can tell "ran and passed" from "never ran."

Worked example — the three-layer decision on one summary

A summary comes back naming a medication. ① Strict schema: the object has medications: string[] with minItems: 0 — valid, passes, 0 ms. ② Grounding check against the chart: the medication string appears in no source document, grounding score 0.41 against a threshold of 0.75 — guardrail.outcome = "block", span attributes written, span status left Unset. ③ The refuse-unknown contract was supposed to catch this first by requiring a quote per clinical claim; that it didn't is a finding for the eval set, not a reason to distrust layer ②. The user sees a logged decline. The trace shows the score, the threshold, and 380 ms of added latency.

Streaming footnote. If the endpoint streams tokens to the browser, an output guardrail is post-hoc by construction — the ungrounded sentence has already rendered. Either buffer the response and guard before first byte (and take the perceived-latency hit honestly), or move the check earlier in the pipeline. "We stream and we guard the output" is not a coherent claim.

Production code: the refusal, emitted as telemetry

The guardrail decision lands on the same trace as the model call, under attributes you published yourself — and the span status stays Unset, because a refusal is the system working.

# Draft the summary, then guard it. A refusal is an EVENT, not an error.
# Auth: Bedrock API key in AWS_BEARER_TOKEN_BEDROCK (boto3 reads it; no IAM role).
import time, boto3
from opentelemetry import trace

bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")
tracer  = trace.get_tracer("riverbend.summary")
THRESHOLD = 0.75   # from shadow-mode data. Bedrock caps at 0.99 -- 1.0 blocks everything.
CONTRACT  = ("Summarize ONLY from the chart below. Quote the chart for every clinical "
             "claim; if you cannot find a supporting quote, drop the claim and say so.")

def guarded_summary(chart: str, question: str) -> dict:
    with tracer.start_as_current_span("guardrail.grounding") as span:
        draft = bedrock.converse(
            modelId="us.anthropic.claude-haiku-4-5-20251001-v1:0",
            system=[{"text": CONTRACT}],                       # layer 3: refuse-unknown
            messages=[{"role": "user", "content": [{"text": f"{chart}\n\n{question}"}]}],
            inferenceConfig={"maxTokens": 400, "temperature": 0},
        )["output"]["message"]["content"][0]["text"]

        t0 = time.perf_counter()
        res = bedrock.apply_guardrail(                          # layer 2: grounding check
            guardrailIdentifier=GUARDRAIL_ID, guardrailVersion="1", source="OUTPUT",
            content=[{"text": {"text": chart,    "qualifiers": ["grounding_source"]}},
                     {"text": {"text": question, "qualifiers": ["query"]}},
                     {"text": {"text": draft}}],
        )
        blocked = res["action"] == "GUARDRAIL_INTERVENED"
        span.set_attributes({          # no gen_ai.guardrail.* exists -- publish your own
            "guardrail.name": "clinical_grounding",
            "guardrail.outcome": "block" if blocked else "pass",
            "guardrail.threshold": THRESHOLD,
            "guardrail.latency_ms": (time.perf_counter() - t0) * 1000,
        })
        # Status stays Unset -- never spend the w07d4 error budget on a working guardrail.
        if blocked:
            return {"summary": None, "decline": "I can't verify that against the chart."}
        return {"summary": draft}

Same trace, five attributes, no Error status. That is the difference between a guardrail you can demo and a guardrail you can prove.
