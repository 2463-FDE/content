Evals in Production: Online and Offline

Week 7 · Day 2 Observability, SRE & Guardrails ~23 min · reading @150 wpm + diagram + check

Yesterday you instrumented a path so you could see it. Today: how do you know the output is any good — and how do you prove it still is next month? Offline evals run a curated dataset with known-correct answers; online evals grade live traffic that has no answer key. Between them sits the LLM judge — genuinely useful, provably biased in three documented ways. The part nobody can outsource is the gold set: only a clinician can label "is this summary safe." Scroll the reading; the panel assembles the loop, then turns a score into a build-breaking gate.

The split

Two evals, told apart by their target

Offline and online are not rival metrics. The difference is the target. An offline evaluation runs on dataset examples — an input paired with a reference output you already believe in: benchmarking, regression testing, backtesting, before you deploy. An online evaluation runs on runs and threads from production tracing — yesterday's spans — for monitoring, anomaly detection, and production feedback.

LangSmith states the consequence directly: "this difference in targets determines what you can evaluate: offline evaluations can check correctness against expected answers, while online evaluations focus on quality patterns, safety, and real-world behavior." Production runs "do not include reference outputs. Online evaluators must assess quality without knowing what the 'correct' answer should be."

That sorts your evaluator library into two piles. Reference-free evaluators survive the jump to production: safety checks (toxicity, PII, policy violations), format validation, quality heuristics, judges for clarity and tone. Reference-based evaluators — correctness, factual accuracy against ground truth, exact match — "only work for offline evaluation."

So when a client asks "can't you just run your accuracy check on live traffic?", the answer is usually no: accuracy needs an answer key, and live traffic doesn't ship with one. What runs live is groundedness, schema validity, refusal compliance.

The loop

Production writes your test set

The two halves are a loop, not a choice: "online evaluations surface issues that become offline test cases, offline evaluations validate fixes, and online evaluations confirm production improvements." Google names the same bridge — "sample directly from production logs to evaluate the real-world usage of your model." OpenAI's workflow ends on it: run evals on every change, "identify new cases of nondeterminism, and grow the eval set over time."

Your client packet already contains the first example. Riverbend handed over a transcript where the summarizer invented a medication the patient isn't on. That is not an anecdote to patch around — it is gold-set example #1: a real trace with a known-bad label, from the exact distribution your system serves. Promote it into a versioned dataset and this week's fix can never silently regress. Meridian's payment rows that don't tie out to the settlement file are the same thing in an accounting costume.

Notice the direction of travel. You don't imagine test cases; you instrument, sample, find failures, and graduate each one into a permanent example. A set built that way tracks real traffic by construction — the opposite of OpenAI's named anti-pattern, "biased design: creating eval datasets that don't reproduce production traffic patterns."

Online · cost & privacy

Grading live traffic is a budget decision too

Every graded run is another model call on top of the one you already paid for, so the discipline is filter, then sample. A run filter narrows to traffic worth grading — negative feedback, a particular tool call, a metadata tag — and a sampling rate does the rest: "to control costs… only apply the evaluator to 10% of traces… set the sampling rate to 0.1." Microsoft Foundry exposes the same two dials as samplingPercent and a per-hour maxRequestRate, capped by "the system limit of 1000/hour."

Two side effects matter more than they look. Billing: a graded trace "will be auto-upgraded to extended data retention. This upgrade will impact trace pricing" — a judge changes what you pay to store traces, not just to grade them. And privacy — raise it before the client's counsel does. Foundry redacts judge reasoning by default, warning that "reasoning explanations might mention sensitive information based on the content of the conversation." For Riverbend that means an evaluator writing commentary about encounter content into telemetry, then upgrading retention on those traces: a new PHI surface, created by a quality feature.

The judge

The judge is an instrument, so calibrate it

Production has no answer key, so something must produce the score — increasingly, another model. The headline result is genuinely strong: "strong LLM judges like GPT-4 can match both controlled and crowdsourced human preferences well, achieving over 80% agreement, the same level of agreement between humans… a scalable and explainable way to approximate human preferences, which are otherwise very expensive."

Both halves matter. The judge is about as good as a human — and humans agree with each other only 80% of the time. The realistic target isn't perfection; it's inter-expert agreement. MedHELM puts a number on that ceiling: their LLM jury "achieved good agreement with clinician ratings (ICC = 0.47), surpassing both average clinician-clinician agreement (ICC = 0.43)." That's not "solved" — it's as good as the human process it replaces, which is the bar, and only claimable if you measured it.

So treat the judge like any instrument: calibration drifts. Track judge-versus-human agreement as its own metric over time, on a fresh labeled sample each cycle. A frontier model doesn't retire the problem — CALM quantifies 12 key potential biases and finds that "while advanced models have achieved commendable overall performance, significant biases persist in certain specific tasks."

Biases

Three biases with receipts

Position bias. In a pairwise comparison, the order you present candidates in changes the verdict: "the quality ranking of candidate responses can be easily hacked by simply altering their order of appearance in the context." With ChatGPT as evaluator, "Vicuna-13B could beat ChatGPT on 66 over 80 tested queries" by exploiting order alone. Mitigations: Multiple Evidence Calibration (evidence before scoring), Balanced Position Calibration (run both orderings, aggregate), and Human-in-the-Loop Calibration, which scores example difficulty and "seeks human assistance when needed" — route the high-disagreement examples into your expert review queue. (That routing framing is ours.)

Verbosity bias. Judges like longer answers: "even simple, known confounders such as preference for longer outputs remain in existing automated evaluation metrics… AlpacaEval is known to favor models that generate longer outputs." The fix is a counterfactual — ask what the preference would be "if the model's and baseline's output had the same length," then regress the length difference out. Length control "increases the Spearman correlation with LMSYS Chatbot Arena from 0.94 to 0.98." Practical rule: when a score jumps after a prompt change, check output length before you celebrate.

Self-preference. An LLM evaluator "scores its own outputs higher than others' while human annotators consider them of equal quality." Measured, not folklore: models have "non-trivial accuracy at distinguishing themselves" from other models and humans, and fine-tuning reveals "a linear correlation between self-recognition capability and the strength of self-preference bias." Consequence: the judge must differ from the generator. "We A/B'd two prompts on one model and let it pick the winner" isn't a weak experiment — it's a broken one.

Mitigations

Use the cheapest grader that works

Before you reach for a judge, walk Anthropic's ladder. Code-based grading is "fastest and most reliable, extremely scalable." Human grading is high quality "but slow and expensive — avoid if possible." LLM-based grading is "fast and flexible… test to ensure reliability first then scale." Meridian's reconciliation is the textbook case: comparing a ledger row to a settlement row needs no judge at all. Reaching for an LLM where a deterministic comparison exists is the mistake, not the sophistication.

When you do need a judge, four documented moves buy most of the reliability. Force reasoning, then throw it away — "ask the LLM to think first before deciding an evaluation score, and then discard the reasoning. This increases evaluation performance, particularly for tasks requiring complex judgement." Constrain the output space — "instruct the LLM to output only 'correct' or 'incorrect'… purely qualitative evaluations are hard to assess quickly and at scale." Prefer comparison to absolute scoring, because "LLMs are better at discriminating between options" — "choosing the more informative of two summaries is often easier than assigning an absolute score to a single summary." And few-shot the judge: grader prompts carrying example inputs, outputs, and expected grades "often improve performance." Google pushes further with per-prompt adaptive rubrics, generated "for each prompt, like unit tests."

Gold set

Build the gold set with the client

Here is the part no tool sells you. A judge is only as good as the labels you calibrate it against, and for the questions that matter, you cannot produce those labels. "Invented a medication," "dropped an allergy," "contradicted the chart" are clinical-safety judgments; "is this the actual reason we declined the applicant?" is a Reg B compliance judgment. MedHELM's answer was a "clinician-validated taxonomy… developed with 29 clinicians," because near-perfect licensing-exam scores "inadequately reflect… real-world clinical practice."

The instinct is to book a kickoff meeting and walk out with a rubric. That fails, and there's a name for why: criteria drift. "Users need criteria to grade outputs, but grading outputs helps users define criteria." Some criteria even turn out dependent on the specific outputs observed, which "raises serious questions for approaches that assume the independence of evaluation from observation." The rubric is an output of the labeling session, not an input. Sit a clinician down with twenty to thirty real summaries, watch what they flag, let the rubric assemble itself — and expect them to disagree with each other. MedHELM's 0.43 is your instrument for measuring that.

Mechanically: start with manually curated examples — "5-10 examples of what 'good' looks like for each critical component," growing to "10-20 high-quality examples covering common scenarios and edge cases." Then the advice inverts: "prioritize volume over quality — more questions with slightly lower signal automated grading is better than fewer questions with human hand-graded evals." Annotation queues give you prescribed rubrics, multiple reviewers, and assertions — acceptance criteria a future offline evaluator grades against, which is how one clinician's objection becomes a permanent test. Then version the dataset and pin versions in CI, or the gate means nothing.

The gate

Turn a score into a build-breaking control

"Generative AI is variable… which makes traditional software testing methods insufficient." Evals test it anyway, and a gate needs a number. Anthropic's example of hardening a hazy criterion is the one to memorize: bad = "safe outputs"; good = "less than 0.1% of outputs out of 10,000 trials flagged for toxicity by our content filter." OpenAI's worked thresholds read like acceptance criteria — "on a held-out set of 1000 reference transcripts → summaries… a ROUGE-L score of at least 0.40 and coherence score of at least 80%."

Three shapes implement it. (A) Assertions in your test runner — LangSmith's pytest plugin (langsmith>=0.3.4) is for when "you want to assert binary expectations… and raise assertion errors locally, e.g. in CI pipelines"; each decorated test syncs to a dataset example. (B) A declarative threshold — promptfoo's test case exposes threshold: "test will fail if the combined score of assertions is less than this number." Wire it to a PR with promptfoo/promptfoo-action@v1 on path-filtered pull_request events, plus pull-requests: write to post results as comments and a response cache to save cost. (C) A hosted run's pass/fail counts — but don't build on OpenAI's Evals platform: read-only 2026-10-31, shut down 2026-11-30; migration path, Promptfoo.

Last question: where does the gate go? Map your architecture and "identify where nondeterminism enters your system. That's where you'll want to implement evals." One end-to-end score says something broke; per-seam gates say what.

The load-bearing idea

A guardrail without an eval is an assertion

Tomorrow you build the content guardrail your packet asks for. Today's idea is what makes it a control instead of a claim. A guardrail nobody measures is the same species as the README that says "HIPAA compliant" — the one you flagged in Week 1: it asserts a property. A named metric, a threshold, a versioned dataset with a clinician's name on it, and a build that fails when the number drops demonstrates one.

The two accounts converge from opposite ends. Riverbend's "it invented a medication and nobody knew until a clinician noticed" is the same missing-detection story as "intake froze twenty minutes and no alert fired" — a reference-free groundedness check on sampled live summaries is the alert that was missing. Meridian's daily reconciliation, scored against a month of labeled breaks with a threshold and an owner, is a regression gate in a SOX costume: "month-end noise" becomes "the control fired."

FDE mindset

When a client asks "is the AI accurate?", never answer with a demo. Answer with the instrument: what is the metric, who labeled the set, what is the threshold, and what breaks when it's missed? Miss any of the four and you don't have an eval — you have a vibe. The one you can't supply yourself is the second: go get the expert.

Deep dive: running your first labeling session with a domain expert

Optional. ~10 minutes. The 90-minute session that produces a rubric, a gold set, and a threshold you can defend.

Before the session. Pull 25-30 real outputs from production traces — deliberately skewed toward the interesting ones (negative feedback, retries, long latency, errors), not a uniform sample. Include the source material next to each output; a clinician cannot judge a summary without the encounter note. Do not arrive with a finished rubric. You are there to discover it.

During. Ask for a binary call first — safe / not safe — then ask why, and write the reason verbatim. Those verbatim reasons are your rubric categories: "invented a medication," "dropped an allergy," "contradicted the chart." This is criteria drift working for you rather than against you: the criteria emerge from the grading. Where two experts disagree, do not resolve it in the room — record it. Disagreement is data, and the rate of it is the ceiling on any automated grader you build next.

After. Convert each verbatim reason into an assertion attached to its example, so a future offline evaluator can grade new runs against it. Version the dataset and pin that version in CI. Then build the judge, run it against the labeled set, and report agreement — not accuracy. If your judge lands near the expert-to-expert agreement rate, that is the realistic ceiling, and you say so out loud.

Worked example — the sentence you hand back to the client

"Groundedness on the clinician-labeled summary set (v3, 42 examples, labeled by Dr. Okonkwo's team) must stay at or above 0.95, measured by a Claude Haiku judge that agrees with clinician labels at κ 0.71 on a held-out slice. A prompt or model change that drops below the floor fails the build. The set grows every time a live groundedness check fires." That sentence contains all four things: metric, labeler, threshold, consequence. Practice writing it for your own account until it takes thirty seconds.

Sizing note. Start at 5-10 examples per critical component, grow to 10-20 covering typical + edge + adversarial cases, then favor volume with automated grading. Do not spend six weeks hand-labeling 500 examples before you ship anything — the first version of the gate should exist inside a week.

Production code: a groundedness judge that respects its own biases

Three mitigations in twenty lines — judge model ≠ generator model, constrained output space, and reasoning forced then discarded.

# Groundedness judge for sampled production summaries (online eval, reference-free).
# Auth: Bedrock API key in AWS_BEARER_TOKEN_BEDROCK (boto3 reads it; no IAM role).
import json, boto3

bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")

# The generator runs on Sonnet. The judge MUST be a different model -- an evaluator
# recognizes and favors its own generations (self-preference bias, arXiv 2404.13076).
JUDGE = "us.anthropic.claude-haiku-4-5-20251001-v1:0"

RUBRIC = """Grade one clinical summary against its source encounter note.
Reason step by step in "why", then output ONLY this JSON object:
{"why": "...", "verdict": "grounded" or "unsupported"}
Answer "unsupported" if ANY medication, allergy, or diagnosis in the summary
does not appear in the source. Two labels only -- no scale, no prose."""

def grade(source: str, summary: str) -> str:
    resp = bedrock.converse(
        modelId=JUDGE,
        system=[{"text": RUBRIC}],
        messages=[{"role": "user", "content": [
            {"text": f"<source>{source}</source>\n<summary>{summary}</summary>"}]}],
        inferenceConfig={"maxTokens": 400, "temperature": 0},  # temp 0 -> repeatable
    )
    out = json.loads(resp["output"]["message"]["content"][0]["text"])
    # Reasoning was forced (it lifts judge accuracy), then discarded: it quotes the
    # encounter, so emitting it to telemetry would create a new PHI surface.
    return out["verdict"]

The same function is both halves of the loop: run it on sampled live traces (online), and on the clinician-labeled gold set in CI where its pass rate is the number the regression gate compares to a floor.
