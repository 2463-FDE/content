SRE for AI Systems: SLOs, Error Budgets, and the OTel GenAI Conventions

Week 7 · Day 4 Observability & Reliability ~23 min · reading @150 wpm + diagram + check

Traces tell you what happened inside one request. Today you turn telemetry into a promise you can defend in a room with the client. The four golden signals — latency, traffic, errors, saturation — are 2016 SRE doctrine, and they cover an LLM path without a single new idea, because the SRE Book already defined an error to include "an HTTP 200 success response, but coupled with the wrong content." From there: an SLI is a proportion of good events, an SLO is a number three parties agree to, and the error budget is how you say "not this sprint" without saying no. Then you alert on burn rate instead of spikes, and give cost its own budget — because a cache regression is a 10× bill that latency never sees.

Golden signals

Four metrics, and the definition that already fits AI

Start from the canonical sentence: "The four golden signals of monitoring are latency, traffic, errors, and saturation. If you can only measure four metrics of your user-facing system, focus on these four." The claim is coverage — measure all four and page when one goes bad, and "your service will be at least decently covered."

Two details do the heavy lifting. First, latency must be split by outcome: "a slow error is even worse than a fast error," but folding 500s into overall latency produces misleading numbers. Second — the line that makes the framework fit AI without new theory — an error is a request that failed "either explicitly (e.g., HTTP 500s), implicitly (for example, an HTTP 200 success response, but coupled with the wrong content), or by policy (for example, 'If you committed to one-second response times, any request over one second is an error')."

Read that with a hallucination in mind. A confidently wrong summary returns HTTP 200 and is, by the SRE Book's own 2016 definition, an error. AI reliability isn't a new discipline — it's the existing one, pointed at a token-metered, nondeterministic dependency.

Instantiation

The four signals on an LLM path

Here is the translation — the first thing to write down when a client hands you an AI feature. Latency is not one number: end-to-end duration plus time-to-first-token and time-per-output-token, because a streaming UI that starts in 400 ms feels fast even if the whole answer takes eight seconds, while a batch job cares nothing about first-token. Traffic is requests per second and tokens per second — rate limits are token-denominated, so a request count alone won't predict the ceiling.

Errors are provider 429s, 500s and 529s, plus every by-policy error you declare: schema-validation failure, a length-capped truncation, a refusal, an empty output, a failed groundedness check. Saturation — "how 'full' your service is" — has no CPU gauge here; the proxies are rate-limit headroom, the 429/529 rate as an upstream signal, and context-window utilization. The SRE Book's tip applies directly: "measuring your 99th percentile response time over some small window… can give a very early signal of saturation." Creeping p99 is usually the first symptom of a provider under load.

None of that is speculative: every one has a defined home in the OpenTelemetry GenAI conventions, in step 8.

SLI

Write the indicator before you pick a number

A service level indicator is the measurement. Split it into two halves people constantly collapse: the specification ("the ratio of intake requests served successfully within 3 seconds") and the implementation (at the load balancer? in the client? from synthetic probes?). "A single SLI specification might have multiple SLI implementations, each with its own set of pros and cons in terms of quality, coverage, and cost." Write both down — arguments about whether a service is healthy are almost always arguments about implementation.

Prefer the ratio form — proportion of good events over valid events, where "the SLI ranges from 0% to 100%." That form makes the error budget fall out arithmetically later.

You don't have to invent one, either. The Workbook publishes a catalogue by system type: request-driven systems get availability, latency and quality ("the proportion of responses served in an undegraded state"); pipelines get freshness, correctness and coverage. Correctness — "the proportion of records coming into the pipeline that resulted in the correct value coming out" — is the closest published analogue to an LLM output-quality SLI, and exactly the shape a nightly reconciliation job needs.

SLO

An SLO is a promise, and promises are negotiated

The objective is a target on the indicator. One question separates it from an SLA: "what happens if the SLOs aren't met? If there is no explicit consequence, then you are almost certainly looking at an SLO." An SLA carries credits, penalties, a contract. Don't let a client blur the two.

What makes an SLO real is not analysis, it is three-party agreement. Product managers must "agree that this threshold is good enough for users." Developers must "agree that if the error budget has been exhausted, they will take some steps to reduce risk to users." Whoever carries the pager must agree "that it is defensible without Herculean effort, excessive toil, and burnout." Then the test: approval of the error budget policy by all three "is a good test for whether the SLOs are fit for purpose." Each objection maps to a fix — too much toil or unacceptable velocity means relax; users suffering before the policy fires means "the SLOs are likely not tight enough."

So when a stakeholder says "make it 100%," you have four documented answers: component failure probability is never zero; "even if you could achieve 100% reliability within your system, your customers would not experience 100% reliability"; a 100%-reliable service can never change, and "the number one source of outages is change"; and "an SLO of 100% means you only have time to be reactive." Keep a safety margin — "users build on the reality of what you offer, rather than what you say you'll supply" — and if the right target isn't reachable yet, declare an aspirational SLO: tracked, explicitly not requiring action.

Error budget

"Not this sprint" without saying no

The error budget is 100% minus the SLO, a spendable quantity. The worked example: at a 99.9% SLO, a service taking 3 million requests over four weeks has a budget of 3,000 errors, so "if a single outage is responsible for 1,500 errors, that error costs 50% of the error budget." An incident now has a price tag everyone shares.

That currency is the point. The budget depoliticizes: it "removes the politics from negotiations between the SREs and the product developers when deciding how much risk to allow." The loop is mechanical — while the SLO is met, releases continue; spend the budget and releases halt while engineering goes to resilience work. The elegant part is that it makes the other side argue your case: "when the budget is nearly drained, the product developers themselves will push for more testing or slower push velocity… the product development team becomes self-policing."

Three honest caveats. The precondition is blunt: "this outcome relies on an SRE team having the authority to actually stop launches if the SLO is broken" — as a consultant you rarely have that authority, which is why the policy must be signed by someone who does. Infrastructure and third-party failures count: "such events also eat into the error budget… everyone shares the responsibility for uptime." And the legitimate escape valve is renegotiation, not evasion — a struggling team "may elect to loosen the SLO… in order to increase innovation." What you're steering away from is the named failure mode: an SLO without teeth.

Burn rate

Alert on the rate you're spending, not the spike

Burn rate is a multiple of budget-neutral consumption: a burn rate of 1 "means that it's consuming error budget at a rate that leaves you with exactly 0 budget at the end of the SLO's time window." At 99.9% over 30 days, a constant 0.1% error rate is burn rate 1. Burn rate 2 exhausts in 15 days, 10 exhausts in 3 days, and 1,000 — a total outage — exhausts the month in 43 minutes. The arithmetic fits on one line: budget consumed = burn rate × alerting window ÷ period.

Why not one threshold? A single burn-rate alert has terrible recall, and the Workbook names the hole: "a 35x burn rate never alerts, but consumes all of the 30-day error budget in 20.5 hours." Fast enough to hurt, slow enough to slip under a spike alarm. The fix is multiple burn rates at several windows. Google's recommended starting configuration: 2% of budget over 1 hour (burn rate 14.4) → page; 5% over 6 hours (burn rate 6) → page; 10% over 3 days (burn rate 1) → ticket. Add a short confirmation window so the page stops when the burn stops — require 14.4× over the previous hour and the previous five minutes, giving "a better reset time by ceasing to fire five minutes later, rather than one hour later."

The trap

Low traffic breaks the table outright

Copy that 14.4/6/1 table onto a low-volume path and you ship an alarm that is useless in both directions. The Workbook is explicit: "if a system receives 10 requests per hour, then a single failed request results in an hourly error rate of 10%. For a 99.9% SLO, this request constitutes a 1,000x burn rate and would page immediately, as it consumed 13.9% of the 30-day error budget. This scenario allows for only seven failed requests in 30 days."

That is the shape of a pilot AI feature, or a clinical intake queue at 2 a.m. — one retryable blip pages a human, someone silences the alert, and the real outage becomes invisible. The mitigations are boring: widen the window, aggregate across a bigger surface, set a minimum-volume precondition, or accept a looser SLO honestly rather than a tight one you mute. Check request volume before you pick thresholds — that check is the difference between a dashboard and an instrument.

Severity routing follows the same logic: "if an issue will exhaust the error budget within hours or a few days, sending an active notification is appropriate. Otherwise, a ticket-based notification… the next working day is more appropriate." A slow reconciliation drift is a ticket, not a 3 a.m. page — and now you have a principled reason rather than a preference.

OTel GenAI

The metric names, and a currency check you must run

Names matter: a client dashboard built on invented metric names can't be handed to anyone. OpenTelemetry's GenAI conventions define the instruments. On the client side — gen_ai.client.operation.duration is a histogram in seconds; gen_ai.client.token.usage is a histogram in {token} with a required gen_ai.token.type of input or output; gen_ai.client.operation.time_to_first_chunk is streaming-only. Self-hosted inference adds gen_ai.server.time_to_first_token (queue + prefill) and gen_ai.server.time_per_output_token (decode). Client and server measure the same idea from different vantage points — the client one includes network and proxy transport, so the delta between them is your infrastructure overhead. Never mix them in one SLO.

On the span: kind SHOULD be CLIENT, name SHOULD be {gen_ai.operation.name} {gen_ai.request.model}, and — the rule that keeps your latency SLI honest — a retried request's span "SHOULD cover the duration of the logical operation with all retries." error.type is conditionally required on failure and is Stable, inherited from core semconv: the one attribute your error-rate SLI can lean on today.

Now the currency check — the FDE habit this day is really teaching. These conventions moved repos: the old opentelemetry.io/docs/specs/semconv/gen-ai/ pages now render only "this page has moved and is no longer maintained in this repository." The live home is open-telemetry/semantic-conventions-genai: status Development, no tagged release, README Schema URL literally "TODO." Names can still change. Pin your instrumentation version and read the source before quoting a convention — anything citing the old URLs is stale.

Cost

Cost is a reliability signal, and nobody emits it

The second thing to discover for yourself: there is no cost metric. The conventions define no gen_ai.*.cost instrument or attribute — the registry carries token counts only. Cost is derived downstream: tokens × price, sliced by model and token type. One trap: OTel's cache attributes are inclusive — cache-read and cache-creation counts "SHOULD be included in gen_ai.usage.input_tokens" — while Anthropic's usage object decomposes the other way. Sum all three and you double-count.

Cost deserves its own SLO because of the price asymmetry. Five-minute cache writes cost 1.25× base input, one-hour writes 2×, and cache reads 10% of base input. A cache-hit-ratio collapse therefore multiplies the cost of your cached prefix by roughly ten times while latency and error rate look perfectly healthy. Nothing pages. Nothing is "down." You find out at month end. Detection is cheap — "if both cache_creation_input_tokens and cache_read_input_tokens are 0, the prompt was not cached" — so a daily hit-ratio check catches it. Give cost a dollars-per-day budget and the same burn-rate machinery.

One last discipline. The conventions are default-private: instructions, messages and outputs "SHOULD NOT" be captured by default, and every content attribute is Opt-In, flagged as likely PII. That's a gift — metrics and spans without payloads give you every golden signal plus token cost, with no regulated data leaving the boundary. Ship the rollout now; content capture is a separate decision.

FDE mindset

"Give me visibility" is not a spec, and a dashboard is not an answer. The deliverable is a promise with a consequence: an SLI whose valid events you can name out loud, an SLO three people signed, and one alert that fires on burn rate. When the provider melts down — the 529, the payer outage — the user failed either way, so the SLI counts it; the policy response is a dependency clause with a fallback, not an exemption. That turns "the vendor was down" into a design requirement.

Deep dive: the 20-minute freeze, priced in burn rate

Optional. ~10 minutes. Take the incident note from your client's materials — "intake froze ~20 min, no alert fired" — and turn it into arithmetic you can put on a slide.

Step 1 — the budget. A 99.9% SLO over 30 days. Thirty days is 43,200 minutes, so the error budget is 0.1% of that: 43.2 minutes of total unavailability per month. That single number is usually the most persuasive thing in the room — most stakeholders have never seen "three nines" expressed as forty-three minutes.

Step 2 — price the incident. A 20-minute total outage spends 20 / 43.2 = 46% of the entire monthly budget in one event. Nearly half the year's-worth-of-risk-per-month, gone before lunch.

Step 3 — would the alert have caught it? Over a one-hour window, 20 minutes down is a 33.3% error rate. Budget-neutral is 0.1%, so the burn rate is 333× — far past the 14.4× page threshold. Check it with the formula: consumed = burn × window ÷ period = 333 × (1 ÷ 720) = 46%. The two numbers agree. And because the 14.4×/1h rule fires at 2% of budget, it would have paged after roughly 52 seconds of full outage, not twenty minutes. The freeze went unnoticed because there was no SLO to breach — not because it was hard to detect.

The published rule you can paste into Prometheus

0.001 below is the 99.9% SLO's budget — change the SLO, change that constant:

# page
expr: (
        job:slo_errors_per_request:ratio_rate1h{job="myjob"} > (14.4*0.001)
      or
        job:slo_errors_per_request:ratio_rate6h{job="myjob"} > (6*0.001)
      )
severity: page

# ticket
expr: job:slo_errors_per_request:ratio_rate3d{job="myjob"} > 0.001
severity: ticket

Then add the short confirmation window — require the 14.4× condition over the previous five minutes as well as the previous hour — so the page clears five minutes after the burn stops instead of an hour later.

Now the sanity check that saves you. Before you ship those rules, count the requests. If the path runs at 10 req/hour overnight, one failure is a 1,000× burn and pages instantly — the Workbook's own example allows only seven failed requests in 30 days at that volume. Widen the window, aggregate across a larger surface, or add a minimum-volume precondition. Shipping the table unchecked is the single most common way a good SLO becomes a muted alert.

Production code: the instrumented call your SLO is measured from

Metrics only, no payload — every golden signal, nothing regulated leaving the boundary. The names are the OTel GenAI ones so the dashboard is portable.

# Emit OTel GenAI client metrics around one Bedrock call. No prompt/output captured.
# Auth: Bedrock API key in AWS_BEARER_TOKEN_BEDROCK (boto3 reads it; no IAM role).
import time, boto3
from opentelemetry import metrics

bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")
m = metrics.get_meter("llm.client")      # one meter per service, not per domain
DUR = m.create_histogram("gen_ai.client.operation.duration", unit="s")
TOK = m.create_histogram("gen_ai.client.token.usage", unit="{token}")

MODEL = "us.anthropic.claude-haiku-4-5-20251001-v1:0"

# Wrap the ONE span the week's packet named: Riverbend's intake/eligibility
# summarizer, or Meridian's payment authorize/capture reconciliation call.
def call_model(messages, model=MODEL):
    attrs = {"gen_ai.operation.name": "chat",
             "gen_ai.provider.name": "aws.bedrock",
             "gen_ai.request.model": model}
    t0 = time.monotonic()                      # one logical op -- retries included
    try:
        resp = bedrock.converse(
            modelId=model, messages=messages,
            inferenceConfig={"maxTokens": 400, "temperature": 0},
        )
    except Exception as e:
        attrs["error.type"] = type(e).__name__  # Stable attr: the error-rate SLI leans here
        DUR.record(time.monotonic() - t0, attrs)
        raise
    DUR.record(time.monotonic() - t0, attrs)
    u = resp["usage"]
    TOK.record(u["inputTokens"],  {**attrs, "gen_ai.token.type": "input"})
    TOK.record(u["outputTokens"], {**attrs, "gen_ai.token.type": "output"})
    # No cost metric exists -- derive it downstream: tokens x list price, by model.
    return resp["output"]["message"]["content"][0]["text"]

Three instruments and one Stable attribute give you latency, traffic, errors, and the token counts cost is derived from — and the SLI you negotiate tomorrow is measured from exactly this call site.
