Observability for LLM Systems: Traces, Spans, and LangSmith

Week 7 · Day 1 Observability & SRE ~24 min · reading @150 wpm + diagram + check

Your client handed you a week of raw latency logs and one sentence: "intake froze about twenty minutes Tuesday, no alert fired." Those logs can't answer the question, because a log line has no parent and no duration — it's a timestamp with an opinion. Today you learn the structure that can: the trace, its spans, and the run tree that nests them — why the span is the natural unit of an LLM call, how latency, tokens, and dollars attribute to specific spans instead of to "the model," and the two documented ways nesting breaks silently. Then the FDE payoff: handing a client a shareable trace URL instead of an adjective, and the disclosure decision that comes with it. Scroll; the panel on the right builds one intake request into one run tree.

The vocabulary

Run, trace, project — the words that replace "it's slow"

Start with the noun that does all the work. A run is a single unit of work your application performs: one LLM call, one prompt format, one document retrieval, one tool invocation. LangSmith states the equivalence outright — if you know OpenTelemetry, a run is a span. One idea, two vocabularies, both in the same meeting. A run has a name, a type, inputs, outputs, a start, an end, and a parent.

That last property is what a log line does not have. A trace is "a collection of runs for a single operation" — one user request that fires an agent, which calls a model, then a tool, then the model again, produces one trace holding all of those runs, bound by a unique trace ID. Above that sits a project: the container for every trace of one application. Three nouns, one hierarchy.

Now re-read the client's incident note with that vocabulary in hand. "The portal froze" is an adjective attached to a system. "The eligibility run under trace a762af6c… started at 14:02:11 and ended at 14:22:00; the summary run never started" is a fact attached to a boundary. Observability for LLM systems is that move — and it needs its own week because agent systems are non-deterministic, multi-step, and branch differently on every request.

Instrumentation

Three mechanisms, one environment variable

Turning tracing on is configuration, not a rewrite. Set LANGSMITH_TRACING=true and LANGSMITH_API_KEY, and your instrumented code starts emitting; LANGSMITH_PROJECT routes traces to a named project, and if you leave it unset a default project is created on first ingestion. One gotcha for the runbook: non-US accounts must also set LANGSMITH_ENDPOINT to their regional API URL, with no trailing slash — otherwise the API key "won't be recognized and requests will fail to authenticate." Five minutes of config; a lost afternoon if nobody knows it exists.

For your own code there are exactly three manual-instrumentation mechanisms. The @traceable decorator is the recommended default: put it on a function and that function becomes a run. The trace context manager (Python only) wraps a block instead of a function. The low-level RunTree API is for explicit trace construction. Reach for RunTree when control flow is too dynamic for decorators — and accept that you now own details the decorator was handling for you.

The parameter that makes a span legible is run_type. Marking a function run_type="llm" is what lets LangSmith render token counts and latency correctly; "tool" marks tool spans, "retriever" retrieval, "chain" a root that orchestrates. Get the type wrong and the span still records — it just stops being countable in the LLM-call charts and the cost rollup. Typing your spans isn't cosmetic; it's the schema.

Run trees · nesting

Parent and child: where the structure comes from

Nesting is what turns a pile of spans into a tree you can read. With the decorator it happens by composition: wrapping the model client logs every LLM call automatically as a nested span, and @traceable on the calling function "captures the full pipeline in one trace, with the tool call and LLM call as nested spans." With RunTree the edge is literal — create a root RunTree(name=…, run_type="chain", inputs=…), .post() it, then .create_child(name=…, run_type="llm", …), and close each with .end(outputs=…) plus .patch().

For the client's intake path, the tree you want is three nodes and takes an afternoon: a root chain span for the intake request, a child tool span for the eligibility/payer call, a child llm span for the patient summary. That shape is the deliverable's foundation, because every later question — which step was slow, what did it cost, what did the model see — is answered by pointing at one of those three nodes.

Now the part that will bite you, and it fails silently. Nesting relies on implicit context propagation through Python contextvars. Under Python below 3.11, asyncio lacks proper contextvar support, "which can lead to disconnected traces" — child runs show up as separate top-level traces and your tree becomes confetti. More common still: ThreadPoolExecutor by default breaks tracing, because contextvars start empty inside new threads. The fixes are boring: upgrade to 3.11+, use LangSmith's ContextThreadPoolExecutor, or pass the parent explicitly via langsmith_extra={"parent": run_tree}. Any brownfield service doing concurrent fan-out is a candidate — check before you trust your first waterfall.

Latency attribution

Which span owns the twenty minutes

Because every run carries its own start and end, a trace renders as a waterfall: nested bars whose widths are durations and whose indentation is parentage. This is the view that converts the client's incident note into an engineering fact. "Intake froze about twenty minutes" becomes "the eligibility tool span held for 19m48s and the llm span never started" — not a model problem at all, and indistinguishable from one in a flat log stream.

Read the waterfall with one rule: the span that owns the latency is the deepest one whose bar is nearly as wide as its parent's. A root that takes 20 seconds tells you nothing. A root at 20 seconds with a retrieval child at 19.2 tells you where to spend the afternoon. Blame travels down the tree, never up.

For streaming LLM runs there's a second number that matters more than total duration: time-to-first-token, the wait a human actually feels. TTFT is auto-populated for streaming runs under traceable or the SDK wrappers — but if you dropped down to the RunTree API you must emit run_tree.add_event({"name": "new_token"}) on the first token yourself, or TTFT stays empty forever. That's the tax for hand-rolling, and exactly the kind of gap that makes a dashboard look healthy while users complain.

Tokens & cost

Cost rolls up three levels — and metadata does not roll anywhere

The same tree that answers "why is it slow" answers "what does it cost" — the one artifact you can show both an engineer and a CFO. Usage aggregates at three levels: the trace tree shows total usage for the whole trace, aggregated values for each parent run, and token and cost breakdowns for each child run; project stats total every trace in the project; dashboards plot the trend over time. The UI splits usage into three buckets — Input (prompt tokens, incl. cache reads), Output (response tokens, incl. reasoning), and Other, which carries "costs from tool calls, retrieval steps, or any custom runs." That third bucket is the one people forget: non-LLM spans can carry money too.

Automatic cost computation needs three things present: token counts, the model and provider, and a model price entry. You get it free when using LangChain, @traceable over common providers, or the LangSmith wrappers. When you're pricing something the platform can't infer — a vendor API call, a per-document retrieval fee, non-linear pricing — attribute manually by setting usage_metadata on the run tree from inside the function, or returning it as a top-level key of the output. The fields cover input and output tokens, cache-read and cache-creation details, reasoning tokens, and direct input_cost/output_cost if you'd rather submit dollars than counts.

Then the trap that quietly invalidates analysis: "Metadata and tags are not propagated from parent to child runs, or vice versa." If the tenant, merchant, or idempotency key sits only on the root run, every per-LLM-call and per-tool-call chart silently drops it — you group by a key that exists on a third of your population and never see an error. Same for threads: without the session identifier on child runs, "token counts and costs from those runs won't be included in thread-level aggregations." Correlation keys go on the root and the children, every time.

Shapes & the UI

Trace, thread, trajectory — pick the right shape

One trace covers one operation. Client complaints are rarely that tidy: "the assistant got confused after the third message" spans several requests. That's what a thread is for — a sequence of traces representing one multi-turn session, where a turn is one exchange (a user message plus everything the agent does in response) and each turn is its own trace. Traces join a thread by carrying a thread_id metadata key; without it, the UI shows only individual runs.

A trajectory is the third shape: a flat, ordered, de-duplicated list of messages projected over a thread's traces with the nesting removed — "the path an agent took from start to finish." The docs differentiate the three by use, which is worth memorizing as a triage rule: a trace when debugging why one operation failed or ran slow; a thread when the behavior only makes sense across turns, timing and nesting intact; a trajectory to read what was exchanged without execution detail — usually the version you paste into a client conversation.

Inside a trace, the side panel offers three views with keyboard switches: Messages (beta, M) is the conversation layer for finding where to look; Turns (T) gives per-turn cards; Details (D) is the debugging layer for a specific run's inputs, outputs, timing, token counts, errors, and metadata. The documented loop, worth making muscle memory: scan Messages for the anomaly — a bad tool result, an unexpected handoff, a latency spike — click through to the exact run in Details, inspect, return.

The client artifact

A URL instead of an adjective

Here is the move that changes how clients see you. Open the trace, click Share in the more menu at the top of the Details view, copy the link. The public URL has the shape https://smith.langchain.com/public/<uuid>/r, and shared traces "are accessible to anyone with the link, even without a LangSmith account. They can view the trace but not edit it." You stop emailing "the eligibility call was very slow" and start sending a link where the client sees the bar, the duration, and the inputs themselves.

The same trace ID is also the join key into their existing logs. The See Logs button in the Details view jumps to the deployment's server logs with the filter box pre-filled with the trace ID you were just looking at. Your client already has logs; what they never had was a correlating key instead of a timestamp guess. Emitting the trace ID into their log lines is a small change that turns two systems into one investigation.

Now the governance half, which the docs bold and so will we: "Sharing a trace publicly will make it accessible to anyone with the link. Make sure you're not sharing sensitive information." A trace contains every run with full inputs and outputs. On a healthcare intake path that is PHI; on a payment path it is card and PII data. Sharing is a disclosure decision wearing a UI button's clothing. Three things make it survivable: redact at emission, not before pressing Share; keep the standing audit item — Settings → Shared URLs lists every publicly shared trace in the workspace with a per-trace Unshare; and know the escape hatch, the delete_runs endpoint, which deletes by project, trace-ID list, or metadata key-value when something got captured that shouldn't have been. Self-hosted inside a VPC, the public link only reaches members authenticated within that VPC.

Portability & limits

OpenTelemetry underneath, and the numbers that bound you

Know the standard sitting under all of this: it's what keeps your instrumentation from being a vendor bet. OpenTelemetry's GenAI semantic conventions define agreed span names and attributes for model calls. Two attributes are required on an inference span — gen_ai.operation.name and gen_ai.provider.name — and token attributes like gen_ai.usage.input_tokens are recommended, with the rollup rule that cached input tokens are included in the input total rather than reported separately. One logical call is one span, retries inside it. The conventions are at Development status and have moved out of the main OpenTelemetry repo into a dedicated semantic-conventions-genai project — expect churn, and don't cite the old page. LangSmith accepts OTLP directly, and the documented topology is fanout: your app emits spans to a Collector that routes them to several backends at once. Instrument once, stay portable. Day 4 goes deeper.

Two hard numbers belong on your slide before you promise a client anything. A trace is capped at 25,000 runs — past that, additional runs for that trace are rejected, a real risk for a long agent loop. And LangSmith SaaS retains trace data for 180 days from ingestion, after which traces are permanently deleted. If a trace is evidence — a regulator's sample, a benchmark baseline — add it to a dataset; datasets persist indefinitely even after the source trace is gone.

Step back to the idea holding the day together: everything today was about giving a claim a boundary. A log line asserts; a span measures, because it has a parent, a start, an end, a type, and a cost. Once your client's critical path has boundaries, "flaky" becomes a duration, "expensive" becomes dollars per decision, and "I'm always the last to know" becomes a threshold something can fire on — which is what the rest of this week builds on top of the tree you instrument today.

FDE mindset

When a client describes a problem with an adjective, hand back a boundary. Never answer "is it slow?" with a sentence you could have written without the data — answer with the span that owns the time, the tokens it burned, and a link they can open without an account. And before you send that link, ask the question nobody at the client will ask you: what is inside this trace that isn't allowed to leave?

Deep dive: instrumenting a brownfield path without a rewrite

Optional. ~10 minutes. How to get a usable run tree out of a codebase you didn't write.

1 · Pick one path, not the app. The week's deliverable says "one instrumented path" for a reason. Choose the path the incident note points at — intake/eligibility for healthcare, authorize/capture for payments — and instrument only its root plus its two or three real children. A complete tree over one path beats partial coverage everywhere.

2 · Decorate the seams, not the internals. The functions worth a @traceable are the ones that cross a boundary: an outbound HTTP call, a database round trip, a model call, a queue publish. Those are where the time actually goes. Internal helpers add depth without adding information, and depth costs you the 25,000-run ceiling on long loops.

3 · Decide your correlation keys before you decorate. Tenant, request ID, and the domain key (member ID, idempotency key) go on the root and every child, because metadata does not propagate. Write them as a tiny helper that sets metadata on get_current_run_tree(), and call it in every decorated function — otherwise someone adds a span in month two and your charts lose a population silently.

Worked example — turning "month-end noise" into a query

Finance track: a double-fund is two spans that should have been one — the same logical operation appearing twice. In a flat log stream that is invisible; in a run tree with the idempotency key attached as metadata to the payment span, it is a filter: group traces by idempotency key, show any key with more than one capture span. The instrumentation didn't fix the bug — it converted an unprovable suspicion into a countable population, which is what makes the W5 idempotency gap arguable in front of Sam. Same pattern on the healthcare side: the eligibility span boundary is what makes the W3 payer-outage finding measurable rather than anecdotal.

Version floors worth noting. The langsmith Python SDK is at 0.10.16 and requires Python 3.10+. The OpenTelemetry path needs langsmith>=0.3.18, with >=0.4.25 recommended for important OTel fixes — check the pinned version in a client's lockfile before you promise that LANGSMITH_OTEL_ENABLED=true will just work.

Production code: one intake request as one run tree

Root chain span, child tool span, child llm span — and the correlation key set on both levels, because metadata does not propagate.

# One intake request = one trace: root chain -> tool span -> llm span.
# Env: LANGSMITH_TRACING=true, LANGSMITH_API_KEY, LANGSMITH_PROJECT=riverbend-intake
# Auth: Bedrock API key in AWS_BEARER_TOKEN_BEDROCK (boto3 reads it; no IAM role).
import boto3
from langsmith import traceable, get_current_run_tree

bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")

def tag(**kv):                       # metadata does NOT inherit -- set it per run
    run = get_current_run_tree()
    if run: run.metadata.update(kv)

@traceable(run_type="tool")          # the span that held for 19m48s
def check_eligibility(member_id, tenant):
    tag(tenant=tenant, member_id=member_id)
    return payer.get_coverage(member_id)

@traceable(run_type="llm")           # run_type=llm is what renders tokens + latency
def summarize(coverage, tenant):
    tag(tenant=tenant)
    resp = bedrock.converse(
        modelId="us.anthropic.claude-haiku-4-5-20251001-v1:0",
        messages=[{"role": "user", "content": [{"text": render(coverage)}]}],
        inferenceConfig={"maxTokens": 400, "temperature": 0},
    )
    u = resp["usage"]
    return {"summary": resp["output"]["message"]["content"][0]["text"],
            "usage_metadata": {"input_tokens": u["inputTokens"],
                               "output_tokens": u["outputTokens"]}}

@traceable(run_type="chain")         # the root run IS the trace
def handle_intake(member_id, tenant):
    tag(tenant=tenant, member_id=member_id)
    return summarize(check_eligibility(member_id, tenant), tenant)

Three decorators and a two-line helper. That is the whole difference between "intake froze" and "the eligibility span held for 19m48s while the LLM span never started."
