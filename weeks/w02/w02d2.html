Embeddings & Vector Stores: turning meaning into geometry

Week 2 · Day 2 Foundation AI Engineering ~18 min · reading @150 wpm + diagram + check

Yesterday you chunked documents; today you make those chunks findable. An embedding turns a piece of text into one fixed-length list of numbers — a vector — and a vector store is the database that holds millions of them and answers "what's closest to this?" in milliseconds. Every retrieval decision an FDE makes downstream — quality, speed, memory, monthly bill — is set here, by four small choices: how long the vector is, how you measure closeness, how you index, and where you store it. The panel on the right builds the whole pipeline one stage at a time. Get these four right and RAG works; get them wrong and no amount of prompt tuning saves you.

The whole game

One model turns text into one fixed-length vector

Start with the single operation everything else hangs on. An embedding model takes a piece of text — a chunk, a query, a product description — and returns a fixed-length vector: an ordered list of floating-point numbers. "Fixed-length" is the part to hold onto. Whether you feed it one word or a full page, the output is the same length every time. Our model, Amazon Titan Text Embeddings V2 (on AWS Bedrock), makes this concrete: it returns 1,024 numbers by default — and you can request 512 or 256 instead — accepting up to 8,192 input tokens per call.

Why bother? Because once text is a vector, "related meaning" becomes "near in space," and "find me relevant documents" becomes a math problem a computer can do fast: rank every stored vector by its distance to the query vector and return the closest. That is the entire mechanical basis of semantic search and of the retrieval half of RAG. The model does the hard part — mapping language into a geometry where distance tracks meaning — and your job is to manage the consequences of that geometry.

So the FDE framing for today is deliberately narrow. You are not training embedding models; you are operating them. Four operational choices flow from this one vector: how many dimensions it should have, which similarity metric ranks it, which index makes the search fast at scale, and which vector store you run it in. Each choice trades quality against cost and speed, and — critically — several of them are locked at index-creation time, so getting them right up front is cheaper than discovering them in production. The rest of the reading walks those four choices in order.

Choice 1 · dimensionality

Dimensionality is a budget decision, not a "bigger is better" one

The length of the vector — its dimensionality — is your first lever. More dimensions can capture more nuance, and that is exactly why Titan V2 at its full 1,024 dims scores higher than the same model truncated to 512 or 256. But every extra dimension is a real cost paid on every vector you ever store: more storage on disk, more memory in the index, and more compute per comparison. Double the dimensions and you roughly double the bytes for your entire corpus.

That cost is the part beginners ignore and FDEs lead with. A million chunks at 1,024 float dimensions is a very different memory and infrastructure footprint than a million at 256 — and the search itself is slower because every distance calculation has four times as many numbers to chew through. When a client asks why their vector database is expensive or their latency is creeping up, "we picked the biggest embedding by reflex" is one of the most common answers.

There is also a hard ceiling lurking here that catches teams off guard: dimensionality can exceed an index's limits. As you'll see in a moment, the most popular Postgres extension for vectors won't build its fast index on vectors beyond 2,000 dimensions — so a raw 3,072-dim model is out unless you shorten it. Titan V2 at 1,024 sits comfortably under that cap, which is one reason its default is convenient. So dimensionality is never just "how good is it?" — it's "how good, at what storage and memory cost, and will my chosen index even accept it?" Decide it against a budget, the same way you sized the context window on Day 1.

Choice 1b · Matryoshka

You can shorten the vector — by design

Here is the lever that makes dimensionality genuinely tunable instead of fixed at the model's default. Titan Text Embeddings V2 was trained so you can shorten the vector — keeping the leading numbers and dropping the rest — without the embedding losing its concept-representing properties. You request a shorter vector by passing the dimensions parameter (1024, 512, or 256), and you get back a smaller, faster, cheaper-to-store embedding that still works.

This isn't a hack; it comes from a training technique called Matryoshka Representation Learning (MRL) — named for the nesting dolls. A single embedding is trained to encode information coarse-to-fine, so the first k dimensions are usable as a standalone embedding all by themselves. The leading numbers carry the broad strokes; later numbers add detail. MRL can yield embeddings up to much smaller with faster retrieval and no extra inference cost — you run the same model, you just keep fewer of the outputs.

The headline result is the one to quote to a skeptical client: Titan V2 cut to 512 dimensions retains about 99% of its full 1,024-dim accuracy, and 256 dimensions about 97% — a 4× smaller vector for a couple of points of quality. One operational warning, though: Titan returns a normalized vector by default (normalize: true), but if you truncate the vector yourself after generation rather than via the dimensions parameter, you must re-normalize the result — otherwise the distance math (next step) silently goes wrong. Shorten on purpose, and re-normalize if you do it by hand.

Choice 2 · similarity metric

The similarity metric decides what "closest" means

You have vectors; now you need to rank them. A similarity metric is the distance or similarity function that scores how close two vectors are, and there are three you'll meet constantly: cosine similarity (the angle between vectors), dot product / inner product, and Euclidean / L2 distance (straight-line distance). For normalized text embeddings, cosine is the common choice — it ignores magnitude and compares direction, and it normalizes scores to a tidy [-1, 1] range.

Two rules make this an FDE topic rather than trivia. First, the metric must match how the embeddings were trained — pick the wrong one and your "closest" results are quietly garbage even though nothing errors out. Second, in most vector stores the metric is fixed at index creation and cannot be changed afterward. Choosing it is a one-way door; switching later means rebuilding the index. So this is a decision you make deliberately on day one, not something you tune later.

Every store exposes its own menu of distance metrics. Pinecone offers cosine, squared Euclidean and dot product, chosen when the index is created. Chroma supports squared Euclidean, cosine and inner product — and its default is squared Euclidean, which cannot be changed after the index exists, so if you wanted cosine you had to say so up front. pgvector is the most generous, exposing six distance operators: L2, negative inner product, cosine, L1, and binary Hamming and Jaccard. The defaults differ across stores, so "we used cosine in dev, why are the results different in the new database?" usually means somebody accepted a different default metric without noticing.

Choice 3 · ANN index · HNSW

HNSW: high recall and fast queries, paid for in build time and memory

Comparing the query against every stored vector — exact search — is accurate but doesn't scale; at millions of vectors it's too slow. So vector stores use approximate nearest neighbor (ANN) indexes that trade a little accuracy for enormous speed. The dominant one is HNSW — Hierarchical Navigable Small World. It builds a multilayer graph you can navigate quickly, giving high recall and fast queries. The price: it is slower to build and uses more memory than the alternatives.

HNSW behaviour is governed by three knobs worth memorizing, because they show up in every store. The first is how many neighbour links each node keeps, which sets graph density. The second is how hard the index works while building — higher means a better graph and a slower build. The third is how hard it works at query time — higher means better recall and slower queries. In pgvector the build defaults are 16 links and a construction effort of 64, with query-time effort defaulting to 40. Chroma uses the same family of knobs with different names: construction effort defaults to 100, search effort to 100, and maximum neighbours to 16.

The practical reading: these are your recall-versus-speed dials. If a client's retrieval is "fast but occasionally misses the obvious document," raising ef_search trades a little query latency for better recall without re-embedding anything. If index builds are painfully slow on a large corpus, ef_construction is where that time is going. Knowing which knob moves which cost is exactly the kind of thing that turns a vague "search feels off" complaint into a one-line config change.

Choice 3b · ANN index · IVFFlat

IVFFlat: lighter and faster to build, but you trade recall

HNSW isn't the only option, and the alternative teaches the tradeoff clearly. IVFFlat (inverted-file flat) takes a different approach: it partitions the vectors into lists — clusters — and at query time only probes a subset of those lists rather than scanning everything. Because it isn't maintaining a rich navigable graph, it is faster to build and lighter on memory than HNSW.

The catch comes in two parts. First, IVFFlat needs training data: it has to see a representative sample of your vectors to choose where the cluster boundaries go, which means you generally build it after you have data loaded, not on an empty table. Second, it generally delivers lower recall than HNSW — if the relevant vector lives in a list you didn't probe, you simply miss it.

So the FDE decision rule is straightforward. Reach for HNSW when recall and query speed matter most and you can afford the heavier build and memory — which is most production semantic-search workloads. Reach for IVFFlat when you need fast, cheap index builds and lighter memory and can tolerate somewhat lower recall, or when your corpus changes often enough that HNSW's slow builds hurt. Both are exposed by pgvector, so you can switch between them on the same data without leaving Postgres — but you choose with the recall/build/memory triangle in mind, not by habit.

Choice 4 · where it lives

Vector stores — and the dimensionality limit that bites teams

Now, where do these vectors actually live? You'll meet three workhorses. pgvector (current release 0.8.3) is an extension that puts vectors inside Postgres, so your embeddings sit alongside your relational data with no extra service to run; it provides both HNSW and IVFFlat indexes. Chroma is a developer-friendly store with a simple collections API and a newer SPANN index for distributed / Chroma Cloud deployments (its configuration isn't yet user-customizable). Pinecone is a managed, serverless vector database that supports dense indexes for semantic search, sparse indexes for lexical search, and document records that mix dense + sparse + full-text ranking.

Now the gotcha that connects today's first choice to its last. In pgvector there are two different limits and they are far apart. The storage limit — how many dimensions a column can hold — is generous at 16,000, for both full-precision and half-precision columns. But the index limit, the maximum number of dimensions the index types can actually cover, is much lower: 2,000 dimensions for a full-precision vector column, and 4,000 for a half-precision one.

Put those together with a high-dimensional model — say a raw 3,072-dim embedding — and you get the classic trap: the vector is fully storable in a vector column (3,072 is well under 16,000), so inserts succeed and everything looks fine — but it exceeds the 2,000-dim index limit, so the moment you try to build an ANN index the whole thing fails. The fixes are exactly the levers from earlier in the reading: store it as halfvec (indexable to 4,000), or shorten the embedding below 2,000 dims. This is one more reason Titan V2's 1,024-dim default is convenient — it indexes directly, no workaround. But the principle stands: dimensionality and store choice aren't separate decisions — they constrain each other, and the time to notice is before you load five million rows.

Beyond dense · hybrid

Dense isn't the only kind of vector — sparse + dense = hybrid

One last reframe before tomorrow. Everything so far has been dense retrieval: the embedding is a few thousand mostly-nonzero numbers that capture meaning, so "car" and "automobile" land near each other. But meaning isn't everything. Sometimes you need an exact term — a part number, an error code, a surname — and a semantic embedding can blur right past it. That's the job of sparse retrieval: lexical vectors (think BM25 or SPLADE) that are mostly zeros with weight on the specific words that appear. Sparse captures exact matches; dense captures meaning.

Hybrid retrieval combines both, so you get semantic recall and exact-term precision in one query — which is why production RAG so often ends up hybrid rather than pure dense. One technical constraint rides along with sparse vectors: they typically require a dot-product metric. Pinecone makes this explicit — a sparse (lexical) index must use the dotproduct metric; it's the only valid option for sparse. This is also why Pinecone exposes dense indexes, sparse indexes, and document records that fuse dense + sparse + full-text ranking as distinct things.

Tie the day together. The vector you create has a length (dimensionality, tunable via Matryoshka), it's ranked by a metric (cosine / dot / L2, fixed at index creation), made fast by an index (HNSW for recall, IVFFlat for cheap builds), kept in a store (pgvector, Chroma, or Pinecone, each with its own limits), and optionally paired with a sparse partner for hybrid search. Tomorrow we go deep on retrieval strategies — dense vs sparse, fusion, and re-ranking — but those all run on the geometry you wired up today. Get the four choices right here and retrieval has a fighting chance; get them wrong and there's nothing downstream that fixes it.

FDE mindset

When an FDE designs a retrieval layer, the first questions aren't about models — they're "how long are the vectors, which metric ranks them, which index serves them, and does my store accept that dimensionality?" Several of those answers are locked at index-creation time, so you decide them on a whiteboard before loading data — not after a five-million-row migration tells you the index won't build.

Deep dive: dimensionality vs index limits

Optional. ~8 minutes. The numbers behind the picture.

Two limits, far apart. In pgvector, how many dimensions a column can store is not the same as how many it can index. Storage is generous; the ANN index is the bottleneck.

pgvector limits (storage vs index)
  • vector — store up to 16,000 dims · index (HNSW/IVFFlat) up to 2,000 dims
  • halfvec — store up to 16,000 dims · index up to 4,000 dims
  • bit — store up to 64,000 dims
  • sparsevec — store up to 16,000 non-zero elements · HNSW index up to 1,000 non-zeros

A high-dimensional (3,072-dim) vector stores fine in a vector column (under 16,000) but exceeds the 2,000-dim index limit — so the ANN index won't build. Fix it by storing as halfvec (indexable to 4,000) or shortening below 2,000 dims. Titan V2 at 1,024 dims indexes directly — no workaround needed.

Why shortening is safe. Titan Text Embeddings V2 is trained with Matryoshka Representation Learning, encoding information coarse-to-fine so the leading k dimensions stand alone. A Titan V2 vector cut to 512 dims keeps ~99% of its 1,024-dim accuracy, and 256 dims ~97% — a 4× smaller vector with no extra inference cost. Caveat: request the size via the dimensions parameter, or re-normalize if you cut the vector by hand.

HNSW defaults to keep handy. pgvector builds with 16 links per node and a construction effort of 64, and searches with an effort of 40. Chroma builds with a construction effort of 100 and 16 maximum neighbours, and searches with an effort of 100. Raising the search effort buys recall at the cost of query latency — and it is tunable at query time, without re-embedding anything.

Production code: embeddings and the dimension dial

Titan Text Embeddings V2 has a built-in Matryoshka dimension dial -- pick 1024, 512, or 256 to trade a little accuracy for storage and latency.

# Embedding with Titan V2's built-in dimension dial (Matryoshka).
# Auth: AWS_BEARER_TOKEN_BEDROCK (Bedrock API key) -- no IAM credentials.
import json, boto3

bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")

def embed(text: str, dims: int = 1024) -> list[float]:
    # Titan V2 emits 1024 (default), 512, or 256 dims. 512 keeps ~99% of 1024's
    # accuracy, 256 ~97% -- shrink the vector at the source to cut storage/latency.
    resp = bedrock.invoke_model(
        modelId="amazon.titan-embed-text-v2:0",
        body=json.dumps({"inputText": text, "dimensions": dims, "normalize": True}),
    )
    return json.loads(resp["body"].read())["embedding"]

# The store's vector column MUST match `dims`. Create it once, up front:
#   CREATE TABLE chunks (id bigserial, body text, embedding vector(1024));
#   CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);

512 dims keep ~99% of 1024's accuracy, 256 ~97%. The store's vector column must match `dims` exactly, and you must use the same model at ingest and query -- different models live in incompatible spaces.
