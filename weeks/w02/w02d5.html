Building a RAG Eval Harness — and the Pipeline It Measures

Week 2 · Day 5 Foundation AI Engineering ~18 min · reading @150 wpm + diagram + check

All week you've been assembling the pieces of retrieval-augmented generation. Today you wire them into one end-to-end pipeline — documents in, grounded answers out — and then do the thing that separates a demo from a delivery: you build the eval harness that tells you, with numbers, whether the pipeline actually works. A RAG system you can't measure is a RAG system you can't improve, and "it seemed fine when I tried it" is not something you say to a client. Scroll the reading; the panel on the right assembles the full pipeline stage by stage, then loops the harness back over it to score what came out.

The whole game

A pipeline you can't measure is a pipeline you can't ship

This is the milestone day for Week 2: everything you've learned about chunking, embeddings, vector stores, and retrieval gets connected into one working path — raw documents on the left, a grounded answer on the right. That path is end-to-end RAG, and by the end of today you'll have run one and, more importantly, scored one.

Here's the reframe that makes you an engineer instead of a tinkerer: a RAG pipeline has many knobs — chunk size, overlap, how many candidates you retrieve, whether you rerank, which index parameters you set — and every one of them changes the output in ways you cannot eyeball. Change the chunk size and answers might get better, or worse, or better for some questions and worse for others. The only honest way to know is to measure. An eval harness is the apparatus that turns "feels better" into a number you can defend in a client review.

Two ingredients make a harness. First, a labeled test set — questions paired with the context that should answer them — so you have something to measure against. Second, a set of metrics that score each run. The reigning open-source toolkit for RAG specifically is Ragas, and it exposes a canonical four: Faithfulness (is the answer grounded in the retrieved context, with no unsupported claims?), Context Precision (are the retrieved chunks actually relevant — signal vs. noise?), Context Recall (did retrieval surface everything needed?), and Response Relevancy (does the answer directly address the question that was asked?). Hold those four in your head; every stage we build today is something one of them will catch when it breaks.

Stage 1 · ingest

Chunking is a retrieval decision, not a formatting chore

RAG starts by breaking your documents into pieces small enough to embed and retrieve. It's tempting to treat this as plumbing — split on every N characters and move on — but chunking is one of the most load-bearing decisions in the whole pipeline. Chunk too large and a single chunk smears several topics together, so a retrieval hit drags in noise; chunk too small and you sever the sentence from the context that gives it meaning.

The workhorse here is LangChain's RecursiveCharacterTextSplitter. Instead of blindly cutting at a fixed offset, it splits on a priority-ordered list of separators — the default is ["\n\n", "\n", " ", ""] — trying the largest semantic unit first (paragraph breaks), and only recursing down to finer separators (line breaks, then spaces, then raw characters) when a piece is still larger than the target chunk_size. The effect is that it tries hard to keep paragraphs, then sentences, intact before it resorts to chopping mid-word.

The second knob is chunk_overlap: it repeats the trailing characters of one chunk at the start of the next, so a fact that straddles a boundary isn't orphaned — context flows across the seam. In the library's base defaults, chunk_size is 4000 and chunk_overlap is 200 characters, though those are starting points you'll tune per corpus, not laws. The FDE instinct: when retrieval quality is mysteriously bad, the chunker is one of the first places to look, because every downstream stage inherits the boundaries it drew.

Stage 2 · index

Embeddings go into an index built for approximate search

Each chunk is turned into an embedding — a vector — and stored in a vector store. Searching millions of vectors by brute force is too slow, so production stores use an approximate nearest-neighbor (ANN) index. The dominant one is HNSW — Hierarchical Navigable Small World — a graph structure that lets a query "navigate" toward its nearest neighbors in roughly logarithmic hops instead of scanning everything.

HNSW has knobs, and they encode a recall-versus-cost trade you'll set deliberately. In pgvector (Postgres' vector extension, 0.8.3), you create one like CREATE INDEX ON items USING hnsw (embedding vector_l2_ops) WITH (m = 16, ef_construction = 64). The build-time parameters m (default 16) and ef_construction (default 64) govern how rich the graph is: higher values raise recall but cost more build time and memory. At query time, ef_search (default 40) trades the other way — raise it for better recall at the cost of query latency. That's the whole tuning story in one sentence: graph quality is paid for at build time, search thoroughness is paid for at query time.

pgvector earns its keep with two more things you'll reach for on real engagements: iterative index scans (since 0.8.0) that keep filtered queries accurate when a WHERE clause prunes the candidate set, and hybrid search that combines vector similarity with Postgres' built-in full-text search — fused via Reciprocal Rank Fusion or a cross-encoder. If you'd rather not run Postgres, a lighter option is Chroma (1.5.9): a chromadb.PersistentClient(path=...), a get_or_create_collection, then collection.add(documents=..., metadatas=..., ids=...) which embeds automatically, and collection.query(query_texts=..., n_results=...) to search — vector, hybrid, and full-text all supported. Same shape, smaller footprint.

Stage 3 · retrieve

The bi-encoder casts a wide, cheap net

Now a question arrives. The first retrieval stage uses a bi-encoder: the query and every document are embedded independently into vectors, and you find the nearest ones. The word "independently" is the whole point — because each document's vector doesn't depend on the query, you can precompute and index all document embeddings ahead of time (that's exactly what Stage 2 did) and, at query time, only embed the one incoming query and run a fast ANN lookup.

That makes the bi-encoder cheap and scalable: it can sweep an enormous corpus in milliseconds. The cost of that speed is precision — encoding the query and document in isolation means the model never gets to directly compare them, so the ranking is approximate. The standard move is therefore to retrieve more candidates than you need — on the order of ~100 — and treat them as a shortlist rather than a final answer. You're casting a wide net on purpose, accepting some junk in the haul because the next stage will sort it out.

This is where Context Recall lives as a metric. If the chunk that truly answers the question never makes it into that shortlist of ~100, no amount of clever reranking or generation downstream can recover it — the answer is doomed before it starts. Low recall at this stage is the most expensive failure in RAG, because it's invisible: the model will still produce a confident, fluent answer, just an ungrounded one.

Stage 4 · rerank

The cross-encoder pays for precision where it counts

The second stage is the cross-encoder reranker, and it's the mirror image of the bi-encoder. Instead of encoding query and document separately, it feeds the query and a candidate document together, jointly, through a single transformer to produce one relevance score. Because the model sees both at once, it can reason about how they actually relate — far more accurate than comparing two pre-baked vectors.

The catch is cost: there's nothing to precompute, because the score depends on the specific query-document pair. You'd never run a cross-encoder over your whole corpus — it would be ruinously slow. So you apply it only to the ~100 candidates the bi-encoder already shortlisted, rerank them, and keep the true top-k. This is the canonical two-stage retrieval pattern: a cheap, wide first pass for recall, then an expensive, narrow second pass for precision — spending compute only where it changes the answer.

That trade maps cleanly onto the metric you'll watch here, Context Precision: of the chunks you ultimately hand the generator, what fraction are genuinely relevant, and are the relevant ones ranked highest? A good reranker is precisely the lever that pushes the signal up and the noise down. When a client says "the retrieval pulls back vaguely-related stuff and the answers wander," a reranker is very often the fix — and now you can prove it moved Context Precision rather than just asserting it feels sharper.

Stage 5 · generate

Generation grounded in the chunks that survived

With a tight, reranked top-k in hand, the final stage is generation: the model writes an answer conditioned on the retrieved context. This is the payoff of everything upstream — the model isn't answering from its parametric memory, it's answering from the specific passages you placed in front of it. Good retrieval makes this stage almost easy; bad retrieval makes it impossible, because the model can only ground its answer in what it was actually given.

And this is exactly where the connection to Week 1 snaps shut. A hallucination, remember, is usually a window problem — the needed fact was never in front of the model. RAG's entire job is to fix that by getting the right context into the window. But "we added RAG" is not the same as "the answers are grounded." The retrieval might miss; the reranker might bury the gold chunk; the generator might drift past its sources and embellish a claim none of them support. You have no idea which of those is happening — and "it looked fine in the three examples I tried" is not evidence, because the failures you didn't try are exactly the ones that reach a client. You only know once you measure the output systematically. That is the precise hand-off into the harness.

Stage 6 · evaluate

Four metrics score what the pipeline produced

Now the harness loops back over the run and grades it. Ragas gives you the canonical four, and each catches a different failure you just walked past.

Faithfulness is the grounding metric, and it's worth understanding mechanically because you'll explain it to clients. An LLM judge decomposes the generated answer into atomic claims, then checks each claim against the retrieved context — can this specific statement be inferred from what we actually retrieved? The score is simply supported claims ÷ total claims, a number from 0 to 1. Crucially, faithfulness measures grounding, not correctness against a reference: an answer can be 100% faithful to its context and still wrong if the context was wrong — but if faithfulness is low, the model is inventing claims its own sources don't support. That's your hallucination alarm.

Response Relevancy attacks a different failure — the technically-grounded answer that dodges the question. Ragas computes it by generating artificial questions from the answer (default 3), embedding them, and averaging their cosine similarity to the original user input: score = (1/N) Σ cos(E_g_i, E_o). The intuition: if you can reconstruct the user's question from the answer, the answer was on-target; if the reverse-engineered questions wander off, the answer didn't really respond to what was asked. Together with Context Precision and Context Recall on the retrieval side, these four give you a scorecard that pinpoints where the pipeline failed, not just that it did — low recall points at Stage 3, low precision at Stage 4, low faithfulness at Stage 5.

Closing the loop

Where the test set comes from — and why this is the milestone

Every metric above needs something to score against, which means the harness needs a labeled test set: questions paired with the context that should answer them. On a real engagement you rarely have one sitting around, and hand-writing hundreds of question/answer pairs is slow and biased toward the obvious cases. Ragas solves this by generating a test set synthetically from your own documents.

The generation runs in two phases. First it builds a KnowledgeGraph from the documents and enriches it with transformations — extracting entities, relationships, and summaries that turn a pile of text into something queryable. Then its TestsetGenerator synthesizes queries across a deliberate mix of types: roughly 50% SingleHopSpecific (answerable from one chunk), 25% MultiHopAbstract, and 25% MultiHopSpecific (questions that require stitching several chunks together). That distribution matters: a test set of only single-hop questions would flatter a pipeline that's actually terrible at the multi-hop reasoning real users demand.

And that's the milestone. You now hold the full loop: chunk → index → retrieve → rerank → generate, wrapped in a harness that synthesizes a test set and scores every run on four metrics. This is the difference between handing a client a demo and handing them a system — because the moment you can measure, you can tune. Change the chunk size and re-run the harness; the numbers tell you if it helped. Add a reranker; watch Context Precision move. That tight measure-tune-remeasure loop, not any single clever trick, is what makes a RAG pipeline actually get good. Diagnose with numbers, ship with evidence.

FDE mindset

Anyone can stand up a RAG demo in an afternoon; what a client pays an FDE for is the harness around it. When someone asks "is the AI any good?", the amateur answer is "it seems pretty good" and the engineer's answer is "on our synthetic test set it scores 0.91 faithfulness and 0.78 context precision, and here's the chunk-size change that moved precision +0.06." Build the ruler before you build the thing you measure.

Deep dive: HNSW tuning & the two-stage cost trade

Optional. ~10 minutes. The numbers behind the picture.

HNSW is a recall/cost dial, in three parts. Two parameters are paid at build time and one at query time. In pgvector 0.8.3 the build-time defaults are m = 16 and ef_construction = 64; raising either makes a richer graph that retrieves more of the true neighbors (higher recall) but costs more build time and memory. The query-time parameter ef_search defaults to 40; raising it explores more of the graph per query — higher recall, higher latency. Build quality and search thoroughness are separate budgets.

Why two stages instead of one. A cross-encoder is more accurate than a bi-encoder because it encodes the query and document jointly — but that's also why it can't be precomputed and can't scale to a whole corpus. The pattern resolves the tension: let the cheap bi-encoder reduce, say, a million chunks to ~100 candidates, then spend the expensive cross-encoder only on those 100.

Worked example — where the compute goes
  • Corpus: 1,000,000 chunks, all bi-encoder vectors precomputed and HNSW-indexed
  • Stage 1 (bi-encoder + HNSW): embed 1 query, ANN lookup → ~100 candidates · milliseconds
  • Stage 2 (cross-encoder): 100 joint query-document passes · the expensive part, but bounded at 100
  • Generation: conditioned on the reranked top-k only

Run the cross-encoder over all 1,000,000 chunks instead and the same query would take ~10,000× the rerank compute — which is exactly why nobody does it. The two-stage split spends precision only on the shortlist that could plausibly contain the answer.

Recall caveat. The reranker can only reorder what the bi-encoder handed it. If the gold chunk isn't in the ~100 candidates, no reranking recovers it — so when Context Recall is low, the fix lives in Stage 1 (better chunking, embeddings, or a larger candidate set), not in the reranker.
