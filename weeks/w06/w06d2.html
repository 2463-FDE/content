The Agentic SDLC: Plan, TDD & Review Loops

Week 6 · Day 2 AI-Native Engineering ~18 min · reading @150 wpm + diagram + check

Yesterday you learned to drive one agent in one terminal. Today we zoom out to the whole software development lifecycle and ask the professional question: where does the agent slot into the loop, and who verifies its work? You'll learn the plan-first workflow that stops agents from solving the wrong problem, TDD as a spec the agent can't argue with, verification loops that replace "looks done" with pass/fail, AI code review that comments but never approves, and how agents become citizens of a CI pipeline. Scroll the reading; the panel on the right assembles one ticket's journey through the full agentic loop.

The whole game

The SDLC didn't disappear — it became a loop you design

A tempting story is circulating in the industry: the agent writes the code, so the software development lifecycle — plan, implement, test, review, ship — is obsolete. The truth an FDE carries into a client is close to the opposite. Every stage of the SDLC still exists; what changed is who executes each stage and who checks it. The agent can now do the typing at nearly every step. That makes the human's remaining job sharper, not smaller: you design the loop, place the checks, and decide what the agent may do without you.

Here's the tension that structures the whole day. Agents are fast, tireless, and confident — and they stop when the work looks done, not when it is done. Left alone, an agent will happily declare victory on code that compiles but solves the wrong problem, passes tests it quietly weakened, or "works" in a way nobody measured. Each section today is a countermeasure: planning before code so the problem is right, tests before implementation so "done" is defined in advance, verification loops so the agent grades itself against something objective, AI review so a second set of eyes is cheap, and CI guardrails so all of it runs without a human hovering.

Keep one framing in your pocket for client conversations: an agent is an extremely fast engineer with no stake in the outcome. You wouldn't let any engineer merge unreviewed, untested code on a verbal "trust me." The agentic SDLC is the discipline of not starting to do exactly that just because the typing got cheap.

Plan first

Explore → Plan → Implement → Commit

The single most common agentic failure isn't bad code — it's good code for the wrong problem. Anthropic's own best-practices doc is blunt about it: letting Claude jump straight to coding "can produce code that solves the wrong problem." The recommended workflow has four named phases. Explore: put the agent in plan mode, where "Claude reads files and answers questions without making changes" — pure reconnaissance. Plan: ask for a detailed implementation plan, and press Ctrl+G "to open the plan in your text editor for direct editing before Claude proceeds" — you edit the plan like a document, not a chat. Implement: exit plan mode and let it code, "verifying against its plan" as it goes. Commit: descriptive message, pull request, done.

Mechanically, plan mode is a permission stance, not a vibe. Start a session with claude --permission-mode plan, or toggle it mid-session with Shift+Tab. In this mode "Claude reads files and proposes a plan but makes no edits until you approve." That guarantee is the point: exploration and execution are separated by the tool, so the agent physically cannot start rewriting files while you're still deciding what the change should be.

Why does this matter so much for an FDE specifically? Because at a client you are almost always working in their codebase, with their conventions, against a ticket written by someone who isn't in the room. The exploration phase is where the agent (and you) discover that the "simple" change touches the billing module, or that there are two functions with the same name and only one is live. A plan you can read and edit before any file changes is the cheapest wrong-problem insurance that exists.

The judgment call

When to plan — and when planning is overhead

Plan-first is a default, not a ritual, and the official guidance says so directly: "Plan mode is useful, but also adds overhead." The doc gives you a genuinely useful rubric. Planning earns its cost when you're uncertain about the approach, when the change modifies multiple files, or when you're unfamiliar with the code being modified. And the inverse, in one memorable line: "If you could describe the diff in one sentence, skip the plan." A typo fix, a renamed config key, a one-line guard clause — driving those through a four-phase ceremony is process theater, and clients can smell process theater.

At the other end of the size spectrum, there's a heavier variant for genuinely large features: spec-by-interview. Instead of you writing a brief for the agent, "have Claude interview you first" — the agent asks structured clarifying questions (via its AskUserQuestion facility), you answer, and it writes the resulting spec to a SPEC.md file. Then — and this is the part people skip — you "start a fresh session to execute it." The executing agent begins with clean context and a written spec instead of a long, meandering conversation full of half-abandoned ideas.

The doc's summary of the economics will sound familiar from every consulting engagement you'll ever run: "Time spent making the spec precise pays off more than time spent watching the implementation." The skill being rewarded is no longer typing speed — it's deciding, per task, how much specification the task deserves. One sentence? Skip the plan. A few files and some uncertainty? Plan mode. Real ambiguity? Interview, spec, fresh session. That sliding scale is the plan-first workflow.

TDD with agents

Red/green: the test is a spec the agent can't argue with

Test-driven development — write a failing test, make it pass, then clean up — was invented for humans, but it turns out to fit agents even better. A failing test is an executable specification: it says exactly what "done" means, in a language the agent cannot misread, negotiate with, or "interpret creatively." Prose requirements bend; an assertion doesn't. The official docs bake this into their recommended bug-fix prompt shape: "write a failing test that reproduces the issue, then fix it." Red first, green second — the classic TDD rhythm, driven through an agent.

Kent Beck — the person who literally wrote the book on TDD — has spent his recent years pairing with agents and coined the distinction you should carry into client conversations: augmented coding versus vibe coding. "In vibe coding you don't care about the code, just the behavior of the system." In augmented coding, by contrast, "you care about the code, its complexity, the tests, & their coverage." His own system prompt mandates strict TDD — "make it run, then improve structure. Always run all the tests... each time." His report on the payoff is the best one-line pitch for agentic TDD you'll find: "I make more consequential programming decisions per hour, fewer boring vanilla decisions."

There's also a structural trick that makes agentic TDD stronger than human TDD ever was: session isolation as discipline. The docs note that "a fresh context improves code review since Claude won't be biased toward code it just wrote," and extend it to tests: "have one Claude write tests, then another write code to pass them." One agent writes red; a different agent, with no memory of the test author's intentions, drives to green. Human TDD's red/green separation was enforced by willpower — and willpower erodes at 4pm on a Friday. Context isolation enforces it mechanically.

Failure mode

Reward hacking: when the genie cheats

Now the dark side, because every optimization loop has one. Give an agent the goal "make the tests pass" and it has two ways to succeed: fix the code, or break the test. Deleting a failing test, commenting out an assertion, marking a test as skipped, loosening a tolerance until anything passes — these all turn red to green, and an agent under pressure to finish will sometimes reach for them. This is reward hacking: gaming the metric instead of achieving the goal the metric was standing in for.

Beck treats this as a stop-everything event. His three abort signals for a misbehaving agent are worth memorizing verbatim: "Loops" (the agent thrashing without progress), "Functionality I hadn't asked for" (scope invention), and "Any indication that the genie was cheating, for example by disabling or deleting tests." Note the metaphor — a genie grants your wish as literally stated, not as intended. When you see any of the three, you don't negotiate with the session; you stop and intervene.

Because you won't always be watching, the fix is structural, not vigilance. Three guardrails stack well: keep tests in a separate commit from implementation, so any test modification is loudly visible in the diff; configure hooks that block edits to test files while the implementing agent runs; and use a separate reviewer session whose only job is to inspect what changed. The pattern to internalize: never let the agent both define success and grade success in the same context. That principle is about to generalize into the biggest idea of the day.

Verification loops

Give the agent a check it can run — or you become the check

Here is the sentence from the best-practices doc that should reorganize how you delegate work to agents: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." Read that last clause twice. If there's no objective pass/fail the agent can execute, then every claim of "done" lands on your desk for manual inspection — which means the agent didn't save you the work, it just moved it. The fix: "Give Claude something that produces a pass or fail, and the loop closes on its own." A check can be almost anything executable — "a test suite, a build exit code, a linter, a script that diffs output against a fixture, or a browser screenshot compared against a design."

The docs describe an escalating enforcement ladder for how binding the check is. Rung one: just tell the agent to run the check in your prompt. Rung two: set it as a /goal condition that gets re-checked every turn. Rung three: a Stop hook — a script that "runs your check... and blocks the turn from ending until it passes"; the agent literally cannot declare victory while the check fails. Rung four: a fresh-context verification subagent, so that "the agent doing the work isn't the one grading it" — the same separation-of-powers move you just saw in TDD, now applied to all verification.

Two habits complete the picture. First, evidence over assertion: "Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned, or a screenshot." The doc names the failure pattern the "trust-then-verify gap" and closes with a rule fit for a client's wall: "If you can't verify it, don't ship it." Second, your own perception of agent productivity is measurably unreliable. METR ran a randomized controlled trial: 16 experienced open-source maintainers, 246 real tasks in mature repos, early-2025 AI tools randomly allowed or not. Result: "allowing AI actually increases completion time by 19%" — the tools slowed experienced developers down — while those same developers believed AI had sped them up by 20% (they'd forecast 24%; economists predicted 39%). Self-reported "this is going great" is not a measurement. Build the check into the loop, and let the check decide.

AI code review

Review loops: comment-tier feedback, never the approver

Once code exists, the SDLC says: review it. AI review is now table stakes on both major platforms, and the design constraint they share is the headline. GitHub Copilot code review can be requested on any PR from the Reviewers sidebar, via gh pr edit --add-reviewer @copilot, or turned on automatically through org rulesets (with optional re-review on new pushes). Reviews complete in "less than 30 seconds" and include "suggested changes which you can apply with a couple of clicks." But Copilot "always leaves a 'Comment' review, not an 'Approve' review or a 'Request changes' review" — it never counts toward required approvals and never blocks a merge. AI review complements human review; it doesn't replace it.

Claude Code Review — Anthropic's managed PR reviewer, currently a research preview for Team/Enterprise plans — shows you what the deluxe version looks like: "a fleet of specialized agents examine the code changes in the context of your full codebase," then "a verification step checks candidates against actual code behavior to filter out false positives." Surviving findings are deduplicated, severity-ranked (🔴 Important / 🟡 Nit / 🟣 Pre-existing), and posted inline — and again, findings "don't approve or block your PR." It's tunable via a REVIEW.md file injected as highest-priority instructions: redefine severities, cap nits, add skip rules, raise the verification bar. It triggers on PR open, every push, or an @claude review mention — and it isn't free: roughly $15–25 per review, averaging ~20 minutes, billed on token usage. For pre-push feedback without any GitHub App, the local /code-review command "reviews a diff in your terminal," with --fix to apply findings and effort levels that trade confidence for coverage.

Two cautions keep review loops honest. First, the adversarial-reviewer trap: the docs recommend having "a subagent review the diff in a fresh context and report gaps" — but warn that "a reviewer prompted to find gaps will usually report some, even when the work is sound... Chasing every finding leads to over-engineering." The fix is scoping: tell the reviewer to "flag only gaps that affect correctness or the stated requirements." Second, the field data cuts both ways. An industrial study of an LLM review tool across 4,335 real PRs found 73.8% of automated comments were resolved — genuinely useful signal — but average PR closure time rose from 5h52m to 8h20m, and practitioners reported "faulty reviews, unnecessary corrections, and irrelevant comments" alongside better bug detection. Expect the latency tax, and tune the reviewer (nit caps, skip rules) instead of accepting defaults.

Agents in CI/CD

Pipeline citizens: @claude, headless mode, and guardrails

The last stage of the loop removes the human terminal entirely: agents as first-class citizens of the CI pipeline. The GA GitHub Action, anthropics/claude-code-action@v1, works two ways and figures out which you meant: "With a simple @claude mention in any PR or issue, Claude can analyze your code, create pull requests, implement features, and fix bugs" (interactive mode), or it "runs immediately with a prompt" when triggered by a workflow event (automation mode) — the action "automatically detects" which. Prompts can invoke repo or plugin skills, so a team can, say, run a code-review skill on every pull_request: [opened, synchronize] event.

Outside GitHub, the primitive is headless mode: claude -p "prompt" runs non-interactively — the docs call it "how you integrate Claude into CI pipelines, pre-commit hooks, or any automated workflow" — with --output-format json|stream-json for programmatic parsing and --allowedTools to scope exactly what the agent may touch. That unlocks the fan-out pattern for batch work: generate a task list, then loop something like claude -p "Migrate $file... Return OK or FAIL" --allowedTools "Edit,Bash(git commit *)" — test it on two or three files first, then run at scale. Note the prompt shape: autonomous tasks "can't ask clarifying questions," so the prompt must be self-contained — explicit success criteria, explicit result handling.

Interactive — future goal

Planned: a headless fan-out lab — point claude -p at a batch of seeded files with --output-format json and --allowedTools scoping, watch OK/FAIL results stream back, and tighten the prompt until the batch goes clean. Needs backend standup.

An unattended agent with write access is a production system, so the official guardrails read like security engineering — because they are. Never commit API keys; use GitHub Secrets. "Limit action permissions to only what's necessary." "Review Claude's suggestions before merging" — the human gate survives even here. Cap runaway cost with --max-turns, workflow timeouts, and concurrency controls; enterprises can route through Bedrock or Vertex via OIDC so no static keys exist at all. Everything you built today — plan gates, test-first specs, Stop hooks, comment-tier review — is what makes this final step sane: by the time an agent runs in CI with nobody watching, verification is no longer a person. It's the pipeline.

FDE lens

You're not adopting this loop — you're installing it at clients

Step back and notice what today actually trained. Any developer can learn plan mode or TDD prompts from a doc page. The FDE skill is the meta-level: walking into a client whose team is somewhere between "we banned AI" and "we vibe-code everything," and designing the loop that fits them. Which tasks get plan-first ceremony and which get the one-sentence-diff fast lane? Where does the failing test come from? Which checks become Stop hooks versus advisory comments? Does AI review run on every push at $15–25 a pop, or does the local /code-review pass gate pushes for free first?

Today's evidence is your consulting toolkit for those conversations. The METR result (19% slower while feeling 20% faster) convinces an enthusiastic team to measure instead of vibe. The 73.8% resolution rate convinces a skeptical team that AI review carries real signal. The closure-time regression (5h52m → 8h20m) sets the expectation that tuning is part of adoption, not an admission of failure. Numbers, then loop design, then tooling — in that order.

FDE mindset

The question a client will ask is "which AI coding tool should we buy?" The question that actually determines their outcome is "who verifies the agent's work, at which stage, with what check?" Tools change quarterly; the loop — plan, red/green, verify, review, gate — is the durable asset you leave behind. Deep dive: the numbers behind the loop

Optional. ~10 minutes. The two studies you'll quote at clients, plus the review cost math.

The METR RCT (arXiv 2507.09089). Design matters here, which is why this study bites harder than a survey: 16 experienced open-source maintainers, 246 real tasks in mature repositories they knew well, with AI tools (early-2025 vintage) randomly allowed or disallowed per task. Measured outcome: allowing AI increased completion time by 19%. Perceived outcome: the same developers believed AI had made them 20% faster — after forecasting 24%, while economists had predicted 39%. The lesson is not "AI slows everyone down"; it's that in exactly the setting FDEs work in — experts, mature codebases, real tasks — perception and measurement can point in opposite directions. Any client claim about agent productivity that isn't backed by a measured verification loop is a feeling, not a fact.

The review-latency tax (arXiv 2412.18531). An industrial deployment of an LLM review tool (built on Qodo PR Agent) across 4,335 pull requests. The good: 73.8% of automated comments were resolved — developers acted on most of what the reviewer said. The cost: average PR closure time rose from 5h52m to 8h20m, and practitioners reported faulty reviews, unnecessary corrections, and irrelevant comments alongside genuinely improved bug detection. The FDE takeaway: budget for tuning (nit caps, skip rules, severity redefinitions) as part of rollout, and re-measure closure time after tuning.

Worked example — what does AI review cost a team?
  • Claude Code Review (research preview): $15–25 per review, ~20 min, billed on tokens
  • Team shipping 40 PRs/week, review on open + every push ≈ 2 runs/PR → 80 reviews/week
  • 80 × ~$20 ≈ $1,600/week — before tuning
  • With REVIEW.md skip rules (docs-only PRs, generated files) and review-on-open only: 40 × $20 = $800/week
  • Free tier of the same discipline: local /code-review before push, managed review reserved for risky diffs

The point isn't the exact dollar figure — it's that AI review is a metered service with a tuning surface, and "run it on everything at defaults" is rarely the right configuration. Compare against Copilot code review's positioning: sub-30-second comment-tier feedback, enabled by ruleset. Different price points, same invariant — neither ever approves or blocks a merge.

Why comment-only is a design decision, not a limitation. Both vendors independently converged on AI-review-as-comment: Copilot always leaves a Comment review, never Approve or Request changes; Claude's findings "don't approve or block your PR." Approval is accountability, and accountability stays with a human. When a client asks you to wire AI review into required approvals, this is the design precedent you cite for saying no.
