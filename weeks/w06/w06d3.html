Alt Research: Cursor, Aider & Copilot vs Claude Code

Week 6 · Day 3 AI-Native Delivery ~18 min · reading @150 wpm + diagram + check

You've spent weeks getting good at one coding agent. Today you zoom out. A client will ask you "why Claude Code and not Cursor?" — or worse, "our team already uses Copilot, convince me" — and the answer "it's what we use" is not an answer. This is an alt-research day: you'll learn to read the coding-agent landscape the way an FDE reads any vendor landscape — classify by form factor, dissect the context strategy, map the review-and-permission model, and treat benchmark numbers as claims to verify, not facts to repeat. Scroll the reading; the panel on the right builds the landscape one tool at a time, then overlays the comparison axes that actually decide the question.

The frame

It's a form-factor spectrum, not a feature checklist

Start by throwing away the listicle comparison — the feature grid with green checkmarks. As of mid-2026, every serious tool in this space ships roughly the same checklist: an interactive agent that edits files and runs commands, an async cloud agent you can delegate tasks to, and MCP support for external tools. If you compare on feature names, everything ties. The grid tells you nothing.

What actually separates the four tools is form factor — where the agent lives, and therefore what workflow it pulls you into. Cursor is an AI-native IDE: a proprietary fork of VS Code with the agent built into the editor, now extending outward to cloud agents and even an iOS app. GitHub Copilot is a platform: an IDE extension, a terminal CLI, and a GitHub-hosted cloud agent, all riding on the repository host itself. Aider is a pure terminal pair-programmer — open source, bring your own API keys, no IDE at all. And Claude Code — our pick — is terminal-native first, with the same engine exposed in VS Code, JetBrains, a desktop app, the web, and CI.

Form factor drives more than preference. It decides who reviews the agent's work and when, how the agent learns your codebase, what it's allowed to touch, and where the audit trail lives. So the research method for today — and for any tool evaluation you run at a client — is four questions asked of every candidate: where does it live? how does it know the repo? who approves what? and what do its numbers actually measure? Hold those four questions; the rest of the day walks each tool through them.

Tool 1 · Cursor

Cursor: the IDE-native agent, sprinting toward the cloud

Cursor's core bet is that the agent should live inside the editor. Its Agent "can complete complex coding tasks independently, run terminal commands, and edit code," with tools for semantic search over an indexed codebase, file operations, web search, terminal, and even browser control. Two design details matter. First, it auto-creates checkpoints — snapshots of your codebase during an agent session — so you can roll back a bad run instead of untangling it. Second, you can queue follow-up messages while the agent is mid-run, which tells you the intended rhythm: you stay in the chair, steering continuously.

The 2026 release cadence shows the direction of travel, and it is away from the chair. Version 3.7 (June 17) added cloud subagents — /in-cloud spins up subagents in isolated VMs, with handoff between local and cloud sessions. Version 3.8 expanded Automations: always-on agents triggered by Slack emoji or GitHub events, with a computer-use tool. Version 3.9 (June 22) unified "plugins, skills, MCPs, subagents, rules, commands, and hooks" under one management surface at the user, team, or workspace level — and a week later (June 29) shipped a public-beta iOS app so you can "launch and manage always-on agents from anywhere."

Read that 3.9 list again slowly: skills, subagents, rules, hooks, MCP. It's near-isomorphic to the Claude Code extension vocabulary you've been using since week one. That's your first research finding of the day: the ecosystem is converging on the same extension grammar. Feature names have stopped being differentiators, which is exactly why the listicle comparison died.

Tool 2 · Aider

Aider: the terminal OG and the repo-map idea

Aider is the open-source original of the category: "pair program with LLMs" in your terminal, model-agnostic, bring your own API keys — cloud or local models. It's git-native by design, automatically committing changes with sensible commit messages, and the numbers say it mattered: roughly 44K GitHub stars and 6.8 million pip installs. But it earns a full section in 2026 for one idea the whole field had to answer: the repo map.

How does an agent "know" a codebase that's a thousand times bigger than any context window? Aider's answer is a static, pre-computed map: a graph-ranking algorithm runs over a graph where each source file is a node and edges connect files with dependencies, then selects "the most important identifiers, the ones which are most often referenced by other portions of the code" into a compact map — about 1k tokens by default, sized dynamically. The agent sees a skeleton of the whole repo — the load-bearing names — and asks for full files only when it needs them.

That's one of three repo-context strategies you should now be able to name on a whiteboard. Aider's graph-ranked map is static and cheap but can go stale between computations. Cursor's semantic embedding index is richer — meaning-based search over the whole codebase — but requires indexing infrastructure and re-indexing as code changes. Claude Code and Copilot CLI mostly take the third path: agentic on-demand search — grep, read, follow the imports, exactly like a human orienting in a strange repo — which is always fresh but spends tokens per task instead of up front. There is no free lunch — only a freshness-cost-scale triangle — and "how does it know the repo?" is now a question you can answer for any agent.

Aider's other gift

The architect/editor split — and an honest staleness warning

Aider's second lasting contribution is a workflow called architect mode. Instead of asking one model to reason about a change and produce the exact file edits, aider splits the job: it first sends your request to a reasoning "architect" model to propose a solution, then "sends another request to an 'editor model', asking it to turn the architect's proposal into specific file editing instructions." Thinking and editing are different skills, so use a different model for each — a strong reasoner to plan, a fast reliable formatter to produce clean diffs.

You've been living inside that pattern's descendants all program. The planner/executor structure of modern agents, Claude Code's subagent teams, Cursor's cloud subagents — all of them are elaborations of the same insight aider shipped as a two-model trick: separate the model that decides from the model that types. Recognizing ancestry like this is a research skill in itself; it stops you from believing each vendor invented the idea last quarter.

Now the honest part, because verify-first cuts both ways. Aider's last release is v0.86.0, dated August 2025 — roughly eleven months old as you read this. Its homepage still headlines Claude 3.7 Sonnet and o1-era models, and its famous leaderboard was last updated in November 2025. Aider remains a superb teaching artifact — repo map, git-first design, architect mode — but it is no longer tracking the frontier, and a comparison that presents it as a current peer of the other three is misleading. Notice how you learned that: not from a competitor's blog, but from the project's own release page. Staleness signals live in primary sources, and checking release dates before recommending a tool is the cheapest diligence you will ever do.

Tool 3 · Copilot

Copilot: from autocomplete brand to agent platform

If your mental model of GitHub Copilot is "the autocomplete thing from 2021," update it — it's now the most platform-shaped player on the board. The centerpiece is the Copilot cloud agent, which "works autonomously in a GitHub Actions-powered environment." You assign it a GitHub issue, @copilot it in a PR comment, or prompt it from Copilot Chat; it gets an ephemeral development environment where it can explore the code, make changes, and run tests and linters; then it presents its work as a draft pull request for a human to review — it never merges its own work. It's on all paid Copilot plans, and the guardrails are refreshingly concrete: 59-minute runs, one repo, one branch, one PR per task, GitHub-hosted repos only.

This is the cleanest example of async delegated agents, and it inverts the interaction model you're used to. With an interactive agent, you steer and review continuously. With a delegated agent, you hand over a well-specified task, walk away, and the only control surface is the review gate at the end — the draft PR. That makes two things critical: the quality of the task specification (a vague issue in means a vague PR out — week 5's spec discipline paying rent), and the integrity of the review gate, now the entire safety contract. The 59-minute cap and one-PR limits aren't weaknesses; they're the platform being explicit about the blast radius of an unattended agent — and an FDE should like vendors who state their limits in a docs page instead of letting you discover them in production.

The venue play

Copilot CLI, and GitHub hosting its rivals

Copilot's second front is the terminal. Copilot CLI is, structurally, a Claude Code-shaped product: conversational and autonomous modes, a plan mode, @ file references, image and PDF attachments, scheduled prompts (/every, /after), custom instructions and custom agents. Its permission posture is explicit: the agent "may attempt to read, modify, and execute files" only after you grant explicit folder trust, with one-time versus session-wide approvals per action. It ships pre-configured with GitHub's MCP server and extends via /mcp add. Meanwhile in VS Code, agent sessions do multi-file work, run multiple sessions in parallel, and a dedicated Agents window orchestrates tasks across projects.

Then comes the move that should make you sit up: GitHub now hosts competitors' agents as first-class citizens. From GitHub's Agents tab — and from issues, PR comments via @AGENT_NAME, and mobile — you can assign work to Anthropic Claude or OpenAI Codex, not just Copilot. Their output flows through the same plumbing: generated code is automatically scanned with CodeQL and secret scanning, and usage bills as Actions minutes plus AI credits.

Think about what that means strategically. GitHub is no longer betting that Copilot beats every agent; it's betting that whichever agent wins, the work lands on GitHub. The moat moved from the model to the venue — the place where code review, CI, security scanning, and billing already live. For client conversations this matters directly: "we use Claude Code" and "our repos and review gates live on GitHub" are no longer competing statements anymore. The platform layer and the agent layer are separating, and an FDE who can articulate that separation sounds five years ahead of one still arguing brand-versus-brand.

The axis that matters most

Review & permission models: how each tool says "not so fast"

Here's the comparison axis that matters most for client work, and the one vendor marketing talks about least: when a semi-autonomous agent is loose in a codebase, what stops it from doing damage, and who signs off on what? Each tool's answer reveals its theory of trust.

Cursor trusts you to supervise and makes recovery cheap: automatic checkpoints of the codebase during agent sessions, so any run can be rolled back. Copilot's cloud agent assumes no one is watching and gates the output: everything arrives as a draft PR, a human must approve, and it never auto-merges — the review gate is the product. Copilot CLI gates the input instead: explicit folder trust before the agent touches anything, then per-action approvals, one-time or session-wide. Claude Code gives you a programmable perimeter: a permission system for tools and paths, plus hooks that let a team encode its own hard rules — you've lived inside one all program, where hooks block .env reads and secret-shaped writes before the model ever sees them.

Notice the pattern: rollback, output gate, input gate, policy perimeter. Which one fits depends on the client — a fintech with change-control requirements wants the draft-PR gate's paper trail; a startup wants checkpoints and speed; a security-sensitive team wants hooks it can write itself. This axis, not the benchmark score, is usually what decides a real procurement conversation.

Reading the numbers

Benchmarks: what SWE-bench and the polyglot board actually measure

Sooner or later someone slides a leaderboard across the table, so learn to read the two names you'll see most. SWE-bench (Jimenez et al., Princeton) is the canonical academic anchor: 2,294 real GitHub issue/PR pairs drawn from 12 Python repositories, where the task is to "edit the codebase to address the issue." Real issues, real codebases — that's why it stuck. Keep this calibration fact: at publication, the best model of the day (Claude 2) resolved 1.96% of tasks. Today vendors quote "SWE-bench Verified" numbers vastly higher. Both facts are true; the gap is model progress plus scaffold progress plus a change of variant — which is exactly why a naked number is meaningless.

So the three questions you ask of any SWE-bench claim: which variant (full, Lite, or the human-validated Verified subset — not comparable to each other), what scaffold (the same model scores wildly differently in different agent harnesses), and what date (a number from last year describes last year). A vendor number missing any of the three is a marketing sentence, not a measurement.

The aider polyglot leaderboard measures something narrower: 225 hard Exercism exercises across C++, Go, Java, JavaScript, Python, and Rust, testing whether a model can follow instructions and produce correctly formatted edits inside one fixed harness, no human in the loop. That makes it a model benchmark, not an agent benchmark — useful for comparing raw models on edit discipline, useless for deciding between Cursor and Copilot. It also doubles as today's staleness exhibit: last updated November 2025, top entry gpt-5 at 88.0%. A board that has stopped updating doesn't say "these rankings hold"; it says "nobody is maintaining this" — a historical document.

Our pick · for the record

Why Claude Code — and what would change the answer

Now the question you'll be asked, answered properly. Claude Code is "an agentic coding tool that reads your codebase, edits files, runs commands, and integrates with your development tools" — one engine across terminal, VS Code, JetBrains, desktop, and web, with shared CLAUDE.md memory, settings, and MCP config across all of them. The distinctives you already use daily: CLAUDE.md plus auto memory, skills, hooks, subagent teams, a Unix-composable CLI (tail -200 app.log | claude -p ...), GitHub Actions and GitLab CI integration, and an Agent SDK for building custom agents on the same engine.

But be honest the way a researcher is honest: most of those historical differentiators now have counterparts. Cursor 3.9 ships skills, subagents, rules, and hooks; Copilot CLI is terminal-native with MCP and custom agents. So the durable case rests on the axes that don't converge overnight: model access (Anthropic-first and immediate, versus a router's menu), the composable-CLI and SDK posture (an agent you can pipe, script, and embed, not just sit in front of), and the maturity of the extension ecosystem your team has already built on — this program's own pipeline of skills and hooks being exhibit A. And the professional's coda: name what would flip the decision. If the frontier model you depend on moved elsewhere, if a client's estate made the GitHub-venue integration decisive, or if a rival's permission model fit a compliance regime yours couldn't — those are real reasons. "The leaderboard changed this month" is not.

FDE mindset

An FDE's tool recommendation is a research artifact, not an allegiance. You classified four tools by form factor, dissected three context strategies, mapped four permission models, and stress-tested two benchmarks — all from primary sources with dates on them. That method survives every product cycle; the conclusions are always dated the day you write them. Re-run the method, not the loyalty.

Deep dive: auditing a benchmark claim in 5 minutes

Optional. ~10 minutes. The checklist behind "check variant, scaffold, and date."

Step 1 — identify the instrument. SWE-bench is 2,294 real GitHub issue/PR pairs from 12 Python repositories; the task is to edit the codebase so the issue's held-out tests pass. The aider polyglot board is 225 hard Exercism exercises in 6 languages, testing edit-format compliance inside one fixed harness. The first measures something agent-shaped on real code; the second measures raw model edit discipline. A vendor quoting polyglot to sell an agent product is already off-instrument.

Step 2 — pin the variant. "SWE-bench" alone is ambiguous: full (all 2,294), Lite (a cheaper subset), and Verified (a human-validated subset) produce different numbers for the same system. Verified scores run higher than full-set scores by construction. Cross-variant comparisons are apples to oranges.

Worked calibration — why a naked number is meaningless

At SWE-bench's publication, the best model available — Claude 2 — resolved 1.96% of tasks. Today's vendor slides quote Verified numbers vastly higher. Between those two figures sit three confounds that all moved at once: the models improved, the scaffolds improved (the same model scores wildly differently in different agent harnesses), and the goalposts moved from full to Verified. Any one of the three can double a number. So the audit question is never "is 70% good?" — it's "70% of which set, inside which harness, measured when?"

Step 3 — date the claim. The polyglot leaderboard's own page shows a last-updated date of 2025-11-20, with gpt-5 (high) at 88.0% on top. That's not evidence the ranking still holds — it's evidence the board stopped being maintained. Same discipline applies to the tools themselves: aider's release page shows v0.86.0 (2025-08-09) as the latest, which is how you caught its staleness today. Dates are the cheapest verification you'll ever run, and they live in primary sources — release pages, changelogs, the leaderboard's own footer — never in the pitch deck.
