AI-Augmented Feature Delivery, End to End

Week 6 · Day 5 · ★ milestone Agentic Delivery ~18 min · reading @150 wpm + diagram + check

All week you've collected the pieces: coding agents, agentic SDLC loops, alternative tools, brownfield tactics. Today they become one delivery — a single feature carried from a self-contained spec through implementation, automated review, CI quality gates, and a human merge decision, with the result measured, not just declared done. The through-line: an agent's output only becomes delivery when it passes gates the agent cannot talk its way through. Scroll the reading; the panel on the right assembles the pipeline stage by stage, from SPEC.md to a merge that survives DORA's throughput-vs-stability question.

★ The milestone

Delivery ends at a PR, not at "code done"

Start with the shape of the whole exercise. Claude Code's canonical feature workflow has four phases: Explore (plan mode, read-only), Plan (a detailed implementation plan you can edit with Ctrl+G before proceeding), Implement (the agent "verifying against its plan"), and — the phase teams forget — Commit: "Ask Claude to commit with a descriptive message and create a PR." Notice what that makes the unit of delivery. Not a diff sitting in a working tree. Not a chat transcript where the agent says it's finished. A pull request — an artifact other systems and other humans can gate, review, and merge.

The entry point is equally specific, and it's the artifact you built in Week 5: for larger features, have the agent interview you until you have a complete SPEC.md, then "start a fresh session to execute it." The docs are precise about what makes a spec worth handing off — the most useful ones are "self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works." That last clause is the load-bearing one. A spec that ends with a verification step gives the whole pipeline something objective to aim at; a spec that ends with a vibe gives you a negotiation.

So today's milestone run is: self-contained spec → fresh-session Explore/Plan/Implement → evidence-bearing commit and PR → automated review → hard merge gates → human merge decision → measurement. Everything you've practiced this week slots into one of those stages. The rest of the reading walks the pipeline in order, and the diagram builds it beside you.

The stop signal

"Looks done" is not a gate — build one

Here's the problem that defines the whole exercise, straight from the best-practices docs: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available, and you become the verification loop." An agent has no native sense of shipped. It has a sense of plausible. If the only thing standing between plausible and merged is your attention, you haven't automated delivery — you've automated typing.

The docs name an escalation ladder for how hard the check gates the stop, and it's worth memorizing as a design menu. Lightest: in-prompt iteration — tell it to run the tests and keep going until they pass. Next: a /goal condition re-checked every turn. Then: a deterministic Stop hook that "blocks the turn from ending until it passes" — the agent literally cannot declare victory while the check fails. Heaviest: a fresh-context verification subagent that inspects the result without the reasoning that produced it. "Each step trades setup for attention." Pick the rung that matches the stakes; for a milestone delivery, you want the deterministic end of the ladder.

And when the run does stop, demand receipts. "Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned, or a screenshot of the result. Reviewing evidence is faster than re-running the verification yourself, and it works for sessions you weren't watching." The docs give this failure pattern a name — the trust-then-verify gap — and a rule blunt enough to put on the wall: "If you can't verify it, don't ship it."

Calibration

Feature work is where agents are weakest — plan for it

Before you trust the pipeline, calibrate your expectations with data, because the gap between what benchmarks advertise and what feature delivery demands is enormous. FeatureBench (ICLR 2026) benchmarks "end-to-end, feature-oriented software development" — the real thing, spanning "multiple commits and PRs scattered across the development timeline" — across 200 tasks, 3,825 executable environments, and 24 open-source repos, with execution-based evaluation. The headline result: "Claude 4.5 Opus, which achieves a 74.4% resolved rate on SWE-bench, succeeds on only 11.0% of tasks."

Sit with that ratio. The same model that resolves three out of four scoped bug-fixes completes roughly one in nine end-to-end features. Bug-fix benchmarks wildly overstate feature-delivery capability, because a feature isn't a localized patch — it's a spec interpreted, decomposed, implemented across files and commits, and verified as a whole. Which is exactly the work you're doing today.

This is not an argument against the milestone; it's the argument for the gates. If agents shipped features reliably, today would be a demo. Because they don't, today is an engineering exercise: the deliverable isn't the feature, it's the delivery system — the stack of checks that catches the eight failures out of nine before a client ever sees them. When a client asks "can the agent just build features for us?", this number is your honest, useful answer: yes, inside a pipeline designed for an 11% first-pass world.

The hard gate

Branch protection: where output meets non-negotiable pass/fail

Now the wall the pull request must climb. GitHub's merge gate is refreshingly deterministic: required status checks must come back successful, skipped or neutral "before collaborators can make changes to a protected branch." Add required reviews and "collaborators can only push changes to a protected branch via a pull request that is approved by the required number of reviewers." Checks can be strict, meaning the branch must be up to date with the base before merging, or loose. That is the whole mechanism — and it is exactly the mechanism you want, because it is immune to persuasion.

This layer matters more with agents than it ever did with humans. An agent can write a confident PR description, summarize its own diff flatteringly, and assert that tests pass. Branch protection doesn't read prose. Tests, lint, and build become gates the agent must satisfy, not suggestions — the merge button stays grey until every required check reports green, no matter how "done" the work looks.

The FDE framing: this is where you convert this week's soft practices into hard policy. The verification step your spec ends with? Make it a required status check. The style rules in CLAUDE.md? Lint gate. On an engagement, configuring the client's protected branch is often the single highest-leverage hour of AI-delivery work you'll do, because it makes every future agent run — yours, theirs, attended or not — answer to the same non-negotiable bar.

Agents in CI

Agents can run inside the gate, too

The pipeline is not just something agents pass through — agents can be stages of it. Claude Code's headless mode, invoked with claude -p, is the non-interactive interface built for "CI pipelines, pre-commit hooks, or any automated workflow." The flags are the interesting part, because each one answers a question an unattended run raises:

  • JSON output format — returns structured results, including the total cost in dollars, so every CI invocation is billed and visible.
  • An output schema — constrains the shape of that result so downstream steps can parse it.
  • An allowed-tools list, plus permission rules — scopes exactly what an unattended agent may touch. Least privilege, for a process that writes code.

One flag deserves special attention for CI: --bare skips auto-discovery of hooks, skills, and MCP servers — "for CI and scripts where you need the same result on every machine." The docs note it's recommended for scripted and SDK calls and "will become the default for -p in a future release." Reproducibility is the whole point of a pipeline stage; an agent that behaves differently depending on which engineer's dotfiles happen to be on the runner isn't a stage, it's a liability.

The documentation's own example shows the pattern at its smallest: pipe a diff against the main branch into claude -p as a project-specific typo linter, wired in as an npm script. Diff in, structured verdict out, exit code gates the pipeline. Once you see that shape, you can put a scoped agent anywhere a deterministic check would go — with the agent held to the same standard: parseable output, bounded permissions, and the same result on every machine.

Review as a stage

Automated review is a pipeline stage, not a favor

Next stage: review the diff before a human spends attention on it. Claude Code's Code Review feature (research preview, Team/Enterprise) runs "a fleet of specialized agents" over the diff in the context of the full codebase, hunting "logic errors, security vulnerabilities, broken edge cases, and subtle regressions." Crucially, it doesn't just generate suspicions — "a verification step checks candidates against actual code behavior to filter out false positives" before anything is posted. What lands on the PR is deduplicated, severity-ranked inline comments: 🔴 Important ("a bug that should be fixed before merging"), 🟡 Nit, 🟣 Pre-existing. Default scope "focuses on correctness: bugs that would break production, not formatting preferences." It triggers on PR open, on every push, or manually via @claude review — and it runs about 20 minutes and $15–25 per review, so it's a real stage with a real budget line.

And it is a configuration surface, not a prayer. A review policy file at the repository root is "injected directly into every agent in the review pipeline as highest priority." Teams use it to redefine what Important means for their codebase, cap noise by asking for at most five nits, skip generated code and lock files, add repo-specific always-checks such as requiring an integration test for every new API route, set an evidence bar so behaviour claims need a file-and-line citation, and control re-review convergence by suppressing new nits after the first pass. Even the project instruction file is enforced in both directions: code that violates it surfaces as a nit, and so does code that leaves the docs stale.

Prefer to self-host the stage? Anthropic's GitHub Action runs the full Claude Code runtime on GitHub runners, in either mention mode — where someone writes @claude in a comment — or automation mode with a standing prompt on pull-request events, which it auto-detects. It respects your project instruction file, supports skills and plugins inside the prompt, and passes through any command-line flag, so turn limits, allowed tools and model choice all remain yours. Setup is a single install command, and enterprises authenticate through Bedrock or Vertex with OIDC, so there are no static keys. The security guidance is worth quoting because it is the theme of the day: secrets stay in GitHub Secrets, permissions stay minimal, and "review Claude's suggestions before merging."

One caveat travels with any adversarial review, managed or the fresh-context subagent flavor from the best-practices docs (a reviewer that "sees only the diff and the criteria you give it, not the reasoning that produced the change"): "A reviewer prompted to find gaps will usually report some, even when the work is sound." Chase only correctness-affecting findings, or the review stage becomes an over-engineering machine.

Wiring review into the gate

Blocking on AI findings is a decision you build

Here is a subtlety that separates people who read the docs from people who assume. The Code Review check run "always completes with a neutral conclusion so it never blocks merging through branch protection rules." By default the AI reviewer advises; it does not gate. That is a deliberate vendor choice, and the escape hatch is explicit: "If you want to gate merges on Code Review findings, read the severity breakdown from the check run output in your own CI." The check's details text ends with a machine-readable comment carrying a severity breakdown — counts of normal findings, nits and pre-existing issues — where a non-zero normal count means at least one bug worth fixing before merge. Parse it in your own pipeline, fail your own required check on it, and now branch protection enforces the AI's findings deterministically.

Note also what the service does not promise: review runs are "best-effort. A failed run never blocks your PR." Read that as a design assignment — the resilience of the merge gate is your CI's job, not the review service's. If AI review is load-bearing for you, your required check must decide what a missing review means (fail closed? re-trigger?) rather than silently merging past it.

This is the pattern to generalize on client engagements: vendors ship AI signals as advice and leave enforcement to you, because how hard to gate is a team-culture decision with real throughput costs. Making that decision explicitly — which severities block, what happens when the reviewer is down, who can override — is FDE work. Leaving it implicit is how teams end up believing they have a gate they don't have.

The human merge

The agent PR meets its reviewer — and that's normal

The last gate is a person, and the empirical picture of what happens there is more interesting than the folklore. A 2026 study of 9,799 human-reviewed agentic PRs (717 manually inspected) found that "only 35.7% of rejected PRs reflected clear agentic failures" — while 31.2% of rejections stemmed from workflow constraints, not bad code. Wrong branch, duplicate effort, project didn't want the change: rejection reasons that have nothing to do with whether the agent can program. Flip side: among merged PRs, "15.4% required explicit reviewer involvement through feedback or direct commits." Roughly one in six shipped agent PRs shipped because a human pushed it over the line.

The study also found the agents differ by how they're embedded: "Copilot and Devin more often embedded in reviewer-mediated workflows, while Codex and Cursor PRs were typically merged with minimal interaction." Same artifact — a PR — but different delivery systems around it. Which is the teaching point: the human reviewer is part of the delivery system, not a bug in it, and raw merge-rate is a bad solo metric. The paper's own conclusion is that evaluation should be "interaction-aware … grounded in review behavior" — measure the collaboration, not just the outcome bit.

Mechanics of that collaboration, for your milestone PR: when the AI reviewer posts a finding, replying does nothing — "To act on a finding, fix the code and push." Push-triggered re-reviews auto-resolve threads when the issue is actually fixed, and 👍/👎 reactions feed reviewer tuning. The loop is code-shaped, not conversation-shaped: findings are resolved by commits, approval is earned by green checks, and the human's merge click is a judgment call informed by evidence — exactly what you set up in step one.

Measure it

Throughput without stability isn't delivery

You merged. Are you done? DORA says: not until you've measured what the speed cost you. The State of AI-assisted Software Development 2025 report's core finding is that "AI's primary role is as an amplifier, magnifying an organization's existing strengths and weaknesses" — and that "the greatest returns on AI investment come … from a strategic focus on the underlying organizational system," not the tools. The tension it documents is the one your milestone must answer for, verbatim: "higher AI adoption is associated with an increase in both software delivery throughput and software delivery instability." Faster and shakier, together, by default. (The context: 90% of tech professionals now use AI at work — while 30% of developers report little to no trust in the code it generates. Both numbers are rational.)

DORA names the control systems that decouple the two, and you should recognize every one of them as a stage you just built: robust test automation ("potentially more valuable than optimizing manual code reviews") — your required checks. Small-batch discipline — "force large AI-generated changes into reviewable, testable units," which is what a self-contained spec with a bounded scope does. AI feedback moved to the authoring phase rather than piling up at review — the stop-gate and in-loop verification from step one. And context-aware review agents enforcing org standards — your REVIEW.md. Measure with holistic frameworks, DORA insists, not lines of code or PR counts.

So the milestone debrief is three questions, asked honestly. Did the throughput come with instability — what would have broken if the gates hadn't caught it? Which control system did the catching — tests, batch size, authoring-phase feedback — and which was missing? And what does the run say about the system, not the agent — because the agent is an amplifier, and what it amplified today was the pipeline you built around it. That reframe, from "how good is the agent" to "how good is the delivery system the agent runs inside," is the week's graduation criterion.

FDE mindset

Clients will ask you to make the agent ship features. The FDE move is to hear the real request: make delivery trustworthy at agent speed. You do that with gates that can't be persuaded — required checks, severity-wired review, evidence at the stop — and you prove it with delivery metrics, not demos. FeatureBench's 11% is why the gates exist; DORA's amplifier is why they're worth more than the model choice. If you can't verify it, don't ship it.

Deep dive: building the severity gate & costing the review stage

Optional. ~10 minutes. The plumbing behind "blocking is a decision you build."

The signal. Every Claude Code Review check run finishes neutral — it can never block a merge on its own. But its Details text ends with a machine-readable comment: bughunter-severity: {"normal": 2, "nit": 1, "pre_existing": 0}. A non-zero normal means at least one bug the reviewer judged worth fixing before merge.

The gate. In your own CI, fetch the check run with the GitHub CLI, extract the JSON tail with jq, and exit non-zero when the normal-severity count is above zero. Mark that job as a required status check in branch protection. Now the deterministic GitHub gate — which only cares about successful, skipped or neutral — enforces the AI's findings on your policy: maybe normal findings block, nits warn, and a missing review run fails closed. Remember that review runs are best-effort and "a failed run never blocks your PR," so deciding what absence means is your job.

Worked cost check — does the review stage pay for itself?

A managed review averages ~20 minutes and $15–25 per review. Say your team ships 15 agent-authored PRs a week: ≈ $225–375/week, ≈ $1,200–1,600/month. Against that: one 🔴 Important finding is "a bug that should be fixed before merging" — a production incident pre-empted. If the stage catches even one real incident a month, it's cheap; if it's drowning you in nits, that's a REVIEW.md tuning problem ("report at most five nits", "Important findings only on re-review"), not a reason to drop the stage. Budget it like a stage, tune it like a stage.

Reproducibility footnote. Any agent you put inside the gate should run in bare mode, which skips auto-discovery of hooks, skills and external tool servers so the check behaves identically on every runner — the docs flag it as the future default for headless runs. A gate that depends on whatever configuration happens to be lying around is not a gate.
