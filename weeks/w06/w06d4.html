Brownfield: Modernizing Legacy Systems with Agents

Week 6 · Day 4 Agentic Engineering in the Real World ~18 min · reading @150 wpm + diagram + check

Almost no client hands you a green field. They hand you a fifteen-year-old system that runs the business, that nobody fully understands, and that they're terrified to touch. Today is the FDE playbook for that system: use agents to read the legacy code before anyone writes a line, pin down its actual behavior with characterization tests, replace it incrementally behind a strangler-fig façade instead of a big-bang rewrite, and treat agent-driven translation as fast-but-unproven until validation says otherwise. Scroll the reading; the panel on the right strangles one legacy monolith, piece by piece, the way you will at a client.

The flip

The bottleneck is comprehension, not code

Here is the scene you will actually walk into. A system that has been in production for a decade or more. The original authors are gone. The documentation, if it exists, describes a version of the system that stopped being true years ago. And every feature request now takes months, because nobody is confident about what any change will break. That's brownfield — and it's where most of the world's software value actually lives.

The instinct everyone brings to agents here is wrong. People assume the win is generation: "the AI will rewrite our old code fast." But the Thoughtworks team that built the CodeConcise modernization accelerator put their finger on the real bottleneck: developers spend far more time reading code than writing it, so GenAI's biggest modernization value is understanding existing systems — reverse-engineering what the legacy code actually does, so the humans and agents downstream aren't working blind.

Their approach makes the point concrete. CodeConcise parses the legacy codebase into an AST-derived knowledge graph, and lets LLM traversal over that graph "reduce noise (i.e. unnecessary code) from the context provided to LLMs" — the same window discipline you learned in Week 1, applied to a million lines of someone else's COBOL. The measured result on one client engagement: reverse-engineering a mainframe module dropped from six weeks to two, projected at roughly 240 FTE-years saved across the client's whole modernization program. That's the shape of the prize — and notice it was won by reading, not writing.

One caveat from the same team, worth keeping honest: not everything in legacy work is an LLM job. Dead-code detection, for instance, stays with classical static analysis — in their words, "GenAI offers minimal value here." The FDE skill is knowing which tool owns which part of the problem.

Agents that read

Broad → narrow: the comprehension workflow

You already own the tool for this. Claude Code's official brownfield recipe is a broad-to-narrow funnel: start with "give me an overview of this codebase," then tighten — "how is authentication handled?" — then tighten again — "trace the login process from front-end to database." Each question spends context on a smaller, deeper slice, and by the third pass you have an execution-flow map that would have taken a new hire weeks to build by hand. The docs also recommend targeted sweeps like "find deprecated API usage in our codebase" to build a refactor hit-list before anyone commits to a plan.

Two details in that recipe are load-bearing. First, delegate exploration to subagents ("use a subagent to investigate…") so the hundreds of file-reads an investigation burns don't pollute your main context — the orchestrator keeps the map, the subagents do the walking. Second, when you graduate from reading to refactoring, the docs' rule is that changes should "maintain the same behavior" and land "in small, testable increments." Hold that phrase; the entire rest of today is about making it enforceable.

And keep a human in the loop on the outputs. When MITRE and collaborators evaluated LLM-generated line-by-line documentation for genuinely dead languages — MUMPS in an EHR system and IBM mainframe Assembly (ALC) — the generated comments were largely accurate and useful, but they found that no automated metric strongly correlates with comment quality. There is no scorer you can point at machine-written legacy docs and trust; a person who knows the domain has to review them. Agents make legacy comprehension cheap. They do not make it self-certifying.

Pin it down

Characterization tests: the code is its own spec

Before any agent — or any human — changes a line of untested legacy code, you pin down what it actually does. The tool is the characterization test, and the definition comes from Michael Feathers, who coined the term in Working Effectively with Legacy Code: its purpose is "to document your system's actual behavior, not check for the behavior you wish your system had." Once code is in production, Feathers argues, "it becomes its own specification. We need to know when we are changing existing behavior regardless of whether we think it's right or not." Even the bugs are load-bearing: some downstream process probably depends on them.

The mechanics are almost embarrassingly simple. Write a test that calls the legacy function with a real input and asserts a dummy expectation — null, say. Run it. It fails, and the failure message tells you what the code actually returned. Record that actual value as the assertion, rename the test to describe what you just learned, and repeat across the input space. You aren't judging the behavior; you're photographing it. The genuinely hard part, Feathers notes, isn't writing the assertions — it's breaking dependencies enough to get the legacy code into a test harness at all.

Now the agent angle, and it's the single highest-leverage pre-agent step in brownfield work. Generating characterization tests is mechanical — call, observe, record, repeat — which is exactly the kind of work agents are good at, so you can build hundreds of pins cheaply. And the resulting suite is your tripwire: when an agent later refactors or translates that code and quietly changes behavior, a pinned test goes red. Write this on the whiteboard at the client: the legacy system is the oracle; the agent must never be. The running production code is the only authority on what "correct" means, and characterization tests are how you make that authority executable.

The pattern

Strangler fig: replace it while it runs

So you understand the system and you've pinned its behavior. How do you actually replace it? Not with a big-bang rewrite — the multi-year project that freezes the old system, rebuilds everything in parallel, and cuts over in one terrifying weekend. The alternative has a name and a quarter-century pedigree: the strangler fig, named by Martin Fowler in 2001 after the vine that grows around a host tree until it can stand on its own — and substantially rewritten as a pattern in his 2024 bliki revision.

Fowler's current framing is four activities, and none of them is "rewrite." First, understand the outcomes you want — modernization serves a goal, not nostalgia for new frameworks. Second, identify the parts that can be independently replaced — seams where a piece of the system can come out without dragging the whole organism with it. Third, deliver replacements in manageable pieces: new work lands as "small additions, often new features, that are built on top of, yet separate to the legacy code base," so each increment carries small risk and ships real value early. Fourth — the one engineers forget — drive the organizational change needed to sustain the effort, because a strangler migration is a way of working, not a sprint.

The economics are the argument you'll make to the client. Replacing small components one at a time means no risk-everything cutover, and the early value from the first new components is what justifies the temporary scaffolding — what Fowler calls transitional architecture, code that exists only so the old and new systems can coexist and that is deliberately built to be thrown away. A big-bang rewrite delivers nothing until it delivers everything; a strangler delivers something every increment, and every increment tightens your characterization-test tripwire around what remains.

In operation

The façade: routing is the migration

The Azure Architecture Center's write-up of the pattern gives you its operational shape, and it's beautifully mechanical. You put a façade — a proxy — in front of the legacy system, so that every incoming request passes through it. At the start, the façade routes everything to the legacy system and users notice nothing. Then, as each new service comes online, the façade starts routing that slice of requests to the new implementation instead. Migration progress becomes a routing table: 0% new, then 10%, then 60%, until the legacy system is receiving no traffic at all — at which point it can be decommissioned and, last of all, the façade itself removed. The vine has consumed the tree.

Notice what this buys the agent-assisted version of the work. Each routing shift is a small, testable increment — exactly the granularity your characterization suite can verify. Route one endpoint to the new service, run the pins, compare. If the new implementation drifts from the oracle, route back. The façade turns "rewrite the system" into a long series of reversible experiments.

The pattern has sharp edges, and Azure's considerations list is your pre-flight check. The façade sits in every request path, so you must keep it from becoming a single point of failure or a performance bottleneck — it inherits the availability requirements of everything behind it. You should structure the new services so that they can themselves be strangled one day; today's replacement is tomorrow's legacy. And the pattern simply doesn't fit everywhere: if requests to the back-end system can't be intercepted, or you can't modify the legacy source at all, there is no seam for the façade to occupy, and you need a different strategy.

Coexistence

The anti-corruption layer: don't import the disease

During the long middle of a strangler migration, old and new must talk to each other — the new order service still needs customer data that lives in the monolith, and the monolith still needs results the new service now owns. The naive move is to let the new system call the legacy system directly, speaking its dialect. Do that and you've imported the disease: legacy data shapes, legacy naming, legacy assumptions leak into the new codebase, and at the end of the migration you discover you've rebuilt the old system with newer syntax.

The guard is the anti-corruption layer (ACL), which the Azure strangler-fig doc cross-references as the companion pattern for exactly this moment: "an adapter that translates requests between the two systems… protects the new system's design from legacy semantics." All cross-system dependencies route through it. The new side speaks its clean domain model; the ACL translates to and from whatever the legacy side requires. Without it, in the doc's words, "cross-system dependencies can break components or force the new system to adopt legacy conventions" — the corruption the layer is named for.

Together, the façade and the ACL are the transitional architecture Fowler described: pure scaffolding, with a planned demolition date. That's a strange thing to build deliberately — engineers hate writing throwaway code — so say the quiet part to your client out loud: this code's job is to be deleted. Its value isn't longevity; it's that it lets the old and new systems coexist safely while value ships every increment. Budget for building it and for removing it, because a "temporary" adapter with no demolition date is just the next generation's legacy.

State

Data strangles last: ETL, CDC, and the rollback window

Everything so far moved behavior. The scariest part of any modernization is moving state — the database where the business actually lives. The Azure doc's database-decomposition example is the template, and it strangles data with the same incremental discipline as code, in three phases.

Phase one: the new domain service goes live, but it keeps reading and writing the monolith's database. Behavior has moved; data hasn't. This feels unsatisfying and is exactly right — you've isolated the risky move instead of making two risky moves at once. Phase two: stand up the isolated domain database and start filling it — an ETL job loads the history, and change-data-capture (CDC) keeps it synchronized with ongoing writes to the monolith. Critically, you now "validate consistency between both databases before cutover": the two stores run side by side, and you measure whether they agree, with real production data flowing. Phase three: cut the service over to its own database as system of record — and only then, as a separate and deliberate act, remove the domain's tables from the monolith.

The design property to sell to the client is the rollback window. Through phase two and into early phase three, going back is cheap: the monolith database is still there, still complete, still synchronized. Deleting the legacy objects is, in the doc's words, "a deliberate final step… only after the new system is validated" — because that deletion is the one move in the whole migration that closes the escape hatch. An FDE never lets that step happen implicitly, on a schedule, or because a script got ahead of the checklist. Validation gates open doors; only a human decision should close one behind you.

Agentic pipelines

Assess → plan → transform → validate: validation is the product

Now put the agents back in, at full scale. Repository-level agentic modernization is real and shipping — and the honest numbers tell you where the value actually sits. AlphaTrans, published at FSE 2025, is a neuro-symbolic system that translates whole repositories compositionally — source and test code — then validates syntax, runtime behavior via translated test execution, and functional correctness via assertions. Across ten projects (836 classes, 8,575 methods, 2,719 tests), it translated 17,874 code fragments with 96.4% syntactic correctness. Impressive — until you read the next line: only around 25–27% passed runtime and functional validation, and developers still needed roughly 20 hours per project to get the translated tests fully passing. Ninety-six percent compiles; a quarter behaves the same. That gap between "compiles" and "behaves" is the entire lesson of today compressed into two numbers — and it's precisely the gap characterization tests exist to measure.

The productized version of the same loop is GitHub Copilot app modernization, generally available for Java and .NET since September 2025. Its four-phase agent workflow is a strangler-era pipeline in miniature: assess (analyze code, configuration, dependencies), plan (a customizable modernization path, saved as plan.md and tasks), upgrade (code changes, build files, deprecated-API refactors), and validate (build patching, test validation after each step, CVE checks, generated reports). And the human-in-the-loop isn't a disclaimer, it's the design: the docs say plainly that "you may frequently be prompted by Copilot cloud agent for confirmation before it performs specific actions," and direct teams to review architectural fit and testing gaps before anything deploys.

Read both systems the same way: transformation is fast and cheap now; validation is the product. The agent will happily translate a million lines over a weekend. What the client is paying an FDE for is the harness around that speed — the characterization suite that defines "same behavior," the façade that makes each change reversible, the consistency checks that gate the data cutover, and the human review at every confirmation prompt. Speed was never the constraint on legacy modernization. Confidence was. Agents fix the first; today's patterns are how you manufacture the second.

FDE mindset

At a brownfield client, the naive pitch is "AI will rewrite your legacy system fast." The FDE pitch is different: agents to understand it, tests to pin it, a façade to replace it one reversible slice at a time, and validation gates before anything irreversible. The running system is the oracle — the agent never is. Tomorrow you put the whole week together and deliver a feature end-to-end.
