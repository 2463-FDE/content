Coding Agents: the Landscape, and Claude Code Up Close

Week 6 · Day 1 Agentic Engineering ~18 min · reading @150 wpm + diagram + check

You've driven Claude Code since Week 1. This week you stop being a passenger. Today's job is two-fold: first, map the terminal-native coding-agent landscape — Claude Code, Codex CLI, and Gemini CLI have converged on one recognizable shape, and knowing that shape lets you walk into any client stack — then go deep on Claude Code's control surfaces: permissions, CLAUDE.md memory, skills, and hooks. The single idea holding it all together is the difference between what the harness enforces and what the model is merely told. Scroll the reading; the panel on the right assembles the landscape, then splits Claude Code's controls into their two very different halves.

The landscape

Three vendors, one converged shape

The terminal-native coding agent has settled into a category with three vendor flagships: Claude Code (Anthropic), Codex CLI (OpenAI), and Gemini CLI (Google). All three are the same species of tool: an agent that lives in your terminal, reads your codebase, edits files, and runs commands — Anthropic's own one-line description of Claude Code, and it applies to all three almost word for word. Codex CLI is open source, written in Rust, installed with a one-line curl script, and bundled into ChatGPT paid plans. Gemini CLI is Apache-2.0, installed via npm install -g @google/gemini-cli, ships a free OAuth tier (60 requests/minute, 1,000/day), and pairs a 1M-token context window with Gemini 3 models.

What matters more than the roster is the convergence. All three tools have independently arrived at the same core mechanics: a project instruction file the agent reads on startup (CLAUDE.md, AGENTS.md, GEMINI.md), approval or sandbox modes that gate what the agent may run — Codex tells you to "choose the approval mode that matches your comfort level before Codex edits or runs commands" — and MCP support for wiring in external tools. Even extensibility has standardized: the Agent Skills format, originated by Anthropic, is now an open standard at agentskills.io adopted by Codex, Gemini CLI, Cursor, GitHub Copilot, Goose, OpenCode, and dozens more.

Why does an FDE care about the shape rather than the horse race? Because clients will already have a tool when you arrive, and benchmark standings churn too fast to memorize. Terminal-Bench is the reference benchmark for terminal agents — versions 2.0 and 2.1 are live, 3.0 announced — and the professional move is to know where to look up current standings, not to recite stale scores. The durable knowledge is the converged shape: if you can locate the memory file, the approval system, and the extension mechanism in one of these tools, you can find them in all of them.

Claude Code

One engine, five surfaces

Claude Code is our primary tool for the rest of the program, so let's pin down what it actually is. The native install is one line — curl -fsSL https://claude.ai/install.sh | bash — after which claude in any project directory starts a session (the native installer keeps itself up to date). But "the terminal app" undersells it: Claude Code runs across five surfaces — the terminal CLI, a VS Code/Cursor extension, a JetBrains plugin, a desktop app, and the web at claude.ai/code.

The load-bearing fact is that all surfaces share the same engine. Your CLAUDE.md files, your settings, your MCP servers — configure them once and they work identically whether you're in a terminal over SSH, inside VS Code, or in a browser tab. For an FDE this is a deployment gift: you can standardize a client team's agent configuration in the repo itself, and it doesn't matter that half the team lives in JetBrains and the other half in a terminal. The configuration is the product you hand over; the surface is personal preference.

This also reframes what "learning Claude Code" means this week. You are not learning a UI. You are learning a configurable agent harness — a system with documented places to put instructions, documented rules for what it may execute, and documented extension points. Every one of those is a file you can check into a client's repository and review in a pull request. That's the difference between "we tried an AI tool" and "we deployed an agent with controls" — and the rest of today walks those controls one by one.

Surfaces · headless

The CLI is Unix-composable — and CI-ready

The surface that separates engineers from tourists is headless mode. claude -p "<prompt>" runs a single non-interactive turn and prints the result — which means Claude Code composes like any Unix tool. It accepts piped stdin: tail -200 app.log | claude -p "what broke?" sends the last 200 log lines in as context. It chains in shell scripts and CI pipelines. The agent stops being an app you sit inside and becomes a command you can wire into anything that can spawn a process.

CI needs auth without a browser, and there's a documented path: claude setup-token mints a one-year OAuth token that you provide via the CLAUDE_CODE_OAUTH_TOKEN environment variable. And once environment variables enter the picture, you need the credential precedence order, because it's a documented failure mode: cloud-provider flags (Bedrock/Vertex/Foundry) beat ANTHROPIC_AUTH_TOKEN, which beats ANTHROPIC_API_KEY, which beats the apiKeyHelper script, which beats CLAUDE_CODE_OAUTH_TOKEN, which beats the subscription login from /login. The classic gotcha: a stray ANTHROPIC_API_KEY exported in someone's shell profile silently overrides their subscription — they burn metered API credits while their paid plan sits unused. Diagnostic: run /status and read which credential won.

Interactive — future goal

Planned: a sandboxed terminal that runs claude -p against a tiny demo repo — pipe a log file in, watch a headless answer come back, then chain two calls in a script. Needs backend standup.

File this under FDE instincts: when a client says "can the agent review every PR automatically?" or "can it triage overnight alerts?", the answer starts with -p, a token, and a pipeline — not with a person sitting in a chat window.

Permissions · evaluation

Deny → ask → allow, first match wins

Now the controls. Before Claude Code touches a file or runs a command, the permission system decides whether to proceed, prompt you, or refuse. The evaluation order is fixed and worth memorizing: deny rules first, then ask rules, then allow rules — and the first match determines the outcome. Crucially, specificity does not change the order. If you write a broad deny like Bash(aws *) and a narrower allow like Bash(aws s3 ls), the deny matches first and the command is blocked. Deny rules cannot carry allowlist exceptions — this is not firewall-style "most-specific-rule-wins," and engineers who assume it is will ship rules that don't do what they think.

Rules live in settings files, and those have their own precedence: managed settings (deployed by IT, highest) beat CLI arguments, which beat .claude/settings.local.json (personal, gitignored), which beats .claude/settings.json (project — shareable, checked in), which beats ~/.claude/settings.json (user-wide). And one property makes the whole scheme trustworthy for security reviews: a deny at any level cannot be re-allowed at another. If the enterprise managed policy denies something, no project file, local file, or CLI flag can resurrect it.

Interactive — future goal

Planned: a permission-rule evaluator — paste a deny/ask/allow ruleset plus a candidate command, and step through which rule matches first and why the broad deny beats the narrow allow. Needs backend standup.

For an FDE, .claude/settings.json is the artifact that turns a security conversation from vibes into a reviewable diff: the client's platform team can read exactly what the agent may and may not do, approve it in a PR, and know a laptop-level tweak can't loosen it.

Permissions · syntax & modes

Rule syntax, honest limits, and permission modes

A rule is Tool or Tool(specifier). Bash rules use * globs and are shell-operator aware — a compound command like a && b must match your rules for each subcommand independently, so nothing sneaks through by riding after an &&. Read and Edit rules use gitignore-style paths with anchors: // for absolute paths, ~/ for home, / for project root. WebFetch rules match on domain:.

The docs are refreshingly honest about where patterns break down: argument-constraining Bash patterns are fragile. A rule trying to restrict curl to certain URLs can be bypassed with flag reordering, redirects, or shell variables. The documented recommendation is to not build load-bearing security out of Bash argument patterns at all — use deny rules on the command family plus WebFetch domain allows, or a PreToolUse hook (coming up in step 7) that inspects the real call. Knowing the limits of your own controls is exactly the kind of thing a client security team will probe you on.

Above individual rules sit permission modes, set via defaultMode: default (prompt on first use of each tool), acceptEdits (auto-accept file edits), plan (read-only analysis, no changes), auto (a research preview with background safety checks), dontAsk, and bypassPermissions. That last one skips prompts entirely — except explicit ask rules and a hard-coded circuit breaker on rm -rf / and rm -rf ~ — and the docs say plainly it's safe only in isolated containers or VMs with no credentials worth stealing. The FDE translation: bypassPermissions on a developer laptop with production AWS keys is malpractice; the same mode inside a throwaway CI container is a reasonable engineering choice. Context decides.

Memory

CLAUDE.md: layered context, plus a memory that writes itself

CLAUDE.md is the instruction file Claude Code reads at session start — project conventions, commands, architecture notes. It's layered, loading broadest to most specific: a managed policy file (e.g. /Library/Application Support/ClaudeCode/CLAUDE.md on macOS), your user file (~/.claude/CLAUDE.md, all projects), the project file (./CLAUDE.md or ./.claude/CLAUDE.md, checked in), and a local overlay (./CLAUDE.local.md, gitignored, personal). Discovery walks up the directory tree — so launching from a subdirectory still finds the repo-root file — and CLAUDE.md files in subdirectories load on demand when Claude reads files there. In a monorepo, api/CLAUDE.md costs nothing until the agent actually works in api/.

Files compose via imports: an @path/to/file line pulls another file in (max depth four hops, loaded at launch; the first import from outside the project prompts for approval). That's also the documented interop answer for the landscape from step 1: Claude Code reads CLAUDE.md, not AGENTS.md — so a repo serving multiple agents keeps one AGENTS.md and a CLAUDE.md containing @AGENTS.md, or a symlink. Guidance: keep each file under ~200 lines, because imported files still cost context on every session. For instructions only relevant to part of the tree, path-scoped rules (.claude/rules/*.md with paths: frontmatter) load only when Claude touches matching files.

Then there's the second memory system: auto memory (v2.1.59+, on by default). Claude writes its own notes to ~/.claude/projects/<project>/memory/ — a MEMORY.md index whose first 200 lines / 25KB load every session, with topic files loaded on demand. It's all plain markdown, and /memory opens it for audit. Notice the design echo from Week 1: both systems are answers to "how do we spend the window on standing knowledge?" — always-loaded index, on-demand detail.

Extension · skills

Skills: procedures that load only when needed

A skill is a folder containing a SKILL.md — YAML frontmatter with at minimum a name and description, then markdown instructions. Skills live at four scopes: personal (~/.claude/skills/<name>/), project (.claude/skills/<name>/), plugin, and enterprise. The directory name becomes a slash command — .claude/skills/deploy/ gives you /deploy — and Claude will also auto-invoke a skill when its description matches the task at hand. (The old .claude/commands/ custom commands have been merged into skills; one mechanism now.) Same-name collisions resolve enterprise > personal > project, and nested monorepo skills get directory-qualified names like apps/web:deploy.

The reason skills exist as a separate mechanism from CLAUDE.md is economics. Skills use three-stage progressive disclosure: at startup the agent loads only each skill's name and description; full instructions load when a task matches; and supporting files load only if the instructions call for them. The docs put it plainly: "a skill's body loads only when it's used, so long reference material costs almost nothing until you need it." Your 500-line deploy runbook costs a one-line description until deploy day. This is Week 1's token accounting applied to agent configuration — CLAUDE.md is always-loaded rent, skills are pay-per-use.

Two more things make skills strategic. First, the format is the open Agent Skills standard from step 1 — a skill you author for a client works in Codex, Gemini CLI, Cursor, and Copilot too, so runbook work survives a vendor switch. Second, Claude Code extends the standard with invocation control, subagent execution, and dynamic context injection — !`cmd` lines in a skill run before Claude reads it, injecting live output (current branch, failing tests) into the instructions.

Extension · hooks

Hooks: deterministic code at lifecycle events

Skills are still instructions — the model reads them and decides. Hooks are the opposite animal: user-defined shell commands (or HTTP endpoints, or LLM prompts) that fire at lifecycle events, outside the model's control. The events span the session (SessionStart, SessionEnd), the turn (UserPromptSubmit, Stop), and — most usefully — every tool call (PreToolUse, PostToolUse). Hooks are configured under hooks in the same settings files as permissions, with matchers targeting tool names: exact matches, |-separated lists, regex, or MCP tools via mcp__server__tool.

A hook talks back through two channels. Exit codes: exit 2 blocks the action and feeds the hook's stderr to Claude as feedback (exit 1 is non-blocking — a warning that doesn't stop anything). Or exit 0 with a JSON payload for fine-grained control: permissionDecision of allow/deny/ask, continue: false to halt the turn, additionalContext to inject information. That means a PreToolUse hook can implement policies no glob pattern can express — parse the actual command, check the target path against a manifest, call your compliance API, and return a verdict.

The interaction with permissions is precisely specified, and asymmetric in the safe direction: a blocking hook takes precedence over allow rules, but a hook's "allow" never bypasses deny or ask rules. Hooks can only tighten, never loosen. That's the property you quote when a client's security architect asks whether custom automation could accidentally open a hole.

Interactive — future goal

Planned: a hook playground — attach a PreToolUse hook to a sample tool call, toggle its exit code between 0, 1, and 2, and watch the call pass, warn, or block with stderr fed back to the model. Needs backend standup.

The load-bearing idea

Harness enforcement vs model steering

Step back and the four mechanisms sort into two piles — and the docs draw the line themselves, twice. On permissions: "Permission rules are enforced by Claude Code, not by the model. Instructions in your prompt or CLAUDE.md shape what Claude tries to do, but they don't change what Claude Code allows." On memory: CLAUDE.md files are "context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." Permissions and hooks are harness enforcement — deterministic, running as code outside the model. CLAUDE.md and skills are model steering — context the model reads and, in the overwhelming majority of cases, follows — but following is a behavior, not a guarantee. Sandboxing adds a third, OS-level layer around Bash and its child processes; permissions plus sandbox is defense-in-depth, not redundancy.

Anthropic's published mental model for choosing among them is worth committing to memory: facts Claude should always hold → CLAUDE.md. Instructions tied to part of the tree → path-scoped rules. Procedures and runbooks → skills ("procedures belong in skills; CLAUDE.md is for facts"). Anything that must happen deterministically → hooks. Context-heavy side work → subagents (later this week).

Here's the client scene this was all building to. A security lead tells you: "We're safe — we wrote 'NEVER touch production configs' in the CLAUDE.md." You now know that sentence is a steering instruction: valuable, usually followed, and not an enforcement boundary. The FDE answer is to keep the sentence and add the guarantee — a deny rule on the config paths in checked-in settings, or a PreToolUse hook that blocks the write with exit 2. Prompts shape behavior; the harness bounds it. Deploying agents at clients means knowing, for every control in your design, which side of that line it lives on.

FDE mindset

When a client asks "is the agent allowed to do X?", never answer from the CLAUDE.md. Answer from the harness: what do the permission rules and hooks actually enforce? Instructions are what the agent will probably do; enforcement is what it can do. Clients are buying the second one — and tomorrow we put these controls to work on real multi-step agent workflows.

Deep dive: the three precedence chains that bite in production

Optional. ~10 minutes. Three ordered lists that explain most "the agent isn't obeying my config" tickets.

1 · Credentials. Highest wins: cloud-provider env flags (Bedrock / Vertex / Foundry) → ANTHROPIC_AUTH_TOKEN → ANTHROPIC_API_KEY → apiKeyHelper → CLAUDE_CODE_OAUTH_TOKEN → subscription OAuth from /login. The classic incident: an ANTHROPIC_API_KEY left in a dotfile silently overrides the team's subscription, and the metered bill climbs. First move: /status, read which credential is active.

2 · Settings. Managed settings → CLI arguments → .claude/settings.local.json → .claude/settings.json (project) → ~/.claude/settings.json (user). The property to quote in a security review: a deny at any level cannot be re-allowed at any other level. Enterprise policy denies it → it is dead, everywhere, regardless of local files or flags.

3 · Hooks × permissions. A blocking PreToolUse hook (exit 2, or JSON permissionDecision: "deny") beats an allow rule. A hook returning "allow" never bypasses a deny or ask rule. Hooks tighten; they cannot loosen.

Worked example — a guardrail that actually guarantees

Requirement: "the agent must never modify infra/prod/." The layered answer: ① a line in CLAUDE.md ("never touch infra/prod — ask a human") so the model steers away by default; ② a deny rule Edit(infra/prod/**) in the checked-in .claude/settings.json so the harness refuses even if the model tries; ③ optionally a PreToolUse hook that logs the blocked attempt to the client's audit channel. Layer ① is steering, ② is enforcement, ③ is observability. If you can label each layer of your own design this way, you're ready for the client's security architect.

Version floors worth noting (docs-referenced, as of this writing): auto memory needs v2.1.59+, /cd needs v2.1.169+, the bundled /run and /verify skills need v2.1.145+. The native installer auto-updates, so these mostly matter when diagnosing a client's pinned or stale install.
