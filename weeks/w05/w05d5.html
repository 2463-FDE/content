Review the Graph Model and Defend the GraphRAG Service

1 · Required

Assessment: review question fit and graph integrity

Review the model from the client decision backward. Which questions and action surfaces does it support? Are stable identities and constraints explicit? Do relationship type, direction, time, and provenance carry one defensible meaning? Run synthetic duplicate, orphan, stale-version, and bounded-path checks. Remove nodes that no representative question uses. A visually rich graph can still be a poor retrieval contract. Record findings as fixed, locked, or deferred with evidence—not as aesthetic preferences.

2 · Required

Deliver to two rooms from one evidence set

The executive readout leads with the client outcome, the decision enabled, one before/after signal or bounded demonstration, and remaining risk. The simulated technical-team session then shows the graph model, representative query, retrieval trace, source/path support, failure or abstention case, and NFR tradeoffs. Both rooms use the same repository evidence; only sequence and vocabulary change. Do not imply real deployment, cloud resources, client data, or external approval. The session is local and simulated.

Required practice · Run the Friday delivery · static path

Arrange the GraphRAG model review so both rooms hear one truth.

  1. Close the evidence pack: question fit, integrity checks, retriever review — one evidence set serves both rooms — assembled before either presentation
  2. Executive readout: outcome, principal risk, decision requested — the business room decides from consequence, not Cypher
  3. Technical defense: schema, retrievers, Text2Cypher review — the technical room examines the same evidence at depth
  4. Share MCP configuration lessons without widening authority — lessons transfer; scopes do not silently grow
  5. Record feedback and the next commitment — the week closes on the loop, not on applause

The evidence pack is assembled before any room hears it; executives get outcome and risk first; the technical room defends structure; MCP lessons transfer without widening authority; feedback closes the loop.

3 · Required

Share MCP configuration lessons without widening authority

In the Claude Code retro, compare scoped Neo4j MCP configurations: tool names, allowed operations, result limits, read/write separation, credential boundary, and denial evidence. Explain what made graph evidence easier to inspect and what remained application-enforced. Never paste secrets, connection strings, or client records into the share-out. An MCP configuration is workflow evidence, not permission to connect to production, make an external change, or certify a control.

4 · Required

Review Text2Cypher for safety and result quality

A Text2Cypher quality set contains representative questions, expected properties or paths, no-evidence cases, ambiguous language, and unsafe-operation prompts. Review schema use, read-only shape, query bounds, and result correctness. Do not require exact string equality: two queries may be semantically equivalent, while a syntactically polished query may answer the wrong business question. Link each answer claim to returned evidence and require abstention when support is missing. A confident unsupported answer blocks the readout.

Required interaction · Readout gate
The service gives a confident answer, but the trace contains no source ID or supporting graph path. What is the correct readout decision?

Required practice · Which generated query passes review? · static path

Two Text2Cypher outputs answer the same review question. Select the evidence that belongs in a safety and quality review.

Claim: This generated query surface is safe to run and its results are quality-checked.

  • Generated query A — supports the claim: parameterized, bounded, read-only — the reviewable shape
  • Result-quality check — supports the claim: result quality is measured against expected evidence, not taken on fluency
  • Model explanation — does not support the claim: a fluent self-description is not a safety property
  • Single timing — does not support the claim: one fast run on one input is neither safety nor quality

A bounded, parameterized, read-only query plus a result check against expected evidence is reviewable; the model's fluent explanation and one fast run are not evidence.

5 · Required

Close the evidence pack and feedback loop

Commit the reviewed graph model, retrieval decisions, synthetic evaluation evidence, ADR register, NFR/cost assumptions, two-audience readout, and MCP note to the approved project branch. Capture weekly feedback on what remained unclear, which diagram or interaction changed a decision, and which evidence gap should shape the next iteration. Keep unresolved placement and package-stability questions visible. This lesson authorizes no merge, deployment, publication, provisioning, paid call, backend change, real learner data, or external message.

Graph-model review rubric · optional depth

Score question fit, identity/integrity, relationship semantics, time/provenance, import repeatability, retriever fit, query/result quality, grounding, abstention, NFRs, ownership, and correction. A weak critical row blocks; totals do not average away unsupported claims.

Text2Cypher test matrix · optional depth

Include paraphrases, multi-hop questions, aggregation, current-versus-expired rules, no match, conflicting evidence, excessive traversal, and write/procedure attempts. Check safety and result semantics independently.

Readout rehearsal · optional depth

Executive cut: outcome → evidence → decision → risk/ask. Technical cut: model → query/retrieval trace → source/path → failure/abstention → NFRs → locked/deferred decisions. Keep both under the trainer’s timebox.
