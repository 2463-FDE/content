Design a Governed Graph Schema and Import

Week 5 · Day 2Neo4j Knowledge Graphs & Context EngineeringCore 30 · ~6 min read · 3 min diagram · 1 interaction · 6-Q check · ~20 min required

Move from a promising diagram to a governed graph: bound traversals, separate indexes from constraints, design an idempotent import, encode rules with provenance, and reuse ADR lock/defer plus AI-native acceptance criteria where the source curriculum assigns them.

Project 1 · solo · insurance brownfield. Continue the fictional property-and-casualty insurer as one learner. Govern the insurance graph and preserve its decision history; do not start the team banking/payments project early.

1 · Required

Traverse only what the question needs

Variable-length paths can express “zero to several hops” without writing each length separately. That power can also explore far more of the graph than the client question needs. State minimum and maximum length, use relationship types, anchor on selective identity, and push eligible predicates into the query. Return a bounded projection, not every path. A query that asks for “all connections at any depth” is usually an unresolved problem statement. Write a representative question and expected path shape first; then choose the traversal.

2 · Required

Indexes find; constraints protect

Search-performance indexes help eligible predicates find data efficiently. Constraints enforce declared integrity such as required uniqueness. The two may interact internally, but their contracts differ. “We added an index” does not mean duplicates are impossible. Start from stable business keys and define what their scope is: global, tenant-specific, or version-specific. Add synthetic negative tests that attempt a duplicate or missing key. A schema review should be able to say what is made impossible, what is merely faster, and what still depends on application validation.

3 · Required

Build an idempotent import pipeline

A reviewable import has stages: read a synthetic source, normalize types and required fields, resolve stable identities, merge nodes, connect relationships, and validate counts plus orphan/duplicate conditions. LOAD CSV is one documented path; driver-based pipelines may be more suitable for application control. Keep mutable attributes out of identity patterns. Batch size, retry, and error handling are NFR decisions, not afterthoughts. Re-run the same fixture and prove the graph does not multiply. Preserve a source identifier so every imported assertion can be traced and corrected.

4 · Required

Represent rules without pretending to enforce them

A business rule can be a node or relationship when the system needs to traverse its owner, version, effective dates, exceptions, standards, or evidence. That makes the rule inspectable institutional knowledge. It does not make Neo4j a policy engine by default. Runtime authorization, approval, and legal interpretation stay in their owned enforcement layers. Model provenance and lifecycle explicitly: who supplied the rule, when it became effective, what supersedes it, and what evidence supports applicability. A rule without this context becomes a confident but stale edge.

Required interaction · Decision register
The team proposes the direction (Policy)-[:GOVERNS]->(Case), but the handover contains no representative queries and both directions read plausibly. What is the defensible status today?

5 · Required

Treat compliance as governed evidence

Compliance labels are not verdicts. Use the graph to connect a policy or control to its source, scope, owner, evidence, and review date. Keep unknown applicability visible. A relationship such as SUPPORTS_CONTROL should mean exactly what the team can prove, not “certifies compliance.” This week makes no certification claim. The graph can help a reviewer reconstruct why a control was considered and which artifact supports it; accountable stakeholders still determine applicability and acceptance.

6 · Required

Lock or defer graph decisions explicitly

Reuse ADR discipline here because the source curriculum assigns it to graph design. Lock stable identity, relationship meaning, time semantics, or a public interface when evidence is sufficient and downstream work depends on it. Defer when the necessary query, data profile, or owner decision is missing. A deferral needs the evidence gap, owner, review date, and flip condition. “We can change it later” is not a decision. The lab asks you to resist locking relationship direction before representative query evidence exists.

7 · Required

Write an AI-native story for graph-backed behavior

An AI-native story names the human outcome, the machine action, the evidence the machine may use, and the human control. Example: “As a case reviewer, I want the assistant to show the active exception path and source passage so I can approve or escalate with traceable evidence.” Acceptance criteria cover grounded success, no-match, conflicting versions, stale sources, denial, and latency/context limits. This preserves useful old Week 5 material in its source-assigned role: a behavior contract for GraphRAG, not a replacement arc about specification tooling.

8 · Required

Workshop: prove the schema against questions

Review the model with three artifacts side by side: the graph diagram, representative questions/Cypher, and the decision register. For each node and relationship, ask which question needs it. For each question, identify the integrity rule and expected result fixture. Remove entities that exist only because a source table had a column. Mark rules stored as evidence versus rules enforced elsewhere. Finish with one locked decision, one honest deferral, and acceptance cases another engineer can run against synthetic data.

Import hardening · optional depth

Quarantine malformed rows; report counts by reason; use explicit transaction boundaries; preserve source IDs; re-run the fixture; assert identity and orphan checks. Performance tuning follows a correct import contract.

ADR fields for a graph decision · optional depth

Decision, context, evidence, chosen semantics, rejected alternatives, consequences, owner, date, status, and flip condition. Supersede rather than erase history.

Acceptance pack · optional depth

Include a normal path, no match, duplicate source row, stale version, conflicting rule, unauthorized operation, latency threshold, and maximum evidence/context size.

Governed import — inert Cypher

Synthetic LOAD CSV shape with constrained identity and post-load validation. The URL is illustrative and performs no request.

// Synthetic path; use only an approved local fixture
LOAD CSV WITH HEADERS FROM 'file:///synthetic_cases.csv' AS row
WITH row WHERE row.case_id IS NOT NULL AND row.policy_id IS NOT NULL
MERGE (c:Case {case_id: row.case_id})
MERGE (p:Policy {policy_id: row.policy_id})
MERGE (c)-[r:CITES]->(p)
SET r.source_id = row.source_id,
    r.observed_at = datetime(row.observed_at);

MATCH (c:Case)
WITH c.case_id AS key, count(*) AS n
WHERE n > 1
RETURN key, n; // expected: zero rows
