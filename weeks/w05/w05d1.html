Spec Before Code: Architecture Before Implementation

Week 5 · Day 1 Spec-Driven Development ~18 min · reading @150 wpm + diagram + check

Four weeks in, you can make a coding agent produce a lot of code very fast. This week is about the harder skill: making it produce the right code, repeatably, on systems that matter. The industry's answer is spec-driven development (SDD) — write the specification first, gate every phase on a human-reviewed artifact, and treat code as something generated from the spec rather than the thing you hand-craft. Today you learn why "just describe it to the agent" fails predictably, what the spec-first workflow actually looks like in the tools winning right now (GitHub Spec Kit, GSD, Kiro), and how to decide when full SDD pays off versus when it's ceremony. Scroll the reading; the panel on the right builds the artifact pipeline piece by piece.

The failure mode

Vibe coding fails on schedule

Start with the pathology this whole week exists to fix. You open a coding agent, describe what you want in a few conversational sentences — "build me a photo-organizing app with albums by date" — and watch it generate hundreds of lines in seconds. It feels like magic right up until you run it. GitHub's own diagnosis of this pattern is blunt: you get code that "looks right, but doesn't quite work." It may not compile. It solves part of the problem and silently skips the rest. It ignores the architectural constraints you had in your head but never wrote down.

The industry's nickname for this is vibe coding: prompt-and-pray, iterate by vibes, hope the pieces converge. And here's the part that matters for you as an engineer — the failure is predictable, and it is not a model-capability problem. GitHub's framing is that developers treat coding agents "like search engines" when they should be treated like literal-minded pair programmers. A search engine rewards vague queries with ranked guesses. A literal-minded pair programmer does exactly what you said — including all the things you didn't say, which it fills in with plausible defaults you never reviewed.

That distinction should feel familiar. In Week 1 you learned that hallucination is usually a window problem: the fact the model needed was never given to it. Vibe coding is the same disease at project scale. The requirements the agent needed — the edge cases, the data model, the "obviously it has to integrate with the existing auth system" — were never placed in front of it, so it generated the most plausible-looking program to fill the gap. The model sounded confident because it always does. The gap was in the input, not the engine. Hold that thought; every fix you meet today is, at bottom, a way of closing that gap before generation starts instead of debugging it after.

The evidence

The paradox is measured, not vibes

If vibe coding merely felt sloppy, you could dismiss this as taste. It doesn't just feel sloppy — it shows up in controlled measurement, and the numbers are strange enough to have a name. Controlled studies of AI coding assistants report 20–56% productivity gains. Yet the most rigorous randomized controlled trial in the same literature found a 19% slowdown for experienced developers using AI assistance. Telemetry across more than 10,000 developers shows the same shape at scale: 98% more pull requests, 91% longer review times, and flat delivery metrics. More code motion, no more shipped value. Researchers call this the productivity–reliability paradox.

Read those numbers as an FDE and the story writes itself. The agent made generating code nearly free — so the bottleneck moved. It moved downstream, into review, integration, and rework: humans staring at thousand-line diffs trying to reverse-engineer what the agent thought it was asked to do. Throughput at the keyboard went up; throughput of the system stayed flat, because the constraint was never typing speed.

The paradox paper's thesis is the sentence to carry into every client engagement this year: "Specification discipline, not model capability, is the binding constraint on AI-assisted software dependability." Not a bigger model. Not a better prompt phrasing. The binding constraint is whether anyone wrote down, precisely, what the software must do — because a non-deterministic generator amplifies whatever you feed it, and if you feed it ambiguity, it manufactures ambiguity at machine speed. When a client tells you "we rolled out AI coding tools and our velocity didn't move," you are almost certainly looking at this paradox in the wild, and the fix they're paying you for starts in the next section.

The inversion

Spec as the source of truth

Spec-driven development is the deliberate inversion of the classic relationship between code and documentation. For decades, code was the source of truth and the spec — if one existed — was a stale document written afterward, drifting further from reality with every commit. SDD flips it: the specification is the source of truth, and code becomes "a generated or verified secondary artifact." The spec is not paperwork about the system; the spec is the system's contract, and the code is one rendering of it.

Why does this inversion suddenly make sense in 2026 when it was a hard sell for fifty years? Because the economics of generation changed. When humans wrote every line, a detailed spec was expensive overhead on top of expensive code. When an agent writes the lines, the spec is no longer overhead — it is the input that determines everything. A precise spec is the difference between the agent building your system and the agent building a system that superficially resembles yours. The research framing calls specs "living, executable artifacts": they stay in the repo, they get versioned, they get updated when intent changes, and regeneration or verification flows from them — rather than docs written after the fact as an act of archaeology.

Notice what this does to your job description. In a code-first world, the senior skill was writing code. In a spec-first world, the senior skill is deciding and articulating what the code must do — goals, journeys, constraints, non-goals — with enough precision that a literal-minded generator can't misread it. That has always been the heart of engineering; SDD just makes it the explicit, load-bearing artifact. And it's precisely the skill clients buy from a forward-deployed engineer: they have domain experts who know what they want and agents that can type; the missing layer is the person who can turn the first into an unambiguous contract for the second.

The workflow

Phase gates: Specify → Plan → Tasks → Implement

So what does spec-first look like as an actual working loop? The canonical shape is GitHub Spec Kit, the open-source toolkit that has become the reference implementation (v0.12.3 as of this writing, with 30+ agent integrations — Claude Code, Copilot, Gemini CLI, Cursor, and friends). Spec Kit structures work as four gated phases, each with one job:

Specify captures goals and user journeys — the what and the why, with no technology choices in it. Plan turns that into architecture: stack, constraints, integration points, the how. Tasks decomposes the plan into small, individually reviewable units of work. Implement is the only phase where the agent writes production code, one task at a time. Each phase emits a Markdown artifact — a spec, then a plan, then a task list — and that artifact is the structured context handed to the next phase. The rule that makes it gated rather than decorative: "you don't move to the next one until the current task is fully validated" — validated by a human, reading the artifact.

This changes where the human sits. You are a steward, not a doer: you steer, verify each artifact, spot the gaps, and refine before advancing. And it changes what review means. Instead of reverse-engineering a "thousand-line code dump" at the end — exactly the bottleneck the paradox data caught — you review a two-page spec, then a plan, then focused per-task diffs. Each gate is cheap to inspect and cheap to fix, because errors are caught in the artifact where they were introduced rather than three phases downstream in generated code. Spec Kit exposes all of this as slash commands, one per phase, plus a constitution command for standing project principles and a couple of optional helpers. But the commands are incidental. The shape is the lesson: artifact, gate, artifact, gate.

Requirement quality

Current state → target state (and the parity trap)

Every workflow you've seen so far starts at /specify — a blank file and a description of what you want. That is the greenfield case, and it is not yours. You have inherited a system that already runs, that the business depends on, and that nobody documented. Where does the spec come from then?

From a method with four beats, in which writing the spec is the third. One: understand the business before a line of code — take the walkthrough, find the modules that halt the business if they break. Two: analyze the sources — code, docs, screenshots, tickets — trusting no single tool and never taking an AI's analysis as hard truth. Three: write the specification against a chosen target state. Four: implement in modules, validated by SMEs. The step people skip is the target state itself, and it's where the real decisions live: UI/UX, storage, target language, deployment architecture, phase-out pattern. Get the target state right and the spec, the backlog, and the implementation all inherit correct decisions; get it wrong and every downstream artifact compounds the error.

One more thing changes on brownfield: the spec is a client-facing proposal, not an internal agent input. It goes to the sponsor, gets argued over, and comes back with features added and omitted. Which is precisely where the discipline earns its keep — because the default answer to "what should the new system do?" is the feature-parity trap: rebuild exactly what exists, in newer tech. Fowler's warning is blunt. Teams badly underestimate it, and merely defining the "as-is" scope is often the single largest cost on the project. Worse, legacy systems bloat — a Standish Group study found roughly half of existing features go unused, and old bug-workarounds calcify into "must-have" requirements. Rebuilding all of it "is not only waste, it's a missed opportunity to build what's actually needed today." Scope to value, not to parity — and if that sounds like a judgment call rather than a procedure, that's the next step.

Specs × context engineering

Specs are persistent context for agents

There's a second, quieter reason spec artifacts earn their keep, and it connects this week directly back to Week 1. GSD ("Get Shit Done") — the other spec-driven workflow you'll meet in the wild, now developed at open-gsd/gsd-core after the original 64.6K-star repo was archived this June — starts from a different diagnosis than GitHub's. Its problem statement isn't just ambiguity; it's context rot: "context bloat silently degrades output quality, there is no shared memory between sessions, and nothing verifies that code actually works." A long agent session slowly fills its window with stale exploration, half-decisions, and dead ends — and quality quietly sags. Sound familiar? It's history eviction and signal-burial from Week 1, wearing project clothes.

GSD's fix is spec-shaped: a set of persistent Markdown artifacts — a project file, a roadmap, a plan, a summary and a state file — that live in the repository and survive session boundaries. Decisions get locked into artifacts once, then reloaded into fresh contexts instead of being re-litigated inside a bloated one. Its five-step loop per milestone — Discuss to lock decisions upfront, Plan to research and decompose while verifying each plan fits within context limits, Execute in parallel waves with each executor starting clean, Verify to validate the built code and generate remediation plans, then Ship — is the same spec-before-code spine as Spec Kit, tuned for context-window economics.

Here is the unifying insight: a spec is context engineering. The same artifact that gives humans a reviewable gate gives agents a curated, high-signal window. Instead of an agent inheriting 150K tokens of meandering conversation, it gets a two-page plan containing only the decisions that survived review. Specs are how decisions travel — across phases, across sessions, across fresh-context subagents, and across the humans and models that come later. Once you see specs as the durable memory of a project, "write the spec first" stops being process piety and becomes the same window discipline you learned in Week 1, applied at project scale.

Judgment call

The rigor spectrum: when SDD is overkill

Now the judgment layer — because the fastest way to discredit SDD at a client is to apply it to everything. The SDD taxonomy research is explicit that rigor is a spectrum, not a binary, and names three distinct positions on it. Spec-first: write the spec, generate the code, and from then on the code lives its own life — the spec was scaffolding. Spec-anchored: the spec is maintained alongside the code for the system's lifetime; changes update the spec, and the code is verified against it. Spec-as-source: the strongest form — code is always regenerated from the spec, and humans stop editing generated output entirely, the way you stopped editing compiler output decades ago.

Each position has different applicability, and the taxonomy paper pairs them with a decision framework for "when SDD provides value and when simpler approaches suffice." You already run this triage instinctively in your own tooling: a typo fix or a one-line config tweak gets a direct edit and a normal commit — spinning up a four-phase pipeline for it would be pure ceremony. A ticket-shaped feature touching auth, data models, and three services is exactly where phase gates earn their cost, because that's where unwritten assumptions breed. The variables that should move you up the rigor spectrum: how expensive is a wrong assumption (compliance, money movement, multi-tenant data)? How many people and agents must share the same understanding over time? How long will the system live? High stakes, many readers, long life → more spec. Throwaway script, one author, one afternoon → vibe away with a clear conscience.

This is the answer you give when a skeptical client engineer says "this is just waterfall with extra steps." It isn't — waterfall gated years of work behind frozen documents; SDD gates hours of generation behind living, versioned artifacts, and the loop runs per-feature, not per-project. But the skeptic is right that rigor has a price. The FDE skill is not "always write specs." It is matching the rigor to the risk — and being able to say out loud which position on the spectrum you've chosen and why.

Honest framing · FDE mindset

Adopted faster than it's proven — carry it anyway

One more thing an engineer owes a client: intellectual honesty about the evidence. SDD's motivation is well measured — the productivity–reliability paradox numbers you saw in step two are real. The workflow's effectiveness is still being formally studied: a SANER 2026 registered report is only now running the controlled experiments, using a three-stage specification → tests → function workflow to measure how "human intervention in specification and test refinement influences the quality and dynamics of LLM-generated code." Meanwhile the governance research names the moderating variables — task abstraction, codebase maturity, developer experience — and the two amplifiers that decide how hard the paradox bites: code-review bottlenecks and context-window constraints. Both of which, you'll notice, are exactly what phase gates and persistent artifacts attack. The honest sentence for a client: industry adoption is running ahead of academic validation — the mechanism is sound and the early signal is strong, but treat vendor-benchmark superlatives with the same skepticism you'd bring to any tool pitch.

And notice where you're standing. The pipeline you'll work inside during client-delivery weeks — plan documents, grounding requirements, human confirmation gates, budgeted context, verification stages — is this pattern. Today's job was to make it explicit and tool-agnostic, because at a client you won't get to choose the logo: one shop runs Spec Kit, another Kiro, another a homegrown pipeline. The shape underneath is what transfers: close the specification gap before generation, gate on artifacts humans can actually review, let the spec be the memory.

FDE mindset

When a client says "the AI wrote the wrong thing," the vibe coder blames the model and re-rolls. The FDE asks: "where is the written contract it was supposed to satisfy — and if there isn't one, what did we expect?" Specification discipline, not model capability, is the binding constraint. Deep dive: the 2026 SDD tooling landscape

Optional. ~10 minutes. Names, versions, and command surfaces you'll actually see at clients.

GitHub Spec Kit (v0.12.3, MIT licensed, 106K+ stars) is the reference implementation. Install it as a command-line tool from its repository and pin the version, because it moves fast. It is agent-agnostic across thirty-plus integrations — Claude Code, Copilot, Gemini CLI, Codex, Cursor and more — so you can switch agents without changing the artifacts. The core commands walk the four phases in order, preceded by a constitution command for standing project principles. Optional helpers probe underspecified areas, check cross-artifact consistency, generate checklists, push tasks out as GitHub issues, and assess an existing codebase against its specs — that last one being the brownfield entry point. Three usage modes are documented: greenfield from zero, creative exploration where one spec produces parallel implementations across stacks, and iterative enhancement of brownfield systems.

GSD is the cautionary tale about tool churn: the famous gsd-build/get-shit-done repo (64.6K stars) was archived on 2026-06-26 at v1.42.3, and active development moved to open-gsd/gsd-core (v1.6.1). If a client's internal wiki still points at the archived repo, that's your first PR. It runs on Claude Code, OpenCode, Gemini CLI, Kimi CLI, Kilo, Codex, Copilot, Cursor, and Windsurf.

Kiro, from AWS, bakes the workflow into an IDE: three artifacts per feature — requirements, design and tasks — written with EARS acceptance criteria and approval gates between phases. It also ships a "Quick Plan" variant that auto-generates all three without gates, which is the built-in acknowledgment that not every change deserves full ceremony.

What to actually remember

Three vendors, one converged shape: artifact chain + human gates + spec as persistent context. Learn the shape, not the logos — the logos changed twice while this course was being written, and the archived-repo story above is the proof.
