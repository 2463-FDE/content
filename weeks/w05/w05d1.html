Model the Client Domain as a Property Graph

Week 5 · Day 1Neo4j Knowledge Graphs & Context EngineeringCore 30 · ~6 min read · 3 min diagram · 3 interactions · 6-Q check · ~28 min required

Start the hands-on Neo4j week by turning one client decision into a property-graph model. Learn the graph primitives, choose graph versus relational or vector access from the question, read and write bounded Cypher, and open a local-only path through Docker and Neo4j Browser.

Project 1 · solo · insurance brownfield. Keep working alone on the fictional property-and-casualty insurer inherited from Weeks 1–4. Model its case, policy, incident, evidence, and decision seams with synthetic data; the team banking/payments engagement has not started.

1 · Required

Milestone: model a decision, not a data dump

The milestone is a Neo4j domain model of the inherited client system, but the first artifact is a question: Which current policy and exception path support this case decision? That framing prevents a noun harvest in which every term becomes a node. Name the person making the decision, the evidence they need, and the action the system may support. Then model the smallest connected slice that can answer it. This reuses the valuable part of problem scoping: outcome before implementation. It does not turn specification workflow into this week’s arc; the graph and its retrieval behavior are now the primary work.

2 · Required

Property-graph primitives

A Neo4j property graph has nodes, directed and typed relationships, labels, and key-value properties. A Case node can carry a stable case identifier and status. A Policy node can carry its version and effective dates. A CITES relationship makes the connection traversable and can carry source and observation time. Labels group nodes for patterns and constraints; they are not a substitute for identity. Relationship direction should express the domain sentence and make representative queries readable, not merely point in the direction the import happened to run.

3 · Required

Cypher reads patterns with MATCH

Cypher is declarative: state the pattern and predicates you need, not a pointer-by-pointer traversal procedure. MATCH (c:Case)-[r:CITES]->(p:Policy) describes the path. WHERE narrows eligible evidence—for example, the policy version effective on the decision date. RETURN projects only the fields the application needs. Treat every query as a reviewable claim about the model. If the query is awkward, the problem may be a poor model, an unclear client question, or both; a larger result set is not automatically a better answer.

Required practice · From decision question to action surface · static path

Step the Juniper Vale claims question through the property graph and watch what each primitive contributes.

  1. The client asks a decision question — question = Which policy supports this case decision? · graph = untouched
    Begin with a decision question, not a fashionable graph-shaped diagram.
  2. Nodes carry stable identity — Case = case_id · status · Policy = policy_id · version
    Nodes carry stable identity; properties describe them.
  3. The CITES relationship carries provenance — CITES = source · observed_at · reviewable = yes — the connection itself holds evidence
    A typed relationship can carry provenance and time, making the connection reviewable.
  4. MATCH reads the pattern — query = MATCH (c:Case)-[r:CITES]->(p:Policy) · filter = current policy version only · rows = eligible evidence
    MATCH describes the pattern to read; the diagram is a query contract.
  5. The decision point grounds an action — decision = approve · review · refuse · action surface = show evidence · escalate
    The graph supports a decision and action surface; it does not make the business decision by itself.
4 · Required

CREATE, MERGE, and stable identity

Use CREATE when the application intentionally creates a new pattern. Use MERGE when it should match an entire stable pattern or create it if absent. Do not translate that into “MERGE prevents duplicates.” It does not replace a uniqueness constraint, especially under concurrent writes. Merge around stable business identity first, then set mutable properties and connect known entities. A giant MERGE pattern containing changing fields can create parallel structures when one field changes. The question is not which command is more advanced; it is whether the identity contract is explicit.

A handover note says: “Case C-17 cites Policy P-4 in paragraph 12.” What should represent cites in the graph?

5 · Required

Filter and aggregate after eligibility is clear

Filtering determines which paths count as evidence. Aggregation summarizes those eligible rows with functions such as count() or collect(). Keep the order of reasoning visible: choose the path, apply time/status/source rules, then aggregate. Counting every related policy before filtering expired versions produces a precise number for the wrong set. Return a bounded projection with source identifiers so a human can inspect it. In client systems, a count or ranked list without the path and eligibility rule often hides the decision that mattered most.

6 · Required

Graph, relational, or vector?

Choose from the access pattern. Relational tables are strong for structured records, set operations, and established transactional constraints. Vector retrieval is strong when language varies and semantic similarity finds useful candidates. A graph is strong when connected structure—ownership, dependencies, exceptions, provenance, multi-hop paths—is itself part of the question. These are not mutually exclusive storage religions. The inherited system may keep operational records in SQL, passages and embeddings in Chroma, and governed relationships in Neo4j. Add a graph only when the connection changes what the application can decide or explain.

Required practice · Is this question graph-shaped? · static path

Juniper Vale hands you four asks. Select the ones whose access pattern actually suggests graph retrieval.

Claim: These asks need traversable relationships with provenance — a graph access pattern.

  • Connection ask — supports the claim: the path and the relationship semantics are the question — graph retrieval's home ground
  • Provenance ask — supports the claim: the evidence lives on the typed relationship (source, observed_at)
  • Aggregate ask — does not support the claim: a relational aggregation — tables answer this without traversal
  • Similarity ask — does not support the claim: semantic similarity is the vector store's question

Path and relationship semantics are first-class in the connection-shaped asks; monthly averages are relational aggregates and passage similarity is vector work.

7 · Required

Run locally with Docker and Browser

Neo4j documents Docker as a local development route and Browser as an interactive Cypher workspace. For this curriculum, setup is local-only: use synthetic fixtures, pinned images, explicit ports, and a disposable volume. Never paste client records or credentials into Browser history. The code popup shows an inert setup and seed example; it does not run automatically. Confirm the edition and version your project approves before executing any command. If Docker is unavailable, the required learning path remains the model, query contract, and review—not provisioning an alternative external service.

8 · Required

Entities, relationships, decisions, actions

Close by walking from entity to action. Entities need stable identity. Relationships need meaning, direction, time, and provenance where the domain requires them. The graph should expose a decision point such as approve, review, or refuse, while the application owns authorization and policy. An action surface might show supporting evidence or route to a reviewer; the graph does not authorize the action itself. Commit one model slice, three representative questions, and the identity assumptions. Tomorrow you will add integrity, import, rules, and explicit lock/defer decisions.

Local-only Docker and Browser checklist · optional depth

Pin the approved Neo4j image; bind only required local ports; use synthetic data; store no secret in committed files; verify health; open Browser at the local endpoint; run a read query; destroy the disposable container when the lab ends. This is an execution checklist, not permission to create cloud resources.

MERGE nuance · optional depth

MERGE acts on the complete pattern supplied. Prefer constrained identity for each entity, then create or merge the relationship deliberately. Re-run synthetic imports and assert node/relationship counts to prove idempotence.

Store selection note · optional depth

Document the question, latency/consistency needs, source of truth, update path, and failure behavior before choosing SQL, vector, graph, or a hybrid. Product names are not an architecture argument.

Local Neo4j seed — inert example

Synthetic, local-only commands and Cypher. Review the image version and project policy before running; nothing on this page executes them.

// Synthetic Week 5 fixture — no client data
CREATE CONSTRAINT case_id IF NOT EXISTS
FOR (c:Case) REQUIRE c.case_id IS UNIQUE;
CREATE CONSTRAINT policy_id IF NOT EXISTS
FOR (p:Policy) REQUIRE p.policy_id IS UNIQUE;

MERGE (c:Case {case_id: 'SYN-17'})
MERGE (p:Policy {policy_id: 'SYN-P4'})
  ON CREATE SET p.version = 3
MERGE (c)-[r:CITES]->(p)
SET r.source_id = 'synthetic-paragraph-12';

MATCH (c:Case)-[r:CITES]->(p:Policy)
RETURN c.case_id, p.policy_id, p.version, r.source_id;
