Construct a Knowledge Graph and Choose a Retriever

Week 5 · Day 3Neo4j Knowledge Graphs & Context EngineeringCore 30 · ~4 min read · 3 min diagram · 1 interaction · 6-Q check · ~18 min required

Begin the GraphRAG milestone by constructing a provenance-aware graph from documents and choosing among vector, vector-plus-Cypher, and text-to-Cypher retrieval. Experimental APIs and generated extraction are labeled honestly, bounded, and evaluated with synthetic fixtures.

1 · Required

Milestone: graph-grounded retrieval begins

GraphRAG adds explicit entities and relationships to an agent’s retrieval path. That can answer questions where semantic similarity alone misses ownership, dependency, exception, time, or provenance. It does not make an LLM answer true automatically. The grounding chain still has failure points: source selection, chunking, extraction, identity resolution, schema validation, retrieval, context assembly, and generation. Today’s milestone is one reproducible path from synthetic documents to a bounded evidence object, plus a reasoned retriever choice for three client questions.

2 · Required

Use SimpleKGPipeline with an experimental label

Neo4j’s GraphRAG package documents SimpleKGPipeline for knowledge-graph construction from text. Its current import path is under neo4j_graphrag.experimental. That namespace is a material limitation, not fine print. Pin the approved package version, test against your fixture, isolate the adapter, and expect compatibility changes. The code popup is an inert shape, not a production recipe and not executed by the page. A “simple” pipeline reduces setup steps; it does not remove the need to own schema, provenance, corrections, and evaluation.

3 · Required

Treat extraction as candidate structure

An LLM can propose entities and relations from document chunks, but extraction output is probabilistic. Preserve document, chunk, version, and offset identifiers. Restrict output to allowed labels, relationship types, and property shapes. Validate required identities before merging; quarantine ambiguous or unsupported assertions. Entity resolution is especially consequential: merging two different customers is corruption, while failing to merge aliases fragments evidence. Keep the original passage reachable so a reviewer can distinguish source text from an inferred edge.

4 · Required

VectorRetriever: semantic candidates

Choose VectorRetriever when the bounded question can be answered from entities or chunks found by embedding similarity. It is the narrowest of today’s three paths. Evaluate whether relevant evidence appears in the top results and whether irrelevant but linguistically similar records crowd it out. Similarity is not truth and not graph connectivity. Return source identifiers and scores as diagnostics, not as confidence that the final answer is correct.

Required interaction · Retriever routing
The reviewer asks: “Find policy text related to a late-fee waiver, then show the active exception, owner, and escalation path.” Which first retrieval design best fits?

5 · Required

VectorCypherRetriever: candidates plus a known path

Choose VectorCypherRetriever when language variation helps find a starting entity but the answer also needs an explicit, developer-known traversal. A policy passage may be found semantically, then enriched with the active version, owner, exception, and escalation relationships. The supplied Cypher is a controlled contract and should be bounded, parameterized, and tested. This pattern often fits production context engineering because it combines flexible entry with reviewable expansion instead of asking a model to invent every query.

6 · Required

Text2CypherRetriever: generated query surface

Choose Text2CypherRetriever only when the question space genuinely requires translating varied natural language into graph queries. Supply a concise schema, examples, and domain vocabulary. Enforce read-only credentials, query validation, time/result limits, and allowlisted procedures; evaluate on representative fixtures and refusal cases. Generated Cypher can be syntactically valid and still ask the wrong business question. Do not execute today’s examples against a live or client database.

7 · Required

FDE situation: defend the context diagram

In the situation session, a client asks why a graph is needed when Chroma already retrieves policy passages. Start with the decision: the reviewer needs the current exception, its owner, and escalation path, not only similar wording. Draw documents, extraction, schema validation, Neo4j, retriever, context assembler, and agent. Then show one graph-model slice and choose the least complex retriever that answers the question. State the failure case and abstention behavior. The deliverable is a defensible architecture decision—not a claim that GraphRAG is universally superior.

Experimental API checklist · optional depth

Pin the package; isolate imports behind an adapter; record tested Neo4j/driver/package versions; keep a synthetic compatibility test; watch release notes; define a fallback. Experimental does not mean unusable—it means stability is not promised.

Extraction review queue · optional depth

Route unknown labels, missing identities, conflicting relations, and low-evidence assertions to a review queue. Store the source span and proposed operation; never ask reviewers to judge an edge without its evidence.

Situation-session prompt · optional depth

Defend one design under challenge: why graph, which retriever, what is bounded, what can fail, what evidence supports the result, and what would make you remove the graph from this path?
