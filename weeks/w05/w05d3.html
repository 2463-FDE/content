The Spec-Driven Tooling Landscape

Week 5 · Day 3 Spec-Driven Development ~18 min · reading @150 wpm + diagram + check

Monday gave you the why of spec-driven development; yesterday you practiced turning vague asks into requirements. Today is the tool map: GitHub's spec-kit and its peers (Kiro specs, OpenSpec), the Architecture Decision Record discipline that outlives any single tool, and the machine-readable knowledge artifacts — constitutions, decision logs, AGENTS.md — that agents now consume instead of tribal knowledge. Underneath the logos there is exactly one design axis: where does each tool lock a decision, and where does it let you defer? Scroll the reading; the panel on the right assembles the landscape one layer at a time, then places every tool on that axis — and the closing section covers why current practice is to steal parts of these kits rather than adopt one whole.

The landscape

Specs became executable — so tooling grew around them

For most of software history, a specification was a document that described the system and then drifted away from it. The generation of tools you meet today inverts that. GitHub's spec-kit — the reference open-source toolkit for Spec-Driven Development — states the thesis outright: specifications become executable artifacts that "directly generate working implementations," not guidance documents. Its methodology paper calls this the power inversion: "code serves specifications." The spec is the generative source of truth, and implementation plans and code are continuously regenerated output. When the spec and the code disagree, the spec wins and the code gets regenerated — the opposite of every "the docs are out of date" culture you've ever worked in.

Once specs are load-bearing like that, they need real engineering support — templates, pipelines, validation gates, version control — and that's what today's landscape is. Three tools anchor it. Spec-kit (currently 0.12.3, with 30+ agent integrations spanning Copilot, Claude Code, Gemini CLI, and Codex CLI) is the rigorous, phase-gated pipeline. Kiro, AWS's agentic IDE, bakes specs into the editor as three structured files with approval gates between phases. OpenSpec is the lightweight rebel that rejects phase gates entirely and scopes artifacts per-change. Around all three sit two older, tool-agnostic disciplines: ADRs for capturing decisions, and agent-facing knowledge files like AGENTS.md.

Here's the frame to hold for the whole day, because it's the one that survives the tools changing names: every one of these systems is answering the same question differently — when a decision comes up, do you lock it now, or defer it and keep moving? Lock too early and you calcify guesses into law. Defer too long and the decision gets made silently, by whoever's code merges first, with no record of why. Each tool is a different bet on that trade, and picking one for a client means matching the bet to the client — not picking the one with the most GitHub stars.

Tool 1 · spec-kit

Spec-kit: a fixed artifact pipeline of slash commands

Spec-kit's workflow is a fixed sequence of slash commands, each of which emits a Markdown artifact that feeds the next. Note the naming — everything is namespaced /speckit.* (older writeups show bare /specify and /plan; that's stale). The core pipeline: /speckit.constitution establishes governing principles; /speckit.specify captures the what and why — deliberately no tech stack; /speckit.plan adds tech stack and architecture; /speckit.tasks breaks the plan into an ordered task list; /speckit.taskstoissues turns those tasks into GitHub issues; and /speckit.implement executes. A seventh core command, /speckit.converge, closes the loop: it assesses the actual codebase against the spec, plan, and tasks and appends the remaining work as new tasks — the mechanism that keeps a living spec honest against a drifting repo.

Three more commands are optional validators, not mandatory pipeline steps: /speckit.clarify runs structured de-ambiguation on a spec, /speckit.analyze checks cross-artifact consistency (does the plan actually cover the spec? do the tasks cover the plan?), and /speckit.checklist generates quality gates. The separation matters: the core pipeline is the spine you always walk; the optional commands are inspection tools you reach for when the stakes or the ambiguity justify them.

Why should an FDE care about the shape and not just the commands? Because the pipeline is the methodology. Each artifact is a checkpoint where a human can read, correct, and approve before the next stage compounds on it — which is precisely the anti-drift structure you already live inside with this program's own pipeline. Spec-kit is what it looks like when "review the plan before the code" gets industrialized into tooling that thirty different coding agents can plug into.

Tool 1 · the lock mechanism

The constitution — and the refusal to guess

Two features make spec-kit the hardest "lock" in the landscape, and they're the two you'll be asked about in interviews. The first is the constitution: a file at memory/constitution.md holding the project's non-negotiable principles — things like library-first design, test-first development, CLI interfaces for every capability, and integration-over-isolation testing. The methodology's language is deliberately strong: the constitution is "immutable architectural law, not guidelines." Its articles are enforced as something like compile-time checks — template gates that every downstream spec, plan, and task list must pass — and any deviation requires documented justification, not a shrug. You write it once, before any planning happens, and everything else is generated under its constraints.

The second is spec-kit's ambiguity discipline. Instead of letting the LLM paper over an unspecified detail with a plausible assumption, the templates mandate that unclear points be flagged inline as [NEEDS CLARIFICATION: specific question]. The spec arrives with its own uncertainty made visible — every place where a real decision is pending is marked, and the optional /speckit.clarify command exists to resolve those markers through structured questioning. Compare that with what you diagnosed in Week 1: a model that wasn't given a fact fills the gap with fluent invention. Spec-kit's markers are the same hallucination lesson applied to requirements: don't let the gap get filled silently — surface it, route it to a human, lock the answer, and only then generate.

Together the constitution and the markers define spec-kit's position on the axis: lock early, explicitly, and in writing. Cross-cutting principles are locked before planning begins; per-feature ambiguities are locked before implementation begins. Nothing significant is allowed to leak, undecided, into code. That rigor is a superb fit for greenfield builds with real stakes — and, as you'll see in two steps, it's exactly the property OpenSpec positions itself against.

Tool 2 · Kiro

Kiro specs: three files, approval gates, EARS

Kiro, AWS's agentic IDE, is what spec-driven development looks like when it's built into the editor rather than bolted on as a CLI. Every Kiro spec is the same three files: requirements.md (user stories with acceptance criteria), design.md (architecture, sequence diagrams, implementation strategy), and tasks.md (discrete, trackable tasks). The workflow walks three phases — requirements → design → tasks — and in the standard workflows there are approval gates between phases: a human signs off on the requirements before design is generated, and on the design before tasks are. For well-understood features there's a "Quick Plan" mode that skips the gates — an explicit acknowledgment that the lock-vs-defer dial should be tunable per feature, not fixed per tool. Kiro also distinguishes feature specs from bugfix specs, and executes tasks in concurrent waves once they're approved.

Kiro's most exportable idea is how it writes requirements: EARS, the Easy Approach to Requirements Syntax. Every requirement takes the shape "WHEN [condition or event] THE SYSTEM SHALL [expected behavior]." That template looks almost too simple until you try it on a mushy sentence. "The app should handle errors gracefully" becomes "WHEN an API call fails with a 5xx error THE SYSTEM SHALL retry twice and then display a cached result." The first version is a vibe; the second is testable and traceable — you can point at the acceptance test it implies and the design element that satisfies it, which is precisely why Kiro chose it.

The FDE takeaway: even if a client never adopts Kiro, EARS is a notation you can carry into any requirements conversation tomorrow, and "approval gates between requirements, design, and tasks" is a shape you can impose on any tool — including a plain Claude Code session.

Tool 3 · OpenSpec

OpenSpec: per-change folders, no gates, brownfield-first

The third anchor, OpenSpec (Fission-AI, v1.5.0), is the deliberate counter-position — and it positions itself explicitly against spec-kit's "rigid phase gates." Where spec-kit and Kiro scope specs at the project or feature-pipeline level, OpenSpec scopes them per change: every change gets its own folder containing a proposal.md (why and what), a specs/ directory of requirements and scenarios, a design.md, and a tasks.md. The loop is propose → apply → archive (driven by slash commands like /opsx:propose, working across 20+ AI assistants): propose the change as artifacts, apply it to the codebase, then archive the folder as a record of what happened. Recent releases add "Stores" — team-shared planning repos, in beta — so the per-change folders can live in a shared space rather than one engineer's checkout.

The philosophical core is that artifacts are fluid: they can be updated at any time, "without ceremony." There is no gate where a requirements document gets frozen and signed. That's a trade, stated honestly — OpenSpec gives up upfront rigor to buy iteration speed. And it buys one more thing that matters enormously in consulting work: brownfield fit. OpenSpec supports adopting spec-driven habits on an existing system by capturing current system state as specs, rather than assuming you're generating a codebase from scratch. Spec-kit's regenerate-from-spec thesis is most natural on greenfield; most clients you'll meet are standing in fifteen years of brownfield.

So the landscape now has its two poles. Spec-kit: lock early, gate every phase, spec as generative source. OpenSpec: defer freely, gate nothing, artifacts as living working notes scoped to the change in front of you. Kiro sits between them, with gates you can switch off. None of these is "right" — the next question is what your client's decisions actually cost when they're wrong, and that's where ADRs come in.

Decision capture · ADRs

ADRs: lock the decision, keep the receipt

Strip away the tooling and the oldest artifact in this landscape is still the most durable: the Architecture Decision Record. The definitions, maintained at adr.github.io: an architectural decision is a justified design choice addressing a functionally or non-functionally significant requirement; an architecturally significant requirement (ASR) is one with measurable effect on architecture and quality; an ADR documents one decision and its rationale — one decision per record, deliberately small.

Michael Nygard's original 2011 format is five sections: Title, Status, Context, Decision, Consequences. Context states the competing forces neutrally — what pressures existed, not a sales pitch for the choice. Consequences lists outcomes both positive and negative. His motivation is the line worth quoting to clients verbatim: "large documents are never kept up to date; small, modular documents have at least a chance." ADRs live in version control (classically doc/arch/adr-NNN.md) with sequential, never-reused numbers, and an outdated ADR is superseded, never deleted. The modern structured alternative is MADR 4.0.0: Context and Problem Statement, optional Decision Drivers, Considered Options, Decision Outcome with justification, Consequences — plus optional pros/cons per option and a Confirmation section stating how compliance will be verified. It ships full and minimal variants, each annotated or bare.

What makes ADRs an operational practice rather than documentation theater is the lifecycle, which AWS's prescriptive guidance formalizes: an ADR is Proposed, reviewed in a meeting that starts with dedicated 10–15 minutes of silent reading, then Accepted or Rejected. Once accepted, the ADR is immutable — new insight doesn't edit the record, it produces a new ADR that supersedes the old one, preserving the full decision history. And the resulting decision log has teeth: it is consulted during code review, where reviewers can block a change that violates an accepted ADR. Scope it by significance — structure, non-functional requirements, dependencies, interfaces, construction techniques (Richards & Ford's list). Write an ADR for every decision in that class; skip the trivia.

Knowledge modeling

Machine-readable project knowledge: the layer agents read

Now zoom out and notice what the constitution and the ADR log have in common: they are project knowledge encoded as versioned artifacts — written once, checked into git, and consumed by both humans and machines. That's the pattern the industry has been converging on, and its most visible standard- bearer is AGENTS.md: "a simple, open format for guiding coding agents." It's a dedicated, predictable file — deliberately separate from the human-facing README — carrying the things an agent needs to work in your repo: build and test commands, code style, conventions, security notes. Over 60,000 open-source projects carry one, with tooling support across OpenAI, Google, GitHub, JetBrains, Cursor, and Devin, and nested files so each subproject in a monorepo can carry its own agent-facing instructions.

Put the three artifact types side by side and you get what today's brief calls the knowledge modeling layer. AGENTS.md answers "how do we work here?" — commands, conventions, style. The spec-kit constitution answers "what principles are non-negotiable?" The ADR log answers "what did we decide, and why?" Each replaces a different flavor of tribal knowledge — the stuff that used to live in a senior engineer's head and leak out over coffee. When knowledge is modeled as files, an agent spinning up on the repo and a human joining the team in month six inherit the same context, automatically, from version control.

You already live this: the repo you work in every day has a CLAUDE.md that shapes how your own coding agent behaves — same layer, same idea. And connect it back to Week 1: an agent's behavior is determined by what's in its window. Knowledge artifacts are the supply side of context engineering — curated, versioned, predictable files that make the right context cheap to load. A client whose conventions live in five veterans' heads has an unwritten knowledge layer, and every agent (and every new hire) they onboard pays that tax. Writing it down is often the highest-leverage first deliverable an FDE can ship.

The axis

Lock vs defer: one axis under all the logos

Time to collapse the landscape onto its single organizing axis. At the lock-early end: spec-kit, which forces ambiguity to the surface with [NEEDS CLARIFICATION] markers and freezes cross-cutting principles in an immutable constitution before planning even starts. Right beside it, Kiro's standard workflows, which insert human approval gates between requirements, design, and tasks — with Quick Plan as the pressure valve for well-understood work. At the defer-and-iterate end: OpenSpec, which rejects gates entirely, keeps every artifact fluid and updatable "without ceremony," and scopes specs per-change — trading upfront rigor for iteration speed and brownfield fit.

And in the middle, the position that's easiest to defend in front of a client: lock with an escape hatch. That's the ADR discipline. Decisions are genuinely locked — accepted ADRs are immutable and enforced at code review — but they're reversible through an explicit supersede process that preserves the full history. The team gets the stability of locked decisions without the brittleness, and the future team gets the why, not just the what. Notice that this isn't a tool at all; it's a discipline you can layer under any of the three tools above.

So the FDE playbook writes itself as diagnostic questions. How expensive is a wrong decision here — regulated fintech core, or an internal dashboard? Expensive-to-reverse pushes you toward the lock end; cheap-to-reverse rewards deferring. Greenfield or brownfield? Greenfield tolerates spec-kit's regenerate-from-spec rigor; fifteen years of brownfield usually wants OpenSpec's capture-what-exists posture. How much process will this team actually follow? A gate the team resents becomes a gate the team routes around. Whatever you choose, two moves are near-universal: start an ADR log (the middle path costs almost nothing and pays compound interest), and write the knowledge layer down — AGENTS.md, a constitution, conventions — so agents and humans inherit the same context.

Practice note · as of August 2026

Know these tools cold. Steal their parts. Do not adopt one wholesale. That is not a swipe at spec-kit, Kiro or OpenSpec — it is where the practice has landed, and there are four reasons worth being able to say out loud in front of a client.

1 · The harness ate the packaging. What these kits actually shipped was a directory of prompt templates plus a command set. Coding agents now have native equivalents of every piece — CLAUDE.md / AGENTS.md for project context, slash commands, skills, hooks, plan mode, subagents. A vendored template directory becomes a fork you have to keep in sync with a harness that changes every few months.

2 · The leverage moved. These kits were built when models needed to be told what a spec contains. Current models produce that structure unprompted. What they cannot produce is your client's constraints, your prior art, and a stopping condition a machine can check — so the value moved from document schema to context plus verification. A generic template cannot express "cite a page-ID from their Confluence, or declare that no prior art exists." A repo-local command can, and that one rule does more work than any template.

3 · Portability never happened. Kiro's specs are excellent and live inside Kiro's IDE. That is precisely why requirements.md / design.md / tasks.md never became a cross-tool standard the way AGENTS.md did.

4 · Follow the money. Tessl raised roughly $125M on the premise that the spec is the primary artifact, then repositioned around registry, governance and evals. When the best-funded pure play moves off spec-as-product, that tells you the durable value sits in enforcement, not in the document format.

So what do you steal? EARS notation and the requirements/design/tasks separation from Kiro. [NEEDS CLARIFICATION] markers and the constitution idea from spec-kit. Per-change folders and capture-what-exists from OpenSpec. The supersede lifecycle from ADRs. Then put them in the client's own repo, as their own commands and conventions, versioned with their code.

And know the failure mode of going fully custom: teams drop the spec entirely, keep the automation, and end up with agents that have no stopping condition — the token furnace from Week 1, rebuilt on purpose. Whatever you assemble, it still needs a written statement of intent and a definition of done that something other than your own code can check.

FDE mindset

Clients will ask "which spec tool should we use?" The FDE answer is a question back: "which of your decisions are expensive to reverse — and where are they currently being made silently?" Tools are bets on the lock-vs-defer axis. Map the client's reversal costs first, then pick the bet — and whatever you pick, leave behind a decision log and a written knowledge layer, because those outlive the tool.

Deep dive: one decision, written both ways

Optional. ~10 minutes. The same decision as a Nygard ADR and as MADR 4.0 — so you can feel the trade.

Scenario. A client's order service must add full-text search. The team debated Elasticsearch (a new cluster to run) vs Postgres tsvector (already in the stack, weaker relevance features). They chose Postgres. Capture it.

Nygard format (2011) — five sections, prose-first
  • Title: ADR-014: Use Postgres full-text search for order search
  • Status: Accepted
  • Context: Search must ship this quarter. Ops team is two people; every new stateful service adds pager load. Relevance needs are modest (order IDs, customer names, SKU text). Forces stated neutrally — Elasticsearch offers better ranking; Postgres is already operated and backed up.
  • Decision: Implement search on Postgres tsvector/tsquery with a GIN index.
  • Consequences: + no new infrastructure, ships inside the quarter, one backup story. − relevance tuning is limited; if search scope grows to documents/attachments we will need a dedicated engine — that would be a new ADR superseding this one.
MADR 4.0.0 — same decision, structured for comparison
  • Context and Problem Statement: Order search needed by Q3; which engine?
  • Decision Drivers: ops headcount, time-to-ship, existing backup/HA story, modest relevance needs.
  • Considered Options: Elasticsearch cluster; Postgres FTS; hosted search SaaS.
  • Decision Outcome: Postgres FTS — because it satisfies the drivers with zero new operational surface. (Pros/cons of each option recorded per template.)
  • Confirmation: code review checks that no new search infra appears; load test proves p95 < 200ms at 1M orders.

What to notice. Nygard optimizes for narrative speed — five sections you can write in ten minutes, forces stated neutrally, consequences honest in both directions. MADR optimizes for comparability and verification — options are enumerated, the winner is justified against explicit drivers, and Confirmation makes compliance checkable at review time. Both share the lifecycle: this record is immutable once Accepted; when the search scope outgrows Postgres, ADR-0NN supersedes ADR-014 — it never edits it — and the history of why survives. MADR ships full and minimal variants (each annotated or bare); start minimal, upgrade when a decision is contested.
