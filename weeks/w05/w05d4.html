Decomposition: From Spec to Phased Plans

Week 5 · Day 4 Spec-Driven Development ~18 min · reading @150 wpm + diagram + check

You have a spec the client signed off on. Between that document and working software sits the most dangerous stretch of any engagement — the part where "we all agreed" quietly turns into forty ungated tasks and one enormous, unreviewable pull request. Today you learn the discipline that closes that gap: decomposing a spec into a phased plan with explicit gates, where every task ends in a check that passes or fails, and where the non-functional requirements — performance, scale, security — are stated as measurable targets instead of adjectives. Scroll the reading; the panel on the right assembles one spec into a gated, verifiable plan, phase by phase.

The gap

A spec is not a plan — decomposition is a pipeline of artifacts

Earlier this week you learned to write a spec: requirements, user stories, acceptance criteria. The rookie move is to hand that spec — to a teammate or to a coding agent — and say "build it." What comes back solves the wrong problem, or solves the right problem as one monolithic change nobody can review. The fix is not a better spec. It's recognizing that between spec and code there is a pipeline of intermediate artifacts, and each artifact is a checkpoint where a human reviews and redirects before more work piles on top.

GitHub's Spec Kit makes the pipeline explicit: Spec → Plan → Tasks → Implement, driven by /speckit.specify, /speckit.plan, /speckit.tasks, and /speckit.implement. The plan step reads the feature requirements, user stories, and acceptance criteria and converts business needs into concrete technical decisions — with the rationale documented, not just the decision. In Spec Kit's own framing, decomposing this way "creates checkpoints where humans review and redirect."

AWS's Kiro arrives at exactly the same shape from a different direction. A Kiro spec is three files: requirements.md captures user stories and acceptance criteria in structured notation; design.md documents the technical architecture, sequence diagrams, and implementation considerations; tasks.md is a detailed implementation plan of discrete, trackable tasks. Two independent tools, one convergent lesson: requirements, design, and tasks are separate artifacts with separate review moments. When you see the same structure emerge independently in competing tools, treat it as a signal about the shape of the underlying problem — not a vendor quirk. Your job today is to internalize that shape so you can produce it with any tool, or with none.

Structure

A plan has phases — and gates at the boundaries

So what does the "Plan" artifact actually contain? Not a flat to-do list. Spec Kit's plan template structures it as ordered phases: Phase 0 — Research (unknowns get resolved into research.md before anything is designed), Phase 1 — Design & contracts (the data model, API contracts, and a quickstart land as data-model.md, contracts/, quickstart.md), and Phase 2 — Task generation (the design is decomposed into tasks.md). Research before design, design before tasks — each phase produces artifacts the next phase consumes.

The part beginners skip is the gate. The template's Constitution Check — the project's standing engineering rules — is phrased as a hard gate: "GATE: Must pass before Phase 0 research. Re-check after Phase 1 design." A gate is a named moment where the plan must demonstrate something before the next phase is allowed to start. Without gates, a "phased plan" is just a task list with headings; nothing stops phase 3 work from starting while phase 1's design questions are still open.

Two more things the template forces up front. A Technical Context section demands performance goals, constraints, and scale before design begins — you'll see why that matters when we reach NFRs. And the phasing itself is a guidance pattern, not bureaucracy: Spec Kit's quickstart tells you that for anything large, you should implement in phases — its Taskify example is literally "Phase 1: basic project/task structure, Phase 2: Kanban functionality, Phase 3: comments and assignments" — because sequencing "prevents context saturation and allows for validation at each stage." That phrase should ring a Week-1 bell: phases are a context-window discipline as much as a project-management one. A phase is a unit of work small enough to hold in one head — human or model — and validate before moving on.

Gates against over-engineering

Phase −1: make complexity justify itself

Gates don't just sequence work — they fight the most common failure of AI-generated plans: over-engineering. Spec Kit's methodology defines a set of Phase −1 pre-implementation gates that run before any phase at all: a Simplicity Gate (is this the simplest thing that satisfies the spec?), an Anti-Abstraction Gate (are we wrapping frameworks in layers nobody asked for?), and an Integration-First Gate (do we prove the pieces talk to each other before polishing them individually?). In the methodology's words, these gates "prevent over-engineering by making the LLM explicitly justify any complexity."

Note the enforcement design, because it's subtle and worth stealing: failing a gate doesn't block the plan. It requires a documented justification in a Complexity Tracking table. The gate's job is accountability, not prohibition — sometimes the complex answer is right, but it should never be the silent answer. That table becomes the record a reviewer (or a future you) reads to understand why the architecture is the shape it is.

The same instinct shows up in how you already work. Claude Code's recommended workflow is Explore → Plan → Implement → Commit, precisely because "letting Claude jump straight to coding can produce code that solves the wrong problem." And the docs are equally clear about when planning pays: when you're uncertain about the approach, when the change touches multiple files, when the code is unfamiliar. The inverse rule is the one to memorize: "If you could describe the diff in one sentence, skip the plan." Decomposition is a tool with a cost. An FDE who runs a full phased-plan ceremony on a one-line config change is making the same mistake — in mirror image — as one who vibe-codes a multi-service feature.

Verifiability

Every task ends in a check that passes or fails

Now the property that separates a plan you can hand off from a plan that generates status meetings: verifiability. The Claude Code docs put it bluntly: "Give Claude a check it can run: tests, a build, a screenshot to compare... Give Claude something that produces a pass or fail, and the loop closes on its own." The same is true of humans. A task whose completion is a matter of opinion ("improve the search experience") cannot be delegated, sequenced, or audited. A task that ends in a binary check ("pytest tests/search/ -m integration green; p95 under 400 ms on the seeded dataset") can be.

This starts at the requirements layer. Kiro writes acceptance criteria in EARS notation — "WHEN [condition or event] THE SYSTEM SHALL [expected behavior]" — and the payoff is exactly the one we want: clarity, testability ("each requirement can be directly translated into test cases"), traceability, and completeness. An EARS-shaped requirement is halfway to being a verifiable task already. The docs' guidance on specs completes the picture: the most useful specs are self-contained — they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works. Put the check in the plan, next to the task it verifies.

Verifiability also unlocks parallelism. Because Kiro's tasks carry explicit outcomes, it "analyzes your task list, figures out which tasks depend on each other, and runs independent tasks concurrently" — waves of independent tasks execute in parallel, waves themselves run in sequence. And you should verify the artifacts, not just the code: Spec Kit ships /speckit.checklist to validate the plan and /speckit.analyze to cross-check spec, plan, and tasks against each other before a line of code exists. There's measurement behind this, too: a 2026 study added phase-level context-grounding hooks that validate each Specify/Plan/Tasks artifact against actual repository evidence — catching hallucinated APIs before implementation — and lifted SWE-bench Lite to 58.2% Pass@1 with 99.7–100% test compatibility. Checking the plan is cheaper than debugging the code it produces.

NFRs · the checklist

Non-functional requirements: use a quality model, not vibes

Everything so far decomposes the functional side of the spec — what the system does. The failures that actually kill client engagements usually live on the other side: the feature works in the demo and falls over at production load, or works beautifully and fails the security review. These are non-functional requirements (NFRs) — how well the system does what it does — and the amateur tell is handling them by vibes: someone remembers to ask about performance, nobody asks about data portability, and the gap surfaces in month three.

The professional move is to walk a quality model — a standard checklist of the dimensions quality can vary on. The current one is ISO/IEC 25010:2023 (edition 2.0, November 2023), which defines nine product-quality characteristics: functional suitability, performance efficiency, compatibility, usability (including accessibility), reliability, security, maintainability, portability/flexibility, and — new in the 2023 edition — safety. The standard is explicit that this model exists for exactly our job: "eliciting and defining product and information system requirements," "validating the comprehensiveness of a requirements definition," setting design and testing objectives, and establishing measures of quality characteristics.

One detail matters for how you write plans: in 25010, "scale" is not a separate category you might forget — capacity is a named subcharacteristic of performance efficiency, alongside time behavior and resource utilization. Handling load is a first-class quality dimension with a slot on the checklist. So the NFR section of a phased plan is a disciplined pass over the model: for each of the nine characteristics, decide whether it is load-bearing for this system — most features care intensely about three or four and only trivially about the rest — and for each load-bearing one, state a target per phase. Phase 1 of a search feature might target correctness at toy scale; phase 3 owns the 50-tenant capacity target. Writing "N/A — internal tool, single tenant" next to compatibility is not wasted ink; it's the proof you asked.

NFRs · perf & scale

Performance targets must be SLO-shaped

"The API should be fast" is not a requirement; it's a wish. To make performance and scale NFRs verifiable — the same property we demanded of tasks — borrow the vocabulary Google's Site Reliability Engineering built for exactly this. An SLI (service level indicator) is "a quantitative measure of some aspect of the level of service": request latency, error rate, throughput, availability. An SLO (service level objective) is "a target value or range of values for a service level, measured by an SLI" — p99 latency ≤ 300 ms, availability ≥ 99.9%. An SLA is an SLO with consequences attached for missing it — which, on a client engagement, is the line item your statement of work may be judged against.

An SLO-shaped NFR slots straight into the plan machinery from earlier: it's a gate condition ("Phase 2 does not close until the p99 target holds on the seeded dataset") and a per-task check. But the SRE book's target-setting guidance is as important as the definitions, and it transfers directly into plan authoring. Don't just adopt current performance as the target — you'll enshrine whatever the prototype happens to do. Keep SLIs simple: "complicated aggregations in SLIs can obscure changes to system performance, and are also harder to reason about." Choose just enough SLOs to cover the system's attributes — if you can't win an argument about priorities by citing a particular SLO, it isn't worth having. And perfection can wait: "you can always refine SLO definitions and targets over time." A rough, stated target in the plan beats a perfect target that arrives after launch.

One counter-intuitive rule earns its own sentence: avoid overachieving. Users calibrate on what your service actually does, not what you promised — Google's Chubby lock service famously became so reliable that teams built unwarranted dependencies on it, so Google introduced planned outages to keep real behavior near the stated SLO. For you the client-facing translation is: the targets in your plan are commitments that shape how the client builds around your system. State them deliberately.

NFRs · security

Security NFRs: pick an ASVS level, cite requirement IDs

"Must be secure" is the security equivalent of "should be fast" — unfalsifiable, so unverifiable, so not a requirement. The standard that fixes it is the OWASP Application Security Verification Standard — ASVS 5.0.0, released May 30, 2025 — an open catalog of roughly 350 security requirements across 17 chapters for designing, developing, and testing modern web applications and services. Crucially for plan-writing, it defines three verification levels, L1 through L3, chosen by how critical the application is: a marketing microsite doesn't carry the same burden as a payments system, and the level makes that judgment explicit instead of implicit.

ASVS's own stated uses map one-to-one onto the plan you're building: use it as a metric (how secure is this application, measurably), as guidance (which controls to actually implement), and during procurement (contractual security requirements — which is exactly what a client-engagement plan's security section is). And because every requirement carries a stable <chapter>.<section>.<requirement> identifier, your plan can cite specific ASVS IDs the same way it cites the spec's REQ-* IDs. "Phase 1 targets ASVS L2; session management tasks verify against chapter 3's session requirements" is checkable by a reviewer, an auditor, or an agent. "We take security seriously" is checkable by no one.

Notice what just happened across these two steps: the same trick, twice. Performance NFRs became verifiable by borrowing SRE's SLI/SLO vocabulary; security NFRs became verifiable by borrowing OWASP's leveled requirement catalog. The general FDE pattern is: for every load-bearing quality characteristic, find the domain's existing measurement standard and cite into it — never invent your own scale when a citable one exists. It makes your plan auditable, and it makes you look like you've done this before. Which, after today, you have.

Assembly

The finished artifact: phased, gated, verifiable, targeted

Put the day back together as a single checklist you can run on any plan — yours or anyone's. A decomposition worth handing off has four properties. Phased: work is ordered into research → design/contracts → tasks (or the domain's equivalent), each phase small enough to validate before the next begins — Spec Kit's Phase 0/1/2, Kiro's requirements/design/tasks, same shape. Gated: the boundaries have named conditions — a constitution check that must pass before research and be re-checked after design, Phase −1 simplicity/anti-abstraction/integration gates with a complexity-tracking table for documented exceptions. Verifiable: every task ends in a pass/fail check, requirements are written in testable EARS shape, dependencies are explicit enough to sequence into waves, and the artifacts themselves get cross-checked (/speckit.analyze) before implementation starts. Targeted: the NFR section walks ISO 25010's nine characteristics, keeps the load-bearing ones, and states each as a citable, measurable target — SLO-shaped for performance and capacity, ASVS-leveled with requirement IDs for security.

Run that checklist against the pipeline you already work inside and you'll recognize everything: this program's own ticket workflow phases work through plan and verify stages, gates plans on grounding citations, and refuses to let reviews silently skip. That isn't coincidence — it's this day's material, operationalized. The plan is also where tomorrow starts: Day 5 takes a finished spec + plan + task list and hands it to an implementing agent end-to-end, then reviews the output against the spec. Everything you wrote into the plan today — the gates, the checks, the targets — is what makes that handoff safe rather than hopeful.

FDE mindset

A spec tells the client what they're getting. The phased plan is where you earn trust: it shows the client their risk is front-loaded into gated phases, their reviews land at checkpoints instead of at the end, and their "it must be fast and secure" has become numbers someone can be held to. When an engagement goes sideways, it is almost never because the spec was wrong — it's because nobody could say, at week three, which phase they were in and what had been proven so far. The plan is the instrument that makes progress a fact instead of a feeling.

Deep dive: a worked NFR section

Optional. ~10 minutes. What the last three steps look like written down for one feature.

The feature. "Tenant-scoped document search" for a 50-tenant SaaS client. The spec's functional side is done; below is the NFR pass a phased plan would carry. Method: walk ISO/IEC 25010's nine characteristics, keep the load-bearing ones, give each a measurable target and a phase that owns it.

NFR pass — ISO 25010 walk (kept vs. waived)
  • Performance efficiency — kept. SLI: request latency & error rate on /search. SLO: p99 ≤ 300 ms, error rate < 0.1% at 50 RPS sustained. Owned by Phase 2 gate (seeded-dataset load test must pass).
  • · Capacity (sub-characteristic) — kept. Target: 50 tenants × 100K docs each with the p99 SLO holding. Owned by Phase 3 gate.
  • Security — kept. ASVS 5.0 Level 2 (multi-tenant, business data, no payments). Plan cites chapter-level IDs for session management and access control; every search task's check includes a cross-tenant-leak test.
  • Reliability — kept. SLO: search availability ≥ 99.9% monthly; graceful degradation to keyword-only if the vector store is down (Phase 3).
  • Usability, compatibility, maintainability, portability, safety, functional suitability — walked and waived or deferred, each with one written line of rationale ("safety: no physical-world actuation — N/A"). The written waiver is the proof the characteristic was considered.

Note the shape: every kept characteristic has an indicator, a target value, and an owning phase gate — SLO discipline applied beyond latency. And per the SRE guidance: four SLOs, not fourteen; simple SLIs; targets set from the client's need (support-agent workflow tolerates ~300 ms), not from whatever the prototype currently does.

Why per-phase ownership matters. If no phase owns the capacity target, it's owned by "the end" — which means it's tested for the first time in production week. Assigning each NFR to a phase gate is what turns "we care about scale" into a date on which scale is proven. That is also exactly where the plan connects back to verifiable tasks: a gate is just a pass/fail check promoted to a phase boundary.
