How an LLM Actually Spends Its Attention

Week 1 · Day 1 Foundation AI Engineering ~45–60 min context windows · token budgets · sampling · hallucination · AI coding
The whole game

One window holds everything

An LLM has no memory between calls and no live access to your databases. For a single request, everything it can reason over must fit inside one finite context window — measured in tokens (≈ ¾ of a word). Nothing outside it exists, as far as the model is concerned.

The most important sentence in the course: capabilities and limits both come from the window. "Can it summarize this?" "Why did it forget?" "Why did it make that up?" — all the same question: how is the window being spent?

Slice 1

The system prompt always goes first

The system prompt sets the model's role and rules. It is prepended to every request, so its cost is paid on every call. A 2,000-token system prompt on a million-request feature is a real line item — latency and dollars.

Slice 2

Few-shot examples buy quality with tokens

Showing the model a handful of examples ("few-shot") is the cheapest way to lock in a format or tone — no fine-tuning. But each example is more tokens, every time. The FDE question is never "do examples help?" (they do) but "how few can I get away with?"

Slice 3

Retrieved context can dominate

When you paste in documents, code, or RAG results, that retrieved context is usually the biggest consumer of the window. It's the lever you'll spend Week 2 learning to pull precisely. More retrieved text is not more intelligence — it's more budget spent, and it can crowd out everything else.

Slice 4 · the silent leak

Conversation history grows every turn

In a chat, the entire prior conversation is re-sent each turn so the model "remembers." Token cost grows with every message — quietly, until a long session gets slow, expensive, or drops the earliest instructions off the front. Most "the assistant forgot the rules" bugs are history eviction.

Slice 5

The user's question is just one more slice

Notice how late the actual user input arrives. By now system prompt + examples + context + history may have consumed most of the window. The question is rarely the expensive part — but it competes for the same finite space as everything else.

Token budget

What's left is room to answer

The window is shared between input and output. Whatever you don't spend on input is the room left for the answer. Overstuff the input and the model truncates or stops mid-thought. A token budget decides, in advance, how many tokens each slice gets.

And every token is metered: cost ≈ (input + output tokens) × price. Token budgeting is cost engineering. "Why is this feature so expensive?" — the answer lives in this picture.

Generation

Sampling decides how it answers

The model produces the answer one token at a time, each from a probability distribution. Temperature and top-p control the draw: low → near-deterministic (good for extraction, classification, code); high → more varied, less repeatable.

FDE reflex: if the same input must give the same output, turn temperature down. Most "flaky" AI features are just sampling left too hot.

Failure mode

Hallucination is a window problem first

A hallucination is a confident, fluent, wrong answer. The most common cause: the needed fact was never in the window, so the model filled the gap with plausible text. It has no built-in way to say "I wasn't given that."

"Your AI lies" is usually "your retrieval missed" or "the answer truncated." You fix more hallucinations by managing the window than by swapping models.

Live diagram

AI coding: Claude Code is a window manager

You'll work all 10 weeks inside Claude Code. The model that makes you good at it fast: it is a context-window manager wearing a terminal. When it indexes your repo, opens files, or pulls in errors, it decides what goes in the window. Great results come from curating that context, not longer prompts.

That's also why a $20 Claude Pro plan is plenty here if you work like an engineer and wasteful if you work like a slot machine. Re-running a huge agent loop to fix a typo burns budget; giving the model the three relevant files and a precise ask does not. Token discipline is the same skill whether you pay the bill or the client does.

Go deeper (+10 min): tokens, pricing math, a worked budget

Rule of thumb: 1 token ≈ 4 characters ≈ 0.75 words; code and rare words run higher. Say a model bills $3 / M input tokens and $15 / M output. A turn with 1,500-token system prompt + 2,000 retrieved + 1,200 history + 100 question + 400 answer ≈ $0.02. Trivial once — until 50,000 turns/day. Now the 1,200-token history you never trimmed is a budget line. (Even at temperature 0, outputs aren't guaranteed bit-identical across hardware — "more deterministic," not perfectly so.)

FDE mindset

At a client, the first real question is never "what model should we use?" It's "what does the system actually have in front of it when it answers — and what is it missing?" Diagnose the window before the model. That's the throughline of the whole program.
