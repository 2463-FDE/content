How an LLM Actually Spends Its Attention

Week 1 · Day 1 (Mon) Phase: Foundation AI Engineering ~60–75 min incl. diagram + check Topics: context windows · token budgets · sampling · hallucination · AI coding

Every superpower and every failure of an LLM traces back to one finite resource: the context window. Today you learn to think like the model's accountant — because that is what a Forward Deployed Engineer does on day one at a client: figure out what the system can actually see, and what it's quietly missing.

The whole game

One window holds everything

An LLM has no memory between calls and no live access to your databases. For a single request, everything it can reason over must fit inside one finite context window — measured in tokens (≈ ¾ of a word in English). Nothing outside that window exists, as far as the model is concerned.

This is the most important sentence in the course: capabilities and limits both come from the window. "Can it summarize this contract?" "Why did it forget what I said?" "Why did it make that up?" — all the same question wearing different clothes. How is the window being spent?

Slice 1

The system prompt always goes first

The system prompt sets the model's role and rules. It is prepended to every request, so its cost is paid on every call. A 2,000-token system prompt on a million-request feature is a real line item — both latency and dollars.

Slice 2

Few-shot examples buy quality with tokens

Showing the model a handful of examples ("few-shot") is the cheapest way to lock in a format or tone — no fine-tuning required. But each example is more tokens in the window, every time. The FDE question is never "do examples help?" (they do) but "how few can I get away with?"

Slice 3

Retrieved context can dominate

When you paste in documents, code, or RAG results, that retrieved context is usually the biggest consumer of the window. This is the lever you'll spend Week 2 learning to pull precisely. For now: more retrieved text is not more intelligence — it's more budget spent, and it can crowd out everything else.

Slice 4 · the silent leak

Conversation history grows every turn

In a chat, the entire prior conversation is usually re-sent on each turn so the model "remembers." That means token cost grows with every message — quietly, until a long session gets slow, expensive, or starts dropping the earliest instructions off the front. Most "the assistant forgot the rules" bugs are really history eviction.

Slice 5

The user's question is just one more slice

Notice how late the actual user input arrives. By the time real intent enters the window, system prompt + examples + context + history may already have consumed most of it. The user's question is rarely the expensive part — but it competes for the same finite space as everything else.

Token budget

What's left is room to answer

The window is shared between input and output. Whatever you don't spend on input is the room left for the answer. Overstuff the input and the model is forced to truncate, rush, or stop mid-thought. A token budget is simply deciding, in advance, how many tokens each slice is allowed — so the answer always has room.

And every token is metered. Cost ≈ (input tokens + output tokens) × price-per-token. Token budgeting is cost engineering. When a client asks "why is this feature so expensive to run?", the answer lives in this picture.

Generation

Sampling decides how it answers

The model produces the answer one token at a time, each drawn from a probability distribution. Temperature and top-p control how that draw happens: low temperature → near-deterministic, picks the most likely token (good for extraction, classification, code). High temperature → more varied, sometimes more creative, less repeatable.

FDE reflex: if you need the same input to give the same output, turn temperature down. Most "flaky" AI features in production are just sampling left too hot.

Failure mode

Hallucination is a window problem first

A hallucination is a confident, fluent, wrong answer. The single most common cause: the fact the model needed was never in the window, so it filled the gap with the most plausible-sounding text. The model has no built-in way to say "I wasn't given that."

This reframes a whole category of client complaints. "Your AI lies" is usually "your retrieval missed" or "the answer got truncated." You'll fix far more hallucinations by managing the window than by swapping models.

Live diagram

AI coding: Claude Code is a window manager

You'll work all 10 weeks inside Claude Code. Here's the mental model that makes you good at it fast: it is a context-window manager wearing a terminal. When it indexes your repo, opens files, or pulls in errors, it is deciding what goes in the window for the model behind it. Great results come from curating that context, not from longer prompts.

That's also why a $20 Claude Pro plan is plenty for this program if you work like an engineer and wasteful if you work like a slot machine. Re-running a huge agent loop over your whole repo to fix a typo burns budget. Giving the model the three relevant files and a precise ask does not. Token discipline is the same skill whether you're paying the bill or the client is.

FDE mindset

An FDE shows up at a client and the first real question is never "what model should we use?" It's "what does the system actually have in front of it when it answers — and what is it missing?" You diagnose the window before you touch the model. Hold onto that; it's the throughline of the whole program.

Go deeper (optional, +15 min): tokens, pricing math, and a worked budget

Tokens aren't words. "tokenization" might be 1 token; "antidisestablishmentarianism" several. Rule of thumb: 1 token ≈ 4 characters ≈ 0.75 words in English; code and rare words run higher.

Worked example. Say a model bills $3 per million input tokens and $15 per million output tokens. A support-bot turn with a 1,500-token system prompt, 2,000 tokens of retrieved help-center docs, 1,200 tokens of chat history, a 100-token question, and a 400-token answer costs: input = 4,800 tokens → $0.0144; output = 400 tokens → $0.0060; ≈ $0.02 per turn. Trivial once — until you multiply by 50,000 turns/day. Now the 1,200-token history you never trimmed is a budget line, and Week 1 Thursday's "context compression" topic is a cost-savings project.

Determinism caveat. Even at temperature 0, outputs are not guaranteed identical across hardware/batching — "more deterministic," not "perfectly deterministic." Design eval checks for that.
