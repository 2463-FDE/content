API Integration Patterns: Calling a Model Reliably

Week 1 · Day 2 · Part 2 Surviving Production ~20 min · reading @150 wpm + diagram + check

Part 1 you picked a model and put it behind a thin interface. Now your code has to actually call it — over the network, thousands of times a day, against a service you don't control. This is where a depressing number of AI features fail: not because the model is wrong, but because the integration is naïve. Part 2 is the patterns that make a call survive production — streaming, batching, rate limits, retries with backoff and jitter, idempotency, timeouts, and graceful failure. Scroll the reading; the diagram on the right builds one resilient call and everything wrapped around it, piece by piece.

The whole game, again

Picking the model was the easy part — now you have to call it

You've chosen a model and put it behind a clean interface. Now your code has to call it, over the network, thousands of times a day, against a service you don't control. The prototype made one call in a notebook, it worked, everyone clapped. Production makes that call forty thousand times against a rate-limited, occasionally-overloaded, sometimes-slow remote API — and every weakness the notebook hid becomes a user-facing outage.

The mental shift for Part 2: an LLM API call is a network request to a shared, metered, fallible service — treat it like one. Everything you know about resilient distributed systems applies. The patterns aren't AI-specific; they're the same disciplines that make any third-party integration survive production — streaming for responsiveness, batching for throughput, respecting rate limits, retrying transient failures correctly, making retries safe, bounding how long you'll wait, and failing gracefully. LLM calls just make each matter more, because they're slower, pricier, and flakier than the average REST call.

The diagram on the right is a single resilient call and everything around it. We'll build it piece by piece: how the response comes back (stream or batch), the gate in front of the call (rate limiting), the call itself with its safety equipment (timeout, retry with backoff and jitter, idempotency), and the two ways it can end (ship the result, or fall back safely). Master it once and you reuse it on every engagement, behind whatever model you picked in Part 1. [example payload card on the diagram: a real POST /v1/messages request]

Pattern 1 · Streaming

Streaming: don't make the user wait for the last token

An LLM generates its answer one token at a time, left to right. By default the API waits until the entire answer is finished, then sends it back in one lump — so for a long response the user stares at a spinner for the full generation time, maybe ten or twenty seconds, before anything appears. Streaming changes the delivery: the API sends each token as it's produced, so text starts appearing almost immediately. Total generation time is unchanged, but perceived latency collapses, because time-to-first-token — not total time — is what the user feels.

This is why every "the AI feels slow" complaint should first be met with "are we streaming?" The familiar typewriter effect in every chat interface is streaming; without it those products would feel broken. It does cost some engineering: a streamed response arrives as a sequence of events over a long-lived connection rather than one JSON object, so your code consumes a stream and assembles the pieces. Two consequences to internalize. First, because the connection stays open for the whole generation, streaming is also how you avoid request timeouts on long outputs — a large non-streaming response can exceed a client's HTTP timeout and get killed mid-flight, which is why SDKs often require streaming above a certain output size. Second, streaming complicates error handling: a failure can happen after some tokens have reached the user, so "the request failed" is no longer a clean before-or-after — you may have a partial answer on screen. Hold that thought; it returns at error handling.

Pattern 2 · Batching

Batching: the opposite trade for work nobody is watching

Streaming optimizes the case where a human is waiting. Batching optimizes the case where nobody is. When you have a large volume of independent calls that don't need to finish right now — classify ten thousand support tickets, summarize last quarter's documents, enrich a database overnight — sending them one at a time through the synchronous API is the wrong tool. You'll fight rate limits, pay full price, and babysit a long sequential loop.

The major providers offer a dedicated batch API for exactly this: you submit a big set of requests as one job, the provider processes them asynchronously over a window (typically up to 24 hours), and you collect the results when it's done — at a substantial discount, commonly around 50% off the normal per-token price. [source: provider batch-API docs — Anthropic Message Batches / OpenAI Batch API, verified 2026-06] You trade immediacy for throughput and cost: results in hours instead of seconds, for roughly half the money and none of the rate-limit juggling.

The FDE judgment is matching the mechanism to the workload's true deadline. The instinct to make everything synchronous and instant is expensive and often pointless — if a report is read tomorrow morning, generating it in a 2 a.m. batch run for half the price is strictly better. Conversely, batching a request a user is actively waiting on would be absurd. Two practical notes carry forward. First, batch results come back keyed by an ID in no guaranteed order, so you match each result to its request by the custom ID you assigned — never by position. Second, batching sidesteps the live rate-limit dance we're about to discuss, which is half its appeal: you hand the provider the whole pile and let them pace it. Ask of every bulk job: does anyone need this in the next few seconds? If not, batch it.

Pattern 3 · Rate limiting

Rate limits: you are sharing a metered service

An LLM API is a shared resource, and the provider caps how much any one account can consume. The caps come in three flavors you'll see constantly: RPM (requests per minute), TPM (tokens per minute), and sometimes TPD (tokens per day). Exceed any of them and the API stops serving you and returns an HTTP 429, "Too Many Requests." A 429 is not a bug in your code and not an error in the usual sense — it's the provider saying "slow down, you've hit your share." Treating it as fatal, or worse, hammering harder when you see one, is the classic way to turn a brief throttle into a sustained outage.

You handle rate limits from both sides. Reactively, when a 429 comes back, you back off and retry — and the provider usually tells you exactly how long to wait, in a Retry-After header. Respecting that header is the single most important thing you can do; it's the difference between recovering in one polite pause and flailing against the wall. (The retry mechanics are the next pattern.) Proactively, you throttle yourself so you mostly don't hit the limit in the first place — a client-side rate limiter (a token-bucket, or a simple semaphore capping concurrent requests) that paces your outbound calls under the known ceiling. The diagram puts this throttle as a gate in front of the call for a reason: it's cheaper to not send a doomed request than to send it and handle the 429.

This is also where Part 1 and Part 2 connect. Rate limits are per account and per model tier, so the model you chose shapes your headroom — a smaller tier may have a roomier limit, and spreading load across tiers (cheap model for the bulk, flagship for the hard cases) spreads load across limit pools too. For an FDE, "we're getting rate-limited" should trigger a design conversation — throttle, batch, cache, or upgrade the tier — not a frantic retry loop.

Pattern 4 · Retries with backoff + jitter

Retries: the right way to handle transient failure

Networks are unreliable and shared services have bad moments. Over thousands of calls you will hit transient failures: a 429 rate limit, a 500 or 503 when the provider is briefly overloaded, a dropped connection. The defining property is that they're temporary — the exact same request, sent again a moment later, usually succeeds. So the correct response is to retry. But how you retry separates a resilient system from one that makes outages worse.

The wrong way is to retry immediately, in a tight loop. If the service is overloaded, a flood of instant retries from every client at once is precisely what keeps it overloaded — a self-inflicted denial-of-service called a "retry storm." The right way has three parts. Exponential backoff: wait longer between attempts — 1s, then 2, then 4, then 8 — giving the service room to recover. Jitter: add a small random amount to each wait, so thousands of clients that failed at the same instant don't all retry at the same instant and re-create the spike. And a bounded cap: retry a fixed, small number of times — three, maybe five — then give up and treat it as a real failure, because an unbounded loop burns money and stalls the user forever. One crucial distinction makes retries correct rather than dangerous: retry only the failures that are actually transient. A 429 or a 5xx is worth retrying — the request was fine, the service just couldn't serve it yet. A 400 (malformed request) or a 401 (bad credentials) is not — retrying a request the server already rejected as invalid will fail identically every time and just waste attempts. The retry logic has to branch on the error type. The good news: mature SDKs implement backoff-with-jitter on the right error classes for you — but you must know what they're doing, because you'll tune it, and because the next pattern is what makes any retry safe. The worked implementation is in today's deep-dive.

Pattern 5 · Idempotency

Idempotency: making it safe to retry at all

Retries introduce a subtle, dangerous question you must answer before you turn them on: what if the request actually succeeded, but the response got lost on the way back? The server did the work and charged you; the acknowledgment never arrived; your retry logic sees "no response" and sends the request again. Now the work has happened twice. For a read-only LLM call that's merely wasteful — you paid for two generations. For anything with a side effect — an agent that placed an order, sent an email, wrote a record, kicked off a payment — doing it twice is a real incident.

Idempotency is the property that doing an operation twice has the same effect as doing it once. The standard mechanism is an idempotency key: you generate a unique ID for the logical operation and attach it to the request. The first time the server sees that key it does the work and remembers the result; if a retry arrives carrying the same key, the server recognizes a duplicate and returns the original result instead of doing the work again. The retry becomes safe — at most one real execution, no matter how many times the network makes you resend.

This is why idempotency sits in the diagram attached to the call, right beside retry: they're a pair. Retry without idempotency is a loaded gun pointed at your client's data — every backoff attempt risks a duplicate side effect. Many LLM APIs support an idempotency key directly on the request for exactly this reason, and where the model is one step in a larger workflow, you carry the same discipline through your own services: assign each logical operation an ID, dedupe on it, and design every step so replaying it is harmless. The FDE rule is blunt: before you enable retries, make the thing being retried idempotent. Retries assume the operation is safe to repeat; idempotency is how you make that assumption true.

Pattern 6 · Timeouts

Timeouts: decide in advance how long you'll wait

Every call needs a deadline. Without one, a single slow or hung request can tie up a connection, a thread, or a user's patience indefinitely — and under load, a pile of stuck requests with no timeout is how one slow dependency takes down an entire service. A timeout is your explicit decision: if this call hasn't returned in N seconds, stop waiting and handle it as a failure. LLM calls make timeouts especially important because they're slow and variable — a response can legitimately take many seconds, the spread between fast and slow is wide, and the naïve defaults that work for a quick REST call are wrong here.

Setting the timeout is a judgment call you tune to the workload. Too short and you'll kill legitimate slow responses, turning a working call into a failure and a wasted retry. Too long and a genuinely hung request blocks resources far past usefulness. An interactive feature wants a tighter deadline (a user won't wait 60 seconds anyway); a batch or long-generation job can afford a generous one. The key is that it's a deliberate number, not whatever the library defaulted to.

Two LLM-specific traps. First, the streaming gotcha from Pattern 1: many HTTP clients implement "timeout" as a per-chunk read timeout that resets every time a byte arrives, not a total wall-clock cap. On a streamed response that trickles tokens slowly, such a timeout may never fire even though the call has dragged on for minutes — so for a hard overall deadline you often track elapsed time yourself at the loop level, not trust a single setting. Second, timeouts compose with retries: your true worst-case wait is the timeout multiplied by the number of attempts (plus the backoff delays). A 30-second timeout with three retries can mean a user waiting well over a minute — so set both numbers together, with the total experience in mind.

Pattern 7 · Graceful error handling

Graceful failure: never let a broken call reach the user raw

Everything so far reduces how often calls fail and how safely you retry. The last pattern decides what happens when, despite all of it, a call still fails — because at scale, some will. The amateur integration lets the exception bubble up and the user sees a stack trace, a spinner that never resolves, or a blank screen. The professional integration has decided, in advance, what failure looks like to the user, and it's never raw. It starts with a taxonomy, because each class is handled differently — but the instinct to wrap everything in one catch-all is exactly the trap:

The classes: a transient error (429, 5xx, dropped connection) → retry with backoff (Pattern 4); a client error (400, 401) → don't retry, fix the request or fail fast; a timeout → treat as failure after the deadline (Pattern 6); a content outcome like a safety refusal → a real, expected response type to branch on, not a crash; and still-failing-after-retries → the genuine dead end this pattern exists for. For that dead end, you define a fallback — the deliberate "what we do when nothing worked": a graceful message ("the assistant is unavailable — here's how to reach a human"), a handoff to a deterministic non-AI path, a cached or default result, or falling back to a different model (the Part 1 portability seam paying off — a clean interface lets you retry on a backup model).

Two refinements for systems that call a lot: a circuit breaker that, after repeated failures, stops sending requests for a cooldown instead of retrying into a wall — protecting both you and the struggling provider; and, recalling Pattern 1, a plan for partial streamed output, since a failure mid-stream may leave half an answer on screen that you must either complete or cleanly retract. The unifying principle is Day 4's, restated for the network layer: "no answer, cleanly handled" always beats "a wrong answer or a crash, delivered raw." A user told the feature is briefly unavailable is mildly annoyed; a user shown a traceback, or left on a dead spinner, has lost trust in the product — and your client has lost trust in you. The resilient call in the diagram ends in exactly two places: a result you ship, or a fallback you chose. It never ends in an exception the user sees.

Your tools

Your tooling is your first resilient-integration test

Both halves of today are things you're already living. You've already made a model-selection decision under constraints, and Part 2's patterns show up every day. Every time Claude Code streams a long answer you read it as it arrives instead of waiting (streaming). Every time you hit a usage limit you pace yourself instead of hammering retries (rate limits + backoff). Every time a long agentic run times out you decide whether to retry the whole thing or fall back to doing the step by hand (timeouts + fallback). Working like an engineer — choosing the right model and calling it resiliently — makes your tooling last; working carelessly — flagship on everything, re-running giant loops on every transient blip — burns through it fast.

FDE mindset

A client will ask two questions that sound separate: "which AI should we use?" and "why does the AI feature keep breaking?" They're the two halves of Day 2. The first (Part 1) is a six-axis trade-off you decide and document. The second is almost never the model's fault — it's a missing timeout, an unbounded retry, a non-idempotent side effect, an un-throttled rate limit, or an error that reached the user raw. The FDE who can pick the right model and wrap it in a call that survives production is delivering the whole job — the consulting decision and the engineering that makes it hold.

Deep dive: the resilient-call loop

Optional. ~6 minutes. Part 2's seven patterns, assembled into one function.

Backoff + jitter on transient errors only, bounded attempts, an idempotency key so a retry can't double a side effect, a deliberate timeout, and a fallback so failure never reaches the user raw:

def call_model(request, *, max_tries=4, base=1.0, cap=30.0, timeout=20.0):
    idem_key = request.idempotency_key or new_uuid()   # safe to retry
    for attempt in range(max_tries):
        try:
            return model.call(request, key=idem_key,    # one logical op
                              timeout=timeout)           # bounded wait
        except RateLimited as e:                         # 429
            delay = e.retry_after or backoff(attempt, base, cap)
        except (ServerError, ConnectionDropped):         # 5xx / network
            delay = backoff(attempt, base, cap)          # transient → retry
        except (BadRequest, Unauthorized):               # 400 / 401
            raise                                        # NOT transient → stop
        sleep(delay)
    return fallback(request)        # exhausted → fail safe, never crash

def backoff(attempt, base, cap):
    raw = min(cap, base * (2 ** attempt))    # exponential: 1,2,4,8...
    return random.uniform(0, raw)            # full jitter — spread the herd

Five things make it production-grade: it retries only transient errors (4xx falls straight through); it honors the server's Retry-After when given; backoff is exponential with jitter so simultaneous failures don't re-spike together; the same idempotency key rides every attempt so at most one real execution happens; and every path that isn't a clean result lands in fallback(). Worst-case wait ≈ timeout × max_tries plus the backoff delays — set those two numbers together, with the user's experience in mind. This is the seam from Part 1: swap the model inside model.call and the whole resilient wrapper keeps working.
