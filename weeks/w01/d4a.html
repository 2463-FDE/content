Token Optimization: Trim the Window Before You Call

Week 1 · Day 4 · Part 1 Cost Engineering ~17 min · reading @150 wpm + diagram + check

Day 1 gave you the mental model: the context window is a finite budget, and every token in and out is metered. Today you turn that model into the first discipline a Forward Deployed Engineer gets paid for — making each call cost less without losing quality. Four levers do it: prompt caching, context compression, dynamic prompt assembly, and the cost tracking that proves any of it worked. Scroll the reading; the panel on the right builds one pipeline — raw context entering at the top and physically shrinking step by step until a lean, cheap call falls out the bottom. Part 2 (next page) takes what comes back and makes it trustworthy.

The whole game

Cost comes from the window, just like capability did

On Day 1 we said the same sentence until it stuck: capabilities and limits both come from the window. Today there's a sequel, and it's the one that shows up on the client's invoice: cost comes from the window too. Every token you place in the window is a token you pay for and a token that can be spent well or wasted. Every token the model generates back is a token you pay for. The base unit never changes — cost ≈ (input tokens + output tokens) × price-per-token — so spending fewer tokens for the same answer is, quite literally, the whole game of Part 1.

So far this week you've been getting things to work. Today is about getting them to work affordably — a different bar. A prototype that answers correctly in the playground and a feature that runs ten thousand times a day for a paying client are separated almost entirely by this page. The prototype ignores cost because it runs twice; production lives and dies by cost because it runs constantly, and at that volume a two-cent call becomes a line item with a year's worth of zeros behind it.

Four levers, taught together because they interact. Prompt caching — stop paying for the same prefix twice. Context compression — carry a smaller representation of what you must carry. Dynamic assembly — include only what this call needs. And cost management — measure all three, because you can't optimize what you don't track. The diagram on the right is the pipeline: everything you could send enters wide at the top, and each lever trims it narrower until the metered call is lean. Walk the levers one at a time.

Lever 1 · Prompt caching

Prompt caching: stop paying for the same prefix twice

Recall the Day 1 picture: the system prompt, the few-shot examples, and a big chunk of retrieved context are the same on almost every call. Your support bot's 1,500-token system prompt doesn't change between requests. The product manual you paste in for grounding doesn't change. Yet by default you pay full price to send and re-process that identical text on every single request. That's the waste prompt caching exists to kill.

Prompt caching lets the provider remember a chunk of your prompt — a prefix — so that on the next call it can reuse the already-processed version instead of re-reading it from scratch. You mark where the stable part ends, and subsequent requests that share that exact prefix get it served from cache. The economics are the whole point: a cached read costs only a fraction of the normal input price, while the first write costs slightly more than normal to populate the cache. As of June 2026, on Anthropic's API a cache read is billed at roughly 0.1× the base input price — about a 90% discount on the cached portion — while the cache write costs about 1.25× for the short (5-minute) lifetime or 2× for the one-hour lifetime. [source: Anthropic prompt-caching docs, platform.claude.com/docs/en/build-with-claude/prompt-caching, verified 2026-06-28]

Run the arithmetic and the discipline becomes obvious. Cache a 10,000-token stable prefix. The first call pays ~1.25× to write it; every call after pays ~0.1× to read it instead of 1×. With the 5-minute cache you break even after just two requests (1.25 + 0.1 = 1.35 versus 2.0 if you hadn't cached), and from the third request on it's nearly free. For a feature handling thousands of requests an hour against a fixed manual, caching routinely cuts the input bill by the better part of an order of magnitude.

But there is one rule you must internalize, because it is the source of nearly every "why isn't my cache working?" bug: caching is a prefix match, and any byte change anywhere in the prefix invalidates everything after it. Put a datetime.now() timestamp, a per-request UUID, or the user's name near the top of your system prompt and the prefix differs on every call — so nothing ever caches, you pay the write premium forever, and you get zero reads.

The fix is structural: keep stable content first (frozen system prompt, deterministic tool list, the manual), and push anything volatile — the user's question, the timestamp, the session ID — to the end, after the cache boundary. You confirm it's working by reading the cache-read usage field the API returns; if that number is zero across repeated identical-prefix calls, a silent invalidator is hiding in your prefix.

Lever 2 · Context compression

Context compression: shrink what you carry

Day 1's "silent leak" was conversation history: every turn re-sends the entire prior conversation, so a long chat gets slower and more expensive the longer it runs, and eventually the oldest tokens — often your rules — fall out of the window. Context compression is the family of techniques that fights this directly. The idea is simple: don't carry raw history verbatim when a smaller representation would do.

The most common move is summarization. After a conversation grows past some threshold, replace the oldest N turns with a compact summary — "User is troubleshooting a failed payment on order #4471; card confirmed valid; agent has checked the gateway log" — and keep only the recent turns verbatim. Twenty turns that cost 4,000 tokens to resend become a 300-token summary plus the last two turns. The model keeps the thread without you paying to re-transmit every word on every turn. Providers increasingly offer this server-side, but the principle is yours to own whether the platform does it for you or not.

Compression also applies to retrieved context, which Day 1 flagged as usually the biggest consumer in the window. If retrieval pulls back a 5,000-token document but the answer lives in two paragraphs, sending the whole document pays for 4,600 useless tokens and buries the signal in noise. The FDE judgment call with any compression is fidelity versus cost. Summarize too aggressively and you drop a detail the model needed three turns later — now you've saved tokens and broken the feature. The skill is choosing what is safe to compress (resolved sub-topics, pleasantries, redundant confirmations) and what must stay verbatim (the user's stated constraints, IDs, numbers, the active task). Remember the Day 1 line: more retrieved text is not more intelligence; it's more budget spent. A good summary is lossy on purpose, but lossy in the right places.

Lever 3 · Dynamic assembly

Dynamic prompt assembly: include only what this call needs

The beginner builds one giant prompt template — every instruction, every tool description, every example, every possible piece of context — and sends it on every request because it's easier than deciding. The practitioner assembles the prompt dynamically, deciding per request what actually belongs in the window this time. This is the same instinct as Day 1's "precision of retrieval," applied to the whole prompt rather than just the documents.

Concretely: if the user's question is about billing, you don't need the 800 tokens of shipping-policy instructions in the window — route them out. If the model has fifteen tools available but this request can only plausibly use two, sending all fifteen tool schemas pays for thirteen the model will never call — and worse, gives it more ways to pick wrong. If a few-shot example is only useful for one kind of request, include it only for that kind. Dynamic assembly means the prompt is built from parts, and you select the parts the current request actually justifies.

There's a tension you have to hold, and it's why this comes after caching in the day: dynamic assembly and prompt caching pull against each other. Caching wants the prefix byte-for-byte identical so it can be reused; dynamic assembly wants the prompt to vary per request. The resolution is layering — keep a stable core (system prompt, the tools you always offer) at the front where it caches, and do your dynamic selection after the cache boundary. You get the cache discount on the stable part and the leanness of dynamic assembly on the variable part. That's why these levers are taught together, not in isolation.

Lever 4 · Cost management

Cost management: you can't optimize what you don't measure

All three levers above are guesses until you measure them. Cost management is the discipline of actually tracking what your AI features spend — the one that turns "the AI feature is expensive" (a vibe) into "the summarization endpoint costs $0.018 per call and runs 40,000 times a day, which is $720/day, and 60% of that is the uncached manual" (an action item). Clients ask the vibe question constantly. Your value is answering with the number. Run a feature's math yourself:

The base unit never changes from Day 1: cost ≈ (input + output tokens) × price-per-token, with input and output billed at different rates and output usually the pricier. As of June 2026, a mid-tier model like Claude Sonnet 4.6 runs about $3 / M input and $15 / M output, while a top-tier Opus model is roughly $5 / $25. [source: Anthropic model pricing, claude-api reference catalog, cached 2026-06-04] Those exact numbers will drift — always re-verify — but the shape is durable: output costs several times more than input, so a feature that generates long responses has a very different cost profile than one that extracts a single label.

The non-obvious part is the granularity of your tracking. A single aggregate "we spent $1,200 last month" tells you nothing actionable. The numbers that drive decisions are sliced three ways. Per feature: which endpoint is the cost center? Often one feature is 80% of the bill, and that's where every optimization dollar should go. Per user (or per tenant): is one power user or enterprise account driving spend? This is what makes usage-based pricing and rate limits possible, and what catches a runaway loop before it becomes a five-figure surprise. Per run: for an agent or multi-step pipeline, how much did this one task cost across all its internal calls? A single user request that fans out into twelve model calls can cost 50× what the user assumes.

You get these numbers from the usage data the API returns on every response — input tokens, output tokens, and crucially the cached-versus-uncached breakdown. Log them, tag each call with the feature and user it belongs to, and you have a cost dashboard. That dashboard is what lets you say, with a straight face, "we cut this feature's cost 70% by caching the manual" — and prove it. Cost management isn't a finance chore bolted on at the end; it's the feedback loop that tells you whether the other three levers actually worked.

Your tools

Your tooling rewards exactly these habits

Everything in Part 1 maps directly onto how you'll actually work this program. Token discipline here isn't an inconvenience — it's the same discipline a client pays an FDE to bring. The habits are identical at every scale.

When you point Claude Code at the three files that matter instead of re-indexing the whole repo, that's dynamic assembly — including only what the task needs. When you keep a tight, stable set of project instructions Claude Code can reuse across a session, you're leaning on caching. When you summarize a long debugging thread instead of letting it balloon, that's compression. Working like an engineer makes these tools go far; working carelessly — re-running giant agent loops to fix a typo — wastes that headroom fast.

FDE mindset

When a client asks "why is this AI feature so expensive?", they expect a hand-wave. Your value is the opposite: a per-feature, per-user, per-run number, and a named lever for each. Cost engineering is just disciplined management of the window — cache the stable part, compress the bulky part, assemble only what's needed, and measure all of it. The FDE who can show the client the cost number and the change that moved it is the one who gets the next contract. Carry the lean call into Part 2, where you make what it returns trustworthy.

Deep dive: the cost math behind the levers

Optional. ~6 minutes. The numbers under today's picture.

1 · What caching actually saves. Caching is a prefix match billed in two parts: a cache write (slightly more than normal input price) and cache reads (a small fraction of it). As of June 2026 on Anthropic's API, a read is ~0.1× base input price and a write is ~1.25× (5-min cache) or ~2× (1-hour cache). [Anthropic prompt-caching docs, verified 2026-06-28] Caching only kicks in above a minimum prefix size (roughly 1,024–4,096 tokens depending on model) — shorter prefixes silently won't cache.

Worked example — caching a 10,000-token stable prefix (5-min cache)
  • Uncached: every call pays 1× → 10 calls = 10.0 prefix-equivalents
  • Cached: 1 write (1.25×) + 9 reads (0.1× each = 0.9) = 2.15 for the same 10 calls
  • That's a ~78% cut on the prefix across 10 calls — and savings only grow with volume

Break-even is fast: by call 2, cached (1.25 + 0.1 = 1.35) already beats uncached (2.0). The one rule: a timestamp/UUID/username near the top of the prefix changes it every call → 0 reads, and you pay the write premium forever. Keep volatile content after the cache boundary.

2 · A per-feature cost model. Base unit unchanged from Day 1: cost = (input × in_price) + (output × out_price). Take a support-bot turn at Sonnet-class pricing (~$3 / M input, $15 / M output as of June 2026 [claude-api catalog, cached 2026-06-04]):

One turn, then at scale
  • System prompt 1,500 + manual 3,000 + history 1,200 + question 100 = 5,800 input
  • Answer = 400 output
  • Input 5,800 → $0.0174 · Output 400 → $0.0060 · ≈ $0.023 / turn
  • × 40,000 turns/day = ~$920/day. Cache the 4,500-token system+manual prefix and the input bill on cached calls drops ~90% of that portion → roughly $300–$400/day saved.

Now slice it: per feature (this endpoint is 80% of the bill), per user (one tenant driving 40% of turns), per run (an agent task that fans out to 12 calls costs ~$0.28, not $0.023). You get every number from the usage fields on each response — log them, tag them, and you have a dashboard you can defend to the client.

The four levers compose: caching kills the repeated-prefix bill, compression shrinks the bulky middle, dynamic assembly drops what this call doesn't need, and cost tracking proves which one moved the number. The lean call that falls out the bottom is the one you make resilient in Part 2.
