Putting It Together: Build a Production LLM API Client

Week 1 · Day 5 Build & Assessment Day ~20 min · build-day reading @150 wpm + diagram + check

Four days of ideas — the context window, model selection, resilient API calls, prompting, token budgets, output guardrails — collapse into one artifact today: a small piece of code that sits between your application and a model and behaves itself in production. That's the LLM API client, and building one is your Week-1 milestone. This is a build day, so the reading is short: it hands you the blueprint and frames the three things you'll turn in — the client, a code review, and a prompt library. Scroll it once; the diagram on the right assembles the client layer by layer as you go.

The whole game

The client is a seam you own

Everything this week pointed at a single object. When an application "uses an LLM," it almost never calls the provider's raw endpoint from twelve scattered places — it calls one well-defined component, a client, the only thing in your codebase that knows how to talk to a model. Every prompt, every retry, every token decision, every guardrail lives behind that one door.

Why is that the whole milestone? Because the client is a seam — a deliberate boundary between your application's intent and the messy, metered, flaky world of a model API. A good seam means you can change models, add a retry, tighten a budget, or redact a log line in one file instead of forty; a bad one — raw API calls sprinkled through controllers and React handlers — makes each a hunt-and-replace and every bug a fresh investigation. At a client site this seam is often the first thing you build, because everything else depends on it.

So today isn't "learn ten new things." It's "take the ten you already learned this week and put each in its proper layer." The word doing the work is production: a notebook that calls a model and prints the result works on your machine, on a good network, with one user; a production client is that same idea hardened against everything that goes wrong once it's real — the network drops, the provider rate-limits you, the model returns slightly-off JSON, a log file lands somewhere it shouldn't. Each layer absorbs one of those realities, and every later week — RAG, agents, evaluation — inherits this seam's reliability or its fragility. The diagram starts where the client does: with config.

Layer 1 · config

Configuration, and where the key lives

Start at the bottom, with the least glamorous layer that quietly causes the most incidents: config. Your client needs to know which model to call, what defaults to use (temperature, max tokens, timeout), and — the part people get wrong — where the API key comes from. The answer never changes: the key is read from the environment (env var, secrets manager, vault), and is never written into source, committed to git, pasted into a prompt, or printed to a log. That's not paranoia; a key hardcoded "just to test it" gets committed, pushed, and scraped within hours.

Config is also where Tuesday's model choice lives — small and fast for classification, larger for hard reasoning — so swapping it later is a one-line change rather than a string-literal archaeology dig. And there's a subtler reason config matters on a forty-hour week with a twenty-dollar plan: defaults are where waste hides. A timeout left at the SDK's generous default lets one hung request tie up a worker; an unbounded max-output lets a runaway answer cost many times the task; a middling temperature turns a deterministic extraction into a "flaky" bug. State your intentions here — short timeout, bounded output, temperature matched to the task — not whatever the library shipped.

Layer 2 · adapter

The model adapter: one interface, many models

On top of config sits the adapter — the layer that hides the provider behind an interface you define. Your application code should never say "call this provider's chat endpoint with this JSON shape." It says client.complete(messages, options) and doesn't care what's underneath; the adapter translates that clean call into whatever the SDK wants and translates the response back into a shape your app understands.

Keep the adapter thin: its job is translation, not business logic. Thinness buys the thing that matters most for testing — it makes the model a replaceable dependency. If your app calls the provider directly, every test of that code also calls the provider, so the suite is slow, costs money on every run, and flakes on network hiccups. Swap in a fake adapter that returns a fixed answer and you can assert "given this model response, does my code do the right thing?" thousands of times for free. The interface you draw here is the contract the team programs against — design it for the caller's convenience, not the provider's quirks.

Layer 3 · request builder

Building the request, on a token budget

Now the layer where Monday and Thursday collect their debt. The request builder assembles the call: it stacks the system prompt, few-shot examples, retrieved context, conversation history, and the user's message into the message list — and as it does, it enforces the token budget you learned on Day 1 and practised on Day 4.

This is where budgeting becomes code. The builder counts tokens as it assembles, and when the inputs would crowd out the answer, it decides what gives: trim the oldest history, cap retrieved context to the top few chunks, and always reserve room for the output. That decision is centralized here, not an accident when the provider silently truncates an overflowing request. Budgeting deliberately is the difference between "our AI feature costs a predictable amount" and "nobody knows why the bill tripled last Tuesday."

The request builder is also where your prompts live. Rather than building prompt strings inline at the call site, good clients pull them from a prompt library — named, versioned, reusable templates with marked slots for the variable parts. We come back to that at the end; submitting one is part of Friday's hand-in.

Layer 4 · resilient transport

The network will fail — plan for it

Here is the layer that separates a demo from a product. The moment your client leaves your laptop it talks to a remote service over a network, and remote services fail: they rate-limit you (HTTP 429), throw transient server errors (500/502/503), time out, drop the connection mid-stream. At any real volume these happen daily. A client that assumes the happy path is a client that pages someone at 2 a.m.

The resilient transport layer wraps the call with Tuesday's patterns: a sensible timeout so a hung request doesn't hang your app; retries on the failures worth retrying (transient 429s and 5xxs) but not on the ones that aren't (a 400 fails identically every time); and exponential backoff with jitter, so a briefly-overloaded provider gets room to recover and a fleet of your own clients doesn't retry in lockstep into a stampede. Two more reflexes. First, idempotency: if a request might have succeeded before your connection dropped, blindly retrying can double-charge you or duplicate a side effect. For pure text generation that's just wasted tokens, but the instinct — "is it safe to retry this exact operation?" — is one you'll need constantly once tools and actions enter in later weeks; build it on the easy case now. Second, knowing when to stop: retries are bounded, and when the client gives up it fails in a way the app can handle — a clear error, a fallback, a queued retry-for-later — never an unhandled exception. The right answer to a 429 is to slow down, not push harder — which makes your client a good citizen of the API and keeps the whole system stable under load.

Layer 4b · streaming

Streaming changes the feel and the failure modes

Transport has a second mode to support deliberately: streaming. Instead of waiting for the whole answer in one lump, a streaming call returns tokens as the model generates them, so the user sees text within a fraction of a second — a far better experience for anything chat-like, because time-to-first-token is what people actually feel, not total completion time.

But streaming isn't free; it reshapes error handling. A non-streaming call succeeds or fails cleanly; a stream can fail halfway, leaving half an answer on screen — so the client must decide whether to discard the partial and retry or keep it. Streaming also makes cancellation matter: if the user navigates away, stop the stream and stop paying for tokens you'll never show. And it complicates the next layer — you can't validate an answer that hasn't finished arriving, so you often buffer, then validate the complete result. The FDE judgment call is simple: stream the things humans watch in real time; don't bother streaming a classification or a JSON object headed for another system. Match the mode to who's on the other end.

Layer 5 · validator / guardrail

Never trust the output unverified

The model has answered. The most important word in this reading is the next one: verify. A model's output is a suggestion, not a guarantee — text shaped like an answer, produced by a system with no built-in way to know if it's correct, complete, or even in the format you asked for. The validator / guardrail layer is where Thursday's lesson stops a bad answer from reaching a user.

Concretely: if you asked for structured output — JSON with specific fields, a value from a fixed set — then parse it and validate it against a schema before anything downstream touches it. Did the JSON parse? Are the required fields present? Is priority really one of low / medium / high and not the model's creative fourth option? On failure the client has options, in order of preference: retry once with a corrective instruction, fall back to a safe default, or surface a clear error — but it must never silently pass malformed output forward.

Guardrails go beyond format: strip outputs that leak the system prompt, block disallowed content, confirm a cited source exists, bound the length. Monday's model holds — a confident wrong answer is the model filling a gap, and the validator is your structured refusal to let that gap become the user's problem. On most real AI features this is the single layer that most determines whether the thing is safe to ship. Treat every model response as untrusted input — because it is.

Layer 6 · logging

Log everything that helps — leak nothing that hurts

The top layer is observability, and it carries a sharp edge. You need logging: when an AI feature misbehaves, the logs are the only way you'll reconstruct what happened. Log what lets you debug and cost-account — latency, input/output token counts (your live cost meter), model and parameters, retry counts, validation failures, error codes, and a request id to correlate across systems.

And here is the edge: what you must never log. Never the API key — not a fragment, not in an error message, not in a "here's the request we sent" debug dump. Never raw PII if your domain has any — at a federal client, prompts may carry names, case numbers, or sensitive records, and a log file is a copy of that data with weaker access controls than the source. Log shapes and metrics, not contents: "received a 1,240-token prompt, returned 380 tokens in 1.9s" is gold; dumping the full prompt with someone's SSN in it is an incident. When you do need content to debug, redact first — make redaction the default, not the thing you remember to add.

One pattern ties it together. Attach a request id to every call and carry it through, so one log line captures id, model, tokens in and out, latency, retries, and outcome. When something breaks, you pull that id and see the whole life of the request — the difference between "we think it's the retrieval step" and "request abc123 spent 4,800 input tokens and timed out after two retries." And every token count you log turns "the AI is expensive" from a complaint into a costed plan.

The Friday lens

How to review LLM-integration code

The client is built. Now the other half of today: the code review — its own skill, because the failure modes aren't the ones you look for in ordinary code. Tests passing tells you almost nothing here: a client can pass every unit test and still leak keys, retry a non-idempotent action, or pass unvalidated JSON to production. So you review against a specific set of questions that map onto the layers you just built. Here's a wrapper a teammate wrote:

goes straight to the caller — output is never parsed, schema-checked, or guarded. Tag each comment with its layer ('Transport: no timeout here') so the author knows exactly where to look.">

That single snippet hits five layers; a real client hides them better. Walk the layers as a checklist. Config: key from the environment, no path where it leaks? Adapter: the provider isolated, or a raw call in a controller? Request builder: a real token budget, or "hope it fits"? Prompts from the library or hardcoded? Transport: timeouts and bounded backoff limited to retryable errors, nothing non-idempotent retried? Validator: output parsed and schema-checked? Logging: could any secret or PII reach a log? Then the cross-cutting one: what happens on the unhappy path — timeout, 429, malformed response — and is it tested with a fake model so the suite doesn't burn tokens or flake? Two habits keep comments useful: tag each by layer, and separate "this is wrong" from "this is style" — a leaked key blocks; a naming preference is a nice-to-have. The Deep-dive card holds both checklists — use it as your literal checklist Friday, on your code and your partner's.

Deliverable · the prompt library

Build a prompt library, not a pile of strings

One deliverable deserves its own moment: the prompt library. By Friday you've written a lot of prompts, and the temptation is to leave them as string literals jammed into the calling code. Resist it. A prompt is a piece of engineering: it has a job, it can be wrong, it gets revised — so when you change it you want to know what changed and why. That earns it the same care as any versioned asset.

A prompt library is just prompts pulled into named, reusable templates with clear slots for the variable parts — classify_ticket, extract_invoice_fields, summarize_with_citations — each documented with what it's for, which model it was tuned against, and an example of good input and output. The benefits compound: prompts get reused instead of re-invented in five places; a partner can improve one without grepping the codebase; and the few-shot examples and format rules you fought for on Days 3 and 4 are captured where the next person finds them. Your Friday submission is a small library like this — a handful of your best prompts, organized so someone else could pick them up and run them without you in the room. That "someone else" mindset is the entire job.

FDE mindset

Notice what every layer today shared: it assumes the model and the network are untrustworthy, and it puts the trustworthiness in the code you wrote around them. That's the whole posture of an FDE shipping AI — you don't ask the model to be reliable, you build a client that stays reliable even when the model isn't. You can't babysit a flaky integration; you build it to behave, then trust it. Ship the client, review it honestly, hand in your prompt library — and then fill out the Week 1 survey (the link is in the sidebar). Your numbers are how we keep the next four weeks calibrated to where you actually are.

Reference: client blueprint & code-review checklist

Keep this open during the Friday build and review. Two checklists — one to build against, one to review against.

LLM API client — build checklist
  • Config — model id, default params, and timeout in one place; API key loaded from the environment; fail loudly at boot if the key is missing.
  • Model adapter — one interface (complete() / stream()) that hides the provider; thin (translation only, no business logic); fakeable for tests.
  • Request builder — assembles system + examples + context + history + user message; enforces a token budget (count, trim, reserve room for the answer); pulls prompts from the library, not inline strings.
  • Resilient transport — timeout on every call; retry only transient failures (429 / 5xx), never 4xx; exponential backoff + jitter; aware of idempotency.
  • Streaming — supported where a human is watching; handles mid-stream failure and cancellation; buffer-then-validate for structured output.
  • Validator / guardrail — parse + schema-check structured output; on failure retry-with-correction, fall back, or error — never pass malformed output forward; enforce content/length/leak guards.
  • Logger — latency, token counts, model+params, retries, errors, request id; never the API key or raw PII; redact by default.
Reviewing LLM-integration code — what to look for
  • Secrets — key from env only? No path where it gets logged, committed, or echoed in an error?
  • Isolation — all model calls behind the adapter? Any raw provider call leaking into app code?
  • Budget — real token budgeting, or "hope it fits"? Prompts from the library or hardcoded?
  • Resilience — timeouts present? Retries bounded, backed-off, and limited to retryable errors? Anything non-idempotent being retried?
  • Validation — structured output parsed and checked against a schema before use? Failure path defined?
  • Logging hygiene — could any secret or PII reach a log line?
  • Unhappy path tested — timeout / 429 / malformed-response covered, using a fake model so tests don't spend tokens or flake?

Review etiquette. Review the code against these questions, not against "does it run." A client that passes every test can still leak a key or trust a hallucination. Lead each comment with the layer ("Transport: no timeout here") so the author knows exactly where to look, and say plainly which findings block and which are optional.
