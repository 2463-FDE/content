Token Optimization & Output Guardrails

Week 1 · Day 4 Cost Engineering & Reliability ~75 min · reading @150 wpm + 2 diagrams + check

Day 1 gave you the mental model: the context window is a finite budget, and every token in and out is metered. Today you turn that model into two engineering disciplines a Forward Deployed Engineer gets paid for — making each call cost less (prompt caching, context compression, dynamic assembly, spend tracking) and making each response trustworthy (schema validation, retry-on-invalid, hallucination mitigation, refusal/fallback handling). Part 1 · Token optimizationSpend fewer tokens for the same quality — trim the window before you call.
The whole game

Cost and trust are the two bills you always pay

On Day 1 we said the same sentence three times until it stuck: capabilities and limits both come from the window. Today there's a sequel, and it's the one that shows up in the client's invoice and in the client's complaints folder: cost and reliability both come from the window too. Every token you place in the window is a token you pay for and a token that can be spent well or wasted. Every token the model generates back is a token you pay for and a token you have to decide whether to trust.

So far this week you've been getting things to work. Today is about getting them to work affordably and safely enough to put in front of a real user — which is a different, harder bar. A prototype that answers correctly in the playground and a feature that runs ten thousand times a day for a paying client are separated almost entirely by the material on this page. The prototype ignores cost because it runs twice; production lives and dies by cost because it runs constantly. The prototype trusts the model's output because a human is reading every word; production has to assume nobody is watching and the output flows straight into a database, an email, or another system.

Two threads run through everything today. The first is cost engineering: spend fewer tokens for the same quality. The second is output guardrails: never let an unverified, malformed, or fabricated response leave the building. They're separate skills, but they share one root — both are just disciplined management of what goes into the window and what you do with what comes out. Hold that, and the rest of the day is detail.

Cost lever 1

Prompt caching: stop paying for the same prefix twice

Recall the Day 1 picture: the system prompt, the few-shot examples, and a big chunk of retrieved context are the same on almost every call. Your support bot's 1,500-token system prompt doesn't change between requests. The product manual you paste in for grounding doesn't change. Yet by default you pay full price to send and re-process that identical text on every single request. That's the waste prompt caching exists to kill.

Prompt caching lets the provider remember a chunk of your prompt — a prefix — so that on the next call it can reuse the already-processed version instead of re-reading it from scratch. You mark where the stable part ends, and subsequent requests that share that exact prefix get it served from cache. The economics are the whole point: a cached read costs only a fraction of the normal input price, while the first write costs slightly more than normal to populate the cache. As of June 2026, on Anthropic's API a cache read is billed at roughly 0.1× the base input token price — about a 90% discount on the cached portion — while the cache write costs about 1.25× for the short (5-minute) cache lifetime or 2× for the longer one-hour lifetime. [source: Anthropic prompt-caching docs, platform.claude.com/docs/en/build-with-claude/prompt-caching, verified 2026-06-28]

Run the arithmetic and the discipline becomes obvious. Cache a 10,000-token stable prefix. The first call pays ~1.25× to write it; every call after that pays ~0.1× to read it instead of 1×. With the 5-minute cache you break even after just two requests (1.25 + 0.1 = 1.35 token-equivalents versus 2.0 if you hadn't cached), and from the third request on it's nearly free. For a feature handling thousands of requests an hour against a fixed manual or system prompt, caching routinely cuts the input bill by the better part of an order of magnitude.

But there is one rule you must internalize, because it is the source of nearly every "why isn't my cache working?" bug: caching is a prefix match, and any byte change anywhere in the prefix invalidates everything after it. Put a datetime.now() timestamp, a per-request UUID, or a user's name near the top of your system prompt and the prefix is different on every call — so nothing ever caches, you pay the write premium forever, and you get zero reads. The fix is structural: keep the stable content first (frozen system prompt, deterministic tool list, the manual), and push anything volatile — the user's actual question, the timestamp, the session ID — to the end, after the cache boundary. You confirm it's working by reading the usage field the API returns for cache reads; if that number is zero across repeated identical-prefix calls, a silent invalidator is hiding in your prefix.

Cost lever 2

Context compression: shrink what you carry

Day 1's "silent leak" was conversation history: every turn re-sends the entire prior conversation, so a long chat gets slower and more expensive the longer it runs, and eventually the oldest tokens — often your rules — fall out of the window. Context compression is the family of techniques that fight this directly. The idea is simple: don't carry raw history verbatim when a smaller representation would do.

The most common move is summarization. After a conversation grows past some threshold, replace the oldest N turns with a compact summary — "User is troubleshooting a failed payment on order #4471; confirmed card is valid; agent has checked the gateway log" — and keep only the recent turns verbatim. Twenty turns of back-and-forth that cost 4,000 tokens to resend become a 300-token summary plus the last two turns. The model keeps the thread of the conversation without you paying to re-transmit every word of it on every turn. Providers increasingly offer this server-side (the API condenses old context automatically as you approach the limit), but the principle is yours to own whether the platform does it for you or not.

Compression also applies to retrieved context, which Day 1 flagged as usually the biggest consumer in the window. If your retrieval step pulls back a 5,000-token document but the answer lives in two paragraphs, sending the whole document is paying for 4,600 useless tokens and burying the signal in noise. Compressing retrieved context — extracting the relevant passages, stripping boilerplate, dropping near-duplicate chunks — is one of the highest-leverage cost moves you'll make in Week 2's RAG work. Remember the Day 1 line: more retrieved text is not more intelligence; it's more budget spent.

The FDE judgment call with any compression is fidelity versus cost. Summarize too aggressively and you drop a detail the model needed three turns later — now you've saved tokens and broken the feature. The skill is choosing what is safe to compress (resolved sub-topics, pleasantries, redundant confirmations) and what must stay verbatim (the user's stated constraints, IDs, numbers, the active task). A good summary is lossy on purpose, but lossy in the right places.

Cost lever 3

Dynamic prompt assembly: include only what this call needs

The beginner builds one giant prompt template — every instruction, every tool description, every example, every possible piece of context — and sends it on every request because it's easier than deciding. The practitioner assembles the prompt dynamically, deciding per request what actually belongs in the window this time. This is the same instinct as Day 1's "precision of retrieval", applied to the whole prompt rather than just the documents.

Concretely: if the user's question is about billing, you don't need the 800 tokens of shipping-policy instructions in the window — route them out. If the model has fifteen tools available but this request can only plausibly use two, sending all fifteen tool schemas is paying for thirteen the model will never call, and worse, giving it more ways to pick wrong. If a few-shot example is only useful for a particular kind of request, include it only for that kind of request. Dynamic assembly means the prompt is built from parts, and you select the parts the current request actually justifies.

There's a tension you have to hold here, and it's the reason this comes after caching in the day: dynamic assembly and prompt caching pull against each other. Caching wants the prefix to be byte-for-byte identical across requests so it can be reused; dynamic assembly wants the prompt to vary per request so it carries only what's needed. The resolution is layering — keep a genuinely stable core (system prompt, the tools you always offer) at the front where it caches, and do your dynamic selection after the cache boundary, in the per-request section. You get the cache discount on the stable part and the leanness of dynamic assembly on the variable part. Knowing where to draw that line is a real FDE skill, and it's why these three levers are taught together rather than in isolation.

Cost lever 4

Cost management: you can't optimize what you don't measure

All three levers above are guesses until you measure them. Cost management is the discipline of actually tracking what your AI features spend — and it's the one that turns "the AI feature is expensive" (a vibe) into "the summarization endpoint costs $0.018 per call and runs 40,000 times a day, which is $720/day, and 60% of that is the uncached manual" (an action item). Clients ask the vibe question constantly. Your value is answering with the number.

The base unit never changes from Day 1: cost ≈ (input tokens + output tokens) × price-per-token, with input and output billed at different rates and output usually the pricier of the two. As of June 2026, a mid-tier model like Claude Sonnet 4.6 runs about $3 per million input tokens and $15 per million output tokens, while a top-tier Opus model is roughly $5 / $25. [source: Anthropic model pricing, claude-api reference catalog, cached 2026-06-04] Those exact numbers will drift — always re-verify current pricing — but the shape is durable: output costs several times more than input, so a feature that generates long responses has a very different cost profile than one that extracts a single label.

The non-obvious part is the granularity of your tracking. A single aggregate "we spent $1,200 on the API last month" tells you nothing actionable. The numbers that drive decisions are sliced three ways. Per feature: which endpoint is the cost center? Often one feature is 80% of the bill, and that's where every optimization dollar should go. Per user (or per tenant): is one power user or one enterprise account driving spend? This is what makes usage-based pricing and rate limits possible, and what catches a runaway loop before it becomes a five-figure surprise. Per run: for an agent or multi-step pipeline, how much did this one task cost across all its internal calls? A single user request that fans out into twelve model calls can cost 50× what the user assumes.

You get these numbers from the usage data the API returns on every response — input tokens, output tokens, and crucially the cached-versus-uncached breakdown. Log them, tag each call with the feature and user it belongs to, and you have a cost dashboard. That dashboard is what lets you say, with a straight face, "we cut this feature's cost 70% by caching the manual" — and prove it. Cost management isn't a finance chore bolted on at the end; it's the feedback loop that tells you whether the other three levers actually worked.

Part 2 · Output guardrailsFrom spending fewer tokens to trusting what comes back.
Guardrail 1

Schema validation: never trust the shape of the output

Now we cross from cost to trust. The hard truth about LLM output is that it is generated text, not a guaranteed data structure. You ask for JSON; most of the time you get clean JSON; some of the time you get JSON wrapped in a chatty preamble ("Sure! Here's the data:"), or JSON with a trailing comma, or a field renamed, or a string where you needed a number, or a perfectly-formed object that's missing the one field your downstream code requires. In a prototype a human notices and shrugs. In production that malformed response flows into json.loads() and throws, or worse, parses into something subtly wrong that corrupts a record.

Schema validation is the guardrail: you define, in code, the exact shape the output must take — these fields, these types, these required keys, these allowed values — and you validate every response against it before you act on it. If it conforms, proceed. If it doesn't, you've caught the problem at the boundary instead of three systems downstream. This is the single highest-value reliability habit on this page, because it converts a silent, intermittent data-corruption bug into a loud, immediate, catchable error.

You have two complementary tools. The first is structured-output features the model provider gives you — telling the API up front "responses must match this JSON schema" so the model is constrained to produce conforming output, or marking a tool's parameters as strictly validated. This dramatically raises the hit rate. The second, which you keep even when you use the first, is your own validation layer — a schema check in your code (a Pydantic model, a Zod schema, a JSON-schema validator) that re-verifies every response. Belt and suspenders is the correct posture here, because "almost always conforms" is not "always conforms", and the cost of the one bad response slipping through is paid by your client's data integrity. Validate the shape before you trust the content.

Guardrail 2

Retry-on-invalid: give the model a second chance, but a bounded one

Catching a bad response with schema validation answers "is this output usable?" The next question is "what do I do when it isn't?" The first-line answer is retry-on-invalid-output: when validation fails, ask again. But how you retry separates the amateur from the engineer.

A naive retry just re-sends the identical request and hopes the dice land differently. That sometimes works — especially if your temperature is above zero, the randomness alone may produce a conforming answer next time (recall the Day 1 sampling discussion). But the smart retry feeds the failure back into the prompt: "Your previous response was not valid JSON — it was missing the required total field. Return only valid JSON matching this schema." Now the model knows specifically what went wrong and is far likelier to fix it. You're using the window deliberately: the error message becomes context that steers the next attempt.

Two non-negotiable rules make retry safe in production. First, bound it. Retry once, maybe twice or three times — never in an unbounded loop. An LLM that keeps producing invalid output will happily do so forever while you burn tokens and stall the user; cap the attempts and treat "still invalid after N tries" as a real failure with its own handling. Second, account for the cost. Every retry is another full billable call (this is exactly why per-run cost tracking from a few minutes ago matters — a feature with a 30% retry rate costs noticeably more than its happy-path math suggests). A bounded, feedback-driven retry loop is one of the most reliable patterns you'll build all program; the worked version is in today's deep-dive.

Guardrail 3

Hallucination mitigation: defend against confident wrongness

Schema validation catches malformed output. It does not catch the more insidious failure: output that is perfectly well-formed and completely wrong. A hallucination — Day 1's confident, fluent, fabricated answer — sails straight through a JSON validator because the JSON is valid; only the facts are invented. So hallucination needs its own layer of defense, and Day 1 already told you where to aim it: the model hallucinates most when the fact it needed was never in the window.

That diagnosis drives the mitigations, and they're mostly about the window, not the model. Grounding is the biggest lever: put the source material in the window and instruct the model to answer only from it — "using only the provided documents, answer the question; if the answer isn't in them, say so." This is the heart of RAG, all of Week 2. Demand citations: require the model to point to where in the provided context each claim came from — a claim it can't cite is a claim to distrust, and asking for citations measurably reduces fabrication because the model has to ground each statement rather than free-associate. Give it an exit: explicitly permit "I don't know." Day 1's insight was that the model has no built-in way to say "I wasn't given that," so it guesses; telling it that "I don't have that information" is an acceptable, preferred answer when the context is silent gives it permission to do the thing it otherwise can't. And verify the high-stakes claims: for facts that matter — a number, a name, a policy — a cheap second check (does this value actually appear in the source? does a follow-up call agree?) catches fabrications before they reach the user.

The mindset to carry: you will fix far more hallucinations by managing the window — better retrieval, grounding, citations, room to answer — than by swapping in a bigger model. Diagnose the window before you reach for the model. That was the spine of Day 1, and it's still the move.

Guardrail 4 · last line

Refusal & fallback: fail safe, never ship garbage

Even with caching, compression, validation, retries, and grounding, some requests will still end in a bad place — the model refuses on safety grounds, every retry still returns invalid output, the grounded context genuinely doesn't contain the answer, or a safety classifier declines the request outright. The final guardrail is deciding, deliberately and in advance, what happens when nothing worked. The wrong answer is to ship the broken response and hope. The right answer is to fail safe.

First, handle refusals as a real outcome. Models can decline to answer — a safety refusal is a distinct, expected response type, not an error, and modern APIs surface it explicitly with a reason. Your code must check for it before it reads the content, or it'll trip over an empty or partial response and crash. Treat a refusal as a branch in your logic: detect it, log it, and route to your fallback — never let it masquerade as a normal answer.

Second, define the fallback path for "we couldn't produce a trustworthy answer." Depending on the feature, that might be: a graceful "I'm not able to help with that right now — let me connect you to a human"; handing off to a deterministic non-AI code path; returning a safe default; or escalating to a person. Some platforms even let you specify an automatic model fallback — if the primary model refuses, transparently retry on another model inside the same call. The unifying principle is that "no answer, cleanly handled" always beats "a wrong answer, confidently delivered." A user who's told the system can't help is mildly disappointed; a user who's given a fabricated account balance is harmed, and your client is liable.

Step back and see the shape of the whole pipeline you've now learned: raw context comes in; you cache the stable part, compress the bulky part, and dynamically assemble only what's needed; you make the metered call and track its cost; you validate the output; invalid output triggers a bounded retry; well-formed output is checked for hallucination; and anything that still can't be trusted hits a safe fallback instead of the user. That pipeline is the diagram on the right, and it's the difference between a demo and a production feature.

Your tools

The $20 plan rewards exactly these habits

Everything today maps directly onto how you'll actually work this program. You're on a $20 Claude Pro plan with a budget measured in roughly 40 hours of focused work a week, and that constraint is not an inconvenience — it's the same discipline a client pays an FDE to bring, just with you holding the bill instead of them. The habits are identical at both scales.

When you point Claude Code at the three files that matter instead of re-indexing the whole repo, that's dynamic assembly — including only what the task needs. When you keep a tight, stable set of project instructions that Claude Code can reuse across a session, you're leaning on caching. When you summarize a long debugging thread instead of letting it balloon, that's compression. And when you read the output critically before pasting it into your codebase — does it actually compile, does that function exist, is that API real — you're doing output validation and hallucination mitigation by hand. Working like an engineer makes the $20 plan plenty; working like a slot machine, re-running giant agent loops to fix a typo, burns your week by Tuesday.

FDE mindset

When a client asks "why is this AI feature so expensive — and why can't we trust it?", those feel like two problems. They're one. Both answers live in how the window is spent and how the output is handled. Cost engineering and reliability engineering are the same discipline wearing two hats — and an FDE who can show the client the per-feature cost number and the validation layer that keeps a fabricated answer out of their database is the one who gets the next contract.

Deep dive: the cost math & a guardrail loop

Optional. ~12 minutes. The numbers and the pattern behind today's picture.

1 · What caching actually saves. Caching is a prefix match billed in two parts: a cache write (slightly more than normal input price) and cache reads (a small fraction of it). As of June 2026 on Anthropic's API, a read is ~0.1× base input price and a write is ~1.25× (5-min cache) or ~2× (1-hour cache). [Anthropic prompt-caching docs, verified 2026-06-28] Note caching only kicks in above a minimum prefix size (roughly 1,024–4,096 tokens depending on model) — shorter prefixes silently won't cache.

Worked example — caching a 10,000-token stable prefix (5-min cache)
  • Uncached: every call pays 1× → 10 calls = 10.0 prefix-equivalents
  • Cached: 1 write (1.25×) + 9 reads (0.1× each = 0.9) = 2.15 prefix-equivalents for the same 10 calls
  • That's a ~78% cut on the prefix across 10 calls — and the savings only grow with volume

Break-even is fast: by call 2, cached (1.25 + 0.1 = 1.35) already beats uncached (2.0). The one rule: a timestamp/UUID/username near the top of the prefix changes it every call → 0 reads, and you pay the write premium forever. Keep volatile content after the cache boundary.

2 · A per-feature cost model. Base unit is unchanged from Day 1: cost = (input_tokens × in_price) + (output_tokens × out_price). Take a support-bot turn at Sonnet-class pricing (~$3 / M input, $15 / M output as of June 2026 [claude-api catalog, cached 2026-06-04]):

One turn, then at scale
  • System prompt 1,500 + manual 3,000 + history 1,200 + question 100 = 5,800 input
  • Answer = 400 output
  • Input 5,800 → $0.0174 · Output 400 → $0.0060 · ≈ $0.023 / turn
  • × 40,000 turns/day = ~$920/day. Cache the 4,500-token system+manual prefix and the input bill on cached calls drops by ~90% of that portion → roughly $300–$400/day saved.

Now slice it: per feature (this endpoint is 80% of the bill), per user (one tenant driving 40% of turns), per run (an agent task that fans out to 12 calls costs ~$0.28, not $0.023). You get every number from the usage fields on each response — log them, tag them, and you have a cost dashboard you can defend to the client.

3 · A bounded, feedback-driven guardrail loop. The production pattern that ties validation, retry, and fallback together:

def call_guarded(prompt, schema, max_tries=3):
    err = None
    for attempt in range(max_tries):
        msg = prompt if err is None else (
            prompt + f"\nYour last reply was invalid: {err}. "
                     f"Return ONLY valid output matching the schema.")
        resp = model.call(msg)            # 1 billable call each loop
        if resp.refused:                  # check refusal BEFORE reading content
            return fallback("model declined")
        try:
            data = schema.validate(resp.text)   # shape guardrail
            return data                          # ✓ valid → ship
        except ValidationError as e:
            err = str(e)                         # feed the failure back
    return fallback("invalid after retries")     # fail safe, never ship garbage

Three things make it production-grade: the retry feeds the specific error back so the next attempt is steered, not just re-rolled; the loop is bounded (no infinite token burn); and every exit that isn't a clean validated result lands in fallback() — a refusal, an exhausted retry budget, anything untrusted — so a malformed or fabricated answer never reaches the user.
