The whole game

Cost comes from the window, just like capability did

On Day 1 we said the same sentence until it stuck: capabilities and limits both come from the window. Today there's a sequel, and it's the one that shows up on the client's invoice: cost comes from the window too. Every token you place in the window is a token you pay for and a token that can be spent well or wasted. Every token the model generates back is a token you pay for. The base unit never changes — cost ≈ (input tokens + output tokens) × price-per-token — so spending fewer tokens for the same answer is, quite literally, the whole game of Part 1.

So far this week you've been getting things to work. Today is about getting them to work affordably — a different bar. A prototype that answers correctly in the playground and a feature that runs ten thousand times a day for a paying client are separated almost entirely by this page. The prototype ignores cost because it runs twice; production lives and dies by cost because it runs constantly, and at that volume a two-cent call becomes a line item with a year's worth of zeros behind it.

Four levers, taught together because they interact. Prompt caching — stop paying for the same prefix twice. Context compression — carry a smaller representation of what you must carry. Dynamic assembly — include only what this call needs. And cost management — measure all three, because you can't optimize what you don't track. The diagram on the right is the pipeline: everything you could send enters wide at the top, and each lever trims it narrower until the metered call is lean. Walk the levers one at a time.

Lever 1 · Prompt caching

Prompt caching: stop paying for the same prefix twice

Recall the Day 1 picture: the system prompt, the few-shot examples, and a big chunk of retrieved context are the same on almost every call. Your support bot's 1,500-token system prompt doesn't change between requests. The product manual you paste in for grounding doesn't change. Yet by default you pay full price to send and re-process that identical text on every single request. That's the waste prompt caching exists to kill.

Prompt caching lets the provider remember a chunk of your prompt — a prefix — so that on the next call it can reuse the already-processed version instead of re-reading it from scratch. You mark where the stable part ends, and subsequent requests that share that exact prefix get it served from cache. The economics are the whole point: a cached read costs only a fraction of the normal input price, while the first write costs slightly more than normal to populate the cache. As verified 2026-10-27, a 5-minute cache write is 1.25× base input and a one-hour write is 2×. Reads are model-specific: Sonnet 5.5 and Opus 5.5 are 0.05×, Fable 5.1 is 0.025×, and models without an exception use 0.1×. [source: Anthropic prompt-caching docs, accessed 2026-10-27]

Run the arithmetic and the discipline becomes obvious. On Sonnet 5.5, cache a 10,000-token stable prefix. The first call pays 1.25× to write it; every call after pays 0.05× to read it instead of 1×. With the 5-minute cache you break even after just two requests (1.25 + 0.05 = 1.30 versus 2.0 uncached), and from the third request on it's nearly free. For a feature handling thousands of requests an hour against a fixed manual, caching routinely cuts the input bill by the better part of an order of magnitude.

But there is one rule you must internalize, because it is the source of nearly every "why isn't my cache working?" bug: caching is a prefix match, and any byte change anywhere in the prefix invalidates everything after it. Put a datetime.now() timestamp, a per-request UUID, or the user's name near the top of your system prompt and the prefix differs on every call — so nothing ever caches, you pay the write premium forever, and you get zero reads.

The fix is structural: keep stable content first (frozen system prompt, deterministic tool list, the manual), and push anything volatile — the user's question, the timestamp, the session ID — to the end, after the cache boundary. You confirm it's working by reading the cache-read usage field the API returns; if that number is zero across repeated identical-prefix calls, a silent invalidator is hiding in your prefix.

Deeper: Context compression: shrink what you carry · outside Core 30
Lever 2 · Context compression

Context compression: shrink what you carry

Day 1's "silent leak" was conversation history: every turn re-sends the entire prior conversation, so a long chat gets slower and more expensive the longer it runs, and eventually the oldest tokens — often your rules — fall out of the window. Context compression is the family of techniques that fights this directly. The idea is simple: don't carry raw history verbatim when a smaller representation would do.

The most common move is summarization. After a conversation grows past some threshold, replace the oldest N turns with a compact summary — "User is troubleshooting a failed payment on order #4471; card confirmed valid; agent has checked the gateway log" — and keep only the recent turns verbatim. Twenty turns that cost 4,000 tokens to resend become a 300-token summary plus the last two turns. The model keeps the thread without you paying to re-transmit every word on every turn. Providers increasingly offer this server-side, but the principle is yours to own whether the platform does it for you or not.

Compression also applies to retrieved context, which Day 1 flagged as usually the biggest consumer in the window. If retrieval pulls back a 5,000-token document but the answer lives in two paragraphs, sending the whole document pays for 4,600 useless tokens and buries the signal in noise. Run the bloated version, then the lean one — same one-sentence answer, a fraction of the tokens spent getting it:

The FDE judgment call with any compression is fidelity versus cost. Summarize too aggressively and you drop a detail the model needed three turns later — now you've saved tokens and broken the feature. The skill is choosing what is safe to compress (resolved sub-topics, pleasantries, redundant confirmations) and what must stay verbatim (the user's stated constraints, IDs, numbers, the active task). Remember the Day 1 line: more retrieved text is not more intelligence; it's more budget spent. A good summary is lossy on purpose, but lossy in the right places.

Deeper: Dynamic prompt assembly: include only what this call needs · outside Core 30
Lever 3 · Dynamic assembly

Dynamic prompt assembly: include only what this call needs

The beginner builds one giant prompt template — every instruction, every tool description, every example, every possible piece of context — and sends it on every request because it's easier than deciding. The practitioner assembles the prompt dynamically, deciding per request what actually belongs in the window this time. This is the same instinct as Day 1's "precision of retrieval," applied to the whole prompt rather than just the documents.

Concretely: if the user's question is about billing, you don't need the 800 tokens of shipping-policy instructions in the window — route them out. If the model has fifteen tools available but this request can only plausibly use two, sending all fifteen tool schemas pays for thirteen the model will never call — and worse, gives it more ways to pick wrong. If a few-shot example is only useful for one kind of request, include it only for that kind. Dynamic assembly means the prompt is built from parts, and you select the parts the current request actually justifies.

There's a tension you have to hold, and it's why this comes after caching in the day: dynamic assembly and prompt caching pull against each other. Caching wants the prefix byte-for-byte identical so it can be reused; dynamic assembly wants the prompt to vary per request. The resolution is layering — keep a stable core (system prompt, the tools you always offer) at the front where it caches, and do your dynamic selection after the cache boundary. You get the cache discount on the stable part and the leanness of dynamic assembly on the variable part. That's why these levers are taught together, not in isolation.

Deeper: Cost management: you can't optimize what you don't measure · outside Core 30
Lever 4 · Cost management

Cost management: you can't optimize what you don't measure

All three levers above are guesses until you measure them. Cost management is the discipline of actually tracking what your AI features spend — the one that turns "the AI feature is expensive" (a vibe) into "the summarization endpoint costs $0.0156 per call and runs 40,000 times a day, which is $624/day, and most input is the uncached manual" (an action item). Clients ask the vibe question constantly. Your value is answering with the number. Run a feature's math yourself:

The base unit never changes from Day 1: cost ≈ (input + output tokens) × price-per-token, with input and output billed at different rates and output usually the pricier. As verified 2026-10-27, Claude Sonnet 5.5 is $2 / M input and $10 / M output, while Opus 5.5 is $4 / $20. [source: Anthropic Models overview, accessed 2026-10-27] Those numbers will drift — always re-verify — but the shape is durable: output costs more than input, so a feature that generates long responses has a very different cost profile than one that extracts a single label.

The non-obvious part is the granularity of your tracking. A single aggregate "we spent $1,200 last month" tells you nothing actionable. The numbers that drive decisions are sliced three ways. Per feature: which endpoint is the cost center? Often one feature is 80% of the bill, and that's where every optimization dollar should go. Per user (or per tenant): is one power user or enterprise account driving spend? This is what makes usage-based pricing and rate limits possible, and what catches a runaway loop before it becomes a five-figure surprise. Per run: for an agent or multi-step pipeline, how much did this one task cost across all its internal calls? A single user request that fans out into twelve model calls can cost 50× what the user assumes.

You get these numbers from the usage data the API returns on every response — input tokens, output tokens, and crucially the cached-versus-uncached breakdown. Log them, tag each call with the feature and user it belongs to, and you have a cost dashboard. That dashboard is what lets you say, with a straight face, "we cut this feature's cost 70% by caching the manual" — and prove it. Cost management isn't a finance chore bolted on at the end; it's the feedback loop that tells you whether the other three levers actually worked.

Deeper: Your tooling rewards exactly these habits · outside Core 30
Your tools

Your tooling rewards exactly these habits

Everything in Part 1 maps directly onto how you'll actually work this program. Token discipline here isn't an inconvenience — it's the same discipline a client pays an FDE to bring. The habits are identical at every scale.

When you point Claude Code at the three files that matter instead of re-indexing the whole repo, that's dynamic assembly — including only what the task needs. When you keep a tight, stable set of project instructions Claude Code can reuse across a session, you're leaning on caching. When you summarize a long debugging thread instead of letting it balloon, that's compression. Working like an engineer makes these tools go far; working carelessly — re-running giant agent loops to fix a typo — wastes that headroom fast.

FDE mindset

When a client asks "why is this AI feature so expensive?", they expect a hand-wave. Your value is the opposite: a per-feature, per-user, per-run number, and a named lever for each. Cost engineering is just disciplined management of the window — cache the stable part, compress the bulky part, assemble only what's needed, and measure all of it. The FDE who can show the client the cost number and the change that moved it is the one who gets the next contract. Carry the lean call into Part 2, where you make what it returns trustworthy.

Harden every untrusted output

Validate shape before use, bound retry-on-invalid, ground factual claims, and end in a safe fallback. On AWS, introduce Bedrock Guardrails content filters and denied topics without pretending they replace application validation; on GCP, preserve the same application-owned contract and use the selected managed filter surface. Add a failing prompt-regression fixture before changing a prompt. The two required exercises diagnose one malformed output and one provider-specific safeguard.

Deeper: Cross from cost to trust: the output is not a contract · outside Core 30
The whole game

Cross from cost to trust: the output is not a contract

Part 1 was about the tokens going in. Part 2 is about the tokens coming back, and a different, harder bar: safe enough to put in front of a real user. A prototype trusts the model's output because a human is reading every word; production has to assume nobody is watching and the output flows straight into a database, an email, or another system. The amateur calls the model and uses what it returns. The professional treats every response as untrusted input until a guardrail says otherwise.

The hard truth is that LLM output is generated text, not a guaranteed structure. You ask for JSON; most of the time you get clean JSON; some of the time you get JSON wrapped in a chatty preamble, or with a trailing comma, or a renamed field, or a string where you needed a number — or a perfectly-formed object that's missing the one field your downstream code requires. And even when the shape is flawless, the facts can be invented. In a prototype a human notices and shrugs. In production that response corrupts a record or reaches a customer.

Four guardrails, in order. Schema validation — never trust the shape. Retry on invalid — give the model a second, bounded chance. Hallucination mitigation — defend against confident wrongness that passes the schema. And refusal & fallback — decide in advance what happens when nothing worked. The diagram on the right is the loop: model output enters, the gates check it, and it ends only as a shipped result or a safe fallback — never as a raw exception on the user's screen.

Guardrail 1 · Schema validation

Schema validation: never trust the shape of the output

Schema validation is the first gate: you define, in code, the exact shape the output must take — these fields, these types, these required keys, these allowed values — and you validate every response against it before you act on it. If it conforms, proceed. If it doesn't, you've caught the problem at the boundary instead of three systems downstream. This is the single highest-value reliability habit on this page, because it converts a silent, intermittent data-corruption bug into a loud, immediate, catchable error.

You have two complementary tools. The first is structured-output features the provider gives you — telling the API up front "responses must match this JSON schema," so the model is constrained to produce conforming output. This dramatically raises the hit rate. The second, which you keep even when you use the first, is your own validation layer — a schema check in your code (a Pydantic model, a Zod schema, a JSON-schema validator) that re-verifies every response. Belt and suspenders is the correct posture, because "almost always conforms" is not "always conforms," and the cost of the one bad response slipping through is paid by your client's data integrity. Validate the shape before you trust the content.

Deeper: why one schema check is the best trade on the page

Think about the asymmetry that makes this the highest-value habit on the page. Without validation, a malformed response doesn't announce itself — it parses into something subtly wrong and quietly corrupts a record, and you find out weeks later when a customer notices their data is off. With validation, the same bad response throws at the boundary, on the very call that produced it, with the exact field and type that failed. You've converted a silent, intermittent, expensive-to-diagnose data bug into a loud, immediate, trivially-loggable error you can route to a retry or a fallback. One schema check buys you that trade on every single call, forever — which is why an FDE adds it before anything else and never takes it out.

Deeper: Retry-on-invalid: a second chance, but a bounded one · outside Core 30
Guardrail 2 · Retry on invalid

Retry-on-invalid: a second chance, but a bounded one

Catching a bad response answers "is this output usable?" The next question is "what do I do when it isn't?" The first-line answer is retry-on-invalid-output: when validation fails, ask again. But how you retry separates the amateur from the engineer.

Practice (optional): which retry actually fixes it?

A naive retry just re-sends the identical request and hopes the dice land differently. That sometimes works — especially above temperature zero, where randomness alone may produce a conforming answer. But the smart retry feeds the failure back into the prompt: "Your previous response was not valid JSON — it was missing the required total field. Return only valid JSON matching this schema." Now the model knows specifically what went wrong and is far likelier to fix it. The error message becomes context that steers the next attempt.

Two non-negotiable rules make retry safe in production. First, bound it. Retry once, maybe twice or three times — never in an unbounded loop. An LLM that keeps producing invalid output will happily do so forever while you burn tokens and stall the user; cap the attempts and treat "still invalid after N tries" as a real failure with its own handling. Second, account for the cost. Every retry is another full billable call — a feature with a 30% retry rate costs noticeably more than its happy-path math suggests, which is exactly why the per-run cost tracking from Part 1 matters. A bounded, feedback-driven retry loop is one of the most reliable patterns you'll build all program.

Deeper: Hallucination mitigation: defend against confident wrongness · outside Core 30
Guardrail 3 · Hallucination

Hallucination mitigation: defend against confident wrongness

Schema validation catches malformed output. It does not catch the more insidious failure: output that is perfectly well-formed and completely wrong. A hallucination — Day 1's confident, fluent, fabricated answer — sails straight through a JSON validator because the JSON is valid; only the facts are invented. So hallucination needs its own layer, and Day 1 already told you where to aim it: the model hallucinates most when the fact it needed was never in the window.

Practice (optional): the schema passed — is it safe to ship?

That diagnosis drives the mitigations, and they're mostly about the window, not the model. Grounding is the biggest lever: put the source material in the window and instruct the model to answer only from it — "using only the provided documents, answer the question; if the answer isn't in them, say so." This is the heart of RAG, all of Week 2. Demand citations: require the model to point to where each claim came from — asking for citations measurably reduces fabrication because the model has to ground each statement rather than free-associate. Give it an exit: explicitly permit "I don't know," because the model has no built-in way to say "I wasn't given that," so it guesses unless you tell it silence is acceptable. And verify the high-stakes claims: for a number, a name, a policy, a cheap second check catches fabrications before they reach the user. The mindset: you'll fix far more hallucinations by managing the window than by swapping in a bigger model.

Deeper: Refusal & fallback: fail safe, never ship garbage · outside Core 30
Guardrail 4 · last line

Refusal & fallback: fail safe, never ship garbage

Even with validation, retries, and grounding, some requests still end in a bad place — the model refuses on safety grounds, every retry still returns invalid output, or the grounded context genuinely doesn't contain the answer. The final guardrail is deciding, deliberately and in advance, what happens when nothing worked. The wrong answer is to ship the broken response and hope. The right answer is to fail safe.

First, handle refusals as a real outcome. Models can decline to answer — a safety refusal is a distinct, expected response type, not an error, and modern APIs surface it explicitly with a reason. Your code must check for it before it reads the content, or it'll trip over an empty or partial response and crash. Treat a refusal as a branch in your logic: detect it, log it, and route to your fallback — never let it masquerade as a normal answer.

Second, define the fallback path for "we couldn't produce a trustworthy answer." Depending on the feature, that might be a graceful "I'm not able to help with that right now — let me connect you to a human," a handoff to a deterministic non-AI code path, a safe default, or an escalation to a person. Some platforms even let you specify an automatic model fallback. The unifying principle is that "no answer, cleanly handled" always beats "a wrong answer, confidently delivered." A user who's told the system can't help is mildly disappointed; a user who's given a fabricated account balance is harmed, and your client is liable.

Deeper: choosing the fallback per feature, in advance

The discipline here is choosing the fallback per feature, in advance — not improvising it inside an exception handler at 2 a.m. A customer-facing chatbot's fallback is a warm handoff to a human; a backend enrichment job's fallback might be to leave the field null and flag the row for review; a code generator's fallback is to surface the error and let the engineer write the function. What they share is that the failure mode is a designed outcome with its own path, logged so you can measure how often you hit it — a rising fallback rate is an early signal that something upstream (the prompt, the grounding, the model) has drifted and needs attention before users feel it.

Step back and see the whole loop: output comes back; you validate its shape; invalid output triggers a bounded retry that feeds the error back; well-formed output is checked for hallucination; and anything that still can't be trusted — a refusal, an exhausted retry budget, an ungrounded claim — hits a safe fallback instead of the user. That loop is the diagram on the right, and it's the difference between a demo and a production feature.

On your cloud · managed guardrails

The managed guardrail layer: what it catches, what stays in your code

Your code owns the loop above. Both clouds also sell a managed screening layer that inspects prompts and responses against policies you configure, outside your application logic. Use it for the policy-shaped failures — unsafe content, prompt attacks, leaked personal data — and keep asking the same question of it that you ask of the model: which of the four guardrails does this actually cover? Open your path; the other cloud stays as an optional comparison.

AWSAmazon Bedrock Guardrails

Bedrock Guardrails applies configurable safeguards to user inputs and model responses: content filters (hate, insults, sexual, violence, misconduct, and prompt attack) with an adjustable strength, denied topics, word filters, and sensitive information filters that block or mask PII. Two safeguards reach into Guardrail 3: contextual grounding checks flag a response that isn't grounded in the supplied source or doesn't answer the query, and Automated Reasoning checks test a response against logical rules you define. The ApplyGuardrail API runs the same guardrail on any text without invoking a model, so one policy can screen inputs and outputs anywhere in your flow. It still sits beside your schema check and bounded retry, not instead of them.

Deep dive: the cost math behind the levers

Optional. ~6 minutes. The numbers under today's picture.

1 · What caching actually saves. Caching is a prefix match billed in two parts: a cache write and cache reads. For Sonnet 5.5 as verified 2026-10-27, a read is 0.05× base input price and a write is 1.25× (5-minute cache) or 2× (1-hour cache). [Anthropic prompt-caching docs, accessed 2026-10-27] Minimum cacheable prefix sizes vary by model, so verify that threshold too.

Worked example — caching a 10,000-token stable prefix (5-min cache)
  • Uncached: every call pays 1× → 10 calls = 10.0 prefix-equivalents
  • Cached: 1 write (1.25×) + 9 reads (0.05× each = 0.45) = 1.70 for the same 10 calls
  • That's an 83% cut on the prefix across 10 calls — and savings grow with volume

Break-even is fast: by call 2, cached (1.25 + 0.05 = 1.30) already beats uncached (2.0). The one rule: a timestamp/UUID/username near the top of the prefix changes it every call → 0 reads, and you pay the write premium forever. Keep volatile content after the cache boundary.

2 · A per-feature cost model. Base unit unchanged from Day 1: cost = (input × in_price) + (output × out_price). Take a support-bot turn at Claude Sonnet 5.5's 2026-10-27 rate ($2 / M input and $10 / M output):

One turn, then at scale
  • System prompt 1,500 + manual 3,000 + history 1,200 + question 100 = 5,800 input
  • Answer = 400 output
  • Input 5,800 → $0.0116 · Output 400 → $0.0040 · $0.0156 / turn
  • × 40,000 turns/day = $624/day. Cache the 4,500-token system+manual prefix at Sonnet 5.5's 0.05× read rate: steady-state calls fall to about $0.0071 → roughly $342/day saved.

Now slice it: per feature (this endpoint is 80% of the bill), per user (one tenant driving 40% of turns), per run (an agent task that fans out to 12 calls costs about $0.19, not $0.0156). You get every number from the usage fields on each response — log them, tag them, and you have a dashboard you can defend to the client.

The four levers compose: caching kills the repeated-prefix bill, compression shrinks the bulky middle, dynamic assembly drops what this call doesn't need, and cost tracking proves which one moved the number. The lean call that falls out the bottom is the one you make resilient in Part 2.

Deep dive: the guardrail loop

Optional. ~6 minutes. Validation, retry, and fallback assembled into one function.

A bounded, feedback-driven loop that ties the four guardrails together — validate the shape, feed failures back, cap the attempts, check refusals before reading content, and end every untrusted path in a safe fallback:

def call_guarded(prompt, schema, max_tries=3):
    err = None
    for attempt in range(max_tries):
        msg = prompt if err is None else (
            prompt + f"\nYour last reply was invalid: {err}. "
                     f"Return ONLY valid output matching the schema.")
        resp = model.call(msg)            # 1 billable call each loop
        if resp.refused:                  # check refusal BEFORE reading content
            return fallback("model declined")
        try:
            data = schema.validate(resp.text)   # shape guardrail
            return data                          # ✓ valid → ship
        except ValidationError as e:
            err = str(e)                         # feed the failure back
    return fallback("invalid after retries")     # fail safe, never ship garbage

Three things make it production-grade: the retry feeds the specific error back so the next attempt is steered, not just re-rolled; the loop is bounded (no infinite token burn); and every exit that isn't a clean validated result lands in fallback() — a refusal, an exhausted retry budget, anything untrusted — so a malformed answer never reaches the user.

What this loop doesn't catch: a well-formed but fabricated value passes schema.validate cleanly. Hallucination is a separate layer — grounding, demanded citations, an "I don't know" exit, and a cheap source-check on high-stakes facts — bolted on around this loop, not inside it. Schema guards the shape; grounding guards the facts.

Production code: prompt caching

A single cachePoint marks where the stable prefix ends; for this dated Haiku 5.5 example, the system rules and manual are served from cache at 0.1× on later calls while the volatile question stays after the boundary.

# Stop paying full price for the same prefix twice: cache the stable part with a cachePoint.
# Auth: Bedrock API key in AWS_BEARER_TOKEN_BEDROCK (boto3 reads it; no IAM role).
import boto3

bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")

# STABLE prefix first (system rules + manual). Haiku 5.5 needs >= 512 tokens to cache.
# The cachePoint marks where the cacheable prefix ends; Haiku 5.5 reads bill at 0.1x.
system = [
    {"text": SYSTEM_RULES + PRODUCT_MANUAL},    # identical on every call
    {"cachePoint": {"type": "default"}},         # <-- everything ABOVE this is cached
]

def ask(question: str):
    resp = bedrock.converse(
        modelId="us.anthropic.claude-haiku-5-5",
        system=system,
        # VOLATILE content goes AFTER the boundary, so the prefix stays byte-identical.
        messages=[{"role": "user", "content": [{"text": question}]}],
        inferenceConfig={"maxTokens": 512, "temperature": 0},
    )
    u = resp["usage"]
    # Confirm it: cacheReadInputTokens should be > 0 from the 2nd call onward.
    print(f"read={u.get('cacheReadInputTokens', 0)} write={u.get('cacheWriteInputTokens', 0)}")
    return resp

Confirm it worked by reading cacheReadInputTokens — zero across identical-prefix calls means a silent invalidator slipped in above the cachePoint.

Production code: forced structured output

The schema is the output contract, enforced at the source. On AWS a forced tool call returns guaranteed-shaped JSON; on GCP a response schema does the same — a real number in total, not the string '1,250.00'.

# Force valid structured output at the source: a tool schema the model must fill.
# Auth: Bedrock API key in AWS_BEARER_TOKEN_BEDROCK (boto3 reads it; no IAM role).
import boto3

bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")

# The tool's inputSchema IS your output contract -- required fields can't be omitted,
# and a number field can't come back as a string.
tool_config = {
    "tools": [{"toolSpec": {
        "name": "record_invoice",
        "description": "Record the fields extracted from an invoice.",
        "inputSchema": {"json": {
            "type": "object",
            "properties": {
                "total": {"type": "number"},
                "due_date": {"type": "string", "description": "YYYY-MM-DD"},
                "vendor": {"type": "string"},
            },
            "required": ["total", "due_date", "vendor"],
        }},
    }}],
    "toolChoice": {"tool": {"name": "record_invoice"}},   # force the tool -> guaranteed shape
}

resp = bedrock.converse(
    modelId="us.anthropic.claude-haiku-5-5",
    messages=[{"role": "user", "content": [{"text": f"Extract the invoice:\n{raw_invoice}"}]}],
    toolConfig=tool_config,
    inferenceConfig={"maxTokens": 512, "temperature": 0},
)

# The model returns a toolUse block; input already matches the schema (total is a real number).
block = next(b for b in resp["output"]["message"]["content"] if "toolUse" in b)
invoice = block["toolUse"]["input"]   # shape guaranteed -- truth is not, so still validate
# Force valid structured output at the source: a response schema the model must match.
# Setup: pip install --upgrade google-genai
#   GOOGLE_CLOUD_PROJECT=<project>  GOOGLE_CLOUD_LOCATION=global  GOOGLE_GENAI_USE_ENTERPRISE=True
import json

from google import genai
from google.genai.types import HttpOptions

client = genai.Client(http_options=HttpOptions(api_version="v1"))

# response_schema IS your output contract -- with response_mime_type=application/json
# the reply is valid JSON of this shape; total comes back as a number.
invoice_schema = {
    "type": "OBJECT",
    "properties": {
        "total": {"type": "NUMBER"},
        "due_date": {"type": "STRING", "description": "YYYY-MM-DD"},
        "vendor": {"type": "STRING"},
    },
    "required": ["total", "due_date", "vendor"],
}

resp = client.models.generate_content(
    model="gemini-3.5-flash",
    contents=f"Extract the invoice:\n{raw_invoice}",
    config={
        "response_mime_type": "application/json",
        "response_schema": invoice_schema,
        "temperature": 0,
    },
)

invoice = json.loads(resp.text)   # shape guaranteed -- truth is not, so still validate

The shape is guaranteed; the facts are not — still validate on your side and keep a bounded retry plus fallback around this call.
