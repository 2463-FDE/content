Prompt Engineering & Requirements Synthesis

Week 1 · Day 3 Designing the interface, then pinning the spec Core 30 · ~11 min read · 2 interactions · 6-Q check · ~27 min required

One topic with two faces of the same discipline: precision about what you ask for. The first half treats prompt engineering as interface design — roles, structure, structured output — not incantation. The second half turns a vague client ask into a testable spec with the same muscles: decompose, make assumptions explicit, and write acceptance criteria you can defend in the FDE Situation session.

The whole game

A prompt is an interface, not an incantation

The internet is full of "prompt hacks" — magic phrases, all-caps threats, "you are a world-class expert" preambles. Forget almost all of it. Here is the framing that serves you for the rest of your career: a prompt is the interface between your software and a probabilistic text engine. Engineering it well is the same discipline as designing any contract between two systems — you specify, as precisely as you can, what goes in, what must come out, and what the rules are in between.

That reframing changes what "good" means. A good prompt is not the cleverest-sounding one. It's the one that produces the right output shape, reliably, at an acceptable cost, for every input your system will actually see — not just the one you tested in the playground at 2pm on a Tuesday. The model is non-deterministic by nature; your job is to remove as much ambiguity as you can so the variation that remains is variation you can live with.

Everything today decomposes a prompt into parts you can engineer independently: the system prompt (the standing contract), examples (teaching by showing — zero, one, or few-shot), a reasoning scaffold (chain-of-thought, giving the model room to work), the user input slot (the one part that changes per call, plus the grounded context you inject there), and the output contract (structured output / JSON mode pinned to a schema). Then we close the loop with iteration and eval — treating the prompt as code you measure, not prose you admire.

Notice that nothing here is model-specific folklore — it's the engineering posture you'd bring to any unreliable dependency. Imagine calling a flaky third-party API that sometimes returns exactly what you asked for and sometimes returns a friendly paragraph apologizing for not understanding. You wouldn't "trick" it with magic words; you'd write the tightest possible request, validate every response, and build tests around it. A language model is precisely that dependency, and every technique today is that same discipline applied to a system whose output happens to be natural language.

Deeper: The system prompt is the standing contract · outside Core 30
Slice 1 · the contract

The system prompt is the standing contract

You met the system prompt on Day 1 as "the first slice of the window, paid on every call." Today we look at what it's for. The system prompt encodes everything that should be true on every request regardless of what the user types: the model's role ("you are a contract-intake assistant for a federal acquisitions team"), the rules ("never invent a solicitation number; if a field is missing, return null"), the output format ("respond only with JSON matching the schema below"), and the guardrails ("do not give legal advice; flag anything that looks like PII").

The most common beginner mistake is treating the system prompt as a junk drawer — dumping every instruction, edge case, and "oh and also" into a 2,000-token wall of text. Remember the budget: that wall is prepended to every call forever, and worse, models reliably follow a tight, well-ordered instruction set better than a sprawling one. Past a certain length, extra instructions don't just cost tokens; they dilute attention and the model starts dropping rules. More instruction is not more obedience.

Two habits make system prompts strong. First, put the most important, least-negotiable rules first and last — models weight the beginning and end of the context more heavily than the middle (the "lost in the middle" effect you'll meet again in Week 2's RAG work). Your hard constraints — "output JSON only", "never fabricate" — belong at the edges, not buried in paragraph six. Second, prefer positive, concrete instructions over negative, vague ones. "Return the date as YYYY-MM-DD" beats "don't format dates weirdly." The model can act on a concrete target; it struggles to infer what you meant by "weirdly."

A third habit, expensive to skip: state the failure behavior explicitly. Most system prompts describe the happy path — "extract the fields" — and go silent on what to do when the input is malformed, empty, off-topic, or missing the requested information. The model then improvises, and its improvisation is rarely what you'd choose. Spell it out: "If the document contains no due date, return null. If the input is not a solicitation at all, return all fields as null and set a valid flag to false." This is the same instinct as writing the else branch and the error handler in ordinary code — you just write it in English. And note the FDE distinction: the system prompt encodes policy, the user message carries data. When a client says "the AI keeps ignoring our compliance rule," the fix is almost never in the user message — it's that the rule was never stated in the system prompt, or was buried so deep it got drowned out. Diagnose the contract before you blame the model.

Deeper: Zero, one, and few-shot: examples teach format · outside Core 30
Slice 2 · teach by showing

Zero, one, and few-shot: examples teach format

There are three points on a spectrum, and naming them precisely keeps you honest. Zero-shot means you describe the task and give no examples — "classify this support ticket as billing, technical, or account." One-shot includes exactly one worked example of input → desired output. Few-shot includes a handful — typically two to five. The jump that matters most is from zero to one or two: a single concrete example often locks in a format, tone, or edge-case handling that a whole paragraph of description fails to convey.

Why examples beat description: language is lossy. If you want output that looks like {"category": "billing", "confidence": 0.9}, you can describe that in words and the model will mostly comply. But show it two real examples and it will nearly always comply — including the subtle things you forgot to describe: whether confidence is 0–1 or 0–100, whether category is lowercase, what to do when the ticket is ambiguous. Examples carry the tacit rules you didn't know you had. Few-shot has a second superpower: it handles edge cases by demonstration. If your classifier keeps mis-handling tickets that mention two topics, add one example of a two-topic ticket with the desired resolution. You've taught the behavior without writing a single new rule.

But the cost discipline from Day 1 applies directly: every example is tokens in the window on every call, and the benefit has steep diminishing returns — zero to two is transformative, eight to twelve usually isn't, and a giant example block can crowd out the user's real input. The best-practice prompt above shows the move: one demonstrated input→output pair pins the format far more reliably than another paragraph of description — but that demonstrated pair is tokens you re-send on every single request. So the FDE question is never "do examples help?" (they do) but "what is the fewest examples that hits my quality bar?" Start at zero, measure, add one or two aimed squarely at the failures you observe, measure again.

There's a subtler trap worth naming. Few-shot examples don't just teach format — they quietly teach distribution. If all three of your examples classify as "billing," the model picks up a bias toward "billing" that has nothing to do with the input in front of it; if they're all short and tidy, it handles long messy input worse. The examples are training data for this one call, and like any training data they carry whatever skew you didn't notice. So balance the classes, vary the length and messiness, and include at least one of the cases that's currently failing — a deliberate act, not grabbing the first three rows of a spreadsheet.

Deeper: Chain-of-thought: give the model room to reason · outside Core 30
Slice 3 · room to think

Chain-of-thought: give the model room to reason

For any task that involves multiple steps — math, multi-condition logic, comparing options, applying a rule with exceptions — the single most reliable quality lever is letting the model reason before it answers instead of forcing an immediate verdict. This is chain-of-thought (CoT) prompting. The classic trigger is as simple as "think step by step," but the real mechanism is deeper: because the model generates one token at a time and each token it writes becomes context for the next, the intermediate reasoning it writes out literally becomes scratch space it can compute against.

That mechanism explains a counterintuitive truth: asking for the answer first and the reasoning after is worse than useless. If your prompt says "give the answer, then explain," the model has already committed to the answer before it did any thinking — the explanation is a post-hoc story, not the path that produced the conclusion. Order matters: reasoning, then conclusion. When you also want a structured final answer, the standard pattern is "reason in a scratchpad, then output the final result in the required format" — you get the accuracy benefit of thinking and the clean output your code needs.

CoT is not free, and this is where it intersects with Day 1 and 2. Reasoning is output tokens, and output tokens are the expensive ones. A task that answered in 50 tokens might now spend 400 thinking out loud. For a hard reasoning task that's a bargain — you turned a wrong answer into a right one. For a trivial classification it's pure waste. So the FDE judgment is match the reasoning budget to the task's actual difficulty. Be aware, too, that some newer models do this reasoning internally as a built-in mode rather than something you prompt for — the technique-level idea is what's durable: steps that need thinking get room to think, before they commit. The exact knob to request it is a per-model API detail to confirm against current docs the day you wire it up.

A close cousin of chain-of-thought is decomposition: instead of asking one prompt to do a hard, multi-part job at once, break it into a small chain of narrower prompts, each doing one thing well. "Extract the clauses" → "classify each clause" → "flag the conflicts" can be three focused calls instead of one overloaded one. Each step is easier to write, test in isolation, and debug. The cost is more calls and more tokens, so it's a trade — but a prompt trying to do five things at once is usually a sign you haven't finished thinking, the same way a 200-line function usually is. It also sets you up for the agentic decomposition you'll build in Week 3.

Deeper: The user input slot — and grounding it in real context · outside Core 30
Slice 4 · the variable part

The user input slot — and grounding it in real context

Everything so far — system prompt, examples, reasoning instructions — is fixed scaffolding that's the same on every call. The user input slot is the one part that changes per request: the actual ticket to classify, the actual contract to summarize, the actual question to answer. Keeping a crisp mental line between the fixed scaffold and the variable slot is one of the cleanest habits in the discipline, because it's exactly the line your code has to respect.

That blurred line is how you get prompt injection and parsing chaos. The defensive habit — treat user input as data, never as instructions — is why you wrap it in delimiters and say so explicitly in the system prompt. The user slot is also where grounding happens, and this is the bridge to Week 2's entire RAG curriculum, so plant the seed now. Most real client value isn't the model answering from its own training; it's the model answering about the client's data: their contracts, their tickets, their policy documents — facts the model was never trained on and cannot know. Grounding means retrieving the relevant facts and placing them, as text, into the window alongside the user's question, so the model reasons over those facts rather than guessing. The user slot is where that retrieved context lands.

This connects straight back to Day 1's hallucination model. A hallucination is, nine times out of ten, a fact that was never in the window. Grounding is the cure: don't ask the model what it "knows," give it the source and ask it to answer from the source — and, crucially, instruct it to say "not found in the provided context" rather than fill the gap. "Answer only from the context below; if the answer isn't there, say so" is one of the highest-leverage sentences in applied prompt engineering. It converts a confident fabrication into an honest miss — which, at a federal client where a wrong contract number has real consequences, is exactly the trade you want.

It helps to picture the assembled prompt as a template with one hole in it. The system prompt, examples, reasoning instructions, and schema are the template — written once, reviewed, version-controlled, tested. The user slot is the hole, filled at runtime. When something breaks, that boundary is your first diagnostic cut: is the problem in the fixed template (affects every call) or in what got injected into the slot this time (affects only some inputs)? Most "the AI is acting weird today" reports resolve cleanly along that line.

Slice 5 · the output contract

Structured output: pin the shape with a schema

Here's the part that separates a demo from a system. In a chat window, freeform prose is fine — a human reads it. But in software, the model's output is almost always consumed by more code: stored in a database, passed to an API, rendered in a UI, used to drive a decision. Code cannot reliably parse "Sure! The contract value looks like about $1.2 million and it expires next March 🙂". Code needs {"value_usd": 1200000, "expiry": "2026-03-31"}. Structured output is the discipline of making the model return data in a shape your code can trust.

The weakest form is just asking nicely: "respond in JSON." It works often and fails occasionally — and "occasionally" at scale means a steady drip of parse errors, wrapped-in-markdown fences, trailing commentary ("Here's your JSON:"), and the dreaded truncated object. A stronger form is JSON mode / structured output features that constrain generation so the output is guaranteed to be syntactically valid JSON, and in the strongest variants, guaranteed to conform to a schema you supply — exact field names, types, required fields, allowed enum values. When the API can enforce the schema, a whole class of "the model returned something weird" bugs moves from runtime surprise to impossible.

A schema is just a precise, machine-readable description of the output shape — usually JSON Schema. It says: there is a category field that must be one of billing, technical or account; a confidence field that is a number; and the category is required. Writing the schema first is a powerful design act, because it forces you to decide exactly what you need before you write a word of prompt. A good schema does half the prompt engineering for you: an enum field cannot come back as freeform text, a required field forces the model to commit, and a nullable field gives it a sanctioned way to say "missing" instead of inventing something.

Two FDE cautions. First, structured does not mean correct. The schema guarantees the shape — that you got a valid date string — not the truth — that it's the right date. You still need grounding and eval for correctness; schema only kills the parsing failures. Second, even with strong schema enforcement, build your consuming code to be defensive: validate the parsed object on the way in, decide in advance what happens when a required field is null, and log the raw output when validation fails. The model returns well-shaped data 99% of the time; your job is to make the other 1% degrade into a handled error rather than a silently-wrong record written to the client's database — the kind of thing that turns into a very uncomfortable meeting at a federal client.

Deeper: Iteration and eval: treat the prompt like code · outside Core 30
Slice 6 · close the loop

Iteration and eval: treat the prompt like code

The amateur writes a prompt, tries it once on a happy-path example, sees it work, and ships. The practitioner knows that "worked once in the playground" tells you almost nothing about behavior across the messy distribution of real inputs. The discipline that closes the gap is evaluation: building a small set of representative inputs with known-good answers — a "golden set" — and measuring your prompt against all of them, every time you change it.

This is the mindset shift that makes everything above engineering instead of guesswork: a prompt is code, and code without tests is a liability. When you tweak the system prompt to fix one client's edge case, how do you know you didn't break three cases that used to pass? You don't — unless you re-run the eval set. Prompts are especially treacherous because changes are non-local: a word added to the system prompt can shift behavior on inputs that have nothing obviously to do with it. Without an eval set you are flying blind and calling it intuition.

An eval set doesn't have to be fancy to be transformative. Ten to twenty real, diverse inputs — pulled from the client's actual data, including the ugly edge cases — with the output you'd accept for each, in a file. For structured output you can often check correctness automatically (did the JSON parse? did category match the expected enum?). For fuzzier tasks you self-grade or use a second model as a judge (a technique you'll meet later). The point isn't sophistication; it's having a ground-truth you measure against instead of vibes. Week 8 turns that habit into an observability and evaluation deliverable.

The iteration loop, then, is tight and repeatable: write the smallest prompt that could work → run it against the eval set → look at the failures specifically, not the successes → make one targeted change → re-run → keep the change only if the score went up. Change one thing at a time so you actually learn what helped. Two failure modes to guard against: overfitting (tune relentlessly against the same fifteen examples and you memorize the test instead of improving the behavior — keep some in reserve), and grading drift (when self-scoring fuzzy outputs, write down what "acceptable" means before you tune). By Week 8 you'll use this evidence in formal evaluation work, and one built on a memorized or drifting set is false confidence with your name on it. Measure, change one thing, re-measure. That loop is the whole job.

FDE Situation: synthesize model requirements

A stakeholder sentence is not a buildable requirement. Identify the user and decision, ask what must be structured, deterministic, and grounded, then write measurable acceptance criteria and explicit non-goals. The diagnosis below gives immediate feedback on the gap; the required synthesis turns the answers into a schema, model constraints, and an evaluation plan.

Deeper: Clients hand you a sentence, not a spec · outside Core 30
FDE Situation · the ask

Clients hand you a sentence, not a spec

Everything in Part 1 assumed you already knew what you were building. In the field, you almost never do. A stakeholder pulls you aside and says some version of: "We've got analysts spending hours reading incoming contract solicitations. Can the AI just, you know, read them and pull out the important stuff?" That's it. That's the requirements document. One sentence, three vague nouns ("the important stuff"), and an implied promise that you'll figure out the rest.

The instinct of a junior engineer is to nod and immediately start writing a prompt — "Summarize the important parts of this solicitation." The instinct of a Forward Deployed Engineer is to recognize that the ask is a symptom, and the requirements are the diagnosis. "Read them and pull out the important stuff" contains at least a dozen unstated decisions, and every one of them is a fork that leads to a different system. Which fields, exactly? In what format — prose for a human, or structured data for a database? How accurate does it need to be, and what's the cost of being wrong? Does it need to be repeatable run-to-run? Where do the facts come from — the document in front of it, or some reference the model has to look up?

Notice these questions are exactly the parts of a prompt you spent Part 1 learning. That's not a coincidence — it's the point. You can only engineer a prompt for requirements you've actually pinned down. The vague-ask conversation isn't a soft "discovery" preamble before the real work; it is the real work, because it's where the prompt's system instructions, output schema, grounding strategy, and determinism settings are actually decided. An FDE who skips it builds a confident, well-crafted answer to a question nobody asked.

FDE Situation · the skill

Problem identification through structured questioning

The skill — and it is a learnable, nameable skill, not a personality trait — is problem identification through structured questioning. You turn the vague ask into a spec by interrogating it along a few reliable axes. What does "important stuff" mean concretely? Push until you have a list: solicitation number, agency, due date, estimated value, set-aside type, key requirements. Who or what consumes the output? An analyst skimming, or a tracking system ingesting? That single answer decides prose versus JSON. What's the cost of an error? A missed due date that loses a bid is catastrophic; a slightly-off summary is a shrug. The blast radius sets your accuracy and review requirements. How variable can the answer be? If two analysts running it on the same document must see the same extraction, you need determinism. What does the model need to know that it can't? Anything client-specific or current must be grounded, not recalled.

There's a human dimension the technical framing can hide. The stakeholder who said "pull out the important stuff" isn't being lazy or deliberately vague — they're an expert in their domain (federal acquisitions) who has never had to write a software spec, and "the important stuff" is genuinely obvious to them because they do it every day on autopilot. Part of your job is to make that tacit expertise explicit, and the way you do it is by asking concrete, almost annoyingly specific questions: "Show me the last solicitation you triaged — walk me through exactly what you looked at, and in what order." Watching an expert do the task, and narrating it back as a list to confirm, surfaces requirements no abstract conversation ever would.

This is why FDE work is forward deployed: you can't synthesize a good spec over email from a one-line ticket. You sit next to the people doing the work, watch the real thing, and turn what they do without thinking into something a system can be told. The engineers who treat that as a chore and hurry back to their keyboard are exactly the ones who build the wrong thing beautifully. The next three sections distill the interrogation into three questions you ask of every vague ask — and they map one-to-one onto the prompt decisions from Part 1.

Deeper: What must be structured? · outside Core 30
Lens ① · structured

What must be structured?

Anything a downstream system consumes has to come back as data with a known shape, not prose. "Pull out the solicitation number, agency, and due date" is a screaming signal for a JSON schema: a solicitation number as a string, an agency as a string, a due date as a date or null, an estimated value as a number or null. The moment you write that schema, half the ambiguity in the original ask evaporates — you have forced "the important stuff" to become a finite, named, typed list.

The deciding question behind this lens is the one from Part 1's tooling discussion: who or what consumes the output? A triage dashboard the analysts sort and filter? Then the output must be structured data — you're building an extractor, not a summarizer. Had the answer been "an analyst reads it over coffee," prose might have been fine. Same ask, different system. The consumer decides the shape, and the shape decides whether you reach for a schema at all.

This lens is also a fast readiness check. If the stakeholder can't tell you the fields, you're not ready to build — and the schema conversation is how you find that out in the first meeting instead of three weeks in. Writing the schema first is the same powerful design act you saw in Part 1: it forces both of you to decide exactly what's needed before a single line of prompt gets written. A nullable field gives the model a sanctioned way to say "not in the document"; a required field forces it to commit; an enum makes a free-text answer impossible. The schema has encoded half your rules before you've touched the system prompt.

Be alert, too, that "structured" is rarely uniform. Some fields in the same extraction are mission-critical and belong in the schema's required list; others are nice-to-have and can stay nullable. Some are clean primitives (a date, a dollar amount); others are themselves small structures (a list of key requirements, each with a label and a weight). The act of typing every field — string, number, date, enum, boolean, array — is where you discover the questions the stakeholder never thought to answer: does estimated value include options years? Is "set-aside" one value or several? Those discoveries are the whole point. The schema isn't paperwork you produce after the thinking; it is the thinking, written in a form a machine and a stakeholder can both check.

Deeper: What must be deterministic? · outside Core 30
Lens ② · deterministic

What must be deterministic?

Ask: if we run this twice on the same document, must we get the same answer? For extraction the answer is almost always yes — two analysts must not see two different due dates — which means low temperature, a tight schema, and an eval set that checks for exactly that stability. For genuinely generative tasks ("draft a friendly rejection email") some variation is fine or even desirable.

Determinism is a requirement you elicit, not a default you assume. Getting it wrong is the root cause of a huge share of the "the AI is flaky / inconsistent / sometimes works" complaints you'll be called in to fix — and the fix is usually not a better model but a temperature near zero, a tighter schema, and an eval that actually checks run-to-run stability. The cost-of-error question from the interrogation feeds straight in here: a wrong or missed due date can lose a bid worth millions, so it needs near-certainty, determinism, and human review; a slightly-off one-line description is a minor annoyance and can be best-effort. Accuracy requirements are not uniform across fields, and that asymmetry shapes both the schema and the eval set.

Deeper: What must be grounded? · outside Core 30
Lens ③ · grounded

What must be grounded?

Separate, ruthlessly, what the model can answer from general knowledge versus what it must answer from this client's facts. The format of a federal solicitation? General pattern — fine to lean on training. This specific solicitation's due date? Must come from the document in the window — never from the model's memory, which has no way to know it and every incentive to invent something plausible. Grounding requirements drive your whole retrieval strategy and feed directly into Week 2's RAG curriculum.

The rule of thumb: if being wrong about a fact has real consequences, that fact must be grounded and the model must be allowed to say "not found." This is Part 1's hallucination cure stated as a requirement rather than a technique — every field that comes from the document is nullable, and the system prompt says "answer only from the document provided; if a field is absent, return null — never infer or guess." An honest miss beats a confident fabrication, especially at a federal client where a wrong contract number has downstream consequences.

Grounding is also where you decide how the facts reach the window, and that decision sizes the rest of the engagement. If every needed fact lives in the one document in front of the model, grounding is easy — you drop the document in the user slot and you're done. But the moment the answer depends on facts spread across many documents the model can't all hold at once — "which of our 4,000 past solicitations is this a re-compete of?" — you need retrieval: a way to find the relevant few and place only those in the window. That is the entire subject of Week 2, and the grounding lens is what tells you, in the first conversation, whether this is a drop-it-in-the-prompt job or a retrieval job. Naming that early is the difference between an accurate scope and a nasty surprise in week three.

These three lenses generalize far past extraction, so keep them in your pocket as a literal checklist. Building a chatbot? Structured: probably its actions and tool calls, not its prose. Deterministic: the policy answers must be, the small talk needn't be. Grounded: anything about the client's accounts, orders, or rules — never from memory. Drafting documents? Structured: the metadata and section headings. Deterministic: the legal boilerplate. Grounded: every factual claim. The three lenses are a portable instrument for converting any "can the AI just..." into a spec.

FDE Situation · the synthesis

Synthesize the answers into a buildable spec

Run those three questions and the vague sentence has become a buildable spec: a system prompt encoding the role and the "answer only from the provided document; return null for missing fields" rule; an output schema naming every field and its type; a temperature near zero for repeatability; a grounding plan for what gets retrieved into the window; and a small eval set of real solicitations with known-correct extractions to measure against. That is the deliverable of the vague-ask conversation — and it's worth far more to the client than any single clever prompt, because it makes every subsequent prompt-engineering decision obvious. The clever prompt was never the hard part; the synthesis was.

Deeper practice: test the synthesized spec · outside Core 30

The three lenses double as a triage tool when something's already broken: a flaky output is usually a determinism gap, a hallucinated fact is a grounding gap, and a parse error is a structure gap. Most of the AI failures you'll be called in to fix at a client are one of those three wearing a costume, and naming which one is half the fix. Run the checklist out loud in front of the stakeholder and you'll often watch them realize, in real time, that they hadn't decided half of these either — which is exactly the value you were brought in to provide. The full end-to-end version of this — one real vague ask carried all the way to a schema — is in today's deep dive. Do it; it's the rep that matters most this week.

Deeper: Claude Code is where you practice the loop · outside Core 30
Your tools

Claude Code is where you practice the loop

Everything across both halves of today has a home in Claude Code. Your system prompts, few-shot examples, and output schemas aren't ephemeral things you type into a chat box and lose — they're artifacts you keep in your repo, version, and iterate on like any other source file. A prompt that lives in a file, with an eval set next to it, is a prompt you can improve over ten weeks. A prompt that lives in your chat history is gone by Thursday.

This is also the most token-efficient way to work. The requirements-synthesis move saves tokens, not just makes better software: every hour you spend pinning down what "the important stuff" means is an hour you don't spend re-running a vague prompt and squinting at why the output keeps drifting. Tight schema, low temperature, a small eval set you run deliberately — that's a few cents and a few minutes. "Keep poking at the prompt in chat until it feels right" is how you hit your daily limit by lunch with nothing reusable to show. Token discipline and engineering discipline are, once again, the same discipline.

FDE mindset

When a client hands you "can the AI just handle this," the value you add isn't a clever prompt — it's the conversation that turns that sentence into a spec. What must be structured? What must be deterministic? What must be grounded? Answer those three and the prompt practically writes itself; skip them and the best prompt in the world solves the wrong problem. Synthesize the requirements before you engineer the prompt.

Deep dive: a weak prompt, hardened part by part

Optional. ~6 minutes. Watch the six slices turn one lazy line into a prompt you could ship.

Where everyone starts. A teammate needs to extract fields from incoming solicitations and writes the prompt in fifteen seconds:

Summarize the important parts of this solicitation.

It demos fine and fails in production: prose instead of data, a different shape every run, invented values when a field is missing, and no way to tell a good output from a bad one. Now harden it, one slice at a time.

The engineered prompt — every slice doing one job
SYSTEM  (the standing contract)
  You are a solicitation-extraction assistant for a federal
  acquisitions team. Extract fields ONLY from the document in
  <document> below. If a field is absent, return null — never
  infer or guess. Respond with JSON matching the schema and
  nothing else.

EXAMPLE  (teach format by showing — one shot)
  <document>…RFP text…due 31 Mar 2026…</document>
  → {"solicitation_number":"W912-26-R-0042",
     "due_date":"2026-03-31","set_aside":"small_business"}

REASON  (scratch, then commit)
  Think step by step in a scratchpad, then emit only the JSON.

USER SLOT  (the one variable part, delimited)
  <document>{the incoming solicitation text}</document>

OUTPUT  (schema-locked)
  { solicitation_number, agency, due_date(date|null),
    set_aside(enum), naics_code, description }   temp ≈ 0

Read what each slice bought you. The system prompt states the role, the "answer only from the document / return null" rule, and "JSON only" — at the edges where the model weights them most. The one example locks the field names and the date format that prose would have left to chance. The reason-then-emit order gives a tricky buried-date document room to work without polluting the output. The delimited user slot keeps the document as data, not instructions. The schema makes "missing" a sanctioned null and an enum impossible to free-text. None of it is a magic phrase — it's six small contracts.

Then close the loop. Drop fifteen real solicitations — including one with a buried due date and one that isn't a solicitation at all — into an eval file with the extraction you'd accept for each. Run the prompt, look only at the failures, change one slice, re-run. That bundle — the engineered prompt plus its eval set — is what makes the prompt improvable over ten weeks instead of a thing you re-guess every Thursday.

Deep dive: a vague ask, carried all the way to a schema

Optional. ~12 minutes. The rep that matters most this week — watch the synthesis happen.

The ask, as you'd actually hear it. A program manager at a federal acquisitions client says: "Our analysts spend hours reading incoming solicitations to figure out which ones we should bid on. Can the AI just read them and pull out the important stuff so they can triage faster?" That is the entire brief. Watch how an FDE turns it into a spec — by interrogation, not by jumping to a prompt.

Question 1 — what is "the important stuff," concretely? You don't guess; you ask, and you keep asking until you have a list. After ten minutes with the PM and one analyst it's: solicitation number, issuing agency, response due date, estimated contract value, set-aside type (e.g. small business), the NAICS code, and a one-line description of the work. "Important stuff" just became seven named things — and you discovered that "is this a re-compete of an existing contract" matters to them too, which the original ask never hinted at.

Question 2 — who consumes the output? A triage dashboard the analysts sort and filter. That single answer is decisive: the output must be structured data, not a prose summary. You're building an extractor, not a summarizer. (Had the answer been "an analyst reads it over coffee," prose might have been fine — same ask, different system.)

Question 3 — what's the cost of an error? A wrong or missed due date can cause them to miss a bid worth millions — catastrophic. A slightly-off description is a minor annoyance. So accuracy requirements are not uniform across fields: due date and solicitation number need near-certainty and human review; the description can be best-effort. That asymmetry shapes both the schema and the eval set.

Question 4 — deterministic? Yes. Two analysts running triage on the same solicitation must see the same extracted due date, or trust collapses. → low temperature, tight schema, and an eval check that the same input yields the same output.

Question 5 — grounded? Every field must come from the document in front of the model. The model must never infer a due date from "documents like this usually." If a field isn't in the document, the correct answer is null — an honest miss, not a confident guess.

The synthesized output schema (JSON Schema, abbreviated)
{
  "type": "object",
  "properties": {
    "solicitation_number": { "type": ["string","null"] },
    "agency":              { "type": ["string","null"] },
    "due_date":            { "type": ["string","null"], "format": "date" },
    "estimated_value_usd": { "type": ["number","null"] },
    "set_aside":           { "type": "string",
                             "enum": ["small_business","8a","sdvosb","none","unknown"] },
    "naics_code":          { "type": ["string","null"] },
    "is_recompete":        { "type": ["boolean","null"] },
    "description":         { "type": ["string","null"] }
  },
  "required": ["solicitation_number","due_date","set_aside"]
}

Read what the schema is doing for you. Every fact field is nullable — that is the sanctioned "not found in the document" that kills hallucinated values. The high-stakes fields, meaning the solicitation number, the due date and the set-aside, are required, which forces the model to commit to a value or an explicit null rather than silently omitting them. The set_aside field is an enum, so it physically cannot come back as freeform prose. The schema has already encoded half your rules before you wrote a line of system prompt.

And now the system prompt practically writes itself: "You are a solicitation-extraction assistant. Extract the fields in the schema only from the document provided below. If a field is not present in the document, return null — never infer or guess. Respond with JSON matching the schema and nothing else." Pair it with temperature ≈ 0, one or two few-shot examples drawn from real solicitations (especially a tricky one where the due date is buried), and a 15-document eval set with known-correct extractions. That bundle — schema + system prompt + temperature + grounding rule + eval set — is the deliverable. The clever prompt was never the hard part; the synthesis was.

Note on API specifics. Exactly how you attach a schema (a structured-output / JSON-mode parameter, a tool/function definition, or a response-format field) is a per-provider, per-model detail that shifts over time — confirm it against current docs the day you wire it up. The durable skill is the one practiced here: decide the shape, the determinism, and the grounding first; the mechanism is the easy part once the spec is right.

Production code: the hardened prompt

The lazy “summarize this” turned into a shippable call — a role, one worked example, a JSON-shape instruction, and the document kept as delimited data.

# The engineered prompt from the reading, as a real call: role + one worked example
# + a JSON-shape instruction -- "summarize this" hardened into something you can ship.
# Auth: Bedrock API key in AWS_BEARER_TOKEN_BEDROCK (boto3 reads it; no IAM role).
import json, boto3

bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")

SYSTEM = """You extract fields from federal solicitations. Reply with ONLY JSON matching:
{"solicitation_id": str, "due_date": "YYYY-MM-DD", "set_aside": "small_business"|"none", "value_usd": number|null}
If a field is not stated, use null -- never guess.

Example input:  RFP 36C10X26, replies by July 9 2026, full and open.
Example output: {"solicitation_id":"36C10X26","due_date":"2026-07-09","set_aside":"none","value_usd":null}"""

doc = "Solicitation N00024-26-R-3007, responses due 2026-08-15, set-aside: small business, est. $4.2M."

resp = bedrock.converse(
    modelId="us.anthropic.claude-haiku-5-5",
    system=[{"text": SYSTEM}],
    # user input stays DATA, wrapped in delimiters -- never instructions
    messages=[{"role": "user", "content": [{"text": f"<solicitation>\n{doc}\n</solicitation>"}]}],
    inferenceConfig={"maxTokens": 300, "temperature": 0},
)

fields = json.loads(resp["output"]["message"]["content"][0]["text"])
print(fields["due_date"])   # 2026-08-15

temperature 0 plus the worked example pins the format; the reply parses straight into fields your code can trust — shape, not yet truth.

Production code: the synthesized spec

The three lenses become three concrete settings on one call — structured (JSON out), deterministic (temperature 0), and grounded (answer only from the document, null when missing).

# The vague ask, synthesized into a call: the three lenses become concrete settings.
# Auth: Bedrock API key in AWS_BEARER_TOKEN_BEDROCK (boto3 reads it; no IAM role).
import json, boto3

bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")

# GROUNDED: answer only from the document; null for missing -- never invent a due date.
SYSTEM = ("You are a solicitation-extraction assistant. Extract fields ONLY from the "
          "document provided. If a field is absent, return null -- never infer or guess. "
          "Respond with JSON for {solicitation_number, agency, due_date, set_aside} and nothing else.")

def extract(doc: str) -> dict:
    resp = bedrock.converse(
        modelId="us.anthropic.claude-haiku-5-5",
        system=[{"text": SYSTEM}],
        messages=[{"role": "user", "content": [{"text": f"<document>\n{doc}\n</document>"}]}],
        # DETERMINISTIC: temperature 0 so two analysts get the same extraction.
        inferenceConfig={"maxTokens": 400, "temperature": 0},
    )
    # STRUCTURED: the reply is JSON your dashboard can ingest -- validate on the way in.
    return json.loads(resp["output"]["message"]["content"][0]["text"])

The synthesis was the hard part; once structured, deterministic, and grounded are decided, the call practically writes itself.
