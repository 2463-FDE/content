Prompt Engineering: Interface Design, Not Incantation

Week 1 · Day 3 · Part 1 Engineering the Prompt ~20 min · reading @150 wpm + diagram + check

Day 1 you learned the context window is a budget. Day 2 you picked a model and made the call survive production. Today you learn what to put in that window on purpose. Prompt engineering isn't magic words — it's interface design for a system that can't read your mind, assembled part by part and measured like code. Scroll the reading; the panel on the right builds one engineered prompt slice by slice — system prompt, examples, reasoning scaffold, the user input slot, and a schema-locked output — then closes the loop with an eval set. Part 2 (next page) takes this discipline one level up: how an FDE turns a client's vague ask into the requirements you engineer against.

The whole game

A prompt is an interface, not an incantation

The internet is full of "prompt hacks" — magic phrases, all-caps threats, "you are a world-class expert" preambles. Forget almost all of it. Here is the framing that serves you for the rest of your career: a prompt is the interface between your software and a probabilistic text engine. Engineering it well is the same discipline as designing any contract between two systems — you specify, as precisely as you can, what goes in, what must come out, and what the rules are in between.

That reframing changes what "good" means. A good prompt is not the cleverest-sounding one. It's the one that produces the right output shape, reliably, at an acceptable cost, for every input your system will actually see — not just the one you tested in the playground at 2pm on a Tuesday. The model is non-deterministic by nature; your job is to remove as much ambiguity as you can so the variation that remains is variation you can live with.

Everything today decomposes a prompt into parts you can engineer independently: the system prompt (the standing contract), examples (teaching by showing — zero, one, or few-shot), a reasoning scaffold (chain-of-thought, giving the model room to work), the user input slot (the one part that changes per call, plus the grounded context you inject there), and the output contract (structured output / JSON mode pinned to a schema). Then we close the loop with iteration and eval — treating the prompt as code you measure, not prose you admire.

Notice that nothing here is model-specific folklore — it's the engineering posture you'd bring to any unreliable dependency. Imagine calling a flaky third-party API that sometimes returns exactly what you asked for and sometimes returns a friendly paragraph apologizing for not understanding. You wouldn't "trick" it with magic words; you'd write the tightest possible request, validate every response, and build tests around it. A language model is precisely that dependency, and every technique today is that same discipline applied to a system whose output happens to be natural language.

Slice 1 · the contract

The system prompt is the standing contract

You met the system prompt on Day 1 as "the first slice of the window, paid on every call." Today we look at what it's for. The system prompt encodes everything that should be true on every request regardless of what the user types: the model's role ("you are a contract-intake assistant for a federal acquisitions team"), the rules ("never invent a solicitation number; if a field is missing, return null"), the output format ("respond only with JSON matching the schema below"), and the guardrails ("do not give legal advice; flag anything that looks like PII").

The most common beginner mistake is treating the system prompt as a junk drawer — dumping every instruction, edge case, and "oh and also" into a 2,000-token wall of text. Remember the budget: that wall is prepended to every call forever, and worse, models reliably follow a tight, well-ordered instruction set better than a sprawling one. Past a certain length, extra instructions don't just cost tokens; they dilute attention and the model starts dropping rules. More instruction is not more obedience.

Two habits make system prompts strong. First, put the most important, least-negotiable rules first and last — models weight the beginning and end of the context more heavily than the middle (the "lost in the middle" effect you'll meet again in Week 2's RAG work). Your hard constraints — "output JSON only", "never fabricate" — belong at the edges, not buried in paragraph six. Second, prefer positive, concrete instructions over negative, vague ones. "Return the date as YYYY-MM-DD" beats "don't format dates weirdly." The model can act on a concrete target; it struggles to infer what you meant by "weirdly."

A third habit, expensive to skip: state the failure behavior explicitly. Most system prompts describe the happy path — "extract the fields" — and go silent on what to do when the input is malformed, empty, off-topic, or missing the requested information. The model then improvises, and its improvisation is rarely what you'd choose. Spell it out: "If the document contains no due date, return null. If the input is not a solicitation at all, return all fields as null and set a valid flag to false." This is the same instinct as writing the else branch and the error handler in ordinary code — you just write it in English. And note the FDE distinction: the system prompt encodes policy, the user message carries data. When a client says "the AI keeps ignoring our compliance rule," the fix is almost never in the user message — it's that the rule was never stated in the system prompt, or was buried so deep it got drowned out. Diagnose the contract before you blame the model.

Slice 2 · teach by showing

Zero, one, and few-shot: examples teach format

There are three points on a spectrum, and naming them precisely keeps you honest. Zero-shot means you describe the task and give no examples — "classify this support ticket as billing, technical, or account." One-shot includes exactly one worked example of input → desired output. Few-shot includes a handful — typically two to five. The jump that matters most is from zero to one or two: a single concrete example often locks in a format, tone, or edge-case handling that a whole paragraph of description fails to convey.

Why examples beat description: language is lossy. If you want output that looks like {"category": "billing", "confidence": 0.9}, you can describe that in words and the model will mostly comply. But show it two real examples and it will nearly always comply — including the subtle things you forgot to describe: whether confidence is 0–1 or 0–100, whether category is lowercase, what to do when the ticket is ambiguous. Examples carry the tacit rules you didn't know you had. Few-shot has a second superpower: it handles edge cases by demonstration. If your classifier keeps mis-handling tickets that mention two topics, add one example of a two-topic ticket with the desired resolution. You've taught the behavior without writing a single new rule.

But the cost discipline from Day 1 applies directly: every example is tokens in the window on every call, and the benefit has steep diminishing returns — zero to two is transformative, eight to twelve usually isn't, and a giant example block can crowd out the user's real input. The best-practice prompt above shows the move: one demonstrated input→output pair pins the format far more reliably than another paragraph of description — but that demonstrated pair is tokens you re-send on every single request. So the FDE question is never "do examples help?" (they do) but "what is the fewest examples that hits my quality bar?" Start at zero, measure, add one or two aimed squarely at the failures you observe, measure again.

There's a subtler trap worth naming. Few-shot examples don't just teach format — they quietly teach distribution. If all three of your examples classify as "billing," the model picks up a bias toward "billing" that has nothing to do with the input in front of it; if they're all short and tidy, it handles long messy input worse. The examples are training data for this one call, and like any training data they carry whatever skew you didn't notice. So balance the classes, vary the length and messiness, and include at least one of the cases that's currently failing — a deliberate act, not grabbing the first three rows of a spreadsheet.

Slice 3 · room to think

Chain-of-thought: give the model room to reason

For any task that involves multiple steps — math, multi-condition logic, comparing options, applying a rule with exceptions — the single most reliable quality lever is letting the model reason before it answers instead of forcing an immediate verdict. This is chain-of-thought (CoT) prompting. The classic trigger is as simple as "think step by step," but the real mechanism is deeper: because the model generates one token at a time and each token it writes becomes context for the next, the intermediate reasoning it writes out literally becomes scratch space it can compute against.

That mechanism explains a counterintuitive truth: asking for the answer first and the reasoning after is worse than useless. If your prompt says "give the answer, then explain," the model has already committed to the answer before it did any thinking — the explanation is a post-hoc story, not the path that produced the conclusion. Order matters: reasoning, then conclusion. When you also want a structured final answer, the standard pattern is "reason in a scratchpad, then output the final result in the required format" — you get the accuracy benefit of thinking and the clean output your code needs.

CoT is not free, and this is where it intersects with Day 1 and 2. Reasoning is output tokens, and output tokens are the expensive ones. A task that answered in 50 tokens might now spend 400 thinking out loud. For a hard reasoning task that's a bargain — you turned a wrong answer into a right one. For a trivial classification it's pure waste. So the FDE judgment is match the reasoning budget to the task's actual difficulty. Be aware, too, that some newer models do this reasoning internally as a built-in mode rather than something you prompt for — the technique-level idea is what's durable: steps that need thinking get room to think, before they commit. The exact knob to request it is a per-model API detail to confirm against current docs the day you wire it up.

A close cousin of chain-of-thought is decomposition: instead of asking one prompt to do a hard, multi-part job at once, break it into a small chain of narrower prompts, each doing one thing well. "Extract the clauses" → "classify each clause" → "flag the conflicts" can be three focused calls instead of one overloaded one. Each step is easier to write, test in isolation, and debug. The cost is more calls and more tokens, so it's a trade — but a prompt trying to do five things at once is usually a sign you haven't finished thinking, the same way a 200-line function usually is. It also sets you up for the agentic decomposition you'll build in Week 3.

Slice 4 · the variable part

The user input slot — and grounding it in real context

Everything so far — system prompt, examples, reasoning instructions — is fixed scaffolding that's the same on every call. The user input slot is the one part that changes per request: the actual ticket to classify, the actual contract to summarize, the actual question to answer. Keeping a crisp mental line between the fixed scaffold and the variable slot is one of the cleanest habits in the discipline, because it's exactly the line your code has to respect.

That blurred line is how you get prompt injection and parsing chaos. The defensive habit — treat user input as data, never as instructions — is why you wrap it in delimiters and say so explicitly in the system prompt. The user slot is also where grounding happens, and this is the bridge to Week 2's entire RAG curriculum, so plant the seed now. Most real client value isn't the model answering from its own training; it's the model answering about the client's data: their contracts, their tickets, their policy documents — facts the model was never trained on and cannot know. Grounding means retrieving the relevant facts and placing them, as text, into the window alongside the user's question, so the model reasons over those facts rather than guessing. The user slot is where that retrieved context lands.

This connects straight back to Day 1's hallucination model. A hallucination is, nine times out of ten, a fact that was never in the window. Grounding is the cure: don't ask the model what it "knows," give it the source and ask it to answer from the source — and, crucially, instruct it to say "not found in the provided context" rather than fill the gap. "Answer only from the context below; if the answer isn't there, say so" is one of the highest-leverage sentences in applied prompt engineering. It converts a confident fabrication into an honest miss — which, at a federal client where a wrong contract number has real consequences, is exactly the trade you want.

It helps to picture the assembled prompt as a template with one hole in it. The system prompt, examples, reasoning instructions, and schema are the template — written once, reviewed, version-controlled, tested. The user slot is the hole, filled at runtime. When something breaks, that boundary is your first diagnostic cut: is the problem in the fixed template (affects every call) or in what got injected into the slot this time (affects only some inputs)? Most "the AI is acting weird today" reports resolve cleanly along that line.

Slice 5 · the output contract

Structured output: pin the shape with a schema

Here's the part that separates a demo from a system. In a chat window, freeform prose is fine — a human reads it. But in software, the model's output is almost always consumed by more code: stored in a database, passed to an API, rendered in a UI, used to drive a decision. Code cannot reliably parse "Sure! The contract value looks like about $1.2 million and it expires next March 🙂". Code needs {"value_usd": 1200000, "expiry": "2026-03-31"}. Structured output is the discipline of making the model return data in a shape your code can trust.

The weakest form is just asking nicely: "respond in JSON." It works often and fails occasionally — and "occasionally" at scale means a steady drip of parse errors, wrapped-in-markdown fences, trailing commentary ("Here's your JSON:"), and the dreaded truncated object. A stronger form is JSON mode / structured output features that constrain generation so the output is guaranteed to be syntactically valid JSON, and in the strongest variants, guaranteed to conform to a schema you supply — exact field names, types, required fields, allowed enum values. When the API can enforce the schema, a whole class of "the model returned something weird" bugs moves from runtime surprise to impossible.

A schema is just a precise, machine-readable description of the output shape — usually JSON Schema. It says: there is a field category that must be one of ["billing","technical","account"]; a field confidence that's a number; and category is required. Writing the schema first is a powerful design act, because it forces you to decide exactly what you need before you write a word of prompt. A good schema does half the prompt-engineering for you: an enum field can't come back as freeform text, a required field forces the model to commit, a nullable field gives it a sanctioned way to say "missing" instead of inventing.

Two FDE cautions. First, structured does not mean correct. The schema guarantees the shape — that you got a valid date string — not the truth — that it's the right date. You still need grounding and eval for correctness; schema only kills the parsing failures. Second, even with strong schema enforcement, build your consuming code to be defensive: validate the parsed object on the way in, decide in advance what happens when a required field is null, and log the raw output when validation fails. The model returns well-shaped data 99% of the time; your job is to make the other 1% degrade into a handled error rather than a silently-wrong record written to the client's database — the kind of thing that turns into a very uncomfortable meeting at a federal client.

Slice 6 · close the loop

Iteration and eval: treat the prompt like code

The amateur writes a prompt, tries it once on a happy-path example, sees it work, and ships. The practitioner knows that "worked once in the playground" tells you almost nothing about behavior across the messy distribution of real inputs. The discipline that closes the gap is evaluation: building a small set of representative inputs with known-good answers — a "golden set" — and measuring your prompt against all of them, every time you change it.

This is the mindset shift that makes everything above engineering instead of guesswork: a prompt is code, and code without tests is a liability. When you tweak the system prompt to fix one client's edge case, how do you know you didn't break three cases that used to pass? You don't — unless you re-run the eval set. Prompts are especially treacherous because changes are non-local: a word added to the system prompt can shift behavior on inputs that have nothing obviously to do with it. Without an eval set you are flying blind and calling it intuition.

An eval set doesn't have to be fancy to be transformative. Ten to twenty real, diverse inputs — pulled from the client's actual data, including the ugly edge cases — with the output you'd accept for each, in a file. For structured output you can often check correctness automatically (did the JSON parse? did category match the expected enum?). For fuzzier tasks you self-grade or use a second model as a judge (a technique you'll meet later). The point isn't sophistication; it's having a ground-truth you measure against instead of vibes. Week 6's deliverable is literally an eval report — this is where that habit starts.

The iteration loop, then, is tight and repeatable: write the smallest prompt that could work → run it against the eval set → look at the failures specifically, not the successes → make one targeted change → re-run → keep the change only if the score went up. Change one thing at a time so you actually learn what helped. Two failure modes to guard against: overfitting (tune relentlessly against the same fifteen examples and you memorize the test instead of improving the behavior — keep some in reserve), and grading drift (when self-scoring fuzzy outputs, write down what "acceptable" means before you tune). By Week 6 you'll hand the client an eval report as a formal deliverable, and one built on a memorized or drifting set is false confidence with your name on it. Measure, change one thing, re-measure. That loop is the whole job.

Deep dive: a weak prompt, hardened part by part

Optional. ~6 minutes. Watch the six slices turn one lazy line into a prompt you could ship.

Where everyone starts. A teammate needs to extract fields from incoming solicitations and writes the prompt in fifteen seconds:

Summarize the important parts of this solicitation.

It demos fine and fails in production: prose instead of data, a different shape every run, invented values when a field is missing, and no way to tell a good output from a bad one. Now harden it, one slice at a time.

The engineered prompt — every slice doing one job
SYSTEM  (the standing contract)
  You are a solicitation-extraction assistant for a federal
  acquisitions team. Extract fields ONLY from the document in
  <document> below. If a field is absent, return null — never
  infer or guess. Respond with JSON matching the schema and
  nothing else.

EXAMPLE  (teach format by showing — one shot)
  <document>…RFP text…due 31 Mar 2026…</document>
  → {"solicitation_number":"W912-26-R-0042",
     "due_date":"2026-03-31","set_aside":"small_business"}

REASON  (scratch, then commit)
  Think step by step in a scratchpad, then emit only the JSON.

USER SLOT  (the one variable part, delimited)
  <document>{the incoming solicitation text}</document>

OUTPUT  (schema-locked)
  { solicitation_number, agency, due_date(date|null),
    set_aside(enum), naics_code, description }   temp ≈ 0

Read what each slice bought you. The system prompt states the role, the "answer only from the document / return null" rule, and "JSON only" — at the edges where the model weights them most. The one example locks the field names and the date format that prose would have left to chance. The reason-then-emit order gives a tricky buried-date document room to work without polluting the output. The delimited user slot keeps the document as data, not instructions. The schema makes "missing" a sanctioned null and an enum impossible to free-text. None of it is a magic phrase — it's six small contracts.

Then close the loop. Drop fifteen real solicitations — including one with a buried due date and one that isn't a solicitation at all — into an eval file with the extraction you'd accept for each. Run the prompt, look only at the failures, change one slice, re-run. That bundle — the engineered prompt plus its eval set — is what makes the prompt improvable over ten weeks instead of a thing you re-guess every Thursday.

Day 3 · Part 1 — goals & deliverable

By the end of Part 1 you can
  • Frame a prompt as an interface you design — and name its parts: system prompt, examples (zero/one/few-shot), reasoning scaffold, user input slot, output schema — and what each is for
  • Choose chain-of-thought, few-shot, and a JSON schema deliberately, with the token cost in mind
  • Keep user input as data behind delimiters, and ground answers in retrieved context with a sanctioned "not found"
