Output Guardrails: Never Trust the Response Raw

Week 1 · Day 4 · Part 2 Reliability Engineering Core 30 · AWS · ~6 min read · 2 interactions · 7-Q check · ~22 min required Core 30 · GCP · ~6 min read · 2 interactions · 7-Q check · ~22 min required

Part 1 made each call cost less. Part 2 makes each response trustworthy. The hard truth about LLM output is that it's generated text, not a guaranteed data structure — and in production it flows straight into a database, an email, or another system with nobody reading every word. Four guardrails stand between the model and the user: schema validation, bounded retry-on-invalid, hallucination mitigation, and a safe fallback for when nothing worked. The whole game

Cross from cost to trust: the output is not a contract

Part 1 was about the tokens going in. Part 2 is about the tokens coming back, and a different, harder bar: safe enough to put in front of a real user. A prototype trusts the model's output because a human is reading every word; production has to assume nobody is watching and the output flows straight into a database, an email, or another system. The amateur calls the model and uses what it returns. The professional treats every response as untrusted input until a guardrail says otherwise.

The hard truth is that LLM output is generated text, not a guaranteed structure. You ask for JSON; most of the time you get clean JSON; some of the time you get JSON wrapped in a chatty preamble, or with a trailing comma, or a renamed field, or a string where you needed a number — or a perfectly-formed object that's missing the one field your downstream code requires. And even when the shape is flawless, the facts can be invented. In a prototype a human notices and shrugs. In production that response corrupts a record or reaches a customer.

Four guardrails, in order. Schema validation — never trust the shape. Retry on invalid — give the model a second, bounded chance. Hallucination mitigation — defend against confident wrongness that passes the schema. And refusal & fallback — decide in advance what happens when nothing worked. The diagram on the right is the loop: model output enters, the gates check it, and it ends only as a shipped result or a safe fallback — never as a raw exception on the user's screen.

Guardrail 1 · Schema validation

Schema validation: never trust the shape of the output

Schema validation is the first gate: you define, in code, the exact shape the output must take — these fields, these types, these required keys, these allowed values — and you validate every response against it before you act on it. If it conforms, proceed. If it doesn't, you've caught the problem at the boundary instead of three systems downstream. This is the single highest-value reliability habit on this page, because it converts a silent, intermittent data-corruption bug into a loud, immediate, catchable error.

You have two complementary tools. The first is structured-output features the provider gives you — telling the API up front "responses must match this JSON schema," so the model is constrained to produce conforming output. This dramatically raises the hit rate. The second, which you keep even when you use the first, is your own validation layer — a schema check in your code (a Pydantic model, a Zod schema, a JSON-schema validator) that re-verifies every response. Belt and suspenders is the correct posture, because "almost always conforms" is not "always conforms," and the cost of the one bad response slipping through is paid by your client's data integrity. Validate the shape before you trust the content.

Deeper: why one schema check is the best trade on the page

Think about the asymmetry that makes this the highest-value habit on the page. Without validation, a malformed response doesn't announce itself — it parses into something subtly wrong and quietly corrupts a record, and you find out weeks later when a customer notices their data is off. With validation, the same bad response throws at the boundary, on the very call that produced it, with the exact field and type that failed. You've converted a silent, intermittent, expensive-to-diagnose data bug into a loud, immediate, trivially-loggable error you can route to a retry or a fallback. One schema check buys you that trade on every single call, forever — which is why an FDE adds it before anything else and never takes it out.

Deeper: Retry-on-invalid: a second chance, but a bounded one · outside Core 30
Guardrail 2 · Retry on invalid

Retry-on-invalid: a second chance, but a bounded one

Catching a bad response answers "is this output usable?" The next question is "what do I do when it isn't?" The first-line answer is retry-on-invalid-output: when validation fails, ask again. But how you retry separates the amateur from the engineer.

Practice (optional): which retry actually fixes it?

A naive retry just re-sends the identical request and hopes the dice land differently. That sometimes works — especially above temperature zero, where randomness alone may produce a conforming answer. But the smart retry feeds the failure back into the prompt: "Your previous response was not valid JSON — it was missing the required total field. Return only valid JSON matching this schema." Now the model knows specifically what went wrong and is far likelier to fix it. The error message becomes context that steers the next attempt.

Two non-negotiable rules make retry safe in production. First, bound it. Retry once, maybe twice or three times — never in an unbounded loop. An LLM that keeps producing invalid output will happily do so forever while you burn tokens and stall the user; cap the attempts and treat "still invalid after N tries" as a real failure with its own handling. Second, account for the cost. Every retry is another full billable call — a feature with a 30% retry rate costs noticeably more than its happy-path math suggests, which is exactly why the per-run cost tracking from Part 1 matters. A bounded, feedback-driven retry loop is one of the most reliable patterns you'll build all program.

Deeper: Hallucination mitigation: defend against confident wrongness · outside Core 30
Guardrail 3 · Hallucination

Hallucination mitigation: defend against confident wrongness

Schema validation catches malformed output. It does not catch the more insidious failure: output that is perfectly well-formed and completely wrong. A hallucination — Day 1's confident, fluent, fabricated answer — sails straight through a JSON validator because the JSON is valid; only the facts are invented. So hallucination needs its own layer, and Day 1 already told you where to aim it: the model hallucinates most when the fact it needed was never in the window.

Practice (optional): the schema passed — is it safe to ship?

That diagnosis drives the mitigations, and they're mostly about the window, not the model. Grounding is the biggest lever: put the source material in the window and instruct the model to answer only from it — "using only the provided documents, answer the question; if the answer isn't in them, say so." This is the heart of RAG, all of Week 2. Demand citations: require the model to point to where each claim came from — asking for citations measurably reduces fabrication because the model has to ground each statement rather than free-associate. Give it an exit: explicitly permit "I don't know," because the model has no built-in way to say "I wasn't given that," so it guesses unless you tell it silence is acceptable. And verify the high-stakes claims: for a number, a name, a policy, a cheap second check catches fabrications before they reach the user. The mindset: you'll fix far more hallucinations by managing the window than by swapping in a bigger model.

Deeper: Refusal & fallback: fail safe, never ship garbage · outside Core 30
Guardrail 4 · last line

Refusal & fallback: fail safe, never ship garbage

Even with validation, retries, and grounding, some requests still end in a bad place — the model refuses on safety grounds, every retry still returns invalid output, or the grounded context genuinely doesn't contain the answer. The final guardrail is deciding, deliberately and in advance, what happens when nothing worked. The wrong answer is to ship the broken response and hope. The right answer is to fail safe.

First, handle refusals as a real outcome. Models can decline to answer — a safety refusal is a distinct, expected response type, not an error, and modern APIs surface it explicitly with a reason. Your code must check for it before it reads the content, or it'll trip over an empty or partial response and crash. Treat a refusal as a branch in your logic: detect it, log it, and route to your fallback — never let it masquerade as a normal answer.

Second, define the fallback path for "we couldn't produce a trustworthy answer." Depending on the feature, that might be a graceful "I'm not able to help with that right now — let me connect you to a human," a handoff to a deterministic non-AI code path, a safe default, or an escalation to a person. Some platforms even let you specify an automatic model fallback. The unifying principle is that "no answer, cleanly handled" always beats "a wrong answer, confidently delivered." A user who's told the system can't help is mildly disappointed; a user who's given a fabricated account balance is harmed, and your client is liable.

Deeper: choosing the fallback per feature, in advance

The discipline here is choosing the fallback per feature, in advance — not improvising it inside an exception handler at 2 a.m. A customer-facing chatbot's fallback is a warm handoff to a human; a backend enrichment job's fallback might be to leave the field null and flag the row for review; a code generator's fallback is to surface the error and let the engineer write the function. What they share is that the failure mode is a designed outcome with its own path, logged so you can measure how often you hit it — a rising fallback rate is an early signal that something upstream (the prompt, the grounding, the model) has drifted and needs attention before users feel it.

Step back and see the whole loop: output comes back; you validate its shape; invalid output triggers a bounded retry that feeds the error back; well-formed output is checked for hallucination; and anything that still can't be trusted — a refusal, an exhausted retry budget, an ungrounded claim — hits a safe fallback instead of the user. That loop is the diagram on the right, and it's the difference between a demo and a production feature.

On your cloud · managed guardrails

The managed guardrail layer: what it catches, what stays in your code

Your code owns the loop above. Both clouds also sell a managed screening layer that inspects prompts and responses against policies you configure, outside your application logic. Use it for the policy-shaped failures — unsafe content, prompt attacks, leaked personal data — and keep asking the same question of it that you ask of the model: which of the four guardrails does this actually cover? Open your path; the other cloud stays as an optional comparison.

AWSAmazon Bedrock Guardrails

Bedrock Guardrails applies configurable safeguards to user inputs and model responses: content filters (hate, insults, sexual, violence, misconduct, and prompt attack) with an adjustable strength, denied topics, word filters, and sensitive information filters that block or mask PII. Two safeguards reach into Guardrail 3: contextual grounding checks flag a response that isn't grounded in the supplied source or doesn't answer the query, and Automated Reasoning checks test a response against logical rules you define. The ApplyGuardrail API runs the same guardrail on any text without invoking a model, so one policy can screen inputs and outputs anywhere in your flow. It still sits beside your schema check and bounded retry, not instead of them.

GCPModel Armor

Model Armor screens prompts before they reach the model and responses before they reach the user, and reports which filters triggered. You configure it with templates — Google's guidance is a separate template for inputs and for outputs. Its documented filters are responsible-AI safety (hate speech, harassment, sexually explicit, dangerous content), prompt injection and jailbreak detection, Sensitive Data Protection for PII and other sensitive data, and malicious URL detection. Deeper: you already run these guardrails by hand

Both days map onto how you actually work. When you read Claude Code's output critically before pasting it into your codebase — does it actually compile, does that function exist, is that API real — you're doing output validation and hallucination mitigation by hand. When you re-prompt with "that import doesn't exist, here's the actual error" instead of blindly re-running, that's feedback-driven retry. And when a generated approach is clearly wrong and you fall back to writing the function yourself, that's your safe fallback. The instinct to never trust generated output raw is the same one a client pays an FDE to bring to production.

Deep dive: the guardrail loop

Optional. ~6 minutes. Validation, retry, and fallback assembled into one function.

A bounded, feedback-driven loop that ties the four guardrails together — validate the shape, feed failures back, cap the attempts, check refusals before reading content, and end every untrusted path in a safe fallback:

def call_guarded(prompt, schema, max_tries=3):
    err = None
    for attempt in range(max_tries):
        msg = prompt if err is None else (
            prompt + f"\nYour last reply was invalid: {err}. "
                     f"Return ONLY valid output matching the schema.")
        resp = model.call(msg)            # 1 billable call each loop
        if resp.refused:                  # check refusal BEFORE reading content
            return fallback("model declined")
        try:
            data = schema.validate(resp.text)   # shape guardrail
            return data                          # ✓ valid → ship
        except ValidationError as e:
            err = str(e)                         # feed the failure back
    return fallback("invalid after retries")     # fail safe, never ship garbage

Three things make it production-grade: the retry feeds the specific error back so the next attempt is steered, not just re-rolled; the loop is bounded (no infinite token burn); and every exit that isn't a clean validated result lands in fallback() — a refusal, an exhausted retry budget, anything untrusted — so a malformed answer never reaches the user.

What this loop doesn't catch: a well-formed but fabricated value passes schema.validate cleanly. Hallucination is a separate layer — grounding, demanded citations, an "I don't know" exit, and a cheap source-check on high-stakes facts — bolted on around this loop, not inside it. Schema guards the shape; grounding guards the facts.

Production code: forced structured output

The schema is the output contract, enforced at the source. On AWS a forced tool call returns guaranteed-shaped JSON; on GCP a response schema does the same — a real number in total, not the string '1,250.00'.

# Force valid structured output at the source: a tool schema the model must fill.
# Auth: Bedrock API key in AWS_BEARER_TOKEN_BEDROCK (boto3 reads it; no IAM role).
import boto3

bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")

# The tool's inputSchema IS your output contract -- required fields can't be omitted,
# and a number field can't come back as a string.
tool_config = {
    "tools": [{"toolSpec": {
        "name": "record_invoice",
        "description": "Record the fields extracted from an invoice.",
        "inputSchema": {"json": {
            "type": "object",
            "properties": {
                "total": {"type": "number"},
                "due_date": {"type": "string", "description": "YYYY-MM-DD"},
                "vendor": {"type": "string"},
            },
            "required": ["total", "due_date", "vendor"],
        }},
    }}],
    "toolChoice": {"tool": {"name": "record_invoice"}},   # force the tool -> guaranteed shape
}

resp = bedrock.converse(
    modelId="us.anthropic.claude-haiku-5-5",
    messages=[{"role": "user", "content": [{"text": f"Extract the invoice:\n{raw_invoice}"}]}],
    toolConfig=tool_config,
    inferenceConfig={"maxTokens": 512, "temperature": 0},
)

# The model returns a toolUse block; input already matches the schema (total is a real number).
block = next(b for b in resp["output"]["message"]["content"] if "toolUse" in b)
invoice = block["toolUse"]["input"]   # shape guaranteed -- truth is not, so still validate
# Force valid structured output at the source: a response schema the model must match.
# Setup: pip install --upgrade google-genai
#   GOOGLE_CLOUD_PROJECT=<project>  GOOGLE_CLOUD_LOCATION=global  GOOGLE_GENAI_USE_ENTERPRISE=True
import json

from google import genai
from google.genai.types import HttpOptions

client = genai.Client(http_options=HttpOptions(api_version="v1"))

# response_schema IS your output contract -- with response_mime_type=application/json
# the reply is valid JSON of this shape; total comes back as a number.
invoice_schema = {
    "type": "OBJECT",
    "properties": {
        "total": {"type": "NUMBER"},
        "due_date": {"type": "STRING", "description": "YYYY-MM-DD"},
        "vendor": {"type": "STRING"},
    },
    "required": ["total", "due_date", "vendor"],
}

resp = client.models.generate_content(
    model="gemini-3.5-flash",
    contents=f"Extract the invoice:\n{raw_invoice}",
    config={
        "response_mime_type": "application/json",
        "response_schema": invoice_schema,
        "temperature": 0,
    },
)

invoice = json.loads(resp.text)   # shape guaranteed -- truth is not, so still validate

The shape is guaranteed; the facts are not — still validate on your side and keep a bounded retry plus fallback around this call.
