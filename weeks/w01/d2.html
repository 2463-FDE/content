Model Selection & API Patterns

Week 1 · Day 2 Choosing a model, then calling it reliably Core 30 · AWS · ~12 min read · 2 interactions · 9-Q check · ~29 min required Core 30 · GCP · ~11 min read · 2 interactions · 9-Q check · ~28 min required

Today is the first decision every Forward Deployed Engineer makes on an engagement — which foundation model do you build on, and how do you defend that choice to a client? — and the discipline that makes the choice survive production. The first half builds the six-axis selection framework around one concrete task (summarize a 40-page RFP, return JSON, 50,000 calls a day); the second half takes the model you picked and wraps the call in streaming, retries, idempotency, timeouts, and graceful failure on your selected cloud. One topic, one thread: pick defensibly, then call reliably.

Begin the brownfield engagement

Before recommending a model, establish what already exists. In one unfamiliar subsystem, use Claude Code only as a reading assistant: identify the system boundary, trace one business rule to a file and symbol, and label every inference that lacks evidence. Then compare Claude, GPT, Gemini, and an open-weight option on capability, cost, latency, context, ecosystem, and data boundary. The exercise below gives immediate feedback on whether your tier choice matches the workload rather than a leaderboard.

The whole game

"Which model should we use?" is a framework, not a leaderboard

The first question a client asks an FDE is almost always "which AI should we use?" — and they usually expect a one-word answer, the way "which database?" resolves to a name. The amateur answer names whatever model topped a benchmark last week. The professional answer is: it depends on what you're building, and here's how I'll decide. Model selection isn't a contest with a single winner. It's a constrained optimization across six axes that pull against each other, and the right model is the one that fits this task, this budget, and this client's rules — frequently not the most capable model on the market.

The landscape verified 2026-10-27 still has four broad options. Anthropic's Claude family currently spans Fable, Opus, Sonnet, and Haiku tiers. OpenAI's GPT family currently spans GPT-6 Astra, GPT-6.1 Sol/Terra, and GPT-6 Luna. Google's Gemini family includes Gemini 3.8 Flash. And the open-weight / self-hosted world — Llama, Mistral, DeepSeek, Qwen — lets you run inference on hardware you control. [sources: first-party Anthropic, OpenAI, and Google model/pricing pages, accessed 2026-10-27] Those names will move again; that is exactly why you learn the axes, not the names.

The six axes: capability, cost, latency, context window, tooling & ecosystem, and data residency / compliance. The diagram is the funnel: a task and its constraints enter at the top, each axis narrows the field, and a defensible pick falls out the bottom — with one rule attached. Walk the axes one at a time.

Axis 1 · Capability

Capability: fit to the task, not the top of the chart

Capability is the axis everyone over-weights. The instinct is to grab the smartest model and stop thinking. But "smartest" is expensive and slow, and most production tasks don't need it. The discipline is to match the model's capability tier to the hardest thing the task actually requires — and no higher. Every major vendor ships a tiered family precisely so you can: Anthropic's Opus / Sonnet / Haiku, Google's Pro / Flash / Flash-Lite, and OpenAI's Astra / Sol / Terra / Luna. The vendor is telling you, in pricing, not to run everything on the flagship.

The FDE move is to decompose the workload. A support feature might use a small cheap model to classify an inbound message ("billing, shipping, or technical?") and escalate only the genuinely hard conversations to a top tier. A document pipeline extracts structured fields with a mid-tier model and reserves the flagship for the final summary a human reads. This cheap-first, expensive-only-when-needed pattern is a model router or cascade, and you'll build a primitive version into nearly every engagement.

How do you judge capability for your task? Not from a public leaderboard — those measure generic benchmarks that may have nothing to do with the client's domain. You judge it with a small eval set: ten or twenty real examples from the client's actual data, with known-good answers, run against two or three candidates. The model that gets your examples right is more capable for you than whatever won an abstract benchmark. Capability is the first axis, but the one you measure last and most concretely.

That asymmetry drives design. A feature that reads a lot and answers briefly (classify, extract, label) is dominated by input cost — a cheap-input, big-context model wins. The FDE who can say "this endpoint costs $0.02 a call, runs 50,000 times a day, and we cut it 70% by moving the classification step to Haiku" is the one who keeps the engagement. For high-volume features, cost isn't a footnote to the model choice — it often is the model choice.

Deeper: Latency: how fast does the answer need to arrive? · outside Core 30
Axis 3 · Latency

Latency: how fast does the answer need to arrive?

Capability and cost get the headlines; latency quietly decides whether users tolerate the feature at all. A brilliant answer that arrives in nineteen seconds is the wrong answer for a chat box where the user expects two. Latency is a first-class axis, and like cost it splits the world cleanly in two.

Interactive workloads — a chatbot, an autocomplete, a "summarize this page" button — live or die on perceived speed, and the metric that matters is time-to-first-token (TTFT): how long until something appears. Part 2 shows streaming is the lever that turns a slow total response into a fast-feeling one, but the tier still sets the floor — smaller models (Haiku, Flash) aren't just cheaper, they're faster, often dramatically. For interactive features, the smallest model that's capable enough usually wins on latency and cost at once. Batch / asynchronous workloads — overnight processing of ten thousand documents, a nightly report — invert the priority: nobody's watching a spinner, so per-call latency barely matters and throughput plus cost dominate (Part 2's batch API does the same work at roughly half price for results in hours, not seconds).

The FDE habit is to ask "who is waiting, and for how long?" before anything else about the model. That sort eliminates whole columns of the options table before you've compared a single benchmark. The classic expensive mistake: a flagship model on a synchronous user-facing path "because it's the best," then a feature that feels broken because every interaction takes eight seconds. The best model that arrives too late is the wrong model.

Deeper: Context window: how much can you hand it, and what does that cost? · outside Core 30
Axis 4 · Context window

Context window: how much can you hand it, and what does that cost?

The context window — Day 1's central idea — is also a selection axis, because models differ in window size and the size you need is set by the task. As verified 2026-10-27, Anthropic lists a 1-million-token context window for all four current Claude tiers. [source: Anthropic Models overview, accessed 2026-10-27] A million tokens is a few thousand pages — an entire codebase, a long contract, a quarter of support transcripts in one call.

But a bigger window is not automatically better, and treating "1M context" as a pure win is a beginner error. Two costs ride along. First, dollars: you pay per token for everything in the window, so stuffing the whole document set into every call means paying for tens of thousands of tokens you don't need — Day 1's lesson that more retrieved text is not more intelligence; it's more budget spent. Second, attention: models can lose precision on facts buried in the middle of an enormous context, so a smaller, well-chosen window often produces a more accurate answer than a giant noisy one.

So the context question is really two. Does the model's max window comfortably exceed the largest input this task will realistically send? If the task is "answer questions about a 300-page manual," you need room for the manual plus the conversation plus the answer — and if no single model fits, that's a strong signal you need retrieval (RAG, all of Week 2), not a bigger model. And what will it cost to fill the window you actually use? A huge window with expensive input can lose to a smaller window with cheap input, if your real inputs fit the smaller one. Size the window to the task, then price the tokens you'll really send.

Deeper: Tooling & ecosystem: the model is half of what you're buying · outside Core 30
Axis 5 · Tooling & ecosystem

Tooling & ecosystem: the model is half of what you're buying

Here's the axis junior engineers forget entirely: you're not just choosing a model, you're choosing the platform around it. Two equally capable models can be worlds apart in how much engineering it takes to ship a reliable feature, because the surrounding tooling differs — and for an FDE on a deadline, that tooling is often the deciding factor.

What's in the ecosystem? Structured output — can you say "return JSON matching this exact schema" and have it guaranteed, rather than parse-and-pray? Tool / function calling — how cleanly the model calls out to your code and APIs, the entire foundation of the agentic systems you build in Week 3. Prompt caching — reusing a stable prefix at a fraction of the price (Anthropic prices cache reads at roughly a tenth of normal input). Batch APIs for async work. The maturity of the SDKs in your client's language. And whether mainstream agent frameworks and observability tools support the model first-class. Anthropic's standard cache-read multiplier is 0.1×, but the current Fable, Opus, and Sonnet pages document lower model-specific multipliers; verify the selected model instead of treating one discount as universal. [source: Anthropic prompt-caching docs, accessed 2026-10-27]

This is where the biggest vendors earn their keep beyond raw model quality. A model with mediocre benchmarks but a rock-solid SDK, native structured output, reliable tool calling, and prompt caching can get a working, affordable feature into production a week faster than a marginally smarter model with a thinner ecosystem — and a week is the entire budget on many FDE engagements. When you evaluate candidates, build a tiny end-to-end slice on each (one structured call, one tool call) and notice how much friction there was. That friction, multiplied across a project, is real cost the benchmark never shows. The model is maybe half of what you're buying; the ecosystem is the other half.

Deeper: Data residency, BAA & self-hosting: the axis that overrules the rest · outside Core 30
Axis 6 · Data residency & compliance

Data residency, BAA & self-hosting: the axis that overrules the rest

The final axis frequently vetoes every other axis at once. It doesn't matter that a model is smartest, cheapest, and fastest if the client is legally forbidden from sending it their data. For a federal-acquisitions client — or healthcare, financial, or defense anywhere — "where does our data go, and who can see it?" comes before "which model is best," and it eliminates options the leaderboard ranked first.

The compliance vocabulary you need: a BAA (Business Associate Agreement) is the contract that lets a vendor process protected health information under HIPAA — no BAA, no PHI, full stop. Data residency guarantees data is processed and stored in a specific geography (a US region for federal work). FedRAMP authorization and government-cloud regions are what let a vendor touch federal systems at all. And "no training on your data" is the baseline that your client's proprietary content won't leak into a future model.

The major API vendors have responded to exactly this pressure. Anthropic offers BAAs and runs Claude through enterprise channels including Amazon Bedrock and Google Cloud. Those channels expose different regional and routing choices; a provider name alone is not a residency guarantee. Confirm the selected endpoint, region, contract, and organization policy before claiming compliance. [sources: Anthropic platform and AWS Bedrock model docs, accessed 2026-10-27] And when even a compliant public API is off-limits — air-gapped networks, classified systems, FedRAMP-High and beyond — this axis is the entire reason open-weight, self-hosted models are in your toolkit. For a Karsun federal engagement, this isn't a tiebreaker; it's often the first filter, settling the decision before capability, cost, or latency get a vote.

Putting it together

Walk the funnel — and never marry one model

Now run the funnel top to bottom. A task with its constraints enters. Compliance and data residency usually filter first and hardest — knocking out whole vendors before anything else. What survives gets sorted by latency (who's waiting?) into interactive or batch, pruning tiers. Context window checks the model holds the real inputs. Then you weigh capability against cost on the survivors — with a small eval set on real client data, not a benchmark — and confirm the tooling won't fight you. A defensible pick falls out: not "the best model," but the right model for this task, this budget, and this client's rules, with the reasoning written down beside it.

That written reasoning is half the deliverable. Clients don't just want a recommendation — they want to understand the trade-off: what you gave up and why. An FDE who can produce a one-page model-selection rationale (the scorecard in today's deep-dive is a template) is doing the consulting half of the job, not just the coding half.

Deeper practice: test the model seam · outside Core 30
FDE mindset

Attach one rule to every pick: keep it swappable. Models leapfrog each other every few months, prices fall, a new compliance region opens, a client's needs shift mid-engagement. If your code hard-codes one vendor's SDK and prompt quirks into every corner, switching means a rewrite. Put the model behind a thin internal interface — one place that builds the request, sends it, and parses the response — and switching is a config change plus a re-run of your eval set. The deliverable is never "we chose Model X." It's "we chose Model X for these reasons, and here's how cheaply we can change our minds." That portability is what Part 2 makes concrete: the resilient call you build there is the seam you swap models behind.

Deeper: Picking the model was the easy part — now you have to call it · outside Core 30
The whole game, again

Picking the model was the easy part — now you have to call it

The mental shift for Part 2: an LLM API call is a network request to a shared, metered, fallible service — treat it like one. Everything you know about resilient distributed systems applies. The patterns aren't AI-specific; they're the same disciplines that make any third-party integration survive production — streaming for responsiveness, batching for throughput, respecting rate limits, retrying transient failures correctly, making retries safe, bounding how long you'll wait, and failing gracefully. LLM calls just make each matter more, because they're slower, pricier, and flakier than the average REST call.

Deeper: why the notebook call breaks, and the call you'll build

You've chosen a model and put it behind a clean interface. Now your code has to call it, over the network, thousands of times a day, against a service you don't control. The prototype made one call in a notebook, it worked, everyone clapped. Production makes that call forty thousand times against a rate-limited, occasionally-overloaded, sometimes-slow remote API — and every weakness the notebook hid becomes a user-facing outage.

The diagram on the right is a single resilient call and everything around it. We'll build it piece by piece: how the response comes back (stream or batch), the gate in front of the call (rate limiting), the call itself with its safety equipment (timeout, retry with backoff and jitter, idempotency), and the two ways it can end (ship the result, or fall back safely). Master it once and you reuse it on every engagement, behind whatever model you picked in Part 1. [example payload card on the diagram: a real POST /v1/messages request]

Deeper: Streaming: don't make the user wait for the last token · outside Core 30
Pattern 1 · Streaming

Streaming: don't make the user wait for the last token

An LLM generates its answer one token at a time, left to right. By default the API waits until the entire answer is finished, then sends it back in one lump — so for a long response the user stares at a spinner for the full generation time, maybe ten or twenty seconds, before anything appears. Streaming changes the delivery: the API sends each token as it's produced, so text starts appearing almost immediately. Total generation time is unchanged, but perceived latency collapses, because time-to-first-token — not total time — is what the user feels.

Practice (optional): which feels faster?
Deeper: what streaming costs you — open connections and partial answers

This is why every "the AI feels slow" complaint should first be met with "are we streaming?" The familiar typewriter effect in every chat interface is streaming; without it those products would feel broken. It does cost some engineering: a streamed response arrives as a sequence of events over a long-lived connection rather than one JSON object, so your code consumes a stream and assembles the pieces. Two consequences to internalize. First, because the connection stays open for the whole generation, streaming is also how you avoid request timeouts on long outputs — a large non-streaming response can exceed a client's HTTP timeout and get killed mid-flight, which is why SDKs often require streaming above a certain output size. Second, streaming complicates error handling: a failure can happen after some tokens have reached the user, so "the request failed" is no longer a clean before-or-after — you may have a partial answer on screen. Hold that thought; it returns at error handling.

Deeper: Batching: the opposite trade for work nobody is watching · outside Core 30
Pattern 2 · Batching

Batching: the opposite trade for work nobody is watching

Deeper: why a synchronous loop is the wrong tool for bulk work

Streaming optimizes the case where a human is waiting. Batching optimizes the case where nobody is. When you have a large volume of independent calls that don't need to finish right now — classify ten thousand support tickets, summarize last quarter's documents, enrich a database overnight — sending them one at a time through the synchronous API is the wrong tool. You'll fight rate limits, pay full price, and babysit a long sequential loop.

The major providers offer a dedicated batch API for exactly this: you submit a big set of requests as one job, the provider processes them asynchronously over a window (typically up to 24 hours), and you collect the results when it's done — at a substantial discount, commonly around 50% off the normal per-token price. [source: provider batch-API docs — Anthropic Message Batches / OpenAI Batch API, accessed 2026-10-27] You trade immediacy for throughput and cost: results in hours instead of seconds, for roughly half the money and none of the rate-limit juggling.

Deeper: matching the mechanism to the true deadline

The FDE judgment is matching the mechanism to the workload's true deadline. The instinct to make everything synchronous and instant is expensive and often pointless — if a report is read tomorrow morning, generating it in a 2 a.m. batch run for half the price is strictly better. Conversely, batching a request a user is actively waiting on would be absurd. Two practical notes carry forward. First, batch results come back keyed by an ID in no guaranteed order, so you match each result to its request by the custom ID you assigned — never by position. Second, batching sidesteps the live rate-limit dance we're about to discuss, which is half its appeal: you hand the provider the whole pile and let them pace it. Ask of every bulk job: does anyone need this in the next few seconds? If not, batch it.

Deeper: Rate limits: you are sharing a metered service · outside Core 30
Pattern 3 · Rate limiting

Rate limits: you are sharing a metered service

An LLM API is a shared resource, and the provider caps how much any one account can consume. The caps come in three flavors you'll see constantly: RPM (requests per minute), TPM (tokens per minute), and sometimes TPD (tokens per day). Exceed any of them and the API stops serving you and returns an HTTP 429, "Too Many Requests."

You handle rate limits from both sides. Reactively, when a 429 comes back, you back off and retry — and the provider usually tells you exactly how long to wait, in a Retry-After header. Respecting that header is the single most important thing you can do; it's the difference between recovering in one polite pause and flailing against the wall. (The retry mechanics are the next pattern.) Proactively, you throttle yourself so you mostly don't hit the limit in the first place — a client-side rate limiter (a token-bucket, or a simple semaphore capping concurrent requests) that paces your outbound calls under the known ceiling. The diagram puts this throttle as a gate in front of the call for a reason: it's cheaper to not send a doomed request than to send it and handle the 429.

Deeper: why a 429 isn't a bug, and how limits connect back to model choice

A 429 is not a bug in your code and not an error in the usual sense — it's the provider saying "slow down, you've hit your share." Treating it as fatal, or worse, hammering harder when you see one, is the classic way to turn a brief throttle into a sustained outage.

This is also where Part 1 and Part 2 connect. Rate limits are per account and per model tier, so the model you chose shapes your headroom — a smaller tier may have a roomier limit, and spreading load across tiers (cheap model for the bulk, flagship for the hard cases) spreads load across limit pools too. For an FDE, "we're getting rate-limited" should trigger a design conversation — throttle, batch, cache, or upgrade the tier — not a frantic retry loop.

Pattern 4 · Retries with backoff + jitter

Retries: the right way to handle transient failure

Deeper: what makes a failure transient

Networks are unreliable and shared services have bad moments. Over thousands of calls you will hit transient failures: a 429 rate limit, a 500 or 503 when the provider is briefly overloaded, a dropped connection. The defining property is that they're temporary — the exact same request, sent again a moment later, usually succeeds. So the correct response is to retry. But how you retry separates a resilient system from one that makes outages worse.

The wrong way is to retry immediately, in a tight loop. If the service is overloaded, a flood of instant retries from every client at once is precisely what keeps it overloaded — a self-inflicted denial-of-service called a "retry storm." The right way has three parts. Exponential backoff: wait longer between attempts — 1s, then 2, then 4, then 8 — giving the service room to recover. Jitter: add a small random amount to each wait, so thousands of clients that failed at the same instant don't all retry at the same instant and re-create the spike. And a bounded cap: retry a fixed, small number of times — three, maybe five — then give up and treat it as a real failure, because an unbounded loop burns money and stalls the user forever. One crucial distinction makes retries correct rather than dangerous: retry only the failures that are actually transient. A 429 or a 5xx is worth retrying — the request was fine, the service just couldn't serve it yet. A 400 (malformed request) or a 401 (bad credentials) is not — retrying a request the server already rejected as invalid will fail identically every time and just waste attempts. The retry logic has to branch on the error type. The good news: mature SDKs implement backoff-with-jitter on the right error classes for you — but you must know what they're doing, because you'll tune it, and because the next pattern is what makes any retry safe. The worked implementation is in today's deep-dive.

Deeper: Idempotency: making it safe to retry at all · outside Core 30
Pattern 5 · Idempotency

Idempotency: making it safe to retry at all

Retries introduce a subtle, dangerous question you must answer before you turn them on: what if the request actually succeeded, but the response got lost on the way back? The server did the work and charged you; the acknowledgment never arrived; your retry logic sees "no response" and sends the request again. Now the work has happened twice. For a read-only LLM call that's merely wasteful — you paid for two generations. For anything with a side effect — an agent that placed an order, sent an email, wrote a record, kicked off a payment — doing it twice is a real incident.

Idempotency is the property that doing an operation twice has the same effect as doing it once. The standard mechanism is an idempotency key: you generate a unique ID for the logical operation and attach it to the request. The first time the server sees that key it does the work and remembers the result; if a retry arrives carrying the same key, the server recognizes a duplicate and returns the original result instead of doing the work again. The retry becomes safe — at most one real execution, no matter how many times the network makes you resend.

Deeper: retry and idempotency are a pair

This is why idempotency sits in the diagram attached to the call, right beside retry: they're a pair. Retry without idempotency is a loaded gun pointed at your client's data — every backoff attempt risks a duplicate side effect. Many LLM APIs support an idempotency key directly on the request for exactly this reason, and where the model is one step in a larger workflow, you carry the same discipline through your own services: assign each logical operation an ID, dedupe on it, and design every step so replaying it is harmless. The FDE rule is blunt: before you enable retries, make the thing being retried idempotent. Retries assume the operation is safe to repeat; idempotency is how you make that assumption true.

Deeper: Timeouts: decide in advance how long you'll wait · outside Core 30
Pattern 6 · Timeouts

Timeouts: decide in advance how long you'll wait

Every call needs a deadline. Without one, a single slow or hung request can tie up a connection, a thread, or a user's patience indefinitely — and under load, a pile of stuck requests with no timeout is how one slow dependency takes down an entire service. A timeout is your explicit decision: if this call hasn't returned in N seconds, stop waiting and handle it as a failure. LLM calls make timeouts especially important because they're slow and variable — a response can legitimately take many seconds, the spread between fast and slow is wide, and the naïve defaults that work for a quick REST call are wrong here.

Deeper: tuning the deadline, the streaming gotcha, and the true worst case

Setting the timeout is a judgment call you tune to the workload. Too short and you'll kill legitimate slow responses, turning a working call into a failure and a wasted retry. Too long and a genuinely hung request blocks resources far past usefulness. An interactive feature wants a tighter deadline (a user won't wait 60 seconds anyway); a batch or long-generation job can afford a generous one. The key is that it's a deliberate number, not whatever the library defaulted to.

Two LLM-specific traps. First, the streaming gotcha from Pattern 1: many HTTP clients implement "timeout" as a per-chunk read timeout that resets every time a byte arrives, not a total wall-clock cap. On a streamed response that trickles tokens slowly, such a timeout may never fire even though the call has dragged on for minutes — so for a hard overall deadline you often track elapsed time yourself at the loop level, not trust a single setting. Second, timeouts compose with retries: your true worst-case wait is the timeout multiplied by the number of attempts (plus the backoff delays). A 30-second timeout with three retries can mean a user waiting well over a minute — so set both numbers together, with the total experience in mind.

Deeper: Graceful failure: never let a broken call reach the user raw · outside Core 30
Pattern 7 · Graceful error handling

Graceful failure: never let a broken call reach the user raw

Practice (optional): the catch-all wrapper that isn't resilient

Everything so far reduces how often calls fail and how safely you retry. The last pattern decides what happens when, despite all of it, a call still fails — because at scale, some will. The amateur integration lets the exception bubble up and the user sees a stack trace, a spinner that never resolves, or a blank screen. The professional integration has decided, in advance, what failure looks like to the user, and it's never raw. It starts with a taxonomy, because each class is handled differently — but the instinct to wrap everything in one catch-all is exactly the trap:

Start with a taxonomy, because each class of failure is handled differently: a transient error (429, 5xx, dropped connection) → retry with backoff (Pattern 4); a client error (400, 401) → don't retry, fix the request or fail fast; a timeout → treat as failure after the deadline (Pattern 6); a content outcome like a safety refusal → a real, expected response type to branch on, not a crash; and still-failing-after-retries → the genuine dead end this pattern exists for. For that dead end, you define a fallback — the deliberate "what we do when nothing worked": a graceful message ("the assistant is unavailable — here's how to reach a human"), a handoff to a deterministic non-AI path, a cached or default result, or falling back to a different model (the Part 1 portability seam paying off — a clean interface lets you retry on a backup model).

Deeper: circuit breakers, partial streams, and why "cleanly handled" wins

Two refinements for systems that call a lot: a circuit breaker that, after repeated failures, stops sending requests for a cooldown instead of retrying into a wall — protecting both you and the struggling provider; and, recalling Pattern 1, a plan for partial streamed output, since a failure mid-stream may leave half an answer on screen that you must either complete or cleanly retract. The unifying principle is Day 4's, restated for the network layer: "no answer, cleanly handled" always beats "a wrong answer or a crash, delivered raw." A user told the feature is briefly unavailable is mildly annoyed; a user shown a traceback, or left on a dead spinner, has lost trust in the product — and your client has lost trust in you. The resilient call in the diagram ends in exactly two places: a result you ship, or a fallback you chose. It never ends in an exception the user sees.

On your cloud · the call surface

Same pattern, different surface: calling the model on your cloud

Everything above is provider-neutral, and it stays that way. What changes on your cloud is the call surface — the streaming operation, the name of the throttling error, the knobs on the SDK's built-in retry, and where extra capacity comes from. The pattern doesn't change: stream, throttle, retry only transient errors with bounded backoff and jitter, carry an idempotency key, set a deadline, fall back. AWSAmazon Bedrock: Converse, throttling, and capacity

On Bedrock you call Converse, or ConverseStream to stream — one consistent API across the Bedrock models that support messages. The stream arrives as events (contentBlockDelta pieces, then metadata), and errors can arrive inside it: a throttlingException or a modelStreamErrorException after tokens are already on screen — Pattern 7's partial answer, made concrete. Branch on the error: ThrottlingException (HTTP 429) means you exceeded your account quotas; ServiceUnavailableException (503) means the service is short of capacity, not that you are over quota; ValidationException (400) is your request, so don't retry. AWS's fix for both 429 and 503 is exponential backoff with random jitter, and the AWS SDKs do it for you: standard retry mode backs off with jitter and stops early when its retry quota runs out; adaptive mode adds a client-side rate limiter — Pattern 3's throttle. For capacity, a cross-Region inference profile as the modelId lets Bedrock route to other Regions, and Provisioned Throughput buys dedicated model units. None of it gives you idempotency, a deadline, or a fallback; those stay in your wrapper.

Route the ID you mean. In the 2026-10-27 Haiku 5.5 and Sonnet 5.5 model cards, us.anthropic.claude-haiku-5-5 and us.anthropic.claude-sonnet-5-5 are US geo inference profiles for bedrock-runtime; they can route across US Regions and are not single-Region promises. The same endpoint also lists bare in-Region IDs where regional availability permits, while global. profiles may route worldwide. The separate bedrock-mantle endpoint also uses bare IDs, so validate the endpoint, target Region, model card, and organization policy together. Do not guess a prefix. This static lesson made no AWS account call and cannot assert organization-specific enablement.

During a busy hour, a Bedrock-backed chat feature starts returning ServiceUnavailableException (HTTP 503). Your account quotas are fine. Beyond retrying with backoff and jitter, which change does AWS's guidance point to?

  1. Request a Bedrock quota increase
  2. Call the model through a cross-Region inference profile
  3. Set the SDK's max attempts to 1 so failures surface faster
  4. Treat 503 as non-retryable, like a ValidationException
Show the answer

Use a cross-Region inference profile. A 429 means your quota; a 503 means Bedrock's capacity, so the fix is to reach more capacity, not to ask for more quota.

GCPGemini on Agent Platform: Gen AI SDK, location, and 429s

On Gemini Enterprise Agent Platform you call Gemini through the Google Gen AI SDK: client.models.generate_content, or generate_content_stream to iterate over chunks as they arrive. The location you set on the client is a resilience decision. The global endpoint routes traffic dynamically and is Google's recommendation for availability and fewer 429s, but you can't control which region processes the request, so a processing-location requirement means a regional or multi-region (us, eu) endpoint instead. On pay-as-you-go a 429 reads "Resource exhausted": shared capacity, no assured throughput. Google's guidance is the global endpoint, truncated exponential backoff, and smoothing sharp spikes — bursts can throttle even when your per-minute average is fine. The SDK already retries timeouts, 429s and 5xx errors with exponential backoff, tuned through HttpRetryOptions (attempts, delays, jitter, status codes) plus a client timeout. Provisioned Throughput reserves capacity; once you exceed it, more retries won't help. Google calls generate_content safe to retry because it changes no server-side state; your side effects still need idempotency keys and a fallback.

Deep dive: the resilient-call loop

Optional. ~6 minutes. Part 2's seven patterns, assembled into one function.

Backoff + jitter on transient errors only, bounded attempts, an idempotency key so a retry can't double a side effect, a deliberate timeout, and a fallback so failure never reaches the user raw:

def call_model(request, *, max_tries=4, base=1.0, cap=30.0, timeout=20.0):
    idem_key = request.idempotency_key or new_uuid()   # safe to retry
    for attempt in range(max_tries):
        try:
            return model.call(request, key=idem_key,    # one logical op
                              timeout=timeout)           # bounded wait
        except RateLimited as e:                         # 429
            delay = e.retry_after or backoff(attempt, base, cap)
        except (ServerError, ConnectionDropped):         # 5xx / network
            delay = backoff(attempt, base, cap)          # transient → retry
        except (BadRequest, Unauthorized):               # 400 / 401
            raise                                        # NOT transient → stop
        sleep(delay)
    return fallback(request)        # exhausted → fail safe, never crash

def backoff(attempt, base, cap):
    raw = min(cap, base * (2 ** attempt))    # exponential: 1,2,4,8...
    return random.uniform(0, raw)            # full jitter — spread the herd

Five things make it production-grade: it retries only transient errors, so client errors fall straight through; it honours the server's Retry-After header when one is given; backoff is exponential with jitter, so simultaneous failures do not re-spike together; the same idempotency key rides every attempt, so at most one real execution happens; and every path that is not a clean result lands in the fallback. Worst-case wait is roughly the timeout times the retry count, plus the backoff delays — set those two numbers together, with the user's experience in mind. This is the seam from Part 1: swap the model inside the call and the whole resilient wrapper keeps working.

Production code: the model seam

The whole vendor choice lives behind one function and one config string — so swapping Haiku for Sonnet (or a self-hosted model later) is a one-line change, not a codebase-wide rewrite.

# One seam every model call goes through -- swapping models is a config change, not a rewrite.
# Auth: Bedrock API key in AWS_BEARER_TOKEN_BEDROCK (boto3 reads it; no IAM role).
import boto3

_bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")

# The pick lives in ONE place. Change this string, not 12 call sites.
DEFAULT_MODEL = "us.anthropic.claude-haiku-5-5"   # US geo profile; verify routing policy

def answer(prompt: str, *, model: str = DEFAULT_MODEL, system: str | None = None) -> str:
    resp = _bedrock.converse(
        modelId=model,
        system=[{"text": system}] if system else [],
        messages=[{"role": "user", "content": [{"text": prompt}]}],
        inferenceConfig={"maxTokens": 512, "temperature": 0},
    )
    return resp["output"]["message"]["content"][0]["text"]

# Callers never name a vendor -- they call the seam:
label = answer("Classify: 'my card was declined'  ->  billing | shipping | technical")

# Size up only where it earns its cost -- same interface, one argument:
summary = answer(long_rfp, model="us.anthropic.claude-sonnet-5-5")

Every caller talks to answer(), never a vendor SDK directly — that is the seam Part 2 wraps in timeouts and retries.

Production code: streaming the response

A streamed answer arrives as a sequence of pieces, not one JSON blob — you print each token for low time-to-first-token and buffer the pieces for later. On AWS that is ConverseStream; on GCP it is generate_content_stream, with the SDK's retry and timeout set on the client.

# Stream tokens as they generate -- the user reads at ~0.4s instead of staring for 12s.
# Auth: Bedrock API key in AWS_BEARER_TOKEN_BEDROCK (boto3 reads it; no IAM role).
import boto3

bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")

resp = bedrock.converse_stream(
    modelId="us.anthropic.claude-haiku-5-5",
    messages=[{"role": "user", "content": [{"text": "Summarize the RFP in 3 bullets."}]}],
    inferenceConfig={"maxTokens": 1024},
)

# The response is a sequence of events, not one JSON blob -- assemble the pieces.
chunks = []
for event in resp["stream"]:
    if "contentBlockDelta" in event:
        piece = event["contentBlockDelta"]["delta"]["text"]
        print(piece, end="", flush=True)     # first token shows immediately -> low TTFT
        chunks.append(piece)
    elif "metadata" in event:
        u = event["metadata"]["usage"]        # usage arrives at the END of the stream
        print(f"\n[in={u['inputTokens']} out={u['outputTokens']}]")

full_text = "".join(chunks)   # buffer the complete answer for validation / storage

from google import genai

    http_options=types.HttpOptions(
        api_version="v1",
        retry_options=types.HttpRetryOptions(
            initial_delay=1.0,

)

chunks = []

    chunks.append(piece)

full_text = "".join(chunks)   # buffer the complete answer for validation / storage
