Part 1 · Model selectionA decision framework on six axes — not "which model is best."
The whole game

"Which model should we use?" is a framework, not a leaderboard

The first question a client asks an FDE is almost always "which AI should we use?" — and they usually expect a one-word answer, the way they'd expect "which database?" to resolve to a name. The amateur answer is to name whatever model topped a benchmark last week. The professional answer is: it depends on what you're building, and here's how I'll decide. Model selection is not a contest with a single winner. It's a constrained optimization across six axes that pull against each other, and the right model is the one that fits this task, this budget, and this client's rules — which is frequently not the most capable model on the market.

The landscape you're choosing from, as of June 2026, is four broad options. Anthropic's Claude family (Opus, Sonnet, Haiku tiers). OpenAI's GPT family (the GPT-5 line, currently topping out at GPT-5.5 on the API). Google's Gemini family (the 3.x and 2.5 lines, across Pro and Flash tiers). And the open-weight / self-hosted world — Llama, Mistral, DeepSeek, Qwen and others — where you download the weights and run inference on hardware you control. [sources: Anthropic model catalog (claude-api reference, cached 2026-06-04); OpenAI API docs, platform.openai.com (verified 2026-06-28); Google Gemini API pricing, ai.google.dev (verified 2026-06-28)] The specific version names will have moved by the time you read this — that's exactly why you learn the axes, not the names.

Those six axes are capability, cost, latency, context window, tooling & ecosystem, and data residency / compliance. The diagram on the right is the funnel: a task and its constraints come in at the top, each axis narrows the field, and a defensible pick falls out the bottom — with one rule attached that we'll come back to. Walk the axes one at a time.

Axis 1 · Capability

Capability: fit to the task, not the top of the chart

Capability is the axis everyone over-weights. The instinct is to grab the smartest model and stop thinking. But "smartest" is expensive and slow, and most production tasks don't need it. The discipline is to match the model's capability tier to the hardest thing the task actually requires — and no higher.

Every major vendor now ships a tiered family precisely so you can make this match. Anthropic offers Opus (the heavyweight, for the hardest reasoning and long-horizon agentic work), Sonnet (the balanced workhorse), and Haiku (fast and cheap for high-volume, simpler tasks). Google mirrors this with Gemini Pro versus Flash versus Flash-Lite; OpenAI ships the GPT-5 line with smaller and larger variants. The tiers exist because the same vendor is telling you, in pricing, that you should not run everything on the flagship.

The FDE move is to decompose the workload. A customer-support feature might use a small, cheap model to classify an incoming message ("is this billing, shipping, or technical?"), and only escalate the genuinely hard, open-ended conversations to a top tier. A document pipeline might extract structured fields with a mid-tier model and reserve the flagship for the final summarization a human will read. This is sometimes called a model router or cascade: cheap model first, expensive model only when the cheap one isn't confident. You'll build a primitive version of this thinking into nearly every engagement.

How do you actually judge capability for your task? Not from a public leaderboard — those measure generic benchmarks that may have nothing to do with your client's domain. You judge it with a small eval set: ten or twenty real examples from the client's actual data, with known-good answers, run against two or three candidate models. The model that gets your examples right is more capable for you than whatever won an abstract benchmark. Capability is the first axis, but it's the one you measure last and most concretely.

Axis 2 · Cost

Cost: input and output are priced differently, and it compounds

Day 1's cost equation returns: cost ≈ (input tokens + output tokens) × price-per-token, with input and output billed at different rates and output almost always the more expensive of the two. The gap is large and it shapes every decision. As of June 2026, on Anthropic's API, Claude Opus 4.8 runs about $5 per million input tokens and $25 per million output, Sonnet 4.6 about $3 / $15, and Haiku 4.5 about $1 / $5. [source: Anthropic model catalog, claude-api reference, cached 2026-06-04] Google's Gemini 3.5 Flash sits far lower — roughly $1.50 input / $9 output — and the Pro tier higher, around $2.70 / $16. [source: Google Gemini API pricing, ai.google.dev, verified 2026-06-28] The numbers will drift; the shape is durable, and the shape is what you reason with: output costs several times input, and the cheapest tier is often an order of magnitude below the flagship.

That asymmetry has a direct design consequence. A feature that reads a lot and answers briefly — classify this, extract that field, label this ticket — is dominated by input cost, so a model with cheap input and a big context window wins. A feature that generates long output — write the report, draft the email, produce the code — is dominated by output cost, and a small move down the tier ladder there saves real money. Two features with identical "AI" labels can have cost profiles that differ by 20×.

And it compounds with volume, which is where prototypes lie to you. A feature that costs two cents per call is free in a demo that runs it ten times. The same feature at forty thousand calls a day is $800/day, a quarter-million dollars a year — and now the difference between Opus and Haiku is the difference between a viable product and a deal-breaker line item. The FDE who can stand in front of a client and say "this endpoint costs $0.02 a call, runs 40,000 times a day, and we can cut it 70% by moving the classification step to Haiku" is the one who keeps the engagement. Cost isn't a footnote to the model choice; for high-volume features it often is the model choice.

Axis 3 · Latency

Latency: how fast does the answer need to arrive?

Capability and cost get the headlines; latency quietly decides whether users tolerate the feature at all. A model that gives a brilliant answer in nineteen seconds is the wrong model for a chat box where the user expects a reply in two. Latency is a first-class selection axis, and like cost it splits the world cleanly into two modes.

Interactive workloads — a chatbot, an autocomplete, a "summarize this page" button — live or die on perceived speed, and the metric that matters most is time-to-first-token (TTFT): how long until something appears. We'll see in Part 2 that streaming is the lever that turns a slow total response into a fast-feeling one, but the model and tier still set the floor. Smaller models in a family (Haiku, Flash) are not just cheaper — they're faster, often dramatically so, and several vendors now offer an explicit low-latency or "fast" mode on their larger models for exactly these cases. For interactive features, the smallest model that's capable enough usually wins on both latency and cost at once.

Batch / asynchronous workloads — overnight processing of ten thousand documents, a nightly report, a back-office data-enrichment job — invert the priority. Here nobody is watching a spinner, so per-call latency barely matters; throughput and cost dominate, and (as Part 2 covers) the provider's batch API will often do the same work at roughly half the price in exchange for letting it complete within hours instead of seconds.

The FDE habit is to ask "who is waiting, and for how long?" before you ask anything else about the model. The answer sorts the task into interactive or batch, and that sort eliminates whole columns of the options table before you've compared a single benchmark. A common, expensive mistake is putting a flagship model on a synchronous user-facing path "because it's the best," then discovering the feature feels broken because every interaction takes eight seconds. The best model that arrives too late is the wrong model.

Axis 4 · Context window

Context window: how much can you hand it, and what does that cost?

The context window — Day 1's central idea — is also a selection axis, because models differ in how big a window they offer, and the size you need is set by the task. As of June 2026, the frontier tiers have converged on very large windows: Claude's current models offer up to a 1 million token context, with the smaller Haiku tier at 200K; Gemini's Pro tier and others sit in the same 1M-class range. [source: Anthropic model catalog, claude-api reference, cached 2026-06-04] A million tokens is roughly a few thousand pages — enough to drop an entire codebase, a long contract, or a quarter's worth of support transcripts into a single call.

But a bigger window is not automatically better, and treating "1M context" as a pure win is a beginner error. Two costs come with the size. First, the dollar cost: you pay per token for everything you put in the window, so a habit of stuffing the whole document set into every call is a habit of paying for tens of thousands of tokens you don't need — Day 1's lesson that more retrieved text is not more intelligence; it's more budget spent. Second, the attention cost: models can lose precision on facts buried in the middle of an enormous context, so a smaller, well-chosen window often produces a more accurate answer than a giant, noisy one.

So the context-window question is really two questions. Does the model's maximum window comfortably exceed the largest input this task will ever realistically send? If the task is "answer questions about a 300-page manual," you need a model whose window holds the manual plus the conversation plus room to answer — and if no single model's window fits, that's a strong signal you need retrieval (RAG, all of Week 2) rather than a bigger model. And what will it cost to fill the window you actually use? A model with a huge window but expensive input may lose to a model with a smaller window and cheap input, if your real inputs fit the smaller one. Size the window to the task, then price the tokens you'll really send.

Axis 5 · Tooling & ecosystem

Tooling & ecosystem: the model is half of what you're buying

Here's the axis junior engineers forget entirely: you are not just choosing a model, you're choosing the platform around it. Two models can be equally capable on raw text and worlds apart in how much engineering it takes to ship a reliable feature, because the surrounding tooling differs. For an FDE shipping on a deadline, that tooling is often the deciding factor.

What's in that ecosystem? Structured output — can you tell the API "return JSON matching this exact schema" and have it guaranteed, rather than parsing and praying? (We covered why that guardrail matters on Day 4's territory; here it's a selection criterion.) Tool / function calling — how cleanly can the model call out to your code, your database, your APIs, which is the entire foundation of the agentic systems you'll build in Week 3. Prompt caching — does the platform let you reuse a stable prefix at a fraction of the price (Anthropic, for instance, prices cache reads at roughly a tenth of normal input). Batch APIs for the async workloads above. The maturity of the SDKs in your client's language. And whether mainstream agent frameworks and observability tools support the model first-class.

This is where the "biggest" vendors earn their keep beyond model quality. A model with mediocre benchmarks but a rock-solid SDK, native structured output, reliable tool calling, and prompt caching may get a working, affordable feature into production a week faster than a marginally smarter model with a thinner ecosystem — and a week is the entire budget on a lot of FDE engagements. When you evaluate candidates, build a tiny end-to-end slice on each (one structured call, one tool call) and notice how much friction there was. That friction, multiplied across a project, is real cost the benchmark never shows. The model is maybe half of what you're actually buying; the ecosystem is the other half.

Axis 6 · Data residency & compliance

Data residency, BAA & self-hosting: the axis that overrules the rest

The final axis is the one that, on the engagements you'll actually staff, frequently vetoes every other axis at once. It doesn't matter that a model is the smartest, cheapest, and fastest if the client is legally forbidden from sending their data to it. For a federal-acquisitions client like the ones in this program — or a healthcare, financial, or defense client anywhere — the question "where does our data go, and who can see it?" comes before "which model is best," and it eliminates options the leaderboard would have ranked first.

The compliance vocabulary you need: a BAA (Business Associate Agreement) is the contract that lets a vendor process protected health information under HIPAA — no BAA, no PHI, full stop. Data residency is the guarantee that data is processed and stored in a specific geography (a US region, say, for federal work). FedRAMP authorization, and government-cloud regions, are what let a vendor touch federal systems at all. And "no training on your data" is the baseline commitment that your client's proprietary content won't leak into a future model.

The major API vendors have responded to exactly this pressure, and it's why they matter for regulated work. Anthropic offers BAAs and runs Claude through enterprise channels — Amazon Bedrock, Google Vertex AI, and a dedicated Claude-on-AWS path — that bring it inside a client's existing cloud-governance and data-residency boundary. [source: Anthropic platform docs, claude-api reference, cached 2026-06-04] OpenAI offers BAAs to eligible customers, a no-training-by-default posture, and data residency across roughly ten regions; Google delivers Gemini through Vertex AI with the full Google Cloud compliance stack. [sources: OpenAI pricing & API docs, openai.com / platform.openai.com, verified 2026-06-28; Google Vertex AI docs]

And when even a compliant public API isn't allowed — air-gapped networks, classified systems, the strictest FedRAMP-High and beyond — this axis is the entire reason open-weight, self-hosted models exist in your toolkit. Llama, Mistral, DeepSeek, Qwen and their kin can run on hardware the client controls, inside their own boundary, with no data ever leaving. You trade away some raw capability and take on the burden of running the infrastructure yourself — but you gain absolute data control, and on some engagements that's the only acceptable answer. For a Karsun federal-acquisitions engagement, this axis isn't a tiebreaker; it's often the first filter, and it can settle the decision before capability, cost, or latency get a vote.

Putting it together

Walk the funnel — and never marry one model

Now run the funnel on the right top to bottom. A task with its constraints enters. Compliance and data residency usually filter first and hardest — they can knock out whole vendors before anything else is considered. What survives gets sorted by latency (who's waiting?) into interactive or batch, which prunes tiers. Context window checks that the model can hold the real inputs. Then you weigh capability against cost on the survivors — with a small eval set on real client data, not a benchmark — and you confirm the tooling won't fight you. A defensible pick falls out the bottom: not "the best model," but the right model for this task, this budget, and this client's rules, with the reasoning you can show the client written down beside it.

That written reasoning is half the deliverable. Clients don't just want a recommendation; they want to understand the trade-off — what you gave up and why — and an FDE who can produce a one-page model-selection rationale (the scorecard in today's deep-dive is a template) is doing the consulting half of the job, not just the coding half.

FDE mindset

Attach one rule to every pick: keep it swappable. Models leapfrog each other every few months, prices fall, a new compliance region opens, and the client's needs shift mid-engagement. If your code hard-codes one vendor's SDK and prompt quirks into every corner, switching means a rewrite. If you put the model behind a thin internal interface — one place that builds the request, sends it, and parses the response — switching is a config change and a re-run of your eval set. The deliverable is never "we chose Model X." It's "we chose Model X for these reasons, and here's how cheaply we can change our minds." That portability is what Part 2 makes concrete: the resilient call you build there is the seam you swap models behind.

Part 2 · API integration patternsFrom "which model" to "calling it reliably in production."
The whole game, again

Picking the model was the easy part — now you have to call it

You've chosen a model and put it behind a clean interface. Now your code has to actually call it, over the network, thousands of times a day, against a service you don't control. This is where a depressing number of AI features fail — not because the model is wrong, but because the integration is naïve. The prototype made one call in a notebook, it worked, everyone clapped. Production makes that call forty thousand times against a rate-limited, occasionally-overloaded, sometimes-slow remote API, and every weakness the notebook hid becomes a user-facing outage.

The mental shift for Part 2 is this: an LLM API call is a network request to a shared, metered, fallible service — treat it like one. Everything you already know about resilient distributed systems applies. The patterns aren't AI-specific; they're the same disciplines that make any third-party API integration survive production — streaming for responsiveness, batching for throughput, respecting rate limits, retrying transient failures correctly, making retries safe, bounding how long you'll wait, and failing gracefully when nothing works. LLM calls just make each of these matter more, because they're slower, pricier, and flakier than the average REST call.

The diagram on the right has now swapped to a single resilient call and everything wrapped around it. We'll build it piece by piece: how the response comes back (stream or batch), the gate in front of the call (rate limiting), the call itself with its safety equipment (timeout, retry with backoff and jitter, idempotency), and the two ways it can end (ship the result, or fall back safely). Master this once and you reuse it on every engagement, behind whatever model you picked in Part 1.

Pattern 1 · Streaming

Streaming: don't make the user wait for the last token

An LLM generates its answer one token at a time, left to right. By default the API waits until the entire answer is finished, then sends it back in one lump — so for a long response the user stares at a spinner for the full generation time, maybe ten or twenty seconds, before anything appears. Streaming changes the delivery: the API sends each token (or small chunk) as it's produced, so text starts appearing almost immediately and flows in as it's written. The total generation time is unchanged, but the perceived latency collapses, because time-to-first-token — not total time — is what the user feels.

This is the single highest-leverage UX move on any interactive AI feature, and it's why every "the AI feels slow" complaint should first be met with "are we streaming?" The familiar typewriter effect in every chat interface is streaming; without it those same products would feel broken. For anything a human watches in real time — chat, assistants, live summaries — streaming is not optional.

It does cost you some engineering. A streamed response arrives as a sequence of events over a long-lived connection rather than a single JSON object, so your code consumes a stream and assembles the pieces, and your front end renders them as they arrive. Two consequences to internalize now. First, because the connection stays open for the whole generation, streaming is also how you avoid request timeouts on long outputs — a large non-streaming response can exceed a client's HTTP timeout and get killed mid-flight, which is why SDKs often require streaming above a certain output size. Second, streaming interacts with error handling: a failure can happen after some tokens have already reached the user, so "the request failed" is no longer a clean before-or-after — you may have a partial answer on screen to deal with. Hold that thought; it returns when we get to error handling.

Pattern 2 · Batching

Batching: the opposite trade for work nobody is watching

Streaming optimizes the case where a human is waiting. Batching optimizes the case where nobody is. When you have a large volume of independent calls that don't need to finish right now — classify ten thousand support tickets, summarize last quarter's documents, enrich a database overnight — sending them one at a time through the synchronous API is the wrong tool. You'll fight rate limits, pay full price, and babchle a long sequential loop.

The major providers offer a dedicated batch API for exactly this: you submit a big set of requests as one job, the provider processes them asynchronously over a window (typically up to 24 hours), and you collect the results when it's done — at a substantial discount, commonly around 50% off the normal per-token price. [source: provider batch-API docs — Anthropic Message Batches / OpenAI Batch API, verified 2026-06] You trade immediacy for throughput and cost: results in hours instead of seconds, for roughly half the money and none of the rate-limit juggling.

The FDE judgment is matching the mechanism to the workload's true deadline. The instinct to make everything synchronous and instant is expensive and often pointless — if a report is read tomorrow morning, generating it in a 2 a.m. batch run for half the price is strictly better. Conversely, batching a request a user is actively waiting on would be absurd. Two practical notes carry into the rest of Part 2. First, batch results come back keyed by an ID in no guaranteed order, so you match each result to its request by the custom ID you assigned — never by position. Second, batching sidesteps the live rate-limit dance we're about to discuss, which is half its appeal: you hand the provider the whole pile and let them pace it. Ask of every bulk job: does anyone need this in the next few seconds? If not, batch it.

Pattern 3 · Rate limiting

Rate limits: you are sharing a metered service

An LLM API is a shared resource, and the provider caps how much of it any one account can consume. Those caps come in three flavors you'll see constantly: RPM (requests per minute), TPM (tokens per minute), and sometimes TPD (tokens per day). Exceed any of them and the API stops serving you and returns an HTTP 429, "Too Many Requests." A 429 is not a bug in your code and not an error in the usual sense — it's the provider saying "slow down, you've hit your share." Treating it as a fatal error, or worse, hammering harder when you see one, is the classic way to turn a brief throttle into a sustained outage.

You handle rate limits from both sides. Reactively, when a 429 comes back, you back off and retry — and the provider usually tells you exactly how long to wait, in a Retry-After header. Respecting that header is the single most important thing you can do; it's the difference between recovering in one polite pause and flailing against the wall. (The retry mechanics themselves are the next pattern.) Proactively, you throttle yourself so you mostly don't hit the limit in the first place — a client-side rate limiter (a token-bucket or a simple semaphore capping concurrent requests) that paces your outbound calls to stay under the known ceiling. The diagram puts this throttle as a gate in front of the call for a reason: it's cheaper to not send a doomed request than to send it and handle the 429.

This is also where Part 1 and Part 2 connect. Rate limits are per account and per model tier, so the model you chose shapes the headroom you have — a smaller tier may have a roomier limit, and spreading load across tiers (cheap model for the bulk, flagship for the hard cases) spreads load across limit pools too. And rate limits feed directly back into cost tracking: a feature that's constantly hitting 429s isn't just slow, it's a signal you're under-provisioned or wasting calls. For an FDE, "we're getting rate-limited" should trigger a design conversation — throttle, batch, cache, or upgrade the tier — not a frantic retry loop.

Pattern 4 · Retries with backoff + jitter

Retries: the right way to handle transient failure

Networks are unreliable and shared services have bad moments. Over thousands of calls you will hit transient failures: a 429 rate limit, a 500 or 503 when the provider is briefly overloaded, a dropped connection. The defining property of these failures is that they're temporary — the exact same request, sent again a moment later, usually succeeds. So the correct response is to retry. But how you retry is what separates a resilient system from one that makes outages worse.

The wrong way is to retry immediately, in a tight loop. If the service is overloaded, a flood of instant retries from every client at once is precisely what keeps it overloaded — a self-inflicted denial-of-service called a "retry storm." The right way has three parts. Exponential backoff: wait longer between each attempt — 1 second, then 2, then 4, then 8 — so you give the service room to recover instead of pounding it. Jitter: add a small random amount to each wait, so that thousands of clients that all failed at the same instant don't all retry at the same instant and re-create the spike; randomizing the waits spreads the load smoothly. And a bounded cap: retry a fixed, small number of times — three, maybe five — and then give up and treat it as a real failure, because an unbounded retry loop burns money and stalls the user forever.

One crucial distinction makes retries correct rather than dangerous: retry only the failures that are actually transient. A 429 or a 5xx is worth retrying — the request was fine, the service just couldn't serve it yet. A 400 (malformed request) or a 401 (bad credentials) is not — retrying a request the server already rejected as invalid will fail identically every time and just waste attempts. The retry logic has to branch on the error type. Get this right and you absorb the provider's bad moments invisibly; get it wrong and you either crash on recoverable blips or hammer the service on unrecoverable ones. The good news: mature SDKs implement backoff-with-jitter retries on the right error classes for you — but you must know what they're doing, because you'll tune it, and because the next pattern is the thing that makes any retry safe. The worked implementation is in today's deep-dive.

Pattern 5 · Idempotency

Idempotency: making it safe to retry at all

Retries introduce a subtle, dangerous question that you must answer before you turn them on: what if the request actually succeeded, but the response got lost on the way back? The server did the work and charged you; the acknowledgment never arrived; your retry logic sees "no response" and sends the request again. Now the work has happened twice. For a read-only LLM call that's merely wasteful — you paid for two generations. For anything with a side effect — an agent that placed an order, sent an email, wrote a record, kicked off a payment — doing it twice is a real incident.

Idempotency is the property that doing an operation twice has the same effect as doing it once. The standard mechanism is an idempotency key: you generate a unique ID for the logical operation and attach it to the request. The first time the server sees that key it does the work and remembers the result; if a retry arrives carrying the same key, the server recognizes it as a duplicate and returns the original result instead of doing the work again. The retry becomes safe — at most one real execution, no matter how many times the network makes you resend.

This is why idempotency sits in the diagram attached to the call, right beside retry: they're a pair. Retry without idempotency is a loaded gun pointed at your client's data — every backoff attempt risks a duplicate side effect. Many LLM APIs support an idempotency key directly on the request for exactly this reason, and where the model is just one step in a larger workflow, you carry the same discipline through your own services: assign each logical operation an ID, dedupe on it, and design every step so that replaying it is harmless. The FDE rule is blunt: before you enable retries, make the thing being retried idempotent. Retries assume the operation is safe to repeat. Idempotency is how you make that assumption true.

Pattern 6 · Timeouts

Timeouts: decide in advance how long you'll wait

Every call needs a deadline. Without one, a single slow or hung request can tie up a connection, a thread, or a user's patience indefinitely — and under load, a pile of stuck requests with no timeout is how one slow dependency takes down an entire service. A timeout is your explicit decision: if this call hasn't returned in N seconds, stop waiting and handle it as a failure. LLM calls make timeouts especially important because they're slow and variable — a response can legitimately take many seconds, and the spread between a fast and a slow call is wide, so the naïve defaults that work for a quick REST call are wrong here.

Setting the timeout is a judgment call you tune to the workload. Too short and you'll kill legitimate slow responses, turning a working call into a failure and a wasted retry. Too long and a genuinely hung request blocks resources far past the point of usefulness. An interactive feature wants a tighter deadline (a user won't wait 60 seconds anyway); a batch or long-generation job can afford a generous one. The key is that it's a deliberate number, not whatever the library happened to default to.

Two LLM-specific traps to internalize. First, the streaming gotcha from Pattern 1: many HTTP clients implement "timeout" as a per-chunk read timeout that resets every time a byte arrives, not a total wall-clock cap. On a streamed response that trickles tokens slowly, such a timeout may never fire even though the call has dragged on for minutes — so for a hard overall deadline you often have to track elapsed time yourself at the loop level, not trust a single timeout setting. Second, timeouts compose with retries: your true worst-case wait is the timeout multiplied by the number of attempts (plus the backoff delays between them). A 30-second timeout with three retries can mean a user waiting well over a minute before you give up — so set both numbers together, with the total experience in mind, not each in isolation.

Pattern 7 · Graceful error handling

Graceful failure: never let a broken call reach the user raw

Everything so far reduces how often calls fail and how safely you retry them. The last pattern decides what happens when, despite all of it, a call still fails — because at scale, some will. The amateur integration lets the exception bubble up and the user sees a stack trace, a spinner that never resolves, or a blank screen. The professional integration has decided, in advance, what failure looks like to the user, and it's never raw.

It starts with a taxonomy of what can go wrong, because each class is handled differently: a transient error (429, 5xx, dropped connection) → retry with backoff (Pattern 4); a client error (400, 401) → don't retry, fix the request or fail fast, because retrying changes nothing; a timeout → treat as failure after the deadline (Pattern 6); a content outcome like a safety refusal → a real, expected response type to branch on, not a crash; and still-failing-after-retries → the genuine dead end this pattern exists for. Code that lumps all of these into one catch (Exception) has thrown away the information it needs to respond correctly.

For the dead end, you define a fallback — the deliberate "what we do when nothing worked." Depending on the feature that might be a graceful message ("the assistant is unavailable right now — here's how to reach a human"), a handoff to a deterministic non-AI code path, a cached or default result, or falling back to a different model (the Part 1 portability seam paying off — if your primary is down or refusing, a clean interface lets you retry on a backup model). Two refinements for systems that call a lot: a circuit breaker that, after repeated failures, stops sending requests for a cooldown instead of retrying into a wall — protecting both you and the struggling provider; and, recalling Pattern 1, a plan for partial streamed output, since a failure mid-stream may leave half an answer on the user's screen that you must either complete or cleanly retract.

The unifying principle is Day 4's, restated for the network layer: "no answer, cleanly handled" always beats "a wrong answer or a crash, delivered raw." A user told the feature is briefly unavailable is mildly annoyed; a user shown a traceback, or left hanging on a dead spinner, has lost trust in the product — and your client has lost trust in you. The resilient call in the diagram ends in exactly two places: a result you ship, or a fallback you chose. It never ends in an exception the user sees.

Your tools

The $20 plan is your first model-selection decision

Both halves of today are things you're already living. You're working on a $20 Claude Pro plan with a budget measured in roughly 40 focused hours a week — which means you have already made a model-selection decision under constraints. You picked a capable model at a fixed price and a hard usage ceiling, and now every habit that stretches that budget is the same discipline a client pays an FDE to bring, just with you holding the meter.

Part 1's framework is exactly how you'd reason about your own toolchain: when a sub-task is simple, you don't need to burn your best model's budget on it — match the tier to the task. Part 2's patterns show up every time Claude Code streams a long answer (you read it as it arrives instead of waiting), every time you hit a usage limit and have to pace yourself instead of hammering retries, and every time a long agentic run times out and you decide whether to retry the whole thing or fall back to doing the step by hand. Working like an engineer — choosing the right model for the task and calling it resiliently — makes the $20 plan stretch across the week. Working like a slot machine — flagship model on everything, re-running giant loops on every transient blip — burns it by Tuesday.

FDE mindset

A client will ask two questions that sound separate: "which AI should we use?" and "why does the AI feature keep breaking?" They're the two halves of today. The first is a six-axis trade-off you decide and document — capability, cost, latency, context, tooling, and the compliance axis that often overrules the rest. The second is almost never the model's fault; it's a missing timeout, an unbounded retry, an un-throttled rate limit, a non-idempotent side effect, or an error that reached the user raw. The FDE who can pick the right model and wrap it in a call that survives production is delivering the whole job — the consulting decision and the engineering that makes it hold.

2 · The resilient-call loop. Part 2's patterns, assembled into one function. Backoff + jitter on transient errors only, bounded attempts, an idempotency key so a retry can't double a side effect, a deliberate timeout, and a fallback so failure never reaches the user raw:

def call_model(request, *, max_tries=4, base=1.0, cap=30.0, timeout=20.0):
    idem_key = request.idempotency_key or new_uuid()   # safe to retry
    for attempt in range(max_tries):
        try:
            return model.call(request, key=idem_key,    # one logical op
                              timeout=timeout)           # bounded wait
        except RateLimited as e:                         # 429
            delay = e.retry_after or backoff(attempt, base, cap)
        except (ServerError, ConnectionDropped):         # 5xx / network
            delay = backoff(attempt, base, cap)          # transient → retry
        except (BadRequest, Unauthorized):               # 400 / 401
            raise                                        # NOT transient → stop
        sleep(delay)
    return fallback(request)        # exhausted → fail safe, never crash

def backoff(attempt, base, cap):
    raw = min(cap, base * (2 ** attempt))    # exponential: 1,2,4,8...
    return random.uniform(0, raw)            # full jitter — spread the herd

Five things make it production-grade: it retries only transient errors (4xx falls straight through); it honors the server's Retry-After when given; backoff is exponential with jitter so simultaneous failures don't re-spike together; the same idempotency key rides every attempt so at most one real execution happens; and every path that isn't a clean result lands in fallback(). Worst-case wait ≈ timeout × max_tries plus the backoff delays — set those two numbers together, with the user's experience in mind.
