Agents: Reasoning and Acting in a Loop

Week 3 · Day 1 Agent Architecture ~18 min · reading @150 wpm + diagram + check

Last week you learned to fill a context window well. This week the model stops being a one-shot answer machine and becomes something that acts: it reasons, calls a tool, reads what came back, and reasons again — until the job is done. That loop is the whole of agents. Today you'll build the mental model from two directions at once: the ReAct pattern that named it, and the provider-native tool-calling contract you'll actually write against at a client. The panel on the right assembles the loop one node at a time; the reading tells you why each node exists and where it breaks.

The primitive

Every agent is an "augmented LLM"

Before the word "agent" means anything useful, pin down the atom it's built from. Anthropic calls it the augmented LLM: a base model enhanced with three capabilities — retrieval (it can pull in outside information), tools (it can trigger actions in the world), and memory (it can carry state) — where the crucial detail is that the model itself drives all three. It generates its own search queries, selects which tool to call, and decides what to keep. That is the difference between an augmented LLM and last week's plain completion: the plain call reads a window and emits text; the augmented call can decide to reach out mid-thought and pull something new into the window.

Hold onto why this matters. A raw LLM has no memory between calls and no live access to your systems — you learned that in Week 1. The augmented LLM doesn't repeal that limit; it gives the model a set of levers it can pull to move facts into the window on its own initiative. Retrieval answers "I need to know X." Tools answer "I need to do X, or fetch X from a live system." Memory answers "I need to remember X across steps."

Here's the sentence to carry through the whole week: every workflow and every agent you will ever build is composed of augmented-LLM calls. There is no exotic new machinery underneath — a sprawling multi-agent system is just augmented LLMs wired together. So when a client shows you an "AI agent" that misbehaves, your first move is to zoom in on a single augmented call and ask the Week-1 question again: what did this specific call have in its window, and what could it reach for? Master the atom and the molecule stops being intimidating.

ReAct · the thought

Reasoning traces steer the next action

The pattern that made agents work has a name and a paper: ReAct — "Reasoning and Acting" — from Yao et al. (ICLR 2023). Its insight is deceptively small. Instead of forcing the model to either think (chain-of-thought) or act (call a tool), ReAct interleaves the two in a single loop. The model writes a free-form reasoning trace — a "thought" — and then takes a task-specific action, over and over.

Start with the thought, because it does more work than it looks. In ReAct the thought is where the model induces, tracks, and updates its plan, and where it handles exceptions. "The question asks for the director's birth year; I have the film but not the director, so I should look up the film first." That is a thought: it decomposes the task, decides the next move, and — critically — can react when the world doesn't cooperate. When an action returns something unexpected ("no results found"), the next thought is where the model notices, re-plans, and tries a different approach rather than barrelling ahead.

This is why a reasoning trace isn't decoration. In a pure act-only agent, a bad tool result derails everything downstream — there's no place to catch it. In ReAct, the thought between actions is exactly that catch: a moment to interpret the last observation and adjust the plan. For you as an FDE, the thought is also the most valuable debugging artifact you'll get. When an agent goes off the rails at a client, the trace of its thoughts tells you where its reasoning turned wrong — long before you start suspecting the tools themselves.

ReAct · act & observe

The Thought → Action → Observation cycle

Now close the loop. After a thought, the model emits an action — a call against an external source. In the paper's canonical setup that source is a Wikipedia API with three verbs: search an entity, look up a string, and finish with an answer. The environment runs that action and returns an observation: the search result, the row, the error. That observation is fed back in, and it becomes the raw material for the next thought. Thought → Action → Observation, repeated, until the model emits a finish action. That cycle is the beating heart of every agent you'll ever touch.

The reason this beats pure chain-of-thought is one word: grounding. A chain-of-thought model reasons in a closed room — nothing checks its steps against reality, so a wrong turn on step two compounds into a confidently wrong answer by step five. The ReAct paper is explicit that interleaving actions "overcomes issues of hallucination and error propagation prevalent in chain-of-thought reasoning by interacting with a simple Wikipedia API." Each observation is a fact from the outside world that the next thought has to reckon with. The model can't hallucinate a search result it just received; it has to respond to what actually came back.

Two consequences the paper measured and you should remember. First, the visible trajectory of thoughts and actions is more interpretable than a bare answer — you can read what the agent did and why. Second, this isn't a party trick that works on one benchmark: ReAct was validated across two very different task families — knowledge-intensive reasoning (HotpotQA multi-hop questions, FEVER fact verification) and interactive decision-making (ALFWorld, WebShop) — which is what established "reason + act" as a general pattern rather than a narrow trick. The loop is the point, not the domain.

When to reach for it

Workflows vs. agents — and the anti-complexity rule

Here's where good engineers separate from cargo-cultists. Anthropic draws a hard architectural line between two things people lazily both call "agents." A workflow is a system where "LLMs and tools are orchestrated through predefined code paths" — you wrote the control flow, the model fills in the steps. An agent is a system where the model "dynamically directs its own processes and tool usage, maintaining control over how it accomplishes tasks." The difference is who holds the steering wheel: your code, or the model.

Most production "AI features" are workflows, and should be. Anthropic names five workflow patterns worth knowing: prompt chaining (decompose into fixed sequential steps), routing (classify, then dispatch to a specialist path), parallelization (run subtasks concurrently and aggregate), orchestrator-workers (a lead model farms out dynamically-sized subtasks), and evaluator-optimizer (one model generates, another critiques in a loop). All of these have predictable, developer-authored paths — which means they're cheaper, faster, and far easier to test and debug.

Agents earn their keep only when you cannot hardcode the path but can still verify progress. That trade — flexibility bought with predictability — is why Anthropic's core guidance is anti-complexity: "Start with simple prompts, optimize them with comprehensive evaluation, and add multi-step agentic systems only when simpler solutions fall short." And whichever you build, the same grounding principle from ReAct applies — it's "crucial for the agents to gain 'ground truth' from the environment at each step (such as tool call results or code execution) to assess its progress." The FDE takeaway is blunt: a dynamic agent is not a prestige upgrade. Reach for the simplest thing that verifiably works, and let the task force you up the ladder — never your enthusiasm.

The contract

Tool use is a contract — the model never executes

Now descend from theory to the API you'll actually write. The single most important thing to internalize about provider-native tool use is that it is a contract, not model-side execution. In Anthropic's words: "The model never executes anything on its own. It emits a structured request, your code (or Anthropic's servers) runs the operation, and the result flows back into the conversation." The model is a planner with a radio, not a robot with hands. It says "please run get_weather(city='SF')"; something on your side actually runs it.

The mechanics are worth memorizing because you'll debug them constantly. You define a tool by three things: a name, a description — which is really a prompt, because the model chooses tools by reading these — and an input schema written in JSON Schema. You send those alongside the user message. Claude replies with a tool-use stop reason and one or more tool-use blocks, each naming a tool and the arguments it wants. Your application runs the operation and returns the outcome as a result block in the next request. Adding strict: true to a custom tool definition makes the provider guarantee the emitted arguments conform to your schema, which retires a whole category of defensive JSON parsing.

This is a cross-vendor pattern, not a Claude quirk. OpenAI's Responses API calls it function calling: tools carry a name, a description and a parameters block in the same JSON-Schema shape, and the documentation is equally blunt: "OpenAI's model does not execute your function — it only decides which function should be called and what arguments to pass." The model returns a function call with a name and a JSON argument payload. Your code executes it and returns an output object carrying the matching call identifier. Same contract, different nouns. Once you see the shape, every provider's tool API stops being a new thing to learn.

The loop, in code

The agentic loop is a while on stop_reason

The ReAct cycle, translated into the code you'll actually write, is a while loop keyed on the response's stop reason. That's the whole engine. For client tools it runs in five steps:

  1. Send the request with your tool definitions and the user message.
  2. Claude comes back with a tool-use stop reason and one or more tool-use blocks.
  3. Your code executes each requested tool and formats the outputs as result blocks.
  4. You send a new request containing the original messages, the assistant's response, and your result blocks.
  5. Repeat for as long as the stop reason keeps coming back as tool-use.

The loop exits the moment the model returns any other stop reason: end-of-turn, meaning it is done and has a final answer; max-tokens, meaning it ran out of room; a stop sequence; or a refusal. Map this back onto ReAct and the correspondence is exact — a tool-use stop is the Action plus the Observation, since you run the action and the result block is what comes back; the model's next assistant turn is the Thought; and end-of-turn is the finish action from the paper. Same loop, one described at research altitude and one at API altitude.

Two failure modes fall straight out of this structure, and you'll see both in the wild. If your loop condition is wrong — say you only check for tool calls once instead of looping — the agent makes a single tool call and then silently stops, half-finished. And because you control the loop, you also control its safety rails: a maximum iteration count so a confused agent can't spin forever, and a running token budget so a long trajectory doesn't quietly blow the context window you spent all of Week 1 learning to respect. The loop is trivial to write and easy to write unsafely; that gap is exactly where an FDE earns their fee.

Who runs the tool

Client tools vs. server tools

Not every tool runs on your machine, and knowing which is which saves you a category of confusion. Claude splits tools into two kinds. Client tools are the ones your code executes: your own user-defined functions, plus the Anthropic-schema tools for shell access, text editing, memory and computer use. For these you run the exact five-step loop above — you receive the request, you do the work, and you construct and return the result.

Server tools are different. Web search, web fetch, code execution and tool search all run on Anthropic's servers. When the model calls one, the provider executes it and the server-side loop iterates internally — you never construct a result block for a server tool, because the result never leaves Anthropic's side until the model is ready to continue. This is a genuine trap for engineers: you go looking for the result you're "supposed" to return and there isn't one, because that tool was never yours to run.

One more piece of machinery to file away: a server-side loop that hits its internal iteration cap comes back with a pause_turn stop reason. That is neither an error nor a completion — it is the provider saying "I paused mid-work; hand the conversation back so I can continue." You resume by simply re-sending the conversation. So your outer loop has to recognise three shapes of "keep going," not one: the model wants you to run something, the server wants to continue its own work, or everything else, which means exit. Miss the paused case and a perfectly healthy agent looks like it froze.

The steering knob

tool_choice — from "answer directly" to "always act"

The last piece is the knob that decides whether and which tool the model may call: tool_choice. It is small, it lives in one line of the request, and it quietly determines whether your feature behaves like a chatbot or like a machine. Claude offers four settings: auto, the default, where the model decides each turn whether to call a tool or just answer; any, where it must call some tool; tool, where it must call one specific named tool; and none, where tools are off for this turn. OpenAI mirrors all four, renaming only the second one to "required."

Read those as a spectrum from freedom to compulsion and the design choices become obvious. Leave it on auto for an open-ended assistant that should answer trivia from its own knowledge but reach for tools when a task demands it. Force a tool call when the model has no business answering from memory — a booking agent must always check live availability, never guess it. Force one named tool when you want a single structured extraction, such as always recording an order; combined with strict: true, that turns the model into a reliable JSON emitter that cannot wander off and write prose instead.

This is the primary lever you'll reach for when steering an agent's behavior, and it's the fix for a whole class of complaints. "The AI sometimes answers from stale memory instead of checking our database" is usually not a smarter-model problem — it's tool_choice: auto where the task needed any. Set the knob to match the task's tolerance for the model improvising, and a surprising amount of "flaky agent" behavior simply disappears.

FDE mindset

An agent is not a magic upgrade — it's a loop you own. The model reasons and requests; your code runs the tools, feeds back the results, counts the iterations, and decides when to stop. When a client's "agent" misbehaves, don't reach for a bigger model. Walk the loop: was the tool defined with a clear description and schema? Did tool_choice let it skip the action it needed to take? Did the loop exit early, or spin without a cap? Every one of those is something you can fix in code — which is exactly why they're paying an engineer, not renting a model.

Deep dive: one tool_use ⇄ tool_result exchange

Optional. ~10 minutes. The contract, in the actual message shapes you'll send.

1 · You define the tool — name, description (a mini-prompt the model reads to decide when to call it), and a JSON-Schema input_schema:

tools (sent on the request)
  • name: get_weather
  • description: "Get the current weather for a city."
  • input_schema: { type:"object", properties:{ city:{type:"string"} }, required:["city"] }

2 · The model requests a call. The response comes back with stop_reason: "tool_use" and a block like: { type:"tool_use", id:"toolu_01A", name:"get_weather", input:{ city:"SF" } }. The model did not run anything — it emitted a structured request.

3 · You execute and return the result as a tool_result block in the next request, referencing the id: { type:"tool_result", tool_use_id:"toolu_01A", content:"62°F, foggy" }. You send the original messages + the assistant's turn + this block.

4 · Loop. If the model now has what it needs it returns end_turn with a final answer; if it needs another tool it returns tool_use again and you repeat.

OpenAI, same dance, different nouns: the request block is a function call carrying a name, a JSON argument payload, and a call identifier; you reply with a function-call output that carries the same identifier and the result. Learn one contract, read both sets of docs.

Why strict: true matters: without it, the arguments the model emits are "usually" valid JSON matching your schema — which means occasionally not, and you end up writing defensive parsers. With it, the provider guarantees conformance, and pairing it with a named tool choice turns the model into a dependable structured-output emitter.
