The Agent Framework Landscape: LangChain, OpenAI, CrewAI & Microsoft

Week 3 · Day 3 Foundation AI Engineering Core 30 · AWS · ~12 min read · 2 interactions · 6-Q check Core 30 · GCP · ~12 min read · 2 interactions · 6-Q check

Once you decide to build an agent, the next question a client asks is "which framework?" — and in 2026 there are four serious answers, all of which changed shape in the last year. LangChain/LangGraph shipped stable 1.0, OpenAI's Agents SDK graduated from the experimental Swarm project, CrewAI matured into a standalone Crews-plus-Flows engine, and Microsoft merged AutoGen and Semantic Kernel into a single Agent Framework. Today you learn what each one actually is, the primitives it gives you, and — the part that earns your fee — how to pick between them on real decision axes instead of hype. The panel on the right assembles the landscape one framework at a time. One warning up front: if you learned this space before 2026, half of what you remember is now wrong, and this lesson tells you exactly where.

The whole game

What an agent framework is — and why 2026 reset the board

Strip away the branding and an agent orchestration framework is one thing: a library that gives you the runtime and abstractions for building LLM agents — the agent loop, tool calling, state and memory, and multi-agent coordination — so you don't hand-roll that plumbing yourself. Every framework on today's board wraps the same beating heart, the agent loop: send a request to the model, handle any tool calls it asks for or return the final answer, and repeat until the task is done. What differs is everything built around that loop — how you define agents, how they hand work to each other, how state persists, and how much explicit control the framework hands you versus hides.

Deeper: the two stale-memory traps, and the four names on the board

Here is the trap you must not fall into. If your mental model of this space predates 2026 — or if you let a model trained before 2026 seed your answer — you will describe it wrong in two specific ways. First, you'll talk about AutoGen and Semantic Kernel as two separate, live Microsoft frameworks. They aren't anymore: Microsoft unified them into one Agent Framework that went GA on 2026-04-03, and AutoGen is now a legacy/migration source. Second, you'll describe LangChain as a pre-1.0 "chains" library. It isn't: LangChain and LangGraph both shipped stable 1.0 on 2025-10-22, re-centered on the agent loop. Getting these two facts wrong in front of a client instantly marks you as out of date, so we anchor the whole day on the current, verified state of the board.

The 2026 landscape has four names worth knowing: LangChain/LangGraph, the OpenAI Agents SDK, CrewAI, and the Microsoft Agent Framework. They are not interchangeable, and they are not ranked — each makes a different bet about the control model, provider lock-in, and enterprise features you get. Your job is not to have a favorite; it's to map the client's constraints onto the framework whose bets match. We'll take them one at a time, then turn the differences into a decision procedure you can run at a whiteboard.

Framework 1

LangChain + LangGraph 1.0: a loop on a durable runtime

LangChain and LangGraph reached their first stable major versions together on 2025-10-22, and LangGraph 1.0 is billed as the first stable major release in the "durable agent framework" space after a year-plus of real production adoption. That simultaneity is the tell: these are not competitors you choose between but two layers of one stack. The mistake is to imagine LangChain-versus-LangGraph as a fork in the road. It's a staircase — you start high and drop down when you need to.

The high layer is LangChain's new create_agent abstraction, pitched as "the fastest way to build an agent with any model provider." It runs exactly the simple loop we named a moment ago: send the request to the model, handle its tool calls or return the final answer, repeat. On top of that loop 1.0 adds two things worth memorizing. Middleware is a set of customizable hooks throughout agent execution — for example, a human-in-the-loop gate that lets a person approve, edit, or reject a tool call before it runs, or automatic context-summarization to keep the window under control. And standard content blocks give you consistent content types — reasoning traces, citations, tool calls — across providers, so you can swap the underlying model without rewriting the code that parses its output.

Deeper: dropping down to the LangGraph durable runtime

The low layer is the LangGraph durable runtime, and this is the piece clients under-rate. LangChain agents are built on LangGraph, so when the high-level API stops being enough you drop into an explicit graph with built-in persistence, resumable state, and human-in-the-loop control. The practical FDE reading: reach for create_agent to move fast on the common case, and descend to LangGraph when the task needs a long-running, checkpointed, resumable process rather than a single loop. Same stack, two altitudes — you don't migrate frameworks to get durability, you just go one layer down.

Framework 2

OpenAI Agents SDK: five primitives, and it isn't OpenAI-only

Deeper: from Swarm to a supported SDK

The OpenAI Agents SDK is a deliberately lightweight, production-ready framework, and OpenAI is explicit about its lineage: it's "a production-ready upgrade of our previous experimentation for agents, Swarm." If someone on the client team remembers Swarm as a fun experiment they couldn't ship, this is the answer to "what happened to it" — Swarm grew up into a supported SDK. The design philosophy is minimalism: a small set of primitives you compose, rather than a large framework you configure.

There are five primitives, and they're worth holding as a set. Agents are LLMs equipped with instructions and tools. Handoffs let one agent delegate to another (the star of the next step). Guardrails validate inputs and outputs — the checkpoints that catch a bad request before it runs or a bad answer before it ships. Sessions provide persistent conversation memory across turns. And running underneath all of it is built-in tracing for visualizing and debugging what the agents actually did — which, on a multi-agent system, is the difference between a bug you can see and a bug you can only guess at.

Deeper: the default is OpenAI, the ceiling is not

Now the fact that saves you from a real misconception. The SDK defaults to OpenAI's Responses API, which makes it look like an OpenAI-lock-in play — but it is not OpenAI-only. It ships extension points for other providers through LiteLLM and Any-LLM adapters, so you can point the same agents at non-OpenAI models. That distinction matters enormously on an engagement: "OpenAI's SDK" does not mean "you must run OpenAI models forever." When a client worries about being trapped on one vendor, this is the nuance you bring — the default is OpenAI, the ceiling is not.

The delegation trick

Handoffs are just tool calls the model chooses

Handoffs deserve their own beat because they demystify multi-agent systems entirely. In the OpenAI Agents SDK, a handoff — one agent transferring control to another — is implemented as a tool exposed to the LLM. Concretely: a handoff to an agent named "Refund Agent" surfaces to the model as a tool named transfer_to_refund_agent. The model doesn't invoke some special orchestration machinery; it simply calls a tool, and that tool call routes the conversation to the other agent.

Deeper: why routing collapses into tool selection

Sit with why that's elegant. Routing and delegation — the thing that sounds like the hard, magical part of "multi-agent AI" — collapses into the exact same mechanism you already learned for tool calling. The model looks at the conversation, decides "this is a refund question," and chooses the transfer_to_refund_agent tool the way it would choose a search_docs tool. There is no separate router model, no rules engine deciding who handles what: the orchestrating LLM makes the routing decision as one more tool selection. Once you see it this way, a triage-plus-specialists system stops being intimidating — it's a handful of agents, each exposed to the others as a transfer tool.

Deeper: handoffs as the baseline for every framework

This is also the mental bridge to the other frameworks. Every multi-agent system on today's board is, under the hood, answering the same question — how does one agent decide to hand work to another? — and the OpenAI SDK gives the cleanest answer: it's a tool call, so it's governed by everything you already know about tool calling, guardrails, and tracing. Hold that as your baseline as we look at how CrewAI and Microsoft frame the same problem differently.

Framework 3

CrewAI: autonomous Crews and deterministic Flows

CrewAI makes a bet the others don't state as sharply: it gives you two complementary orchestration models and expects you to combine them. Crews are autonomous, role-based agent collaboration — you define agents by role, goal, and backstory and let them collaborate with flexible, model-driven decision-making. Flows are the opposite temperament: event-driven, deterministic control with precise state management and conditional branching. The README says it plainly — "the true power of CrewAI emerges when combining Crews and Flows." Crews for the parts where you want judgement; Flows for the parts where you want guarantees.

Deeper: how Flows work, and why CrewAI is standalone

The Flows machinery is concrete enough to picture. A Flow is built from decorated entry-point methods and listener methods that fire when a prior method produces output, with or and and operators to wait on multiple upstream steps, router-based conditional branching, and per-execution state that is either unstructured, as a plain dictionary, or structured, as a Pydantic model. If that reads like an event-driven workflow engine, that is exactly right — and the payoff is that you can embed an autonomous Crew as a step inside a deterministic Flow, getting model judgement where you want it and hard control everywhere else.

One grounding fact that changes how you position CrewAI to a client: it is a standalone framework. The dated PyPI snapshot used for this lesson (1.15.1, 2026-06-27) describes CrewAI as "built entirely from scratch — completely independent of LangChain or other agent frameworks," and it requires Python >=3.10,<3.14. That independence is a genuine architectural choice, not marketing — it means adopting CrewAI doesn't drag in the LangChain stack, and its dual Crews/Flows model is its own thing to learn on its own terms. When a team asks "is this just a LangChain wrapper?", the answer is a clean no.

Framework 4

Microsoft Agent Framework: AutoGen and Semantic Kernel, merged

This is the framework most likely to trip up anyone running on pre-2026 memory, so read it carefully. The Microsoft Agent Framework (pip package agent-framework, GA 2026-04-03) is the direct successor to BOTH AutoGen and Semantic Kernel, built by the same teams. It didn't replace one with the other; it merged them. It takes AutoGen's simple single- and multi-agent abstractions and combines them with Semantic Kernel's enterprise features — session state, type safety, filters, telemetry — then adds graph-based Workflows for explicit multi-agent orchestration. Two frameworks became one.

Deeper: Agents vs Workflows inside the Microsoft Agent Framework

The internal split mirrors a distinction you're now seeing everywhere. Microsoft Agent Framework divides capabilities into Agents — an LLM plus tools plus MCP access, aimed at open-ended, conversational tasks — and Workflows, which are graph-based, type-safe routing with checkpointing and human-in-the-loop for well-defined, multi-step processes. Agents for when you don't know the path in advance; Workflows for when you do. And the framework hands you a piece of advice worth quoting to every client: "if you can write a function to handle the task, do that instead of using an AI agent." Even the vendor selling you the agent framework tells you not to reach for an agent when plain code will do.

Now the fact you must not get wrong: AutoGen is legacy. Microsoft ships an official AutoGen-to-Agent-Framework migration guide (the page is dated 2026-04-01), which confirms AutoGen is now a migration source, not the recommended target for new work. So if a client says "we're building on AutoGen" or "we're standardizing on Semantic Kernel," the correct, current guidance is: those have been unified into the Microsoft Agent Framework, and new projects should target the merged framework and migrate existing AutoGen code toward it. Saying "use AutoGen for new agents" in 2026 is the single clearest way to sound a year out of date.

The decision

Choosing: control model, lock-in, and enterprise features

Four frameworks, one decision. The way to pick is not "which is best" — none dominates — but to score the client's situation on a handful of decision axes and let the constraints choose. The first and biggest axis is the control model: do you want an autonomous agent loop that decides its own path, or an explicit graph/workflow where you specify the steps? Every framework on the board actually offers both ends of this spectrum, which is the deepest pattern of the day — LangChain's create_agent loop drops to LangGraph's explicit graph; CrewAI's autonomous Crews embed inside deterministic Flows; Microsoft's open-ended Agents sit beside graph-based Workflows. The recurring shape is "loop when you don't know the path, graph when you do." Pick the framework, then pick the altitude within it.

The second axis is provider lock-in. Is the framework provider-agnostic or vendor-first? The OpenAI Agents SDK defaults to OpenAI but reaches other providers via LiteLLM/Any-LLM; LangChain's create_agent is built to work "with any model provider" and its content blocks explicitly let you swap models without rewriting parsing; CrewAI is standalone and independent of any single stack. The nuance, which you now carry, is that "OpenAI's SDK" doesn't force OpenAI models forever — but the default path of least resistance still points at each vendor's own models, and defaults quietly decide architectures.

Deeper: the remaining axes on the scorecard

The remaining axes round out the scorecard. Enterprise / state features: does it give you durable persistence, checkpointing, session state, type safety, and telemetry out of the box (LangGraph's durable runtime, Microsoft's Semantic-Kernel-derived features) or do you bolt those on? Ecosystem maturity: LangChain/LangGraph's year-plus of production adoption before 1.0 versus newer entrants. Score the client against these axes, and the "which framework" argument stops being a taste debate and becomes a short, defensible mapping from their constraints to a choice.

The FDE move

The best framework is sometimes no framework

Before any of this framework comparison matters, ask the question every one of these vendors quietly agrees on. Microsoft says it out loud — "if you can write a function to handle the task, do that instead of using an AI agent" — and it's the most valuable sentence in the whole landscape. An agent framework buys you an autonomous, tool-calling, sometimes-multi-agent loop; that loop is worth it exactly when the path isn't knowable in advance. When the path is knowable, an agent is slower, costlier, and less predictable than the function you could have written. The first FDE instinct is not "which framework," it's "does this task even need an agent?"

Deeper: no universal winner — the four bets side by side

When the answer is yes, the axes from the last step turn a religious debate into an engineering decision. There's no universal winner: LangChain/LangGraph gives you a fast loop over a battle-tested durable runtime; the OpenAI Agents SDK gives you five clean primitives and handoffs-as-tool-calls with tracing built in; CrewAI gives you an independent Crews-plus-Flows engine that pairs autonomy with determinism; the Microsoft Agent Framework gives you the unified AutoGen-plus-Semantic-Kernel enterprise story with graph Workflows. Match the client's control model, lock-in tolerance, and enterprise needs to the framework whose bets fit — and be ready to justify the pick on those axes, not on which name you've heard most.

FDE mindset

When a client asks "which agent framework should we standardize on?", don't answer with a favorite. Answer with three questions: Does this task even need an agent, or would a function do? Do we want an autonomous loop or an explicit graph? And how much does provider-agnosticism and enterprise state actually matter here? And keep your facts current — it's LangChain/LangGraph 1.0, the OpenAI Agents SDK (not Swarm), CrewAI's Crews and Flows, and the Microsoft Agent Framework that merged AutoGen and Semantic Kernel. Getting the map right is half of getting the choice right.

On your cloud · the provider SDK

Your spine is create_agent — defend it next to the cloud's own SDK

This program builds on LangChain v1 create_agent. Each cloud also ships its own open-source agent SDK and a managed runtime to deploy agents into, and when a client has standardized on that SDK, it is the comparison you must be able to defend. Score it on the same axes — control model, lock-in, enterprise features — and check where each runtime lets your LangChain agent run. Open your path; the other cloud stays as an optional comparison.

AWSStrands Agents on AgentCore Runtime

Strands Agents is an open-source SDK initially released by AWS, built model-first: an agent is a model, tools, and a prompt, and the model drives the loop. Strands invokes the model with the prompt, context, and tool descriptions; if the model selects a tool, Strands runs it and feeds the result back; repeat until the task is done — the same loop create_agent runs. Any Python function becomes a tool with the @tool decorator, MCP servers plug in as tools, and multi-agent work uses built-in Swarm, Graph, and Workflow patterns. It isn't Bedrock-only: models in Amazon Bedrock, Anthropic, Ollama, and others through LiteLLM. To deploy, Amazon Bedrock AgentCore Runtime is framework-agnostic: you wrap the agent in a BedrockAgentCoreApp with an @app.entrypoint handler, and AWS documents that pattern for Strands, LangGraph, Google ADK, and the OpenAI Agents SDK, with each user session in its own isolated microVM. The defensible comparison: Strands buys tight AWS-service integration, but a LangGraph-based agent — which is what create_agent builds — gets the same runtime through the same entrypoint. Same loop; different defaults.

GCPADK on Agent Runtime

Agent Development Kit (ADK) is Google's open-source agent framework, available in Python, TypeScript, Go, and Java. It covers both ends of the control-model axis: workflow agents for predictable pipelines, or agent-coordinated dynamic routing for adaptive behavior, with native multi-agent composition so specialist agents can collaborate and delegate, plus evaluation tools that test execution trajectories. You deploy it to Agent Runtime (formerly Agent Engine) on Gemini Enterprise Agent Platform — a fully managed runtime — or run it on Cloud Run or GKE. Agent Runtime grades its framework support: ADK gets full integration (deploy with the adk CLI, or wrap the agent in AdkApp); LangChain and LangGraph get managed templates in the Agent Platform SDK, such as the LangchainAgent class; CrewAI and custom frameworks use a custom template or any container that meets the runtime contract. The defensible comparison: ADK buys the deepest Agent Platform integration, while your LangChain agent still has a documented, supported path onto the same runtime. Same decision axes; different defaults.

Route a synthetic Bedrock handoff request

Treat a handoff as an allowlisted tool request while keeping the example entirely local and deterministic.

# Synthetic Amazon Bedrock Converse output: no model or network call.
SYNTHETIC_RESPONSE = {"output": {"message": {"content": [{
    "toolUse": {
        "toolUseId": "handoff-01",
        "name": "transfer_to_refund_agent",
        "input": {"reason": "duplicate charge"},
    }
}]}}}

HANDOFFS = {
    "transfer_to_refund_agent": "refund-agent",
    "transfer_to_shipping_agent": "shipping-agent",
}


def route_handoff(response):
    block = response["output"]["message"]["content"][0]["toolUse"]
    if block["name"] not in HANDOFFS:
        raise ValueError("handoff is not allowlisted")
    return {
        "agent": HANDOFFS[block["name"]],
        "tool_use_id": block["toolUseId"],
        "context": dict(block["input"]),
    }


handoff = route_handoff(SYNTHETIC_RESPONSE)

The fixture shows the portable mechanism—handoff as tool selection—without importing an agent framework or contacting a provider.
