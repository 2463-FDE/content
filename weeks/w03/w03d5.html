Building a Production Single Agent

Week 3 · Day 5 Agents in Production ~18 min · reading @150 wpm + diagram + check

All week you've built up to this: a single agent a client would actually let near their systems. Today we assemble one end to end with LangChain 1.0 — create_agent for the loop, middleware for every production concern, response_format for structured output, and MCP to bridge in real tools. The panel on the right builds that agent piece by piece, in the same order you'd build it at a client. By the end you can name every layer between a user's message and a governed, auditable answer — and defend why each one is there.

The whole game

An agent is a model calling tools in a loop

Strip away the hype and an agent is almost embarrassingly simple to define: it is "a model calling tools in a loop until a given task is complete." The model looks at the current state, decides whether to call a tool, the runtime executes that tool and feeds the result back, and the model looks again. It keeps going until it decides no more tool calls are needed, then returns a final answer. That loop — model, tool, result, model — is the entire mechanism. Everything else today is governance wrapped around it.

In LangChain 1.0, the high-level factory that builds this loop for you is create_agent. It went GA on October 22, 2025, and it shipped with a stability commitment the team stated plainly: no breaking changes until 2.0. That matters more than it sounds when you're an FDE. You're recommending a framework a client will build on for years, and "we promise not to break your imports for a major version" is exactly the kind of assurance that turns a demo into a production decision. create_agent is built on the LangGraph runtime underneath, so you inherit durable execution, state, and streaming without hand-writing a graph.

Hold the loop picture for the rest of the day. When we add middleware, we're hooking into moments in this loop. When we add structured output, we're shaping what the loop returns. When we add MCP, we're changing where the tools come from. The loop is the spine; you're about to learn its vertebrae.

The factory

create_agent in four arguments

Here's the minimal shape. You import the factory, hand it a model, some tools, and a system prompt, and you get back a runnable agent you can invoke (or ainvoke for async):

from langchain.agents import create_agent agent = create_agent( model="anthropic:claude-sonnet-4-5-20250929", tools=[search, lookup_order], system_prompt="You are a support agent. Always cite order IDs.", ) result = agent.invoke({"messages": [{"role": "user", "content": "Where is order 8812?"}]})

Read the signature like an FDE. model accepts either a provider-qualified string (the reference page's own example is "anthropic:claude-sonnet-4-5-20250929") or an already-initialized model instance — so you can swap providers by editing one string, or pass a fully-configured client when you need custom auth or a proxy. tools is your list of callables. system_prompt takes a string or a SystemMessage. And then three arguments that separate a toy from a product: middleware, response_format, and checkpointer/store for persistence. Those first three lines make a demo. The rest of today is the other three arguments.

This is the FDE value in one factory call. A junior engineer wires a raw model-plus-tools loop by hand and reinvents retries, limits, and logging badly. You reach for the factory that already has the extension points and spend your time on the client's actual policy — what's allowed, what needs a human, what must be redacted.

The primitive

Middleware is how you customize the loop

Now the idea that reorganizes everything. In LangChain 1.0, the customization primitive is middleware: "each piece handles one concern, hooks into the agent loop at the right moment, and composes freely." That sentence is worth reading twice, because it's a design philosophy, not just an API. Instead of a giant configurable agent with fifty flags, you get a small loop plus a stack of single-purpose pieces you snap on.

The categories the docs call out map cleanly onto the production concerns you've been meeting all week: execution environment (sandboxing, filesystem, shell), context management (summarizing or editing history before it overflows — the Week 1 window problem, solved as a component), fault tolerance (retries, fallbacks, call limits), guardrails (PII handling, input/output validation), and human steering (pausing for approval). Each of those is a concern a client will name in the first requirements meeting. Middleware gives you a place to put each answer.

The payoff for you is separation. When the client says "actually, also mask customer emails," you add one PII middleware — you don't reopen the tool code or the prompt. When they say "cap it at five tool calls so a runaway loop can't rack up a bill," that's another single piece. Concerns stay decoupled, they compose in a predictable order, and you can point at each one in a review and say what it does and why it's there.

The hooks

Six moments where you can intervene

An AgentMiddleware intervenes at named moments in the loop. The verified hooks are: before_agent (once, before the run starts), before_model (every time, just before the LLM is called), wrap_model_call (around the model call — you see the request and the response and can modify either), after_model (right after the model responds), wrap_tool_call (around each tool execution), and after_agent (once, when the run ends).

The naming tells you the shape. before_* and after_* are one-way observation-and-edit points: read the state, tweak it, move on. The wrap_* hooks are two-sided — they surround a call, so they can short-circuit it, retry it, or transform both what goes in and what comes out. That's why the powerful production behaviors live in the wrappers: a retry needs to catch the call and re-run it; a fallback needs to replace a failed model with another; an approval gate needs to pause before the tool actually fires. before_model is where history summarization slots in — trim the context right before it's handed to the model.

You rarely write these by hand at first, and that's the point of the next step: the framework ships the common ones already built. But knowing the six hook names means that when a client has a truly bespoke rule — "log every tool call to our SIEM with the tenant ID attached" — you know exactly which hook to reach for (wrap_tool_call) and that it'll compose cleanly with everything else on the stack.

Batteries included

The production middleware you didn't have to write

Here's where the framework earns its keep. LangChain ships a shelf of built-in middleware for exactly the concerns that make agents scary in production. Three you'll reach for constantly:

HumanInTheLoopMiddleware pauses the agent before a high-stakes tool call and surfaces it to a person to approve, edit, or reject. This is the single most important control for an agent that can spend money, email customers, or write to a database. "The agent can issue refunds, but anything over $100 waits for a human click" is a one-line policy that turns an unshippable capability into a shippable one. SummarizationMiddleware hooks before_model and summarizes conversation history before it overflows the context window — the Week 1 eviction failure, prevented as a component instead of a bug you find in production. PIIMiddleware detects sensitive data and can mask, redact, or hash it across inputs, model outputs, and tool outputs — so a customer's SSN never lands in a log or a downstream call.

Behind those sit the fault-tolerance and cost-control classes: ModelCallLimitMiddleware and ToolCallLimitMiddleware cap how many times the loop can run (your runaway-bill insurance), ModelFallbackMiddleware swaps to a backup model when the primary errors, and ToolRetryMiddleware re-runs a flaky tool. There's more on the shelf — TodoListMiddleware, LLMToolSelectorMiddleware, ContextEditingMiddleware, ShellToolMiddleware, and others — but the reflex to build is this: before you write custom middleware, check whether the concern already has a class. Most of the standard production worries do.

Shaping the output

response_format folds structure into the loop

A production agent almost never wants a free-text blob back — it wants a typed object your code can act on: { order_id, status, refund_approved, reason }. The naive way to get that is a second LLM call after the agent finishes, asking it to reformat its answer as JSON. That's an extra round trip: more latency, more cost, more to break.

create_agent's response_format argument folds structured output into the main model-and-tools loop instead. You pass it a Pydantic model (the usual choice), or a ToolStrategy / ProviderStrategy when you need to control how the structure is enforced; raw schemas get auto-wrapped based on what the model supports. Because it's part of the same loop, the LangChain team's framing is precise: integrating structured output this way reduces latency and cost by "eliminating extra LLM calls." You define the shape once, as a type, and the agent returns something that already matches it.

The FDE angle: structured output is the seam between the agent and the rest of the system. A support agent whose answer is a validated object can drive a real workflow — flip a ticket status, trigger a refund, update a CRM — with no brittle string-parsing in between. Free text impresses in a demo; a typed contract is what lets the agent become a step in an actual business process. Getting the structure for free inside the loop, rather than paying for a second call to bolt it on, is the kind of quiet efficiency a client notices on the invoice.

Real tools

MCP bridges the agent into real systems

So far the tools were Python functions you wrote. In production, the useful tools already live somewhere — in a database service, an internal API, a filesystem server — and increasingly they're exposed through the Model Context Protocol (MCP), the open standard for connecting agents to tools and data. The bridge from MCP into LangChain is MultiServerMCPClient, from the langchain-mcp-adapters package (v0.3.0). You point it at one or more MCP servers, and it hands you back LangChain tools:

client = MultiServerMCPClient({...}) tools = await client.get_tools() # → LangChain BaseTools agent = create_agent(model, tools) # drop them straight in

get_tools() returns ordinary BaseTools, so they pass straight into create_agent exactly like your hand-written ones — the agent can't tell the difference. One important detail for reasoning about behavior and cost: the client is stateless by default. Each tool invocation opens a fresh ClientSession, runs the call, and cleans up. That's simple and robust, but if you need a persistent connection — a session that keeps state across several calls — you use client.session() explicitly. Knowing that default is how you answer "why does each tool call reconnect?" without guessing.

There's also error handling worth pinning down before an incident, not during one. By default, when an MCP tool fails, the failure comes back to the model as a ToolMessage with status="error" — so the agent can read the error and retry or adapt, which is usually what you want. If you'd rather a failure raise an exception and stop the loop hard, set handle_tool_errors=False. That single flag is the difference between "the agent gracefully recovers from a flaky tool" and "the run halts loudly so a human sees it" — and which you want depends on the client's risk posture.

The wire

stdio vs. Streamable HTTP: pick the transport

MCP defines two standard transports, and choosing between them is a real FDE decision. The current spec (2025-06-18) settles on stdio and Streamable HTTP — the latter replacing the older HTTP+SSE transport from the 2024 spec. In the client, the transport is just config.

stdio launches the MCP server as a local subprocess and talks JSON-RPC over its stdin/stdout (newline-delimited, no embedded newlines). You configure it like {"transport": "stdio", "command": "python", "args": [...]}. The spec says clients SHOULD support stdio whenever possible — it's the natural fit for a tool server that runs on the same box as the agent: a local database adapter, a filesystem tool, a CLI wrapper. No network, no ports, no auth to misconfigure.

Streamable HTTP targets a remote endpoint — {"transport": "http", "url": "http://localhost:8000/mcp"} — a single URL that handles POST and GET with optional SSE streaming. Use it when the tool server is a shared service other teams also call. But it comes with security homework the spec makes normative: servers MUST validate the Origin header and SHOULD bind to localhost when running locally, both to defend against DNS-rebinding attacks, and can use an optional Mcp-Session-Id for stateful sessions. When a client asks "is exposing this tool server over HTTP safe?", that is your checklist — Origin validation and binding scope, not vibes. Local subprocess tool → stdio; shared network service → Streamable HTTP with the security requirements actually met.

Putting it together

What a production single agent actually is

Now stack the whole thing and look at it. A production single agent is create_agent at the core — the model-and-tools loop on the LangGraph runtime — wrapped in a middleware stack that encodes the client's policy (human approval on high-stakes actions, PII redaction, summarization to survive long sessions, call limits and fallbacks for cost and resilience), returning a typed object via response_format so it can drive real workflows, with its tools supplied by MCP servers over the right transport. That's it. Four arguments to a factory and a shelf of composable pieces.

Notice what this buys you as an engineer. Every worry a client raises has a named home. "Can it spend money without oversight?" → HITL middleware. "Will it leak customer data into logs?" → PII middleware. "What happens on a long conversation?" → summarization. "What if a tool flakes?" → retry and fallback. "How does it connect to our internal API?" → MCP client and the transport choice. You're no longer hand-waving; you're pointing at layers. That legibility — being able to walk a stakeholder through exactly what stands between a user message and an action — is a large part of what makes an agent shippable rather than just impressive.

FDE mindset

A client rarely rejects an agent because it isn't smart enough. They reject it because nobody can tell them what it will and won't do, or what happens when a tool fails, or where the customer's data goes. A production single agent isn't a smarter model — it's the same loop with every risk given a named, composable home. Build the loop, then defend it layer by layer. That defense is the deliverable.

Deep dive: the middleware stack, ordered

Optional. ~10 minutes. Why the same pieces in a different order behave differently.

Middleware "composes freely" — but composition has an order, and order has consequences. Because the wrap_* hooks surround a call, the pieces form nested shells around the model-and-tools loop: the first middleware on the stack is the outermost shell, the last is closest to the model. A request passes inward through each before / wrap entry, hits the model or tool, then passes back outward through each after / wrap exit.

Worked example — one support turn, four middleware
  • PIIMiddleware — masks the customer's email on the way in, so nothing downstream (model, tools, logs) ever sees the raw value.
  • SummarizationMiddleware (before_model) — trims long history so the window doesn't overflow before the model is called.
  • HumanInTheLoopMiddleware — pauses at the refund tool call for an approve/edit/reject click.
  • ToolCallLimitMiddleware — caps the loop at, say, 6 tool calls so a stuck agent can't spin.

Put PII redaction outermost and it protects everything inside it. Put it innermost — after the model has already seen the raw data — and you've defeated the point. Same four pieces, different guarantee. When you review a client's agent, read the stack top-to-bottom and ask, for each guardrail, "is this early enough to actually protect what it needs to?"

Human-in-the-loop is durable, not a blocking sleep. When HumanInTheLoopMiddleware pauses, it does so through the LangGraph runtime's persistence — the run's state is checkpointed and can wait minutes, hours, or across a process restart for the human's decision, then resume exactly where it stopped. That's why the checkpointer/store arguments matter: durable pause-and-resume is what makes approval gates practical instead of a socket held open.
