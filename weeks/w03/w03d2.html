Tools & MCP: One Port for Every Integration

Week 3 · Day 2 Agents & Tool Use ~18 min · reading @150 wpm + diagram + check

Yesterday a model could only talk. Today it can act — read a file, query a database, open a pull request — because something standard sits between the model and the outside world. That something is the Model Context Protocol (MCP): an open standard, open-sourced by Anthropic on 2024-11-25, that Anthropic itself calls "a USB-C port for AI applications." Today you learn its architecture, its primitives, how a tool is discovered and called, how the bytes travel, and — the part clients actually pay an FDE to get right — why every tool is arbitrary code execution and must have a human in the loop. We teach against the current stable spec revision, 2025-11-25. The panel on the right builds up one MCP deployment piece by piece as you scroll.

The whole game

The N×M problem, and the port that kills it

Before MCP, every time you wanted an AI app to touch a new system — a filesystem, GitHub, a Postgres database, a Slack workspace — someone wrote a bespoke connector. Anthropic describes the pre-MCP world bluntly: AI assistants were "constrained by their isolation from data — trapped behind information silos and legacy systems." Worse, the cost multiplied. If you have M AI applications and N data sources, the naive world needs up to M×N custom integrations, each one written, tested, and maintained separately. Every new tool meant new glue code in every app that wanted it.

MCP replaces that mesh with a single contract. It is, in the official words, "an open-source standard for connecting AI applications to external systems" — data sources, tools, and workflows — so you "build once against the protocol instead of one bespoke connector per data source." The analogy the docs lead with is worth memorizing because you will repeat it to clients: "Think of MCP like a USB-C port for AI applications." Just as USB-C standardized how devices connect to peripherals, MCP standardizes how an AI app connects to external systems. Write a tool as an MCP server once, and any MCP-aware app can use it — no per-app glue.

That is the reframe for the day. Tools are not a feature you bolt onto one model; they are an ecosystem you plug into through a shared port. When a client asks "how do we let our assistant use our internal systems without rewriting integrations for every vendor's AI?", the honest first answer is: expose them once, behind MCP. The rest of today is what that port actually looks like when you open it up.

Architecture

Host, client, server — and a 1:1 wire

MCP "follows a client-host-server architecture where each host can run multiple client instances." Three roles, and keeping them straight is the difference between reasoning clearly about a deployment and hand-waving. The host is the AI application itself — Claude Desktop, an IDE assistant, your agent. It is the coordinator: it runs the model, it enforces security and user consent, and it decides which servers to connect to. The server is a program that "exposes resources, tools and prompts via MCP primitives" — the Filesystem server, the GitHub server, your own internal-API server. Between them sits the client, which lives inside the host and "maintains an isolated server connection."

Here is the detail people miss: a client has a 1:1 relationship with a particular server. One client, one server, one dedicated connection. If your host talks to three servers, it spins up three clients. That isolation is deliberate — it keeps a misbehaving or malicious server boxed into its own channel, and it makes consent and auditing tractable one connection at a time.

Underneath, every message is JSON-RPC 2.0 — a small, boring, well-understood request/response format. Nothing exotic on the wire; that is a feature. And the design lineage is intentional: MCP is inspired by the Language Server Protocol (LSP), which did for editors and languages exactly what MCP does for AI apps and tools — standardize one integration surface so an N×M explosion collapses into N+M. Learn the port once; the whole ecosystem opens.

Primitives · who's in control

Three server primitives, split by who controls them

A server can offer three kinds of thing, and the load-bearing mental model for the entire day is not what they are but who controls them. Get this and everything downstream — safety, invocation, UX — falls out of it.

Tools are "functions for the AI model to execute," and they are explicitly model-controlled: "the language model can discover and invoke tools automatically." The model decides, mid-reasoning, to call search_flights or run_query. Resources are "context and data, for the user or the AI model to use" — files, records, documents — and they are application-controlled: the host app decides what context to pull in and attach. Prompts are "templated messages and workflows for users" and are user-controlled — think the slash-commands a user picks from a menu. Model / app / user: three controllers, three primitives.

The symmetry runs the other way too. A capable client can offer three server-initiated primitives back to the server: Sampling ("server-initiated agentic behaviors and recursive LLM interactions" — the server asks the host's model to think), Roots ("server-initiated inquiries into URI or filesystem boundaries to operate in" — the server asks which directories it's allowed to touch), and Elicitation ("server-initiated requests for additional information from users" — the server asks the human a question mid-task). These aren't automatic; sampling, for instance, "requires the client to declare support in its capabilities." Which is our first hint at how MCP stays safe and extensible — a preview of the negotiation step coming up.

Tool invocation

Discover with tools/list, act with tools/call

Because tools are model-controlled, the model first has to know what exists. Discovery is a single JSON-RPC method: the client sends a tools/list request (paginated with a cursor, so a server exposing hundreds of tools returns them in pages) and gets back an array of Tool objects. Each Tool carries a name (its unique id), a description (which the model reads to decide when to use it — write it like a prompt, because it is one), and an inputSchema that "MUST be a valid JSON Schema object" (defaulting to JSON Schema 2020-12). Optionally it carries a human-friendly title, an outputSchema, and annotations (hints like "read-only" or "destructive"). If the available tools change at runtime, a server that declared listChanged should send a notifications/tools/list_changed so the client re-fetches.

To actually run one, the client sends tools/call with the tool's name and an arguments object that satisfies the input schema. That's the whole loop: list to discover, call to act. The Tool's schema is what makes this safe-ish to automate — the model can only fill in arguments the schema allows, and a client can validate the arguments before anything executes. The description and schema together are your primary lever on tool quality: a vague description gets a tool called at the wrong moment; a loose schema gets it called with garbage. Both are FDE tuning surface.

Results & errors

Two kinds of error, and why the difference matters

A tool result carries a content array — one or more typed items: text, image, audio, a resource_link, or an embedded resource. For machine-readable results, a tool can also return structuredContent as a JSON object; if it declared an outputSchema, then servers "MUST provide structured results that conform to this schema" and clients "SHOULD validate structured results against this schema." (For backwards compatibility, a tool returning structured content should also serialize it into a text block, so older clients still see something.)

Now the part that trips up everyone the first time, and the reason it's worth a whole step: MCP has two distinct error channels, and choosing the wrong one quietly breaks agent behavior. Protocol errors — unknown tool, malformed request, server crash — are standard JSON-RPC error objects. But a tool-execution error — the flight search found nothing, the API returned 403, the input failed a business rule — is returned inside a successful result with isError: true set in the result body. Not a JSON-RPC error. A successful response that says "the tool ran and here's why it didn't work."

The spec's rationale is the whole point: "Tool Execution Errors contain actionable feedback that language models can use to self-correct and retry with adjusted parameters," and "clients SHOULD provide tool execution errors to language models to enable self-correction." If you bury a validation failure in a JSON-RPC protocol error, the model never sees it and can't fix its own arguments; surface it as isError content and the model reads "date must be in the future," adjusts, and retries. Business-logic failures belong in isError; only genuine protocol faults belong in JSON-RPC errors. That distinction is a real bug you will find in client codebases.

Transports

Two ways the bytes travel: stdio and Streamable HTTP

The architecture is transport-agnostic, but the spec "currently defines two standard transport mechanisms," and knowing which is which saves you an afternoon of debugging. The first is stdio: "the client launches the MCP server as a subprocess," and the two exchange newline-delimited JSON-RPC over the process's stdin and stdout. It's local, it's simple, there's no network, and "clients SHOULD support stdio whenever possible." This is how a desktop app talks to a Filesystem or Git server running on the same machine — no ports, no auth, just a child process.

The second is Streamable HTTP: the server exposes "a single HTTP endpoint path" that supports POST (client → server) and GET, optionally upgrading a response to Server-Sent Events (SSE) so the server can stream multiple messages back over one connection. This is for remote and multi-client servers — a hosted GitHub server your whole team hits. Two headers matter: HTTP clients "MUST send MCP-Protocol-Version: <revision>" on every request so the server knows which spec revision to speak, and a session can be tracked with an MCP-Session-Id header.

One historical footnote that saves you from stale tutorials: Streamable HTTP replaced the deprecated HTTP+SSE transport from protocol version 2024-11-05. If you find a guide wiring up two separate endpoints (one POST, one long-lived SSE), it's teaching the old two-endpoint design. The current model is a single endpoint that optionally streams. Pin your reading to a dated revision — MCP moves fast enough that undated blog posts are a real trap.

Capability negotiation

You can only use what was declared at init

Every MCP connection opens with a handshake, and that handshake is where MCP gets its extensibility. MCP "uses a capability-based negotiation system where clients and servers explicitly declare their supported features during initialization. Capabilities determine which protocol features and primitives are available." The rule is strict and simple: a feature is only usable if it was declared.

Concretely: a server that wants to offer tools declares the tools capability at initialize time — for example {"capabilities":{"tools":{"listChanged":true}}}, which also promises it will send list-changed notifications. A server that wants clients to subscribe to resource updates must declare subscription support. A client that will honor sampling requests must declare that it can. If it wasn't declared in the handshake, the other side must not use it — no probing, no surprises.

Why is this the quietly brilliant part? Because it means "features can be added to servers and clients progressively" without breaking anyone. A brand-new server capability that an old client never declared support for simply doesn't get exercised against that client; both sides degrade gracefully to the intersection of what they both understand. That is how a fast-moving protocol stays backward-compatible: nobody assumes, everybody declares, and the negotiated set is the contract for that session. When you debug "why won't this server's fancy feature work in this host?", your first move is to read the negotiated capabilities — the answer is almost always that one side never declared it.

Safety · the FDE's real job

A tool is arbitrary code — keep a human in the loop

Here is the sentence to tattoo next to yesterday's: "Tools represent arbitrary code execution and must be treated with appropriate caution." A tool call is not a query — it can delete files, move money, send email, run shell commands. The moment you give a model tools, you have handed a probabilistic system the ability to act on the world. The spec responds not with a vibe but with hard requirements, and these are exactly what a client is paying you to get right.

First, human-in-the-loop is mandatory: "there SHOULD always be a human in the loop with the ability to deny tool invocations," and hosts "MUST obtain explicit user consent before invoking any tool." The model proposes; a human disposes. Second — and this is the footgun that catches experienced engineers — "clients MUST consider tool annotations to be untrusted unless they come from trusted servers." A tool can annotate itself as "read-only" or "safe." That annotation is a claim by the server, not a guarantee; a malicious or compromised server will happily label a destructive tool as harmless. Never let a self-reported annotation stand in for a real consent gate.

Third, for network transports the spec is specific about a classic attack: Streamable HTTP servers "MUST validate the Origin header ... to prevent DNS rebinding attacks," and local servers "SHOULD bind only to localhost" rather than 0.0.0.0. Skip that and a random web page the user visits can reach the tool server running on their laptop. This is the FDE's actual job on an agent engagement: not "make the model call tools" — that's easy — but "make sure it can't call the wrong tool, without consent, against a server that lied about being safe, reachable from the open internet." Diagnose the consent path before you celebrate the capability.

Roadmap · not yet stable

Where MCP is heading — and the mindset that outlasts it

Teach today against 2025-11-25, but know what's coming so you don't design into a corner. The next revision — an RC locked 2026-05-21, publishing 2026-07-28 — reorients MCP around a stateless HTTP core. The roadmap's top priority is transport scalability: today's "stateful sessions fight with load balancers, horizontal scaling requires workarounds," so the RC moves toward statelessness plus .well-known capability discovery. It also adds an Extensions framework, Tasks for long-running work (with retry/expiry semantics under an "Agent Communication" banner), and MCP Apps (server-rendered UI). A tell that this is already in motion: even the 2025-11-25 Tool object carries an optional execution.taskSupport field (forbidden default / optional / required), foreshadowing Tasks. Treat all of it as roadmap, not shippable API — pin your code to a dated revision and flag the RC as "coming, not yet stable."

The through-line from yesterday holds. Day 1 said: diagnose the window before you blame the model. Today says: diagnose the protocol boundary before you blame the tool. Who controls this primitive — model, app, or user? Was this capability actually declared at init? Is this an isError the model can self-correct from, or a protocol fault it never sees? Is there a human on the consent gate, and did anyone verify the server before trusting its annotations? Those questions don't expire when the spec revision does.

FDE mindset

When an FDE wires an agent into a client's systems, the win is never "look, it can call tools." It's "every tool call is discoverable, validated, negotiated, and gated by a human who can say no." MCP is the USB-C port; your job is to make sure what gets plugged in is safe, scoped, and auditable. Tomorrow we take these tool-calling foundations and build the agent loop that decides which tools to call, in what order, until the task is done.

Deep dive: JSON-RPC on the wire

Optional. ~10 minutes. What the port actually says when you open it — every message is plain JSON-RPC 2.0, teaching revision 2025-11-25.

1 · The handshake. Nothing works until both sides declare capabilities. The client opens with initialize; the server answers with the features it supports. A feature not named here cannot be used this session.

client → server
  • {"jsonrpc":"2.0","id":1,"method":"initialize",
  •  "params":{"protocolVersion":"2025-11-25",
  •  "capabilities":{"sampling":{}}}}
server → client
  • {"jsonrpc":"2.0","id":1,"result":{
  •  "capabilities":{"tools":{"listChanged":true}}}}

2 · Discover, then call. tools/list returns Tool objects (name + inputSchema); tools/call runs one with arguments.

tools/call — the request
  • {"jsonrpc":"2.0","id":7,"method":"tools/call",
  •  "params":{"name":"get_weather",
  •  "arguments":{"city":"Austin"}}}
a tool-execution error — note it's a success result
  • {"jsonrpc":"2.0","id":7,"result":{
  •  "content":[{"type":"text","text":"No data for 'Austn'"}],
  •  "isError":true}}

Why isError and not a JSON-RPC error? Because the model reads the result. "No data for 'Austn'" tells it the city was misspelled, so it retries with "Austin" — the self-correction loop the spec is explicitly designed for. A JSON-RPC error object would have been hidden from the model, and the agent would have simply given up.
