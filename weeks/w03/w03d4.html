Agent Memory: What the Agent Keeps in Hand vs What It Files Away

Week 3 · Day 4 Agents & Orchestration ~18 min · reading @150 wpm + diagram + check

An LLM forgets everything the instant a call returns. So the moment you ask it to act across many turns — an agent, not a one-shot answer — you have to build the memory yourself. There are exactly two tiers, and confusing them is the source of most "why did the agent forget / why is it so slow / why did it repeat itself" tickets you will ever field. Today you learn the split: short-term (working) memory that lives inside the context window for one thread, and long-term memory that lives in an external store, outside the window, recallable from any thread. The panel on the right builds both tiers, then shows how data pages between them.

The whole game

A stateless model can't remember — so the agent has to

Everything this week has circled one uncomfortable fact from Week 1: the model has no memory between calls. Each request is a blank slate; whatever the model can reason over has to be sitting in the context window for that call. That's tolerable for a single question. It is a crisis for an agent — an LLM running in a loop, taking actions over many turns — because an agent that can't remember what it just did will re-ask, re-plan, and re-tread the same ground forever.

So "memory" for an agent is not a feature the model has. It is infrastructure you build around the model: text you decide to keep, store somewhere, and re-supply on the next call. And the single most useful thing you can carry into any client engagement is that this infrastructure comes in exactly two tiers, with a hard line between them. Short-term memory is the ongoing conversation — the working set the agent holds in hand right now, inside the window, for this one thread. Long-term memory is everything the agent has filed away for later — persistent, outside the window, recallable from any thread at any time.

Almost every real agent-memory bug is a category error between those two tiers: someone tried to make the window do long-term memory's job (and it overflowed), or expected the store to behave like the live conversation (and it felt stale). Get the taxonomy crisp first and the fixes become obvious. That's today. By the end you'll diagnose an agent's memory the way you learned to diagnose a window in Week 1 — by asking which tier is this, and is the data where it needs to be?

Tier 1 · short-term

Short-term memory is the thread you're in

Short-term memory — also called working or conversational memory — is thread-scoped. It tracks the ongoing conversation by maintaining the message history within a single session or thread: the user turns, the model's replies, the tool calls and their results, all in order. In LangGraph's terms it is part of the agent's runtime state, and it is persisted across steps by a checkpointer — the mechanism that snapshots the graph's state so the agent can pause, resume, and continue the same thread without losing its place.

The key word is thread. Short-term memory belongs to one conversation. Start a new thread — a different user, a different session, a fresh support ticket — and this working set is gone, by design. It is the equivalent of what you're holding in your head during a single meeting: sharp, complete, and irrelevant the moment the meeting ends. The OpenAI Agents SDK models the exact same idea under a different name: a Session. Before each run, its runner "automatically retrieves the conversation history for the session and prepends it," and after the run "all new items generated during the run are automatically stored" — so you never hand-thread the transcript between turns yourself.

That automation is worth pausing on, because it hides where the tokens go. The framework is quietly re-sending the growing transcript on every turn to keep the conversation feeling continuous. Convenient — and, as you'll see in the next slice, a ceiling you will slam into. Short-term memory is powerful precisely because it is always present in the window; it is also fragile for exactly the same reason.

The ceiling

Working memory is bounded by the context window

Here is the wall. Short-term memory lives inside the context window, which means it inherits the window's hard ceiling. The core short-term challenge, stated plainly in the LangChain docs, is that the full history may not fit inside an LLM's context window. A long agent run — dozens of tool calls, pages of intermediate output — will grow its message history past the limit, and then something has to give.

The standard moves are trimming and summarization: drop or compress stale turns so the working set stays under budget. Trimming deletes old messages outright; summarization replaces a span of old turns with a short synopsis that preserves the gist while spending far fewer tokens. Both are, in effect, deliberate forgetting — you choose what stale information to let go of to manage token usage and keep the agent fast. This is the same discipline you met in Week 1 as history eviction, but now you're the one doing it on purpose, with a strategy, rather than letting the front of the window silently drop off.

The FDE reflex to build here: when an agent "loses the plot" partway through a long task, don't reach for a bigger model. Ask whether its working memory blew past the window and got crudely truncated. The fix is a memory-management strategy — trim, summarize, or offload — not more parameters. And notice the limitation this exposes: short-term memory can never be the place you keep something that must survive. Anything the agent truly needs to remember tomorrow, or in a different thread, has to live somewhere the window can't evict it. That somewhere is Tier 2.

Tier 2 · long-term

Long-term memory lives outside the thread and outside the window

Long-term memory is the opposite of everything we just said. It stores user-specific or application-level data across sessions and is shared across conversational threads. It can be recalled at any time and in any thread, and — crucially — it is scoped to any custom namespace, not just within a single thread ID. Where short-term memory is the meeting you're in, long-term memory is the filing cabinet you walk back to between meetings.

Two properties define it, and both are the mirror image of Tier 1. First, it lives outside the context window: it is not always sitting in the prompt burning tokens. It is stored externally and pulled in only when relevant. Second, it is not thread-scoped: a fact the agent learned about a user in Monday's conversation is available in Friday's, in a different session, in a different workflow entirely. That cross-thread persistence is the whole point — it's what lets an assistant say "last quarter you told me your team standardized on Postgres" three weeks and ten conversations later.

Because it isn't always present, long-term memory has to be retrieved on demand rather than assumed. The agent (or the framework) decides a stored memory is relevant, fetches it, and drops it into the window for this call — then it's gone from the window again when the call returns. This is why long-term memory pairs so naturally with retrieval: fetching the right memory at the right moment is the same precision-of-retrieval skill you practiced with RAG, applied to the agent's own accumulated knowledge instead of a document corpus.

The store

The memory store: namespaces and keys, not a thread

Long-term memory needs a home, and that home is a memory store — a persistent, cross-thread key/value store (LangGraph calls the interface a BaseStore) that holds memories independently of any conversation. This is where the checkpointer / store distinction becomes load-bearing, and it's a favorite interview trap: the checkpointer persists within-thread state (Tier 1); the store persists across threads (Tier 2). They are different components doing different jobs. Conflating them is exactly the category error we opened with.

The store organizes memories with two coordinates. A namespace works like a folder — typically built from user or org IDs so information is filed hierarchically (all of one user's memories under their ID, for instance). A key works like a filename, identifying an individual memory within that namespace. So "user 4471's dietary preferences" is a namespace plus a key, addressable and updatable without touching anyone else's memories or any particular conversation thread. That structure is what makes cross-thread recall tractable: the agent knows where to look because the memory was filed under a stable, meaningful address rather than buried in the flow of one chat.

Design consequence for you as an FDE: the namespace scheme is your multi-tenancy and privacy boundary. Namespace memories by user or org and one tenant's agent can never recall another's. Get lazy and dump everything into a flat namespace and you've built a data-leak. The store's folder/file structure isn't bookkeeping trivia — it's the seam where memory design meets the tenant-isolation rules the client will hold you to.

Taxonomy

Three flavors of memory, borrowed from human psychology

Long-term memory isn't monolithic. A useful taxonomy — lifted straight from how psychologists describe human memory — splits it into three types, and knowing the vocabulary helps you talk to a client about what kind of thing the agent should remember. Semantic memory is the retention of specific facts and concepts: the user's name, their tech stack, a policy threshold. Episodic memory is recalling past events and experiences: what happened in a prior session, how a previous task played out. Procedural memory is remembering the rules used to perform tasks — for an agent, "a combination of model weights, agent code, and the agent's prompt."

The clean way the docs draw the line: facts can be written to semantic memory, whereas experiences can be written to episodic memory. Semantic is the what — durable, atomic truths. Episodic is the what happened — narrative, time-stamped. And procedural is the how, which for an agent mostly lives not in a store at all but in its weights, its code, and above all its prompt. That last point is worth holding onto: when you refine an agent's system prompt to change how it approaches a task, you are, in a real sense, editing its procedural memory.

You don't have to build three separate databases to use this. The taxonomy is a design lens: faced with "the agent should remember X," ask which kind X is. A stable fact about the user? Semantic — store it, overwrite it when it changes. A record of a past interaction? Episodic — append it, timestamp it, retrieve similar ones later. A change in how the agent should behave? Procedural — that's a prompt or code change, not a row in the store. Matching the memory type to the storage strategy is what separates a coherent memory design from a junk drawer of stashed strings.

The pattern

Virtual context management: the model as its own OS

Where did the whole "two tiers, page between them" idea come from? The cleanest articulation is MemGPT, which framed LLMs as operating systems. Its central move is virtual context management — "a technique drawing inspiration from hierarchical memory systems in traditional operating systems." An OS gives each program the illusion of vast memory by paging data between fast RAM and slow disk; MemGPT gives the LLM the illusion of unbounded memory by paging between the context window and an external store.

The analogy is precise. Main context is the LLM's prompt tokens — "anything in main context is considered in-context," analogous to RAM. External context is everything else — "out-of-context data must always be explicitly moved into main context," analogous to disk. Main context is subdivided into three sections: read-only system instructions, a fixed-size read/write working-context block that the model can edit only through function calls, and a FIFO queue holding a rolling message history. External context splits into recall storage (a conversation-history database) and archival storage (a read/write database of arbitrary-length text). Map that back onto today: main context is your short-term tier, external context is your long-term tier, and the sections are just the anatomy of each.

Interactive — future goal

Planned: a MemGPT-style paging visualizer — the agent hits a full window, issues a function call to evict old turns to recall storage, then later issues another call to page a relevant memory back from archival storage into main context. You'd step through the calls and watch data move between RAM and disk. Needs backend standup.

The genius stroke is who drives the paging. In MemGPT, "memory edits and retrieval are entirely self-directed": the LLM autonomously issues the function calls to move data between main and external context. The model manages its own memory the way a program requests pages — except the program is doing the requesting via tool calls it decides to make. That self-directed paging is the conceptual foundation under every "LLM-managed long-term memory" system you'll meet, and it's why memory operations show up as tools in modern agent frameworks.

In practice

Two tiers, two toolchains — and they're complementary

The taxonomy is abstract; the products make it concrete, and they line up cleanly on the two tiers. For short-term memory, the OpenAI Agents SDK's Sessions handle the working set with pluggable backends — SQLite (the default, file or in-memory), Redis, SQLAlchemy, MongoDB, Dapr, and OpenAI-hosted Conversations storage. The agent code doesn't change; you swap a local file for a production datastore as you scale. That's the whole promise of the abstraction: short-term memory that grows from a laptop demo to a real system without a rewrite.

For long-term memory, Anthropic's memory tool lets Claude "store and retrieve information across conversations in a directory of memory files," building up knowledge over time "without keeping everything in the context window" — an explicit long-term mechanism, distinct from the in-context conversation. Architecturally it's worth knowing it's client-side: Claude only requests file operations (view, create, str_replace, insert, delete, rename) under a /memories prefix, and your application executes them against storage you control. It's generally available — tool type memory_20250818, no beta header, on all Claude 4+ models. Your app owns the disk; the model just asks for pages. Straight out of the MemGPT playbook.

The synthesis to carry out the door: these two tiers are complementary, not interchangeable. Anthropic pairs the memory tool with context editing and server-side compaction, and describes the division exactly — for long-running agents, "compaction keeps the active context small … and memory preserves the information that must survive summarization." Read that twice. Compaction manages short-term memory (keep the window lean); the memory files are long-term memory (keep what has to outlive the summary). When a client's agent forgets something that mattered, your first question is now a taxonomy question: was this supposed to be in working memory or long-term memory — and was it actually written to the right tier? That single question resolves the vast majority of agent-memory tickets before you ever touch the model.

Deep dive: MemGPT's memory hierarchy

Optional. ~10 minutes. The anatomy under "two tiers."

The OS analogy, literally. MemGPT treats the LLM like a process and the context window like RAM. Just as an OS pages data between fast RAM and slow disk to give programs the illusion of near-unlimited memory, virtual context management pages data between the window (main context) and external stores (external context) to give the LLM the illusion of unbounded memory. Anything in main context is in-context; out-of-context data "must always be explicitly moved into main context" before the model can use it.

Main context — the window, in three sections
  • System instructions — read-only; the standing rules (procedural memory).
  • Working-context block — fixed size, read/write, editable only via function calls; the agent's scratchpad of durable facts.
  • FIFO queue — a rolling message history; oldest turns roll off the front as it fills.
External context — outside the window
  • Recall storage — a conversation-history database (past messages beyond the FIFO queue).
  • Archival storage — a read/write database of arbitrary-length text; the long-term filing cabinet.

Self-directed paging. The defining move: "memory edits and retrieval are entirely self-directed." The LLM itself issues the function calls to move data between main and external context — no external orchestrator decides what to page. Map it to today: main context ≈ short-term memory, external context ≈ long-term memory, and the function calls ≈ the memory tools (like Anthropic's /memories operations) that modern agents use to manage their own recall.
