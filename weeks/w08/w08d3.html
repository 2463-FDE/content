Guardrail Frameworks: Pricing the Control

Week 8 · Day 3 Responsible AI & Governance ~26 min · reading @150 wpm + diagram + check

Week 7 Day 5 wired a guardrail into a path you already observe. Today you choose which guardrail, on what hardware, at what price, from a vendor that will still exist next year. Four names dominate — NeMo Guardrails, Guardrails AI, LLM Guard, Presidio — and they are not four options; three wrap the fourth. The angle is the only one an exec can act on: cost of control versus cost of incident, every term priced — added latency, dollars per thousand units, and the false-positive rate the front desk actually feels. Output: a recommendation memo, via the 60-minute decision protocol from Week 7 Day 3. Scroll; the panel assembles the request path, then hangs a price on every position in it.

Taxonomy

Four names, but not four options

The instinct is a four-way bake-off. That is a category error: these tools sit at different altitudes.

NeMo Guardrails (NVIDIA, Apache-2.0, 0.23.0) is a dialogue-management runtime; its EMNLP paper frames it as "programmable rails… user-defined, independent of the underlying LLM, and interpretable," as distinct from guardrails "embedded into a specific model at training." Guardrails AI (Apache-2.0, 0.10.2) is an output-validator framework: its unit is the Guard, which "wraps LLM calls, orchestrates validation, and keeps track of call history." LLM Guard is a flat scanner pipeline — scanners around the call, each returning (sanitized_prompt, is_valid, risk_score). And Presidio is not a guardrail at all; its README calls it a "Data Protection and De-identification SDK."

Here is the fact that collapses the comparison. Three of the four wrap the fourth. NeMo's sensitive-data rails require you to pip install nemoguardrails[sdd] and pull spaCy's en_core_web_lg — because they are Presidio. Guardrails Hub's Detect PII validator says it detects PII "using Microsoft Presidio." LLM Guard's Anonymize scanner advertises "Integration with Presidio Analyzer." So the real decision is two decisions: which orchestration model you want, and what you feed the detector. NeMo's own guardrail catalog — Content Safety, Jailbreak Protection, Topic Control, PII Detection, Agentic Security, Tool Calling, Hallucinations & Fact-Checking, LLM Self-Check, Third-Party APIs — is the cleanest available list of what "a guardrail" can even mean. Use it as the memo's option space so nothing gets silently dropped.

Placement

Five positions — and two different products at each

NeMo ships five rail types, and the vocabulary is worth borrowing even if you never install it: it gives an exec five nameable places instead of one vague "filter." Input rails reject or alter the input. Dialog rails operate on canonical forms. Retrieval rails can reject a chunk "preventing it from being used to prompt the LLM." Execution rails wrap tool input and output. Output rails reject or alter the response.

Two consequences. First, the same capability at the same position is two different products — a product decision, not a config detail. NeMo's docs: detect sensitive data on input means "the bot will refuse to respond"; mask sensitive data on input means the bot "will mask the sensitive parts… and continue." One produces a blocked user. The other produces a degraded answer with holes in it. Somebody at the client owns that choice; leave it out of the memo and they inherit whatever the default is.

Second — and this is the position teams forget — the retrieval rail is the only one that stops corpus PHI from entering the prompt at all. An output filter on a RAG-over-records system is theatre: by the time it fires, the record has already been sent to the vendor. If PHI lives in your corpus, the scrub belongs on the request and on the chunk, not on the answer.

Placement · streaming

Streaming defaults to the unsafe half of the tradeoff

All five positions assume a request/response shape. Streaming breaks that assumption, and NeMo is unusually honest about the consequence. Under rails.output.streaming, stream_first defaults to True, meaning "the client receives each chunk of tokens before output rails process that chunk. This provides faster time-to-first-token, but if a rail blocks the content, the user has already received the tokens." The stream then terminates with a JSON error — after the disclosure. Set it to False and "the user never sees blocked content, but time-to-first-token increases by the rail execution time per chunk."

The knobs price that tradeoff explicitly. chunk_size defaults to 200 tokens: larger means fewer rail executions but higher latency to first output; smaller means more executions and faster first token. context_size defaults to 50 tokens carried across chunk boundaries so a sentence spanning two chunks can still be evaluated — drop it and you get misses that look random. And enabled defaults to False: calling stream_async() with output rails configured but streaming disabled is a hard error, not a silent degrade.

Write it into the memo as a sentence an exec can veto: "Streamed summaries show the clinician tokens the safety rail has not yet cleared. Turning that off costs roughly one rail execution per 200 tokens of added time-to-first-token." That is a decision. "We enabled guardrails" is not.

Latency

A latency number without an instance type is fiction

LLM Guard is the only project here that publishes per-scanner p90/p95/p99 with the machine named — Amazon Linux 2, Python 3.11.6, five runs. That makes it the category's reference table, including for tools that publish nothing.

PromptInjection (384-char input): m5.xlarge 212.87 ms avg / 317 ms p99; the same box with ONNX 104.21 / 107; g5.xlarge GPU 81.01 / 329; g5.xlarge GPU + ONNX 7.65 / 14.75; Azure Standard_D4as_v4 421.46 / 1,237. Anonymize — the PII scanner, Presidio plus BERT NER, 317-char input — is the expensive one: m5.xlarge 177.13 / 325.71, +ONNX 128.64 / 179.93, GPU+ONNX 38.11 / 99.26.

Two levers fall straight out. ONNX runtime is roughly 2× on CPU and ~10× on GPU, and it is a one-line change (pip install llm-guard[onnxruntime], use_onnx=True) — it also collapses variance, from 3.00 to 0.00 on m5.xlarge for PromptInjection. And instance type can dominate tool choice: Toxicity runs at 4.80 ms on g5.xlarge GPU+ONNX, 34.13 ms on m5.xlarge+ONNX, and 620.79 ms on r6a.xlarge — a 129× spread on identical code and an identical benchmark. Benchmark on the client's actual fleet or you are quoting someone else's hardware.

One more shape: LLM-based rails cost an order of magnitude more than purpose-trained small models and are usually less accurate. NeMo's fact-checking rail, per checked fact: align_score-base 84.5% at 23.0 ms; gpt-3.5-turbo 82.5% at 435.1 ms. A frontier model as your validator is the expensive way to be slightly worse.

Latency · composition

Read the units, then read the execution model

Now the trap that embarrasses people in front of clients. Every LLM Guard benchmark table has a QPS column. It is not queries per second. From benchmarks/run.py: throughput = input_length * (1000.0 / latency_ms), where input_length is len(prompt) in characters. It reproduces exactly — PromptInjection on m5.xlarge, 384 chars / 0.21287 s = 1,804 against a published 1,803.91. The harness is timeit.repeat(..., number=1): sequential, single-threaded, no concurrency and no batching anywhere. Those tables support no request-throughput claim at all. The only rate they license is single-stream 1000 / avg_latency_ms — ~131 req/s for the fastest configuration in the corpus (7.65 ms). Anything above that needs a concurrency factor you measured yourself.

The second half is composition. LLM Guard's shipped API states: "Scanners will be executed in the order of configuration," with SCAN_FAIL_FAST defaulting to False. Serial, and it does not stop at the first failure. So a multi-scanner budget is a sum, not a max — the parallel number is an engineering project, not a config flag.

Finish this budget. Stack: Anonymize + PromptInjection + Toxicity, serial. On m5.xlarge with no ONNX the p99s are 325.71 + 316.97 + 188.11 = ~831 ms. Add ONNX on the same box: 179.93 + 107.01 + 35.71 = ~323 ms. Now do the last row yourself — g5.xlarge GPU + ONNX, p99s 99.26 + 14.75 + 10.65. Your answer is the "buyable" claim: what multiple did a hardware line item and one boolean just buy? State the caveat with it — summing p99s is an upper bound, not a p99, since the p99 of a sum only equals the sum of p99s if the scanners are perfectly correlated. Quote the sum as a ceiling and the sum of averages (~476 ms on CPU) as the central estimate, and say which one you are using.

False positives

Precision is a staffing number

This is the term nobody models and it is the largest one. Start with the ceiling: in Guardrails AI's index — 24 guardrails, 6 datasets, "32 days spent on GPU" — the best PII detector scores F1 0.65. Category bests elsewhere: Topic Restriction 0.93, Jailbreaking 0.81, Hallucination 0.77, Content Moderation 0.72. Nothing here is near-perfect; a memo implying otherwise is what gets the FDE fired two quarters later.

Now the failure mode that looks like success. NVIDIA's evaluation on ToxicChat (n=10,165, 7.2% harmful) scores gpt-3.5-turbo-instruct with self check input at accuracy 66.5%, precision 0.16, recall 0.85, F1 0.27 — against llama guard check input at 94.4% / 0.67 / 0.44 / 0.53. NVIDIA's read: "The low precision and high recall numbers… indicates an overly defensive behavior." A deck reporting "85% recall" is reporting the flattering half.

Convert it. False alarms per true catch is (1 − precision) / precision = 0.84 / 0.16 = 5.25 — precision alone fixes that ratio; the base rate never enters. At 200 front-desk chats/day: harmful = 200 × 0.072 = 14.4, true catches = 14.4 × 0.85 = 12.2. You finish it: false alarms, total blocked, and the share of all traffic wrongly blocked. Then run the consistency check in front of the room — back out TN and FN and recompute accuracy; if it lands on NVIDIA's published 66.5%, your arithmetic is safe to quote. That is the sentence the memo needs, in patients rather than percentages. And it is why the acceptance metric is Fβ=2, not F1 — Presidio's own recommendation, because "recall is often more important than precision, as we'd like to avoid missing any PII."

Coverage

Detection method predicts where the errors live

Presidio's recognizers are grouped by jurisdiction, and each one declares how it detects — which makes a coverage matrix mechanically derivable rather than a guess. Global: CREDIT_CARD, CRYPTO, DATE_TIME, EMAIL_ADDRESS, IBAN_CODE, IP_ADDRESS, MAC_ADDRESS, NRP, LOCATION, PERSON, PHONE_NUMBER, MEDICAL_LICENSE, URL. USA: US_BANK_NUMBER, US_DRIVER_LICENSE, US_ITIN, US_MBI, US_NPI, US_PASSPORT, US_SSN.

The useful column is not the entity name — it is the method, because method predicts the error class. Pattern + checksum (CREDIT_CARD, IBAN_CODE, US_NPI, UK_NHS) is high-precision and cheap. Pattern + context (US_SSN, US_DRIVER_LICENSE, IP_ADDRESS, DATE_TIME) is where false positives concentrate — Presidio's own example is that a driver's licence number "could be any 9-digit number." NER-driven (PERSON, LOCATION, NRP) is where recall fails. A real domain difference follows: a lending identifier set is mostly checksum-shaped and cheaper to redact than a clinical one. Presidio's tuning levers, in order: raise the acceptance threshold; delete recognizers your data cannot contain — free, and the one teams skip; rewrite the recognizer; replace it with a third-party service.

Three footnotes the matrix needs. Language — Anonymize states "current entity detection functionality is English-specific," and PhoneRecognizer needs explicit supported_regions; a multilingual population is a coverage gap, not a config detail. Structure — presidio-structured handles tabular data, the easy half; the note body and the model's generated summary are the hard half, and only NER sees identifiers there. And Presidio's own non-guarantee, which belongs in the memo verbatim: "there is no guarantee that Presidio will find all sensitive information. Consequently, additional systems and protections should be employed."

Dollars

The term everyone models is the smallest one

Managed meters give you a defensible price without a capacity model. Amazon Bedrock Guardrails bills per 1,000 text units, per filter, filters individually optional: content filters and denied topics $0.15/1k, sensitive-information filters $0.10/1k, contextual grounding $0.10/1k. Regex-based sensitive-information filters and word filters are free — which matters for a lending identifier set that is mostly regex-shaped. A text unit is ≤1,000 characters, rounded up. The standalone InvokeGuardrailChecks API is cheaper for the same checks ($0.07/1k content, $0.08/1k prompt attack) and is the cheap way to guardrail a model you host yourself. Azure Content Safety is a blended meter — $0.38 per 1,000 text records covering Text + Prompt Shields + Protected material + Groundedness, with a capped 5,000-record/month free tier. The two are not comparable at face value: Azure bundles four capabilities, Bedrock's $0.15 buys one, and a Bedrock unit is 1,000 characters against Azure's 1,000 Unicode code points.

Then the sentence that ends the budget argument, from AWS's own worked example: 10,000 clinical summaries at 3,500 characters each is 4 text units apiece, so 10000 × 4 × ($0.10/1000) = $4.00. That converts "can we afford de-identification?" from a budget question into a design question — the move that makes a board's "turn it on for everyone" answerable with "yes, behind this, at this price."

Which leaves self-hosting. Be honest about why: a g5.xlarge is an always-on fixed cost and the managed meter has a $0 floor at zero traffic, and without a measured concurrency figure you cannot state a crossover volume — deriving one from a chars-per-second column is exactly the error this day exists to teach. Make the case on residency instead: the data must not leave the boundary. That is a compliance argument and does not depend on the arithmetic at all.

Continuity · the memo

The fourth term: will this control still exist?

Three of the four projects in this landscape changed ownership, governance, or lifecycle status inside twelve months. LLM Guard was archived by Protect AI on 2026-07-09 and is read-only — last release 0.3.16 (2025-05-19), changelog still listing 0.3.17 as "Unreleased" — while its documentation site is still live, still renders, and still advertises the Slack community. A healthy-looking docs site over a dead project is the trap. Presidio left Microsoft: microsoft/presidio now resolves to data-privacy-stack/presidio, and the transition doc says the project "will not be owned or operated by a commercial entity." That one breaks deployments — legacy MCR images "remain available for older tags but are no longer updated," so anything pinned to mcr.microsoft.com/presidio-* is pinned to a frozen image. Guardrails AI pivoted to "The AI Reliability Platform" with a 404ing pricing page: the OSS library is alive and current, but everything past it is a sales conversation. Even NeMo moved repos, and carries a strategic caveat — Apache-2.0 and vendor-neutral, but its strongest configuration points at NVIDIA assets (NemoGuard Content Safety, the Jailbreak Detection NIM, the GLiNER-PII NIM). Cheap on the open path; an infrastructure decision on the recommended one.

So record four fields for every control you name: licence, last release date, governing entity, container-image origin. A control that stops receiving security updates does not fail loudly. It quietly stops being a control.

FDE mindset

Run the 60-minute protocol from Week 7 Day 3, but price the control in four terms: latency (p99, instance named), dollars (per 1k units, at a stated volume), false positives (in humans per day), and continuity (licence, last release, owner, image origin). Set that total against the cost of the incident it prevents. An exec cannot sign "we added guardrails." They can sign "$4 per ten thousand summaries, 99 ms at the tail, roughly N people a day wrongly blocked, on an MIT library that moved owners in July."

Deep dive: the three-term cost model, filled in twice

Optional. ~10 minutes. The frame, then the same frame against both brownfield systems.

cost_of_control =  latency_cost         p99 ms × turns × what a slow turn costs
                +  dollar_cost          per-1k-unit meter, or instance-hours if self-hosted
                +  false_positive_cost  FP rate × turns × cost per wrongly-blocked interaction
                (+ continuity_risk      non-monetary, but it is the term that kills you)

Riverbend (healthcare). Term 2: $4.00 to redact 10,000 clinical summaries at Bedrock's $0.10/1k. Term 1: Anonymize alone is 177 ms avg / 326 ms p99 on m5.xlarge, 38 / 99 on GPU+ONNX — quote both and label them, because an exec told "177 ms" who then experiences 326 ms at the tail stops trusting the memo. Add injection and toxicity scanning and the stack is serial by default: ~831 ms p99 on CPU, ~125 ms on GPU+ONNX. Term 3 is the one that decides the design: detect mode refuses to answer, mask mode answers with holes, and stream_first: True shows the clinician tokens no rail has cleared. Term 4: Presidio moved to data-privacy-stack and the MCR images are frozen — that single line turns "we'll use Microsoft's library" into a real vendor-governance finding.

Meridian (finance). Term 2 is smaller per identifier because lending identifiers are regex-shaped — US_SSN, US_ITIN, US_BANK_NUMBER, CREDIT_CARD with checksum — and Bedrock's regex sensitive-information filters are free. Term 1 barely matters on a batch scoring path. Term 3 is where the harm is: if a validator gates adverse-action reasons and it behaves like NeMo's self-check rail (precision 0.16), you have manufactured wrongly-denied applicants — the exact ECOA harm the governance package exists to prevent. State the FP budget in applicants per month, not percent.

Completion — the intervention that fits a live scorer

Meridian's scorer is in production and you have one week. You are not rewriting the decision path. Guardrails AI's guard.parse(llm_output=…, num_reasks=0) validates output you already generated and, at zero re-asks, stays "purely as a post-processor" — bolt-on, no extra LLM round trip. Above zero re-asks, each failure costs another call. Your move: decide whether Meridian's adverse-action validator runs at num_reasks=0 or higher, and write the one sentence of justification the memo needs — it has to name what a re-ask buys and what it costs, in both latency and regulatory defensibility.

One pattern worth stealing: LLM Guard's Anonymize + Vault + Deanonymize round trip — redacted values go into a vault on the way out (use_faker substitutes fabricated data), and the paired output scanner restores them on the way back. That is the mechanism for "the vendor never sees the identifier, but the clinician still does." The project is archived; the pattern is not.

Production code: the scrub is an input rail, not an output filter

The rail runs before the request crosses the vendor boundary — and the recognizer list is trimmed to entities this system can actually contain, which is Presidio's free false-positive lever.

# Input rail: de-identify BEFORE the request crosses the vendor boundary.
# Auth: Bedrock API key in AWS_BEARER_TOKEN_BEDROCK (boto3 reads it; no IAM role).
import boto3
from presidio_analyzer import AnalyzerEngine
from presidio_anonymizer import AnonymizerEngine

# Trim to what Riverbend records can actually hold. Removing recognizers is
# Presidio's documented false-positive lever #2 -- it is free, and teams skip it.
ENTITIES = ["PERSON", "US_SSN", "US_MBI", "US_NPI", "PHONE_NUMBER",
            "EMAIL_ADDRESS", "DATE_TIME", "LOCATION"]

analyzer, anonymizer = AnalyzerEngine(), AnonymizerEngine()
bedrock = boto3.client("bedrock-runtime", region_name="us-east-1")

def scrub(text: str, threshold: float = 0.4) -> str:
    hits = [r for r in analyzer.analyze(text=text, entities=ENTITIES, language="en")
            if r.score >= threshold]          # lever #1: the acceptance threshold
    return anonymizer.anonymize(text=text, analyzer_results=hits).text

def summarize(note: str) -> str:
    clean = scrub(note)                       # ~177 ms avg / 326 ms p99 on m5.xlarge
    resp = bedrock.converse(
        modelId="us.anthropic.claude-haiku-4-5-20251001-v1:0",
        system=[{"text": "Summarize this visit for the patient. Never invent identifiers."}],
        messages=[{"role": "user", "content": [{"text": clean}]}],
        inferenceConfig={"maxTokens": 400, "temperature": 0},
    )
    return resp["output"]["message"]["content"][0]["text"]

Two lines carry the whole day: scrub() runs before converse(), and it is mask semantics — the caller still gets an answer, with holes. Swap to detect (refuse on any hit) and you have changed the product, not the config.
