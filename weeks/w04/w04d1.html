Multi-Agent Orchestration Patterns

Week 4 · Day 1 Multi-Agent Systems ~18 min · reading @150 wpm + diagram + check

Last week you built a single production agent. This week the question changes: when is one agent not enough — and when you split the work, who decides who works next? Today you learn the two canonical answers — the supervisor (a central coordinator that routes everything) and the swarm (peers that hand control directly to each other) — plus the mechanism underneath both: the handoff, which turns out to be nothing more exotic than a tool call. Scroll the reading; the panel on the right builds both architectures side by side, then shows why naive multi-agent systems fail and the one rule that makes them work.

The threshold

One agent is the default — multi-agent has to earn it

Start with the least glamorous fact in this whole topic, straight from the people who sell multi-agent frameworks. LangChain's own multi-agent documentation opens with a warning: "Not every complex task requires this approach — a single agent with the right (sometimes dynamic) tools and prompt can often achieve similar results." That's the vendor telling you not to buy the second agent. Take the hint. The single agent you built last week — one loop, curated tools, a tight system prompt — remains the default architecture, and everything today is about knowing exactly when it stops being enough.

So when does it stop? The same docs name three legitimate drivers. Context management: a support agent that handles research, billing, and refunds needs three domains of instructions, schemas, and tools crammed into one window — you learned in Week 1 what happens to a window treated like a junk drawer. Splitting into specialists gives each its own focused context. Distributed development: separate teams can own separate agents with clear boundaries, the same reason you split a monolith into services. Parallelization: some tasks genuinely decompose into independent pieces that can run at the same time.

And there's an equally important anti-signal. Anthropic, who run one of the most successful multi-agent systems in production, are blunt that the approach falls short for domains that require all agents to share the same context, or that involve many dependencies between agents — which is why, in their words, most coding tasks don't have enough truly parallelizable components to benefit. Tightly coupled work wants one agent with one window. Hold that line: agent count is a cost you pay, not a feature you ship. If a client's first instinct is "let's have twelve agents," your first instinct is to ask which of the three drivers is actually present.

Pattern 1

Supervisor: one hub, all decisions

Once you've decided to split, the first architecture to reach for is the supervisor. One central agent — the supervisor — owns the conversation with the user and coordinates a set of specialized workers. Every routing decision flows through the hub: the supervisor reads the current state and, in the words of the LangGraph reference, "makes decisions about which agent to invoke based on the current context and task requirements." A worker does its slice, hands its result back up, and the supervisor decides what happens next — another worker, a follow-up, or a final answer to the user.

This is such a common shape that LangGraph ships it prebuilt: the langgraph-supervisor package gives you create_supervisor() to wire the hub, create_handoff_tool() for delegation, and plumbing helpers like create_forward_message_tool() and create_handoff_back_messages() for moving messages between hub and workers. LangChain 1.0's docs describe the same shape under the name subagents — "a main agent coordinates specialized agents as tools, with all routing flowing through the primary coordinator." Notice that phrasing: workers as tools. To the supervisor, delegating to the billing agent looks exactly like calling any other tool. That's a preview of today's biggest punchline.

The supervisor's virtues are control and observability. There is exactly one place where routing happens, so there's one prompt to debug, one trace to read, one throat to choke. The cost is that the hub becomes a bottleneck — every worker result round-trips through the supervisor, burning latency and tokens — and the supervisor's own context fills with routing traffic. It's the org chart with a manager: clear accountability, extra meetings.

Pattern 2

Swarm: peers hand off directly, no manager

The second architecture deletes the manager. A swarm is — verbatim from the langgraph-swarm project — "a type of multi-agent architecture where agents dynamically hand off control to one another based on their specializations." No central coordinator. A triage agent talking to a traveler realizes this is a flight question and transfers control directly to the flights agent; if hotel questions come up mid-conversation, the flights agent transfers to the hotels agent. Whoever holds the conversation, holds it fully — until they hand it off.

The detail that makes swarms feel natural in chat products is the sticky active agent: "the system remembers which agent was last active, ensuring that on subsequent interactions, the conversation resumes with that agent." If the hotels agent was helping you when you went to lunch, the hotels agent picks up when you come back — no re-triage, no "please hold while I transfer you" on every turn. In code it's compact: create_swarm(agents, default_active_agent="Alice") assembles the team, and each agent gets handoff tools like create_handoff_tool(agent_name="Bob", description="Transfer to Bob") naming the peers it may transfer to.

The trade against the supervisor is exactly what you'd guess. Swarms cut out the hub round-trip — transfers are one hop, so latency and token overhead drop, and the conversation flows like being walked between desks rather than filtered through a receptionist. But routing logic is now smeared across every agent's prompt instead of concentrated in one place, so answering "why did the wrong agent take this?" means auditing N prompts instead of one. Supervisor when you want central control and auditable routing; swarm when the conversation should follow specialization fluidly and you can tolerate distributed routing logic.

The mechanism

A handoff is just a tool call

Both patterns run on the same primitive, and the OpenAI Agents SDK — the canonical implementation — defines it with no mystery at all: "handoffs allow an agent to delegate tasks to another agent," and they are "represented as tools to the LLM." Read that twice. There is no telepathy between agents, no shared consciousness. When the triage agent decides a refund specialist should take over, what actually happens is that the model emits a tool call — named, by default, transfer_to_<agent_name>, so handing off to the refund agent is literally a call to transfer_to_refund_agent. Everything you learned in Week 3 about tool calling — schemas, the loop, failure handling — applies unchanged. Multi-agent is tool calling with agents on the other end.

Because it's a tool, you can customize it like one. The SDK's handoff() function takes the target agent plus tool_name_override and tool_description_override (what the routing model sees), on_handoff (a callback to fire when the transfer happens — log it, prefetch data), input_type (a schema for structured handoff arguments, so the escalation agent receives a typed reason, not vibes), and is_enabled to switch routes on and off. The consequential one is input_filter: it controls what conversation history the receiving agent sees. By default the new agent sees the entire prior conversation; a filter can prune it — the SDK ships prebuilt filters in agents.extensions.handoff_filters, like one that strips old tool calls. That single parameter is context engineering applied to agent boundaries, and it foreshadows today's failure section: what the next agent can't see, it can't respect.

Two more production details. Agents route better when they're told handoffs exist — the SDK ships RECOMMENDED_PROMPT_PREFIX and prompt_with_handoff_instructions() in agents.extensions.handoff_prompt precisely so you don't hand-roll that boilerplate. And there's an opt-in beta, nest_handoff_history on RunConfig, that collapses the prior transcript into a summary block on transfer instead of forwarding it raw — the framework authors converging on the same window discipline you learned in Week 1.

The axis

Who routes: the LLM or your code?

Underneath supervisor-vs-swarm sits a deeper axis that the OpenAI SDK docs name explicitly: who makes the routing decision? Everything so far has been LLM-driven orchestration — a model reads the situation and chooses, via handoff tools, which agent acts next. The docs' verdict: that "is great when the task is open-ended." When you can't enumerate the paths a conversation might take, an intelligent router earns its tokens.

But there's a second option that beginners skip because it doesn't feel AI enough: code-driven orchestration. Have a model classify the request into a structured output, then let ordinary Python route on it. Chain agent A's output into agent B as plain function composition. Fan out independent subtasks with asyncio.gather. The SDK docs are unambiguous about the payoff: orchestrating via code "makes tasks more deterministic and predictable, in terms of speed, cost and performance." No routing model to prompt, no routing model to pay, no routing model to misroute. If every refund request should go to the refund pipeline, an if statement is a better router than an LLM — cheaper, faster, and it has never once hallucinated.

The FDE reflex: use exactly as much LLM in the control flow as the task's open-endedness demands, and not one call more. Known, enumerable paths → route in code. Genuinely open-ended conversation → let the model route via handoffs. Most real systems are hybrids — code-orchestrated pipelines whose individual stages are agents, with LLM routing reserved for the one junction where intent is truly ambiguous. When a client shows you an "agentic workflow" where an LLM decides something a lookup table could decide, you've found latency, cost, and a failure mode to delete in your first week.

At scale

Orchestrator-worker: parallelism with a price tag

Now the pattern working hardest in production, with real numbers attached. Anthropic's research feature is an orchestrator-worker system: "a lead agent coordinates the process while delegating to specialized subagents that operate in parallel." It's the supervisor shape tuned for the third driver — parallelization — with one crucial property: each subagent gets its own context window. The lead agent plans; workers explore different facets of a question simultaneously, each burning its own window instead of crowding into one; results compress back to the lead. Separation of concerns, and no single window has to hold the whole investigation.

Does it work? On Anthropic's internal research eval, the multi-agent system — an Opus 4 lead with Sonnet 4 subagents — beat single-agent Opus 4 by 90.2%, and parallel tool calling cut research time by up to 90% for complex queries. But read the fine print like an engineer, because it's a token story: they found token usage explains about 80% of the variance in performance. Multi-agent wins substantially because it spends more — an agent uses roughly 4× the tokens of a chat, and a multi-agent system around 15×. The architecture is a machine for converting money into coverage. Anthropic's own conclusion: the economics only make sense for high-value tasks where the answer is worth the burn. "15× tokens for 90% better research" is a great trade on due diligence and a terrible one on password resets.

Their orchestration-prompt lessons generalize to any supervisor you'll build. Early lead agents gave workers vague briefs, and workers duplicated each other's effort or wandered — so the fix was explicit delegation: every subagent brief states an objective, an output format, the tools to use, and task boundaries. And the lead is taught scaling rules so effort matches complexity: a simple query gets one agent; a complex investigation fans out to ten-plus subagents with divided responsibilities. Delegation quality, not agent count, is what separates a research team from an expensive mob.

The counter-argument

Why naive multi-agent systems fail

Time for the cold water, because a client will quote it at you. In June 2025, Cognition — the Devin team — published a post titled, bluntly, "Don't Build Multi-Agents." Their argument rests on two principles. One: "Share context, and share full agent traces, not just individual messages." An agent that sees only a summary of what happened is reasoning about a redacted case file. Two: "Actions carry implicit decisions, and conflicting decisions carry bad results." Their running example: parallel subagents building a Flappy Bird clone, where one picked a visual style for the background and another, unable to see that choice, drew a bird that matched nothing. Neither agent was wrong; the system was, because every action smuggles in decisions the other agents never learn about. Note what both principles actually are: context-window arguments. Week 1 again, wearing an org chart.

The empirical record backs the skepticism. The Berkeley MAST study — Why Do Multi-Agent LLM Systems Fail? — analyzed 150+ expert-annotated execution traces across seven frameworks (annotator agreement κ = 0.88; the dataset has since grown past 1,600 traces) and found that multi-agent gains over strong single agents are often minimal, while the failures are systematic enough to taxonomize: 14 recurring failure modes in 3 categories — system design issues, inter-agent misalignment, and task verification failures. Read that list against today's mechanics and it stops being surprising. Fragmented context and conflicting implicit decisions are inter-agent misalignment; a supervisor accepting a worker's confident garbage is a verification failure; wrong topology for a coupled task is a design issue. The failure taxonomy is the mirror image of the patterns — which means architecture choices, not model quality, are usually what's broken when a client's agent team embarrasses itself.

The resolution

2026's rule: single-threaded writes, extra intelligence

So who's right — Anthropic's 90.2% or Cognition's "don't"? As of this spring, they've converged. In April 2026 Cognition published a follow-up, "Multi-Agents: What's Actually Working," naming three patterns that survived contact with production. The code-review loop: a second agent with fresh context reviews the first agent's diff, catching around two bugs per PR precisely because it doesn't share the author's context and assumptions. The smart-friend pattern: a stronger model consulted for a hard sub-decision, returning advice, not code. And manager-child delegation: a lead handing scoped work down — Anthropic's orchestrator-worker by another name.

One throughline unites all three, and it's the sentence to carry out of today: "multi-agent systems work best today when writes stay single-threaded and the additional agents contribute intelligence rather than actions." Look at what the extra agents do in every working pattern — review, advise, research. They add reads and judgment. Exactly one thread holds the pen. The moment two agents both take actions on shared state — both writing code, both mutating the same ticket — you're back in Flappy Bird territory, with implicit decisions colliding where no one can see them. Notice this also explains the research system: subagents read the web in parallel, but one lead agent writes the report.

That gives you the whole decision procedure on one napkin. First: does a single agent with better tools and a tighter prompt solve it? Ship that. If not, which driver — context, ownership, parallelism — justifies the split? Then: enumerable routing → code; open-ended → LLM handoffs. Central control → supervisor; fluid specialization → swarm; parallel research → orchestrator-worker. And across all of it, one invariant: writes stay single-threaded, and every extra agent must justify its tokens by adding intelligence the main thread lacks.

Your tools · AI coding

You already operate a supervisor

Here's the part that makes this concrete before lunch: Claude Code's subagents are a supervisor architecture, and you've been the beneficiary all program. When it fans a big search across parallel subagents, that's orchestrator-worker — each explorer burns its own context window and reports a compressed summary back, so the lead's window stays clean. When you ask for a review of code the main thread just wrote, you're running Cognition's code-review loop: the value comes precisely from the reviewer's fresh context. And notice what the subagents return — findings, never direct edits to your files. Writes stay single-threaded in the main thread. The 2026 rule is implemented in the tool on your laptop.

So today's deliverable practice is free: next time you use it, narrate the architecture. Who routed — model or harness code? What did the delegation brief contain? What came back, intelligence or actions? An FDE who can read the orchestration pattern out of a tool they use daily can read it out of a client's system in the first hour on site.

FDE mindset

When a client says "we want a multi-agent system," they're proposing an org chart for software. Your job is the same as any good consultant staring at an org chart: ask what the communication cost is, who owns each decision, and whether the work actually decomposes. Agent count is a cost you pay, not a feature you ship — and the winning architectures are the ones where exactly one thread holds the pen. Deep dive: the handoff() API surface & version reality-check

Optional. ~10 minutes. The parameters you'll actually touch, and how fresh this ecosystem is.

The full handoff() customization surface (OpenAI Agents SDK). Every one of these is a lever on a tool call, because that's all a handoff is:

handoff(...) parameters — what each one is for
  • agent — the target agent to transfer to
  • tool_name_override / tool_description_override — rename what the routing model sees (default name: transfer_to_<agent_name>)
  • on_handoff — callback fired at transfer time (audit-log it, prefetch data)
  • input_type — a schema for structured handoff arguments (typed escalation reason, not vibes)
  • input_filter — controls what conversation history the receiving agent sees; prebuilt filters live in agents.extensions.handoff_filters (e.g. strip old tool calls)
  • is_enabled — turn a route on/off without rewiring the graph
  • nest_handoff_history — with RunConfig, the opt-in beta that collapses prior transcript into a summary block on transfer

The one to remember under pressure is input_filter: it is the context-window lever at the agent boundary. Cognition's principle — share full traces, not fragments — is a policy you implement (or violate) with exactly this parameter. And don't hand-roll routing prompts: use prompt_with_handoff_instructions() / RECOMMENDED_PROMPT_PREFIX from agents.extensions.handoff_prompt.

How young is this stack? Check the version numbers. As of mid-2026: langgraph-supervisor is at 0.0.31 (2025-11-19) and langgraph-swarm at 0.1.0 (2025-12-04) — pre-1.0 packages wrapping patterns the industry settled on within the last eighteen months. LangChain 1.0's docs now frame multi-agent as five patterns — subagents, handoffs, skills, router, custom workflow — with "supervisor" and "swarm" living on as the prebuilt libraries. The vocabulary is still moving. For a client, that means two things: pin your versions, and sell them the pattern (hub vs peer handoffs vs orchestrator-worker), not the package name — the pattern will outlive this quarter's API.

The MAST taxonomy, one level deeper. The Berkeley team's 14 failure modes group into three categories worth memorizing as a diagnostic checklist: system design issues (wrong topology or roles for the task), inter-agent misalignment (agents working from fragmented context or undoing each other's implicit decisions), and task verification (nobody competent checks the work before it ships). When a client's agent team misbehaves, walk the categories in that order — it's the multi-agent version of Week 1's "walk the window."
