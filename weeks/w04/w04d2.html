Durable Agents: State, Checkpointers & the Art of Not Losing Your Place

Week 4 · Day 2 Foundation AI Engineering Core 30 · ~10 min read · 3 interactions · 6-Q check

Yesterday you built your first LangGraph. Today you make it survivable. A real agent run at a client crosses process restarts, waits hours for a human approval, and occasionally crashes halfway through a five-step workflow — and the difference between a demo and a production system is whether the run can pick up where it left off. That's what LangGraph's persistence layer buys you: a checkpointer snapshots graph state at every step, a thread gives the run a durable identity, and interrupt/resume turns "pause for a human" from a hack into a first-class control-flow primitive. Scroll the reading; the panel on the right follows one refund-approval agent from state schema to crash, resume, and time-travel fork.

Foundation

A StateGraph is a schema plus functions

Strip LangGraph down to its skeleton and there are only two ideas. First, a state schema: you declare the shape of your agent's working memory — as a typed dictionary, a Pydantic model, or a dataclass — say a message list plus an order id plus an approval flag, for a refund agent. That schema becomes the input to every node and edge in the graph. Second, nodes are plain functions. Each one receives the current state and returns a partial update — just the keys it changed, not the whole object. The docs put it bluntly: nodes and edges "are nothing more than functions — they can contain an LLM or just good ol' code."

That second point deserves a beat, because it's where beginners overcomplicate. A node that calls a model and a node that runs a SQL query are the same species: state in, partial update out. There is no magic "agent object" holding things together — the state object flowing through the graph is the agent's memory, and everything the run knows lives in it. If a fact isn't written into state, it doesn't survive to the next node. Sound familiar? It's Week 1's context-window discipline wearing a graph costume: you decide, explicitly, what the system carries forward.

Why does this matter for durability, today's actual topic? Because you can only persist what you can serialize. A pile of closures and hidden instance variables can't be snapshotted; a declared, typed state object can. LangGraph's entire persistence story — checkpoints, resume-after-crash, human-in-the-loop, time travel — rests on the fact that at any moment, the whole run is representable as one state value plus a position in the graph. Design the schema first, and everything else today falls out of it.

Merging updates

Reducers decide how updates land

If every node returns a partial update, something has to decide how those updates merge into state. That something is a reducer, and every key in your schema has its own. The default is brutal and simple: overwrite. Node returns {messages: [x]}, and whatever was in messages is gone, replaced by a one-element list. This is the classic first-day LangGraph bug — "my conversation keeps resetting to the last message" — and it's not a framework glitch, it's the default reducer doing exactly what it says.

The fix is to attach a custom reducer to the key using an annotated type hint — pairing the list with an add operation makes updates append instead of replace. For chat history specifically, the prebuilt add_messages reducer goes further: it merges by message id, so re-sending a message with the same id updates it in place rather than duplicating it, and it handles deserialization for you. One schema, per-key merge policies — overwrite for a status flag, append for a log, id-merge for messages.

Around the state flow sits control flow. Normal edges route unconditionally from node to node; conditional edges call a routing function that returns the name of the next node; and two virtual nodes mark the entry and the exit of the graph. Two power tools you'll meet again this week: a command object lets a node bundle a state update with a routing decision, and a send object fans work out dynamically to multiple targets, each with its own state.

And one hard rule from the documentation: "You MUST compile your graph before you can use it." Compiling validates the structure — and, crucially for today, it is where you plug in the checkpointer.

Required practice · Why did the resume double-append? · static path

After an approval resume, the thread shows the refund note twice. Probe the durable-agent machinery, then name the design flaw.

Symptom: The resumed run appended the same message twice; the checkpoint history looks healthy.

  • State reducer: messages: append reducer (add_messages) — not idempotent for repeated inserts without stable IDs
  • Node source: the node appends the note and calls an external logger BEFORE interrupt()
  • Checkpoint log: checkpoint saved at interrupt · resume re-entered the node at its top, as documented

Failing boundary: Side effects before interrupt in a re-run node. resume re-runs the node from the top, so work placed before interrupt() executes twice; make pre-interrupt work idempotent or move it after the approval

Persistence

Checkpoints: a save file for every step

Here's the move that turns a graph into a durable system. Compile with a checkpointer, and LangGraph saves a checkpoint — a snapshot of graph state — as the run proceeds, step by step. Those checkpoints are grouped under a thread: you pass a thread_id in the config when you invoke the graph, and every checkpoint from that run files under it. The docs call this "short-term, thread-scoped memory," and the framing is exact: a thread is one conversation, one task, one workflow instance — and its checkpoints are that instance's complete save history.

Think of it as the save system in a video game. The thread_id is the save slot; each checkpoint is an autosave at the end of a step. Process dies at step three of five? Re-invoke with the same thread_id and the run continues from the last checkpoint instead of starting over. Same mechanism, one id per customer, and yesterday's stateless chatbot becomes a continuous conversation across requests, restarts, and deploys. This single feature is what unlocks everything else today: conversation continuity, human-in-the-loop pauses, time travel, and fault tolerance are all downstream of "the state is snapshotted somewhere durable."

One distinction to file now, because clients confuse it constantly: checkpointing is not long-term memory. A checkpointer remembers this thread. For knowledge that must span threads — user preferences, facts learned across many conversations — LangGraph has a separate concept, the Store, holding application-defined key-value data across threads. Checkpointer = the run's save file; Store = the agent's notebook. Today is entirely about the save file.

Interactive practice: JavaScript is required to step through the synthetic crash and resume state machine.

Required practice · Pause, approve, resume — in order · static path

Arrange the approval-gate flow so the checkpoint machinery works for you.

  1. The node runs until interrupt() raises the approval payload — pausing is just a checkpoint: the save file is written here
  2. A human approves or rejects outside the graph — the graph is parked state while the decision happens elsewhere
  3. Command(resume=…) re-enters the node from the top — re-execution from the top is the documented contract — design the node for it
  4. The reducer lands the resulting update — reducers decide how updates land; they are the write discipline
  5. Replay or fork the thread from its checkpoint history — history is a data structure: time travel is a read, not a stunt

The checkpoint is saved at the interrupt; the approval happens outside the graph; resume re-enters the node from the top; the reducer lands the update; replay and fork read the history afterwards.

Backends

Where checkpoints actually live

A checkpointer is an interface, not a database. The contract is small — five operations, plus an async variant of each: store a checkpoint, store pending writes, fetch one checkpoint, list a thread's history, and delete a thread. Anything that implements those methods can be your persistence layer, which is why the backends ship as separate packages you choose per deployment.

Three tiers ship, and the tier names are the deployment advice:

  • In-memory saver — keeps checkpoints in process memory. Perfect for development and tests, and gone the moment the process restarts, which means it silently defeats the entire point in production.
  • SQLite saver, sync and async — persists to a local file. Fine for demos and single-machine experiments, explicitly not production.
  • Postgres saver, sync and async — the production tier: durable, and shared across application instances.

Under the hood, checkpoints are serialized with a msgpack-based serializer that falls back to JSON, and if your state carries anything sensitive you can wrap it in an encrypting serializer for encryption at rest. Remember what a checkpoint actually is: a full copy of agent state, personal data and all, sitting in a database.

The FDE reflex here is a one-line code review: find the checkpointer, check the tier. "Our agent forgets everything when we redeploy" is almost never a LangGraph bug — it's an InMemorySaver that followed the tutorial into production. The fix is a two-line swap to Postgres, and you'll look like a wizard for spotting it.

Shared-state boundary

Make handoffs and conflicts explicit

A subgraph or external agent receives a typed envelope: task and trace IDs, a versioned state reference, sanitized evidence references, requested output schema, deadline, and escalation target. Messages propose updates; they do not silently replace shared state. One coordinator validates the envelope and owns the committed transition.

Declare a merge policy per field: append immutable observations, reject stale version numbers, and route incompatible proposals to a human owner. Parallel branches may read the same checkpoint but must not both commit the same decision. Across frameworks, interoperate at the envelope and trace boundary rather than sharing framework-specific memory objects.

Optional depth: durability modes, HITL edge cases & time travel
Tuning

Durability modes: when the write happens

Having a checkpointer settles where snapshots go; durability mode settles when they're written relative to execution — and it's a genuine engineering trade-off, tunable per call: graph.stream(input, config, durability="sync"). Three settings.

Sync — changes are persisted before the next step starts. Most durable, slowest: every step waits for the database write to land, so a crash can never lose a completed step. Async — changes are persisted while the next step executes. The write and the work overlap, so you get most of the durability at much less latency cost, with a small crash window where a step finished but its checkpoint hadn't landed. Exit — changes are persisted only when the graph exits. Fastest, and if the process dies mid-run there is nothing to resume from; you have opted out of mid-run crash recovery entirely.

Notice the shape of this decision — you have made it before. It is the same durability-versus-throughput dial as database write concerns or fsync policy, applied to agent state. And the right answer is workload-shaped, which is why it is set per invocation: a money-touching approval workflow wants the synchronous setting, a chat assistant is happy with the asynchronous one, and a bulk overnight batch job that can simply be re-run from the top might take the fastest option and accept the risk. When a client asks "why is the agent slow?" and "what happens if it crashes?", know that those two questions share one knob — and be able to say which setting they are on, and why.

Human-in-the-loop

interrupt(): pausing is just a checkpoint

Now the payoff feature — the one clients ask for by name. "The agent can draft the refund, but a human must approve it before it executes." In a stateless world that's an architectural headache: you'd have to tear the workflow in half, stash intermediate results somewhere, and rebuild everything when the human answers. With checkpointing, it's one function call. Inside a node, call interrupt(payload): the graph stops, the current state is saved through the checkpointer, and your payload — "Approve this $840 refund?" — is surfaced to the caller. Under the hood, interrupt() works by raising a special exception that the LangGraph runtime catches; it's control flow, not an error.

This is why the docs are blunt that a checkpointer is mandatory for interrupts — "state is saved using the checkpointer so execution can be resumed later." A pause with nowhere to save is just a crash with good manners. The paused thread now sits in the database, costing nothing, for seconds or for a week — however long the human takes.

Resuming is the mirror image: re-invoke the graph with a resume command on the same thread id, and the value you pass becomes the return value of the interrupt() call inside the node — the human's "approved" flows into the code exactly where the question was asked. The thread id is, in the documentation's phrase, your persistent cursor: same id, same paused run; new id, fresh thread with empty state, and a support ticket asking why the agent "forgot" the approval. One contract note — the resume form is the only command pattern meant to be passed as input when you invoke or stream a graph; the rest live inside nodes.

Sharp edges

Resume re-runs the node from the top

Here is the sharpest edge in today's material, and it is exactly the kind of thing that separates "read the quickstart" from "ready for a client." When a thread resumes, the runtime restarts the entire node from the beginning — it does not continue from the exact line where the interrupt was called. Everything in the node before the interrupt runs again. Picture a node that charges a card and then asks for approval: on resume, the card gets charged a second time. That is not a hypothetical; it is the canonical double-side-effect bug.

The documentation draws three rules straight from those semantics. One: code before an interrupt must be idempotent — safe to run twice — or moved into its own node before the interrupting one, so the checkpoint boundary protects it. Two: never wrap an interrupt in a bare try/except, because it is implemented as an exception and a catch-all will swallow the pause signal and break the mechanism silently. Three: if one node contains several interrupts, resume values are matched to them strictly by index — the first answer goes to the first interrupt, and so on — so their order must stay consistent across executions. Conditionally skipping one shifts every answer onto the wrong question.

With the semantics respected, a small set of HITL patterns covers most client asks: approval workflows (pause before the sensitive action, route on approve/reject), state review & editing (show the human the draft, let them correct it), tool-call review (inspect and fix an agent's proposed tool call before it executes — Week 3's consent gate, now durable), and input validation. For that last one the docs give structural advice worth quoting into your notes: build validation loops with conditional edges between nodes, not with a while loop wrapped around an interrupt inside one node.

Time travel

Replay and fork: the history is a data structure

Because every step is checkpointed, a finished (or failed) run isn't a log line — it's a navigable history. get_state_history(config) returns the thread's checkpoints, newest first, and each one carries a checkpoint_id in its config. Invoke the graph with a prior checkpoint's config and you replay from that point: nodes before the checkpoint aren't re-run — their results come straight from the snapshot — while nodes after it execute again for real. And the docs flag the trap in that sentence: "replay re-executes nodes — it doesn't just read from cache." LLM calls, API requests, and interrupts genuinely fire again and may return different results. Replaying is rewinding a live system, not scrubbing a recording.

The second tool is the fork. Updating state does not edit history in place — it creates a new checkpoint that branches from the point you specify, leaving the original history intact. Invoking the graph again from that configuration continues execution from the fork with your modified state. An optional parameter attributes your edit to a specific node's writes, so the graph resumes from that node's successors, which also makes it a scalpel for skipping a node or disambiguating parallel branches. The debugging workflow, made concrete: a customer reports the agent approved the wrong refund, so you pull the thread's history, find the checkpoint where retrieval returned the wrong order, fork there with corrected state, and re-run the tail to confirm the fix — all without touching the customer's real thread.

Three production footnotes from the docs before you leave: checkpoints accumulate over long threads (latency and storage — prune), keep thread_id under 255 characters (a Postgres column limit), and subgraphs checkpoint under their own namespace, so a parent graph doesn't immediately see child state updates. Small print now; incident reports later.

FDE mindset

Clients don't buy "an agent" — they buy a workflow they can trust with money, and trust means survivability: survives a crash, waits for a human, and can be rewound when something goes wrong. All three are the same primitive — state, snapshotted at every step under a durable id. When you evaluate any agent framework or any client's homegrown orchestrator, ask the checkpoint questions first: where does state live, when is it written, and can I resume a thread? Deep dive: the checkpointer contract, serialization & production limits

Optional. ~10 minutes. What's under the compile(checkpointer=...) line.

The contract is tiny. The checkpointer interface asks for five operations — store a checkpoint, store pending writes, fetch one, enumerate a thread's checkpoints, and delete a thread — plus an async variant of each. That is the whole persistence interface. In-memory, SQLite and Postgres are just different homes for the same five verbs, which is also why the backends ship as separate packages you swap without touching graph code.

Serialization is a security surface. Checkpoints are serialized with JsonPlusSerializer — ormsgpack with a JSON fallback. A checkpoint is a complete copy of agent state: messages, retrieved documents, customer data. If that includes PII, the checkpoint table is now a PII store, with all the compliance consequences. EncryptedSerializer wraps the serializer for encryption at rest — cheap to add on day one, painful to retrofit after the audit.

Worked choice — durability mode per workload
  • Refund-approval agent (moves money): durability="sync" — every completed step is on disk before the next starts; a crash can never replay or lose a committed step.
  • Support chat assistant: "async" — write overlaps the next step; worst case a small crash window re-runs one step of conversation.
  • Overnight bulk classifier, safely re-runnable from the top: "exit" — no mid-run recovery, maximum throughput, and that's an acceptable trade because a re-run is free.

The knob is per-invocation (graph.stream(input, config, durability=...)), so one deployed graph can serve all three postures.

Production small print (all from the persistence docs): checkpoints accumulate per thread — long conversations mean growing storage and slower loads, so prune; keep thread_id under 255 characters (Postgres column limit); and subgraphs checkpoint under their own namespace, so a parent graph does not immediately observe a child's state updates — remember that before you "fix" a parent that looks stale.

Resume from the last durable checkpoint

Read-only worked example. A local fixture records completed nodes and derives exactly which work a resumed thread skips or replays.

# Synthetic checkpoint fixture: no LangGraph runtime, storage, or network.
NODES = ["validate_request", "load_order", "calculate_refund",
         "write_ledger", "notify_customer"]
CHECKPOINT = {
    "thread_id": "demo-refund-204",
    "next_index": 2,
    "completed": NODES[:2],
}
CRASHED_NODE = "calculate_refund"  # output existed, checkpoint did not


def resume_plan(checkpoint, crashed_node):
    skipped = list(checkpoint["completed"])
    replayed = [crashed_node]
    remaining = NODES[checkpoint["next_index"] + 1:]
    return {"skipped": skipped, "replayed": replayed, "remaining": remaining}


plan = resume_plan(CHECKPOINT, CRASHED_NODE)
assert plan["skipped"] == ["validate_request", "load_order"]
assert plan["replayed"] == ["calculate_refund"]

Static example, separate from the interactive simulator above. It explains the checkpoint boundary but cannot run a graph or persist state.
