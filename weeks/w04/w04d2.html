Durable Agents: State, Checkpointers & the Art of Not Losing Your Place

Week 4 · Day 2 Foundation AI Engineering ~18 min · reading @150 wpm + diagram + check

Yesterday you built your first LangGraph. Today you make it survivable. A real agent run at a client crosses process restarts, waits hours for a human approval, and occasionally crashes halfway through a five-step workflow — and the difference between a demo and a production system is whether the run can pick up where it left off. That's what LangGraph's persistence layer buys you: a checkpointer snapshots graph state at every step, a thread gives the run a durable identity, and interrupt/resume turns "pause for a human" from a hack into a first-class control-flow primitive. Scroll the reading; the panel on the right follows one refund-approval agent from state schema to crash, resume, and time-travel fork.

Foundation

A StateGraph is a schema plus functions

Strip LangGraph down to its skeleton and there are only two ideas. First, a state schema: you declare the shape of your agent's working memory as a TypedDict, a Pydantic BaseModel, or a dataclass — say {messages, order_id, approved} for a refund agent. That schema becomes the input to every node and edge in the graph. Second, nodes are plain functions. Each one receives the current state and returns a partial state update — just the keys it changed, not the whole object. The docs put it bluntly: nodes and edges "are nothing more than functions — they can contain an LLM or just good ol' code."

That second point deserves a beat, because it's where beginners overcomplicate. A node that calls a model and a node that runs a SQL query are the same species: state in, partial update out. There is no magic "agent object" holding things together — the state object flowing through the graph is the agent's memory, and everything the run knows lives in it. If a fact isn't written into state, it doesn't survive to the next node. Sound familiar? It's Week 1's context-window discipline wearing a graph costume: you decide, explicitly, what the system carries forward.

Why does this matter for durability, today's actual topic? Because you can only persist what you can serialize. A pile of closures and hidden instance variables can't be snapshotted; a declared, typed state object can. LangGraph's entire persistence story — checkpoints, resume-after-crash, human-in-the-loop, time travel — rests on the fact that at any moment, the whole run is representable as one state value plus a position in the graph. Design the schema first, and everything else today falls out of it.

Merging updates

Reducers decide how updates land

If every node returns a partial update, something has to decide how those updates merge into state. That something is a reducer, and every key in your schema has its own. The default is brutal and simple: overwrite. Node returns {messages: [x]}, and whatever was in messages is gone, replaced by a one-element list. This is the classic first-day LangGraph bug — "my conversation keeps resetting to the last message" — and it's not a framework glitch, it's the default reducer doing exactly what it says.

The fix is to attach a custom reducer with an Annotated type hint: Annotated[list, operator.add] makes updates append instead of replace. For chat history specifically, the prebuilt add_messages reducer goes further — it merges by message ID, so re-sending a message with the same ID updates it in place rather than duplicating it, and it handles deserialization for you. One schema, per-key merge policies: overwrite for a status flag, append for a log, ID-merge for messages.

Around the state flow sits control flow: normal edges route unconditionally from node to node; conditional edges call a routing function that returns the next node's name; START and END are the virtual entry and exit. Two power tools you'll meet again this week: Command lets a node bundle a state update with a routing decision, and Send fans work out dynamically to multiple targets, each with its own state. And one hard rule from the docs: "You MUST compile your graph before you can use it." .compile() validates the structure — and, crucially for today, it's where you plug in the checkpointer.

Persistence

Checkpoints: a save file for every step

Here's the move that turns a graph into a durable system. Compile with a checkpointer, and LangGraph saves a checkpoint — a snapshot of graph state — as the run proceeds, step by step. Those checkpoints are grouped under a thread: you pass a thread_id in the config when you invoke the graph, and every checkpoint from that run files under it. The docs call this "short-term, thread-scoped memory," and the framing is exact: a thread is one conversation, one task, one workflow instance — and its checkpoints are that instance's complete save history.

Think of it as the save system in a video game. The thread_id is the save slot; each checkpoint is an autosave at the end of a step. Process dies at step three of five? Re-invoke with the same thread_id and the run continues from the last checkpoint instead of starting over. Same mechanism, one id per customer, and yesterday's stateless chatbot becomes a continuous conversation across requests, restarts, and deploys. This single feature is what unlocks everything else today: conversation continuity, human-in-the-loop pauses, time travel, and fault tolerance are all downstream of "the state is snapshotted somewhere durable."

One distinction to file now, because clients confuse it constantly: checkpointing is not long-term memory. A checkpointer remembers this thread. For knowledge that must span threads — user preferences, facts learned across many conversations — LangGraph has a separate concept, the Store, holding application-defined key-value data across threads. Checkpointer = the run's save file; Store = the agent's notebook. Today is entirely about the save file.

Backends

Where checkpoints actually live

A checkpointer is an interface, not a database — the contract is BaseCheckpointSaver, and it's small: put stores a checkpoint, put_writes stores pending writes, get_tuple fetches one, list enumerates a thread's history, delete_thread drops it, and each has an a-prefixed async variant. Anything that implements those methods can be your persistence layer, which is why the backends ship as separate packages you choose per deployment.

Three tiers, and the tier names are the deployment advice. InMemorySaver (from langgraph-checkpoint) keeps checkpoints in process memory — perfect for dev and tests, and gone the moment the process restarts, which means it silently defeats the entire point in production. SqliteSaver / AsyncSqliteSaver (langgraph-checkpoint-sqlite) persist to a local file — fine for demos and single-machine experiments, explicitly not production. PostgresSaver / AsyncPostgresSaver (langgraph-checkpoint-postgres) is the production tier: durable and shared across app instances. Under the hood, checkpoints are serialized with JsonPlusSerializer (ormsgpack with a JSON fallback), and if your state carries anything sensitive you can wrap it in EncryptedSerializer for encryption at rest — remember, a checkpoint is a full copy of agent state, PII and all, sitting in a database.

The FDE reflex here is a one-line code review: find the checkpointer, check the tier. "Our agent forgets everything when we redeploy" is almost never a LangGraph bug — it's an InMemorySaver that followed the tutorial into production. The fix is a two-line swap to Postgres, and you'll look like a wizard for spotting it.

Tuning

Durability modes: when the write happens

Having a checkpointer settles where snapshots go; durability mode settles when they're written relative to execution — and it's a genuine engineering trade-off, tunable per call: graph.stream(input, config, durability="sync"). Three settings.

"sync" — changes are persisted synchronously before the next step starts. Most durable, slowest: every step waits for the database write to land, so a crash can never lose a completed step. "async" — changes are persisted while the next step executes. The write and the work overlap, so you get most of the durability at much less latency cost — with a small crash window where a step finished but its checkpoint hadn't landed yet. "exit" — changes are persisted only when the graph exits. Fastest, and if the process dies mid-run there is nothing to resume from; you've opted out of mid-run crash recovery entirely.

Notice the shape of this decision — you've made it before. It's the same durability-versus-throughput dial as database write concerns or fsync policy, applied to agent state. And the right answer is workload-shaped, which is why it's per-invocation: a money-touching approval workflow wants "sync", a chat assistant is happy with "async", and a bulk overnight batch job that can simply be re-run from the top might choose "exit" and take the speed. When a client asks "why is the agent slow?" and "what happens if it crashes?", know that those two questions share one knob — and you should be able to say which setting they're on and why.

Human-in-the-loop

interrupt(): pausing is just a checkpoint

Now the payoff feature — the one clients ask for by name. "The agent can draft the refund, but a human must approve it before it executes." In a stateless world that's an architectural headache: you'd have to tear the workflow in half, stash intermediate results somewhere, and rebuild everything when the human answers. With checkpointing, it's one function call. Inside a node, call interrupt(payload): the graph stops, the current state is saved through the checkpointer, and your payload — "Approve this $840 refund?" — is surfaced to the caller. Under the hood, interrupt() works by raising a special exception that the LangGraph runtime catches; it's control flow, not an error.

This is why the docs are blunt that a checkpointer is mandatory for interrupts — "state is saved using the checkpointer so execution can be resumed later." A pause with nowhere to save is just a crash with good manners. The paused thread now sits in the database, costing nothing, for seconds or for a week — however long the human takes.

Resuming is the mirror image: re-invoke the graph with Command(resume=value) on the same thread_id, and the value you pass becomes the return value of the interrupt() call inside the node — the human's "approved" flows into the code exactly where the question was asked. The thread id is, in the docs' phrase, your persistent cursor: same id, same paused run; new id, fresh thread with empty state — and a support ticket asking why the agent "forgot" the approval. One more contract note: Command(resume=...) is the only Command pattern meant as input to invoke()/stream(); the rest live inside nodes.

Sharp edges

Resume re-runs the node from the top

Here is the sharpest edge in today's material, and it's exactly the kind of thing that separates "read the quickstart" from "ready for a client." When a thread resumes, the runtime restarts the entire node from the beginning — it does not continue from the exact line where interrupt() was called. Everything in the node before the interrupt runs again. Picture the node that charges a card and then asks for approval: charge_card(); interrupt("confirm?"). On resume, charge_card() fires a second time. That's not a hypothetical — it's the canonical double-side-effect bug.

The docs draw three rules straight from this semantics. One: code before an interrupt() must be idempotent — safe to run twice — or moved into its own node before the interrupting one, so the checkpoint boundary protects it. Two: never wrap interrupt() in a bare try/except — remember, it's implemented as an exception, and a catch-all will swallow the pause signal and break the mechanism silently. Three: if one node contains multiple interrupts, resume values are matched to them strictly by index — first resume answers the first interrupt, and so on — so their order must stay consistent across executions; conditionally skipping one shifts every answer onto the wrong question.

With the semantics respected, a small set of HITL patterns covers most client asks: approval workflows (pause before the sensitive action, route on approve/reject), state review & editing (show the human the draft, let them correct it), tool-call review (inspect and fix an agent's proposed tool call before it executes — Week 3's consent gate, now durable), and input validation. For that last one the docs give structural advice worth quoting into your notes: build validation loops with conditional edges between nodes, not with a while loop wrapped around an interrupt inside one node.

Time travel

Replay and fork: the history is a data structure

Because every step is checkpointed, a finished (or failed) run isn't a log line — it's a navigable history. get_state_history(config) returns the thread's checkpoints, newest first, and each one carries a checkpoint_id in its config. Invoke the graph with a prior checkpoint's config and you replay from that point: nodes before the checkpoint aren't re-run — their results come straight from the snapshot — while nodes after it execute again for real. And the docs flag the trap in that sentence: "replay re-executes nodes — it doesn't just read from cache." LLM calls, API requests, and interrupts genuinely fire again and may return different results. Replaying is rewinding a live system, not scrubbing a recording.

The second tool is the fork. update_state doesn't edit history in place — it creates a new checkpoint that branches from the point you specify, leaving the original history intact. Then invoke(None, config) continues execution from the fork with your modified state. The as_node parameter attributes your edit to a specific node's writes, so the graph resumes from that node's successors — which also makes it a scalpel for skipping a node or disambiguating parallel branches. Debugging workflow, made concrete: customer reports the agent approved the wrong refund → pull the thread's history → find the checkpoint where retrieval returned the wrong order → fork there with the corrected state → re-run the tail and confirm the fix — all without touching the customer's real thread.

Three production footnotes from the docs before you leave: checkpoints accumulate over long threads (latency and storage — prune), keep thread_id under 255 characters (a Postgres column limit), and subgraphs checkpoint under their own namespace, so a parent graph doesn't immediately see child state updates. Small print now; incident reports later.

FDE mindset

Clients don't buy "an agent" — they buy a workflow they can trust with money, and trust means survivability: survives a crash, waits for a human, and can be rewound when something goes wrong. All three are the same primitive — state, snapshotted at every step under a durable id. When you evaluate any agent framework or any client's homegrown orchestrator, ask the checkpoint questions first: where does state live, when is it written, and can I resume a thread? Deep dive: the checkpointer contract, serialization & production limits

Optional. ~10 minutes. What's under the compile(checkpointer=...) line.

The contract is tiny. BaseCheckpointSaver asks for five operations — put (store a checkpoint), put_writes (store pending writes), get_tuple (fetch), list (enumerate a thread's checkpoints), delete_thread (drop one) — plus a-prefixed async variants. That's the whole persistence interface; SQLite, Postgres, and in-memory are just different homes for the same five verbs, which is also why backends ship as separate packages (langgraph-checkpoint, -sqlite, -postgres) you swap without touching graph code.

Serialization is a security surface. Checkpoints are serialized with JsonPlusSerializer — ormsgpack with a JSON fallback. A checkpoint is a complete copy of agent state: messages, retrieved documents, customer data. If that includes PII, the checkpoint table is now a PII store, with all the compliance consequences. EncryptedSerializer wraps the serializer for encryption at rest — cheap to add on day one, painful to retrofit after the audit.

Worked choice — durability mode per workload
  • Refund-approval agent (moves money): durability="sync" — every completed step is on disk before the next starts; a crash can never replay or lose a committed step.
  • Support chat assistant: "async" — write overlaps the next step; worst case a small crash window re-runs one step of conversation.
  • Overnight bulk classifier, safely re-runnable from the top: "exit" — no mid-run recovery, maximum throughput, and that's an acceptable trade because a re-run is free.

The knob is per-invocation (graph.stream(input, config, durability=...)), so one deployed graph can serve all three postures.

Production small print (all from the persistence docs): checkpoints accumulate per thread — long conversations mean growing storage and slower loads, so prune; keep thread_id under 255 characters (Postgres column limit); and subgraphs checkpoint under their own namespace, so a parent graph does not immediately observe a child's state updates — remember that before you "fix" a parent that looks stale.
