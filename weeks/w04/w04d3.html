Alt Research: CrewAI & AutoGen vs LangGraph

Week 4 · Day 3 Multi-Agent Systems with LangGraph ~18 min · reading @150 wpm + diagram + check

This week you're building multi-agent systems on LangGraph — but a client will absolutely ask "why not CrewAI?" or "isn't Microsoft's thing the enterprise answer?", and an FDE who can only defend the tool they happen to know is not defending anything. Today is the alt-research day: how CrewAI and AutoGen's successor, Microsoft Agent Framework, each do multi-agent orchestration, mechanism by mechanism, against the LangGraph machinery you met on Day 2. The panel on the right assembles all three stacks side by side and ends where every framework debate should end — on a single tradeoff axis you can draw for a client. Scope check: Day 1 gave you the orchestration patterns generically, Day 2 gave you LangGraph state and checkpointers; today is strictly the multi-agent layer of the competing frameworks, and everything here is source-verified as of July 2026.

Why re-litigate

Same job, three philosophies — and a stale-advice minefield

All three frameworks are trying to solve the identical problem you sketched on Day 1: several specialized agents, one coherent outcome, and some mechanism deciding who acts next. Where they differ — and where your recommendation to a client lives — is how much of that routing decision is explicit code you wrote versus judgment delegated to an LLM versus a prebuilt pattern you configure. Hold that axis in your head; every mechanism today lands somewhere on it.

First, pin the versions, because this landscape moved hard and most of what the internet (and, frankly, most models' training data) will tell you is stale. As of July 2026: LangGraph 1.2.7 (released 2026-06-30) describes itself as "a low-level orchestration framework for building, managing, and deploying long-running, stateful agents." CrewAI 1.15.1 (2026-06-27) is "built entirely from scratch — completely independent of LangChain or other agent frameworks" — so if anyone tells you CrewAI is a LangChain wrapper, they're reciting 2023. And AutoGen is now a legacy migration source: its GroupChat and event-driven runtime ideas live on inside Microsoft Agent Framework (agent-framework 1.10.0, 2026-06-30, production/stable), built by the core AutoGen and Semantic Kernel teams as "a new foundation for building AI applications going forward."

That last one matters for client conversations. A stakeholder who read a 2024 blog post will present "AutoGen GroupChat" as Microsoft's live answer. It isn't — Microsoft's own migration guide (dated 2026-04-01, updated 2026-06-26) maps AutoGen's teams onto Agent Framework Workflows. Part of today's value is simply being the person in the room whose facts are current.

Our pick, restated

LangGraph's frame: five patterns, one design concern

Before comparing, restate the home team precisely — because the current LangGraph story is not the "just draw a graph" folklore either. The docs now frame multi-agent design as five named patterns: subagents (a main agent calls subagents as tools), handoffs (agents transfer control to each other via tool calls), skills (one agent loads specialized prompts on demand), router (classify the request, then dispatch), and fully custom LangGraph workflows when none of the above fits.

And the docs name the design concern that governs all five: "at the center of multi-agent design is context engineering — deciding what information each agent sees." Read that twice, because it's Week 1 wearing Week 4 clothes. Splitting one agent into five doesn't add intelligence; it partitions the context window. The whole reason to go multi-agent is that each specialist gets a small, curated view instead of one agent drowning in everything — which means the architecture question is really a window-budgeting question, the same accounting you've been doing since Day 1.

Notice also what LangGraph is selling underneath the patterns: durable execution, streaming, human-in-the-loop, and persistence — the substrate that Day 2's checkpointers gave you. The patterns are the vocabulary; the durable, stateful runtime is the product. Keep that in view when the competitors show up, because it's the part they each had to answer for.

LangGraph mechanism

Handoffs are tools that return a Command

Here's the LangGraph handoff mechanism at the metal, because this is the thing you'll contrast all day. A handoff is implemented as a tool — the agent decides to transfer by calling it, like any other tool call — but instead of returning data, the tool returns a Command object that combines a state update with control flow. When your agents are built as subgraphs, Command(goto=..., graph=Command.PARENT) jumps execution to a sibling agent node in the parent graph. The routing decision was the LLM's (it chose to call the tool); the routing destination and semantics are yours, in code.

There's a sharp edge the docs are explicit about: when a tool call triggers a handoff, you must still return a ToolMessage with the matching tool_call_id — otherwise the conversation history becomes malformed. Every tool call needs its receipt, even when the "result" of the call is that control went somewhere else. Forget the receipt and you've corrupted the transcript every downstream agent reads. That's exactly the class of bug that produces "the second agent acts confused" symptoms with no stack trace.

Interactive — future goal

Planned: a Command-handoff tracer — step through a two-agent LangGraph run, watch the handoff tool emit Command(goto="billing_agent", graph=Command.PARENT) with its state update, and toggle the paired ToolMessage off to see the malformed-history failure the docs warn about. Needs backend standup.

Now the twist most people miss: the docs' own recommendation is to "use single agent with middleware for most handoffs use cases — it's simpler," reserving multiple agent subgraphs for when you need bespoke agent implementations — say, a node that is itself a complex graph with its own reflection or retrieval loop. The most graph-native framework on the market telling you not to reach for multi-subgraph builds by default is a data point worth carrying into every architecture review this week.

LangGraph, packaged

Supervisor and swarm — the two archetypes as libraries

LangChain ships the two Day-1 archetypes as official prebuilt libraries. langgraph-supervisor-py packages the hierarchical pattern: create_supervisor([agent1, agent2], model=model) builds a central supervisor that delegates to workers via tool-based handoffs — the same Command machinery you just met, pre-wired into a coordinator shape. langgraph-swarm-py (latest release 0.1.0, 2025-12-04) packages the peer-to-peer shape: "agents dynamically hand off control to one another based on their specializations," with no boss node at all.

Swarm has one genuinely clever detail: an active_agent state variable persisted via the checkpointer, so "on subsequent interactions, the conversation resumes with that agent." If the user was mid-conversation with the refund specialist yesterday, they land back with the refund specialist today — conversational continuity as a one-variable consequence of Day 2's persistence layer. That's the LangGraph aesthetic in miniature: multi-agent behavior expressed as state you can point at.

But note the fine print, because it's the honest version of "our pick": the supervisor library's own maintainers now recommend "using the supervisor pattern directly via tools rather than this library for most use cases." The pattern outlived its packaging. Add that to the middleware-first advice from the last section and LangGraph's current posture is clear — a low-level substrate plus named patterns you mostly assemble yourself, not a menu of turnkey team shapes. Whether that's a feature or a cost is precisely what the next two frameworks disagree about.

CrewAI

CrewAI: orchestration is an enum and a manager

CrewAI comes at the same problem from the opposite end. Its multi-agent unit is the Crew — a role-based team of agents — with Flows alongside for deterministic, event-driven control. And where LangGraph hands you nodes and edges, CrewAI hides orchestration behind a Process enum with exactly two implementations. Process.sequential: "task execution follows the predefined order in the task list, with the output of one task serving as context for the next" — a pipeline, no routing decisions at all. Process.hierarchical: a manager runs the show — "the manager allocates tasks to agents based on their capabilities, reviews outputs, and assesses task completion." Tasks are not pre-assigned; they're dynamically delegated at runtime.

Standing up hierarchical mode requires one of two things: set manager_llm and CrewAI auto-creates the manager agent for you, or supply a custom manager_agent when you want to shape its behavior. Either way, the manager "coordinates the workflow, delegates tasks, and validates outcomes." Read what that is mechanically: prompt-driven manager routing. There is no graph to inspect — the routing logic lives inside an LLM's judgment about who's capable of what. That is the sharpest single contrast with LangGraph's explicit node/edge control, and it cuts both ways: dramatically less code to get a working team, dramatically less to point at when the manager delegates somewhere strange.

Planned: a crew-run inspector — define a three-agent crew, toggle between Process.sequential and Process.hierarchical with a manager_llm, and watch the task-allocation decisions the manager makes (and re-makes) on the same input. Needs backend standup.

CrewAI, sideways

Peer collaboration is a flag, not a graph

What about the swarm shape — peers handing work sideways without a boss? In CrewAI that's not an architecture, it's a flag. Set allow_delegation=True on an agent and CrewAI automatically injects two tools into it: Delegate work to coworker(task, context, coworker) and Ask question to coworker(question, context, coworker). Any agent so equipped can hand a subtask to any teammate, or query one for information, mid-task — no edges drawn, no Command objects, no parent graph.

The docs carry a piece of role-design advice worth stealing regardless of framework: enable delegation for coordinators and generalists, disable it for focused specialists. A specialist that can delegate is a specialist that can wander — you gave it an escape hatch from its own job. That's a context-engineering insight in CrewAI clothing: the tools an agent holds define its behavioral surface, and trimming that surface is how you keep a role a role.

Step back and compare mechanisms directly, because this is the exam-grade contrast. A LangGraph handoff is a tool returning a Command whose destination you wrote into the parent graph. A CrewAI delegation is a tool whose destination is whatever coworker the LLM names in the tool arguments. Both are tool-call handoffs — the frameworks converge on the mechanism — but LangGraph makes the route a compile-time fact and CrewAI makes it a runtime judgment. Same verb, opposite ends of the explicitness axis.

AutoGen → MAF

AutoGen is legacy; Agent Framework ships five orchestrations

Now Microsoft — and start with the succession, because it reframes everything. By Microsoft's own account, AutoGen "started as a research project at Microsoft Research and pioneered several concepts in multi-agent orchestration, such as GroupChat and event-driven agent runtime." Agent Framework, built by the core AutoGen and Semantic Kernel teams, is the designated new foundation. The migration guide maps AutoGen's RoundRobinGroupChat and GraphFlow onto Agent Framework Workflows, with Swarm and SelectorGroupChat listed as roadmap items still in development — so the mapping isn't even complete yet. If a client is on AutoGen today, they're on a framework whose own vendor has published its exit path.

The migration guide also concedes a gap LangGraph had first — and this should sound familiar from Day 2. "AutoGen's Team abstraction runs continuously once started and doesn't provide built-in mechanisms to pause execution for human input." Agent Framework closes it with a workflow-level request/response API: ctx.request_info() plus a @response_handler. Durable pause-for-a-human, the thing LangGraph's checkpointer gave you natively, was important enough that Microsoft rebuilt its stack partly to get it. When you argue for LangGraph's persistence layer in a design review, that's your corroborating witness.

What does the new stack actually ship? Five built-in multi-agent orchestrations: Sequential, Concurrent, Handoff ("agents transfer control to each other based on context"), Group Chat ("agents collaborate in a shared conversation"), and Magentic ("a manager agent dynamically coordinates specialized agents") — all supporting human-in-the-loop via tool approval and request info. That's a third philosophy on the axis: not LangGraph's build-it-from-substrate, not CrewAI's two-value enum, but a catalog of named, prebuilt patterns you select and configure.

The interesting one

Magentic: a manager with a ledger and a stall detector

Four of those five orchestrations map onto shapes you've already seen this week. The fifth is the one worth your attention. Magentic orchestration "is designed based on the Magentic-One system invented by AutoGen" — the research lineage that survived the migration. The pattern: a Magentic manager plans the task, selects the next agent to act each round, and — here's the novelty — maintains a progress ledger, explicitly tracking four questions: is the request satisfied? are we in a loop? is progress being made? who should speak next?

That ledger is what separates Magentic from CrewAI's hierarchical manager. Both are LLM coordinators — but Magentic's is instrumented against its own failure modes. When the ledger detects a stall, the manager auto-replans, and the whole loop runs under configurable limits — max_round_count, max_stall_count, max_reset_count — with optional human review of the plan before execution. Every Day-1 fear about agent loops ("what if they just talk in circles, burning tokens?") has a named knob here. The pedigree is real, too: the underlying Magentic-One paper (Microsoft, Nov 2024) describes an Orchestrator that "plans, tracks progress, and re-plans to recover from errors" using task and progress ledgers, hitting statistically competitive results with state-of-the-art systems on the GAIA, AssistantBench, and WebArena benchmarks.

The FDE takeaway isn't "use Magentic." It's that an LLM coordinator is trustworthy roughly in proportion to how observable and bounded it is. Magentic is what CrewAI-style manager routing looks like after someone added instrumentation, budgets, and a recovery policy. If you ever build a supervisor by hand in LangGraph — which the maintainers told you to do — the ledger-and-limits design is the checklist for doing it like an adult.

The decision

One axis, three positions — making the call like an FDE

Put the whole day on one axis: how much of the orchestration is explicit, inspectable structure versus LLM judgment versus vendor-packaged pattern? LangGraph exposes the graph itself — nodes, edges, Command handoffs, subgraphs — so orchestration is code you wrote and can debug, checkpoint, and replay. CrewAI hides orchestration behind a two-value Process enum, an LLM manager, and delegation tools — fastest path to a working role-based team, thinnest surface when routing misbehaves. Agent Framework packages five named orchestrations as prebuilt workflows — pattern selection over pattern construction, with enterprise HITL wired through. None of these is "best"; they're three prices for the same groceries.

And notice what all three agree on, because convergence is evidence: every stack lands on the same two archetypes from Day 1. A central coordinator — LangGraph supervisor, CrewAI hierarchical manager, MAF group chat and Magentic — or peer handoffs — LangGraph swarm, CrewAI delegation tools, MAF handoff orchestration. The market has converged on the shapes; the frameworks compete on how much of the routing you can see. So the client conversation writes itself: pick the archetype first (that's a workflow question), then pick the framework by how much explicitness the engagement needs. Regulated domain, long-running state, audit trail, replay? That's the explicit-graph end — our LangGraph pick, and now you can say why in the competitors' own vocabulary. Weekend-speed prototype with clean role separation? CrewAI's enum gets a team standing in an afternoon. Microsoft-committed enterprise wanting supported, named patterns with HITL gates? Agent Framework is purpose-built — just make sure nobody's greenfielding on AutoGen.

Deep dive: inside the Magentic progress ledger

Optional. ~10 minutes. What an instrumented LLM coordinator actually tracks.

The lineage. Magentic orchestration in Microsoft Agent Framework is "designed based on the Magentic-One system invented by AutoGen." The Magentic-One paper (Microsoft, Nov 2024, arXiv 2411.04468) describes a generalist multi-agent system whose Orchestrator "plans, tracks progress, and re-plans to recover from errors" using two artifacts: a task ledger (the plan) and a progress ledger (how it's going). On GAIA, AssistantBench, and WebArena it achieved "statistically competitive performance to the state-of-the-art."

The loop, per round. The Magentic manager plans the task, then each round consults the progress ledger before selecting the next agent:

The four ledger questions, every round
  • Is the request satisfied? → if yes, stop and answer.
  • Are we in a loop? → repeated states are a stall signal.
  • Is progress being made? → no progress also counts toward stall.
  • Who should speak next, and what should they do?

On stall detection the manager auto-replans — it doesn't just retry harder. The whole thing runs under explicit budgets: max_round_count, max_stall_count, max_reset_count, plus optional human plan review before execution begins.

Why this matters beyond Microsoft's stack. Compare it to CrewAI's hierarchical manager, which delegates, reviews, and validates — but whose docs describe no self-monitoring ledger or stall budget. Magentic is the existence proof that "LLM as coordinator" can be engineered rather than merely hoped for. If you hand-build a supervisor in LangGraph (as its maintainers recommend over the prebuilt library), the ledger questions and the three limits are your design checklist: every autonomous coordinator you ship should be able to answer "are we looping?" and should have a hard ceiling on rounds before a human sees it.
