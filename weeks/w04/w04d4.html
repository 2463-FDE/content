Operating envelope

Start with a budget, not an agent count

Every worker adds at least one model call, another context, another failure surface, and another trace to correlate. Write the service envelope before the graph: maximum wall-clock time, aggregate input/output tokens, model-call count, retry count, and the one outcome metric that justifies the work. These are scenario limits, not provider prices. If one agent meets the outcome inside the envelope, keep one agent.

Parallelism

Fan out only independent work

Parallel workers reduce elapsed time only when their inputs are ready and their writes do not collide. Give each worker a typed brief, read-only inputs, an output schema, and a deadline. The coordinator joins results in a deterministic order. Dependent work stays sequential; shared mutation stays with one named owner.

Predict before revealing: which work can run in parallel?
Check the boundary

The independent, read-only classifications may fan out. Two writers to one decision record create an ownership conflict; route proposals to one commit owner.

Cost and latency

Track the critical path and the total burn

For each span, record agent, model, input/output tokens, cache status, attempts, duration, and outcome. Total token use is the sum across every call; wall time follows the longest dependent path, not that sum. Caching may reduce repeated-prefix processing, but it is provider-specific and measurable—not an invariant you carry across a swap. A dashboard should show both totals and the slowest path.

Human authority

Put approval before the side effect

Classify tools as read, propose, or commit. Reads can run inside their bounded scope. Proposals produce an artifact. A commit that changes a claim decision, sends a message, or writes a system of record requires the named human gate and one write owner. Persist the proposed action, evidence reference, approver decision, and reason before execution; retries must not duplicate the side effect.

Correlation

One trace ID crosses every handoff

Carry a trace ID through coordinator, worker, model, and tool spans. Add an agent name, handoff ID, parent span, attempt, and policy decision as attributes; put large prompts or sensitive content behind controlled references, not into ordinary logs. Structured logs answer what happened; the trace answers in what order and under whose decision. A failure must resolve to a specific span and owner.

Your tools

Use Claude Code subagents as the boundary rehearsal

A subagent has a separate context, prompt, and scoped tools. Rehearse the production rule locally: explorers inspect; reviewers challenge; one parent owns edits. In the retro, compare planned versus actual delegation, duplicated work, context returned, and evidence quality. “More agents” is not a success criterion.

Provider seam

Keep the contract portable and test the differences

The source names a ChatBedrock versus ChatAnthropicVertex seam. Treat that seam as an adapter boundary, not a drop-in-equivalence claim. Normalize messages, tool schemas, stop/error categories, and your trace envelope. Then acceptance-test model identity, tool-call shape, streaming, retries, usage fields, caching, and telemetry separately for the selected provider.

Knowledge Graphs & Cypher: When Retrieval Needs Relationships

Week 4 · Day 4 Retrieval Beyond Vectors Historical pacing label · superseded by the source-restored route above

Vector search finds text that sounds like the question. But some questions aren't about similar text at all — they're about connections: who reports to whom, which contract covers which system, what breaks if this component fails. Today you learn the retrieval backend built for those questions: the knowledge graph. You'll pick up Neo4j's property-graph model, the schema-design workflow that turns a messy domain into labeled nodes and directed relationships, enough Cypher to read and write graph queries, and the two retrieval patterns — vector-then-traverse and text-to-Cypher — that make a graph a first-class RAG citizen. The panel on the right grows one small graph from a single hard question into a full GraphRAG retrieval architecture.

Why a graph

The questions chunk retrieval can't answer

Picture the client question that breaks a plain vector pipeline: "What are the main themes across all of our incident reports?" There is no single chunk in the corpus that contains that answer. Similarity search retrieves the top-k passages that resemble the question — but a "what are the main themes" question resembles everything vaguely and nothing specifically. The answer lives in the connections between hundreds of documents, not inside any one of them.

Deeper: what the GraphRAG paper did, and what a knowledge graph is

This is exactly the gap the GraphRAG paper (Microsoft, arXiv:2404.16130) called out. Their move: have an LLM read the source documents and extract an entity knowledge graph — the people, systems, and events, and how they relate — then run community detection to group closely related entities and pre-generate summaries for each community. At query time, a global question is answered by mapping over those community summaries and reducing the partial answers into a final one. On corpora around a million tokens, they reported substantial improvements over a conventional RAG baseline on both comprehensiveness and diversity of answers.

A knowledge graph, for our purposes, is a database whose native shape is entities and the typed relationships between them — not rows, not documents, not vectors. Once your facts live as a graph, a whole family of questions that made vector RAG sweat become simple traversals. The rest of today is the practical stack underneath that idea: the data model, the schema discipline, the query language, and how it plugs into the RAG pipelines you built earlier this week. Keep last week's window math in your head throughout — a graph doesn't replace retrieval, it changes what you retrieve into the window.

The data model

Property graphs: nodes, relationships, properties

Neo4j's model is called the property graph, and it has exactly three moving parts. Nodes are your entities, and each carries one or more labels saying what kind of thing it is — a person, a movie, an incident. Relationships connect exactly two nodes, always with a direction and a single type. And properties are key-value pairs that can sit on both nodes and relationships: a person has a name, and the relationship that connects them to a film can itself carry the role they played. One line of Cypher shows all three at once:

(:Person {name:"Keanu"})-[:ACTED_IN {role:"Neo"}]->(:Movie {title:"The Matrix"})

Deeper: first-class relationships, and the schema-flexibility trap

Two things make this model different from the tables you're used to. First, relationships are first-class data, not something you reconstruct at query time with JOINs — the connection is stored, typed, directed, and can hold its own attributes. Second, the model is schema-flexible: unlike SQL, Neo4j does not mandate uniform properties across entities of the same label. One Person node can have a twitterHandle and its neighbor can lack one, and nothing complains.

That flexibility is a gift and a loaded gun. It means you can grow a graph organically as a client's domain reveals itself — no migration ceremony to add a property. It also means nothing stops you from building an inconsistent mess where half your people have name and half have fullName. The database won't impose discipline. The schema-design workflow in the next section is where the discipline comes from — and as you'll see by the end of the day, that discipline is what decides whether your GraphRAG retrieval works at all.

Schema design

Nouns become labels, verbs become relationships

Neo4j's own modeling tutorial gives you a workflow, and it starts somewhere beginners skip: define the use-case questions first. Before you draw a single node, write down the questions the application must answer — "which customers are affected by this outage?", "who approved this change?" Then model, then test the model against every one of those questions, then refactor. A graph schema isn't right in the abstract; it's right for a set of questions.

Deeper: the naming conventions

The translation rules are pleasingly mechanical. The dominant nouns in your use case become node labels, written in CamelCase — customer, support ticket. The verbs become relationship types, written in capitals with underscores, as in REPORTED or DEPENDS_ON. The attributes become properties, in camelCase and not capitalized. Every relationship gets an explicit direction, and relationship properties are where you record how two nodes relate — the role in the film, the date of the approval.

The rule that will pay your salary later: make relationship types as specific as possible, never generic. A graph full of edges that all say "related to" is a graph that can answer no precise question, because every traversal drags in every kind of connection at once. Acted-in versus directed versus produced is the difference between a query that returns the cast and a query that returns noise. And enforce unique identifiers with uniqueness constraints, so the same real-world entity cannot sneak in twice as two nodes — duplicates silently split your graph's connectivity, and every downstream traversal pays for it.

The query language

Cypher: patterns you can read out loud

Cypher, created in 2011, is Neo4j's query language, and its core design choice is the same one SQL made: it's declarative. You specify what to retrieve, not how to walk the graph to get it. What's different is the syntax — Cypher patterns are essentially ASCII art of the graph itself: rounded brackets for nodes, arrows for relationships. (nodes)-[:CONNECT_TO]->(otherNodes) looks like the thing it matches, which is why the docs call it highly intuitive to both read and write. One habit shift from SQL: the RETURN clause comes at the end of the query, after you've described the shape you want.

The mental model that makes Cypher click is the distinction the manual draws between a pattern and a path. A pattern is "a queryable specification of a graph structure" — the shape you describe. A path is "an actual sequence of nodes and relationships in the graph that matches a pattern" — one concrete answer. Write MATCH (p:Person)-[:ACTED_IN]->(m:Movie) RETURN p.name, m.title and you've declared a shape; the engine finds every path in the graph that fits it.

Deeper: variable-length, shortest-path, and match modes

Patterns scale up in expressive power. Fixed-length patterns chain hops explicitly. Variable-length patterns say "follow this relationship one to five times," which is how you ask transitive questions such as "everything downstream of this service" without knowing the depth in advance. Shortest-path patterns find the minimal route between two nodes, and the newest language version adds match modes for finer control over how a path may revisit the graph. You do not need to memorize the full grammar today. You need to be able to read a traversal query and, crucially, to recognise that the query is only writable because the schema gave the relationships specific types and directions. Vague schema, unwritable query.

Version trap

Cypher 5 vs Cypher 25 — the stale-tutorial hazard

A short section that will save you real debugging time. Two Cypher language versions currently coexist. Cypher 25 is the evolving one, where all new features land. Cypher 5 is frozen as of Neo4j 2025.06; per the documentation, no new features will be added to it. Which one you are speaking is selected per database, through a default-language setting when the database is created, or per query, by literally prepending CYPHER 25 to the statement.

The trap: from Neo4j 2026.02, new deployments explicitly set db.query.default_language=CYPHER_25 — but if the setting is absent, the default is still Cypher 5. Meanwhile, most of the tutorials, blog posts, and Stack Overflow answers you'll find online were written in the Cypher 5 era. So a student — or a client's engineer — on a fresh 2026 install is running Cypher 25 by default while pasting Cypher 5–era advice. Usually it works; occasionally it doesn't, and the failure looks like mystery.

Deeper: the version-check reflex

You've seen this movie before in this program: the model-version churn of Week 1, the framework churn of Week 3. The FDE reflex is always the same — check which version the environment is actually running before you trust any advice, including your own memory. One CYPHER 25 prefix on a query is a cheap way to make the version explicit while you're diagnosing.

Vectors in the graph

Neo4j's vector index: semantic search and traversal in one store

Here's the feature that turns Neo4j from "interesting graph database" into a serious RAG backend: it ships a built-in vector index. Under the hood it's a Lucene-backed HNSW approximate-nearest-neighbor index — the same family of algorithm as the dedicated vector stores you met earlier this week — and in the manual's words, it lets you "retrieve a neighborhood of nodes or relationships based on the similarity between the embedding properties."

Deeper: creating the vector index

You attach it to a property. Store an embedding on each node — m.embedding on your Movie nodes, say — then:

CREATE VECTOR INDEX moviePlots FOR (m:Movie) ON m.embedding
OPTIONS { indexConfig: { 'vector.dimensions': 1536, 'vector.similarity_function': 'cosine' }}

Dimensions can range from 1 to 4096, and the similarity function is cosine or euclidean — with the useful footnote that for l2-normalized vectors the two produce the same similarity ordering. On Neo4j 2026.01+, current Cypher 25 uses MATCH … SEARCH to return nearest nodes and scores. Put a tenant predicate inside the SEARCH subclause against a filterable index property: the index keeps searching until it fills the requested limit with same-tenant results. An outer WHERE runs after global top-k and can silently lose valid tenant results. The older db.index.vector.queryNodes() procedure is deprecated as of Neo4j 2026.04.

Deeper: why a vector hit that is a node matters

Pause on why this matters architecturally. The result of a vector query here isn't a text chunk — it's a node in a graph, with typed relationships radiating out of it. One database now serves both retrieval modes: semantic "find me things like this" and structural "now walk the connections." That combination is the hinge the next section swings on.

GraphRAG pattern 1

Vector in, traversal out

Now assemble the retrieval pattern. Plain vector RAG stops at "here are the five most similar chunks." Graph-enhanced retrieval uses the vector hit as an entry point, then follows relationships to gather the context that similarity alone would never surface: find the incident report most similar to the question, then traverse to the affected systems, the on-call engineer who resolved it, and the three earlier incidents linked to the same root cause. The retrieved context arrives in the window already structured — entities and their relations, not a bag of prose.

Deeper: the neo4j-graphrag-python retrievers, and the two meanings of "GraphRAG"

You do not have to hand-roll this. neo4j-graphrag-python is Neo4j's first-party GraphRAG package — the long-term-support successor to an earlier GenAI package, wanting Python 3.10 to 3.14 and Neo4j 5.18.1 or newer. Its retriever taxonomy is a menu of exactly the patterns you would want. A plain vector retriever does similarity search over a vector index. The vector-plus-Cypher retriever is the star: after finding similar nodes it "executes a Cypher query to traverse the graph based on these nodes," enriching the result with connected context you specify. The hybrid variants add a full-text index alongside the vector index, optionally with the same traversal step. And if the client's embeddings already live in Weaviate, Pinecone or Qdrant, external retriever variants join those hits back to Neo4j nodes.

One naming caution for client conversations: "GraphRAG" covers two different mechanics. What we just described — vector entry point plus Cypher traversal — is local and entity-anchored: great for "tell me everything connected to X." The GraphRAG paper's flagship mode is global: community summaries over an LLM-extracted entity graph, map-reduced to answer "what are the main themes" sensemaking questions. Same name, different retrieval shapes, different questions they're good at. When a stakeholder says "we want GraphRAG," your first job is finding out which of the two they actually read about.

GraphRAG pattern 2

Text2Cypher: retrieval by writing the query

The second pattern skips embeddings entirely. Text2Cypher hands the LLM your graph's schema and the user's natural-language question, and — in the package's description of Text2CypherRetriever — "first asks an LLM to generate a Cypher query to fetch the exact information required to answer the question from the database," then executes that query and returns the results. The model isn't answering from retrieved prose; it's writing a database query, and the database answers.

Think about which questions this wins. "How many open tickets does each region have?" is a terrible vector query — no chunk contains the count — but a trivial aggregation once translated to Cypher. Multi-hop questions with precise semantics ("which engineers worked on incidents affecting systems owned by this team?") compile naturally to a traversal pattern. The results are exact and structured, straight from the graph, not paraphrased from similar-sounding text.

And here is the day's throughline landing: text-to-Cypher is only as good as the schema it is prompted with. The model can only write -[:ACTED_IN]-> into a query if your schema has that relationship to name — a graph of vague "related to" edges gives it nothing precise to compile the question into. The same is true of the traversal retriever: its query is only writable because your relationships are specific and directed. Every hour you spent on schema design in section three was retrieval engineering in disguise. Schema quality determines retrieval quality. That is the sentence to carry out of today.

FDE lens

Choosing the graph — and defending the choice

You now hold both retrieval families from this week: vector similarity over chunks, and graph traversal over entities. The client-facing skill is knowing which question calls for which. "Find passages about X" — vectors. "What's connected to X, and how?" — graph. "What are the themes across everything?" — the paper's global, community-summary shape. Most real engagements end up hybrid, which is precisely why Neo4j putting an HNSW index inside the graph store, and shipping retrievers that chain the two, is architecturally interesting: one backend, both questions.

Deeper: the honest cost of a graph

But hold the cost honestly. A knowledge graph is not free retrieval quality — it's an upfront modeling investment (those use-case questions, that refactor loop) plus an ongoing curation obligation, and the GraphRAG paper's pipeline spends real LLM tokens extracting entities and pre-generating community summaries before a single query is served. The graph pays off when the client's questions are genuinely relational or global; it's overhead when a well-tuned vector index would have answered everything asked of it.

Then decide where the graph runs. The Cypher and the modeling on this page don't change with the cloud; placement does, and placement decides latency to your app and model, where the data sits, and who gets paged when the database is down. FDE mindset

When a client's retrieval "misses obvious things," ask what shape the miss is. If the answer existed in one chunk and search didn't find it, that's a vector problem. If the answer only exists across connections — ownership chains, dependencies, themes — no amount of embedding tuning will fix it, because the corpus never contained the answer as text. Diagnose the shape of the question before you pick the shape of the store. And when you do reach for a graph, remember where its power comes from: not the database, the model. Specific nouns, specific verbs, directed edges, unique IDs — schema quality determines retrieval quality.

Deep dive: a VectorCypherRetriever, line by line

Optional. ~10 minutes. How the two retrieval modes actually chain.

Step 1 — the index. Everything starts with embeddings stored as node properties and a vector index over them:

The setup, in order
  • Index invariant: configure the embedding property plus tenantId as a filterable property on Neo4j 2026.01+; dimensions must match the embedding model and similarity is cosine or euclidean.
  • CYPHER 25 MATCH (incident:Incident) SEARCH incident IN (VECTOR INDEX incidentEmbeddings FOR $queryEmbedding WHERE incident.tenantId = $tenantId LIMIT 5) SCORE AS score — the tenant predicate is evaluated inside the index, which continues until it finds five matching incidents.
  • The fixed traversal must scope every connected node too, e.g. (system:System {tenantId: $tenantId}) and (team:Team {tenantId: $tenantId}). Read-only does not by itself prevent cross-tenant disclosure.

The window payload is now the traversal's output — structured entities and relations — not raw chunks. You control exactly which neighborhood gets spent into the context budget.

Why not always Text2Cypher instead? Text2CypherRetriever is unbeatable for aggregations and precise multi-hop questions — the LLM generates a Cypher query, the database returns exact rows. But it's only as good as the schema it's prompted with, and a generated query that misreads the schema returns confidently wrong exactness. Vector-entry + fixed traversal is the safer default when the question is fuzzy; Text2Cypher shines when the question is precise and the schema is clean.

Version footnote. If a generated or pasted query misbehaves on a 2026-era server, check the Cypher language version first — new deployments from 2026.02 onward default to the newer language, while most examples online are still written for the frozen one. Prepending CYPHER 25 or CYPHER 5 to the query makes the version explicit while you diagnose.

Vector entry, then a read-only graph traversal

Read-only worked example. Cypher 25 filters a synthetic vector search inside a tenant-aware index, then scopes every traversed incident, system, and team to the same tenant.

// Synthetic parameters: $query_embedding and $tenant_id.
// Index invariant: tenantId is configured as a filterable property.
// Read-only clauses only: no procedure, mutation, driver, or global top-k.
CYPHER 25
MATCH (incident:Incident)
  SEARCH incident IN (
    VECTOR INDEX synthetic_incident_embeddings
    FOR $query_embedding
    WHERE incident.tenantId = $tenant_id
    LIMIT 3
  ) SCORE AS score
MATCH (incident)-[:AFFECTED]->(system:System {tenantId: $tenant_id})
MATCH (team:Team {tenantId: $tenant_id})-[:OWNS]->(system)
WHERE system.tenantId = incident.tenantId
  AND team.tenantId = incident.tenantId
RETURN
  incident.id AS incidentId,
  score,
  collect(DISTINCT system.name) AS affectedSystems,
  collect(DISTINCT team.name) AS owningTeams
ORDER BY score DESC
