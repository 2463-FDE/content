GraphRAG End-to-End: When Retrieval Grows a Graph

Week 4 · Day 5 · ★ milestone Knowledge Graphs & Multi-Agent Systems ~18 min · reading @150 wpm + diagram + check

Week 2 gave you vector RAG; yesterday gave you Neo4j and Cypher. Today they fuse. GraphRAG is the end-to-end pipeline that turns unstructured documents into a knowledge graph, then retrieves with vector similarity as the entry point and graph traversal as the context expander — and it exists because a whole class of client questions is simply unanswerable by top-k chunk retrieval. This is the week's milestone: by the end you can draw the full path from raw docs to grounded, graph-aware answers, and justify every stage. Scroll the reading; the panel on the right assembles the pipeline one layer at a time.

The gap

Vector RAG hits a wall on "whole corpus" questions

Start with the failure that motivates everything today. Your Week 2 RAG pipeline — embed the query, pull the top-k most similar chunks, answer against them — is excellent at one shape of question: "find me the passage that says X." Now imagine the client asks, "What are the top themes across all of last quarter's incident reports?" There is no chunk anywhere in the corpus that contains that answer. Similarity search retrieves five near-duplicate fragments about whichever theme happens to sit closest to the query embedding, and the model summarizes a sliver while sounding like it surveyed the whole.

Microsoft's GraphRAG paper — From Local to Global: A Graph RAG Approach to Query-Focused Summarization (Edge et al.) — names this precisely: baseline vector RAG fails on questions "directed at an entire text corpus." These are global sensemaking questions — query-focused summarization tasks, not needle-in-haystack lookups. Their proposed fix has two moves: use an LLM to build an entity knowledge graph out of the documents, and pre-generate summaries for communities of closely related entities so the corpus has a structured, hierarchical index to reason over. Answers are then produced hierarchically — a partial answer per community summary, then a final summarizing pass. On corpora in the one-million-token range, the paper reports substantial improvements over a conventional RAG baseline in both the comprehensiveness and diversity of answers, and the approach "scales with both the generality of user questions and the quantity of source text."

Microsoft's own framing is the one to carry into a client meeting: GraphRAG is "a structured, hierarchical approach to RAG, as opposed to naive semantic-search approaches using plain text snippets." Keep the diagnostic in your pocket — when a client's RAG demo aces lookup questions and faceplants on "summarize the landscape" questions, that isn't a tuning problem. It's a missing layer of structure, and today you learn to build it.

The shape

Two pipelines, one system: index time and query time

Every GraphRAG system, whichever library you use, is really two pipelines welded together. The index-time pipeline runs once (and on updates): it eats raw documents and emits a knowledge graph plus supporting indexes. The query-time pipeline runs per request: it takes a question, enters the graph somewhere, expands context, and generates a grounded answer. Confuse the two and every architecture conversation goes sideways — index-time cost is paid up front and amortized; query-time cost is paid on every call, the same budget discipline you learned in Week 1.

Microsoft's reference indexing pipeline is four stages. One: segment the raw text into TextUnits — the chunks that remain the unit of analysis and citation throughout. Two: use the LLM to extract entities, relationships, and claims from each unit. Three: run hierarchical community detection over the resulting entity graph with the Leiden algorithm, clustering entities that are densely connected to each other. Four: generate community summaries bottom-up, so every cluster — and cluster of clusters — has a pre-written digest of what it's about.

Notice what stages three and four buy you: they are the paper's answer to the global-question gap from the last section. The graph alone gives you structure; the community summaries give you a corpus-level semantic index you can answer "top themes" questions from. We'll return to them in depth near the end of the reading. For the next three sections we zoom into the first half of the story — how unstructured text becomes a graph at all — using the first-party Neo4j tooling you'll build the milestone with, because it plugs straight into the Neo4j instance and Cypher skills you set up yesterday.

Index time · construction

SimpleKGPipeline: docs in, graph out

Neo4j's official Python package, neo4j-graphrag (version 1.18.0 as of late June 2026, and the long-term maintained successor to the older GenAI package), wraps the entire index-time pipeline in one orchestrator. It chains four components, and each one maps to a decision you will defend at a client.

First, a fixed-size splitter chunks the documents, approximating boundaries by default so chunks end cleanly rather than mid-word. Second, a chunk embedder computes an embedding for every chunk and stores it as a property on the chunk node — this is the hook that lets vector search live inside the graph database later. Third, the star of the show: an entity and relation extractor reads each chunk and pulls out entities and relationships, guided by a schema you supply. It uses structured output on providers that support it, and its error setting decides per-chunk failure behaviour — whether one malformed extraction kills the run, or gets skipped and logged. Fourth, a writer persists everything, batching a thousand rows at a time by default.

Read that chain again and you'll see something familiar: it's your Week 2 ingestion pipeline with one component swapped. Split, embed, store — but between "embed" and "store" now sits an LLM doing information extraction, upgrading a pile of chunks into a network of entities. That framing matters for cost conversations too: the extractor is an LLM call per chunk, which makes index-time the expensive phase. You pay it once per corpus, not once per query — but you should be able to estimate it before you run it.

Index time · quality control

Schema guardrails and entity resolution

Left unguided, an LLM extractor will happily invent forty entity types and a zoo of one-off relationships — a graph that is technically populated and practically useless. The pipeline takes a schema for exactly this reason. You pass the node types, the relationship types, and the allowed patterns between them, written as triples such as ("Person", "PARENT_OF", "Person"). Turn off the flag that permits additional node types and the pipeline rejects anything outside the schema instead of letting the graph drift. Skip properties on a type and a name property is added automatically, so every entity is at least addressable. This is yesterday's modeling lesson operationalized: the schema you designed on the whiteboard becomes the contract the extractor is held to, chunk after chunk.

The second quality problem is subtler. Chunk 12 mentions "Acme Corp", chunk 87 says "Acme Corporation", chunk 203 says "ACME" — and a naive pipeline writes three disconnected nodes, quietly shattering the connectivity that makes graph retrieval worth anything. The fix is an entity resolution pass after writing, and the package ships a ladder of resolvers: exact match on a single key property, semantic similarity of names, and a fuzzy matcher for the typo-and-abbreviation middle ground. Which rung you pick is a precision-versus-recall trade you should make consciously — over-merging is as destructive as under-merging, because fusing two genuinely different "J. Smith"s poisons every traversal that passes through the merged node.

The FDE habit here: inspect the graph before you build retrieval on it. A handful of Cypher spot-checks — how many entity types actually got created, which entities have suspicious duplicate near-names, what the degree distribution looks like — catches extraction drift on day one instead of after the demo.

The two-layer graph

Lexical graph vs entity graph — you need both

Here is the single most load-bearing design idea of the day. When SimpleKGPipeline runs with create_lexical_graph=True, it doesn't build one graph — it builds two coexisting layers in the same database.

The lexical graph preserves the documents themselves: document and chunk nodes, wired together by relationships recording which chunk came from which file and what the reading order was. Its embeddings live on the chunk nodes. This layer is the model's evidence locker — the actual source text, structure intact, that a grounded answer quotes from. The entity graph is the schema-pruned domain layer the extractor produced: people, systems, incidents, whatever your schema named, connected by typed relationships. It is the map of what the corpus is about, abstracted away from any single passage.

Why insist on both? Because each one alone reproduces a failure you've already met. Entity graph only, and you can traverse beautifully but you've thrown away the source text — answers float free of quotable evidence, which is exactly the hallucination-adjacent behavior Week 1 taught you to fear. Lexical graph only, and you're back to Week 2: chunks and similarity, with no structural way to hop from a retrieved passage to the related facts two documents away. The magic is in the connections between the layers: entities link back to the chunks that mention them, so retrieval can enter through one layer and harvest from the other. Find a chunk by vector similarity, hop to the entities it mentions, walk the entity graph to related entities, then collect their source chunks — text the query's embedding would never have surfaced, but the graph knows is relevant.

That two-layer hop is the entire mechanical basis of "hybrid vector + graph retrieval." Which brings us to query time.

Query time · retrieval

The retriever ladder: vector entry, graph expansion

The package expresses query-time strategy as a family of first-party retrievers, best understood as a ladder where each rung adds one capability:

  • Vector retriever — the floor: pure similarity search over chunk embeddings. Your Week 2 pipeline, living inside Neo4j.
  • Vector-plus-Cypher retriever — the day's headline. Vector search finds the entry chunks, then a graph traversal you write runs from each hit to enrich the result with connected-node context. The cross-layer hop from the last section, made concrete in one class.
  • Hybrid retriever — widens the entry point instead: it searches a vector index and a full-text index at once and merges the results, so exact keywords such as error codes, product names or statute numbers cannot slip past a purely semantic match.
  • Hybrid-plus-Cypher retriever — both upgrades together: hybrid entry, then traversal.
  • Text-to-Cypher retriever — steps off the ladder entirely. An LLM translates the question into a graph query, executes it, and returns structured results, with a guardrail that validates generated queries before execution to block destructive operations.

Two composition notes that matter in real engagements. A tools retriever exposes several retrievers to an LLM as tools, letting it pick per query and combine results with attribution — Week 3's tool-routing pattern applied to retrieval. And the external-store retrievers for Qdrant, Weaviate and Pinecone run vector search in an outside vector database and map the hits back to Neo4j nodes, so a client's existing vector-database investment composes with the graph rather than competing with it.

Generation, after all that machinery, is one class: you construct a GraphRAG object with a retriever and a model, then call search with your question and a retriever configuration. The retriever fetches context, the model answers against it, and asking it to return the context hands you the evidence for citation and for evaluations.

Index time · the corpus-level index

Communities and their summaries: a table of contents the LLM wrote

Now back to the two Microsoft indexing stages we parked earlier, because they're the part of GraphRAG that answers the question this whole day opened with. Once the entity graph exists, the Leiden algorithm partitions it into hierarchical communities — clusters of entities that are densely connected to each other and sparsely connected to everything else. Hierarchical is the key word: small tight communities nest inside larger ones, level by level, so the corpus gets organized at multiple resolutions at once — like sections nesting inside chapters.

Then comes the insight that makes global questions tractable: for every community, at every level, the pipeline pre-generates a summary, bottom-up — leaf communities are summarized from their entities and relationships, and parent communities are summarized from their children's summaries. The result is a corpus-level semantic index: a layered, LLM-written table of contents describing what every neighborhood of the graph is about, sitting there before any user asks anything.

Spot the trade, because it's the same one you've been making all program — spend tokens at index time to save capability at query time. Community summarization is a pile of LLM calls you pay once per corpus build. In exchange, "what are the major themes?" stops being an impossible retrieval problem and becomes a reading problem over a few dozen pre-written summaries. When a client balks at GraphRAG's indexing bill, this is the sentence: you are pre-paying for the questions vector RAG can't answer at any price. And when their corpus is genuinely all lookup traffic — no sensemaking questions in sight — that same sentence tells you they may not need this layer at all. The pipeline is a menu, not a mandate.

Query time · modes

Local vs global search: match the mode to the question's shape

Microsoft's reference library ships four query modes — Global, Local, DRIFT, and Basic — and the local/global pair is the vocabulary you'll use for the rest of your career to sort questions into retrieval strategies.

Local search is entity-centric, for questions about specific things: "what happened with the Meridian outage?" It embeds the query and matches it against entity description embeddings — entering the graph through entities, not chunks. From those access points it fans out to connected entities, relationships, covariates, community reports, and the associated raw text chunks, then the candidates are "prioritized and filtered to fit within a single context window." Hear the echo of Week 1? Even the fanciest graph retrieval terminates in the same finite window, and the last step is always triage.

Global search is for the corpus-shaped questions from the top of the reading, and it never touches individual entities at all — it runs map-reduce over the community reports. Map: chunk the community reports, and have the LLM produce intermediate answer points from each batch, each with a numerical importance rating. Reduce: filter to the top-rated points and aggregate them as context for the final answer. The dial is which community hierarchy level you read from — lower levels mean more detailed reports, better answers, and more LLM calls. That's a literal cost/quality knob you can quote in a proposal. DRIFT blends the two — entity-centric local search with community context folded in — and Basic is plain vector similarity, kept around as the baseline (and as a quiet reminder that the baseline is sometimes enough).

The milestone, assembled: the ingestion pipeline loads your corpus into the two-layer graph on yesterday's Neo4j instance; a vector index goes over the chunk embeddings; a Cypher-enriched retriever — hybrid, if exact keywords matter — does the retrieval; and the generation class produces grounded answers. Local versus global is the frame for explaining why the graph hop earns its complexity over Week 2's pure-vector approach.

FDE mindset

GraphRAG is not "better RAG" — it's more RAG: an indexing bill, a schema to govern, resolvers to tune, and two retrieval layers to keep healthy. The FDE move is to ask what shape of question the client actually has. Lookup questions? Week 2's pipeline is cheaper and simpler. Sensemaking questions across a corpus — or answers that must follow relationships the text never states in one place? Now the graph earns its keep. Recommending the simpler system when it suffices is what makes the client trust you when you recommend the complex one.

Deep dive: versions, Text2Cypher guardrails & index-time cost

Optional. ~10 minutes. The production edges of today's pipeline.

Pin your versions. As of 2026-07-01 the Neo4j package neo4j-graphrag is at 1.18.0, released 2026-06-24, supporting Neo4j 5.18.1 and above, Aura 5.18.0 and above, and Python 3.10 through 3.14. On Neo4j 2026.01 and later the package auto-detects the server and uses the newer Cypher search clause for vector queries. Microsoft's reference GraphRAG library is at v3.1.0. The Neo4j package replaced a now-deprecated predecessor — if a client codebase still imports the old name, that is a migration item, not a style nit.

Text2Cypher is powerful and sharp. An LLM writing Cypher against production data can also write destructive Cypher. Since 1.16.0 the package validates generated queries before execution to block destructive operations — but treat that as one layer, not the whole answer: run Text2Cypher through a read-only database user, and log every generated query for review. Related hardening: 1.15.0 added schema constraint alignment (EXISTENCE/KEY), so the graph the LLM queries actually honors the schema you promised it.

Worked sketch — where the index-time money goes
  • Chunking & embedding: cheap — embedding-model rates, one pass over the corpus
  • Entity/relation extraction: one LLM call per chunk — the dominant line item
  • Entity resolution: cheap-to-moderate depending on resolver (exact match ≈ free; semantic match costs compute)
  • Community summarization: LLM calls per community, per hierarchy level — second-biggest line

So the estimate a client actually wants is: (number of chunks × extraction cost) + (number of communities × summary cost), paid per corpus build. Query-time cost then rides on which retriever and, for global search, which community level you read — lower levels = more detail = more map-reduce calls. Same Week 1 arithmetic, bigger stage.

When vectors live elsewhere. The external-store retrievers (QdrantNeo4jRetriever and friends) mean "adopt GraphRAG" never has to mean "migrate the vector DB": vector search runs where the embeddings already are, and hits map back to Neo4j nodes for the graph hop.
